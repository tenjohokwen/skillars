# Story 12.4: Coach-Facing Player-Detail Page

Status: done

## Story

As a coach,
I want to click through from my player roster into a single player's full development history — their timeline, their neglected skills, and how much of their recent progress came from training with me versus other coaches,
so that the roster becomes a real relationship view instead of a dead-end list, with the same richness of history a parent already sees today.

## Acceptance Criteria

1. **`SluTargetService.getNeglectedSkills` gains the same coach-player relationship check `SluDashboardService`'s three methods already have, mirroring that exact pattern.** Add `private final SecurityUtil securityUtil;` and `private final PlayerProfileRepository playerProfileRepository;` to `SluTargetService` (it already has `CoachPlayerAuthorizationService` injected for `getTargets`/`setTargets`, `SluTargetService.java:23`). Add a private `requireCoachPlayerRelationshipIfCoach(Long playerId)` helper byte-for-byte equivalent to `SluDashboardService.java:132-138`'s, and call it as the first line of `getNeglectedSkills(Long playerId)` (`SluTargetService.java:52-58`). **Do not** change `getNeglectedSkills`'s signature to take an explicit `coachId` parameter the way `getTargets`/`setTargets` do — those two are coach-only endpoints (`SluTargetResource` is `@PreAuthorize(SecurityConstants.HAS_COACH_ROLE)` with no ownership-guard alternative); `/neglected-skills` is dual-access (`NeglectedSkillResource.java:22`: `hasRole('ROLE_COACH') or @playerOwnershipGuard.check(...)`), so it needs the same self-resolving-from-SecurityContext shape `SluDashboardService` uses, not the controller-passes-coachId shape `SluTargetResource` uses for its other two endpoints (see Dev Notes "Why `getNeglectedSkills` doesn't take an explicit `coachId` like its two siblings"). `NeglectedSkillResource.java` itself needs **zero changes** — exactly like `SkillExposureResource.java`'s three already-fixed sibling endpoints, which also pass no `coachId` from the resource layer.
2. **`SluContributionService.getCoachContributions` gains the identical check.** Add `CoachPlayerAuthorizationService`, `SecurityUtil`, and `PlayerProfileRepository` to `SluContributionService`'s constructor (currently only `SluRepository` and `CoachProfileService`, `SluContributionService.java:28-29`). Add the same private `requireCoachPlayerRelationshipIfCoach(Long playerId)` helper, call it as the first line of `getCoachContributions(Long playerId, Instant since)` (`SluContributionService.java:35`). `SkillExposureResource.java` needs zero changes here either.
3. **Both fixes must not break existing parent/player access, and must preserve the helper's second, coach-is-also-parent exemption branch — not just its first.** `requireCoachPlayerRelationshipIfCoach` (`SluDashboardService.java:132-138`) is a **two-condition** guard: it only invokes `coachPlayerAuthorizationService.requireCoachPlayerRelationship(...)` when **both** (a) `securityUtil.isCurrentUserInRole(AuthoritiesConstants.COACH)` is true **and** (b) `!playerProfileRepository.existsByIdAndParentId(playerId, securityUtil.requireCurrentUserId())` — i.e. the caller is a coach *and* is not also this specific player's registered parent. For a plain parent/player caller, condition (a) is false and the check never runs at all; `@playerOwnershipGuard.check(...)` at the `@PreAuthorize` layer remains the only gate for them, completely unchanged. For a coach who is *also* the player's own parent, condition (b) is false and the relationship check is skipped even though they hold `ROLE_COACH` — this is why `PlayerProfileRepository` is in the dependency list at all, and the "byte-for-byte equivalent" helper (AC1/AC2) must copy both conditions, not only the first. **Pre-existing, out-of-scope adjacent gap (do not fix here):** the exemption checks only `existsByIdAndParentId`, not the `existsByIdAndUserId` branch `PlayerOwnershipGuard.java:33-34` was separately fixed to add (`skillars-deferred-147`) — so a self-registered adult player who also somehow held `ROLE_COACH` would be wrongly 403'd on their own profile by this helper. Confirmed not currently triggerable (`CoachRegistrationService.java` grants exactly one role-bearing authority at account creation, with no production path to add a second), and the same incomplete predicate already exists unfixed in `RadarDisplayService.java:46` and `ReportGenerationService.java:231` — this story copies the existing (incomplete but currently-safe) pattern verbatim rather than silently fixing it in one of its three now-four copies.
4. **New read-only coach page at `coach/players/:playerId`** (route name `coach-player-detail`, component `pages/coach/CoachPlayerDetailPage.vue`, `meta: { requiresAuth: true, requiresCoach: true }` — the exact convention already used by the roster route at `routes.js:163-167`) assembling, per Converge #12, exactly three pieces and nothing else: (a) `PlayerTimelinePanel.vue` **unchanged**, imported and used exactly as `ParentDevelopmentPortalPage.vue:97/114` already does; (b) `CoachContributionSection.vue` **unchanged**, fed by `store.coachContributions` after calling `store.fetchCoachContributions(playerId)`, exactly as `ParentDevelopmentPortalPage.vue:62/112/159` already does; (c) a neglected-skills section built from the **already-fetched** `store.neglectedCodes`/`store.exposure` (via `store.fetchExposure(playerId)`) and `store.skillDefinitions` (via `store.fetchSkillDefinitions()`) — reusing `ParentDevelopmentPortalPage.vue:131-135`'s own `neglectedSkillNames` code-to-display-name mapping pattern — **not** a new component and **not** a call to `/neglected-skills` (see Source). Do not add the Skills Radar, the exposure bar chart, the session-pack tracker, or the Performance Reports panel — none of those are part of Converge #12's scope, and adding them would be scope creep into a parent-only feature set.
5. **The player's display name is passed through from the roster, not re-fetched — and `playerId` itself must be read and forwarded as a raw string, never coerced to a `Number`.** `MyPlayersPage.vue`'s player rows become clickable (currently a dead-end list — confirmed via its template, no `@click`/`to`/`router-link` anywhere today), navigating to `{ name: 'coach-player-detail', params: { playerId: player.playerId }, query: { playerName: player.playerName } }`. The new page reads `route.query.playerName` for its heading, falling back to a generic `coach.playerDetailUnknownPlayerName` string if absent (e.g. a coach bookmarks/shares the URL directly) — this mirrors `SessionPrepCard.vue`'s own precedent of taking `playerName` from the parent's already-available data rather than adding a new fetch (established by `skillars-12-3`'s AC5/Task 4.3, not Task 4.2 as an earlier draft of this story misattributed — Task 4.2 additionally specified a `playerId` prop `skillars-12-3`'s own code review later deleted as dead), just via route query instead of a prop since the parent here is a different route, not a parent component. **`playerId` itself must be read from `route.params.playerId` and passed to every API call as-is (a string), never wrapped in `Number(...)`.** `CommonConfig.java:48-49` deliberately serializes `Long` player ids as JSON strings specifically because they are backend Tsids (18–19 digits), past `Number.MAX_SAFE_INTEGER` — converting one back to a `Number` silently corrupts it. This is not a hypothetical: it is a **twice-fixed production bug** on the two existing player-detail-style pages this story's own page is modeled on (`skillars-deferred-148` on `ParentDevelopmentPortalPage.vue`, mirroring an identical `skillars-deferred-147` fix on `PlayerDevelopmentDashboardPage.vue`), both documented in-file at the top of their own specs. Do not reintroduce it a third time here.
6. **The page must not crash or render a blank screen if any of its three data calls 403s**, and must surface a user-visible, **translated** error rather than an unhandled console error, hardcoded English, or a raw untranslated i18n key. This is not a hypothetical: `skillars-12-1`'s own deferred-work.md entry ("Roster membership is wider than the `development` module's own authorization predicate") already documents that `ROSTER_MEMBERSHIP_STATUSES` (**12** statuses — re-counted against `CoachRosterService.java:53-56` at drafting time; an earlier draft of this story, and the `deferred-work.md` entry it quoted, both understated this as 10) is wider than `CoachPlayerAuthorizationService.ACTIVE_RELATIONSHIP_STATUSES` (4) by **8** statuses, not 6: `NO_SHOW_PLAYER`, `NO_SHOW_COACH`, `PAYMENT_PENDING`, `IN_PROGRESS`, `PAUSED`, `COMPLETED_PENDING_CONFIRMATION`, plus `DISPUTED` and `REFUND_PENDING` (added by `skillars-12-1`'s own code-review owner decision, `CoachRosterService.java:47-52`, on the grounds that both "represent a session that genuinely happened"). So a roster row can legitimately exist (and now, for the first time, be clickable per AC5) for a coach-player pair whose only booking sits in one of these eight wider statuses, which this story's own AC1/AC2 fixes will now correctly 403 on `/neglected-skills` and `/slu/coach-contributions` for that exact pair (where they previously silently 200'd with wrong/empty data) — `DISPUTED`/`REFUND_PENDING` pairs are precisely among the ones a coach is likeliest to click into, since they were deliberately kept on the roster as "genuinely happened" sessions. This story does **not** fix that underlying roster-membership-vs-relationship-check mismatch (that remains `skillars-12-1`'s own flagged, separate follow-up) — it only ensures the detail page degrades gracefully when it is hit. **The error banner's text must actually resolve to something readable.** Both `store.error` and `store.coachContributionsError` are currently populated from `err?.response?.data?.message` (`development.store.js:65`, `:227`) — but this backend's error body (`ErrorDto.java`) has no top-level `message` field at all; the real text lives at `err.response.data.errorMsg.message`, exactly as `boot/axios.js:228`'s own 403-logging branch already reads it. As written today this means the aggregated `pageError` is always either the hardcoded string `'Failed to load skill exposure'` or the literal, un-interpolated key `'development.portal.contributionsLoadError'` — never a real, translated message, for *any* caller of `ParentDevelopmentPortalPage.vue` too, not just this new page. This story must fix both `fetchExposure`'s and `fetchCoachContributions`'s catch blocks in `development.store.js` (Task 4.0) to read `err?.response?.data?.errorMsg?.message` first, falling back to a translated default (not hardcoded English, not a raw key) only when that is also absent.
7. **A player-to-player navigation while already on the detail page must not silently show the previous player's data under the new player's name or identity.** Two independent problems, both real:
   - `PlayerTimelinePanel.vue` fetches only in `onMounted` (`PlayerTimelinePanel.vue:100-103`) with no watcher on its `playerId` prop — confirmed by reading the file — so simply changing the route param while Vue Router reuses the existing component instance (its default behavior for a param-only navigation on the same route) would leave the previous player's timeline on screen. **Fix in the new page, not in `PlayerTimelinePanel.vue` itself** (out of scope to patch a shared component's lifecycle behavior for one new caller): bind `:key="playerId"` on the `<PlayerTimelinePanel>` usage so a `playerId` change forces a clean remount.
   - **The `:key` fix does *not* cover the page's own two store-backed sections, and this is the one this story must not under-scope.** `development.store.js`'s `exposure`/`coachContributions` refs are app-lifetime Pinia state that is **only ever overwritten on a successful fetch** — the existing `fetchExposure`/`fetchCoachContributions` implementations clear only their own error ref before each call, never the data ref. Concretely, on a route-param-only navigation (same route, no remount) from Player A to Player B, the heading repaints "Player B" synchronously from `route.query.playerName` while the neglected-skills list and `<CoachContributionSection>` keep rendering **Player A's** data for the entire in-flight round trip — and if Player B's fetch then 403s (exactly AC6's own wider-roster-status scenario), those sections **never update at all**, leaving Player A's neglected skills and contribution breakdown on screen indefinitely, mislabeled as Player B's, next to the error banner. This is a cross-player data-misattribution, not a cosmetic flash, and the `:key`/`watch` mechanism alone does not touch it. Required fix (Task 4.0): `fetchExposure` and `fetchCoachContributions` must each reset their own data ref (`exposure.value = null` / `coachContributions.value = []`) **synchronously, before** issuing the request — not only on success — so a player switch always starts from a clean slate and the page's existing loading/empty-state handling (not stale old data) covers the gap until the new data (or an error) arrives.
   - Related, lower-severity defect in the same code fixed in the same pass (Task 4.0): `fetchExposure` has no in-flight sequence guard at all, unlike `fetchCoachContributions`'s existing `_coachContributionsSeq` pattern (`development.store.js:212-234`). A rapid A→B→A round trip (double-click, or back/forward on the roster) can let an in-flight request for an *earlier* player resolve *after* a later one, silently overwriting fresh data with stale data — add the same per-field sequence-number guard to `fetchExposure` that `fetchCoachContributions` already has.
   - The page's own `store.fetchExposure`/`fetchCoachContributions` calls must be re-triggered on a `playerId` change via a `watch(() => route.params.playerId, ...)`, mirroring `ParentDevelopmentPortalPage.vue:171-176`'s existing watcher.
8. All new user-facing strings are externalized via i18n in `en-US`, `de-DE`, and `fr-FR`, under a new `coach.playerDetail*` prefix inside the existing shared `coach` namespace (e.g. `coach.playerDetailTitle`, `coach.playerDetailUnknownPlayerName`, `coach.playerDetailNeglectedSkillsTitle`, `coach.playerDetailNoNeglectedSkills`, `coach.playerDetailNoContributions`, `coach.playerDetailError`, `coach.playerDetailBackToRoster`), following the `coach.myPlayers*`/`coach.sessionPrep*` flat-key convention already established (`en-US/index.js:246-264`). AC6's fix means `coach.playerDetailError` must actually be the string the banner renders, not a key the banner never reaches (see AC6).

The new page must wrap `<CoachContributionSection>` in its own section with a heading and a `v-else`/fallback empty state (`coach.playerDetailNoContributions`) at the page level — matching the treatment the neglected-skills section already gets — rather than relying on the child component's own silent-collapse behavior. (This story does not change `CoachContributionSection.vue`'s own selection/filtering logic — only adds a wrapper around it; see "Explicitly out of scope.")

## Dev Notes

### Why `getNeglectedSkills` doesn't take an explicit `coachId` like its two siblings in the same service

`SluTargetService` already has two methods, `getTargets`/`setTargets`, that take an explicit `UUID coachId` resolved by their resource (`SluTargetResource.java:35,45`: `coachProfileService.getCoachIdByUserId(securityUtil.getCurrentCoachUserId())`), because `/targets` is a coach-only endpoint (`SluTargetResource` is `@PreAuthorize(SecurityConstants.HAS_COACH_ROLE)` with no alternative). `/neglected-skills`, by contrast, is dual-access (`NeglectedSkillResource.java:22`: `hasRole('ROLE_COACH') or @playerOwnershipGuard.check(...)`) — a parent/player calls the exact same method with no coach identity to resolve at all. `SluDashboardService`'s three methods face the identical dual-access shape (`SkillExposureResource.java`'s `@PreAuthorize` lines are all the same `hasRole('ROLE_COACH') or @playerOwnershipGuard...` pattern) and solve it by resolving from the request's own `SecurityContext` inside the service (`securityUtil.isCurrentUserInRole`, `securityUtil.getCurrentCoachUserId()`), only when the caller actually is a coach. This story follows that precedent exactly rather than widening `getNeglectedSkills`'s signature, so `NeglectedSkillResource` (and `SkillExposureResource`, for Task 2) need zero changes — the fix is entirely inside the two service classes.

### Why the new neglected-skills panel doesn't call `/neglected-skills`

Confirmed via `grep -rn "neglected-skills" src/frontend` that no frontend code calls the dedicated endpoint today; `development.store.js:46`'s `neglectedCodes` computed already derives the same information from `SkillExposureResponse.neglectedSkillCodes` (`SluDashboardService.getWeeklyExposure`, `SluDashboardService.java:78-83`, populates it from the same `NeglectedSkillFlagRepository.findByPlayerIdAndResolvedAtIsNull` call `SluTargetService.getNeglectedSkills` makes independently — two code paths, same underlying data). Since this page already calls `fetchExposure` for the exposure/neglected data, adding a second call to the dedicated endpoint would be a redundant round-trip for identical data. The dedicated endpoint is still fixed in Task 1 because it is a real, independently reachable production API regardless of which path any particular UI takes — the deferred-work.md item is about the endpoint's authorization, not about which frontend surface happens to call it.

### Residual risk: the roster-membership-vs-relationship-check mismatch becomes visible for the first time

`skillars-12-1`'s own code review flagged that `CoachRosterService`'s `ROSTER_MEMBERSHIP_STATUSES` (**12** statuses: `ACCEPTED`, `PAYMENT_PENDING`, `CONFIRMED`, `UPCOMING`, `IN_PROGRESS`, `PAUSED`, `COMPLETED_PENDING_CONFIRMATION`, `COMPLETED`, `NO_SHOW_PLAYER`, `NO_SHOW_COACH`, `DISPUTED`, `REFUND_PENDING` — re-counted against `CoachRosterService.java:53-56` during this story's pre-implementation review; an earlier draft, and the `deferred-work.md` entry it quoted, both said 10) is deliberately wider than `CoachPlayerAuthorizationService.ACTIVE_RELATIONSHIP_STATUSES`'s 4 (`ACCEPTED`, `CONFIRMED`, `COMPLETED`, `UPCOMING`) by **8** statuses, not 6 — the six originally named plus `DISPUTED` and `REFUND_PENDING`, both added by `skillars-12-1`'s own code-review owner decision (`CoachRosterService.java:47-52`) specifically because they "represent a session that genuinely happened," which makes them more, not less, likely for a coach to click into. Before this story, that mismatch was latent for `/neglected-skills`/`/coach-contributions` specifically, because neither endpoint checked the relationship at all — a coach whose only booking sat in one of the eight wider statuses got a (wrong, empty-ish) 200 rather than a 403. After this story, the same pair gets an honest 403, surfaced through this new page's AC6 error banner for the first time via a path a coach can actually click into. This is **more correct than before** (an honest error beats a silently-wrong 200), but it is a new, real UX edge case this story's own existence creates visibility for.
