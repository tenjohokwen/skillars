## Story

As the platform owner,
I want a coach's block-out create/delete to be protected by the same per-coach lock the availability-window CRUD methods already have, a video-account-deletion cascade to actually run each deletion in its own transaction as its own doc comment already claims, and a downgraded coach's stale branding to stop being served from their own settings view,
so that the check-then-act race window this codebase has now flagged three times on `addBlock`/`deleteBlock` is finally closed, `cascadeDeleteForAccount` gets the atomicity guarantee it already promises instead of silently not having it, and `GET /api/development/coaches/me/branding` stops disagreeing with `PUT`'s own tier gate on the exact same row.

## Acceptance Criteria

1. **Give `AvailabilityService.addBlock`/`deleteBlock` the same per-coach pessimistic lock `addWindow`/`updateWindow`/`deleteWindow` already have (`skillars-deferred-78` AC1).** This is a mechanical follow-on flagged three separate times without ever being picked up: `skillars-deferred-78` AC1's own scope note ("out of scope; the deferred item and the batch re-check both concern windows only"), `skillars-deferred-79`'s Dev Notes ("straightforward mechanical follow-on... flag for a future story only if observed in practice"), and `skillars-deferred-79`'s own code review (two deferred findings: "Race Condition in addBlock() Check-Then-Act Window" and "Missing Pessimistic Lock on Booking Overlap Check in addBlock()"). All three ledger entries describe the identical gap and the identical fix.

   - `AvailabilityService` already has the exact helper this AC needs — `private CoachProfile lockProfile(UUID coachId)` (`AvailabilityService.java:298-305`) — acquires `coachProfileRepository.findByIdForUpdate(coachId)` under `lockRetryer.withBoundedRetry(...)` then `entityManager.refresh(c, LockModeType.PESSIMISTIC_WRITE)`, mirroring `BookingService`/`BookingBatchService`/`RescheduleService`'s own per-coach lock. `addWindow`/`updateWindow`/`deleteWindow` already call it (`AvailabilityService.java:253-289`) right after the unlocked `requireProfile` resolves the coach by userId — same shape this AC needs, no new lock helper to write.
   - **`addBlock`** (`AvailabilityService.java:307-330`): after `CoachProfile profile = requireProfile(userId);`, add `CoachProfile lockedProfile = lockProfile(profile.getId());` and use `lockedProfile.getId()` everywhere `profile.getId()` is currently used (the `findOverlappingBookings` call and `block.setCoachId(...)`) — same substitution `addWindow` already makes for `window.setCoachId(lockedProfile.getId())`. This closes both deferred-79 code-review findings at once: the lock now covers the check-then-act window between the overlap check and the block save (the "Race Condition" finding) and the overlap check itself now runs against a coach row this transaction holds locked (the "Missing Pessimistic Lock" finding) — they are the same gap from two angles, not two fixes.
   - **`deleteBlock`** (`AvailabilityService.java:332-338`): same substitution — resolve `lockedProfile` via `lockProfile(profile.getId())` after `requireProfile`, then use `lockedProfile.getId()` in the `blockRepository.findByIdAndCoachId(blockId, ...)` call. Mirrors `deleteWindow`'s exact shape (`AvailabilityService.java:282-289`) — no behavior change to the not-found path (`ResourceNotFoundException`/`OperationNotAllowedException` semantics are unchanged, only the row read is now locked).
   - **Do not change `addBlock`'s existing overlap-then-save ordering or error codes.** This AC only adds the lock around the existing check; `BLOCK_OVERLAPS_BOOKING` (`skillars-deferred-79` AC2) is unaffected.
   - **Confirmed the coach-row-deleted-mid-call race is not a new failure mode (story-review edge case, resolved)**: if the coach is deleted between `requireProfile` and the new `lockProfile` call, `lockProfile`'s own `findByIdForUpdate` returns empty and throws `ResourceNotFoundException` — correctly failing the operation instead of proceeding against stale data. `addWindow` has had this identical exposure since `skillars-deferred-78` AC1 shipped (`AvailabilityService.java:253-255`); this AC does not introduce a new one.
   - **Confirmed no cross-coach interference in the lock's coverage (story-review false-positive check)**: the lock is per-`coachId`, and both the overlap check (`findOverlappingBookings`) and the block save are scoped to that same `coachId` — a concurrent operation against a *different* coach's row is entirely unaffected, and no other coach's booking/window/block state could ever race this check regardless.
   - Test: `AvailabilityServiceTest`'s three existing `addBlock_...` tests (`addBlock_overlapsActiveBooking_throwsBlockOverlapsBooking`, `addBlock_noOverlappingBooking_succeeds`, `addBlock_overlappingBookingInTerminalStatus_doesNotBlock`, lines 926-988) each currently stub only `coachProfileRepository.findByUserId(...)` — once the lock lands they will fail (the lenient `lockRetryer.withBoundedRetry` stub already in `setUp()` calls straight through, so `coachProfileRepository.findByIdForUpdate(coachId)` returning empty by default throws `ResourceNotFoundException` before the test's own assertion runs). Add `when(coachProfileRepository.findByIdForUpdate(coachId)).thenReturn(Optional.of(profile));` to all three, mirroring `updateWindow_overlappingConfirmedBooking_returnsHasConflictTrue`'s existing stub pair (`AvailabilityServiceTest.java:107-108`).
   - **`deleteBlock` has no existing test at all — add one.** `deleteBlock_ownedByCallingCoach_succeeds`: stub `findByUserId`/`findByIdForUpdate` (same pair as above), `blockRepository.findByIdAndCoachId(blockId, coachId)` returning a block owned by that coach, call `service.deleteBlock(userId, blockId)`, and `verify(blockRepository).delete(block)`. This is new coverage, not a regression fix — closes the pre-existing gap that `deleteBlock` had zero tests before this story.

2. **Fix `VideoDeletionService.cascadeDeleteForAccount`'s false transactional-isolation doc comment.** `cascadeDeleteForAccount` (`VideoDeletionService.java:145`) is deliberately NOT `@Transactional` at the method level, with a doc comment claiming "each deleteVideo() runs in its own transaction" — but it calls `deleteVideo(video.getId(), LifecycleTrigger.ACCOUNT_DELETION, true)` (`VideoDeletionService.java:158`) as a plain same-class call, which resolves to `this.deleteVideo(...)` and bypasses `deleteVideo`'s own `@Transactional` proxy entirely. This is the identical self-invocation pitfall already fixed twice elsewhere in this codebase: `RadarCompositeCalculationService.onRadarEntrySubmitted` (`RadarCompositeCalculationService.java:46-62`) and `TimelineEventListener`'s own field (referenced in the same comment). Found during `skillars-deferred-77`'s full-module regression sweep, deferred as out-of-scope for that story.

   - Add `@Autowired @Lazy private VideoDeletionService self;` to `VideoDeletionService`, mirroring `RadarCompositeCalculationService.java:50-52` exactly (same two annotations, same field-injection shape — `@Lazy` breaks the circular-bean-creation problem a constructor-injected self-reference would otherwise cause).
   - In `cascadeDeleteForAccount`, change the `deleteVideo(video.getId(), LifecycleTrigger.ACCOUNT_DELETION, true)` call (line 158) to `self.deleteVideo(...)` — this now goes through the Spring proxy, so each call genuinely gets its own transaction, making the method's own doc comment true instead of aspirational.
   - Do not change `deleteByUser` (line 134) or the two-arg `deleteVideo` overload (line 95) — both already call `deleteVideo` from a *different* public entry point (`deleteByUser`, `deleteVideo(id, trigger)`), and Spring's proxy is only bypassed by a call from **inside** the same bean; `deleteByUser`'s own `@Transactional` on itself is a separate, correctly-proxied entry that already gets one transaction for the whole method (its own single-video scope means one transaction is the intended behavior there, not a bug).
   - **Precise mechanism for why `deleteByUser`/the two-arg overload don't need this fix (story-review edge case, resolved)**: their own internal `deleteVideo(...)` call is *also* same-class and *also* bypasses `deleteVideo`'s own proxy — but it doesn't matter, because `deleteByUser`/the two-arg overload are each themselves `@Transactional` and called from *outside* the bean, so a transaction is already open on the thread by the time the internal call runs; `deleteVideo`'s body simply joins that already-open transaction (default `REQUIRED` propagation) rather than needing its own. `cascadeDeleteForAccount` is the only one of the three internal callers with no ambient transaction to join at all, which is exactly why it — and only it — needs the `self.` fix.
   - **Confirmed concurrent calls through the proxy are independent transactions, not a bug (story-review false-positive check)**: `deleteVideo`'s default `REQUIRED` propagation means two concurrent external calls each get their own transaction rather than sharing one — the intended behavior for per-video isolation, unrelated to and unaffected by this AC's fix.
   - Test: `VideoDeletionServiceTest` constructs `service` via `new VideoDeletionService(...)` directly (9-arg `@RequiredArgsConstructor`-generated constructor, unchanged by this AC since `self` is a plain non-final field, not a constructor parameter). Add `org.springframework.test.util.ReflectionTestUtils.setField(service, "self", service);` to `setUp()` (`VideoDeletionServiceTest.java:46-50`) so `self.deleteVideo(...)` resolves to the same test-constructed instance instead of NPEing — this repo already uses `ReflectionTestUtils` for direct field injection elsewhere (`ReportGenerationServiceTest`, `ModerationSlaMonitorServiceTest`). All three existing `cascadeDeleteForAccount_...` tests (lines 61-96) continue to exercise the same behavior unchanged; no new test case is required since this AC is a plumbing fix, not a new behavior — the existing three tests already prove each per-video outcome (success, individual failure, empty) and would fail on the `self` NPE if the field wire-up were missing, which is suffient regression coverage.

3. **Gate `ReportGenerationService.getBranding()` by subscription tier, matching `saveBranding`'s own gate on the identical row.** `getBranding(UUID coachId)` (`ReportGenerationService.java:218-224`) unconditionally returns whatever `CoachBranding` row exists for that coachId with no tier check at all, while `saveBranding` (`ReportGenerationService.java:226-231`) throws `FeatureGatedException("development.branding", "ACADEMY")` for any non-ACADEMY coach on the same row, and `generateReport`'s own branding fetch (`ReportGenerationService.java:126-128`) is conditioned on `tier == CoachSubscriptionTier.ACADEMY` too. `getBranding` backs only `GET /api/development/coaches/me/branding` (`CoachBrandingResource.java:29-35`), a coach-self settings-view endpoint — not the report-serving path, so this is not a report-content leak (`generateReport`'s own gate already prevents that); it means a coach who downgrades from ACADEMY keeps seeing their old logo/colour as "still set" on their own branding settings page even though `saveBranding` would now reject any attempt to re-save it and `generateReport` will never use it. Confirmed via direct source read during this story's creation — the original ledger item's "served on any report request" framing was checked against the actual call graph and found not to apply; the real, narrower defect is this GET/PUT inconsistency on the coach's own settings view.

   - **Project-owner decision (2026-08-28): gate `getBranding()`, leave the existing S3 logo object untouched on downgrade.** No deletion/orphan-cleanup logic is added by this AC — the object is simply not surfaced through this endpoint once the coach falls out of ACADEMY, and re-upgrading later would restore visibility of whatever `saveBranding` last wrote for them, matching this codebase's established forward-only convention for adjacent downgrade cases (`skillars-deferred-63`'s equivalent decision, referenced in this file's own Dev Notes precedent list).
   - Add the same tier lookup `saveBranding` already does (`CoachSubscriptionTier tier = coachProfileService.getCoachSubscriptionTier(coachId);`) to `getBranding`, before the existing `brandingRepository.findById(coachId)` lookup.
   - **Do not throw `FeatureGatedException` for a non-ACADEMY tier on this GET.** `saveBranding` throwing is correct for a *write* attempt on a gated feature (the existing UX pattern this codebase's `FeatureGatedException` mapping is built around); `getBranding` backs a settings-page load that must not error just because the coach previously held a higher tier — throwing here would turn a normal page load into a hard error for every downgraded coach, forever, with no path to recover except contacting support. Instead, when `tier != CoachSubscriptionTier.ACADEMY`, return `new CoachBrandingResponse(null, null)` directly, skipping the repository lookup entirely — the coach's branding settings page renders exactly as if they had never set a logo/colour, consistent with the feature being unavailable to them.
   - When `tier == CoachSubscriptionTier.ACADEMY`, behavior is unchanged: existing `brandingRepository.findById(coachId)` lookup and signed-URL resolution logic stays exactly as it is today.
   - **Client-side response caching is out of scope (story-review edge case, resolved)**: `CoachBrandingResource.getBranding()` sets no cache-control headers today (confirmed by source read), and this AC does not add any — a client caching this coach-self, `@PreAuthorize`-gated response across a tier downgrade without re-validation would be a pre-existing client-side concern unrelated to and unintroduced by this fix, not something this AC needs to address.
   - Test: `ReportGenerationServiceTest` has zero existing coverage of `getBranding` (confirmed by source read — no `getBranding` call anywhere in the file). Add three cases: (a) `getBranding_academyTierWithSavedBranding_returnsSignedUrlAndColour` — ACADEMY tier, an existing `CoachBranding` row, asserts the response carries the signed URL and colour (mirrors this file's existing `coachProfileService.getCoachSubscriptionTier(...)` stubbing pattern, e.g. line 293); (b) `getBranding_downgradedTierWithExistingRow_returnsEmptyBrandingWithoutQueryingRepository` — non-ACADEMY tier (e.g. `INSTRUCTOR`) with a `CoachBranding` row still present in the mock repository, asserts the response is `(null, null)` **and** `verify(brandingRepository, never()).findById(any());` — this is the actual regression case, proving the fix stops surfacing stale branding rather than merely stops erroring; (c) `getBranding_academyTierNoSavedBranding_returnsEmptyBranding` — ACADEMY tier, no row, asserts `(null, null)` (pre-existing behavior, unchanged — a non-regression check).

### Architecture / conventions to follow

- **Locking pattern**: `PessimisticLockRetryer.withBoundedRetry(...)` + `entityManager.refresh(entity, LockModeType.PESSIMISTIC_WRITE)` is this codebase's one per-coach locking pattern (`BookingService.java:245-256`, extended to `AvailabilityService`'s window CRUD by `skillars-deferred-78` AC1). AC1 of this story extends it to `addBlock`/`deleteBlock` using the `lockProfile` helper that already exists — no new locking code, no new pattern.
- **Self-invocation fix pattern**: `@Autowired @Lazy private <SameClass> self;` field, then call through `self.` instead of a bare/`this.` call for any method that needs its own `@Transactional` proxy from within the same bean. Established twice already (`RadarCompositeCalculationService.self`, `TimelineEventListener`'s own field) — AC2 is the third application of the same fix, not a new pattern.
- **Feature-gating pattern**: `CoachSubscriptionTier` tier checks throw `FeatureGatedException(featureKey, requiredTier)` for a **write** attempt on a gated feature (`saveBranding`, `generateReport`). AC3 deliberately does **not** follow that pattern for `getBranding` — see AC3's own reasoning for why a settings-page GET returning an empty/default response is the correct shape here, not an exception.
- **i18n**: not touched by this story — no new user-facing error codes are introduced (AC3 returns a normal 200 with empty fields, not a new error).
- **Testing**: per `docs/validation-strategy.md`, do not run `mvn verify` locally — GitHub CI is the sole full-verification gate. Run targeted `mvn -o test -Dtest=<ClassName>` for touched classes (`AvailabilityServiceTest`, `VideoDeletionServiceTest`, `ReportGenerationServiceTest`).
