## Story

As the platform owner,
I want `BookingService`'s per-row name-lookup N+1 closed, `DrillUploadService`'s upload/delete lock widened to cover two drills that share one `videoId`, a visible notification when a drill/session video fails to load instead of a silent background refetch, and a self-registered (no-parent) player to be able to purchase a session pack instead of being limited to pay-per-session,
so that booking-list endpoints scale with row count instead of firing one extra query per row, a coach cloning a `PLATFORM` drill can no longer race a concurrent delete on the source drill into losing or double-publishing the shared video's deletion event, a coach or player sees a clear signal when a video genuinely fails rather than staring at a broken player, and a self-booking player gets full purchase-option parity with a parent-managed player.

3. **Widen `DrillUploadService`'s per-`Drill`-row lock to also cover the shared `videoId` when a `PLATFORM` drill has been cloned — closing the cross-drill half of the `Def14`/`skillars-deferred-22` TOCTOU race that `skillars-deferred-75` AC5 explicitly left open.** Confirmed live: `DrillLibraryService.cloneDrill` (`:109-142`) copies the source drill's `DrillVideoRef.videoId` verbatim into a **new** `DrillVideoRef` row keyed by the **clone's own** `drillId` (`:132-137`, `cloneRef.setVideoId(sourceRefOpt.get().getVideoId())`) — so one `videoId` can be referenced by two independent `Drill` rows, each with its own `drillId`. `DrillUploadService.initiateUpload`/`deleteVideo` both lock only `drillRepository.findByIdForUpdate(drill.getId())` (`:87-88`, `:141-142`) before their own check-then-act sequence on `drillVideoRefRepository` (`existsByVideoId`/`clearVideoId`/`setVideoId`/`upsertVideoId`) — two calls against two *different* `drillId`s that happen to share one `videoId` (e.g. `deleteVideo(sourceDrillId, ...)` racing `deleteVideo(cloneDrillId, ...)`, or either racing `initiateUpload` on the other) take two independent locks and do not serialize against each other, so both can observe `existsByVideoId(videoId) == true` before either commits its own `clearVideoId`, and neither publishes `VideoPhysicalDeletionEvent` — leaking the S3 object with zero remaining `DrillVideoRef` rows pointing at it (`refCount`, tracked by `cloneDrill`'s own `incrementRefCount` call, is not what either `initiateUpload`/`deleteVideo` actually checks — both use a fresh `existsByVideoId` scan, so this is not a `refCount`-accounting bug, it is a lock-scope gap).

   - **Lock-acquisition order**: acquire the existing `Drill`-row lock first (as both methods already do), then — only once the current `videoId` is known from the now-safely-locked `DrillVideoRef` read — acquire the `Video`-row lock via `videoRepository.findByIdForUpdate(videoId)`, inside the same `lockRetryer.withBoundedRetry(...)` block. This order (`Drill` → `Video`) must be identical in both `initiateUpload` and `deleteVideo` to avoid introducing a *new* deadlock risk between the two methods — document this explicitly with a short comment at both lock sites (mirroring this codebase's existing per-site lock-order comments, e.g. `RescheduleService.acceptReschedule`'s own).
   - **Confirmed deadlock-safe with no mutual caller (story-review assumptions, both resolved)**: `grep`-confirmed `DrillUploadService.initiateUpload`/`deleteVideo` are called from exactly one place each — `DrillUploadResource`'s two endpoint methods, one call per HTTP request, with no other method in the codebase composing a call to both (or to either twice) within one request/transaction. Even setting that aside, the `Drill → Video` order is deadlock-safe by construction regardless of caller composition: each individual call acquires **at most one** `Drill` lock and **at most one** `Video` lock, always in that order, so two concurrent calls can only ever contend by both waiting on the *same* single `Video` row (e.g. `deleteVideo(sourceDrillId)` and `initiateUpload(cloneDrillId)` racing on the shared `videoId`, each already holding its own *distinct* `Drill` row) — this is ordinary serialization on one shared resource, not a two-resource cyclic wait, which is what a deadlock requires. No scenario exists where thread A holds `Video`-X waiting for `Drill`-Y while thread B holds `Drill`-Y waiting for `Video`-X, because nothing acquires a `Drill` lock *after* a `Video` lock anywhere in this pair of methods.
