## Acceptance Criteria

1. **`MessagingService.getConversations` rejects an unrecognised `role` instead of silently treating the caller as a PLAYER.** Today (`MessagingService.java:96-138`) the branch dispatch is `if ("COACH".equals(role)) {...} else if ("PARENT".equals(role)) {...} else {...}` — the `else` at line 117 is the PLAYER path, so any role string that is not literally `"COACH"` or `"PARENT"` (a future 4th role, or a caller bug) silently gets full PLAYER handling instead of being rejected. Convert the dispatch so `"PLAYER"` is its own explicit branch and anything else throws `new OperationNotAllowedException("Caller does not hold a recognised messaging role", MessagingErrorCode.NOT_A_PARTY)` — the exact type and message `skillars-deferred-16` AC6 already uses at this class's other three exhaustive role-dispatch `switch` sites: `verifyIsParty` (`:329-348`), `resolveLastReadAt` (`:439-449`), and `updateLastRead` (`:452-463`). **Correction to this AC's own premise, found during a review pass:** there are three sibling sites in this file, not four — `ModerationResultApplier.resolveRecipient` (`platform.messaging.service`) and `AdminMessageService.resolveRecipient` (`platform.admin.service` — a different package) are a separate pair of methods in different classes, and both **deliberately return `null` instead of throwing** for a documented reason (`ModerationResultApplier.java:146-149` / `AdminMessageService.java:206-208`: throwing there would roll back an already-committed moderation/admin decision mid-transaction over what both comments call "a display concern") — do not touch those two or make them throw; they are correct as they are and out of scope for this AC. **Scope note carried over from the ledger item itself:** `MessagingResource.resolveRole` (the only caller today) is verified to always pass one of exactly `"COACH"`/`"PARENT"`/`"PLAYER"`, so this is a defense-in-depth/consistency fix, not a fix for a currently-reachable bug — do not skip it as "unreachable so low priority." It is the fourth exhaustive-dispatch site in `MessagingService` that `skillars-deferred-16` AC6's sweep should have caught but didn't; this AC completes that sweep for this file.

2. **`StripeClient.createPaymentIntent` passes an idempotency key**, mirroring the pattern `createSubscription` already uses (`StripeClient.java:64-70`, `"sub-create-" + stripeCustomerId + "-" + priceId`). `createPaymentIntent` has exactly one direct caller — `StripePaymentGateway.chargeAndCapture` (`StripePaymentGateway.java:34-73`) — which is itself called from three places: `PaymentLifecycleService` (single-booking settlement, `:205`), `PaymentLifecycleService` (batch settlement via `chargeAndCaptureForBatch`, `:326`, which just delegates to `chargeAndCapture`), and `SessionPackPaymentService.purchasePack` (`:63`). **The key must be derived from something unique per charge attempt, not from `chargeAndCapture`'s `referenceId` parameter alone.** `SessionPackPaymentService.purchasePack` passes `packTierId` as `referenceId` (`SessionPackPaymentService.java:63`) — a session-pack tier's id, which is **the same value for every parent who buys that tier**, not a per-purchase identifier. A key built naively from `referenceId` alone (e.g. `"pi-" + referenceId`) would let two different parents' pack purchases of the same tier collide on the same idempotency key, and Stripe would silently return the first parent's `PaymentIntent` for the second parent's purchase attempt. The two `PaymentLifecycleService` call sites pass a booking/batch id as `referenceId`, which *is* already purchase-unique — so the collision risk is specific to the pack-purchase path. The key must incorporate `parentId` alongside `referenceId`, not `referenceId` in isolation — `parentId` is already a direct parameter of `StripePaymentGateway.chargeAndCapture` (the method that owns `builder`/`params` right before the `stripeClient.createPaymentIntent` call), so building the key as e.g. `"pi-" + referenceId + "-" + parentId` needs no signature change anywhere in the call chain. Scoped to `createPaymentIntent` only — do not touch `createRefund` or `createSetupIntent`, the two other Stripe-SDK wrappers in this class that also lack a key; the ledger item names only `createPaymentIntent`.

3. **A fully-misconfigured feature gate (every tier disabled) no longer surfaces as `"requires tier: NONE"` — fixed in both places this bug exists.** `DrillLibraryService.resolveMinEnabledTier` (`:246-254`) returns the literal string `"NONE"` when no `CoachSubscriptionTier` has `feature.sessionBuilder.enabled.<TIER>` set to `true` — its caller, `checkSessionBuilderGate` (`:180-187`), passes that straight into `new FeatureGatedException("session_builder", resolveMinEnabledTier())`, whose constructor (`FeatureGatedException.java`) renders the message `"Feature 'session_builder' requires tier: NONE"` — a coach or API consumer reading that has no reason to believe `NONE` is anything but a broken tier name, not "this feature is currently unavailable at every tier due to misconfiguration." **`DrillUploadService.resolveMinUploadTier` (`:139-147`) is a structural duplicate of the identical bug**, found during a review pass on this story (not named by the original ledger item): same loop-over-`CoachSubscriptionTier`-returning-`"NONE"` shape, same `FeatureGatedException("drill_video_upload", resolveMinUploadTier())` call at its own gate (`checkDrillUploadGate`, `:131-137`). Fix both: distinguish "no tier is currently enabled" (a misconfiguration — each of these key sets should always have at least one tier enabled) from "you need a higher tier than yours" at the message level, and log a `WARN` in each method when it finds no enabled tier at all, since that state means the corresponding feature is unreachable for every coach regardless of subscription. Do not change either gate method's control flow (`checkSessionBuilderGate`/`checkDrillUploadGate` must still throw `FeatureGatedException` either way) — this AC is about what the returned tier value/message communicates, and adding operational visibility for the all-disabled case, not about changing when either gate fires.

4. **`SessionPlanService.buildResponse` reuses the drills `resolveMetaMap` already fetched instead of re-querying.** Every call site (`createSession`, `updateSession`, `getSession`, and the list-mapping path at `:162-163`) calls `resolveMetaMap(blocks)` (`:186-196`, which internally does `drillRepository.findAllById(uniqueIds)`) and then immediately calls `buildResponse(saved, metaMap)`, which independently re-derives the identical unique-drill-id set and calls `drillRepository.findAllById(drillIds)` again (`:222-234`) — a fully redundant DB round-trip on every read and write of a session plan. Thread the already-fetched `Drill` entities through so `buildResponse` derives its `Map<UUID, DrillResponse>` from the same fetch `resolveMetaMap` already performed, instead of querying twice. `resolveMetaMap` currently returns `Map<UUID, DrillMetadata>` (via `Drill::getMetadata`) while `buildResponse` needs `Map<UUID, DrillResponse>` (via `drillLibraryService.toResponse(...)`) — the fix needs to fetch the `Drill` entities once and derive both maps from that single result, not just delete one of the two `findAllById` calls outright. **No unit test exists for `SessionPlanService` today** (verified during a review pass on this story — `src/test` has zero references to the class); the resource-layer `SessionBuilderResourceIT` exists and exercises this code path end-to-end but does not assert on `drillRepository` invocation counts, so it cannot by itself prove the dedup happened. See Task 4 for what new coverage this AC requires.

5. **`DrillUploadService.initiateUpload` releases the old video's quota reservation when replacing a non-READY video.** Today (`:71-93`), when a drill already has a `DrillVideoRef` pointing at a video that is not `READY` (still `PROCESSING` or `FAILED`), `initiateUpload` overwrites the ref via `drillVideoRefRepository.setVideoId(drillId, resp.videoId())` (`:90`) with no release of the old reservation — unlike `deleteVideo` (`:98-118`), which checks `existsByVideoId` and publishes a `VideoPhysicalDeletionEvent` (the path that triggers quota release) before clearing a ref. The old video's reserved bytes are orphaned until the reaper eventually times them out — not the brief, accepted window `Def9` documents elsewhere in this same code-review round, but one that can persist until the reaper's cutoff. Fix: in the `existing.isPresent() && existingVideoId != null` branch, after the new upload URL is obtained, check `drillVideoRefRepository.existsByVideoId(existingVideoId)` and if `false`, publish `new VideoPhysicalDeletionEvent(existingVideoId, drillId)` — the exact two-line pattern `deleteVideo` already uses at `:114-115`. Do not touch `Def14`'s separate TOCTOU concern in `deleteVideo` (a double-publish race) — that is a different mechanism and out of scope here.

6. **Ledger hygiene in `deferred-work.md`.** Annotate every item this story closes (see **Deferred Items Closed** table) with `[CLOSED by skillars-deferred-22 ACn]` at its current ledger location once implemented.

### Review Findings

- [x] [Review][Decision] Stripe idempotency key can collide across legitimate repeat purchases by the same parent — `"pi-" + referenceId + "-" + parentId` (`StripePaymentGateway.java:69-73`) has no per-attempt/per-transaction component. `SessionPackPaymentService.purchasePack` passes the pack tier id as `referenceId`, which is stable per tier — so if the same parent buys the same tier twice within Stripe's idempotency-key retention window, the second purchase would silently reuse the first `PaymentIntent` instead of creating a new charge (the parent isn't charged the second time). Relatedly, neither new `StripePaymentGatewayTest` case actually proves AC2's own stated goal — that a *retry* of the same attempt reuses the key; the "different keys" test only varies the parent, never asserts the same call repeated by the same parent produces the *same* key. Needs a decision: should the key fold in a per-purchase-attempt component (client-supplied idempotency token, a pending-order id created before the Stripe call, etc.) so retries of the same attempt share a key while two independent purchases don't? — **Resolved (Mbah): coarse time bucket.** Key now includes a 1-minute epoch bucket (`Instant.now(ClockProvider.getClock()).getEpochSecond() / 60`), so a true retry within the same minute still dedupes (the original AC2 goal) while a later, separate purchase gets a fresh key. Two new tests added and mutation-checked: `chargeAndCapture_repeatedWithinWindow_producesSameIdempotencyKey` (freezes the clock, asserts two calls produce the *same* key — the missing retry proof the review flagged) and `chargeAndCapture_samePackTierAndParent_separatePurchaseWindow_producesDifferentIdempotencyKey` (freezes the clock 1 day apart, asserts different keys — proves the collision itself is closed). Used the codebase's existing `ClockProvider`/`TestClockProvider` pattern (`AuthService`, `TokenCreatorImpl`, `JwtManagerImplTest`) rather than inventing new test infrastructure.

- **AC3 and AC5 both touch `DrillUploadService.java`, but in unrelated methods** — AC3 fixes `resolveMinUploadTier`'s misleading-message duplicate, AC5 fixes `initiateUpload`'s orphaned-reservation gap. No interaction between the two changes; implement and test them independently. Otherwise, three of the five ACs (AC3, AC4, AC5) live in the same `platform.session.service` package but touch three different classes (`DrillLibraryService`, `SessionPlanService`, `DrillUploadService`) with unrelated root causes (a misleading error string, a redundant query, an orphaned resource) — this grouping was a deliberate selection during story creation, re-verified against current code rather than trusted from the ledger.

Don't let a reviewer flag it as "unreachable, why bother" — it's the fifth site in a sweep that only fixed four (`skillars-deferred-16` AC6), and a future second caller of `getConversations` could reintroduce the live bug silently.

- **AC3 is deliberately scoped to messaging/logging, not to changing when either gate fires.** `checkSessionBuilderGate`/`checkDrillUploadGate` must still throw `FeatureGatedException` for a coach below the required tier — this AC only fixes what a fully-misconfigured (all-tiers-disabled) state communicates in both `resolveMinEnabledTier` and `resolveMinUploadTier`, plus adds a WARN for that specific misconfiguration case in each. Do not conflate this with a broader "make the feature gate more configurable" scope.

- **AC5's downstream listener check is a "verify, don't assume" step**, not optional busywork — `deleteVideo`'s existing call to the same event constructor is proof the event handles a non-READY video safely in *that* call path, but confirm the handler itself has no state-dependent logic that assumes it's only ever called from `deleteVideo`.

- **This story touches Java only** (`MessagingService`, `StripeClient`, `DrillLibraryService`, `FeatureGatedException` possibly, `SessionPlanService`, `DrillUploadService`) plus `deferred-work.md`/`sprint-status.yaml` — no frontend, no migration, no schema change. `mvn -o test` (targeted per-AC, or a full run before marking done) is the verification bar; no `mvn -o verify`/IT run is required unless a chosen fix approach needs a real DB — use Mockito-based unit tests matching each file's established test style.
