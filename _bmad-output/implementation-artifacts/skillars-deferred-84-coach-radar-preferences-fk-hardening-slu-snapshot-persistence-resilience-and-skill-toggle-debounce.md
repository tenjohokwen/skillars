# Story skillars-deferred-84: coach_radar_preferences FK hardening, SLU snapshot-persistence resilience, skill-toggle debounce, and SkillDefinitionResource architecture compliance

Status: done

## Story

As the platform owner,
I want (1) `coach_radar_preferences` to stop leaving orphaned rows on player deletion, (2) the weekly SLU snapshot write to get the same retry/compensation protection its sibling `saveAll` call already has, (3) rapid skill-selection clicks on the radar chart to stop firing a PUT per click, and (4) `SkillDefinitionResource` to stop bypassing the service layer every other resource in this module uses,
so that four real, previously-picked-up-but-left-open findings from the `skillars-5-1` through `skillars-5-4` code-review cycles (2026-06-18/19) finally close, instead of continuing to sit in `deferred-work.md` as known gaps nobody returns to.

2. **`SnapshotBatchWriter.writeAll` gets the same retry/compensation protection `SluPersistenceRetrier` already gives `sluRepository.saveAll`.**

   - Create `SnapshotPersistenceRetrier` (new `@Component`, package `com.softropic.skillars.platform.development.service`), mirroring `SluPersistenceRetrier.java` structure exactly — including its own javadoc's stated reason for being a separate bean (so `@Retryable` goes through the Spring AOP proxy; a call from `SluCalculationService` via a hypothetical `this.writeAllWithRetry(...)` would bypass the proxy and silently never retry, the same self-invocation pitfall `SluPersistenceRetrier`'s own class javadoc documents):
     ```java
     @Slf4j
     @Component
     @RequiredArgsConstructor
     public class SnapshotPersistenceRetrier {
         private final SnapshotBatchWriter snapshotBatchWriter;

         @Retryable(
             retryFor = DataAccessException.class,
             maxAttemptsExpression = "${app.slu.snapshot-retry.max-attempts:3}",
             backoff = @Backoff(
                 delayExpression = "${app.slu.snapshot-retry.backoff-initial-ms:100}",
                 multiplierExpression = "${app.slu.snapshot-retry.backoff-multiplier:2.0}"
             )
         )
         public void writeAllWithRetry(List<PlayerSkillStat> stats, short isoYear, short isoWeek) {
             snapshotBatchWriter.writeAll(stats, isoYear, isoWeek);
         }

         @Recover
         public void recoverSnapshotWriteFailure(DataAccessException ex, List<PlayerSkillStat> stats, short isoYear, short isoWeek) {
             log.error("Failed to write SLU weekly snapshot after retries — {} rows lost for {}-W{}, manual recovery needed",
                 stats.size(), isoYear, isoWeek, ex);
         }
     }
     ```
     (the snippet above is illustrative of shape, not literal copy-paste — it needs its own imports: `DataAccessException`, `Backoff`, `Recover`, `Retryable`, `List`, `PlayerSkillStat`; mirror `SluPersistenceRetrier.java`'s own import block exactly, including `@Slf4j` shown above, which the class needs for the `log.error(...)` call in `@Recover`.)
     Use a distinct property namespace (`app.slu.snapshot-retry.*`, not `app.slu.retry.*`) so the two retriers can be tuned independently — matching `SluPersistenceRetrier`'s own precedent of inline `@Value`-style defaults with no corresponding `application.yaml` entry (confirmed by grep: no `app.slu.retry.*` key exists in any `application*.yaml` file either — the defaults are the only configuration today, and that is the established pattern to follow, not a gap to fill).
   - **Retry-safety note (verify during implementation, no code change needed if confirmed)**: `SnapshotBatchWriter.writeAll` is `@Transactional` and loops calling `snapshotRepository.upsertAdd(...)` (an additive `ON CONFLICT ... DO UPDATE SET total_slu = total_slu + EXCLUDED.total_slu` upsert). A retry of the whole method is safe under the same reasoning `SluPersistenceRetrier`'s retry of `saveAll` already relies on: an uncaught exception during the loop rolls back the entire transaction (nothing partially commits), so a retry re-runs against a clean slate, not a partially-applied one. Confirm this by reading `SnapshotBatchWriter.java` fully before wiring the retrier — if some other code path already reads mid-batch state non-transactionally, flag it as a blocker rather than proceeding.
   - Change `SluCalculationService.java:186`'s `snapshotBatchWriter.writeAll(stats, isoYear, isoWeek)` call to `snapshotPersistenceRetrier.writeAllWithRetry(stats, isoYear, isoWeek)`, and add the new `snapshotPersistenceRetrier` field alongside the existing `sluPersistenceRetrier` field (`:48`).
   - New unit test `SnapshotPersistenceRetrierTest` (package `com.softropic.skillars.platform.development.service`), mirroring `SluPersistenceRetrierTest.java`'s exact three-test shape: `writeAllWithRetry_delegatesToWriter` (verifies delegation via Mockito, plain instantiation), `recoverSnapshotWriteFailure_logsAndDoesNotRethrow` (asserts no exception via `assertThatCode`), `writeAllWithRetry_writerThrows_propagatesToCaller` (pins that the un-proxied method is a thin pass-through — retries come from the AOP proxy, not self-invocation).
   - **`SluCalculationServiceIT` currently asserts nothing against `development.player_slu_weekly_snapshot`** (confirmed by grep — no reference to the table or `SluWeeklySnapshotRepository` anywhere in that IT). It exercises the code path end-to-end, so a broken AOP proxy or a thrown-and-not-recovered exception would fail it, but a `writeAllWithRetry` that silently no-ops would still pass green — it proves nothing about the snapshot write specifically. Add an assertion to at least one existing test in that IT confirming a `player_slu_weekly_snapshot` row exists with the expected `total_slu` after `onBookingCompleted`/equivalent runs, so this AC's own wiring change is actually verified, not just exercised.
   - Test: `mvn -o test -Dtest=SnapshotPersistenceRetrierTest,SluCalculationServiceIT`, confirm both green (the strengthened IT assertion above confirms the wiring change didn't silently break the snapshot-write flow, not just that it didn't throw).
   - **Two accepted, precedent-consistent quirks — no action needed, just be aware so they aren't mistaken for new bugs**: (1) `SluCalculationService`'s `log.debug("Weekly snapshot updated: …")` (`:187`) fires unconditionally after `writeAllWithRetry` returns, even on a fully-recovered failure (since `@Recover` swallows the exception and returns normally) — this exactly matches the pre-existing SLU-save path's own `log.info("SLU recorded: …")` (`:179-180`) behaving identically after `saveSluWithRetry`, so it's a pattern this story inherits, not introduces. (2) On full retry exhaustion, `@Recover` only logs "manual recovery needed" while `player_skill_stats` already holds the committed rows — `player_slu_weekly_snapshot` is then permanently under-counted (unlike the SLU-row-loss case, this is a *derived aggregate* and could in principle be rebuilt from `player_skill_stats` by a future reconciliation job, but that is out of this AC's scope, which is only to mirror the sibling `SluPersistenceRetrier`'s accepted tradeoff, not improve on it).

3. **Rapid skill-selection clicks on the radar chart no longer fire one PUT per click — without regressing the (already imperfect) visual feedback that exists today.**

   - **Corrected premise, verified live (the original draft of this AC assumed instant optimistic visual feedback exists today; it does not — confirmed by reading the full chain)**: `SkillsRadarChart.vue` has **no local selection state of its own**. `toggleSkill` (`:272-279`) computes `updated` from the `selectedSkillCodes` **prop** and only `emit('update:selectedSkillCodes', updated)` — every derived view (`activeSkills`, `polygonPoints`, `nodePositions`, `hasBaseline`, `:198-203` and around) reads that same prop. The parent binds it via `:selected-skill-codes="store.radarPreferences?.selectedSkillCodes ?? []"` (`PlayerDevelopmentDashboardPage.vue:27`, plain prop binding, not `v-model`) and handles the emitted event with `@update:selected-skill-codes="onSkillSelectionChange"` (`:240-244`), which does nothing but `await store.saveRadarPreferences(playerId.value, codes)` — no synchronous local write anywhere. `development.store.js:147-154`'s `saveRadarPreferences` sets `radarPreferences.value = { selectedSkillCodes }` **only after `await putRadarPreferences(...)` resolves** (`:149-150`) — it is not optimistic. **Consequence: today, the chart's visual selection already lags one full network round-trip behind every click.** Debouncing the PUT alone (the original approach) would make that lag debounce-delay-plus-round-trip instead, with **zero** visual feedback during a rapid click burst — worse than today, and impossible to reconcile with a "confirm the chart updates instantly per click" acceptance test, because no such instant update exists to preserve.
   - **The fix decouples visual state from persistence** — add a local ref in `PlayerDevelopmentDashboardPage.vue`, e.g. `const localSelectedSkillCodes = ref(store.radarPreferences?.selectedSkillCodes ?? [])`, and redirect **both** places that currently read `store.radarPreferences?.selectedSkillCodes` directly to read this ref instead:
     - `SkillsRadarChart`'s `:selected-skill-codes` prop (`:27`).
     - The parent's **own separate** `hasBaseline` computed (`:168-175` — note this is a second, independent copy of the same active-skill-filtering logic `SkillsRadarChart.vue` has internally; it also currently derives from `store.radarPreferences?.selectedSkillCodes` and must move to the new local ref too, or it will keep lagging even after the chart itself is fixed).
   - In `onSkillSelectionChange(codes)`, write `localSelectedSkillCodes.value = codes` **synchronously, first** (this is what gives instant visual feedback — the prop changes immediately, no network round-trip in the path), *then* call the debounced persistence function with `codes`.
   - Debounce **only** the `store.saveRadarPreferences(...)` call, mirroring `DrillLibraryPage.vue`'s own established inline pattern (`:164-169` — a local `useDebounce(fn, delay)` helper function defined in the same `<script setup>` block; this codebase has no shared debounce composable, confirmed by grep, so introducing one here would be a new abstraction beyond this AC's scope). Use the same `300`ms delay `DrillLibraryPage.vue`'s own `debouncedSearch` uses (`:208-211`).
   - **Capture `playerId` at click time, not at debounce-fire time** — `playerId` is `computed(() => Number(route.params.playerId))` (`:156`). If the debounced save closure reads `playerId.value` when it *fires* rather than when it was *scheduled*, a coach who changes the selection and then navigates to a different player within the 300ms window persists the wrong player's codes against the new player's id, racing `loadPlayerData`'s own fetch for the new player. Pass `playerId.value` as an argument captured at the point `onSkillSelectionChange` runs, not read fresh inside the debounced callback.
   - **Flush (don't drop) the debounce on unmount and on player switch.** `DrillLibraryPage.vue`'s `useDebounce` (`:164-169`) is a bare `setTimeout` with no `cancel`/`flush` — fine for a search re-run, not fine for a persistence call: a selection change followed immediately by navigation would otherwise silently drop the PUT, with no error surfaced (`store.error` is never set for a call that never happens). Extend the local `useDebounce` helper (or wrap it) with a `flush()` that immediately invokes any pending call, and call it: (1) in the existing `watch(() => route.params.playerId, ...)` handler (`:227-233`, which already calls `clearDevelopmentState()`) before switching players, and (2) in a new `onBeforeUnmount` hook. Reset `localSelectedSkillCodes` to `[]` inside `clearDevelopmentState()` alongside its existing resets, so a player switch doesn't briefly show the previous player's selection.
   - Test: no frontend test framework exists (standing convention); verify by `npx eslint` clean plus a manual dev-server pass as a coach viewing a player's radar chart: (1) click multiple skill nodes in rapid succession — confirm the chart's visual selection (and the "Compare to baseline" toggle's visibility) updates instantly per click, and only one PUT request fires (browser devtools Network tab) roughly 300ms after the last click; (2) click a selection then immediately switch to a different player before 300ms elapses — confirm the PUT that fires targets the *original* player's id with the selection made before switching, and the new player's own preferences load correctly, unaffected.

### Architecture / conventions to follow

- **Migration pattern for adding a late FK to an existing table**: `V113__radar_composite_baseline_player_fk.sql` is the direct precedent for AC1 — defensive orphan-delete before `ADD CONSTRAINT`, itself following `V109`'s established pattern.
