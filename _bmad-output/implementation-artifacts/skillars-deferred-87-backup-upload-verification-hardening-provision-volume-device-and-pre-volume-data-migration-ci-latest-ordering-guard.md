## Story

As the platform operator,
I want (1) `pg-backup.sh` / `volume-backup.sh` to stop hard-failing a good backup upload when the object-storage ETag is not a whole-object MD5 (bucket-side encryption, provider-specific ETag scheme) — the already-verified `ContentLength` match is the authoritative check — and to tolerate a brief read-after-write visibility delay on the post-upload `head-object` instead of `exit 1`-ing on a good upload, (2) `provision.sh` to stop hard-coding the Hetzner Volume as `/dev/sdb` (unreliable device-name ordering on a multi-volume server) and to **migrate** a pre-Volume `acme.json` / `data/` tree onto the Volume on the re-run where the Volume first appears — safely, resumably, and without clobbering an existing Volume — rather than leaving it stranded and hidden on the root disk under the new mount, (3) `first-time-setup.md` to stop over-promising that `provision.sh`'s `chown_if_needed` fully covers a run killed mid-`chown -R` (top-level owner correct, children half-changed, "just re-run" then skips), (4) the `master` CI `build-and-push` job to stop being able to overwrite `ghcr.io/…:latest` with an **older** commit's image when two `master` pushes' `test` jobs finish out of push order, and (5) `deferred-work.md` brought back in sync with the code — three of its Deploy/Infra items and, unrelatedly, the "cross-drill `videoId` lock still open" cluster are already closed in shipped code and were never annotated,
so that a routine backup no longer writes a false failure line to `/var/log/skillars-backup.log` and deletes its own local dump via the `trap`, a Volume re-attach no longer silently loses every TLS certificate and the LGTM/Redis data written before the Volume was attached, a partially-completed provision no longer leaves permanently mixed ownership under the data mount with a doc that says it is fine, a fast Dependabot merge landing right behind a slower story merge can no longer republish stale `:latest`, and the next full-file `deferred-work.md` audit stops re-flagging items that are done.

## Acceptance Criteria

### AC1 — A non-MD5 single-part ETag no longer hard-fails a `ContentLength`-verified backup upload.

**`deploy/backup/pg-backup.sh` and `deploy/backup/volume-backup.sh`** (structurally-matching `case "${REMOTE_ETAG}" in … esac` blocks — `pg-backup.sh:85-97`, `volume-backup.sh:90-102`; they differ only in the artifact variable (`DUMP_FILE` vs `ARCHIVE_FILE`), the log tag (`[pg-backup]` vs `[volume-backup]`), and "dumps" vs "archives" wording — edit each in its own idiom, do not try to share code):

- **Restructure the `*)` (single-part, no `-`) branch to `if mismatch → warn ; else → success`** — do **not** just delete the `exit 1`. Concretely:
  ```sh
  *)
    LOCAL_MD5=$(md5sum "${DUMP_FILE}" | cut -d' ' -f1)
    if [ "${REMOTE_ETAG}" != "${LOCAL_MD5}" ]; then
      echo "[pg-backup][warn] single-part ETag ${REMOTE_ETAG} != local MD5 ${LOCAL_MD5}. Upload already confirmed by the ContentLength match above (the authoritative leg); a single-part ETag equals the raw object MD5 only for an unencrypted bucket with a plain ETag scheme, so SSE-KMS/SSE-C or a provider-specific ETag is the expected cause here. Continuing." >&2
    else
      echo "[pg-backup] Upload verified: single-part ETag matches local MD5."
    fi ;;
  ```
  A literal "drop the `exit 1`, keep the rest" edit would print the misleading `Upload verified: …` line immediately after the warning on a real mismatch — the `else` is required.
- Keep the `""|None` and `*-*` (multipart) branches exactly as they are (already informational, not fatal).
- **Update the block's lead comment** in both scripts: record that a single-part ETag mismatch is now advisory (was `exit 1`, `skillars-deferred-85` AC4 — reversed here) and that the `ContentLength` check at the top of the verification section is the sole hard gate on upload integrity.
- **Note in the story's ledger closure (AC7):** this deliberately overrides `skillars-deferred-85` AC4's "spec-mandated `exit 1` on single-part mismatch". Record the reversal in `deferred-work.md`, do not silently drop the original bullet.

**Tests / verification:** these are shell scripts with no test harness in this repo (`grep -rn "\.sh" src/test` → none; the `deploy/backup/*` scripts have never had automated tests — see `skillars-deferred-85`'s own dev notes). Verify by: (a) `bash -n` parses clean on both; (b) `shellcheck deploy/backup/pg-backup.sh deploy/backup/volume-backup.sh` reports no new findings vs. the pre-change baseline (run `shellcheck` on the unmodified files first and diff); (c) a hand-trace in the story's Dev Agent Record of all three `case` branches showing the `*)` branch now falls through to the final `echo "[…] Done."`. Do **not** add a bash test framework.

### AC2 — The post-upload `head-object` size check tolerates read-after-write visibility lag.

**`deploy/backup/pg-backup.sh` and `deploy/backup/volume-backup.sh`** (the `REMOTE_SIZE=$( … aws s3api head-object … --query 'ContentLength' … ) || true` capture then the `if [ -z … ] || [ "${REMOTE_SIZE}" = "None" ] || [ … != … ]; then … exit 1` gate — `pg-backup.sh:60-70`, `volume-backup.sh:67-77`):

- Wrap **only** the `head-object` `ContentLength` read in a bounded retry loop: **5** attempts, **3s** `sleep` between attempts (**4 sleeps → ~12s total wall time**; wording in comments and the failure message must say ~12s, not 15s), retrying **only** while `REMOTE_SIZE` is empty / `None` (object not yet visible). A retrieved-but-mismatched size is a genuine corruption/truncation signal — **do not** retry that; break and fail immediately.
- Factor the retry as a small local function **within each script** (`deploy/backup/*.sh` deliberately duplicate small guards per-script — `skillars-deferred-24` AC4 precedent). **The helper must declare `local` on its own line, then assign separately** — `local REMOTE_SIZE` then `REMOTE_SIZE=$(aws … ) || true` on the next line — never `local REMOTE_SIZE=$(…) || true`: the combined form triggers shellcheck **SC2155** (a *new* finding, which fails this AC's own no-new-findings bar) and makes the `|| true` dead (it tests `local`'s always-0 exit, not the command substitution's). Sketch:
  ```sh
  head_object_content_length() {  # $1 bucket, $2 key — echoes ContentLength or empty
    local i out
    for i in 1 2 3 4 5; do
      out=$(AWS_ACCESS_KEY_ID="${HOS_ACCESS_KEY}" AWS_SECRET_ACCESS_KEY="${HOS_SECRET_KEY}" \
        aws s3api head-object --bucket "$1" --key "$2" --endpoint-url "${HOS_ENDPOINT}" \
        --query 'ContentLength' --output text) || out=""
      case "$out" in ""|None) ;; *) printf '%s' "$out"; return 0 ;; esac
      [ "$i" -lt 5 ] && sleep 3
    done
    return 0   # still empty — caller's existing -z / None check handles it
  }
  ```
  The `|| out=""` keeps the transport-failure-under-`set -euo pipefail` behaviour the scripts' existing comment describes — update that comment to mention the retry.
- On exhausting all 5 attempts still empty/`None`, keep today's exact failure: the `[…][error] upload verification failed …` line and `exit 1` (the `trap` still deletes the local artifact — unchanged; a genuinely-invisible-after-~12s object is a real failure, and the operator learns of it only via the backup log — see AC1's harm note).
- The **ETag** `head-object` read (AC1's block, immediately below) reuses the now-confirmed-visible object — it does **not** need its own retry loop; add a one-line comment saying so.

**Tests / verification:** same as AC1 — `bash -n`, `shellcheck` no-new-findings **including no SC2155 in the new helper**, and a hand-trace of the loop (0 visible on all 5 → exit 1 after ~12s; visible on attempt 3 → proceeds; visible-but-wrong-size on attempt 1 → immediate exit 1, no further attempts).

### AC3 — `first-time-setup.md` states the real `chown -R` partial-completion hazard, and `provision.sh` closes it.

**`docs/deployment/first-time-setup.md`** — the "If `provision.sh` fails partway through" section (around line 119-120, "The one non-idempotent hazard is `chown -R` over live data mounts. It is already mitigated — …"):

- Correct the over-promise: `chown_if_needed` compares **only the top-level directory's owner**, so a run killed **mid-`chown -R`** leaves the top-level correct and children half-changed, and the re-run then **skips** (with the AC's `provision.sh` change below, it now catches the shallow case; deep partial changes are still the operator's to remediate). State this explicitly.
- Give the operator the remediation to run after any interrupted provision, for each data subdir with a non-root owner (`prometheus` 65534, `loki`/`tempo` 10001, `grafana` 472, `redis` 999:1000): detect with `find "${DEPLOY_ROOT}/data/grafana" \( \! -uid 472 -o \! -gid 472 \) -print -quit` (**uid *and* gid** — `chown -R` sets both), fix with `chown -R 472:472 "${DEPLOY_ROOT}/data/grafana"`.

**`deploy/provision.sh`** — `chown_if_needed()` (line ~23-30):

- The recorded design intent (`provision.sh:23-25`) is "no recursive traversal when the top-level owner already matches". Preserve that as the fast path. Add a **bounded, uid+gid** second tier: when the top-level matches, run `find "$dir" -maxdepth 2 \( \! -uid "${uid}" -o \! -gid "${gid}" \) -print -quit` (with `uid=${owner%%:*}`, `gid=${owner##*:}` — every `owner` passed in this script is fully numeric `uid:gid`) and fall through to `chown -R` if it finds a mismatch. `-maxdepth 2` deliberately bounds the walk to the directory and its immediate children — enough to catch the realistic "top-level chowned, first-level children not yet" interruption pattern (`chown -R` descends roughly breadth-first) without a full metadata scan of a Volume with real observability retention on **every** idempotent re-run. Document both the uid+gid check and the `-maxdepth 2` bound (and its limitation — a mismatch buried >2 levels deep is not caught here; the doc remediation above covers that) in the function's comment.
- Must stay **idempotent and safe to re-run**, and must not change first-provision behaviour (a freshly-created dir has no children → `find` finds nothing → the existing top-level branch still runs the `chown -R`).

**Verification:** `bash -n deploy/provision.sh`; `shellcheck` no-new-findings; Dev Agent Record hand-trace of `chown_if_needed` for (a) first-provision fresh dir, (b) fully-correct dir on re-run (fast path, bounded `find` finds nothing → no `chown -R`), (c) top-level-correct-but-immediate-child-wrong dir on re-run (`-maxdepth 2` `find` hits it → `chown -R`), (d) child wrong *gid only*, right uid (caught by the `-gid` arm).

### AC4 — `provision.sh` resolves the Hetzner Volume by its stable device id, not `/dev/sdb`.

**`deploy/provision.sh`** section 7 (around line 158-160, `VOLUME_DEVICE="/dev/sdb"`, `FSTAB_ENTRY`, idempotency via `grep -qF "${FSTAB_ENTRY}" /etc/fstab` at `:181`):

- Resolve `VOLUME_DEVICE` at runtime: prefer the first present `/dev/disk/by-id/scsi-0HC_Volume_*` symlink (Hetzner's documented stable per-Volume path), resolved to its real device node via `readlink -f`. Fall back to `/dev/sdb` **only** if no such symlink exists, with a `log` line naming which path was used. Keep `VOLUME_LINK` (the `/dev/disk/by-id/...` path, or `/dev/sdb` in the fallback case) as a separate variable — it is what goes in `/etc/fstab`.
- If `HETZNER_VOLUME_ID` is available in the environment (referenced elsewhere in the deploy tooling — confirm during dev), prefer the exact `scsi-0HC_Volume_${HETZNER_VOLUME_ID}` match over "first `scsi-0HC_Volume_*`" so a multi-Volume server picks the right one deterministically; otherwise "first match" with a `log` line is acceptable (single-Volume is the current topology).
- `FSTAB_ENTRY` uses `VOLUME_LINK` (the stable `by-id` path — survives device-name reordering across reboots), not the resolved `/dev/sdX`. Keep `nofail` (already present).
- **Purge a stale pre-existing fstab line before writing the new one.** A node provisioned by today's script already carries `/dev/sdb ${MOUNT_POINT} ext4 defaults,nofail 0 2` in `/etc/fstab`; after this AC changes `FSTAB_ENTRY` to the `by-id` form, the `grep -qF` no longer matches that line and the script would **append a second entry for the same mount point** (double `mount -a` on next reboot). Before the "add if not present" block, remove any existing `/etc/fstab` line whose mount-point field is `${MOUNT_POINT}` (match on ` ${MOUNT_POINT} ` regardless of the device field) — mirror the exact pattern `install-crons.sh:28-31` uses to purge the stale `volume-snapshot.sh` cron (`grep -vF … | … -` style, or `sed -i` on the mount-point column). Then the existing "add if not `grep -qF "${FSTAB_ENTRY}"`" block runs and is now correct.
- All other section-7 idempotency (already-mounted `mountpoint -q` check, `blkid` "already has a filesystem" check) must keep working against the new identifier.
- Preserve the no-Volume-attached `else` branch (the warning block) unchanged in behaviour — it triggers when neither the `by-id` symlink nor `/dev/sdb` is a block device (test the resolved `VOLUME_DEVICE` with `[ -b … ]` as today).

**`docs/deployment/first-time-setup.md`** — this AC also owns the three `/dev/sdb` statements the script no longer honours (the file is already edited by AC3 and AC5, so it is in play):

### AC5 — A pre-Volume `data/` tree is migrated onto the Volume on the re-run where the Volume first mounts — via a root-disk staging dir, resumably, without clobbering an existing Volume.

**Context the design must respect** (all verified against `provision.sh` at `cc0a9f6`):
- Section 6 (`:124-126`) runs `mkdir -p "${DEPLOY_ROOT}/data/postgres"` **before** section 7, so `${MOUNT_POINT}` on the root disk is **never empty** by the time section 7 runs — a bare `[ -n "$(ls -A …)" ]` "non-empty" test is **always true** and cannot be the trigger.
- `redis/` and `traefik/acme.json` are created by **section 7.5, which runs *after* section 7** (`:218`, `:224-245`). So section 7 must **not** verify `traefik/acme.json` as a "did the migration land" check on a fresh install — it does not exist yet on a from-scratch host.
- `provision.sh` is `set -euo pipefail`; section 7 is short-circuited on re-run by `if mountpoint -q "${MOUNT_POINT}"`. Any staging state that lives *at or under* `${MOUNT_POINT}` becomes invisible once the Volume is mounted over it.

**`deploy/provision.sh`** section 7, Volume-present branch:

1. **Trigger on a concrete pre-Volume payload marker, not "non-empty".** Before `mount`, arm the migration only if a real pre-Volume artifact is present on the root disk at `${MOUNT_POINT}` — specifically `[ -f "${MOUNT_POINT}/traefik/acme.json" ]` **OR** a non-empty `${MOUNT_POINT}/redis/` **OR** a non-empty `${MOUNT_POINT}/grafana|loki|tempo|prometheus/` (any LGTM data dir with content). A lone empty `postgres/` from section 6 must **not** arm it.
2. **Stage to a root-disk dir *outside* `${MOUNT_POINT}`.** `STAGING="${DEPLOY_ROOT}/.pre-volume-migration"`. When armed: `mkdir -p "${STAGING}"` and `rsync -aHAX --numeric-ids "${MOUNT_POINT}/" "${STAGING}/"` (copy the pre-Volume tree aside). `${STAGING}` sits next to `${DEPLOY_ROOT}/data`, never under the mount, so it survives `mount` and a `mountpoint -q` re-run short-circuit.
3. `mount "${VOLUME_DEVICE}" "${MOUNT_POINT}"` (unchanged), add the fstab entry (per AC4).
4. **After mount, decide by Volume contents (excluding `lost+found`).** Compute `VOL_NONEMPTY` = "the mounted `${MOUNT_POINT}` has any entry other than `lost+found`" (`find "${MOUNT_POINT}" -mindepth 1 -maxdepth 1 \! -name lost+found -print -quit`). Fresh `mkfs.ext4` volumes always contain `lost+found`, so a plain `ls -A` emptiness test is wrong.
   - **`${STAGING}` non-empty AND `VOL_NONEMPTY` false** → migrate: `rsync -aHAX --numeric-ids "${STAGING}/" "${MOUNT_POINT}/"`. Verify only paths that existed **in `${STAGING}`** (the migration source) — e.g. re-run the trigger predicate against `${STAGING}` and assert each armed path now also exists under `${MOUNT_POINT}` with matching `stat -c '%a %u:%g'`. ### AC6 — CI `build-and-push` will not overwrite `:latest` with an older commit's image.

**`.github/workflows/ci.yml`** — the `build-and-push` job (currently: `needs: test`, `concurrency: build-and-push-${{ github.ref }}` / `cancel-in-progress: false`, then the `docker-build` action pushing `sha-<short>` **and** `latest`):

- **`fetch-depth: 0`** on this job's `actions/checkout` (needed for `git merge-base --is-ancestor` against an arbitrary older commit).
- Add a step that reads the `org.opencontainers.image.revision` label from the **currently-published** `ghcr.io/${{ github.repository }}:latest` and computes whether `$GITHUB_SHA` descends from it. **Robustness constraints — the prescribed shape must handle all three of these or the guard is worse than nothing:**
  - **The published `:latest` is an OCI image index, not a single manifest.** `docker/build-push-action@v6` attaches provenance attestations **by default on push** (the `action.yml` here does not set `provenance: false`), so `:latest` is published as a manifest list. `docker buildx imagetools inspect --format '{{ index .Image.Labels … }}'` assumes a single image and **fails against an index** (`.Image` is a per-platform map with no `.Labels`). Use an index-aware read — e.g. `docker buildx imagetools inspect ghcr.io/${{ github.repository }}:latest --raw` piped to `jq` to walk to the `linux/amd64` image config's `Labels`, or the `{{ (index .Image "linux/amd64").Config.Labels ... }}` template form — and the dev **must verify the exact invocation against a real published `:latest`**, which is only possible post-merge (see Verification).
  - **`:latest` may not exist yet** (first publish ever, or after a registry wipe) → treat as "no constraint", push both tags.
  - **The published revision may not be in local git history** — `git merge-base --is-ancestor <rev> "$GITHUB_SHA"` exits **128** (not 0/1) for an unknown commit (reachable after a `master` force-push or a rebased/deleted branch). The step must **not** run under bare `set -e` for this call: capture `$?` explicitly and treat **anything other than exit 0** (not-ancestor `1`, unknown-commit `128`, or an errored `imagetools`/`jq`) as **"cannot confirm `HEAD` is newer → publish `sha-<short>` only, skip `:latest`, `echo "::notice::"`"**. Fail safe, never abort the job.
- **Decision:** published rev absent, OR `$GITHUB_SHA` is a descendant of (or equal to) the published rev → push `sha-<short>` **and** `latest`. Otherwise → push `sha-<short>` only + `::notice::` (`:latest` already points at newer/divergent commit `<rev>`; this run published only its SHA tag).
- Implement by computing the tag list in the new step and passing it via `$GITHUB_OUTPUT` into the `tags:` input of the existing `./.github/actions/docker-build` step. **Do not change `.github/actions/docker-build/action.yml`** — it stays a dumb "push these tags" action.
- **`sha-<short>` coverage caveat (M2, pre-existing — this AC does not fix it, only must not overstate it):** `build-and-push` has `concurrency: { group: build-and-push-${{ github.ref }}, cancel-in-progress: false }`. GitHub keeps only **one** run *pending* per concurrency group and cancels a previously-pending run when a newer one queues. In a ≥3-push burst (a story merge plus two Dependabot squashes in quick succession) the middle run's `build-and-push` can be cancelled *while pending* and never execute — so that commit gets **no** `sha-<short>` tag either, and `docs/deployment/rollback.md` has no rollback target for it until its CI is manually re-run. AC6 changes only which tags a run that *does* execute pushes; it neither introduces nor fixes the burst gap. State this in the Dev Notes, and do **not** claim "the SHA tag is always pushed regardless" anywhere in the shipped comments.
