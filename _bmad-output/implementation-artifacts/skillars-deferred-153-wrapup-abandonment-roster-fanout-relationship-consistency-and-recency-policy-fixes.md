## User Story

As **a coach, parent, and player on Skillars, and the developer maintaining the `booking`/`admin`/`development` modules' lifecycle, authorization, and scoring consistency**, I want eleven independently-verified, currently-open defects fixed — a permanently-stuck-booking remediation path (both an automatic sweeper and a manual admin tool) for a coach who abandons the wrap-up wizard, a GDPR-erasure gap closed on the session-recap free-text columns, a hard cap on the roster endpoint's per-player query fan-out computed *before* scoring (not after), standard pagination on the player-timeline endpoint, a coach-player relationship authorization check widened to match the roster's own membership rules — across **every** read endpoint it actually gates, not just the ones that happened to share one helper — a 5-copy duplicated predicate consolidated into one shared, corrected method, report generation brought under the same recency policy the timeline already enforces, the roster's attention-score recency normalizer decoupled from the operator-configurable dormancy threshold, a silent upload-failure logging gap closed, and the coach-contribution empty-state *selection rule* de-duplicated alongside its already-shared threshold — so that **no booking can be permanently orphaned by an abandoned wizard; an erased player's coach-authored recap text cannot outlive their own erasure; a 300-player academy coach's roster GET no longer issues ~900 synchronous queries per request; a player with years of session history can page through their timeline instead of risking an unbounded response; a coach is never 403'd viewing detail for a player who is legitimately on their own roster, on any of the endpoints that detail spans; a dual coach-and-self-owned-player account (should one ever exist) is protected by one correct check instead of five incomplete copies; a coach whose last session with a player was years ago is refused a report the same way they're refused that player's timeline; retuning one operator config knob can no longer silently reshape the entire roster ranking; a failed coach-logo upload is diagnosable from logs; and the two contribution-panel consumers can no longer drift on which empty-state message applies to which case.**

## Acceptance Criteria

1. **Wrap-up abandonment remediation: an automatic sweeper, and a manual admin force-complete action.** A coach who taps Quick Complete (moving the booking to `COMPLETED_PENDING_CONFIRMATION`) and then abandons `WrapUpSequence.vue`'s wizard before its mandatory step-5 submit leaves **no** `SessionCompletionData` row at all. The only existing sweeper, `QuickCompleteTimeoutService.processExpiredQuickCompletes` (`:50-79`), only matches rows that already exist (`SessionCompletionDataRepository.findPendingQuickCompletes`), so it can never pick this case up, and the parent's `confirmCompletion` hard-fails identically on the missing row. There is no resumable path back into the wizard (both `showWrapUp = true` writers in `CoachCommandCenterPage.vue` fire only from the in-session Quick Complete button or a live-session-end callback, neither reachable once the booking has left that state).

   **Both paths share one method.** Add `BookingCompletionService.forceCompleteWithPlaceholderData(UUID bookingId, ActorRole actorRole, Long actorUserId)`, modeled on **`submitWrapUp`'s** actual sequence (`:127-170` — **not** `confirmCompletion`, which only *reads* an existing row and hard-fails if it's missing; despite the surface similarity, `confirmCompletion` is the wrong precedent for a method that must *build* a row): construct a `SessionCompletionData` with `bookingId`, `coachId = booking.getCoachId()`, `playerId = booking.getPlayerId()` (both are `nullable = false` on the entity — they must be set explicitly, they are not optional like the recap fields), `completionMode = "QUICK"`, `playerAttended = false` (see Dev Notes — the real value was never captured for an abandoned session; `false` is the conservative default and matches `TimelineEventListener`'s existing `!isPlayerAttended() → null coachId` principle for exactly this question), every rating/recap/voice-note field left `null` (all nullable at the schema level — confirmed against `SessionCompletionData.java` — so this needs no migration). Save it; `submitWrapUp`'s own existing `catch (DataIntegrityViolationException e) { log.warn(...); return; }` around its `completionDataRepository.save(scd)` call is the **real** concurrency guard here (the `session_completion_data_booking_id_key` UNIQUE constraint) and must be copied verbatim — an unlocked pre-check alone is not sufficient, since `BookingService.transition`'s pessimistic lock is acquired only *after* this insert, not before it, so a legitimate `submitWrapUp` can still land between a pre-check and the insert. If the save succeeds, call `bookingService.transition(bookingId, BookingEvent.COMPLETE, new TransitionContext(actorRole, actorUserId))` and publish `BookingCompletedEvent` exactly as `processExpiredQuickCompletes` does, catching `BookingStateTransitionException | OptimisticLockingFailureException` the same way (log warn, skip) for the case where the booking moved to some other state between the save and the transition.

   **Sweeper:** new `StuckCompletionSweeperService` (`platform.booking.service`), mirroring `QuickCompleteTimeoutService`'s `@Scheduled(fixedDelay = 5, timeUnit = MINUTES)`/`@SchedulerLock`/`TransactionTemplate` shape. It finds every `Booking` with `status = 'COMPLETED_PENDING_CONFIRMATION'`, `updatedAt` before a cutoff, and no matching `SessionCompletionData` row (a new `NOT EXISTS`-style `BookingRepository` query method), then calls the shared method with `ActorRole.SYSTEM`, `actorUserId = null`. (`Booking.updatedAt`'s `@PreUpdate` means this measures time since the booking last changed — since nothing else ever writes to a row-less `COMPLETED_PENDING_CONFIRMATION` booking, that is exactly the time since Quick Complete was tapped, a fine proxy for "how long has this sat unresolved," just not literally "how long the coach has been idle in the wizard.") Add a new `ConfigBounds` key `booking.stuck_completion_timeout_hours` — **declare it exactly like `DEVELOPMENT_ROSTER_DORMANT_AFTER_DAYS`** (a real `defaultValue`, registered in `HAS_CODE_DEFAULT`, read via the 4-arg `getBoundedLong(key, defaultValue, min, max)`) — **not** like `BOOKING_QUICK_COMPLETE_TIMEOUT_HOURS`, which uses the `0L` not-applicable sentinel, is deliberately excluded from `HAS_CODE_DEFAULT`, and only works today because `V139` seeds a real value separately. The two existing keys look similar but follow opposite patterns, and `ConfigBoundsEnumCoverageTest` enforces the distinction mechanically — getting this wrong fails that test. Bounds `1L..720L`, default `24L`. (That happens to equal `quick_complete_timeout_hours`'s own seeded default — also `24`, not `1` — so there is no "intentionally shorter" relationship between the two; a separate key is still correct because the two sweepers answer different questions — row exists and is awaiting parent vs. row never existed at all — not because the numbers must differ.)

   **Admin force-complete:** add `ActorRole.ADMIN` to the `ActorRole` enum (never persisted anywhere, no `switch`/`values()` dependency on it elsewhere — zero-migration) and to `BookingService.EVENT_ROLES`'s `BookingEvent.COMPLETE` entry. New `POST /api/admin/bookings/{bookingId}/force-complete`: `AdminBookingResource` (`platform.admin.api`) + `AdminBookingCompletionService` (`platform.admin.service`), following `AdminDisputeResource`/`DisputeService`'s pattern — **matching its exact division of labor**: `resolveAdminId()` is a private method on the **resource** (`AdminDisputeResource.java:62`), not the service; the resource resolves the id and passes it as a parameter into the service call, the way `AdminDisputeResource` calls `disputeService.resolveDispute(..., resolveAdminId())`. The service calls the shared `forceCompleteWithPlaceholderData(bookingId, ActorRole.ADMIN, adminId)`, then `logAdminAction(adminId, AdminActionType.BOOKING_FORCE_COMPLETE, bookingId.toString(), note)` (mirroring `DisputeService.java:384`'s private helper's shape, callers at `:281`/`:306`). Add `BOOKING_FORCE_COMPLETE` to `AdminActionType` and widen `admin_action_log`'s `action_type` CHECK constraint in a new migration (`V162`, the next free version — `BOOKING_FORCE_COMPLETE` is 22 chars, fits the column's `varchar(25)`) — mirror `V153__admin_alerts_subscription_orphaned_type.sql` exactly: `DROP CONSTRAINT IF EXISTS` + re-`ADD CONSTRAINT` with the full widened value list, `SET LOCAL lock_timeout = '5s'`, a `-- migration-lint: allow-validating-constraint` comment with V153's identical reasoning (`admin_action_log` is an internal admin-queue-shaped table with no bulk-insert path, and this project has never had a production deploy, so the widening and its first write ship together). If the save hits the UNIQUE-constraint race (a legitimate completion landed first), the admin endpoint should respond the same benign way the sweeper does — treat as already-resolved (e.g. success with a "no action needed, already completed" note), not an error — both callers want the identical outcome when that happens.

   **Disclosed consequence — this releases the coach's payout, exactly as the existing timeout-based auto-confirm already does.** `CoachPayoutEnqueueListener` (`@TransactionalEventListener(BEFORE_COMMIT)`, `MANDATORY` enqueue inside `CoachPayoutOutboxSupport`) fires on **every** `BookingCompletedEvent` regardless of `playerAttended` — there is no attendance gate on the payout path. Its own Javadoc currently asserts there are exactly three publish sites, all already inside an active transaction; `forceCompleteWithPlaceholderData` becomes a fourth (sweeper) and fifth (admin). As long as the shared method runs inside an active transaction (the class's existing `@Transactional`, or the sweeper's `TransactionTemplate` joining rather than nesting it), the enqueue stays atomic exactly as today — but **update `CoachPayoutEnqueueListener`'s Javadoc in the same commit** so its "no fourth publisher" claim doesn't go silently false. This is a deliberate consistency choice, not a new policy: `processExpiredQuickCompletes` already releases payout on an auto-confirm with no explicit parent confirmation, so extending the identical mechanism to "no coach-authored confirmation either" is extending existing behavior, not introducing a new one — but it is real money movement for a session nobody actively confirmed happened, and is called out here so it is a visible, reviewable consequence rather than an implicit side effect discovered later.

2. **GDPR erasure anonymizes the session-recap free text (and the pre-existing `voice_note_text` gap on the same table).** `GdprErasureService` never touches `booking.session_completion_data` today — its injected `bookingRepository` field has zero call sites in the class — so `what_we_did`/`whats_next` (added by `skillars-12-2`) and the pre-existing `voice_note_text` survive a player's own erasure indefinitely and never appear in their DSAR export (`GdprExportService` has no dependency on this table either). Add `SessionCompletionDataRepository.anonymizeByPlayerId(Long playerId)` — `@Modifying @Query("UPDATE SessionCompletionData s SET s.voiceNoteText = NULL, s.whatWeDid = NULL, s.whatsNext = NULL WHERE s.playerId = :playerId")` — and call it from `GdprErasureService`. (There is no existing repository method in this codebase that nulls a free-text column in place to mirror verbatim — `CoachReviewRepository.anonymiseApprovedReviews` writes an integer sentinel, `0`, to an **id** column, a different mechanism despite the similar name; treat this as a new, simple pattern, not a copy of an established one.) `session_completion_data` lives in the `booking` schema, not `development` — **read `deletePlayerDevelopmentData`/`deletePlayerDevelopmentDataInDedicatedPool` in full before touching either**: that method's own Javadoc carries exact cumulative lock-budget arithmetic sized to its current, `development`-schema-only statement count, and folding a `booking`-schema statement into it would require updating that arithmetic. Decide, and document in a code comment, whether this new call belongs inside that budgeted method (updating its count/group assignment) or as its own independently-bounded step elsewhere in the erasure flow — either way, apply the same per-statement `lock_timeout` convention every sibling statement in this service already uses. **Pre-existing, not introduced by this story:** anonymizing the three columns does not delete the `SessionCompletionData` row itself — no code path deletes that row today, and this AC does not add one. That is the right scope for *this* AC (the row's other fields — ratings, attendance — are not personally-identifying free text), but is worth naming so it is not mistaken for a complete erasure of the table.

3. **Roster endpoint: cap the candidate player set before the per-player fan-out runs, not after.** `CoachRosterService.getRoster` (`:68-104`) issues one membership query (`BookingRepository.findRosterPlayerActivityByCoachIdAndStatusIn`, `@Query` at `:228-236`) with no cap, then fans out per-player calls (`CoachPlayerLastSessionResolver.resolve`, `NeglectedSkillFlagRepository.countByPlayerIdAndResolvedAtIsNull`, `SluWeeklySnapshotRepository.findByPlayerIdFromWeek`) before sorting by `attentionScore` (`:100`) — AC1's 730-day recency floor means a real academy coach's candidate set can be 300+ players, i.e. hundreds of synchronous queries on one GET. **Bound the DB cost directly:** add a `Pageable` parameter to `findRosterPlayerActivityByCoachIdAndStatusIn`, and change its `ORDER BY` (currently `b.playerId` only — a stability tie-break the `skillars-12-1` code review added, comment at `:223-227`) to `MAX(b.requestedStartTime) DESC, b.playerId ASC`, preserving that tie-break as the secondary key; `CoachRosterService.getRoster` passes `PageRequest.of(0, maxPlayers)`. **Two load-bearing constraints, neither optional:** the method must keep its `List<>` return type — a `Page<>` return would derive a `COUNT` query over a `GROUP BY b.playerId`, which Spring Data evaluates per-group (one row per group), throwing `IncorrectResultSizeDataAccessException` — and the `ORDER BY` must stay written into the `@Query` text with an **unsorted** `PageRequest`, since Spring Data appends any `Pageable`-carried `Sort` *after* the query's own `ORDER BY`, making a sorted `PageRequest` a silent no-op here. Add a new `ConfigBounds` key `development.roster.maxPlayers`, declared exactly like the adjacent `DEVELOPMENT_ROSTER_DORMANT_AFTER_DAYS` (`HAS_CODE_DEFAULT`, 4-arg `getBoundedLong`) — bounds `1L..10000L`, default `150L` (margin above the ledger's own "~100 players" revisit trigger). No `RosterResponse`/`RosterEntryResponse` contract change is needed — neither record carries a count/page field today, and none is needed, since the cap bounds the candidate set computed server-side, not the response shape. Update the query's own comment (`:218-221`, currently "no cap/limit like `findQualifyingCompletedBookings`") to reflect the new cap and why it exists. **Note for the implementer:** the existing missing-player-profile filter (`:97-98`) runs *after* this query, so a filtered-out row still consumes one of the `maxPlayers` slots — a minor, latent shrinkage of the effective cap; not worth a design change given how rare a missing profile is (see `skillars-deferred-152` AC6's own reachability analysis), but worth knowing if the cap is ever tuned against observed roster sizes.

   **Document the accepted trade-off explicitly, do not let it pass silently:** capping by *most-recently-booked* before scoring (rather than by *attentionScore* after scoring, which the owner rejected as not reducing DB load) means a long-dormant-but-genuinely-neglected player with an old `latestBookingTime` can now be excluded from the roster in favor of a recently-booked but otherwise unremarkable one, for a coach whose candidate set exceeds `maxPlayers`. Call this out in a code comment at the query/config-key declaration, not just in this story.

4. **Timeline endpoint: standard offset pagination.** `PlayerTimelineRepository.findByPlayerIdOrderByOccurredAtDesc(Long)` (`:14`) takes no `Pageable` and returns the player's entire timeline (up to ~1KB of recap text per completed session since `skillars-12-2`), consumed via `TimelineQueryService.getTimeline` (`:31-64`). Add a trailing `Pageable` parameter and change the return type to **`Slice<PlayerTimelineEvent>`** — not a bare `List<>` with `Pageable` (pages the rows but gives no way to know whether more exist), and not `Page<>` either (adds a `COUNT` query this feature doesn't need `totalElements` from). `Slice.hasNext()` is the `hasMore` source. `PlayerTimelineResource.getTimeline` (`:26-36`, currently a single `@PathVariable Long playerId`) gains bounded page/size params — **this codebase's real precedent is the annotated-bound style**, e.g. `CoachMarketplaceResource`'s `@RequestParam(defaultValue = "0") @Min(0) int page, @RequestParam(defaultValue = "50") @Min(1) @Max(200) int size`, or `ReliabilityStrikeResource`'s named `MAX_PAGE_SIZE` constant with a manual `Math.min(Math.max(size, 1), MAX_PAGE_SIZE)` clamp — pick one and be consistent with it. (`AdminReviewResource` is **not** a valid precedent here — it has no `size` parameter at all, its page size is a hardcoded `20` inside `AdminReviewService`; and there **is** a repo-wide `Pageable`-as-controller-param convention already, contrary to an earlier claim — `AdminGdprResource.listRequests` takes a bare `Pageable pageable` directly.) `TimelineQueryService.getTimeline` builds an **unsorted** `PageRequest.of(page, size)` — the repository's own `OrderByOccurredAtDesc` already orders it; a sorted `Pageable` would be appended after that and silently do nothing — and passes it through. `TimelineResponse` gains `boolean hasMore`, which **both** of its construction sites need: the access-expired early return (`:51`, `new TimelineResponse(true, expiryDays, List.of())`) and the normal return (`:63`).

   **Minimal frontend wiring is in scope, not deferred — a silent, invisible truncation at 50 events would be a regression, not a neutral default.** `development.store.js`'s `fetchTimeline` (`:218-227`) currently does `timeline.value = null` then replaces it wholesale with the response — there is no separate events array to append to, and `timelineLoading = true` hides the whole panel while it runs. Restructure `fetchTimeline` to accept a `page` argument; for `page === 0` keep today's replace behavior, for `page > 0` append the returned events to the existing array under a **separate** `timelineLoadingMore` flag that does not hide the already-rendered panel. Update `development.api.js`'s `getTimeline` to accept and forward `page`/`size` query params. Add a "Load more" button to the timeline-rendering component, shown only while `hasMore` is true. **`PlayerTimelinePanel.vue` has three page consumers, not one** — `CoachPlayerDetailPage.vue`, `ParentDevelopmentPortalPage.vue`, and `PlayerDevelopmentDashboardPage.vue` — so the new ceiling and the Load-more affordance land on coach, parent, and player surfaces alike; this is intended, since the backend endpoint is shared across all three, not an accidental scope widening.

### Why AC1's sweeper writes a placeholder row rather than skipping `SessionCompletionData` entirely

`BookingCompletedEvent` already expects `whatWeDid`/`whatsNext` as nullable `String` (confirmed via its own constructor overloads, which default both to `null`). Writing a real (if blank) `SessionCompletionData` row, rather than inventing a second "booking completed with truly nothing" code path, means every existing downstream consumer of `BookingCompletedEvent`/`SessionCompletionData` keeps working unmodified — the row's *presence* signals "this booking completed," its *null recap fields* signal "no coach-authored recap was ever captured," which is simply the truth.

### Why AC1's two mechanisms share one method, and why that method is modeled on `submitWrapUp`, not `confirmCompletion`

Both the sweeper and the admin action need the identical three-step sequence (placeholder row → transition → publish) and the identical concurrency guard (don't corrupt state if a legitimate completion-data row lands between the caller's query and this method running). `confirmCompletion` only ever *reads* an existing row and hard-fails if it's missing — it has nothing to offer a method that must *build* one. `submitWrapUp` is the real template: it already builds a `SessionCompletionData`, saves it with the exact `DataIntegrityViolationException`-as-benign-idempotency-signal guard this new method needs, and only then transitions. Writing the shared logic once on `BookingCompletionService` avoids the sweeper and the admin action silently drifting on this exact state-machine-adjacent logic.

### Why AC2's GDPR fix is its own repository method and insertion point, not folded into `deletePlayerDevelopmentData` on faith

`session_completion_data` lives in the `booking` schema, not `development` — folding it into `deletePlayerDevelopmentDataInDedicatedPool`'s existing lock-budget-bounded statement groups would require updating that method's own documented cumulative-lock-budget arithmetic, which is sized to its current, `development`-only statement count. The implementer must read that method in full and make an explicit, documented choice rather than assume either answer.

### Why AC3 changes the `ORDER BY`/adds a `Pageable` rather than a native aggregate query

The owner explicitly rejected re-opening "introduce a bespoke batched/aggregate native query" (the same thing `skillars-12-1`'s own Performance note already rejected once). Adding `Pageable` to an existing JPQL `@Query` with a `GROUP BY`/aggregate `SELECT` is natively supported by Spring Data JPA, with the two load-bearing caveats called out in AC3 itself (keep `List<>`, keep the sort in the query text). The real behavior change is the `ORDER BY` switching from "deterministic tie-break only" to "most-recently-active first, then deterministic tie-break" — see AC3's own trade-off paragraph for what this changes about which players get excluded under the cap.

### Why AC4 includes minimal frontend wiring, unlike how `skillars-deferred-152` scoped similar frontend gaps out

`skillars-deferred-152` left two `AvailabilityManagerPage.vue` error-message duplicates out of scope because fixing them was *optional* — the bug was no worse with or without the fix. Here, shipping backend pagination **without** any frontend affordance to see page 2 would be a strict regression from today's behavior — so the minimal "Load more" button is part of closing AC4 correctly, not optional polish.

### Why AC5 is scoped to "every affected read endpoint," not "every endpoint the 5-copy helper touches"

The first draft of this story conflated "the callers of the `ifCoach` helper" with "the callers of the narrow status check" — they are not the same set. `ACTIVE_RELATIONSHIP_STATUSES`/`requireCoachPlayerRelationship` has 11 callers; only 5 of the 8 reads go through the `ifCoach` wrapper AC6 consolidates. Scoping AC5 to only those 5 would have left three real, coach-gated GET endpoints (`RadarAssessmentService.getMyEntries`, `SluTargetService.getTargets`, `DevelopmentCorrelationService.getInsights`) permanently 403-ing for the exact roster-only statuses this AC exists to fix — defeating the AC's own stated purpose for a third of its true scope. AC5 and AC6 remain two separate ACs (AC6's consolidated method depends on AC5's new wider check existing first), but AC5's own text now owns all 8 read call sites, not just the 5 that happen to share a duplicated predicate.

### Why AC7 keeps `AccessDeniedException` rather than introducing a dedicated "stale" exception type

No distinct "access was valid but has expired" vs. "access was never valid" exception exists anywhere in `platform.development` today — `AccessDeniedException` is already this codebase's one authorization-denial type for this exact guard. Introducing a new exception type for one additional denial reason inside the same method, when the existing type's semantics already cover it correctly, would be exactly the kind of unnecessary abstraction this project's own conventions ask to avoid.

### Why AC8 rewrites two existing tests rather than treating them as "should still pass"

Both `daysSinceLastActivityAtThreshold_isDormant_andAgreesWithSaturatedRecencyScore` (asserts `attentionScore ≈ 0.4` at `daysSinceLastActivity = dormantAfterDays = 30`) and `recencyComponent_clampsAtDormancyThreshold` (asserts `d=31` and `d=9999` produce the *same* score, both `≈0.4`, because both currently clamp at `dormantAfterDays = 30`) encode the exact coupling AC8 removes. Once the normalizer divides by a fixed `90` instead of `dormantAfterDays`, `d=30` no longer saturates (`30/90 × 0.4 ≈ 0.133`, not `0.4`) and `d=31` no longer equals `d=9999` (`31/90 × 0.4 ≈ 0.138` vs. `90/90 × 0.4 = 0.4`, since the ceiling moved to 90). These are not incidental breakages to patch around — they are the tests correctly going red because the behavior they pinned is precisely the behavior this AC changes. Re-author them to assert the new, decoupled behavior (dormant-but-not-saturated at `d=30`; saturated only at `d=90`), don't just adjust the numbers to make the old assertions pass again.

### Why AC10 is bundled here even though it wasn't one of the four headline priority items

AC10 (the contribution-panel empty-state *selection-rule* duplication) lives in the exact same `deferred-work.md` section — "code review of `skillars-deferred-152`…(2026-10-17)" — as AC7's and AC9's own source bullets. It is cheap, already-scoped by its own ledger text, and leaving it unpicked while taking its two same-day siblings from the identical section would have been an inconsistent mining pass for no real reason.
