# Story Deferred-12: Booking Payment-State Recovery & Admin Review Integrity

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a platform operator,
I want the admin review-approval flow to be idempotent and correctly error-shaped, a parent's booking to never be permanently stuck if a payment never captures, batch-accepted bookings to complete their payment transition at all, and internal payment events to carry correctly-named fields,
so that admins cannot silently create duplicate audit trail/events by re-approving a review, parents always have an escape hatch from a crashed payment flow without risking a fraudulent refund, coaches accepting a multi-slot batch actually get confirmed bookings, and the codebase does not carry a semantically-wrong field name into future features that consume it.

## Acceptance Criteria

1. **Given** a review is already in `APPROVED` moderation status
   **When** `AdminReviewService.approveReview()` is called on it again
   **Then** the call is rejected before any DB write or event publish — no duplicate `ReviewModerationLog` row and no duplicate `ReviewModerationResolvedEvent` are produced
   **And** the rejection follows the codebase's existing idempotency-conflict pattern for this domain (an `OperationNotAllowedException` carrying a new `ReviewErrorCode.ALREADY_APPROVED` mapped to HTTP 409, matching how `ALREADY_SUBMITTED`/`RESPONSE_ALREADY_SUBMITTED`/`ALREADY_FLAGGED` are already handled in `ReviewApiAdvice`)
   **And** the guard holds under **concurrent** calls, not merely sequential ones — a plain `findById` + status check is a check-then-act race that two simultaneous requests both pass, which is exactly the admin-double-click scenario this AC exists to stop. `CoachReview` has no `@Version` (verified) and `reviews.review_moderation_log` has no unique constraint beyond its `log_id` PK (`V69__review_flags_moderation_log.sql:14-21`, verified), so neither optimistic locking nor the DB will catch it. The read in `approveReview()` must therefore use the **already-existing** `CoachReviewRepository.findByIdForUpdate()` (`CoachReviewRepository.java:23-25`) so the second caller blocks until the first commits and then observes `APPROVED`. This needs no migration and no new repository method
   **And** the following consequence is **accepted, not a defect**: `approveReview()` and `blockReview()` are the only two callers of `reviewFlagRepository.resolveAllOpenFlags()` (verified), and `ReviewFlagService.java:76-83` only auto-holds a review when `openFlagCount >= threshold` (default 3) — so an `APPROVED` review carrying 1–2 open flags stays `APPROVED` with those flags open, and this AC removes "re-approve" as a way to clear them. This is acceptable because the admin queue lists only `UNDER_REVIEW` reviews (`AdminReviewService.java:43-44`), so no UI surfaces those reviews; the endpoint is reachable by ID alone. Do not add a flag-clearing side door to satisfy this — if it needs solving, it is a separate story

2. **Given** `AdminReviewResource` (package `com.softropic.skillars.platform.admin.api`) throws an `OperationNotAllowedException` or `MethodArgumentNotValidException` for a review-domain error (e.g. the new AC1 conflict)
   **When** that exception propagates from the controller
   **Then** it is handled by `ReviewApiAdvice`'s existing review-shaped logic, not the global `ApiAdvice` handler
   **And** this is achieved by adding `assignableTypes = AdminReviewResource.class` to `ReviewApiAdvice`'s `@RestControllerAdvice` annotation — **not** by widening `basePackages` to all of `com.softropic.skillars.platform.admin.api`, which also contains `AdminDisputeResource`, `AdminGdprResource`, `AdminCoachEnforcementResource`, `AdminModerationResource` and others whose errors must keep going through their own/global handling
   **And** the existing `AdminReviewQueueIT.approveReview_notFound_returns404WithConsistentErrorShape` test (which asserts `errorKey":"RESOURCE_NOT_FOUND"` from the *global* handler) continues to pass unmodified — `ReviewApiAdvice` has no `ResourceNotFoundException` handler, so that exception type still falls through to the global advice exactly as today
   **And** the **side effect on `POST /api/admin/reviews/{id}/block` is explicitly specified and pinned by a test**, because `assignableTypes` routes *every* exception from that controller to `ReviewApiAdvice` — not just the AC1 conflict. `blockReview` takes `@Valid @RequestBody BlockReviewRequest` (`AdminReviewResource.java:61`), whose sole field is `reason`, not `body` (`record BlockReviewRequest(@NotBlank @Size(max = 500) String reason)`). A blank or over-length `reason` therefore misses `handleValidation()`'s `hasSizeViolationOnBody` branch (`ReviewApiAdvice.java:46-54`) and lands in the generic branch, returning `errorKey: "reviews.validationError"` in place of whatever the global `ApiAdvice` returns today. No existing test asserts that endpoint's validation shape, so this change would otherwise land silently. Add an `AdminReviewQueueIT` test asserting the post-change response shape for a blank `reason`, and treat that shape as the endpoint's contract from here on

3. **Given** a coach's profile is `ACTIVE` (or `REDUCED`/`PENDING_REVIEW`) at the moment `createBookingRequest` performs its first, unlocked status read
   **When** an admin suspends that coach after that read but before `coachProfileRepository.findByIdForUpdate(req.coachId())` (the per-coach lock acquired later in the same method, immediately before the overlap check) succeeds
   **Then** the booking request is rejected with the same `BookingError.COACH_UNAVAILABLE` (or `SecurityError.MISSING_RIGHTS` for other non-active statuses) used by the earlier check — by re-validating the coach's status **against a genuinely re-read row** before proceeding to the overlap check, not only on the earlier unlocked read
   **And** the re-read must be explicit, because simply calling `getStatus()` on the object returned by `findByIdForUpdate` **is a no-op**: `BookingService.java:155` has already loaded that same row via `findById`, making it managed in the persistence context, and `findByIdForUpdate` is a JPQL `@Query` (`CoachProfileRepository.java:31-34`) — Hibernate acquires the `SELECT … FOR UPDATE` lock at the DB level, but when hydrating a row whose entity is already managed it returns the **existing instance without overwriting its in-memory state**. The re-check would read the same stale `status` and could never fire. Satisfy this AC by refreshing under the held lock (`entityManager.refresh(coach, LockModeType.PESSIMISTIC_WRITE)`) or by reading the status through a scalar projection query that bypasses the first-level cache — and state in the code comment which one and why, since the existing comment at `BookingService.java:195-198` ("The lookup result itself is unused beyond the lock it acquires") is what makes this trap easy to walk into
   **And** the test proving this **must be a real `@SpringBootTest` + `@Testcontainers` IT, not a mocked repository**. A mock returns whatever the test tells it to and would pass against a fix that does nothing in production — and mocking the DB is forbidden by the project's own testing rules. Contrast with AC1, where the locked read *is* the first read of the row in that method, so no refresh is needed there

4. **Given** `BookingStateMachine`'s current `PAYMENT_PENDING` transition map only contains `PAYMENT_CAPTURED` and `PAYMENT_FAILED`
   **When** a booking is stuck in `PAYMENT_PENDING` (payment never captured or failed — e.g. an app crash between the `INITIATE_PAYMENT` commit and the `AFTER_COMMIT` payment listener completing) and the parent calls the existing parent-cancel endpoint (`POST /api/bookings/{id}/cancel`, `CancellationResource.java:28-33`)
   **Then** `BookingStateMachine` allows `CANCEL_PARENT` from `PAYMENT_PENDING` to `CANCELLED_PARENT`
   **And** `BookingService.cancelBookingAsParent()` must **never** write a `BOOKING_REFUND` credit-ledger entry and must **never** restore a session-pack unit for **any** booking whose payment was not actually captured — expressed as a **whitelist, not as a `PAYMENT_PENDING` special case**: `refundEligible` may only be `true` when the pre-transition status is `CONFIRMED` or `UPCOMING`. The current computation at `BookingService.java:531` is purely time-until-session (`>24h`) with no status check at all, and must be gated behind that whitelist before the event is published
   **And** the whitelist form is required rather than an `if (status == PAYMENT_PENDING)` guard because **`ACCEPTED` carries the identical hole and is reachable today**: batch-accepted bookings rest in `ACCEPTED` (`BookingBatchService.java:159` issues only `ACCEPT`, never `INITIATE_PAYMENT`), `CANCEL_PARENT` from `ACCEPTED` is already permitted (`BookingStateMachine.java:27`), and no payment has been captured in that state — so a parent cancelling a batch booking more than 24h out currently receives a `BOOKING_REFUND` credit for money never taken, or a restored pack unit never deducted. A `PAYMENT_PENDING`-only guard would leave the story's own stated fraud vector wide open. The whitelist also happens to match the exact status set `applyRefundLogic` already uses (see AC4 note in Dev Notes), aligning the two refund models instead of adding a second special case
   **And** restoring an already-deducted session-pack unit for the narrow crash-*during*-deduction case is explicitly **out of scope** for this story (documented limitation — the original deferred item itself was accepted as "MVP acceptable"); do not attempt to solve it here. This scoping is sound and was re-verified: `acceptBooking` commits `PAYMENT_PENDING` at `BookingService.java:283-284`, and `deductSession` only runs afterwards inside the `AFTER_COMMIT` listener (`PaymentLifecycleService.java:62`) — so a booking stuck in `PAYMENT_PENDING` has, in the ordinary case, **not** had its pack unit deducted, and skipping restoration is correct rather than lossy

5. **Given** `SessionPackExhaustedEvent`'s constructor is invoked with `purchase.getParentId()` in `PackSessionService.deductSession()`
   **When** the event class exposes that value
   **Then** the field, constructor parameter, and getter are named `parentId` (not `playerId`) throughout `SessionPackExhaustedEvent.java` — a pure rename with no behavioral change, since the event has zero listeners today (verified 2026-08-04: only the class itself and the one publish call-site reference it)

6. **Given** a coach accepts a multi-slot batch via `POST /api/bookings/batches/{batchId}/accept-all` (`BookingBatchResource.java:48`)
   **When** `PaymentLifecycleService.onBatchBookingAccepted()` subsequently tries to settle those bookings
   **Then** each booking reaches `CONFIRMED` on success and `DECLINED` on payment failure, with **no** `BookingStateTransitionException` thrown — for both the pack-based branch (`confirmPackBatchPayment`) and the credit/Stripe branch (`confirmCreditBatchPayment`), and for the failure branch (`declineBatchBooking`)
   **And** this is achieved by making the batch flow issue `INITIATE_PAYMENT` after `ACCEPT`, exactly as the single-booking flow already does — **not** by adding `PAYMENT_CAPTURED`/`PAYMENT_FAILED` transitions from `ACCEPTED` to `BookingStateMachine`. The state machine's invariant that payment capture follows payment initiation must hold for both flows; teaching it to skip `PAYMENT_PENDING` would erase the "payment in flight" step from batch bookings' status history and leave the two flows permanently divergent
   **And** the duplicated accept-then-initiate sequence is **extracted into one method on `BookingService`** used by both callers, so the two flows cannot drift apart again — this divergence is the root cause of AC6 and re-implementing the pair inline in `BookingBatchService` would only reset the clock on it
   **And** the intermediate `ACCEPTED` `BookingStatusChangedEvent` is suppressed for the batch flow just as it is for the single flow (`transitionInternal(..., publishEvent = false)` on the `ACCEPT` leg, `true` on the `INITIATE_PAYMENT` leg), so batch bookings emit one status-change event per accept, not two
   **And** batch-status derivation is unchanged in behaviour: `BookingBatchService.POST_ACCEPTANCE_STATUSES` (`:55-58`) already contains **both** `ACCEPTED` and `PAYMENT_PENDING` (verified), so `updateBatchStatusFromBooking` computes the same `FULLY_ACCEPTED`/`PARTIALLY_ACCEPTED`/`DECLINED` result before and after this change. A test must pin that, because it is the one thing quietly relying on which of the two statuses a freshly-accepted batch booking holds

- **Tasks 4 and 5 attack the same root cause from two directions, and both are needed.** Task 5 makes batch bookings pass through `PAYMENT_PENDING` like every other booking, which incidentally brings them under Task 4's whitelist via the normal path. Task 4's whitelist is still written to cover `ACCEPTED` as well, because `ACCEPTED` remains briefly reachable inside the accept transaction and a whitelist does not rot when new statuses are added. ### Completion Notes List

**AC1 — idempotent review approval.** `approveReview()` now reads through `CoachReviewRepository.findByIdForUpdate()` and rejects an already-`APPROVED` review with `OperationNotAllowedException(ReviewErrorCode.ALREADY_APPROVED)` before any write. The pessimistic read is what makes this hold under an admin double-click; `CoachReview` has no `@Version` and the moderation log has no unique constraint, so nothing else would catch the second caller. As AC1 specifies, this is *not* symmetric with Task 2: here the locked read is the first read of the row in the method, so it returns fresh state and no `refresh` is needed.

**AC2 — error routing, and the contract it quietly changed.** `ReviewApiAdvice` now carries `assignableTypes = …AdminReviewResource.class` alongside its `basePackages`. The class is referenced fully-qualified rather than imported: there is no ArchUnit rule in this repo, but `admin.api` already depends on `reviews.contract`, and an import statement would have written the module cycle into the import list for no gain. `approveReview_notFound_returns404WithConsistentErrorShape` still passes unmodified, as predicted — `ReviewApiAdvice` has no `ResourceNotFoundException` handler.

The side effect on `POST /api/admin/reviews/{id}/block` is real and is now pinned by a test. Shapes for a blank `reason`, both captured from actual runs:

- **Before:** `{"helpCode":"<generated>","errorMsg":{"errorKey":"validation.invalidData","message":"Invalid Data"},"fieldErrors":[{"field":"reason","errorMsg":{"errorKey":"invalid.reason","message":"must not be blank"},"objectName":"blockReviewRequest"}]}`
- **After:** `{"helpCode":"reviews.validationError","errorMsg":{"errorKey":"reviews.validationError","message":"reason must not be blank"}}` — still HTTP 400, but the per-field `fieldErrors` array is gone. Any client reading `fieldErrors` off this endpoint would break.

**AC3 — coach-suspension race.** The locked lookup's result is now captured and `entityManager.refresh(lockedCoach, PESSIMISTIC_WRITE)` forces a genuine re-read before the status checks are repeated. This was the trap the AC warned about, and it is not theoretical: the IT was written first and failed against the un-refreshed code, because `findByIdForUpdate` takes the DB lock but hands back the same managed instance loaded earlier in the method. `EntityManager` is the one new collaborator on `BookingService`; the two unit tests that build the service by hand (`BookingServiceTest`, `ExpiredPackBookingValidationTest`) were given a mock for it.

**AC4 — refund whitelist.** `cancelBookingAsParent` now reads the pre-transition status and only lets `refundEligible` stay true for `CONFIRMED`/`UPCOMING`. Written as a whitelist, so `PAYMENT_PENDING`, `ACCEPTED` and any future pre-payment status are covered without being named. `applyRefundLogic` was left alone.

**AC5 — event field rename.** `SessionPackExhaustedEvent.playerId` → `parentId`. `PackSessionService` needed no edit at all — the argument is positional and was already `purchase.getParentId()` — so that file is **not** in the File List despite being named in the task.

**AC6 — batch accept, and two further defects found while proving it.** The premise reproduced, with one correction and two additions worth reviewer attention:

1. *The defect was silent, not loud.* The AC predicted every batch settle would throw `BookingStateTransitionException`. It does throw, but inside an `AFTER_COMMIT` listener where it is swallowed and logged — bookings simply sat in `ACCEPTED` forever with no error surfaced to the coach. `BookingBatchResourceIT` was passing against this the whole time, because it only asserted the *batch* row's status.
2. *`PaymentLifecycleService.onBatchBookingAccepted` was missing `REQUIRES_NEW`.* With the accept-then-initiate fix alone, bookings reached `PAYMENT_PENDING` and still never settled. During `AFTER_COMMIT` the accept transaction is still bound to the thread but already committed, so every nested `@Transactional` call joined it and lost its writes. Its single-booking sibling `onBookingAccepted` has carried `@Transactional(propagation = REQUIRES_NEW)` all along; the batch listener did not. **`BatchPaymentIT` could never have caught this** — it invokes the listener directly, with no surrounding transaction.
3. *`declineBatchBooking` needed its own transaction.* It only ever runs after a settle attempt has thrown, and that throw came from a nested `@Transactional` call which marked the shared batch transaction rollback-only — so the DECLINED write was rolled straight back. It is now `REQUIRES_NEW`.

They are annotation-only changes, no signatures touched, and **AC6's stated outcome (`CONFIRMED` on success, `DECLINED` on failure) is unreachable without them** — the spec's diagnosis was correct but incomplete. Flagging explicitly rather than burying it: a reviewer who disagrees can revert items 2–3 and AC6 will regress to "bookings reach PAYMENT_PENDING and stop there".

**Known limitation, unchanged and now better understood.** The story documents that `acceptAll`'s per-booking catch cannot isolate a failure because the shared transaction is marked rollback-only. The same mechanism affects the settle loop: in a *mixed* batch where one booking's payment fails, the failure poisons the batch transaction and the other bookings' settlements are rolled back with it. The all-succeed and all-fail paths are both covered by `BatchAcceptPaymentIT` and both behave correctly; the mixed case is a pre-existing isolation weakness that this story narrows but does not close. Worth its own follow-up — settling each booking in its own transaction is the real fix.

**Status-list consumers, deliberately not touched** (per Task 5): `PackSessionService.CONFLICT_STATUSES`, `CoachPlayerAuthorizationService`, and `GdprRequestService` all list `ACCEPTED` without `PAYMENT_PENDING`. **Pre-existing inconsistency noted for a future story** (per Dev Notes): the entity's `refundEligibility` string records `PARTIAL` for 6–24h parent cancellations while the event's boolean says not eligible, so no partial refund is ever actually issued. Untouched.
