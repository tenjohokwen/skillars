### AC1 — `ApiAdvice.integrityViolationHandler`: null-guard the constraint lookups **and** recover the exclusion-constraint case so the V87 double-booking backstop keeps returning `409 booking.slotUnavailable`.

Closes: *"`ApiAdvice.integrityViolationHandler` throws NPE on a null constraint name"* — `deferred-work.md` § "code review of skillars-deferred-89" (2026-09-01). **Re-rooted per `story-review.md` F1 (blocker).**

- **Corrected root cause.** Hibernate `PostgreSQLDialect`'s templated constraint-name extractor templates a name for exactly four SQLSTATEs — **`23502 / 23503 / 23505 / 23514`**. `23502` (NOT NULL) and `23514` (CHECK) **do** return a name — the original premise was wrong. The `lookupswitch` also carries a fifth case, **`23001` (RESTRICT violation), which branches straight to `aconst_null`** — i.e. it is explicitly mapped to `null`, not templated (R2). The genuine null triggers are therefore **two**:
  1. **SQLSTATE `23P01` (`exclusion_violation`)** — not in the `lookupswitch` at all, so `Integer.parseInt("23P01")` throws `NumberFormatException`, which `TemplatedViolatedConstraintNameExtractor.extractConstraintName` catches and converts to `null`. This codebase has exactly one exclusion constraint: `excl_bkg_coach_slot_overlap` (`src/main/resources/db/migration/V87__booking_overlap_exclusion_constraint.sql:15`).
  2. **SQLSTATE `23001`** — mapped to `null` by the dialect. No current constraint raises it; it is the natural input for the "genuinely-unmappable" test below.
- **Consequence today.** The `excl_bkg_coach_slot_overlap` entries in `CONSTRAINT_MAPPINGS` (`ApiAdvice.java:142`) and `CONFLICT_CONSTRAINTS` (`:155`) are dead code — the name arrives `null` and `getOrDefault(null, …)` / `contains(null)` on the `Map.of` / `Set.of` NPEs first. Corroborated by `RescheduleResourceIT.java:412-416` javadoc (*"an unmapped 500 rather than the clean `booking.slotUnavailable`"*). The only write paths without an app-layer overlap pre-check — `BookingBatchService`, `RescheduleService` — hit exactly this.
- **Fix:**
  1. Guard `constraintName == null` before both immutable-collection lookups (`ApiAdvice.java:159-176`).
  2. **Before falling through**, recover the exclusion case: either `extractUsingTemplate("violates exclusion constraint \"", "\"", <sqlException.getMessage()>)`, or map SQLSTATE `23P01` directly → `booking.slotUnavailable` + `HttpStatus.CONFLICT`.
  3. A genuinely-unmappable `null` (not `23P01`, no recoverable name) → the existing `generic.dataError` / `400` branch.
- **Correct the exposure claim.** `/resend-otp` is **not** an ingress-exposed crash: `uq_pot_one_active_per_user` is a partial unique index (`V121__phone_otp_tokens_one_active_per_user.sql:30-32`) → SQLSTATE `23505` → name extracted normally → no NPE. Keep the null-guard for defensiveness; drop the "newly reachable unauthenticated" framing.
- **No new i18n work needed (R3).** `booking.slotUnavailable` already exists in **all four** backend bundles — `messages_en.properties:124`, `messages_de.properties:67` ("Dieses Zeitfenster ist nicht mehr verfügbar."), `messages_fr.properties:112`, `messages.properties:78`. The new 409 renders localized text out of the box. **Do not add a duplicate key during AC12's bundle pass** — `booking.slotUnavailable` is one of the 82 keys `messages_de` already carries.
- **Tests (`ApiAdvice` slice, no new context):** (a) `ConstraintViolationException` with `getConstraintName() == null` **and** a non-`23P01` SQLSTATE (use `23001`) → clean `400` + `generic.dataError`, no NPE; (b) a real `excl_bkg_coach_slot_overlap` breach (SQLSTATE `23P01`, null name) → `409` + `booking.slotUnavailable`. Prefer an IT that provokes the constraint on the `BookingBatchService` / `RescheduleService` path so the regression is pinned in both directions.

### AC2 — a blank `user=` cookie no longer counts as an authenticated session (frontend: live fix; backend: hardening, **sentinel** not skip).

Closes: *"`user=` with an empty value counts as authenticated"* — `deferred-work.md` § "code review of 1-7-session-refresh-mechanism-fix" (2026-09-02). **Adjusted per `story-review.md` F3 (blocker) + F24 (severity).**

- **Frontend (the live half).** `App.vue`'s `isAuthenticated()` (`:22`) does `document.cookie.split(';').some((c) => c.trim().startsWith('user='))` — `startsWith('user=')` is `true` for a zero-length value. Change to require a non-empty value.
- **Backend (defense-in-depth — F24).** `first_name TEXT NOT NULL` (`V10__security_schema.sql:30`) → the claim chain (`JwtManagerImpl.java:219-220` ← `TokenCreatorImpl.java:58` ← `Principal.java:154` ← `user.getFirstName()`) cannot yield `null` for a persisted user; the one `displayName("")` (`ClaimsExtractorImpl.java:94`) is the ANONYMOUS principal, which never reaches `createLoginCookies`. An **empty / whitespace** `first_name` may still be reachable — **first verify the registration DTO validation** before calling this a live defect.
- **Fix must use the sentinel option (F3), not "skip".** When `displayName` is blank (`StringUtils.isBlank` — covers the `""` source too), write a documented **sentinel** value into the `user` cookie in `JwtManagerImpl.createLoginCookies` (`:217-220`) / `CookieUtil` (`:17-25`). Skipping the cookie would make `isAuthenticated()` return `false` for a valid session and (per AC3 / F3) make AC3's liveness check force a logout.
- **The sentinel is USER-VISIBLE — third file in scope (R4).** `DashboardPage.vue:44-49` reads the cookie's **value** and renders it as the dashboard greeting:
  ```js
  function getUsernameFromCookie() {
    const match = document.cookie.match(/user=([^;]+)/);
    if (match) { try { return decodeURIComponent(match[1]); } catch { return match[1]; } }
    return 'User';
  }
  ```
  Left alone, a blank-`displayName` user is greeted by the sentinel string. Fix: have this reader treat the sentinel (and blank) as "no name" so it falls through to its **existing** `'User'` default. Pick a sentinel that is unambiguous and never a real first name, and define it as a shared constant on both sides (backend `SecurityConstants`, frontend) — do not duplicate a magic literal.
- **Anchor that regex while in the file (R4).** `/user=([^;]+)/` is unanchored, so it also matches `xuser=…` — the exact substring bug `App.vue:21`'s own comment warns about. Change to `/(?:^|;\s*)user=([^;]*)/`. (The empty-value half is accidentally safe today: `[^;]+` requires ≥1 char, so a bare `user=` already falls through to `'User'`.)
- **Consolidation (recommended, not required).** The `user` cookie now has six hand-rolled consumers — cleared with the same literal at `App.vue:29`, `useSession.js:70`, `boot/axios.js:49`, `MainLayout.vue:312`; presence-checked at `App.vue:22`; value-read at `DashboardPage.vue:45` — and AC3 adds a seventh. Since this AC is explicitly hardening the cookie's contract, extract one shared `readUserCookie()` / `clearSessionCookies()` helper here and route all consumers through it; that is what prevents the next drift.
- **Framing:** one live frontend fix + one backend hardening — not a shipped-bug pair.
- **Tests:** backend unit test on the blank-`displayName` path asserting the sentinel is written; frontend by code-read + build, confirming the dashboard greeting shows `'User'` (not the sentinel) for a blank display name.

### AC3 — a sibling browser tab stops rendering an authenticated UI once the shared session cookies are cleared — **without logging out anonymous visitors**.

Closes: *"A sibling tab keeps rendering an authenticated UI after another tab logs out"* (§ "code review (round 2) of 1-7b") and the defense-in-depth *"Legacy fallback fails open on the 401 path"* (§ "code review of 1-7b" round 1), both 2026-09-02. **Re-scoped per `story-review.md` F2 (blocker).**

- **Root cause.** When `rint` is **absent or present-but-expired**, `computeTimeUntilExpiry()` (`sessionManager.js:88-89`) returns the local `LEGACY_SESSION_TTL - (now - lastActivityTime)` estimate, which the axios **request** interceptor re-arms on every outgoing request. Nothing re-checks cookie presence after mount.
- **`tick()` is not interval-only (F2).** It is invoked from `boot/axios.js:126` (response **success** interceptor) and `:142` (response **error** interceptor) via `refreshExpiryState()` (`sessionManager.js:100` — literally `tick()`), on **every** request through `api`, authenticated or not (login POST, registration, OTP resend, marketplace browsing). The `session:expired` listener is registered unconditionally at `App.vue:46`, *before* the `isAuthenticated()` gate at `:49`. A naive "cookie absent → dispatch `session:expired`" would bounce the public marketplace and the login page itself to `/login?expired=true` on their first API call.
- **Fix — the "session looks dead" branch fires only when ALL of:**
  1. monitoring is actually active (`checkIntervalId !== null`);
  2. `rint` has been observed **in this browser tab** — a durable flag in **`sessionStorage`** (per-tab, survives reload, dies with the tab). Module-level state is lost on reload and re-opens the bug (F2): after tab A logs out and tab B reloads, a module flag is `false` again and the missing-cookie branch can no longer tell "legacy backend" from "dead session".
  3. the session cookie (the AC2-hardened `user` check) is now absent.
  When `rint` was never seen this tab (legacy backend), keep the local-TTL fallback.
- **The 60-second window (F2).** `rint` is written with `maxAge = JWT_TTL + 60s` (`JwtManagerImpl.java:241-245`), so for ~60s after real expiry a cookie-presence check still sees `rint`. That case is already handled by the existing `remaining <= 0` path (`:88-89`); the new branch only adds the **cleared-cookie** case, so it does not need to reason about the expired-but-present window.
- Closes the round-1 "fallback fails open on 401" item via the same `sessionStorage` `rint`-seen flag.
- Verify `boot/axios.js:151`'s `errorKey` gate (`security.sessionExpired || security.unauthorized`) still tears the session down on the primary 401 path; note the interaction in Dev Notes.

- **Approach — option (a) with a durable outbox. Option (b) is REJECTED (R1).** v0.2 briefly preferred option (b) ("cap + batch in-transaction"); the re-check found it cannot deliver, because **no bulk-delete capability exists anywhere in the storage stack**:
  | Layer | Signature |
  | --- | --- |
  | `infrastructure/blobstore/service/StorageService.java:11` | `void delete(String key)` — single key |
  | `infrastructure/blobstore/service/S3StorageService.java:115-116` | `s3Client.deleteObject(...)` — singular, **not** `deleteObjects` |
  | `platform/filestorage/service/FileStorageService.java:324` | `deleteRawBytes(String storageKey)` — single key |
  Consequently, under option (b): **"batch" is not implementable** (every delete stays one blocking S3 round-trip); **"cap" breaks the erasure guarantee** (it deliberately leaves PII objects undeleted with no re-drive record — the outcome this AC says it must not weaken); and **the defect is not fixed either way**, because the DB connection is still held across N sequential blocking S3 calls. "Fewer calls" is not "stops scaling with report-history size", which is the ledger item being closed.
- **Required shape (option a):**
  1. Inside the erasure transaction, write every storage key due for deletion into a **durable pending-deletion table** (e.g. `main.pending_blob_deletions` — `storage_key`, `created_at`, `attempts`, `last_error`). This is what makes a post-commit S3 failure re-drivable; an in-memory `List<String>` + `log.warn` is not (the keys die with the JVM and nothing in the DB can enumerate the orphans).
  2. Commit the DB deletion.
  3. Drain the table from an `@TransactionalEventListener(AFTER_COMMIT)` step, deleting each row as its S3 delete succeeds and leaving failures in place with an incremented `attempts` for the next sweep. **The listener runs after the transaction is closed, so its outbox writes need `@Transactional(propagation = REQUIRES_NEW)`** — without it the row deletes are non-transactional and silently no-op.
  4. **Dogfood AC10:** that table's migration must pass this story's own lint guard (additive `CREATE TABLE`; any index needs `CONCURRENTLY` or the `-- migration-lint: allow-blocking-index <reason>` opt-out).
- **If the team instead wants option (b)**, it must be re-scoped to include **adding a bulk-delete method** to `StorageService` / `S3StorageService` (AWS `DeleteObjects`, up to 1000 keys/call) and the word **"cap" must be dropped entirely** — a capped GDPR erasure is not an acceptable outcome. Recorded as the fallback, not the plan.
- **Tests:** for `getConversations` (COACH **and** PARENT branches) and `listPendingApprovals` — an IT asserting query count is O(1) in row count (Hibernate statistics / datasource-proxy) with a multi-row fixture + an unchanged-response assertion. For the GDPR path — "the connection isn't held" is not IT-assertable (F14); instead assert, with an N-report fixture: (i) the pending-deletion rows are written **inside** the erasure transaction, (ii) the AFTER_COMMIT listener observes the report rows already deleted, (iii) a forced `deleteRawBytes` failure leaves its pending-deletion row behind with `attempts` incremented (the re-drivability guarantee), and (iv) a successful drain empties the table.
