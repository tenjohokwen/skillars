## Acceptance Criteria

### AC1 — the concurrent-duplicate-SLU-delivery collision on the **existing** `uq_player_skill_stats_session_skill` index becomes a clean idempotent no-op instead of a retry storm + false alarm.

**Problem** (verified against source at `dab5b88`): `PlayerSkillStat` (`src/main/java/com/softropic/skillars/platform/development/repo/PlayerSkillStat.java`) is `@Table(schema = "development", name = "player_skill_stats")`, `@Id @GeneratedValue(GenerationType.UUID) UUID id`, columns `player_id` (Long TSID), `session_id` (UUID, **nullable**, `updatable = false`), `coach_id`, `skill_code` (`length = 10`, `updatable = false`), `slu_value`, `calculated_at`. One `SluCalculationService.onBookingCompleted` invocation writes exactly one row per distinct `skill_code` for one `session_id`. The guards against a duplicate `BookingCompletedEvent` delivery are non-locking reads: `SluCalculationService.onBookingCompleted:80` (`sluRepository.findBySessionId(...).isEmpty()`) and `SluPersistenceRetrier.saveSluWithRetry` (`existsBySessionId(...)`, `skillars-deferred-86` AC2).

**The DB uniqueness key this story was originally scoped to add already exists.** `src/main/resources/db/migration/V47__player_skill_stats_unique_constraint.sql` (Story 5.1 review) is:

```sql
CREATE UNIQUE INDEX uq_player_skill_stats_session_skill
    ON development.player_skill_stats (session_id, skill_code)
    WHERE session_id IS NOT NULL;
```

— column-for-column and predicate-for-predicate the index scoped as `V122`. It is never dropped; `player_skill_stats` is created in `V46` and never altered since. So **the permanent double-write cannot happen** — when two deliveries race the check-then-`saveAll`, the losing `saveAll` is rejected by `V47` with PG `23505`. Both this story's creation pass and all three `skillars-deferred-86` review layers missed `V47`.

**What is still open — the collision *behaviour*.** `DataIntegrityViolationException extends NonTransientDataAccessException extends DataAccessException`, and `SluPersistenceRetrier.java:58` already has `retryFor = {DataAccessException.class, …}`. So today the losing `saveAll`'s `23505` **is retried** — 3 attempts, each a guaranteed-fail insert, each preceded by a `@Backoff` sleep on the bounded `sluRetryExecutor` — then lands in `recoverSluSaveFailure(DataAccessException, …)`, which logs `"… rows lost for session … manual recovery needed"` **for rows that are in fact persisted by the winning delivery**. False alarm + wasted retries.

**Fix (no migration):**

- **`SluPersistenceRetrier.saveSluWithRetry`** — wrap the `saveAll` (the actual flush point) in a catch that identifies the `uq_player_skill_stats_session_skill` collision **specifically** and treats it as the idempotent no-op it is:
  - Catch `DataIntegrityViolationException`, unwrap to the underlying `org.hibernate.exception.ConstraintViolationException` (mirroring `ApiAdvice.java:163-169`'s existing pattern), and compare `getConstraintName()` against `"uq_player_skill_stats_session_skill"`.
  - **On a match:** `log.info` "SLU detail rows for session {} skipped — already persisted by a concurrent delivery" and **return normally** (which, under AC2, means return `true`).
  - **On any other constraint** (FK on `skill_code` — `SluCalculationService.java:120-122` explicitly pre-filters to avoid it, but it is the guarded-against case; PK; NOT NULL): **re-throw**, so it retries and recovers exactly as it does today. A blanket `catch (DataIntegrityViolationException)` that swallows every constraint would let `saveSluWithRetry` return `true` for a session with **zero** persisted rows and defeat AC2 — do not do that.
  - **Do not** widen or narrow `@Retryable`'s `retryFor`/`noRetryFor`. The in-method catch is the whole fix; `23505` for this constraint never reaches `@Retryable` because the catch consumes it, and every other `DataAccessException` still retries.
  - Record in the AC and the class javadoc: the catch works **because `saveSluWithRetry` is not `@Transactional`** and `SimpleJpaRepository.saveAll` opens/commits its own transaction, so the constraint fires *inside* the call. A later `@Transactional` on the retrier would move the failure to commit time, outside the catch — flag that if anyone adds it.
  - Update the class javadoc's "Why a whole-method retry is safe" paragraph to name `uq_player_skill_stats_session_skill` as the concurrent-*delivery* backstop (the merge-on-detached reasoning it documents covers only the *retry* case, not two *distinct* deliveries).
  - Keep both `@Recover` overloads (AC2 changes their return type to `boolean`/`false`; nothing else).
- **`SluCalculationService.onBookingCompleted`** — no change required.
- **Do not** create `V122`. **Do not** change `PlayerSkillStat`'s field set, `updatable = false` flags, `@GeneratedValue`, or the `SluRepository` query set.
- **Known residual (record, do not fix here):** if a concurrent delivery persisted only a *subset* of skills (reachable if `slu.*.scale` config or `skill_definitions.active` changed between deliveries — both read per-invocation), the `23505` rolls back the whole batch and the extra skills are silently dropped. Same shape as the existing `existsBySessionId` short-circuit, so not a regression — the log line should read "skipped, rows already present", not assert equivalence.

**Tests:**

### AC2 — `SluPersistenceDispatcher` runs the weekly-snapshot write only when the SLU detail save actually succeeded.

**Problem** (verified against source): `SluPersistenceDispatcher.dispatchSluPersistence` (`src/main/java/com/softropic/skillars/platform/development/service/SluPersistenceDispatcher.java`) is:
```java
sluPersistenceRetrier.saveSluWithRetry(stats);
snapshotPersistenceRetrier.writeAllWithRetry(stats, isoYear, isoWeek);
```
`SluPersistenceRetrier.saveSluWithRetry` is `void`; both its `@Recover` methods are `void` and return normally on exhausted retries (logging `"… rows lost … manual recovery needed"`). So when the detail save is permanently lost, control still falls into `writeAllWithRetry`, which applies additive deltas to `player_slu_weekly_snapshot` and inserts V119 marker rows for a session that now has **zero** `player_skill_stats` rows. The dashboard fast-path (`player_slu_weekly_snapshot`) then shows SLU that `SUM(player_skill_stats.slu_value)` for that session cannot reproduce.

**Fix:**

- **`SluPersistenceRetrier.saveSluWithRetry`** — change the signature to return a `boolean` (`true` = rows are persisted, either by this call, the `existsBySessionId` short-circuit, or the AC1 concurrent-collision catch; `false` = **only** from the `@Recover` paths). Both `@Recover` methods return `false`. The happy path and both idempotent-skip paths return `true`.
  - **The `if (rows.isEmpty()) { return; }` early return at the top of the method must return `true`** — an empty batch is not a failed save, and returning `false` would fire the new AC2 ERROR on a benign empty list. (Production cannot reach it today — `SluCalculationService.java:169-173` returns before dispatching when `stats.isEmpty()` — but `SluPersistenceRetrierTest` / `SluRetrierProxyRetryTest` call the method directly.)
  - This is a small, self-contained contract change: `SluPersistenceDispatcher` is the **only** production caller (`grep -rn "saveSluWithRetry" src` — confirm; one production call site plus test callers).
