## Story

As a **coach**,
I want **to complete or correct a session recap after the fact, be reminded when one is missing, and know exactly who will read it**,
so that **"every completed session has a recap attached" becomes true and my notes are only seen by the people I expect**.

### G7 — Edit / resume a recap (backend)

1. **Read endpoint.** `GET /api/bookings/{id}/recap` → `SessionRecapResponse(UUID bookingId, String whatWeDid, String whatsNext, String whatWentWell, boolean editable, Instant editableUntil)`. New `SessionRecapResource` in `platform.booking.api` (mirror `CoachPlanNoteResource`: `@Observed(name = "booking.sessionRecap")`, `@PreAuthorize(SecurityConstants.HAS_COACH_ROLE)`, caller resolved via `securityUtil.requireCurrentUserId()`). Only the owning coach may read; a non-owner gets what `BookingCompletionService.verifyCoachOwnership` produces (`OperationNotAllowedException` → HTTP 403 with the fixed default message; a 404 only comes from `getBookingOrThrow`/`resolveCoach`). Never returns another coach's data. `editable` is computed by the SAME service-level check the PUT uses (AC3), not by the `Booking` predicate alone.
2. **Write endpoint.** `PUT /api/bookings/{id}/recap`, body `UpdateSessionRecapRequest(@NotBlank @Size(max = 500) String whatWeDid, @NotBlank @Size(max = 500) String whatsNext, @Size(max = 500) String whatWentWell)`, response = the same `SessionRecapResponse`. Service method `BookingCompletionService.updateRecap(UUID bookingId, Long coachUserId, UpdateSessionRecapRequest req)`, `@Transactional`.
   - Preconditions, in this order: coach resolves + owns the booking; **the coach's `User` is not erased/locked** (`GdprErasureService` keeps the `coach_profiles` row and only sets `user.setLocked(true)`, `GdprErasureService.java:~392`; `resolveCoach` still succeeds after erasure and the JWT fast path does no DB check, so an erased coach's token can stay valid for minutes — this explicit guard is required, the profile failing to resolve cannot be relied on); booking status is exactly `COMPLETED` (a `COMPLETED_PENDING_CONFIRMATION` booking uses the resume path, AC7a); a `SessionCompletionData` row exists (else `ResourceNotFoundException`); the booking's player is not erased (`PlayerProfile.developmentDataErasedAt` null); `now` is inside the **edit window** (AC3). Load the SCD row with a pessimistic write lock before the player-tombstone check so a concurrent player erasure (`anonymizeByPlayerId`, `GdprErasureService.java:~1524`) cannot interleave; this method writes only the SCD row, so the REQUIRES_NEW row-lock trap below does not apply.
   - Writes `whatWeDid`, `whatsNext`, `whatWentWell` on the existing row. **Does NOT touch `playerAttended`, ratings, `homeworkDrillIds`, `completionMode`, or the booking state/payout.** (Attendance of a sweeper-placeholder stays `false` — see Open Question 1.)
   - Both `whatWeDid` and `whatsNext` stay `@NotBlank` (parity with `WrapUpRequest`); `whatWentWell` blank → stored as `null`.
3. **Bounded edit window.** New `ConfigBounds.BoundedKey BOOKING_RECAP_EDIT_WINDOW_DAYS = new BoundedKey("booking.recap.editWindowDays", 7L, 365L, false, "<risk text>", 30L)` (min 7, not 1: the stuck-completion sweeper can create the placeholder up to `booking.stuck_completion_timeout_hours` (default 72h, max 720h) after the booking's last update, so a window shorter than that makes a swept session born un-editable and un-nudged; document the coupling in the key's Javadoc and add a test that the default window exceeds the default sweeper timeout), registered in **both `HAS_CODE_DEFAULT` and `ConfigBounds.ALL`** (`ConfigBounds.java:~435` and `~459`; `ConfigBoundsEnumCoverageTest.hasCodeDefaultKeysAreAllRealBoundedKeys` fails otherwise) and read via the 4-arg `getBoundedLong(key, default, min, max)` (out-of-range falls back to the default, it does not clamp) — copy the shape of `DEVELOPMENT_ROSTER_DORMANT_AFTER_DAYS` (`ConfigBounds.java:185`) exactly. Window = `now` (via `ClockProvider`, a 12-6 precedent; `BookingCompletionService`/`QuickCompleteTimeoutService` still use bare `Instant.now()`, do not copy that) strictly before `booking.requestedEndTime + N days`. Two layers, one source of truth: `Booking.isRecapEditable(Instant now, long windowDays)` (status `COMPLETED` **and** inside window; decide `requestedEndTime == null` explicitly: `isPrepNoteEditable`, `Booking.java:116`, treats null as open, here treat it as closed) is the pure part; `BookingCompletionService.recapEditability(...)` adds the erasure checks (coach user erased/locked, player `developmentDataErasedAt`) and returns verdict + reason. BOTH the PUT guard and the GET `editable`/`editableUntil` call the service method, so they can never disagree (a bare `Booking` predicate would report `editable=true` for an erased player and the dialog would open, then fail on save). Outside the window → `OperationNotAllowedException` carrying a NEW `BookingError.RECAP_EDIT_WINDOW_CLOSED` code (precedent: `BOOKING_NOT_EDITABLE`/`SESSION_ALREADY_ENDED`, `BookingService.java:~786-793`). The exception *message* never reaches the client: `ApiAdvice.operationDeniedHandler` returns a fixed default plus the `ErrorCode` key (still HTTP 403), so the dedicated text is an i18n mapping of that `errorKey` in the dialog (x3 locales). Tests assert the `errorKey`, not just the status. Use a second code (or the same) for the erased cases.
4. **Propagation, no second event.** An edit must update `development.player_timeline_events.metadata` of the **existing** `SESSION_COMPLETED` row for that `reference_id = bookingId`, never insert a second event (a second `SESSION_COMPLETED` would double-count the session in the timeline, the roster and the access clock). Cross-module rule: `booking` MUST NOT import `development` repos. Mechanism: `booking` publishes a new `SessionRecapUpdatedEvent(UUID bookingId, UUID coachId, Long playerId)` (ids only, see the re-read rule below) (in `booking.contract`), and a new `@TransactionalEventListener(AFTER_COMMIT)` + `@Async("taskExecutor")` method `TimelineEventListener.onSessionRecapUpdated` calls a new `@Transactional(REQUIRES_NEW)` `updateSessionRecapMetadata(...)` via the existing `self` proxy (not a direct call: only calls through `self` get the `REQUIRES_NEW`; same shape as `onBookingCompleted`, `TimelineEventListener.java:42-73` — failures are logged, never thrown back to the caller).
   - New native `@Modifying` query on `PlayerTimelineRepository`: `UPDATE development.player_timeline_events SET metadata = <merge> WHERE player_id = :playerId AND reference_id = :bookingId AND event_type = 'SESSION_COMPLETED' AND metadata->>'coachId' = CAST(:coachId AS text)`; `player_id` is there so the existing `(player_id, occurred_at)` index (V138:3334) serves it, since there is NO index on `reference_id`. `PlayerTimelineEvent.metadata` is `updatable = false` on the entity (`PlayerTimelineEvent.java:48`) — a JPA `save` of a mutated entity silently does NOT persist, so this MUST be a native/JPQL bulk statement. Build the merged JSON with `||` for present keys and `-` for keys now blank (a blank `whatWentWell` must REMOVE the key, not store `""`); `jsonb_exists`, not the bare `?` operator (see the comment at `PlayerTimelineRepository.java:57-61`).
   - **`NativeModifyingVersionAuditTest` needs nothing here:** it only audits UPDATEs on tables backing an `@Version` entity (`if (entitySimple == null) continue; // not a versioned table`), and `player_timeline_events` has no version column. Do NOT add `version = version + 1` (no such column) and do not add an opt-out.
   - **Re-read, don't trust a payload (ordering + erasure race):** the listener MUST re-read the current `SessionCompletionData` row by `bookingId` and build the metadata from THAT. Two quick edits on the multi-thread `taskExecutor` could otherwise apply out of order (blind overwrite; SCD has no version), and an edit committed just before an erasure could re-add keys after the scrub. Reading the row in the listener makes the timeline converge on the SCD source of truth, and an erased (nulled) row naturally yields a key-stripping update.
   - **Siloing:** the update is keyed on `metadata->>'coachId'` = the editing coach, so another coach's event for the same booking (impossible today, but defence in depth) can never be touched.
   - **GDPR tombstones:** coach erasure nulls the SCD recap columns and strips the metadata text keys but keeps `coachId` in metadata and keeps the profile row (see AC2), so the explicit user-erased/locked guard is what rejects the edit. Add an IT: erase a coach, then `PUT` → rejected, SCD and timeline metadata unchanged. Player erasure (`anonymizeByPlayerId`) must not be resurrected either: `updateRecap` rejects when `PlayerProfile.developmentDataErasedAt` is set (`PlayerProfileRepository` is already injected in `BookingCompletionService`).
5. **Eventual-consistency is accepted but observable.** If the timeline row is missing (event write failed originally), the listener logs a `WARN` with the bookingId and does nothing — it does NOT create one. The `session_completion_data` row is the source of truth; document this in the listener's comment.

### G8 — Nudge for sessions without a recap

8. **Missing-recap definition + endpoint.** A completed session "has no recap" iff its booking is `COMPLETED`, belongs to the calling coach, inside the edit window (AC3), and its `session_completion_data` row has `what_we_did IS NULL AND whats_next IS NULL`, **and the booking's player is not erased** (`player_profiles.development_data_erased_at IS NULL`; player erasure nulls both columns too, so without this filter erased players' sessions would nag for the whole window and every "Add recap" would be rejected). (Since 12-2 the wizard requires both fields, so null recaps come only from the stuck-completion sweeper placeholder and pre-V159 legacy rows; the window makes legacy rows age out instead of nagging forever.) New `GET /api/bookings/coaches/me/recaps-missing` → `MissingRecapsResponse(int count, List<MissingRecapItem> items)`, `MissingRecapItem(UUID bookingId, Long playerId, String playerName, Instant sessionDate)`; `items` capped (constant 50, most recent first, deterministic `ORDER BY requested_end_time DESC, id DESC`), `count` is the true total. Drive the query from `Booking` (indexed by coach) joined to `SessionCompletionData` by `booking_id` — `session_completion_data` has NO index on `coach_id` (only `idx_scd_booking_id`, V138:3280), so do not drive it from the SCD side. `@PreAuthorize(HAS_COACH_ROLE)`, `@Observed`. Player names via `BookingService.resolvePlayerNames(Collection<Long>)` (the batched "Deferred-81 AC1" helper, used by `getParentBookings`/`getCoachBookingRequests`). Do NOT copy `getCoachWeekSchedule`'s per-row `resolvePlayerName` (`:~634`): that is the N+1 this AC forbids.
9. **Command Center banner.** `CoachCommandCenterPage.vue` shows a banner "N sessions need a recap" (hidden at 0) with an expandable list (player, date, "Add recap" → AC6 dialog). After a successful save the list and count refresh. Five-state convention (loading/error/empty/data) as in `CoachReviewsPage.vue`. **Roster flag is out of scope** (the AC says "Command Center *or* roster"; the banner is the direct-action surface and avoids touching the capped roster fan-out that 12.10 owns).

### Non-obvious guardrails (the "why")

- **Native update, not entity save, for the timeline edit** — `updatable = false` makes `save()` a silent no-op that would pass a naive unit test and fail in production.
- **Event, not a direct repo call, for booking→development** — module boundary rule (`project-context.md`: modules communicate via contracts/events). The listener must be async + AFTER_COMMIT like its siblings so an unavailable timeline never fails the coach's save.
- **Edit window is anchored on `requestedEndTime`, not completion time** — there is no `completed_at` on `Booking`; `requestedEndTime` is the stable, indexed, already-used anchor (`isPrepNoteEditable` uses it). A sweeper-completed session can complete days after it ended; using `requestedEndTime` is slightly more conservative for the coach and is simple and deterministic. Do not add a column for it.
- **No second `SESSION_COMPLETED` event** — it would double-count in `PlayerTimelineEvent` listings, the roster's last-session clock and the report.
- **`whatWentWell` optional** — see AC10 (rolling-deploy + wizard friction). The *edit* endpoint does not require it either.
- **Voice step removal is bigger than "stop saving text"** — the step also uploads an audio blob to blob storage under the booking entity. Removing only the text would leave orphan audio uploads; remove the recorder and the upload calls. The existing audio files from past sessions are not touched (out of scope; there is no reader and no linking row, so nothing to migrate — note it in the ledger).
- **Denylist redaction (G25) is not fixed here** — 12.10 converts it to an allowlist. This story only adds the new key to the existing denylist and a regression test; do not refactor `redactRecapIfNotAuthoringCoach`.
- **Roster and `CoachPlayerLastSessionResolver` untouched** — 12.10 owns them.

### Open questions for the owner (do not block dev; defaults chosen)

1. **Attendance on recovery.** A sweeper placeholder has `playerAttended=false` (a system default, "no real signal"). `updateRecap` deliberately does not change it, so a recovered recap on a swept session appears in the **timeline, the report and the feed-forward suggestion** (AC16) but not as the prep card's *last-session* recap (that stays attended-gated by 12-3 AC3). If the owner wants the coach to also be able to confirm attendance while recovering, that touches the access clock and SLU and belongs in its own story. *Default taken: do not change attendance.*
2. **Edit window length.** Default 30 days, configurable via `booking.recap.editWindowDays` (7-365). *Default taken: 30.*
3. **Date/ordering of recovered recaps.** `TimelineEventListener.writeTimelineEvent` stamps `occurredAt = Instant.now()` (write time), so a swept session's event carries the sweep time (>= 72h after the session). With AC16, a recovered Monday `whatsNext` can outrank Wednesday's normally-completed one in `findLatestWhatsNextSuggestion` (`ORDER BY occurred_at DESC`) and be labelled with the sweep date; the report's Session Notes date has the same skew. *Default taken: accept and document (rare: only swept sessions); fixing it means putting the session end time into metadata and ordering/labelling by it, which is its own change.*

### Project rules that apply (`_bmad-output/project-context.md` and memory)

- DTOs are Java `record`s; every endpoint `@PreAuthorize` with `SecurityConstants`; `@Observed` on resources; Jakarta validation on request records; Flyway only, expand/contract (`docs/deployment/migration-conventions.md`), `SET LOCAL lock_timeout`; `ClockProvider` for time (a 12-6 precedent, not a project-context rule).
- Frontend: `<script setup>`, `async/await`, Pinia for shared state, API in `src/api/*.api.js`, all strings in vue-i18n for **three** locales, Prettier mandatory.
- **ID spaces:** `Booking.playerId` is a `PlayerProfile` PK, not a User id; `Booking.coachId`/`SessionCompletionData.coachId` are `coach_profiles.id`, the caller's `userId` is not. Resolve the coach through `resolveCoach(userId)` as `submitWrapUp` does.
- **REQUIRES_NEW row-lock trap:** `updateRecap` writes `session_completion_data`; the timeline write is a *separate async* transaction on a *different table* — no same-row REQUIRES_NEW, so no 55P03 self-deadlock. Keep it that way: do not call the timeline `REQUIRES_NEW` method synchronously inside `updateRecap`'s transaction.
- **IT autocommit trap:** bare `jdbcTemplate` writes in an IT method body never commit (hikari auto-commit=false); wrap fixture writes in `transactionTemplate`.
- **Booking fixture CHECK:** `chk_bkg_end_after_start` — derive start/end from one `Instant`, never two `Instant.now()` calls.
- **Never run `mvn verify` locally**; GitHub CI is the gate. Targeted `mvn -o test -Dtest=...` / failsafe on specific ITs only.
- Prettier gate lives in `.github/actions/`; a failure blocks build-and-push — run `npx prettier --check` on touched frontend files.
