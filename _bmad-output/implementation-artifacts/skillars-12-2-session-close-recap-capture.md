# Story 12.2: Session-Close Recap Capture

Status: done

## Story

As a coach,
I want to jot a tiny structured note — what we worked on, and what's next — the moment I close out a session,
so that I have a real, private record of session content over time, and a later story can use "what's next" to pre-populate my prep for the next session.

## Acceptance Criteria

1. `WrapUpRequest` (`src/main/java/com/softropic/skillars/platform/booking/contract/WrapUpRequest.java`) gains two new required fields, `recapWhatWeDid` and `recapWhatsNext` (`@NotBlank @Size(max = 500)` each), submitted through the **existing** `POST /api/bookings/{id}/complete` endpoint — no new endpoint. A submission missing or blanking either field is rejected with `400`, the same as every other validated field on this request today. This applies identically whether `mode` is `LIVE` or `QUICK` — both already converge on this one endpoint and request shape.
2. Both fields are persisted on the **existing** `SessionCompletionData` row (`src/main/java/com/softropic/skillars/platform/booking/repo/SessionCompletionData.java`), which is already written 1:1 per booking at wrap-up time and already carries `voiceNoteText`/ratings/attendance. Two new nullable `varchar(500)` columns (`what_we_did`, `whats_next`) are added by an additive Flyway migration, matching the entity's `@Column(length = 500)`. No new entity or table is introduced.
3. When the (possibly deferred) `BookingCompletedEvent` for this booking is *published* — in-request, inside the same transaction, for both `LIVE` mode (immediately) and `QUICK` mode's two deferred triggers (parent confirmation, or the Quick-Complete timeout job) — the already-captured recap text travels on that event. The event is always *delivered* to the timeline listener **asynchronously**, after that publishing transaction commits (`@TransactionalEventListener(AFTER_COMMIT)` + `@Async`) — this is pre-existing behavior unchanged by this story, and true for every mode, not just `QUICK`. The listener writes the recap into the **existing** `PlayerTimelineEvent` row of type `SESSION_COMPLETED` for that booking, inside its **existing** `metadata` JSONB field (alongside the already-present `coachId` key). No new timeline event type, no new table.
4. On read (`GET /api/development/players/{playerId}/timeline`), the recap's `whatWeDid`/`whatsNext` metadata keys are visible **only** to the authoring coach — the coach whose id matches that `SESSION_COMPLETED` event's own `coachId` metadata value. They are **stripped** for every other viewer: any other coach with (non-expired) read access to this player's timeline, **and** the player/parent viewing their own timeline. This matches the source brainstorm's own framing (see Dev Notes "Pre-Implementation Review Resolution" for why an earlier draft of this story read it differently): Theme 4 says raw session notes "stay private per coach" (contrasted explicitly with aggregate signals, which *are* shared); Priority 2's success indicator says the recap should be "visible back to **the coach**" (coach only — no parent/player mention); and the recap's second use was "chosen explicitly **over a parent-visible summary for now**" in favor of the Fast-Follow report-generation tie-in. Practical consequence: since no coach-facing page renders `PlayerTimelinePanel.vue` yet (Priority 4, a separate future story), this recap is not visible through **any** UI to anyone for the duration of this story. **Code-review correction (D1, 2026-10-15):** capture is unconditional, but read access is not — `GET .../timeline` gates every coach behind `TimelineQueryService`'s access-expiry clock, which is computed from `player_skill_stats` (SLU rows) alone; a Quick-Complete-only coach never earns an SLU row (see `SluCalculationService.onBookingCompleted`'s early return), so that coach's own `GET` returns `accessExpired=true` with an empty event list despite the recap being durably captured. The recap is captured today for every mode; it is reliably *readable* via this API today only for coaches with an independently-qualifying SLU-bearing session. See "Known residual risks" and `deferred-work.md` for the accepted fix-later rationale.
5. The recap is captured inside the existing coach wrap-up wizard, `WrapUpSequence.vue`, as a new step shown after the existing Homework step and before submission — two required text inputs, each capped at 500 characters client-side (matching the server-side `@Size(max = 500)`), with the submit button on that step disabled until both are non-blank and within the limit. This one wizard already backs both the Quick-Complete and the live-session End-Session paths (both already funnel into the same `POST .../complete` call), so no separate capture point is needed for either. A rejected submission must surface a visible error to the coach rather than leaving the wizard silently stuck open — today this call has no error handling at all, and this story's new required fields are the first ones on this request a coach can actually violate from the UI.
6. All new/changed user-facing strings (the new wizard step and its error message) are externalized via i18n in `en-US`, `de-DE`, and `fr-FR`.
7. The two pre-existing `submitWrapUp` ITs in `SessionCompletionResourceIT` (`submitWrapUp_liveMode_returns204AndStatusIsCompleted`, `submitWrapUp_quickMode_returns204AndStatusRemainsCompletedPendingConfirmation`) are updated to include the two new required fields in their request payloads, so they keep passing against the new `@NotBlank` validation this story adds rather than starting to fail it. Beyond that regression fix, test coverage must also exercise: the two new columns actually landing in `session_completion_data` (not just the HTTP status code), and at least one of the two **deferred** publish paths (`confirmCompletion` or the Quick-Complete timeout job) end-to-end — not only the `LIVE`-mode path, whose publish reads straight from the in-hand request and would stay green even if the `session_completion_data` persistence step were broken or omitted entirely.
8. Out of scope for this story, explicitly deferred to later Epic 12 stories per the source brainstorm doc — must not be implemented here: any frontend rendering of the recap (there is currently no coach-facing page for it to render on, and AC4's coach-only policy means the existing Player/Parent-facing `PlayerTimelinePanel.vue` must never render it either — rendering is deferred until Priority 4's coach-facing player-detail page exists to actually reuse that panel from a coach route); the Session Prep Card surfacing a prior recap's "what's next" when planning the next session (Priority 3); any new coach-facing page or route (this story adds **zero** new frontend routes); feeding accumulated recaps into `ReportGenerationService`/`PerformanceReportResource` (the Fast-Follow after this story); and the player/parent-initiated flag (permanently deferred).

### Review Findings

_Code review run 2026-10-15 (`/bmad-code-review`), three parallel layers (Blind Hunter / Edge Case Hunter / Acceptance Auditor) over the full 16-file uncommitted diff. 3 decision-needed findings were resolved by the owner on 2026-10-15; 7 patches, 4 defers, 8 dismissed._

#### Decision-needed — all three resolved 2026-10-15

- [x] **D1 — The authoring coach cannot read their own recap back in the common case.** `TimelineQueryService.getTimeline` gates every coach read behind `sluRepository.findLastSessionDate(playerId, coachId)` (`TimelineQueryService.java:43-52`), which reads only `development.player_skill_stats`. That table's sole writer, `SluCalculationService.onBookingCompleted`, returns early on no-show, on a missing `Session` row (**every Quick Complete**), and on a session not in `SAVED`/`COMPLETED` (`SluCalculationService.java:52-62`). So a Quick-Complete-only coach writes the recap and then gets `accessExpired=true` + an empty `events` list on their own `GET /api/development/players/{id}/timeline`. The root cause is that SLU rows are a **lossy proxy** for the clock's own stated definition of activity ("most recent completed session") — they silently miss the Quick-Complete path, the same blind spot Story 12.1 flagged for its roster `lastSessionDate`. All three new AC4 ITs hand-seed a `player_skill_stats` row (`PlayerTimelineResourceIT.java:159-165, 191-197`) and the Task-3.4 e2e IT asserts via `jdbcTemplate` rather than the GET endpoint, so the capture→read loop AC4 describes is never exercised end-to-end. **RESOLVED: accepted for this story.** No data is lost — the recap is durable in both `session_completion_data` and `player_timeline_events.metadata`, so a later clock fix surfaces the whole accumulated history retroactively, making the cost of waiting near zero. Changing the access-expiry policy belongs in a story with its own ACs, not a code-review patch. Two consequences, both tracked below: AC4's closing sentence and Dev Notes "Codebase grounding" are corrected (patch P1), and the real fix — making `SESSION_COMPLETED` events satisfy the access clock — is recorded in `deferred-work.md` bundled with Story 12.1's identical lossy-proxy blind spot.
- [x] **D2 — Two required request fields with no rolling-deploy compatibility window.** `WrapUpRequest.java:21-22` hard-requires both fields immediately, while the migration correctly follows expand/contract. The traced failure chain was: stale SPA bundle posts the old 7-field body → 400 → silent on the client (`boot/axios.js` branches on 401/403/≥500 only, no 400 branch, and no app-version skew detection exists) → no `session_completion_data` row → booking stranded in `COMPLETED_PENDING_CONFIRMATION`, unreachable by the wizard (`showWrapUp` is gated on `UPCOMING`), unrescuable by the parent (`confirmCompletion`'s `orElseThrow` rolls back, `BookingCompletionService.java:199-201`) and unrescuable by the sweeper (its query requires an existing row). **RESOLVED: dismissed — the premise does not hold.** The application has not been released; there is no production deployment, so there are no stale bundles and no rolling-deploy skew. `@NotBlank` stays exactly as AC1 specifies.
- [x] **D3 — The recap is required even on a no-show wrap-up.** Neither `WrapUpRequest.java:21-22` nor the client guard (`WrapUpSequence.vue:256-261`) has a `playerAttended` carve-out, while the wizard lets a coach uncheck attendance at step 1 and still walk to step 5. The reachable case is narrow: a dedicated no-show route already exists and is the exposed UI affordance (`CancellationResource.java:43`, `POST /{id}/no-show-player`, confirm dialog at `CoachCommandCenterPage.vue:291`) and performs a pure transition to `NO_SHOW_PLAYER` with no wrap-up; `playerAttended=false` *within* wrap-up still completes and bills the booking, differing only in that `SluCalculationService` skips SLU (`:52`). **RESOLVED: keep required, no change.** A recap reading "Player did not attend" is informative rather than filler — SLU is already suppressed for that booking, so the recap is the only surface carrying any explanation of why the session produced nothing, and the report Fast-Follow must tolerate thin recap prose regardless. The direction of regret is also asymmetric: required→optional later is a two-line change, optional→required later is blocked by accumulated nulls. Revisit if complete-with-non-attendance proves common in real coach usage.

### Codebase grounding — why this story is smaller than the brainstorm doc expected

The brainstorm's own Priority 2 plan ("Add a small structured recap form ... triggered at session/booking completion. Persist it into the existing `PlayerTimelineEvent.SESSION_COMPLETED` metadata JSONB") assumed the capture step itself needed building from scratch. It doesn't: `WrapUpRequest`/`SessionCompletionData`/`BookingCompletionService.submitWrapUp` is already *exactly* that mechanism — a small structured form (ratings, attendance, an optional voice-note text) captured at the precise moment of session-close, for **both** completion paths (`LIVE` — the coach ran the session live — and `QUICK` — Quick Complete, no live session). This closes the "Quick-Complete blind spot" that Story 12.1's own Dev Notes flagged for `lastSessionDate` (a Quick-Complete-only coach produces zero SLU rows, ever) for the **capture** side specifically — `submitWrapUp` runs identically for both modes and does not depend on a session-builder `Session` row at all (unlike `SluCalculationService.onBookingCompleted`, which silently no-ops when no `Session` row exists for the booking). So this story is mostly: add two fields to an existing request/entity, and thread them through an existing event — not build a new capture mechanism. **Code-review correction (D1, 2026-10-15):** the *read* side (`GET .../timeline`) still gates on that same SLU-row proxy via `TimelineQueryService`'s coach-access clock, so a Quick-Complete-only coach's capture has no gap, but that same coach's own read of it does — see AC4's corrected closing sentence and "Known residual risks."

### Why two new fields, not a repurposed `voiceNoteText` — and what Pattern #4's third component maps to

`voiceNoteText` (`WrapUpRequest.java:18`, already captured at the wizard's existing Step 3 "Session Note") is a separate, already-shipped field with **no validation constraints at all** (not "optional with app-level requiredness" — just entirely unconstrained) and no established downstream consumer beyond storage on `SessionCompletionData`; it is not currently exposed via the timeline endpoint or anywhere else. Pattern #4 ("Structured Micro-Recap") names three conceptual pieces — "what we did, what went well, what's next" — but the brainstorm's own later convergence (Priority 2's Next Steps item 1, and Converge #15) settles on two new structured fields ("what we did / what's next") *plus* "an optional free-text note." This story ships exactly that converged shape: the two new required fields (`recapWhatWeDid`/`recapWhatsNext`), and the pre-existing, already-optional `voiceNoteText` stands in for the third, free-text piece — unchanged, not read differently, not exposed differently. Repurposing or renaming `voiceNoteText` itself was considered and rejected: it would conflate two independently-evolving fields and risk an undocumented behavior/visibility change to something already shipped. If a future story wants `voiceNoteText` to also flow into timeline metadata, that is its own deliberate decision, not a side effect of this one.

### The cross-coach *and* cross-family redaction this story adds — and why (AC4, resolved per the Pre-Implementation Review)

`PlayerTimelineResource`/`TimelineQueryService` today gate coach access to a player's timeline **only** at the whole-response level — the configured expiry-since-last-session check (`TimelineQueryService.java:39-48`; config key `development.timeline.coachAccessExpiryDays`, seeded to 90 days, operator-adjustable in `[1, 3650]` — not a hardcoded "90 days") either returns the full event list or an empty one; it does not filter individual rows by which coach authored them, and it never gates the player/parent branch at all. Every pre-existing metadata value is harmless under that shape (a bare `{"coachId": "..."}`, or skill codes, or a report id — nothing qualitative). The moment this story writes real coach-authored text into `metadata`, that shared-response shape would leak it to every viewer who can see the event at all — the brainstorm's whole point in isolating "raw session notes" (Theme 4) as the one thing that stays private. AC4/Task 3.2 is not a new product decision; it closes the gap the brainstorm's own decision requires, once an actual coach-note field entered the picture for the first time (the same kind of discovery Story 12.1 made about the Quick-Complete blind spot — the design was already right, the gap was in an assumption about existing infrastructure).

### Task 3.3's second-coach test needs a real SLU row, not just a booking

`TimelineQueryService.getTimeline`'s coach-expiry check (`:39-48`) computes "last activity" for a given coach **only** from `sluRepository.findLastSessionDate(playerId, coachId)` — i.e. a `player_skill_stats` row for that exact coach-player pair, not from any booking. A second coach seeded only with a qualifying booking (no SLU row) reads `lastSession = null` → `accessExpired = true` → the service returns an empty event list **before ever reaching the redaction code** — making the "second coach does not see the recap" assertion vacuous (it would pass for the wrong reason: no events at all, not redacted events). Task 3.3's second-coach test must seed a real `player_skill_stats` row for that coach, exactly like `getTimeline_asCoach_withActiveAccess_returns200WithEvents` already does for the first coach, or the assertion proves nothing.

### `BookingCompletedEvent` blast radius — touch exactly 3 production files, 0 test files

`BookingCompletedEvent` is a plain `class extends ApplicationEvent` with Lombok `@Getter` (not a record) — its existing constructor takes **10** parameters (`Object source` plus 9 fields). Widening it naively could touch all 13 existing `new BookingCompletedEvent(` call sites across the codebase (3 production, 10 test). Task 2.1's backward-compatible overload — a new 12-arg constructor alongside the untouched 10-arg one — keeps the real edit surface to 3: `BookingCompletionService.java` (2 call sites) and `QuickCompleteTimeoutService.java` (1 call site), all of which already have direct access to the recap data (either the `WrapUpRequest` itself or the already-fetched `SessionCompletionData` row), so no new repository lookup is needed anywhere. The 10 test call sites across `SluCalculationServiceIT`, `HomeworkAssignmentServiceTest`, and `SessionPlanServiceTest` test *other* listeners on the same event (SLU calculation, homework assignment, session status transition) and have no reason to care about recap content — leave them on the old 10-arg constructor untouched. Reaching into `platform.booking.repo.SessionCompletionDataRepository` directly from `platform.development.service.TimelineEventListener` was considered and rejected: it would cross a module boundary this project's `project-context.md` explicitly wants closed via events ("Prefer Domain Events for cross-module communication"), and it's unnecessary once the event itself carries the data.

### Migration safety

`booking.session_completion_data.what_we_did`/`whats_next` are added **nullable**, with no backfill — matching the existing `voice_note_text` column's own precedent (also nullable, also with zero validation at the DTO level, never a DB `NOT NULL`). A backfill is not just unnecessary here but impossible: there is no way to reconstruct "what did we work on" for a session that already completed before this column existed. This follows `docs/deployment/migration-conventions.md` rule 1 ("Additive first... New columns are nullable or carry a default") exactly, and borrows the `SET LOCAL lock_timeout = '5s';` + `ADD COLUMN IF NOT EXISTS` syntax from the two most recent `ADD COLUMN` migrations (`V157`, `V158`) — but, unlike both of those (V157 backfills; V158 bundles unrelated config fixes), this migration is genuinely bare: one additive statement, nothing else.

### Explicitly out of scope (do not implement, do not let scope creep in)

Any frontend surface for the recap at all (see AC4/AC8 — there is nowhere a coach can see it yet, and AC4's policy forbids rendering it on the one page that currently reads the timeline, `PlayerTimelinePanel.vue`, since that page is Player/Parent-only); the Session Prep Card (Priority 3 — a prior recap's "what's next" pre-populating the next session's prep inside a booking's detail view); the coach-facing single-player detail page (Priority 4 — reusing `PlayerTimelinePanel.vue` from a *new* coach route, which is also when rendering the recap finally becomes meaningful; this story adds **no** new route and does not touch `router/routes.js`, `MainLayout.vue`, or any `pages/coach/*` file); the recap→report-generation tie-in (`ReportGenerationService`/`PerformanceReportResource`, the Fast-Follow); the player/parent-initiated flag (permanently deferred); and the pre-existing missing-relationship-check gap on `/neglected-skills`/`/slu/coach-contributions` that Story 12.1 already flagged as a separate follow-up — this story does not touch those endpoints at all.

### Known residual risks (acceptable for this story, not for silent "fixing")

- **Silent async-write loss on failure (M3).** `TimelineEventListener.onBookingCompleted`'s catch is `log.error(...)` only — no retry, no outbox, no DLQ, unlike the sibling `SluPersistenceRetrier`/`SluPersistenceDispatcher` in the same package. If the `taskExecutor` pool rejects the task, or the `REQUIRES_NEW` transaction fails, the recap silently never reaches the timeline, with no reconciliation path from the durable `session_completion_data` row where the text still sits. This is a pre-existing risk shared by every other `PlayerTimelineEvent` writer (`RADAR_ASSESSMENT`, `PERFORMANCE_REPORT`) — not new to this story, and out of scope to fix here (it would mean building retry/outbox infrastructure for the whole listener, a disproportionate scope increase for "add two fields").
- **No recap-correction path, and an unverified idempotency edge case (L12).** This story adds no way to edit a submitted recap, and a resubmission attempt may not behave exactly as the existing `catch (DataIntegrityViolationException)` guard's comment implies (`SessionCompletionData.id` uses `GenerationType.UUID`, which can defer the actual `INSERT` past that `try` block to flush/commit time — meaning the real failure mode on a duplicate submit may be a generic error rather than the silent no-op the comment describes). This is pre-existing behavior for every field on this row, not something this story's two new columns change; accepted as-is.
- **GDPR-erased players (timeline copy only).** `GdprErasureService` already bulk-deletes `player_timeline_events` by `playerId` on erasure — no new erasure gap from this story's two new metadata keys.
- **GDPR-erased players (`session_completion_data` columns — code-review finding, deferred).** The two new `what_we_did`/`whats_next` columns on `booking.session_completion_data` are **not** touched by `GdprErasureService` and never appear in the DSAR export (`GdprExportService` has no completion-data source). This is pre-existing in shape — `voice_note_text` on the same table has the identical gap — so it is accepted as-is and recorded in `deferred-work.md` for a settle-together fix rather than patched in isolation here.
