## Story

As the business owner,
I want coach review eligibility to require a matured, paid session (not merely a recent one), a monthly edit cadence backed by genuinely new training activity, reviews authored by whoever actually owns the session (the linked player's parent, or a self-registered player themselves), and no reviews while a genuinely open dispute with the coach exists,
so that reviews stay trustworthy evidence of real client experience and can track a coach's quality drifting over months, not just a single recent visit.

## Why This Story Exists

`skillars-9-1-review-submission-eligibility` shipped (`a5f27563`, 2026-06-29) and is `done`. Its eligibility rules work exactly as specified: a `COMPLETED` booking within a 14-day recency window (`reviews.submissionWindowDays`) to submit, the same window re-checked plus a 365-day annual gate to edit. A business review of those rules (2026-10-06) found two of them actively fighting the feature's own stated purpose, and one epic requirement (`FR-REV-001`) that was never implemented at all:

1. **The 14-day recency window makes "wait a week before reviewing" nearly impossible to combine with "let a review track a coach over time."** A 14-day window barely fits a 7-day minimum wait, and gives no room for a first review of a coach trained with months ago. The business intent is the opposite shape of gate: a session should be old enough to have "sunk in" (a floor), not young enough to still be fresh (a ceiling).
2. **The 365-day annual edit gate defeats the entire premise of making the review editable in the first place.** The business owner's stated reason for allowing edits at all: "a coach may start off well and then start misbehaving later." Once a year does not track that. A monthly cadence does — but only if each edit is backed by real, new training activity, or "once a month" becomes an unmotivated timer.
3. **`FR-REV-001`** (`_bmad-output/planning-artifacts/skillars-epics.md:149`) **requires "a completed paid session and no active dispute."** `ReviewSubmissionService.checkEligibility()` (current, shipped) only ever checked for a recent `COMPLETED` booking — it never checked for an open dispute at all. The pre-implementation review found that the dispute state this story needs to check actually lives in a separate `admin.disputes` table, not on `Booking.status` as first assumed — see the banner above and AC2.c/Task 3/Task 6 below, all rewritten against the real mechanism.

A fourth gap: the shipped check never distinguished *who owns the session* at all — it compared the author id against `Booking.playerId`, a `PlayerProfile` primary key rather than a user id, so the comparison could never match (see F2 above). AC2.b/Task 6 fix that by resolving the `PlayerProfile` and comparing against its `userId` (a self-registered player reviewing their own session) or its `parentId` (a parent reviewing their linked player's).

**Superseded sub-rule, recorded for history:** the original draft also added an *age* restriction here, mirroring `FR-MSG-002`'s 18+ parental-visibility cutoff — a parent would lose standing to review once a linked player turned 18. Round-1 decision **D2 removed that entirely**, on the owner's rule that "so long as a player is under a parent account, the parent should be the reviewer." The age check had a dead end: `chk_pp_owner` makes `parent_id`/`user_id` mutually exclusive for life and no flow ever transfers an existing parent-linked profile to self-owned, so the moment a linked player turned 18 the session became unreviewable by anyone and the parent's existing review froze. Eligibility is therefore structural, not age-based, and `FR-MSG-002` is no longer the precedent for it.

This story reworks `ReviewSubmissionService.checkEligibility()` and `updateReview()`'s gate to close all four gaps (the fourth as re-scoped by D2 above — ownership, not age). It does not touch anything else already shipped in the `platform.reviews` module (moderation, flagging, rating aggregation, public listing — see `platform/reviews/service/{ReviewModerationService,ReviewFlagService,CoachRatingService,ReviewQueryService}.java`), none of which reads the config keys or calls the eligibility method this story changes — **but it does break the fixtures of five test classes that were never meant to be in scope**, because every existing reviews fixture across the module uses an `ADULT`-tier player and a booking completed hours-to-days ago, both of which the new rules reject. See Task 7.

## Acceptance Criteria

1. **Given** this story's migration runs
   **When** `platform_config` is seeded
   **Then** two new bounded keys exist, replacing `reviews.submissionWindowDays`:
   - `reviews.minSessionAgeDays` (default `7`, bounds `[1, 365]`) — minimum age, in days, a `COMPLETED` booking must have before it counts toward *any* eligibility check (first review or update). No upper bound exists elsewhere in the system — a session from any point in the past still qualifies once it has matured past this minimum.
   - `reviews.updateCooldownDays` (default `30`, bounds `[1, 365]`) — minimum days that must have elapsed since a review's `lastModifiedAt` before it can be edited again
   **And** `reviews.submissionWindowDays` is deleted by this migration (`V156`) and removed from `ConfigBounds` — **not** literally "removed from the seed data": `V139__baseline_seed_data.sql` is grandfathered (`migration-conventions.md`) and still seeds the row; a fresh database ends up without it only because `V156` deletes it afterward, net of both migrations (code review 2026-10-06 — the original wording here read as an instruction to edit `V139`, which must never happen)
   **And** both new keys use `min = 1`, not `min = 0` — a stored `0` must be treated as an out-of-range operator error (falls back to the coded default and is flagged by `ConfigStartupAssertion`), not silently honored as "no floor"/"no cooldown" (see Dev Notes, F6)

2. **Given** a parent or player wants to submit a review for a coach
   **When** `POST /api/reviews/coaches/{coachId}` is called
   **Then** the eligibility check (`ReviewSubmissionService.checkEligibility`) runs, replacing the current single recency check, as follows:
   - **a. Qualifying session exists** — a booking exists where `(parentId = authorId OR playerId = authorId) AND coachId = {coachId} AND status = 'COMPLETED' AND updatedAt <= now() - reviews.minSessionAgeDays days`. `403` with `ErrorDto` code `reviews.noQualifyingSession` (renamed from `reviews.noRecentSession`) if none exists.
   - **b. Self vs. parent-linked discriminator** — for each qualifying booking, resolve its `PlayerProfile` by `playerId` and compare `authorId` against **that profile's own `userId` and `parentId` fields** (not against `Booking.playerId` directly — they are different ID spaces; see the banner above). If `authorId == player.userId`, the author is reviewing their own session. If `authorId == player.parentId`, the author is the linked player's parent. Either match is eligible unconditionally — **code review 2026-10-06 (D2, owner decision): the age-tier restriction originally specified here was removed entirely.** So long as a player is under a parent account (`parentId` set, per `chk_pp_owner`), the parent is the legitimate reviewer regardless of that player's age; no flow ever transfers an existing parent-linked `PlayerProfile` to self-owned, so an age check would have made a parent-linked player's session permanently unreviewable by anyone the moment that player turned 18. A booking whose `PlayerProfile` row cannot be resolved (orphaned `playerId`) contributes to neither outcome and is skipped. `403` with `ErrorDto` code `reviews.noQualifyingSession` if no booking matches either branch.
   - **c. No active dispute the author themselves raised** — no row exists in `admin.disputes` with `status NOT IN ('RESOLVED', 'DISMISSED')` and `raisedBy = authorId` whose `bookingId` joins to a booking where `coachId = {coachId} AND parentId = authorId`. `403` with `ErrorDto` code `reviews.activeDispute` if one exists. **The `raisedBy = authorId` narrowing is a deliberate departure from "any open dispute between the pair"** — resolved by the owner at kickoff, per the "Not Yet Resolved" item 2 below: scoping to disputes the author themselves raised closes a one-sided coach-side veto (`BookingEvent.DISPUTE` is permitted to both `PARENT` and `COACH`, resolution is admin-only with no time bound) while still satisfying the "mid-conflict review as leverage" concern from the author's own side. A dispute the *coach* raised does **not** block the author's review.
   **And** the existing duplicate check (`409 reviews.alreadySubmitted`), moderation defaults, and event publication are unchanged

## Business Rationale

- **7-day maturity floor, no ceiling, on every qualifying session (first review and every edit)** — lets the experience "sink in" before becoming a public review, rather than an immediate reactive post after one session. The lack of a ceiling is deliberate: unlike the old 14-day window, a session from any time in the past still counts, because staleness of a never-edited review is handled by surfacing `lastModifiedAt` publicly (already true for every `CoachReview` row — confirmed at `ReviewDto.java:14`, emitted by `ReviewQueryService`), not by expiring eligibility.
- **30-day rolling cooldown on edits, gated on a genuinely new matured session since the last edit** — frequent enough to track a coach's quality drifting over months (the business owner's explicit scenario), but never a free-running timer: every edit must be backed by actually training with the coach again.
- **Self-vs-parent discriminator keyed off `PlayerProfile.userId`/`parentId`, not `Booking.playerId`** — the only identifiers that actually distinguish "the author trained themselves" from "the author's linked player trained." **Code review 2026-10-06 (D2, owner decision), superseding this bullet's original `FR-MSG-002` justification:** the age-tier cutoff this bullet originally mirrored (messaging/video visibility lapsing at 18) does not apply here — "so long as a player is under a parent account, the parent should be the reviewer," regardless of that player's age. A parent-linked `PlayerProfile` is never transferred to self-owned by any flow, so an age restriction would have permanently locked the parent out of reviewing (and editing an existing review for) a session the moment the linked player turned 18.
- **Active-dispute exclusion against the real `admin.disputes` table, scoped to disputes the author themselves raised** — implements the dispute half of `FR-REV-001` against the mechanism that actually exists. Scoping to `raisedBy = authorId` (owner decision, see AC2.c and "Not Yet Resolved" item 2 below) means `FR-REV-001`'s unqualified "no active dispute" is deliberately half-implemented: an author-raised dispute blocks the author's own review; a coach-raised dispute does not. A live dispute an author raised is exactly the situation where a review is most likely to be used as leverage by that author against the coach; a dispute the coach raises is not given veto power over the author's ability to review, since dispute resolution is admin-only with no time bound.

            ConfigBounds.REVIEWS_MIN_SESSION_AGE_DAYS.key(), 7, 1, 365);
        Instant maturedBefore = Instant.now().minus(minAgeDays, ChronoUnit.DAYS);

        List<BookingReviewEligibilityProjection> qualifying =
            bookingRepository.findQualifyingCompletedBookings(coachId, authorId, maturedBefore, sinceAfter);

        boolean eligible = false;
        for (BookingReviewEligibilityProjection booking : qualifying) {
            PlayerProfile player = playerProfileRepository.findById(booking.getPlayerId()).orElse(null);
            if (player == null) {
                continue; // orphaned playerId -- contributes to neither outcome, see Dev Notes F5
            }
            if (authorId.equals(player.getUserId()) || authorId.equals(player.getParentId())) {
                eligible = true; // the author is reviewing their own session, or their linked player's
                break;
            }
        }

        if (!eligible) {
            throw new OperationNotAllowedException(
                "No qualifying completed session with this coach",
                ReviewErrorCode.NO_QUALIFYING_SESSION);
        }

        if (disputeRepository.existsActiveDisputeByAuthor(coachId, authorId)) {
            throw new OperationNotAllowedException(
                "An active dispute exists between this author and coach",
                ReviewErrorCode.ACTIVE_DISPUTE);
        }
    }

### F6 — `min = 1`, not `min = 0`, for both new `BoundedKey`s

`ConfigService.getBoundedLong`/`getBoundedInt` (4-arg form) does **not clamp** — an out-of-range value falls back to the coded default. With `min = 0` (an earlier draft of this story), a stored `0` would be *in range*, silently honored as the real value, and never flagged by `ConfigStartupAssertion` — the floor/cooldown would vanish with zero operator-visible warning. With `min = 1` (as specified in AC1/Task 2 above), a stored `0` is out-of-range, falls back to the safe coded default (7/30), and is caught by the startup check. Every sibling day-window key in the registry already uses `min = 1` (`disputes.submissionWindowDays`, the key this story removes, `reviews.autoHoldFlagThreshold`); the one `min = 0` precedent in the registry (the video-quota keys) words its own note specifically for that deliberate choice ("0 is a legitimate sentinel") — a choice that doesn't apply here, since 0 is never a legitimate value for either of these two keys.

### F1 (resolved) — the dispute gate is checked against `admin.disputes`, not `bookings.status`

An earlier draft of this story predicated the dispute gate on `b.status = 'DISPUTED'`. That status is legal in the schema's `chk_bkg_status` constraint but **unreachable in running code**: `BookingEvent.DISPUTE` has zero invocation sites outside the state-machine transition table (`BookingStateMachine.java:57,64,71,74`) and the actor-role permission map (`BookingService.java:106`); `DisputeService.raiseDispute`/`resolveDispute`/`dismissDispute` only ever write `Dispute.status`, never touch `Booking.status`. A disputed booking stays `COMPLETED` for as long as the dispute is open. The fixed design (AC2.c, Task 3, Task 6 above) checks the real table instead.

One consequence worth stating plainly, since it was reasoned about incorrectly in an earlier draft: `Booking.@PreUpdate` (`Booking.java:86-89`) stamps `updatedAt` on **any** row write — a reminder-sent flag, a `cancelReason`, a `batchId` assignment, an optimistic-lock `@Version` bump — not only a status transition. Under the old upper-bound recency window, an incidental bump on an old `COMPLETED` row would have *extended* eligibility (harmlessly, since the booking was already eligible). Under this story's lower-bound maturity floor, the same incidental bump **revokes** eligibility for another `reviews.minSessionAgeDays` days, because the maturity check reads the same `updatedAt` column. There is no `completedAt` column on `Booking` to use instead (9.1 established this constraint; still true), and adding one is a schema change out of scope for this story. Accepted as a known limitation: the maturity floor is occasionally, incidentally, and silently extended past its configured value by unrelated booking writes. Not worth fixing here; worth knowing before someone files it as a bug later.

### F5 (resolved) — the orphaned-`PlayerProfile` fail-closed path no longer reports a wrong error code

An earlier draft of this story's discriminator logic would have let an unresolvable `PlayerProfile` fall through to `reviews.parentalReviewNotApplicable` — a factually wrong message ("linked player is 18+") for what is actually a missing-row condition. The Task 6 rewrite above's `continue` on `player == null` fixed this as a side effect of fixing F2: an orphaned row contributed to neither `eligible` nor the then-existing `sawAdultParentMatch` flag, so it correctly fell through to `NO_QUALIFYING_SESSION` instead. **Moot after the 2026-10-06 code review's D2 (see AC2.b):** with the age-tier restriction (and `sawAdultParentMatch`/`PARENTAL_REVIEW_NOT_APPLICABLE` with it) removed entirely, an orphaned `PlayerProfile` row now has exactly one place to fall through to — `NO_QUALIFYING_SESSION` — by construction, not as a side effect of anything. (`PlayerProfile.dateOfBirth` is `nullable = false` in the schema either way, so this was always about a missing *row*, not a present row with a null date of birth.)
