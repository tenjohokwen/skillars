# Story Ses-1.2: Move SMTP Behind the Port and Contain It

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the platform's email transport owner,
I want the SMTP path moved behind the `OutboundEmailSender` port from Phase 1 — sealed into a single `infrastructure/email/smtp` package with containment invariants enforced by tests — and `MailService`/`MailManager` reimplemented on top of that port,
so that **every** email in every environment goes through one transport abstraction, dev and uat gain registration/OTP mail for the first time (fixes D4), and the eventual SMTP removal (Phase 6) stays a one-commit job instead of a project.

This is **Phase 2 of 7** in `requirements/ses-email-consolidation.md`. It builds directly on Phase 1 (story `ses-1.1`, done): the `OutboundEmailSender` port, the `EmailTransport{Transient,Permanent}Exception` taxonomy, the `EmailTransport` enum/selector, `EmailTransportPropertyValidator`, `LoggingEmailSender` and the rebuilt `SesEmailSender` all already exist and are **not** touched by this story except where explicitly noted (the validator's accepted-value set, below). Per the source doc: *"all email in every environment goes through one port. Prod is fully on SES; dev and uat are fully on SMTP, including registration mail... Risk: medium. Prod flips to SES for booking mail — but prod is not live."*

**Already done, not part of this story:** `platform/notification/infrastructure/DevSesEmailService` — the source doc's §5 Phase 2 item 5 lists deleting it, but story `ses-1.1` already deleted it (it was superseded by `transport=log`). Do not search for it; it does not exist. `EmailTemplate.deliveryDeadline()` is explicitly **Phase 4 only** (§5 Phase 4 item 3) — do not add it here even though `EmailTemplate` is otherwise untouched by this story.

## Acceptance Criteria

**AC1 — `EmailContentRenderer` extracted from `MailService`, proven lossless by a characterization test written first**

- Given a new `EmailContentRenderer` in `platform/notification/service`, with one public method rendering `(subject, htmlBody, textBody)` from `(Recipient, EmailTemplate, Map<String,Object>)`
- Then it contains, moved **verbatim** from `MailService.sendEmailFromTemplate` (current lines 61–74): the `Locale.forLanguageTag(recipient.getLangKey())` resolution, the Thymeleaf `Context` construction with `recipient`/`map` variables, `templateEngine.process(CaseFormat.UPPER_UNDERSCORE.to(CaseFormat.LOWER_CAMEL, emailTemplate.name()), context)`, and the `messageSource.getMessage(emailTemplate.subjectKey(), null, locale)` subject lookup
- And it reproduces the `EmailTemplate.NONE` special case (current lines 63–67): `subject`/`body` read directly from the `values` map, `htmlBody` **null**, `textBody` set to the map's `"body"` value — this is what makes `AlertNotificationListener`'s plaintext ops alerts (§6.2) work through the new port, since SESv2's `simple` content has separate `html`/`text` parts
- And a golden-value `EmailRenderingCharacterizationTest` is written and passing **against the current, unmodified `MailService`** *before* any extraction code is touched: for a representative set (one transactional template, one OTP template, one booking template, plus `EmailTemplate.NONE`) × `{de, en, fr, an-unrecognised-tag}`, it captures rendered subject and body and asserts against those captured values. After the extraction, the **same test runs unchanged** and passes — a faithful move produces byte-identical output, and this is what makes "templates and language are preserved" (§10 item 5) a checked claim rather than an assertion
  - **"Representative" is defined by code path, not by template count.** `EmailTemplate` has 40 values (39 real templates + `NONE`), backed by 31 physical `.html` files — but all 39 non-`NONE` values are rendered by the exact same generic mechanism (`Context` + `templateEngine.process(...)` + `messageSource.getMessage(subjectKey(), ...)`), verified by reading `MailService.sendEmailFromTemplate` in full: there is no per-template branching anywhere in it. This test exists to prove the *extraction* (moving that mechanism into a new class) is lossless, not to re-verify each template's individual content — that is `EmailTemplateSubjectKeyParityTest`'s and the mail-bundle tests' job, unaffected by this move. One template from each of a few different categories, plus `NONE` (the one branch that *is* different), covers every distinct code path this test needs to cover. Do not attempt to enumerate all 39 — that would test content correctness, not extraction correctness, and duplicates coverage that already exists elsewhere
- [Source: requirements/ses-email-consolidation.md#5 Phase 2 item 1, #3.3, #6.2, #7.2 item 11]

**AC2 — `infrastructure/email/smtp` created; SMTP moves behind the port with today's classification preserved exactly**

- Given a new, sealed package `infrastructure/email/smtp`
- Then it contains `SmtpEmailSender implements OutboundEmailSender`, gated `@ConditionalOnProperty(name = "app.email.transport", havingValue = "smtp")`, folding in: (a) the `MimeMessage`/`MimeMessageHelper` construction currently in `MailService.sendEmail` (lines 40–55) — `to`, `from` (from the picked `JavaMailSenderImpl.getUsername()`, unchanged — sender identity for SMTP stays a side effect of round-robin, D1 is not fixed here, only for SES), `subject`, `text(content, isHtml)` where `isHtml` derives from which of `request.htmlBody()`/`request.textBody()` is present (§6.2 — mirror `SesEmailSender`'s "html when present, independently text when present" shape, but SMTP's `MimeMessageHelper.setText` takes one body + an `isHtml` flag, so pick `htmlBody` when present, else `textBody`, matching today's `MailService.sendEmailFromTemplate` behavior exactly); and (b) the round-robin provider selection, calling `MailSenderProvider.nextSender()` **directly** (no `SenderProvider` interface — see the deletion below)
- And `MailSenderProvider` (round-robin `JavaMailSenderImpl` selection) moves here unchanged in logic, now constructed from `SmtpProperties` instead of `EmailProperties`
- And `ProviderConfig` moves here unchanged
- And `EmailProperties` is renamed `SmtpProperties`, rebound from `@ConfigurationProperties(prefix = "email")` to `@ConfigurationProperties(prefix = "app.email.smtp")` — this is what makes `NoStraySmtpConfigTest` (AC8) assertable: every SMTP property lives under one YAML key
- And `SmtpHealthIndicator` + `SmtpHealthProperties` move here unchanged in logic. **Do not re-gate `SmtpHealthIndicator` on `app.email.transport=smtp` in this story** — that re-gating is explicitly Phase 3 (§5 Phase 3 item 2). Its existing `@ConditionalOnProperty(prefix = "email", name = "providerConfigs[0].host")` guard moves with it, with **both** the prefix *and* the property name updated to `prefix = "app.email.smtp", name = "provider-configs[0].host"` (kebab-case) — **not** `providerConfigs[0].host` left as-is. This is a correctness requirement, not a style preference: `@ConditionalOnProperty`'s relaxed binding does **not** bridge camelCase↔kebab-case across an indexed (`[0]`) segment — verified empirically (`ApplicationContextRunner` with a camelCase-named indexed conditional against a kebab-case-set property never activates the bean). Since AC6 moves the backing YAML key to kebab-case `app.email.smtp.provider-configs`, leaving the Java literal as `providerConfigs[0].host` would silently and permanently disable this health indicator — no compile error, no obvious test failure, just an indicator that never reports anything. Leave the conditional's *semantics* (gated on a provider being configured, not on the transport enum) unchanged — only the literal string casing changes
- And `platform.notification.service.SenderProvider` (the single-method interface `JavaMailSenderImpl nextSender()`) is **deleted** — its one implementation is folded directly into `SmtpEmailSender`'s use of `MailSenderProvider`, per §3.3's ownership table: "Pick an SMTP provider (`SenderProvider`)" moves to `infrastructure.email.smtp` as a concrete call, not a re-abstracted interface
- And a new `SmtpErrorClassifier` in the same package preserves `MailManager.NON_REPAIRABLE_ERRORS`'s exact classification: `MailParseException`, `MailPreparationException`, `jakarta.mail.internet.AddressException`, `jakarta.mail.internet.ParseException` → `EmailTransportPermanentException`; every other `MessagingException` → `EmailTransportTransientException`. This is a pure relocation — SMTP retry semantics must not change for dev/uat
- [Source: requirements/ses-email-consolidation.md#5 Phase 2 item 2, #3.2, #3.3, #4.1, #4.3]

**AC3 — `MailService` reimplemented on the port; composition unchanged**

- Given the existing `MailService` in `platform/notification/service`
- Then `sendEmail`/`sendEmailFromTemplate` no longer construct a `MimeMessage` or select a provider — they call `EmailContentRenderer.render(...)` then `outboundEmailSender.send(new OutboundEmailRequest(...))`, logging the returned `messageId()`
- And both methods **stop declaring `throws MessagingException`** — nothing downstream of the port throws it any more; a caller only ever sees `EmailTransport{Transient,Permanent}Exception` (unchecked)
- And `@Observed(name = "mail.send_from_template")` stays exactly where it is
- And `correlationId` for the `OutboundEmailRequest` is **not** `envelope.sendId()` — `MailManager` loops `recipients` and calls `sendEmailFromTemplate` once per recipient (§6.13, unchanged by this story), so a per-call `UUID.randomUUID()` (mirroring the pattern the three registration listeners already use from Phase 1) keeps one correlation id per actual send. Persisting `sendId` as the correlation id is a Phase 4 concern once `OutboundEmailResult.messageId()` is written onto `EnvelopeEntity` — out of scope here
  - **Accepted limitation, not a bug — but document it in code.** `MailManager`'s `retryTemplate.execute(...)` (3 attempts, 1s backoff) calls `sendEmailFromTemplate` again on a transient failure, and each call mints a fresh UUID — so a single logical send that takes two attempts shows up as two unrelated correlation ids in the logs, not "attempt 1 / attempt 2 of the same send." Add a one-line comment where `MailService` generates the id: *"One correlation id per call, not per logical send — a `RetryTemplate` retry gets a new id. Correlating retries of the same envelope is a Phase 4 concern, once `sendId` is available to key off of."* This is the same tradeoff the Phase 1 registration listeners already accept (they have no retry today, so it's invisible there); it just becomes visible here because `MailManager` does retry
- [Source: requirements/ses-email-consolidation.md#5 Phase 2 item 3, #3.3, #4.3]

- Given `MailManager.NON_REPAIRABLE_ERRORS`

- And `isRetryable`'s two-level cause-walk (direct exception, its cause, its cause's cause) stays exactly as it is — only the checked types in `NON_REPAIRABLE_ERRORS` change, not the walking logic or its depth
- And `MailManagerResilienceTest` is updated to match: the `MailParseException`/`AddressException`/`ParseException`-wrapped-in-`MessagingException` cases become `mailService.sendEmailFromTemplate` throwing (unwrapped) `EmailTransportPermanentException` directly — no double-wrapping, since the port's exceptions are already at the depth `isRetryable` expects from an adapter. The generic-failure/timeout case (currently a bare `MessagingException`) becomes `EmailTransportTransientException`. The circuit-breaker state-transition assertions (`testSendEmail_CircuitBreakerOpens`, etc.) are transport-agnostic and are **not** touched
