# Story Deferred-17: Booking Request Slot Payload & Timezone Integrity

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a parent trying to book or batch-book a coaching session, and as a coach relying on session timestamps shown in my own timezone,
I want the booking-request page to actually submit the slot I selected instead of `undefined`, the batch-booking submission to stop being rejected by a payload type error, and every session time — request-page slot list, batch review list, and stored `canonicalTimezone` — to reflect the coach's timezone rather than my browser's,
so that requesting or batch-requesting a session works at all, and nobody looks at a mistimed slot or a batch total that was never actually computed.

### Why this story exists

Story creation set out to verify one `deferred-work.md` item — `skillars-3-3` Group D's `canonicalTimezone` bug in `BookingRequestPage.vue` — before writing a grooming story around it. Tracing that item's data flow surfaced two live, more severe defects in the exact same file that were **not in the ledger at all**: the parent-facing booking-request page cannot currently complete a booking, in either single or batch mode. The user was informed mid-investigation and chose to make the newly-found breakage the anchor of this story, with the ledger's own timezone item folded in alongside it (same file, same page, one coherent fix).

### Items examined and deliberately NOT folded in

- **Removing `canonicalTimezone` validation entirely rather than re-deriving it.** Considered and rejected: `BookingBatchService.createBatch` already trusts `coach.getCanonicalTimezone()` with zero validation at the point of use, so AC3 makes the single-booking path consistent with an existing, already-shipped pattern rather than inventing a new one. Whether `CoachProfile.canonicalTimezone` itself should be validated as a real IANA zone at profile-creation time (`ProfileBuilderStep1Request`/`ProfileBuilderStep4Request`, both merely `@NotBlank`) is a separate, pre-existing gap affecting both booking paths equally. Out of scope here — do not touch profile-builder validation.
- **Computing a real `totalAmount` for batch bookings client-side.** `BookingRequestPage.vue` never loads per-session pricing (confirmed: no `pricing`/`perSessionPrice` reference anywhere in the page or `booking.store.js`), and `totalAmount` is used only for the acceptance-email preview (`BookingBatchService.java:233,255`), never for charging — real settlement happens elsewhere against actual pack/Stripe pricing. AC2 restores the parameter binding to a valid `BigDecimal` (the pre-regression `0` placeholder); wiring real pricing into this page is a product feature, not a bug fix, and is not part of this story.

## Acceptance Criteria

1. **The booking-request page and store consume `AvailableSlotResponse`'s actual field names.** Every reference to `slot.startTime`/`slot.endTime` (or `s.startTime`/`s.endTime`) in `BookingRequestPage.vue` and `booking.store.js` is corrected to `slot.startDatetime`/`slot.endDatetime`. This includes, at minimum: the `v-for` `:key` bindings (both the main slot list and the batch review dialog list), the `disable`/`active` state expressions, `formatSlot()`'s four call sites (`:55`, `:56`, `:142`, `:143`), `toggleSlotInBasket`/`removeSlotFromBasket` in the page and `isSlotInBasket`/`removeSlotFromBasket` in the store (`addSlotToBasket` pushes the whole slot object and touches no field name by itself; `toggleSlotInBasket` exists only in the page, not the store — see Task 2 for the exact 4 store-side hits), and both submit payloads (`submit()`'s `requestedStartTime`/`requestedEndTime`, and `submitBatch`'s per-slot `requestedStartTime`/`requestedEndTime` mapping).

   **Beyond `"Invalid Date"`, the pre-fix bug produces three further symptoms worth knowing before touching this code**, because they explain why some of today's behavior looks superficially fine and will change once this AC lands: (a) `selectedSlot?.startTime === slot.startTime` (`:49`) evaluates `undefined === undefined` → true for *every* slot, so every slot renders with the active/selected highlight from first paint, before any real selection; (b) `isSlotInBasket(undefined)` (`booking.store.js:131-132`) returns true the moment *any* slot is in the basket, so the batch basket is effectively capped at one item today — `toggleSlotInBasket` never reaches `addSlotToBasket` for a second slot, and clicking any slot calls `removeSlotFromBasket(undefined)`, which empties the whole basket; (c) `bookedStartTimes.has(slot.startTime)` (`:43-44`) is always false pre-fix (the set holds real `b.requestedStartTime` strings), so **the already-booked-slot disable guard is dead code today and goes live for the first time with this fix** — it string-compares `BookingResponse.requestedStartTime` against `AvailableSlotResponse.startDatetime`, both `Instant` under the same non-timestamp JSON serialization, so they should match, but this is newly-reachable behavior with no prior verification anywhere.

   After the fix, selecting a slot and submitting a single booking request succeeds end-to-end (201, booking visible on `/parent/bookings`), adding multiple slots to the batch basket and reviewing them shows real dates (not `"Invalid Date"`, and more than one slot at a time), and an already-booked slot renders disabled rather than clickable.

2. **`submitBatch` no longer sends a timezone string where a monetary amount belongs.** `booking.store.js`'s `submitBatch(coachId, playerId, totalAmount)` keeps `totalAmount` as a real parameter bound to `CreateBatchRequest.totalAmount`; `BookingRequestPage.vue`'s `submitBatchRequest()` stops passing `Intl.DateTimeFormat().resolvedOptions().timeZone` into that slot and passes a valid `BigDecimal`-serializable value instead — restore the pre-regression `0` placeholder (documented via a one-line comment noting `totalAmount` is display-only for the acceptance email and real settlement is computed server-side against actual pricing elsewhere; do not attempt to compute a real total as part of this fix). After the fix, submitting a full batch basket succeeds end-to-end (batch created, visible to the coach at `/coach/booking-requests` or equivalent, and `acceptAll` still settles correctly). Note this is not a regression check in the usual sense — no batch could ever have been created through this page before this fix, so there is no prior working behavior to regress from — but `acceptAll` is downstream code this story does not otherwise touch, so exercising it once end-to-end is still worth doing to confirm the fix doesn't stop short of a settleable batch.

3. **A booking's `canonicalTimezone` is derived from the coach's profile server-side, never trusted from the client, for both booking-creation paths consistently.** `BookingService.createBookingRequest` stops reading `req.canonicalTimezone()` and instead sets `booking.setCanonicalTimezone(coach.getCanonicalTimezone())` after the existing coach lookup, mirroring `BookingBatchService.createBatch:131` exactly (including using it in the published `BookingRequestedEvent`, replacing `req.canonicalTimezone()` at `BookingService.java:262`). Remove the `canonicalTimezone` field from `CreateBookingRequest` (`CreateBookingRequest.java:17`) — including the `ZoneId.of(req.canonicalTimezone())` validation block at `BookingService.java:181-186`, which no longer has anything to validate — rather than leaving an accepted-but-ignored field on the contract. `BookingRequestPage.vue`'s `submit()` stops sending `canonicalTimezone` in its payload entirely.

   This is a breaking constructor change to `CreateBookingRequest` (7 args → 6). Every direct construction must be updated, not just JSON-body tests: `BookingServiceTest.java` (two call sites: `:257`, `:547`), `BookingServiceConcurrencyIT.java` (three call sites: `:130`, `:132`, `:262`), `PaymentPendingSweeperIT.java:171`, and `ExpiredPackBookingValidationTest.java` (**five** call sites: `:108`, `:151`, `:181`, `:205`, `:229`) — 11 direct constructions total. `BookingRequestResourceIT.java`'s JSON request-body maps (15 occurrences of the `"canonicalTimezone", WINDOW_TZ` key across `createBookingRequest_*` tests) drop that key; because the coach fixture in that IT already inserts `coach_profiles.canonical_timezone = WINDOW_TZ` (`BookingRequestResourceIT.java:129-132`), no test's expected timezone value changes — only how it gets there. **`SuspendedCoachBookingBlockIT.java:161,183` carries the same JSON key against the same endpoint and is outside `BookingRequestResourceIT` — drop it there too**; Spring's default of ignoring unknown JSON properties means leaving it would not fail the build, only leave dead test data asserting a contract that no longer exists.

   **`ExpiredPackBookingValidationTest`'s hand-built `CoachProfile` fixtures (`:87`, `:128`, `:243`) never call `setCanonicalTimezone`.** Once this AC makes `coach.getCanonicalTimezone()` the sole source of the booking's timezone, those fixtures would silently produce null-timezone bookings with nothing in the suite asserting on the field — a real coverage gap (production itself is protected: `coach_profiles.canonical_timezone` is `NOT NULL` and drafts default to `"UTC"`, so this cannot happen outside a test double). Set a real zone (e.g. `"UTC"` or `WINDOW_TZ`-equivalent) on all three fixtures as part of this change.

4. **`formatSlot()` in `BookingRequestPage.vue` displays slot times in the coach's canonical timezone, read from the same column AC3 stores on the booking — not from `coach_availability_windows`.** `CoachAvailabilityResponse` (`CoachAvailabilityResponse.java`) gains a `canonicalTimezone` field; `AvailabilityService.getAvailabilityCalendar` populates it from `coach.getCanonicalTimezone()` (the coach lookup already happens in that method's window-timezone-fallback logic — reuse the same `CoachProfile`, do not add a second query). This is deliberately **not** `windows[0].canonicalTimezone`: that is a different, independently-writable column (`coach_availability_windows.canonical_timezone`, set per-window at Step 4 profile-builder time and never re-synced to the profile's own zone) that can genuinely diverge from it — see the "Why this story exists" table for the concrete divergence path. Expose the new field from `booking.store.js` (e.g. a `coachTimezone` ref/computed populated in `loadAvailability()` alongside `windows`/`computedSlots`) rather than threading it through props.

   `formatSlot()` uses the `ParentBookingsPage.vue:184-190` pattern (`Intl.DateTimeFormat('en', { timeZone, dateStyle: 'medium', timeStyle: 'short' })`) but **must not trust the zone string blindly** — nothing validates `coach_profiles.canonical_timezone` as a real IANA zone (`ProfileBuilderStep1Request`/`ProfileBuilderStep4Request` are both merely `@NotBlank`), and AC3 deletes the one syntactic check (`ZoneId.of(...)`) that existed on this exact value's write path. `Intl.DateTimeFormat` throws `RangeError` on an unrecognized zone, which inside a `v-for` item label kills the render of the entire slot list, not one row — and a missing/falsy zone (e.g. an empty `bookingStore.coachTimezone` before `loadAvailability()` resolves) silently falls back to the browser's zone, which is the exact bug this AC exists to fix, now invisible. Guard `formatSlot()` the same way `AvailabilityService.java:52-60` already guards this same value server-side: default to `"UTC"` when the zone is missing/blank, and wrap the `Intl.DateTimeFormat` construction in try/catch, falling back to `"UTC"` on `RangeError`.

   This does not need a "show in my time" toggle like `ParentBookingsPage.vue` has — that AC is out of scope; just stop silently using the browser's implicit zone.

5. **A failed initial drill-library fetch is visible to the coach, not silent.** `DrillLibraryPage.vue`'s `onMounted` surfaces a failure via a `watch` (or computed) on `sessionStore.error` that fires `$q.notify({ type: 'negative', ... })` once. **This is the only viable shape — do not use a `try/catch` around `sessionStore.fetchDrills('PLATFORM')`.** `fetchDrills` (`session.store.js:22-33`) catches its own failure into `error.value` and never rethrows (`catch (err) { error.value = err }`, no `throw`), so a `try/catch` at the call site is dead code: it will never see a rejection to catch, regardless of whether the underlying request succeeds or fails. `CoachPublicProfilePage.vue:285-297`'s `try/catch` pattern works only because `getCoachProfile` is a raw API call that genuinely throws — it is not analogous here. Do not add a retry affordance or change `session.store.js` — the store's existing catch-into-`error.value` behavior is correct and unchanged by this AC.

6. **`deferred-work.md` reflects reality.** Both bullets under `## Deferred from: code review of skillars-3-3-booking-request-approval-workflow Group D (2026-06-15)` are deleted (AC3, AC4) — this empties the heading; remove the heading too. Under `## Deferred from: code review of skillars-4-1-drill-library-foundation (2026-06-17)`, only the `D5` bullet is deleted (AC5) — `D1`–`D4` and `D6`–`D9` stay, so the heading remains. A `## Last audit: 2026-08-06 (skillars-deferred-17 story creation)` block already exists recording the AC1/AC2 discovery and the `OWNED BY skillars-deferred-17` annotations on the three items above — do not duplicate it; amend it after implementation with what was found (in particular: the exact post-fix line numbers, since AC1's edits shift everything below them in `BookingRequestPage.vue`) rather than adding a fifth `## Last audit: 2026-08-06` heading if one already exists for another reason.

Computing a real batch total needs pricing data this page doesn't load; flagged in "Items examined and deliberately NOT folded in" above as explicitly out of scope.
