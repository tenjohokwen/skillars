## Dev Notes

### Why this story bundles several unrelated things

The user explicitly directed a large, multi-origin story this time rather than the usual narrow bundling — `deferred-work.md` has accumulated enough real, verified gaps that a small story would leave more open than it closes. Several decision points were resolved with the user via `AskUserQuestion` before and during drafting (scope for Converge #16 and Deferred #17, the a11y pattern, and — after an independent story review surfaced a real consequence of this story's own new content — the `performance_reports` GDPR scope). Three of those decisions were **corrected by code-level research** before being re-confirmed with the user a second time: Converge #16's date-range premise, the coach-GDPR gap's "tombstone" premise, and (post-draft) the `performance_reports` purge's scope. Do not re-litigate these during implementation — the corrected designs are the ones actually specified in the ACs above, verified against real HEAD, twice.

### The metadata-key vs. entity-column trap (appears in AC1 and AC9 — get this right, it is the story's central risk)

`PlayerTimelineEvent.coachId` (the entity column) is **attendance-gated** — `NULL` for a completed-but-unattended session (`TimelineEventListener.java:61`). `metadata.get("coachId")` is **unconditional** — always present for every `SESSION_COMPLETED` event (`:55`), written regardless of attendance. A query that filters on the column (including an innocent-looking Spring Data derived method like `findByPlayerIdAndCoachIdAndEventType...`) silently excludes every unattended session's rows from the result set entirely — not "returns them with missing data," but "never returns them at all," because `NULL = ?` is never true in SQL. The first draft of this story got this wrong in AC1 itself (prescribing exactly that derived-method shape while its own prose warned against doing so) and the correction above is not cosmetic — it's a genuine functional bug fix to the story's own design, caught by an independent review, not by the author. Every new piece of code in this story that needs to know "which coach authored this recap" (AC1's report query, AC9's GDPR scrub) must filter on `metadata->>'coachId'` via a native query. `SessionPrepService`'s existing column-based query is **not** safe precedent to copy for this purpose — it gets away with the narrower signal only because it's paired with a different, attendance-aware resolver for a different purpose (the access-expiry clock), not because column-based filtering is generally safe.

### Why `anonymizeByCoachId` was not the thing to extend, and why `performance_reports` joined the scrub too

The original story-scoping instinct (and the user's first-choice answer) was to add a coach-side tombstone column modeled on `PlayerProfile.developmentDataErasedAt`. Research proved two independent things wrong with that: (1) that player-side tombstone protects against a *resurrection race* during erasure, not a *missed scrub location* — the wrong precedent to mirror for this gap; (2) `anonymizeByCoachId` (`SessionCompletionDataRepository`) already exists, already runs synchronously inside the coach-erasure transaction, and already closes the `booking.session_completion_data` half of the recap-persistence story (added by `skillars-deferred-154` AC2). The two remaining gaps are **copies of the same underlying fact in two more places**, not one feature needing one bigger fix: `development.player_timeline_events.metadata` (written by a different listener at a different time — session completion, not wrap-up submission) and, once AC1/AC2 ship, `development.performance_reports` (written by `ReportGenerationService`, at report-generation time, on demand — a *third* time and a *third* path). This story's own new content is what makes the third one worth fixing now rather than leaving it for later: before AC1/AC2, a generated report's recap-adjacent gap was "deferred-154's own three same-root-cause gaps" (metadata copy, `PerformanceReport.nextSteps`, `CoachProfile.displayName`, all narrow, pre-existing, and explicitly accepted as a known residual); after AC1/AC2, that same unscrubbed table now contains the coach's full recap history verbatim, readable by any parent who downloaded the report. Treat all three as one scrub operation triggered from the same place, not three separate features.

### `Booking.playerRequest` vs. `Booking.notes` — do not conflate

`notes` is write-once, set only at booking creation (`createBookingRequest`), and is surfaced on the *coach's* request-acceptance queue. `playerRequest` is editable any time the booking is `CONFIRMED`/`UPCOMING`, and is surfaced on the *coach's Session Prep Card* — a completely different screen, viewed at a completely different point in the relationship (prepping for an already-confirmed session, not deciding whether to accept a new one). They happen to be adjacent columns on the same entity and share a validation shape, nothing more. A dev agent that notices `notes` already exists and tries to reuse/repurpose it will produce a confusing, write-once "editable" field that silently fails to persist edits after the booking is first created.

Also note: `notes` is persisted **unsanitized** today (`BookingService.java:336` has no sanitizer call) despite reaching the coach exactly the same way `playerRequest` will. `playerRequest` *is* sanitized in this story (AC5) — the two columns end up inconsistent with each other, which is a known, disclosed, and deliberately *not fixed here* gap (see Task 6.4's new ledger entry) rather than an oversight. Sanitizing the new column is still the right call on its own merits; just don't frame it as restoring a consistency that doesn't currently exist.
