# Story 11.2: Cut Over Booking Flow and Frontend to the Single Payment Path

Status: done

## Story

As a parent and coach,
I want session-pack purchase, credit display, and booking-time deduction to run entirely on `payment.session_pack_purchases`,
so that there is only one way to buy, track, and spend session-pack credits.

**This story cuts every caller over to the new path but does not delete the legacy system** (`booking.session_packs_purchased`, `SessionPackService`, `SessionPackResource`, `SessionPackExpiryScheduler`) — that is Story 11.3's job, once this story is verified in UAT. Leave the legacy Java classes in place but unreferenced by any live caller by the end of this story.

**No live/production system exists yet (development/UAT stage)** — there is no user data to protect. The legacy system currently is the *only* thing the frontend calls; after this story ships, the frontend calls only the new path.

## Acceptance Criteria

1. **Given** the parent-facing purchase and credits UI **When** this story ships **Then** `SessionPackPurchasePage.vue` purchases through `POST /api/payment/session-packs/purchase` (`purchaseSessionPack` in `payment.api.js`, updated to send `playerId` — it currently omits it entirely, a stale pre-Story-11.1 call shape) instead of legacy `POST /api/bookings/players/{playerId}/packs/purchase`, and `SessionPackTracker.vue`/`SessionPackDashboardPage.vue` read pack data from `GET /api/payment/session-packs?coachId=` (new `getMySessionPacks` call added to `payment.api.js`) instead of legacy `getPlayerPacks`. Pause UI (`SessionPackDashboardPage.vue`'s pause dialog) calls `POST /api/payment/session-packs/{purchaseId}/pause` instead of legacy `POST /api/bookings/players/{playerId}/packs/{packId}/pause`.

2. **Given** a parent submits a booking request for a specific coach **When** the parent has one or more active (non-expired, non-exhausted, non-paused) packs for that coach **Then** the booking-request UI lets the parent pick a specific pack (or "pay per session" if no pack is selected) and `createBookingRequest`'s payload includes that pack's `purchaseId` as `sessionPackPurchaseId` — **today the frontend never sends `sessionPackPurchaseId` at all** (confirmed: zero references to it anywhere under `src/frontend/src`), so this is new UI, not a rename.

3. **Given** `BookingService.createBookingRequest()`'s legacy pessimistic-lock branch at `BookingService.java:233-238` (`if (req.sessionPackPurchaseId() == null) { sessionPackPurchasedRepository.findActivePacksForDeduction(...) }`, dead-code-commented as "Acquire pessimistic lock on legacy pack rows... Skipped for the new path") **When** this story ships **Then** that branch is deleted entirely — a null `sessionPackPurchaseId` unambiguously means "pay-per-session" (handled today by `PaymentLifecycleService.handleCreditBasedBooking`, which already charges Stripe directly and is untouched by this story), never "look up a legacy pack."

4. **Given** `BookingCompletionService.submitWrapUp()` (`BookingCompletionService.java:150`) and `.confirmCompletion()` (`BookingCompletionService.java:184`), both of which unconditionally call legacy `sessionPackService.deductCredit(booking.getPlayerId(), booking.getCoachId())` at session **completion** time **When** this story ships **Then** both calls are removed. **This is the critical bug this story exists to fix, not a style migration**: `PaymentLifecycleService.handlePackBasedBooking()` (`PaymentLifecycleService.java:58-71`) already calls `packSessionService.deductSession(purchaseId)` at booking **acceptance** time, for every booking whose `sessionPackPurchaseId != null`. Once callers pass a real `sessionPackPurchaseId` per AC2, every pack-based booking's session was already decremented at accept-time — calling legacy `deductCredit(playerId, coachId)` again at completion would either double-deduct (if a matching legacy pack coincidentally exists) or throw `booking.creditsExhausted` and hard-fail every session completion (if it doesn't, which is the common case once the new path is the only purchase route). Do not replace these calls with a `PackSessionService` equivalent — there is nothing left to deduct at completion time; the deduction already happened.

5. **Given** `QuickCompleteTimeoutService.processExpiredQuickCompletes()` (`QuickCompleteTimeoutService.java:49`), which also unconditionally calls legacy `sessionPackService.deductCredit(scd.getPlayerId(), scd.getCoachId())` on auto-confirm **When** this story ships **Then** this call is removed for the same reason as AC4 (accept-time deduction already happened via `PaymentLifecycleService`).

6. **Given** `HomeworkAssignmentService`'s two read-only legacy calls — `sessionPackService.hasActivePack(playerId, coachId)` (`HomeworkAssignmentService.java:102`, gates which coaches' homework assignments show as "active") and `sessionPackService.getActivePackId(playerId, coachId)` (`HomeworkAssignmentService.java:165`, `resolvePackId`) **When** this story ships **Then** both are replaced with new equivalents added to `PackSessionService`/`SessionPackPurchaseRepository` in this story (see Task 1): `hasActivePack(Long playerId, UUID coachId)` and `getActivePackId(Long playerId, UUID coachId)`, mirroring legacy's exact selection semantics (prefer a pack with `remainingSessions > 0 && expiresAt > now`, else fall back to the most recently created pack for that player+coach).

7. **Given** `BookingBatchService.createBatch()` (`BookingBatchService.java:103-104`), which today calls legacy `sessionPackPurchasedRepository.findActivePacksForDeduction(...)` (lock) and `sessionPackService.hasCredits(playerId, coachId)` (eligibility gate) as a pre-flight check, but **never sets `sessionPackPurchaseId` on any created slot** (confirmed: `createBatch`'s per-slot `Booking` construction at lines 116-127 has no `setSessionPackPurchaseId` call) **When** this story ships **Then** the legacy eligibility check is replaced with a new-path equivalent, and a decision is made (see Dev Notes — this needs a product call, do not silently guess) on whether batch bookings should carry an explicit `sessionPackPurchaseId` per slot (deducting from a specific pack at accept time, same as single bookings) or continue to always settle via the credit-wallet/Stripe path in `PaymentLifecycleService.onBatchBookingAccepted` (in which case the pre-flight check should simply be dropped, not migrated, since it was never actually wired to the payment outcome).

8. **Given** `BookingDuplicationService.duplicateNextWeek()` (`BookingDuplicationService.java:56`), which checks legacy `sessionPackService.hasCredits(original.getPlayerId(), original.getCoachId())` but **never copies `original.getSessionPackPurchaseId()` onto the new booking** **When** this story ships **Then** the eligibility check uses the new-path `hasActivePack`/`getActivePackId` equivalents from Task 1, and the new booking's `sessionPackPurchaseId` is set from the resolved pack id (mirroring how the original booking would have been created under AC2), so accept-time deduction works correctly for the duplicated booking too.

9. **Given** the full purchase → book → pause → complete → expire lifecycle **When** exercised end-to-end (manual UAT — no live payment gateway sandbox assumed beyond what existing tests already stub) **Then** observable behavior matches what the legacy system did, with no regression in `BookingServiceTest`/`BookingServiceConcurrencyIT`, and legacy `SessionPackServiceTest`/`SessionPackExpirySchedulerTest` remain green and untouched (they exercise code this story does not modify — only stops calling).

## Dev Notes

- **The single most important thing this story fixes is not in the epic's original wording**: `BookingCompletionService`/`QuickCompleteTimeoutService` unconditionally call legacy `SessionPackService.deductCredit(playerId, coachId)` at session *completion*, while `PaymentLifecycleService` (already shipped, pre-dating this story) calls the new-path `PackSessionService.deductSession(purchaseId)` at booking *acceptance*. Once callers start passing a real `sessionPackPurchaseId` (AC2), every pack-based booking gets deducted once at accept-time by the new path and would then hit the legacy deduction call again at completion-time — which either double-counts against a coincidentally-existing legacy pack or throws `booking.creditsExhausted` outright (the common case, since the new and legacy tables are unrelated). This is a latent bug hiding behind the fact that the new path currently has zero live traffic. See Task 2.
- **The accept-time payment plumbing is already done — do not rebuild it.** `PaymentLifecycleService.onBookingAccepted`/`onBatchBookingAccepted` (`PaymentLifecycleService.java`) already branch on `booking.getSessionPackPurchaseId() != null` and call `packSessionService.deductSession`/`restoreSession` correctly for single and batch bookings. This story's job for the *payment* side is almost entirely about getting a real `sessionPackPurchaseId` onto bookings that should have one (frontend selection, batch, duplication) — not writing new deduction logic.
- **`CreditWalletService`/`ParentCreditLedger` is a separate, pre-existing "pay with wallet balance + Stripe top-up" feature, unrelated to session packs.** It's what `sessionPackPurchaseId == null` bookings settle through today (`PaymentLifecycleService.handleCreditBasedBooking`) and is out of scope for this story — don't touch it, don't confuse it with either pack system.
- **`BookingBatchService`'s pre-flight pack check was already disconnected from reality before this story** — it validates legacy credit availability but never attaches a pack to the resulting bookings, so batch bookings always settle via credit-wallet/Stripe regardless. This needs an explicit product decision (Task 4), not a silent 1:1 migration of the check — migrating it as-is would just move a disconnected check onto the new schema without fixing the disconnect.
- **Frontend is currently 100% on the legacy path** — `payment.api.js`'s `purchaseSessionPack` doesn't send `playerId` at all (pre-dates Story 11.1's request shape change), and `createBookingRequest`'s payload has zero references to `sessionPackPurchaseId` anywhere in `src/frontend/src`. This is not a "flip an endpoint" story on the frontend side — pack selection UI at booking-request time does not exist yet and must be built (AC2/Task 6).
- **`SessionPackTracker.vue` today models "one active pack" as a single credits/session-count pair** (`creditsForCoach`/`currentSessionCount` computed properties picking `activePacks[0]`), whereas the new list endpoint naturally returns multiple simultaneously-active packs per player+coach (no schema-level "only one active at a time" constraint the way legacy sort-of implied via `hasActiveCredits`/`sumActiveCredits`).
