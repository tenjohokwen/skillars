# Story 12.1: Coach Player Roster and Attention Summary

Status: review

## Story

As a coach,
I want a single page listing every player I currently have (or recently had) a training relationship with, ranked by who most needs my attention,
so that I can see at a glance who's gone quiet, who has neglected skills, and where to focus next — without hunting through bookings.

## Acceptance Criteria

1. A new read-only endpoint `GET /api/development/coaches/me/roster` returns, for the **calling coach's own** coachId (resolved server-side from the authenticated principal — never from a client-supplied id), one entry per **distinct player** that currently has a booking in one of the roster-membership statuses — `ACCEPTED`, `PAYMENT_PENDING`, `CONFIRMED`, `UPCOMING`, `IN_PROGRESS`, `PAUSED`, `COMPLETED_PENDING_CONFIRMATION`, `COMPLETED`, `NO_SHOW_PLAYER`, `NO_SHOW_COACH`, `DISPUTED`, `REFUND_PENDING` — against that coach, where that booking's `requestedStartTime` falls within the last 730 days (a fixed recency floor, independent of the dormancy threshold in AC4, so the roster cannot grow unbounded from one ancient booking). No other coach's players ever appear. This status list is deliberately **wider** than, and must not be assumed identical to, `CoachPlayerAuthorizationService.ACTIVE_RELATIONSHIP_STATUSES` (`ACCEPTED, CONFIRMED, COMPLETED, UPCOMING`) — that constant answers an authorization question ("may this coach read this player's data"), not a roster-membership question, and must not be widened or repurposed to answer this one (see Task 1.2). **Amended by code review (2026-10-15) Patch, owner decision:** `DISPUTED` and `REFUND_PENDING` added — both are reachable from `COMPLETED` (`BookingStateMachine`) and represent a session that genuinely happened, so dropping the player from the roster mid-dispute/mid-refund-processing is wrong. `REFUNDED` stays excluded — a processed refund is the engagement being formally unwound, a principled cut-off avoiding an indefinite 730-day tail for a refunded one-off.
2. No new entity, table, or persisted "roster"/"relationship status" column is introduced. The roster is derived at read time from `Booking` + existing `development` module data. (A single new `platform_config` row for the dormancy-threshold key, per AC4/Task 2.4, is config, not a roster/relationship-status entity, and is not forbidden by this AC.)
3. Each roster entry includes: `playerId`, player display name, `lastSessionDate` (nullable — the most recent **SLU-recorded** session date for *this specific coach-player pair*, i.e. a session that went through the session builder and produced an SLU row; a `Quick Complete`d or builder-less booking does not advance this field even though the session happened — see Dev Notes "lastSessionDate vs. last activity"), `openNeglectedSkillCount`, a boolean `dormant` flag, and a numeric `attentionScore`.
4. `dormant` is computed, not stored: true when the player's **last activity** with this coach — defined as the later of `lastSessionDate` (AC3) and the most recent roster-qualifying booking's `requestedStartTime` (AC1), **counting only activity that has actually happened (not in the future)** — is more than a configurable threshold number of days ago, or there is no activity at all; **and the player has no roster-qualifying booking whose `requestedStartTime` is in the future** (a future-dated booking — e.g. an unpaid `PAYMENT_PENDING` request, or an `ACCEPTED`/`CONFIRMED`/`UPCOMING` booking scheduled ahead — suppresses only this flag, since the coach already has a touchpoint coming up; it does not retroactively count as "recent activity" for the purpose of the first clause). Changing the threshold via existing config changes which players are flagged dormant within the config cache TTL (`app.config.cache-ttl-seconds`, default 300s) on the node(s) that serve subsequent calls — not necessarily instantaneously across a multi-instance deployment, and not without the key being writable (see Task 2.4). **Amended by code review (2026-10-15) Patch, owner decision:** the original wording let a future-dated booking's `requestedStartTime` count directly as "last activity", which could make `daysSinceLastActivity` negative and mask a genuinely long-silent player (e.g. 11 months since last session, but a newly-booked session 3 weeks out) as neither dormant nor low-scoring. The badge ("do I need to chase them?") and the recency score ("how long has it been?") are now governed by this split definition instead of being conflated.
5. The response is sorted by `attentionScore` descending by default (highest-attention-needed player first). A player with no recent activity (per AC4) within the dormancy window must rank at or near the top; among non-dormant players, more open neglected-skill flags and more declining skill trends must rank higher than fewer/none. Exact score values are an implementation detail; only this relative ordering is a contract.
6. A brand-new player (first booking just created, no SLU/skill-trend history yet) must not error and must not be mis-ranked as if they had missing/null data treated as "maximum urgency" — a player whose only activity is a booking created moments ago must score **low** urgency on the recency component (nothing to be neglectful of yet), not be pinned to the top of the roster. Missing neglected-skill and trend signals independently default to their lowest-urgency value (0), not null-propagate into the score.
7. The endpoint requires `ROLE_COACH` and has no path/query parameter that accepts a player id or coach id from the caller — it is a "my own roster" endpoint by construction, so it cannot be used to enumerate another coach's players (this is a deliberate design choice, not an oversight — contrast with the pre-existing missing-relationship-check gap on `/neglected-skills` and `/slu/coach-contributions` specifically, which this story does **not** touch; `/exposure`, `/slu/skill-trends`, and `/narrative` already enforce the relationship check today and are not part of that gap).
8. A new coach-only frontend route (e.g. `/coach/players`) renders a "My Players" page with five distinct states, matching `CoachReviewsPage.vue`'s precedent exactly: loading spinner, an incomplete-profile state (the calling coach has `ROLE_COACH` but no `CoachProfile` row yet — e.g. mid profile-builder — which the backend surfaces as a 404; render a dedicated message + link to the profile builder, not a generic error banner), a generic error state, an explicit empty state (zero roster entries), and — when populated — the roster sorted by attention, each row **always** showing player name and last-session date (or "never trained together" when there's no `lastSessionDate`), a dormant badge when applicable, and an open-neglected-skill-count badge when that count is greater than zero. All new UI strings are externalized via i18n in `en-US`, `de-DE`, and `fr-FR`. **Amended by code review (2026-10-15) Patch, owner decision:** the original wording's parenthetical ("dormant indicator when applicable") was read as license to substitute the dormant indicator for the last-session date on a dormant row — hiding the one fact (how overdue the player is) a coach most needs for that row. The date is now unconditional; the dormant badge is a separate, additional indicator, not a replacement.
9. A nav entry for the new page exists under the existing Coach section of the main navigation, visible only to authenticated coaches (same gating as the other coach nav items).
10. Out of scope for this story — explicitly deferred to later Epic 12 stories per the source brainstorm doc, must not be implemented here: session-close recap capture, the Session Prep Card inside a booking's detail view, a coach-facing single-player detail page reusing `PlayerTimelinePanel.vue`, the recap→report-generation tie-in, the player/parent-initiated flag, fixing the missing-relationship-check gap on `/neglected-skills`/`/slu/coach-contributions`, and surfacing `SkillTrendDirection` as its own field in the roster response (it is consumed only internally, folded into `attentionScore`, per Task 2.3 — no per-skill trend breakdown is part of this story's contract).

## Dev Notes

### Why this is a new epic, not a `skillars-deferred-N` bundle

Most other recent stories in this project (`skillars-deferred-140`…`151`) bundle small, already-identified bugs/gaps mined from `deferred-work.md`. This is a genuinely new feature initiative sourced from a fresh brainstorming session, so it follows the `skillars-epic-11` precedent (the payment-cutover initiative) instead: its own epic number (12), its own story sequence, tracked the same way in `sprint-status.yaml`. The epic-11 precedent also added a corresponding `## Epic 11` section to `skillars-epics.md` alongside its first story — consider adding a matching `## Epic 12` section there for consistency, though it isn't a functional requirement of this story.

### Multi-coach data boundary — why reusing these specific signals is safe

The brainstorm doc's Theme 4 resolved the multi-coach question as: **raw session notes/recaps stay private per coach; aggregate/quantitative skill-development signals stay shared across coaches.** This story never touches notes/recaps (those don't exist yet — Priority 2, future story). Every signal this story surfaces — `NeglectedSkillFlag` (player-level, not coach-scoped) and skill-trend direction — is exactly the "aggregate, shared" category already established by the existing `/slu/coach-contributions` endpoint. Skill-trend direction is derived from `player_slu_weekly_snapshot` (via `SluWeeklySnapshotRepository.findByPlayerIdFromWeek`, consumed by `SluDashboardService.getSkillTrends`) — **not** `player_skill_stats`, which does carry a `coach_id` column. The two are separate tables; `player_slu_weekly_snapshot` has no coach dimension at all, so the trend signal cannot be coach-filtered even in principle — stronger grounds for "shared" than the `player_skill_stats` citation would have given. Only `lastSessionDate` is coach-scoped (via `SluRepository.findLastSessionDate(playerId, coachId)`, which *does* read `player_skill_stats`), which is correct: "when did *I* last see this player" is inherently per-coach.

### The real architectural gap this story closes

Per the brainstorm's Codebase Grounding section: the backend development-tracking infrastructure (`PlayerTimelineEvent`, `NeglectedSkillFlag`, `SluDashboardService`, `CoachContributionDto`, `DrillSuggestionService`) already exists and is already `ROLE_COACH`-authorized at the API layer — but no coach-facing page composes it into a ranked, development-aware "my players" view. (The one adjacent exception, `CoachCommandCenterPage.vue`'s client-side `activeClients` week-scoped name list, is a quick-glance widget with no development signals or ranking — see Source section; this story's roster page coexists with it rather than replacing it.) This story is almost entirely new composition over existing read paths, not new domain modeling — resist the urge to introduce a persisted roster/relationship-status entity; AC2 forbids it.

### `lastSessionDate` vs. last activity — the Quick Complete blind spot

`SluRepository.findLastSessionDate` is `MAX(calculated_at)` over `player_skill_stats`, and a row is written **only** when `SluCalculationService.onBookingCompleted` sees an attended booking with a session-builder `Session` in `SAVED`/`COMPLETED` status that has blocks with drills. `BookingCompletionService.initiateQuickComplete` is a first-class shipped coach flow that skips all of this — a coach who Quick-Completes sessions, or never uses the session builder, produces **zero** SLU rows for that player, ever. If dormancy/recency were computed from `lastSessionDate` alone, every player on such a coach's roster would read `lastSessionDate = null`, normalize to maximum urgency, and the whole roster would invert into "everyone is urgent, everyone is dormant" — exactly the failure AC6 forbids. This is why Tasks 2.1/2.5/2.6 compute `dormant` and the recency score component from the merged `lastActivityDate` (`max(lastSessionDate, latestBookingTime)`) rather than `lastSessionDate` alone: a Quick-Complete-only coach's players still have a `latestBookingTime` signal even with no SLU rows at all. `lastSessionDate` itself — the API-facing field — keeps its narrower, honest meaning ("last SLU-recorded session"), and the frontend should favor the dormant flag over inferring urgency from a null `lastSessionDate` directly.

### Explicitly out of scope (do not implement, do not let scope creep in)

Session-close recap capture, Session Prep Card, the coach-facing single-player detail page (`PlayerTimelinePanel.vue` reuse), recap→report-generation, the player/parent-initiated flag, surfacing `SkillTrendDirection` as its own roster field, and fixing the pre-existing missing-relationship-check gap on `/neglected-skills`/`/slu/coach-contributions` specifically (`/exposure`, `/slu/skill-trends`, and `/narrative` already enforce the relationship check and are not part of that gap — see AC7). Flagged in the brainstorm doc as a separate follow-up, not this story — do not fix it as a drive-by here.

### Known residual edge cases (acceptable for this story, not for silent "fixing")

- **GDPR-erased players.** `GdprErasureService` deletes SLU rows, weekly snapshots, and neglected-skill flags on erasure, but `player_profiles` survives as a tombstone and `booking.bookings` rows are untouched (no FK from bookings to player_profiles). An erased player can still appear on the roster with `lastSessionDate = null` and `openNeglectedSkillCount = 0`; the `latestBookingTime` fallback means they won't necessarily rank top (unlike before this story's redesign), but they also won't be filtered out. Acceptable: this story doesn't own erasure-aware roster filtering; do not add it here.
- **Bounds at the extremes.** Corrected by code review (2026-10-15) Patch: the original bullet here inverted `ConfigService`'s two overloads. The 4-arg `getBoundedLong(key, defaultValue, min, max)` — what `CoachRosterService` actually calls — **falls back to `defaultValue` (30)** on an out-of-range stored value; it does **not** clamp to the nearest bound (clamping is the *3-arg*, no-default overload's behavior, which this key does not use). So a stored `0` or `99999` both read as `30`, not `1` or `3650`. Task 5.1's bounds test (`getRoster_outOfRangeDormantAfterDaysConfig_fallsBackToDefaultNotClamped`) asserts the default-fallback behavior, not clamped values.
- **i18n parity across locale files is reviewer-enforced, not mechanically gated** — no lint or parity check exists for `en-US`/`de-DE`/`fr-FR` today (pre-existing drift: `auth.emailVerifiedPleaseLogin` is en-US-only). Keep the three files in sync by inspection in Task 4.5; do not attempt to fix the pre-existing drift as an unrelated drive-by.
