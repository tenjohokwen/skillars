## User Story

As **a coach using Skillars in a non-English locale, and the developer maintaining the `development`/`booking`/`payment` modules' error-handling and roster-scoring consistency**, I want nine independently-verified, currently-open defects and gaps fixed — a store-wide sweep (not repo-wide — see Dev Notes for two known-remaining `AvailabilityManagerPage.vue` sites explicitly left out of this pass) closing the remaining hardcoded-English fallback messages in `development.store.js`/`booking.store.js` (plus `errorHandler.js`'s own hardcoded status-code fallbacks, the shared helper the sweep routes through), a de-duplicated 30%-contribution-threshold between `CoachContributionSection.vue` and `CoachPlayerDetailPage.vue` with an unambiguous empty-state message, the third and final SLU-only coach-access gate (in `ReportGenerationService`) widened to the same merged signal the roster and timeline already use, an efficiency fix removing two needless full-entity hydrations that exist only to read `.size()`, a one-line off-by-one fix on the roster's dormancy boundary, a null-safety guard on the roster's player-name lookup, and three small test/UI-completeness gaps in the coach-branding feature (no end-to-end test pinning its id-space fix, an unrendered fetched logo preview, and a stub assertion that never exercises what it claims to) — so that **a French- or German-speaking coach sees a translated error on every one of these eleven store call sites instead of an English literal; the 30% threshold that decides whether the contribution panel's empty state shows cannot silently drift between its two copies ever again; a Quick-Complete-only coach can finally generate a report for a player they've actually trained, the same fix already applied to that coach's timeline and roster; two hot paths stop materializing full JPA entity graphs to read a count; the dormant badge and the recency score agree at the boundary instead of disagreeing for one exact-threshold day; a missing player-profile row degrades to a `null` `playerName` in the roster JSON instead of being surfaced unguarded; and the coach-branding feature's test suite and UI are both honest about what they cover and render.**

## Acceptance Criteria

1. **Store-wide hardcoded-English error-message sweep.** `errorHandler.js`'s `parseApiError` (`:83-101`) routes its five status-code-fallback messages (`'Bad request'`, `'Unauthorized'`, `'Forbidden'`, `'Not found'`, `'Server error'`/`'An error occurred'`) through `i18n.global.t(...)` using the existing `defaultErrorKeyByStatus` map (`:29-34`), mirroring the `error.network` branch above (`:60`) which already does this — but the map is not a drop-in message source as-is; it was built to pick an `errorKey`, not a user-facing string, and two decisions must be made explicitly rather than inherited silently: **(a)** 401 must map to `security.sessionExpired` ("Your session is no longer valid. You need to sign-in again"), **not** `defaultErrorKeyByStatus[401]`'s current `security.unauthorized` ("You do not have the required rights…" — that is a 403-shaped, not-authenticated-vs-not-authorized message); **(b)** since **no `error.serverError` key exists in any of the three locale bundles** (confirmed), 5xx should map to `error.generic` ("An unexpected error occurred. Please try again.") rather than collapsing into the same `error.unknown` ("An unknown Exception has occurred") used for every other unmapped non-5xx status — losing the 5xx-vs-client distinction the current English literals (`'Server error'` vs `'An error occurred'`) still preserve today. `development.store.js`'s ten remaining `err?.response?.data?.message ?? '<hardcoded English>'` call sites (`fetchNarrative:93`, `fetchTargets:103`, `saveTargets:113`, `fetchRadarEntries:124`, `submitRadarAssessment:136`, `fetchRadarDisplay:148`, `saveRadarPreferences:168`, `fetchCorrelationInsights:180`, `fetchReports:195`, `generateReport:208`) and `booking.store.js:293`'s `packsError` fallback are all replaced with `getErrorMessage(err)` from `src/utils/errorHandler.js` (new import in both files) — none of these eleven sites reads `err?.response?.data?.message` directly again, since that field never exists on the real `ErrorDto` shape (confirmed: `ErrorDto.java` has no top-level `message` field, only `errorMsg.message`). **Known trade-off, accepted rather than silently inherited:** `getErrorMessage` returns `i18n.global.t('error.network')` for *any* thrown value without a `.response` (a client-side `TypeError`, an aborted promise, a plain `throw`) — today each of these ten sites at least names the failing operation (e.g. "Failed to generate report"); after the sweep every one says the same generic network-error string even for a non-network bug. `booking.store.js:293`'s current fallback is three-armed (`?? e?.message ??`), so `getErrorMessage` also drops that middle, non-axios-message arm. Accepted as a net improvement (ten-for-one English-literal leaks fixed) but the implementer should not assume this is lossless. **Scope boundary:** this is a *store-wide* sweep (`development.store.js` + `booking.store.js` + their shared `errorHandler.js` dependency), not repo-wide — see Dev Notes for two further `AvailabilityManagerPage.vue` sites with the identical bug, deliberately left out of this story's scope.

2. **30%-contribution-threshold de-duplication and unambiguous empty state.** `CoachContributionSection.vue` is `<script setup>` (confirmed: `:20`), which compiles to a single default export — a named `export` statement inside a `<script setup>` block is a build error (confirmed repo-wide: zero `.vue` files under `components/` or `pages/` contain a top-level named export; this codebase's established convention for genuinely shared logic is a plain module under `src/utils/` or `src/composables/`, e.g. `src/utils/sessionRedirect.js`, `src/composables/useLoading.js`). **AC2's fix is therefore: extract the `30` threshold and the group-by-skill-then-filter logic into a new shared module — e.g. `src/utils/coachContributions.js` exporting a `hasTopAttributions(contributions)` predicate (and/or the `topAttributions(contributions)` list itself)** — and have both `CoachContributionSection.vue`'s `topAttributions` computed and `CoachPlayerDetailPage.vue`'s `hasTopContributions` computed (`:101-112`) import and call it instead of each re-implementing the identical logic. This new module must be added to the File List and to AC10's test list (a focused Vitest spec covering the 30%-boundary case, since this is the one piece of shared logic AC2 actually introduces). A new boundary test asserts both consumers agree at exactly 30%. Note this is a drift *guard*, not a fix for a current discrepancy — both existing copies already use `>= 30` and already agree at exactly 30%; the value is preventing future drift, not correcting today's behavior. **A third, previously-missed consumer:** `ParentDevelopmentPortalPage.vue:62` renders `<CoachContributionSection :contributions="store.coachContributions" />` with no `v-if`/`v-else`/empty state at all, relying on the component's own silent root-`v-if` collapse — the exact defect this AC's split fixes for the coach page. Add the same wrapper there too (or explicitly scope it out with a one-line reason) and add this file to the File List. `coach.playerDetailNoContributions` (shown whenever every per-skill top contributor is under 30%, even when real contribution data exists below that line — `CoachPlayerDetailPageSpec.js:157-172` already demonstrates this exact case with a genuine 10% contribution at `:163`) is split into two distinct, correctly-scoped messages in all three locale bundles: one for `coachContributions.length === 0` (genuinely no data) and one for "data exists but none cleared the 30% display threshold" — the page selects between them instead of showing the same string for both cases. (This split is safe: `coach.playerDetailNoContributions` is used only at `CoachPlayerDetailPage.vue:59` and asserted only at `CoachPlayerDetailPageSpec.js:170`, so nothing else breaks.)

3. **Third and final SLU-only coach-access gate fixed — and its widening named explicitly.** `ReportGenerationService`'s report-generation guard (`:145-148`, currently `sluRepository.findLastSessionDate(playerId, coachId)`) is replaced with a call to the existing `CoachPlayerLastSessionResolver.resolve(playerId, coachId).lastSessionDate()` (`CoachPlayerLastSessionResolver.java:27`, already introduced by `skillars-12-3` and already consumed directly by `CoachRosterService`, `TimelineQueryService`, and `SessionPrepService`) — the identical merged SLU-row+coach-scoped-timeline-event signal those three surfaces already use. A Quick-Complete-only coach who can already read their own timeline, roster entry, and Session Prep Card for a player can now also generate a report for that same player, closing the last of the three independently-discovered instances of this same narrow signal.

   **This is a real, if bounded, authorization widening — not a purely mechanical swap — and the implementer must make two explicit calls rather than assume parity with the other three surfaces.** Unlike the coach-scoped timeline/roster/Prep Card surfaces this fix is modeled on, the report's own body is keyed by `playerId` alone: `buildSkillEntries(playerId)` (`:291-312`, including a per-skill `distinctCoachCount`), `sumTotalSluByPlayerId(playerId)`, and `countDistinctSessions(playerId)` all return the player's **entire cross-coach SLU history**, not anything scoped to the calling coach. So widening the gate also widens *what* a newly-permitted coach can see in the generated PDF, not just *whether* they can generate one. This is bounded severity, not an unprotected-access gap: `generateReport:137` already calls `coachPlayerAuthorizationService.requireCoachPlayerRelationship(coachUserId, playerId)` first, which requires an active booking relationship — the SLU-clock gate being widened here is a second, narrower layer, not the only protection. Two decisions to make and document during implementation, not defer silently: **(a)** is a report showing cross-coach aggregate SLU data acceptable for a coach whose own relationship with the player is Quick-Complete-only (no session-builder usage), given the other three surfaces only ever showed that coach's *own* scoped view; **(b)** `notifyParent(...)` (`:226`) fires **unconditionally** inside `onReportGenerated` on every successful report — should a newly-permitted coach's report generation still trigger a `PERFORMANCE_REPORT_SHARED` email to the parent, or should that stay as-is. (A player with zero SLU rows produces a structurally empty but non-erroring PDF — `sumTotalSluByPlayerId`/`countDistinctSessions` are `COALESCE(...,0)`, and `buildSkillEntries` returns an empty list — so this is not a crash risk, just an edge case worth a passing mention in the implementation.)

4. **`.size()`-for-a-count efficiency fix.** A new `int countByPlayerIdAndResolvedAtIsNull(Long playerId)` method (declared `int`, matching both call sites' existing variable type — `CoachRosterService.java:131`'s `neglectedCount` and `SessionPrepService.java:80`'s equivalent are both assigned to an `int`) is added to `NeglectedSkillFlagRepository` (alongside the existing `findByPlayerIdAndResolvedAtIsNull`, not replacing it — there are at least four other entity-consuming callers of the existing method: `SluDashboardService:78`, `SluTargetService:60`, `NeglectedSkillProcessor:58`, `DrillSuggestionService:55` — so keeping it is mandatory, not merely a hedge). Both existing call sites that discard the hydrated entities to read only `.size()` — `CoachRosterService.java:131` and `SessionPrepService.java:80` — are switched to the new count query.

5. **Dormancy-boundary off-by-one fix — fix the comparison operator only, not the day calculation.** `RosterAttentionCalculator.compute`'s `dormant` flag (`:58-59`, currently `signals.daysSinceLastActivity() > signals.dormantAfterDays() && !signals.hasUpcomingBooking()`) disagrees with its own recency-score saturation (`:64-65`, `clampedDays = min(max(d,0), D)`, `recencyNorm = clampedDays/D`) at exactly `d == D` (`d` = `daysSinceLastActivity`, `D` = `dormantAfterDays`): `recencyNorm` is already fully saturated to `1.0` at `d == D` (since `clampedDays` clamps *at* `D`, not before it), but `dormant` requires the strictly-greater `d > D` — so a player exactly at the threshold reads as "maximally urgent by score" but "not yet dormant by badge" for one day. **The fix is `>` → `>=` on line 58 only.** `CoachRosterService.java:129`'s `Duration.between(...).toDays()` (truncation-toward-zero) is a red herring, not the root cause: the disagreement is purely an integer-space mismatch between a strict `>` and a clamp-at-`D`, and it reproduces for *any* way of computing the integer `d` — rounding instead of truncating only changes which real elapsed duration maps to which integer `d`, it does not close the `>` vs. `>=` gap at all. Worse, changing the day calculation (rounding) actively violates this AC's own "no change away from the boundary" requirement: `daysSinceLastActivity` feeds `recencyNorm` → `attentionScore` → the roster's sort order (`CoachRosterService.java:94`), so switching from truncation to rounding would change the score for **every** player with a fractional elapsed-day count `>= 0.5`, not just the ones at the exact boundary. Leave `toDays()` untouched.

6. **Roster `playerName` null-safety.** `CoachRosterService.java:146`'s `namesByPlayerId.get(playerId)` (fed by `findAllById`, which silently returns fewer rows than requested for any player-profile row that's gone missing, per `:80-83`) no longer surfaces an unguarded `null` `playerName` into `RosterEntryResponse` (a plain record, no compact constructor, no null constraint — the resulting defect is simply `"playerName": null` in the JSON response, an identity-less roster row; this is **not** an NPE risk, since nothing downstream dereferences it unchecked). Either filter such entries out of the roster response, or substitute a safe fallback display value — **but if choosing a fallback, return `null` from the backend and localize client-side**, following this codebase's actual precedent: `coach.playerDetailUnknownPlayerName` (`en-US/index.js:266`, `'this player'`) is a lowercase, mid-sentence pronoun fragment consumed only as a frontend `route.query.playerName || t('coach.playerDetailUnknownPlayerName')` fallback (`CoachPlayerDetailPage.vue:92`) — it is not a value meant to be returned from an API field, and reusing its *string* in the backend would put untranslated English into JSON. This gap is latent, not reachable today (`player_profiles.name` is `NOT NULL`, and no hard-delete path exists for `player_profiles` — `GdprErasureService` tombstones rather than deletes), so there is no urgency pressure forcing one specific choice.

7. **Coach-branding id-space end-to-end test.** A new integration test exercises the real `/api/storage/sign/upload` → confirm → `PUT /api/development/coaches/me/branding` flow end-to-end (not a hand-built `FileStorageObject` fixture with `.ownerId(...)` set directly, which is what the existing `ReportGenerationServiceTest` branding coverage does today), pinning that all four call sites this project's `coach_branding` ownership fix depends on — `SecurityUtil.getCurrentCoachUserId()` (consumed by `CoachBrandingResource:45`, not a method on the resource itself), `ReportGenerationService.saveBranding`'s `assertOwnership` call (`:281`), `StorageResource`'s `coach_branding` entry in `OWNER_BOUND_ENTITIES` (`:41-42`), and the frontend's `entityId: String(userId)` (`EditCoachBrandingDialog.vue:179`) — actually agree end-to-end, not just that each one's own unit test passes in isolation. **Concrete target, not a new class:** `ReportGenerationServiceIT` already `extends BaseStorageIT`, which brings up a real SeaweedFS S3 container in the same package — add the new test method there rather than hedging on a brand-new IT class. `StorageResourceIT` (`:138-143`, helpers at `:222-265`) already performs the exact real `signUploadHttp → putToS3 → confirmUploadHttp` round trip this AC needs; follow that precedent rather than inventing a new upload-flow helper. Unmentioned setup the implementer will need: the test coach needs `ROLE_COACH`, a `CoachProfile`, and `CoachSubscriptionTier.ACADEMY` (`ReportGenerationService:276-279` throws `FeatureGatedException` otherwise), and the authenticated principal's `businessId` must equal the request's `entityId` (`StorageResource:50`).

8. **`ProfilePage.vue` renders its own fetched logo.** The branding section (`:270-291`) — which already fetches `coachBranding.logoSignedUrl` via `getCoachBranding()` (`:554`) — renders that logo (an `<img>` or `q-avatar`, matching whatever visual precedent `EditCoachPhotoDialog.vue`/the existing player-photo-preview convention elsewhere in this codebase uses) in the unlocked, uploaded state, instead of showing only the hex `brandColour` swatch (`:290`) and leaving the logo preview reachable only from inside `EditCoachBrandingDialog`.

9. **`EditCoachBrandingDialogSpec.js`'s dead fetch-response assertion removed or made meaningful.** `EditCoachBrandingDialog.vue:186`'s `await fetch(uploadUrl, {...})` never reads `.ok` (or any other field) off the response, so `global.fetch = vi.fn().mockResolvedValue({ ok: true })` (`EditCoachBrandingDialogSpec.js:21`) tests nothing about response handling. The narrow, correct fix is adding an `if (!res.ok) throw new Error(...)` check after the `fetch` call — **not** a larger error-handling redesign: `handleSave` (`:159-211`) already has exactly one `try` wrapping the whole sign→PUT→confirm→save sequence with one `catch (err) { setError(err) }` (`:205-207`), so a thrown error from the new check is already caught by existing machinery, with zero new i18n keys needed (it lands in the existing `!error.response` → `error.network` path, rendered by the dialog's own `{{ errorMessage }}`). **This is a real but low-severity gap, not data corruption:** a failed PUT does **not** silently leave a broken `logo_key` persisted — `FileStorageService.confirmUpload` calls `s3Client.headObject(...)` and throws `StorageObjectNotFoundException` on a missing object (plus validates `contentType`/`fileSizeBytes`/ETag) *before* anything is saved, so a failed upload already fails loudly at the very next call, just with a confusing message ("The requested resource was not found" instead of an upload-specific one). Add the `.ok` check and a corresponding test asserting the failure path; do not scope this up into redesigning the dialog's broader error handling.

## Dev Notes

### Why the `errorHandler.js` fallbacks are in scope, not just the two store files

`getErrorMessage`'s only real content is whatever `parseApiError` computes for `message` (`errorHandler.js:166-169`) — routing the two stores through it without first fixing `parseApiError`'s own hardcoded status-code fallbacks (`:83-101`) would just move the same English-literal-to-non-English-user bug one layer deeper, not fix it. The `error.network` branch above (`:60`) already demonstrates the correct pattern (`i18n.global.t('error.network')`) for exactly this file — apply the same pattern to the status-code switch, with the two key-mapping decisions from AC1 (401, 5xx) made explicitly rather than inherited from a map built for a different purpose.

### Why `booking.store.js:293` is bundled with the `development.store.js` sweep

The ledger's own text (`deferred-work.md:3810`) explicitly says "`booking.store.js:293` has the same bug and should be included" — same root cause (a nonexistent `data.message` field), same fix (`getErrorMessage`), trivially small addition to an already-in-scope sweep.

### Why AC2's empty-state split, not a reworded single string

The ledger (`deferred-work.md:3813`) offers two options: reword the existing string to be threshold-aware, or distinguish the two cases outright. Distinguishing the cases is the more correct fix — a coach who has real, measured contribution data that simply didn't clear 30% is in a meaningfully different situation from a coach for whom no contribution data exists at all, and conflating them (as today) can read as "no coach has worked with this player," which is false in the first case. This is a small in-scope wording/scoping judgment call, not a product decision requiring sign-off — no existing design doc specifies this copy's two cases separately, so there is nothing to contradict.

### Why AC3's call-site swap is still a real decision, not a pure redesign-avoidance

`CoachPlayerLastSessionResolver` (`CoachPlayerLastSessionResolver.java:22-68`) already exists, already merges the SLU-row signal with the coach-scoped `player_timeline_events` signal, and is already injected and consumed **directly** by `CoachRosterService`, `TimelineQueryService`, and `SessionPrepService` — all added by `skillars-12-3`. (Correction: `TimelineQueryService` injects the resolver directly at `TimelineQueryService.java:29`; it does not reach it "via `SessionPrepService`'s own dependency" — the three are three independent direct consumers, not a chain.) `ReportGenerationService` is the third and final consumer of the old, narrower `sluRepository.findLastSessionDate` signal that `skillars-12-3`'s own pre-implementation story review (`deferred-work.md:3802`) flagged as deliberately out of that story's scope. This story closes it by injecting the existing resolver — no new class, no schema change, and no transaction-boundary change (the resolver's own transaction demarcation joins `generateReport`'s existing `@Transactional` `REQUIRED` propagation; Spring does not downgrade it). But — see AC3 above — the guard's `lastSession == null` swap is mechanically trivial while what it *unlocks* (a cross-coach aggregate report body) is not; don't let the mechanical simplicity of the diff imply the authorization question is equally simple.

### Why AC4's fix adds a new repository method rather than changing the existing one's return type

`NeglectedSkillFlagRepository.findByPlayerIdAndResolvedAtIsNull` (`:11`) returns `List<NeglectedSkillFlag>` and may have callers elsewhere in the codebase beyond the two named call sites that only need a count — changing its return type would be a breaking signature change for any such caller. Adding a sibling `countByPlayerIdAndResolvedAtIsNull` (Spring Data's standard count-derivation naming) is additive and lets each of the two call sites choose the shape it actually needs.

### Why AC5's fix is pinned to one call site, not left to the implementer's judgment

An earlier draft of this story treated `CoachRosterService.java:129`'s `Duration.toDays()` truncation and `RosterAttentionCalculator.java:58`'s strict `>` comparison as two equally-valid places to fix the same off-by-one, resolvable "either way." That is wrong, and worth recording why so it isn't re-proposed during implementation: the disagreement is a pure integer-space mismatch (saturation happens at `d >= D`, dormancy requires `d > D`) that exists for *any* method of computing the integer `d` — changing truncation to rounding only shifts which real-world elapsed duration maps to which `d`, it does not make the `>` vs. `>=` gap disappear. Worse, rounding the day count is actively harmful: `daysSinceLastActivity` also feeds the roster's sort order via `attentionScore`, so rounding would silently re-score every player with a `>= 0.5`-day fractional elapsed time, directly contradicting the "no change away from the exact boundary" promise. The only fix that satisfies AC5 as written is `RosterAttentionCalculator.java:58`'s comparison operator. `toDays()` stays untouched.

### Why AC6 asks the implementer to check existing precedent before choosing filter-vs-fallback, and why that precedent points at the backend, not away from it

`coach.playerDetailUnknownPlayerName` (`en-US/index.js:266`, `'this player'`) is this codebase's one established "entity went missing but the parent record didn't" display convention — but it is a **frontend-only** pattern: a lowercase pronoun fragment interpolated into a sentence, never a value meant to flow through an API field. The correct reading of this precedent for AC6 is therefore the opposite of "add a backend English fallback": **keep `RosterEntryResponse.playerName` nullable (or filter the entry out) and let the frontend apply the same client-side localization pattern it already uses elsewhere**, rather than inventing an untranslated string inside `CoachRosterService`. This gap is latent, not reachable today (`player_profiles.name` is `NOT NULL`, and `GdprErasureService` tombstones rather than hard-deletes `player_profiles`), so there is no urgency pressure forcing a choice before implementation — but whichever is chosen, it must not put raw English into the JSON response.

### Why AC7 doesn't just add more unit-test coverage to `ReportGenerationServiceTest`

Correction to an earlier draft: `ReportGenerationServiceTest` does **not** mock `FileStorageService` away entirely — `@Mock` is the class-level default (`:67`), used by most tests, but `saveBranding_realFileStorageService_ownershipCheckPassesForCallersOwnUserId` (`:377-423`) already constructs a **real** `FileStorageService` (`:390-391`) with a hand-built `.ownerId(COACH_USER_ID.toString())` fixture (`:383`) — exactly the kind of test that was itself missing when the original ownership-id-space bug (fixed by `skillars-deferred-151` AC3) shipped unnoticed, per that story's own Finding 3 #1. That existing test strengthens confidence in the fix's correctness but still doesn't prove the four call sites agree about *which* identifier flows through the real upload pipeline end-to-end — a hand-built fixture asserts the backend's own ownership check works, not that the frontend's `entityId`, the presign response's `key`, and the confirm/save calls all actually carry the same identifier through a real round trip. Only a real sign-upload→confirm→save IT does that.

### Why AC9 is a small, mandatory fix, not a choice between two options

An earlier draft of this story offered two options (add a real failed-upload branch, or simplify the stub to not imply coverage that doesn't exist) and claimed the surrounding presign/confirm/save calls "do have `security.featureGated`-style catches" to mirror. Both the choice and that claim don't hold up: `handleSave` (`:159-211`) has exactly **one** `try` wrapping the entire sign→PUT→confirm→save sequence with a single shared `catch (err) { setError(err) }` (`:205-207`) — there are no individual per-step catches anywhere in the function to mirror; `featureGated` appears only in a code comment (`:206`), not as an actual catch block. So the real, narrow defect is just: the PUT's response is never checked for `.ok`. Adding `if (!res.ok) throw new Error(...)` after the `fetch` call is cheap (the existing shared `catch` already handles the throw, no new i18n key needed) and is the only change that both fixes the dead-assertion problem *and* closes a real (if minor, see AC9's severity note) UX gap — there is no meaningfully-larger-scope version of this fix to budget away from.

### Correction found during this story's drafting, not in the ledger: `SessionBuilderPage.vue` is no longer orphaned

The "coach UI CRUD audit (2026-10-14)" ledger bullet (`deferred-work.md:3780`) says no page links to `coach/session-builder/:bookingId`.
