## Acceptance Criteria

### Booking free-text GDPR coverage & sanitization/truncation parity

1. **`Booking.notes` and `Booking.playerRequest` are anonymized when their authoring player's data is erased.** Add a new `@Modifying @Query` method to `BookingRepository.java` (alongside its existing `@Query` methods, `:18-115` etc.):
   ```java
   @Modifying
   @Query("UPDATE Booking b SET b.notes = NULL, b.playerRequest = NULL WHERE b.playerId = :playerId")
   void anonymizeNotesAndPlayerRequestByPlayerId(@Param("playerId") Long playerId);
   ```
   Wire it into `GdprErasureService.deletePlayerDevelopmentDataInDedicatedPool` (`:1267-1381`) as its own independently-bounded step, **mirroring `sessionCompletionDataRepository.anonymizeByPlayerId`'s existing placement exactly** (`:1337-1339`, right after the comment block explaining why that call sits outside the `development`-schema cumulative-lock-budget groups — `booking.bookings` is the same `booking` schema as `session_completion_data`, for the same reason, not folded into the `development`-schema groups' budget). Add the new call directly after the existing `sessionCompletionDataRepository.anonymizeByPlayerId(playerId)` line, under its own `setStatementLockTimeout(lockTimeoutSeconds)` call (one more un-budgeted statement, same convention). **Do not key this on `coachId` or add a COACH-branch call** — both columns are purely player/parent-authored text read *by* the coach, never written by them, so there is no coach-authored half to also scrub. (**Precedent correction:** the comment at `:341-344` does *not* describe a player-authored/coach-authored split within `session_completion_data` — `voiceNoteText`/`whatWeDid`/`whatsNext` are **all three coach-authored**; `anonymizeByPlayerId` and `anonymizeByCoachId` null the *same* three columns, keyed differently only because the table has no single "owner" column and needs an erasure arm for each party who could be erased. `Booking.notes`/`playerRequest` don't have that problem — they have exactly one author, the player/parent — which is the actual reason a single playerId-keyed method is correct here, not an extension of that precedent.) One playerId-keyed method correctly covers both the self-registered-PLAYER-erasure call site (`eraseTransactional`, `:480`) and the per-child call inside PARENT erasure (`eraseParentChildren`, `:851`) — both already funnel through this same shared method, so no second call site is needed anywhere.
   DSAR *export* needs no change — `GdprExportService` already serializes whole `Booking` entities (confirmed pattern from the ledger item's own note), so both columns are already covered there for free.
   **Decide before implementing:** `Booking` is `@Version`-managed (`:60-62`); a bulk `@Modifying @Query UPDATE` does **not** bump the version column (Hibernate only does that for `UPDATE VERSIONED` HQL), and `Booking` is not `@DynamicUpdate`. A booking loaded concurrently (e.g. `setCancelReason`/`save` at `:893-894`, or `setPlayerRequest`/`save` at `:751-753`) will rewrite every column — including `notes`/`playerRequest` — from its stale in-memory snapshot, silently resurrecting just-erased text, with no optimistic-lock failure. `session_completion_data` has no `@Version`, so this gap doesn't exist for that precedent. Either write the query as `UPDATE VERSIONED` (bumps the version so a racing save fails `OptimisticLockException` instead of clobbering) or explicitly accept the race as out of scope and say so — don't silently inherit the non-versioned precedent's safety without checking it applies.

2. **A single, shared helper sanitizes and truncates both `notes` and `playerRequest` consistently.** **Corrected premise:** `commons-lang3` is pinned at `3.21.0` (`pom.xml:369`), and that version's `StringUtils.truncate` is already surrogate-pair-aware — verified by executing it against the real jar with an astral character straddling the 500-char cutoff: it backs the cut off to 499 chars rather than splitting the pair. **There is no surrogate-splitting bug to fix, and no guard code is needed for it.** (If `commons-lang3` is ever downgraded below the version that introduced `splitsSurrogatePair`, this reasoning needs re-checking — but do not write dead defensive code against today's pinned version.)
   The real, still-open gaps this AC fixes: (a) `createBookingRequest`'s `booking.setNotes(req.notes())` (`:346`) has no sanitizer call at all, unlike the sibling column's `setPlayerRequest` (`:744-749`); (b) that same raw, unsanitized `req.notes()` is also published on `BookingRequestedEvent` (`:351-354`) and rendered into the coach's booking-request email by `BookingEmailListener:72` / `mails/bookingRequested.html:11` — sanitizing only the DB write leaves the more exposed off-platform-contact channel (email) completely open, so the local variable must be sanitized once and reused at both the `setNotes` call and the event-publish call, not just at the write.
   Add one new private static helper to `BookingService.java` (near the other small private helpers, e.g. after `resolvePlayerNames`/`resolveParentNames`, `:1046-1054`):
   ```java
   private static String sanitizeAndTruncate(ContactDetailSanitizer sanitizer, String input, int maxLength) {
       if (input == null || input.isBlank()) return null;
       String sanitized = sanitizer.sanitize(input).sanitized();
       return StringUtils.truncate(sanitized, maxLength);
   }
   ```
   Replace `setPlayerRequest`'s existing inline sanitize+truncate block (`:744-749`) with `sanitized = sanitizeAndTruncate(contactDetailSanitizer, playerRequest, 500);`. In `createBookingRequest`, sanitize `req.notes()` into a local once and use it both for `booking.setNotes(...)` (`:346`) and for the `BookingRequestedEvent` publish at `:351-354` (so the email template never sees the raw value either). **Do not reuse or repurpose the `notes` column for `playerRequest` or vice versa** — they remain two separate columns with separate lifecycles (`notes` write-once at creation, surfaced on the coach's request-acceptance queue; `playerRequest` editable any time the booking is `CONFIRMED`/`UPCOMING`, surfaced on the Session Prep Card) per `skillars-deferred-155`'s own Dev Notes on this exact point — this AC only changes how each column's value gets *sanitized* (and, for `notes`, where the sanitized value additionally flows — into the email event), not what it *is* or where it's *surfaced*.

### PDF font encoding

4. **Generated performance-report PDFs render non-WinAnsi characters correctly instead of silently dropping them.** `ReportGenerationService.java:458-461`'s four `Font`s are all built via `FontFactory.getFont(FontFactory.<style>, <size>)`, which resolves to a base-14 Type1 font under WinAnsi (cp1252) encoding — openpdf's base-14 fonts cannot substitute an out-of-range glyph, they drop it. Per the user's explicit decision, fix this by vendoring a real embeddable TTF rather than depending on an OS-installed font (the runtime image, `eclipse-temurin:17-jre-alpine`, ships no fonts at all, and the CI/test environment that actually renders and asserts these PDFs — `ReportGenerationServiceTest`/`ReportGenerationServiceIT` — is a different OS than that Alpine image, so a system-font-path dependency would need installing in two unrelated places and silently drift).
   - Source a single-weight, Apache-2.0-licensed **Noto Sans Regular** TTF (Google; broad glyph coverage including Latin Extended-A, Cyrillic, Greek) and commit it to `src/main/resources/fonts/NotoSans-Regular.ttf`. (Obtaining the actual font file is implementation work for this story, not something decided in advance here — verify the exact license text that ships with whatever release is pulled, and keep the file to the single regular weight needed; do not vendor an entire variable-font family if a static instance is available and smaller.)
   - Replace the four `FontFactory.getFont(...)` calls with a single shared `BaseFont` loaded once via `BaseFont.createFont("fonts/NotoSans-Regular.ttf", BaseFont.IDENTITY_H, BaseFont.EMBEDDED)` (classpath-relative resource load — openpdf's `BaseFont.createFont` resolves a bare relative path against the classpath when no absolute/filesystem path is given; confirm the exact loading idiom this openpdf 2.0.5 version expects before writing the final code, since this differs across openpdf/iText major versions), then build the four `Font` objects (`headerFont`/`sectionFont`/`normalFont`/`tableHeaderFont`) from that one `BaseFont` at their existing sizes/weights (`new Font(baseFont, 18, Font.BOLD)` etc.) instead of from `FontFactory`. **Decide explicitly on the bold weight:** three of the four fonts (`headerFont`/`sectionFont`/`tableHeaderFont`) currently use `HELVETICA_BOLD`; building `Font.BOLD` over a single Regular-weight `BaseFont` makes openpdf emit a synthetic fill-stroke "faux bold" instead of selecting a true bold face — visible on every report header/section/table heading. Either vendor a second, Bold-weight TTF (e.g. `NotoSans-Bold.ttf`) and use it for those three, or accept the faux-bold rendering as a known tradeoff and say so — don't let this be an unexamined side effect of the font swap. `openpdf` 2.x keeps the `com.lowagie.text.*` package (the `org.openpdf.text.*` rename is 3.x-only, confirmed at `pom.xml:527-529`), so the `BaseFont`/`Font` imports stay `com.lowagie.text.pdf.BaseFont`/`com.lowagie.text.Font`, matching the file's existing imports.
   - **Do not bump the `openpdf` dependency version.** The project is pinned to `openpdf 2.0.5` on Java 17 (`pom.xml:525-532`, with an explicit comment on why — 2.1.0+ and all 3.x are Java-21 bytecode and will break this build). This fix is font-embedding code only, fully compatible with 2.0.5.
   - Extend `ReportGenerationServiceTest.java`, reusing its existing `extractPdfText` helper (`:298-310`, built on `PdfReader`/`PdfTextExtractor`, already proven working in this same test class) with a new case: generate a report whose recap text (or coach name) contains a character outside cp1252, and assert the extracted text contains the real character, not a dropped or mangled one. **Choose the proof character carefully:** `è`, `—`, `é`, and `à` are all cp1252/WinAnsi-encodable, so a string like `"Session went well — très bien ✓"` would pass against today's unfixed code and prove nothing. Use a character actually outside cp1252 — `✓` (already present and already invisible in every report via `ReportGenerationService.java:589-590`'s `" ✓ Verified"` note) or `Ł` (e.g. `"Łukasz"`) — and write the test so it **fails against the current, unfixed code first**, since this is also the only concrete proof in the repo that the base-14 glyph-dropping premise is real.

### i18n template-key resolution

6. **A new spec proves every `$t()`/`$te()`/`t()` call in every template and script resolves against a real key in the real `en-US` catalog**, closing the half of the `skillars-12-5` code-review finding that `skillars-deferred-155` AC14 explicitly scoped out ("template-key-resolution... left for a future story" — this is that story). `localeKeyParitySpec.js` (`src/frontend/src/i18n/__tests__/localeKeyParitySpec.js:18-29`) already has a `collectKeyPaths(obj, prefix)` helper that recursively walks a locale object into dot-path leaf keys — reuse it (it is **not currently exported** — export it from that file, or extract it to a small shared test util, implementer's call) rather than re-deriving the same recursion.
   **Mechanism correction:** the premise that keys stay silently green today is right, but not for the reason originally cited. The global `$t` mock (`setup-file.js:34-35`) only covers the ~218 call sites that use the explicit `$t(`/`$te(` form in `.vue` files; it is not even a pure echo (it special-cases `params.date`). What actually makes the *dominant* bare composition-API `t('…')` form (used in `<script setup>`, far more common than `$t(`) echo its key back is the **real** `createI18n` instance installed at `setup-file.js:18-27` with empty message catalogs and `missingWarn: false, fallbackWarn: false` — a genuinely missing key resolves through real i18n machinery to its own key string, not a mock. Separately, `$te` is **not stubbed at all** and always returns `false` under test, which is itself a second, currently-unflagged blind spot worth naming in the new spec's rationale (e.g. `PlayerTimelinePanel.vue:40` renders a raw enum name under test today because of it).
   New spec, e.g. `i18nTemplateKeyResolutionSpec.js`:
   - Statically walk every `.vue` file under `src/` **and every `.js` file that calls `i18n.global.t(` directly** (e.g. `development.store.js`, `utils/errorHandler.js` — a `.vue`-only glob misses these) using a glob (`fast-glob`, or Node's built-in `fs.readdirSync(dir, { recursive: true })` — already available given `engines.node: ^20+`; no new devDependency needed) and extract every `$t(...)`/`$te(...)`/`t(...)`/`i18n.global.t(...)` call's first argument **where it is a string literal**. A regex is a pragmatic first pass, but place the backtick correctly in the character class (` ['"`] `, not inside it in a way that also matches template-literal openers) — a sloppy class matches template-literal and string-concatenation call sites too and produces bogus, non-existent "keys" (e.g. dynamic enum interpolations), which is worse than missing real ones.
   - Any call whose key argument is **not** a string literal (a dynamic/interpolated key, e.g. `` $t(`coach.${status}Label`) `` or string concatenation) cannot be statically resolved — collect these into an explicit, named exception list in the spec file with a one-line comment per entry explaining why it's excluded, rather than silently skipping them with no record. **Survey first, don't assume this list is empty:** a real pass over this codebase found roughly 16 such non-literal-key call sites (split across `.vue` and `.js`), not zero — the exception-list mechanism is required, not an optional nicety to skip if the count happens to be low.
   - For every statically-resolved key, assert it exists as a real leaf in `en-US`'s catalog (via `collectKeyPaths`, or a direct nested-lookup against the imported `en-US` object). Extend to `de-DE`/`fr-FR` too if straightforward given `localeKeyParitySpec.js`'s existing key-SET parity already guarantees those two have the identical key set to `en-US` — so resolving against `en-US` alone is sufficient and not worth triplicating; just don't contradict that existing guarantee by also asserting per-locale resolution redundantly unless it's genuinely cheap to do.

   **Correction: there are three lock-taking statements, not four.** `findStorageKeysByCoachId` (`PerformanceReportRepository:40-41`, used to build the outbox enqueue) is a plain `SELECT` — no `FOR UPDATE`, cannot contend. The outbox `enqueue` itself is 0..N plain INSERTs with no unique index beyond the PK on `main.outbox_messages` (`V138:688`, `:3406`) — it cannot block either. **The outbox enqueue must stay bundled with the `performance_reports` scrub as one group, not split out as its own** — `BlobDeletionOutboxSupport:20-23,37-38` documents that `enqueue` "MUST be called inside the producing business transaction," because `anonymizeByCoachId` (`PerformanceReportRepository:64-66`) nulls `storage_key`, and `findStorageKeysByCoachId` (`:61`) only sees rows where `storage_key IS NOT NULL` — if the scrub commits in one transaction and the enqueue's separate transaction doesn't, the keys are gone from the only place that recorded them, and the retry handler finds nothing to delete, permanently orphaning the S3 blobs (the PLAYER branch's own Javadoc, `:1143-1149`, names this exact hazard as "a real Article 17 violation"). So the three groups are: (1) `session_completion_data` anonymize, (2) `player_timeline_events.metadata` anonymize, (3) `performance_reports` scrub + outbox enqueue together.
   The PLAYER branch's `deletePlayerDevelopmentDataInDedicatedPool` (`:1267-1381`) models the pattern to mirror: explicit statement groups, each with its own `nextGroupLockTimeoutSecondsOrThrow(remainingBudget, statementCount, lockTimeoutSeconds, playerId, groupLabel)` call before the group runs and `spendDownLockBudget(remainingBudget, groupStartedAt)` after it, tracked against a `cumulativeLockWaitBudget` field. **But read its Javadoc (`:1259-1265`) before assuming this shape gives durability**: it states outright that a bail-out there "rolls back the ENTIRE `requiresNewTemplate` transaction … including every earlier group's already-executed statements in THIS SAME call … there is no partial-commit risk to reason about" — i.e. that method's own groups share **one** transaction and get **zero** durability from the grouping; they get per-group timeout budgeting and per-group logging/labels only. Mirroring that shape for the coach branch literally, as the AC's own precedent, delivers the same thing: better observability (which of the three groups failed), not independent durability of earlier groups when a later one fails.
   **Decide and state explicitly which goal this AC is pursuing, since they are not both free:**
   - **(a) Observability-only (recommended default, matches the named precedent exactly):** keep all three groups inside the existing single `REQUIRES_NEW` transaction, add per-group `lock_timeout` labeling and a distinct reason-code pair per group. Cheap, matches the PLAYER branch precedent exactly, but a failure on group 2 or 3 still rolls back group 1's already-succeeded scrub — no durability gain, observability gain only (and only for whichever group fails *first*, since the dedup check at `:1014-1020` keys on `(referenceId, GDPR_ERASURE_DEADLINE, OPEN)` and returns early on any existing open alert for that reference — a second group's failure after a first group's alert is already open would be silently swallowed, not merely mislabeled).
   - **(b) Real durability:** split into genuinely separate `REQUIRES_NEW` transactions per group, so group 1/2's commits survive a group-3 failure. This is a bigger change than "mirror the PLAYER branch" (its own groups don't do this either) and needs its own sign-off that the resulting non-atomicity across groups is acceptable for a GDPR erasure path.
   Give each group its own pair of alert reason codes (contended/timeout) instead of the current two shared across all three. **`GdprErasureIT`'s existing coach-branch contention/timeout tests do not cover this scenario today** (`COACH_RECAP_CONTENDED`/`COACH_RECAP_LOCK_TIMEOUT` have zero references anywhere in `src/test`; the file's existing coach tests are happy-path only, and a comparable real-contention IT for the PLAYER branch was deliberately *not* written — see `GdprErasureIT:1989-1993`'s own documented rationale: "an unreasonably long test or exact-timing choreography across several simultaneous held locks"). Treat this as net-new test authoring scoped like that precedent (deterministic unit-level bail-out/reason-code assertions in `GdprErasureServiceTest`, not a real multi-lock-contention IT), not as "updating existing assertions."
   This is a **blast-radius/observability improvement**, scoped per the decision above — the correctness bug this originally protected against (a contended scrub reporting COMPLETED instead of FAILED) was already fixed by `skillars-deferred-155` code-review Decision 1(a), independently of this AC. Do not re-introduce or re-litigate that fix; this AC is additive on top of it.

## Dev Notes

### Why this story bundles several unrelated things

Per explicit user direction, this is a large, multi-item bundle rather than the narrower single-feature stories most of this epic family has used — `deferred-work.md` had accumulated enough independently-verified, real gaps (mostly surfaced by `skillars-deferred-155`'s own review cycle, which is itself exactly this kind of bundle) that a small story would leave more open than it closes. Items 1-3 (AC1-AC3) are tightly related — all three touch the same two `Booking` columns and the same `BookingService` methods — and should likely be implemented together even within this story, in that order, since AC2's helper is needed correctly before AC1's test fixtures would exercise genuinely-sanitized data. Items 4-7 (AC4-AC7) are independent of each other and of 1-3; implement in any order, but each is self-contained — don't let any one AC's scope creep into another's module.

### The metadata-key vs. entity-column trap does NOT apply here

`skillars-deferred-155`'s Dev Notes documented a specific trap in that story (filtering a query on `PlayerTimelineEvent`'s attendance-gated `coachId` *column* instead of the always-present metadata *key*, silently excluding unattended sessions). **This story's AC1 does not touch that trap at all** — `Booking.notes`/`playerRequest` are plain entity columns being erased by `playerId`, which is never null on a `Booking` row (every booking has exactly one player). Do not import caution from that story's trap into a context where it doesn't apply; there is no metadata-vs-column ambiguity anywhere in this story.

### `Booking.playerRequest` vs. `Booking.notes` — still two different things, now with parity of a different kind

`skillars-deferred-155` already documented why these two columns must not be conflated functionally (write-once-at-creation vs. editable-while-confirmed; different coach-facing surfaces). This story adds **sanitization and erasure parity** between them without touching that functional distinction at all — both AC1 and AC2 apply the identical treatment to both columns precisely *because* they're adjacent, same-shape, same-author, same-audience free text, not because they're becoming the same field. Keep them as two separate columns, two separate setters, two separate call sites — just route both call sites' writes through the one new shared helper (AC2) and both columns through the one new erasure method (AC1).

### Font licensing and the runtime/test-environment split

The decision to vendor rather than install-via-package was made specifically because `ReportGenerationServiceTest`/`ReportGenerationServiceIT` run on whatever OS executes `mvn test`/`mvn verify` (a CI runner or a developer's machine), which is never the same OS as the `eclipse-temurin:17-jre-alpine` production runtime image (`Dockerfile:50`). A system-font-path dependency would require installing the same font package in two unrelated places (the Dockerfile's runtime stage, and separately in whatever CI image runs the test suite) with no mechanism keeping them in sync if either one's available fonts change. A classpath-embedded TTF has no OS dependency at all and behaves identically everywhere `mvn` or the packaged jar runs. Do not revisit this decision as part of implementation without re-raising it — it was a deliberate, already-made call.

### Test architecture recap

Backend: JUnit 5 + Testcontainers for `*IT` classes, Mockito for plain unit tests. `GdprErasureIT` already covers the per-table anonymize pattern this story's AC1/AC7 extend — read its existing coach- and player-branch test cases before adding new ones, to match its existing fixture-setup idioms rather than inventing new ones. `ReportGenerationServiceTest` (unit, Mockito) already has the `extractPdfText` helper AC4's test needs; `ReportGenerationServiceIT` (`extends BaseStorageIT`) likely needs no change unless it has its own font-sensitive assertions. Frontend: Vitest + `@vue/test-utils`, run via `cd src/frontend && npm run test:unit`, not part of `mvn verify` (`docs/validation-strategy.md`) — per that document and this project's own standing guidance, do not run `mvn verify` locally for this story; targeted backend tests plus the frontend suite are the complete local gate.
