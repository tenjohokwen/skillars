# Story Ses-1.3: Health, Monitoring, Rate Limiting

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the platform's email transport owner,
I want an SES-specific health indicator wired into the `notification` health group, a non-blocking send-rate limiter guarding the SES API call, and transport-tagged send metrics,
so that an environment on `transport=ses` reports whether SES can actually send (sandboxed, suspended, or genuinely healthy) before it matters, a post-outage retry burst cannot trivially exceed the account's send-rate quota, and every email's outcome is observable per-transport in Prometheus.

This is **Phase 3 of 7** in `requirements/ses-email-consolidation.md`. It builds on Phase 1 (`ses-1.1`, done — the port, exception taxonomy, `SesEmailSender`/`SesConfig`/`SesProperties`/`SesErrorClassifier`, all already carrying the timeouts and validation Phase 3 relies on) and Phase 2 (`ses-1.2`, done — SMTP contained behind the port, `SmtpHealthIndicator` moved to `infrastructure/email/smtp`). Per the source doc: *"whichever transport an environment runs, its health is visible"* and *"the SES rate limiter never blocks inside `sendEmailSync`'s transaction."* This story adds monitoring and rate-limiting only — it does not change what any email says, add durability to registration/OTP mail (Phase 4), or touch the SES cutover (Phase 5).

**Already true, not part of this story — verify by reading, don't re-derive:**
- `SesConfig`'s `SesV2Client` bean already sets `apiCallTimeout = 5s` / `apiCallAttemptTimeout = 3s` (ses-1.1 AC6). `SesHealthIndicator` (AC1) reuses this **same bean** — its `getAccount` call is bounded by the same 5s ceiling with no extra wiring.
- `app.ses.max-send-rate-per-second` (default `10`, bound on `SesProperties`, validated positive by `SesPropertiesValidator`, WARN-logged at startup when `>= 10` as a sandbox-risk hint) already exists from ses-1.1 and is already wired end-to-end through every compose file's `APP_SES_MAX_SEND_RATE_PER_SECOND` env var (verified: `docker-compose.yml:99`). **Nothing about this property is new in this story** — `SesSendRateLimiter` (AC3) is the first consumer of a value that has existed, validated and documented, since Phase 1.
- `SesConfig`'s SDK-level retry stays at the SDK default (not `doNotRetry()`) until Phase 4, per ses-1.1's owner decision recorded in that file's Dev Notes — **do not touch this in Phase 3.**

## Acceptance Criteria

**AC1 — `SesHealthIndicator`: gated on `transport=ses`, TTL-cached, actually detects sandbox/suspension, not just "is the API reachable"**

- Given a new `SesHealthIndicator` in `infrastructure/ses`, `@Component`, `@ConditionalOnProperty(name = "app.email.transport", havingValue = "ses")`, extending `AbstractHealthIndicator` and constructor-injecting the existing `SesV2Client` bean
- Then `doHealthCheck` calls `sesV2Client.getAccount(r -> {})` (no request fields needed) and reports:
  - **UP** only when **all three** hold: `Boolean.TRUE.equals(response.sendingEnabled())`, `Boolean.TRUE.equals(response.productionAccessEnabled())`, and `!"SHUTDOWN".equals(response.enforcementStatus())`. **This three-part mapping is a deliberate, stated decision, not the obvious one** — `sendingEnabled()` alone is insufficient: a sandboxed account still reports `sendingEnabled=true` (sandbox restricts *recipients*, not the sending switch), so a literal "UP ⟺ sendingEnabled" mapping reports a sandboxed or production-access-revoked prod account as healthy, which is exactly the "before it matters" failure §6.8 exists to catch. `productionAccessEnabled()` is SES's actual sandbox signal; `enforcementStatus()` (`HEALTHY`/`PROBATION`/`SHUTDOWN`) is the actual suspension signal — both exist on the pinned SDK's `GetAccountResponse` (verified against `sesv2-2.54.13.jar`, the version this project's `dependency:tree` actually resolves — not `2.54.7`, a different cached jar that does not apply here). If the owner would rather not page on sandbox alone, that's a valid alternative (report UP-with-a-`sandboxed` detail instead of DOWN) — but it must be a stated choice in this file, not left to whichever mapping the dev agent finds first
  - **DOWN** on any of the three conditions failing, or when the call throws any `SdkException` (mirror `SesEmailSender`'s catch scope — client-side timeouts/DNS failures are just as much "can't send" as an explicit account block)
  - All accessors on `GetAccountResponse` (`sendingEnabled`, `productionAccessEnabled`, `enforcementStatus`) and on `response.sendQuota()` (`SendQuota.max24HourSend/maxSendRate/sentLast24Hours`) return **boxed, nullable types** (`Boolean`/`Double`, confirmed via `javap`) — a partial `GetAccount` response (a real shape, not hypothetical: `SesEmailEndToEndIT`'s WireMock stub is exactly where a hand-written partial body would appear) must not NPE. Use `Boolean.TRUE.equals(...)` everywhere above (never unboxing `if (response.sendingEnabled())` directly), and null-guard `sendQuota()` itself before reading its fields — a null `sendQuota` still yields a valid DOWN/UP `Health` with those three detail fields simply omitted, not a thrown `NullPointerException`
  - Details (when available, per the null-guarding above): `sendingEnabled`, `productionAccessEnabled`, `enforcementStatus`, `sendQuota.max24HourSend`, `sendQuota.maxSendRate`, `sendQuota.sentLast24Hours`; on the exception branch, `error` = the exception's message
- And the result is **TTL-cached** — mirror `SmtpHealthIndicator`'s `AtomicReference<Cached>` + double-checked-locking pattern **in structure** (do not name that class by its simple name anywhere in `SesHealthIndicator`'s own source, including javadoc — see the containment note below): a stale-but-fresh-enough cached `Health` is served without a second `GetAccount` call. **Deliberately simpler than the SMTP indicator's version**: no parallel-probe thread pool (there is exactly one account to check, not N providers) and no new `@ConfigurationProperties` class — hardcode the TTL as a `private static final Duration CACHE_TTL = Duration.ofSeconds(60)` constant (matching the SMTP indicator's own default). The source doc asks only for "TTL-cached," not for a new tunable; adding one here would be unrequested scope, not fidelity to the doc
- And this indicator's failure to reach AWS must never throw out of `doHealthCheck` — **not** because a throwing indicator would break the endpoint for other contributors (it wouldn't: `AbstractHealthIndicator.health()` already wraps `doHealthCheck` in its own `try/catch (Exception)` and degrades only that one contributor to DOWN — verified via `javap` on the pinned `spring-boot-actuator:3.5.16`), but because catching locally is what lets this AC control the exact detail shape above and keep a raw stack trace out of the health payload. Catch `SdkException` locally exactly as described above
- **Containment note**: `EmailTransportArchitectureTest` rule 2 scans **whole file content, including javadoc**, for the literal token `SmtpHealthIndicator` in any file outside `infrastructure/email/smtp/` (confirmed by reading that test — this is the same trap ses-1.2's own code review hit and fixed in `ComponentConfig`/`EmailTransportPropertyValidator`'s comments). Describe the mirrored pattern in `SesHealthIndicator`'s comments without repeating that class's simple name, or the containment test fails on this story's own new file

**AC3 — `SesSendRateLimiter`: non-blocking, ahead of the SDK call, rejection is Transient and distinctly observable — no resilience4j type leaks out**

- Given a new `SesSendRateLimiter` in `infrastructure/ses`, `@Component`, `@ConditionalOnProperty(name = "app.email.transport", havingValue = "ses")`, constructor-injecting `SesProperties` **and `MeterRegistry`** (needed for the rejection counter below — both are already unconditional beans in this context)
- Then it builds one `io.github.resilience4j.ratelimiter.RateLimiter` at construction from `RateLimiterConfig.custom().limitForPeriod(props.getMaxSendRatePerSecond()).limitRefreshPeriod(Duration.ofSeconds(1)).timeoutDuration(Duration.ZERO).build()` — **`timeoutDuration(Duration.ZERO)` is the entire point (§6.5): it makes every acquire attempt non-blocking**, never waiting inside the caller
- And exposes one method (e.g. `acquireOrThrow()`) that calls **`limiter.acquirePermission()`** (the interface's no-arg default method — returns `boolean`, throws nothing) — **do not use the `RateLimiter.waitForPermission(...)` static helper.** That helper additionally checks `Thread.currentThread().isInterrupted()` and throws `io.github.resilience4j.core.exception.AcquirePermissionCancelledException` — a **second**, distinct resilience4j type, unchecked, that is *not* `RequestNotPermitted` and would otherwise slip past a `catch (RequestNotPermitted)` here, past `SesEmailSender`'s `catch (SdkException)` (verified via `javap` on `resilience4j-ratelimiter:2.2.0` — confirmed present in the compiled bytecode), and past AC5's `catch (EmailTransportException)`, reaching `MailManager.isRetryable` unclassified — reachable in practice whenever `sendMailPool`'s executor is shutting down while an `@Async` send is in flight. Calling `acquirePermission()` directly sidesteps this: it has no interrupt-checking side path, so there is nothing to leak
- And when `acquirePermission()` returns `false`: (a) logs at WARN with the configured `limitForPeriod` rate, (b) increments a new, distinct Micrometer counter `mail.ses.rate_limiter.rejected` (no tags needed — this is SES-only by construction), and (c) throws the **new** `EmailTransportRateLimitedException` (AC4)
- And `SesEmailSender.send(...)` calls `rateLimiter.acquireOrThrow()` **after** `validateRecipient(...)` (a malformed address must not consume a permit for a send that was never going to succeed) and **before** the `sesV2Client.sendEmail(...)` call — resilience4j-ratelimiter is already a transitive compile-scope dependency of this project via `spring-cloud-starter-circuitbreaker-resilience4j` → `resilience4j-spring-boot3` → `resilience4j-ratelimiter:2.2.0` (verified via `dependency:tree`) — **no `pom.xml` change is needed or permitted**
- And `RateLimiterConfig.custom().limitForPeriod(n)` itself throws its own (unhelpfully generic) `IllegalArgumentException` for `n <= 0`. `SesPropertiesValidator` already owns the friendly, actionable `"app.ses.max-send-rate-per-second must be positive"` message for exactly this input, via its own `@PostConstruct`, but `@PostConstruct` ordering between two independent `@Component`s is not guaranteed — a misconfigured deployment could hit the generic resilience4j message first depending on bean-creation order. Avoid the race rather than depend on ordering: build the `RateLimiter` **lazily on first `acquireOrThrow()` call** (a simple memoized/`synchronized` initializer is sufficient — no need for a `Supplier`-based Spring bean laziness mechanism), so `SesPropertiesValidator`'s startup-time check has already run and failed fast before this class ever constructs a `RateLimiterConfig`
- [Source: requirements/ses-email-consolidation.md#5 Phase 3 item 1 (rate limiter half), #6.5, #6.17]

**AC4 — `EmailTransportRateLimitedException`: transport-neutral marker so `MailManager` can special-case it without importing anything SES-specific**

- Given `MailManager` (in `platform.notification`) must stay transport-agnostic — it is not allowed to import `infrastructure.ses` types (`EmailTransportArchitectureTest` rule 4 already enforces "no SES SDK or mail API reference under `platform/**`", and a bespoke SES exception type would be the same category of leak in spirit even though it isn't itself an SDK/mail-library type)
- Then create `EmailTransportRateLimitedException extends EmailTransportTransientException` in `infrastructure.email` (the existing transport-neutral package, alongside `EmailTransportPermanentException`/`EmailTransportTransientException` — note neither is `final`, so this subclass compiles cleanly) — a marker type any future rate-limited transport could reuse, not an SES-specific name
- And `ComponentConfig.retryTemplate()`'s bean is reconfigured **using the builder's own exception-routing methods, not a hand-built `SimpleRetryPolicy`**:
  ```java
  RetryTemplate.builder()
      .maxAttempts(3)
      .notRetryOn(EmailTransportRateLimitedException.class)
      .traversingCauses()
      .fixedBackoff(Duration.ofSeconds(1))
      .build();
  ```
  **Do not** call `.maxAttempts(3)` together with `.customPolicy(new SimpleRetryPolicy(...))` on the same builder — verified via `javap` on `RetryTemplateBuilder` (pinned `spring-retry:2.0.13`): both `maxAttempts(...)` and `customPolicy(...)` assert `baseRetryPolicy` is still `null` before setting it, so calling both throws `IllegalArgumentException: You have already selected another retry policy` **at context startup, in every environment** — this is not a style preference, it is the difference between a booting and a non-booting app. The builder-native form above avoids the conflict entirely: `.maxAttempts(3)` populates `baseRetryPolicy` (a `MaxAttemptsRetryPolicy`), while `.notRetryOn(...)`/`.traversingCauses()` populate a *separate* classifier that `build()` composes into a `CompositeRetryPolicy` alongside it (verified via `javap` on `RetryTemplateBuilder.build()`'s bytecode) — no conflicting field write. `.notRetryOn(X)` puts the classifier in blacklist mode, so `EmailTransportRateLimitedException` classifies `false` (not retryable) and **every other exception type still classifies `true`** (retryable, unchanged default) — exactly AC4's intended semantics, with less code than a hand-rolled `Map`
  - `.traversingCauses()` is required because `MailManager.sendEmailSync`'s `retryTemplate.execute(...)` catches whatever `mailService.sendEmailFromTemplate(...)` throws and **rewraps it** in a `new RuntimeException(...)` before rethrowing (see current code) — the classifier must walk that one level of wrapping to find the real `EmailTransportRateLimitedException` underneath
- And the effect: a rate-limited send fails `retryTemplate.execute` on its **first** attempt (no 1s-backoff retries burned against the transaction/circuit-breaker budget described in §6.17), propagates to the outer `circuitBreaker.run(...)` catch, and the envelope is persisted `FAILED, retry=true` — picked up by `EmailRetryScheduler`'s next tick rather than the in-request retry loop, per §6.5's explicit reasoning
- **Two consequences of this fix, recorded here as accepted trade-offs — not silently absorbed:**
  1. **Duplicate sends on re-drive for multi-recipient envelopes.** `sendEmailSync`'s `retryTemplate.execute(...)` runs **per recipient inside a loop** (`MailManager.java`); today a transient failure on recipient *N* of *M* still gets up to 3 in-loop attempts before the loop aborts. This AC makes a rate-limit rejection abort the loop on attempt 1 instead — recipients after the rejected one are never attempted this pass, the whole envelope goes `FAILED, retry=true`, and `EmailRetryScheduler` re-drives the **entire envelope** on its next tick (re-sending to recipients who already succeeded this pass). Sharper because the removed backoff (1s) equals the limiter's own `limitRefreshPeriod` (1s) — the retry this AC removes was, on average, the one most likely to have succeeded a moment later. §6.19 already documents this exact re-send-the-whole-envelope shape as a pre-existing, currently-unreachable trap (every producer today sends to exactly one recipient) — this AC does not create a new failure mode, but it does make the existing one measurably more likely to fire, and that should be visible to whoever signs off on this story, not discovered later.
  2. **Circuit-breaker exposure.** `circuitBreaker.run(...)` wraps the whole per-envelope loop, so a rate-limited rejection still counts as one failure against the shared `emailService` breaker (`slidingWindowSize=5, minimumNumberOfCalls=5, failureRateThreshold=50%, waitDurationInOpenState=5s`) even though this AC stops it from being *retried*. Five rate-limited envelopes in a row open the breaker for **all** outbound mail (any transport, any recipient) for 5 seconds, including sends that were comfortably under the SES rate quota. This is plausible, intentional-looking backpressure, but it is a real behaviour change this story introduces and should be named as such, not implied away by "avoids burning the retry budget."
  3. **A rate-limit rejection still consumes one of `EmailRetryScheduler`'s 6 scheduler attempts** (`MAX_RETRY_ATTEMPTS`), same as any other transient failure — the scheduler has no concept of "this failure wasn't SES's fault, don't count it." `EnvelopeEntityRepository` fetches up to 10 retryable envelopes per ~60s tick and dispatches them in a tight, unpaced loop; against the default `max-send-rate-per-second=10`, a burst of multi-recipient envelopes can burn through all 6 attempts on rate-limit rejections alone within a few ticks, reaching `ATTEMPTS_EXHAUSTED` (permanently dropped, `retry=false`) without a single genuine SES error. **This story does not fix that** — it is flagged here as an owner decision for a follow-up (e.g. a scheduler-side exemption for this exception type), not silently left for a future incident to discover
- [Source: requirements/ses-email-consolidation.md#6.5 ("Don't let the in-transaction RetryTemplate burn attempts on it"), #6.17, #6.19]

**AC5 — Transport-tagged `mail.send` outcome metric, alongside the existing `mail.send_from_template` observation**

- Given `MailService.sendEmailFromTemplate` already carries `@Observed(name = "mail.send_from_template")` (unchanged — this AC adds a second, distinct signal, it does not replace or duplicate that one)
- Then create `MailMetrics` in `platform/notification/service`, mirroring the `MeterRegistry`-backed pattern already established by `platform.video.service.VideoMetrics` / `infrastructure.blobstore.service.StorageMetrics` (constructor-injected `MeterRegistry`, a `Timer.builder(...).tag(...).register(...).record(...)` call per invocation — no new library, no new pattern)
- And `MailService` gains two constructor dependencies: `MailMetrics` and the existing (unconditional, already-`@Component`) `EmailTransportProperties` — read once, purely to label the metric with which transport is active; **this is not a behavioural branch** (`MailService` still calls the port polymorphically and never chooses a transport itself, preserving §3's "platform never imports transport SDKs" rule)
- **`EmailTransportProperties.getTransport()` can be `null`** — the field has no default (`private EmailTransport transport;`), and property-absent is a state this codebase deliberately keeps working: `LoggingEmailSender` carries `matchIfMissing = true` specifically so an absent/unresolvable `app.email.transport` still boots and sends via the safe logging transport (`TransportWiringTest.transportAbsent_fallsBackToTheSafeLoggingTransport` pins exactly this). Micrometer's `Tag`/`ImmutableTag` does `Objects.requireNonNull` on both key and value (verified via `javap`), so tagging with a raw `null` transport value throws an `NullPointerException` **on every single email send** in that state — the metrics addition must never be able to break sending itself. Resolve the tag as `props.getTransport() == null ? "log" : props.getTransport().name().toLowerCase(Locale.ROOT)` (the explicit `Locale.ROOT` avoids a Turkish-locale `toLowerCase()` trap on `"SES"`/`"LOG"` — cheap to get right while touching this line)
- And the whole method body from rendering onward is wrapped — not only the `outboundEmailSender.send(request)` call. `MailService.sendEmailFromTemplate` already has its own local `catch (IllegalArgumentException ex) { throw new EmailTransportPermanentException(...) }` around `OutboundEmailRequest` construction (added by ses-1.2's code review, for a malformed rendered payload) — if the metric wrapper covers only the `.send(...)` call, that malformed-payload failure path never records `outcome=failure`, leaving a real failure class invisible to "what happened to this email" the metric exists to answer. Use a `try { ... } catch (Throwable t) { record(outcome=failure); throw t; } ` (or an equivalent `finally` with an outcome variable) spanning both the construction and the send, not just the send — **and use `Throwable`, not `EmailTransportException`**, so an unexpected type (a bug, a `RejectedExecutionException` from the async executor, anything not yet in the taxonomy) still gets counted as a failure rather than silently under-counting `mail_send_seconds_count` relative to actual attempts. Either shape must still satisfy AC's core constraint: **rethrow the exact same exception instance, never wrap it** — `MailManager.isRetryable`'s cause-walk is bounded to exactly two levels deep (see that method's own comment) specifically because of past incidents where an extra wrapper silently pushed the real type out of range, and a version that wraps-and-rethrows here would break AC4's retry-policy classification and `isRetryable`'s depth assumption simultaneously

- `SesEmailSender`'s current field order is `sesV2Client, props, addressParser, errorClassifier` via `@RequiredArgsConstructor` — add `rateLimiter` as a new `final` field; Lombok regenerates the constructor, so no manual constructor edits are needed. **Three existing test call sites break as a result, not one** — `SesEmailSenderTest` (already noted), plus `SesAddressValidationTest.setUp()` (currently constructs `SesEmailSender` with 4 args — a compile error once the 5th is added) and `TransportWiringTest.transportSes_wiresSesEmailSenderAndSesV2Client` (currently wires `SesEmailSender` without `SesSendRateLimiter` in its `ApplicationContextRunner` config, and the file has no `MeterRegistry` bean anywhere — a runtime `NoSuchBeanDefinitionException`, not a compile error, so it will not surface until the test actually runs). Fix all three in this story, not just the one that fails loudest.
- `SesProperties`/`SesConfig`/`SesPropertiesValidator`/`SesErrorClassifier`/`EmailAddressParser` are all Phase 1 and stay exactly as they are — this story only *adds* two new classes in `infrastructure.ses` and *reads* `SesProperties.getMaxSendRatePerSecond()`.
- **`application.yaml`'s SMTP provider-config block is unconditional, and prod does not clear it.** `app.email.smtp.provider-configs[0/1].host` (`mail.gmx.net`/`smtp.gmail.com`) is set in the base `application.yaml`, applied under every profile; `application-prod.yaml` sets `app.email.transport: ses` but never overrides that list to empty. Property sources merge, not replace, across profiles — so today, with only the pre-existing provider-presence gate, `SmtpHealthIndicator` **is already an active bean in prod**, probing real SMTP endpoints from prod nodes every ~60s. AC2's fix is closing a live defect, and its test (AC6) must exercise that exact combination (`transport=ses` + provider host set), not a synthetic "what if" shape.
- **Two resilience4j-ratelimiter static-helper exception types exist, not one.** `RateLimiter.waitForPermission(RateLimiter, int)` throws both `RequestNotPermitted` (no permit available) and `io.github.resilience4j.core.exception.AcquirePermissionCancelledException` (calling thread was interrupted) — verified by disassembling the method. `SesSendRateLimiter` must not use this static helper at all; call `limiter.acquirePermission()` directly (returns `boolean`, throws neither type) per AC3.

Use the builder's `.notRetryOn(...)`/`.traversingCauses()` methods instead (AC4) — they populate a separate classifier that composes with `.maxAttempts(...)`'s policy via `CompositeRetryPolicy`, with no conflicting field write.
- **`AbstractHealthIndicator.health()` already catches `Exception` around `doHealthCheck(...)` and maps it to that one contributor's `DOWN`** (verified via `javap` on the pinned `spring-boot-actuator:3.5.16`) — a throwing indicator degrades only itself, not sibling indicators in the same group or the endpoint as a whole. `SesHealthIndicator` still catches `SdkException` locally (AC1), but for detail-shape control, not because an uncaught exception would be more broadly destructive.

**Deviation from AC1/AC2's literal bean-gating mechanism — proposed during implementation, then REVERSED by code review 2026-09-12 (owner decision D2):**

The boot failure found during implementation was **real**, and is now pinned by a test rather than prose.
`application.yaml`'s original profile-independent `management.endpoint.health.group.notification.include: smtp,ses`
cannot coexist with transport-gated indicator beans: Spring Boot's `HealthEndpointGroupMembershipValidator`
(a `SmartInitializingSingleton`) resolves every name in an `include` list against actually-registered
`HealthContributor` beans at context refresh and throws `NoSuchHealthContributorException` on a miss.
`TransportWiringTest.healthGroupInclude_mustNameOnlyIndicatorsTheActiveTransportRegisters` now asserts
exactly that, against the real `HealthEndpointAutoConfiguration`, in both directions.

**What the original write-up got wrong:** it concluded "there is no property in Spring Boot 3.5.16 to relax
this." There is. The validator's `@Bean` method carries
`@ConditionalOnBooleanProperty(name = "management.endpoint.health.validate-group-membership", matchIfMissing = true)`,
documented in the jar's own `spring-configuration-metadata.json`. A second option was also never evaluated:
declaring `include` **per profile**, since Spring replaces rather than merges collections across property
sources. Because the option set was wrong, the deviation was re-decided with the true options.

**What ships now (owner decision D2 — option 2, bean-gating + per-profile include):**

- `SesHealthIndicator` carries `@ConditionalOnProperty(name = "app.email.transport", havingValue = "ses")`
  exactly as AC1 specifies, with a direct `SesV2Client` constructor dependency — no `ObjectProvider`.
- `SmtpHealthIndicator` carries `@Conditional(SmtpHealthIndicator.ActivationCondition.class)`, a nested
  `AllNestedConditions` ANDing the provider-presence check with `transport=smtp`, exactly as AC2 specifies.
- Both in-`doHealthCheck` transport checks, the `EmailTransportProperties` dependencies they needed, and the
  back-compat constructor overloads that hid them from the unit tests are all gone.
- `management.endpoint.health.group.notification.include` is declared **per profile**: `ses` in
  `application-prod.yaml`, `smtp` in `application-dev.yaml`/`application-uat.yaml`, and absent from the base
  `application.yaml`, whose `transport=log` registers no indicator at all. Each list names exactly the
  indicator its own profile's transport implies.
- `validate-group-membership=false` was considered and rejected: it would also stop protecting the unrelated
  `smoke` group from a typo.

`TransportWiringTest` now asserts bean existence rather than reported status — existence is the mechanism the
group contract actually depends on — across all four shapes: `transport=ses` + SMTP provider set (only SES),
`transport=smtp` + provider set (only SMTP), `transport=log` (neither), plus the boot-shape case above.


Owner follow-up worth a line, per the Dev Notes' own pre-existing note: `transport=log` still leaves the `notification` health group reporting `UNKNOWN` for both members rather than an active UP/DOWN signal — informational, matches the Dev Notes' original assessment, and nothing in `docs/`/`deploy/`/`.github/`/`src/test` consumes that endpoint today.
