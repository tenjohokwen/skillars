# Story Deferred-16: Messaging Moderation Recovery, Identity Fail-Safety & Delete-Race Integrity

Status: done

## Story

As a platform operator and safety reviewer,
I want a message that never receives a moderation verdict to be recovered into a state a human can act on instead of hanging invisible forever, a late verdict to be unable to overwrite a decision already recorded against the row, every message held for review to actually reach the admin queue, the messaging module to survive an orphaned player profile instead of 404-ing a whole conversation list, and a concurrent double soft-delete to lose cleanly,
so that no message can be silently swallowed by a crashed moderation call, no admin approval can be reverted by a straggling Gemini response, no held message sits in a queue nobody can see, one bad `player_profiles` row cannot take out every conversation a coach or parent has, and the module's remaining check-then-act and counting defects stop being latent.

Every item was re-verified by direct read of the tree at commit `0d06925` during story creation — file and line references below come from those reads, not from trusting the ledger. ### Corrections to `deferred-work.md` this story must record

- **`skillars-8-4` W4 prescribes the wrong fix. Do not add `@Version` to `Message`.** The item says the race "requires `@Version` on `Message`". Optimistic locking on this entity would make **every** writer of the row contend: `ModerationResultApplier.applyResult`, `AdminMessageService.approveMessage`/`blockMessage`, AC2's sweeper and `softDeleteMessage` all `save()` the same row, and a version bump would convert the moderation pipeline's benign interleavings into `OptimisticLockingFailureException`s thrown from an SSE-emitting `AFTER_COMMIT` path with no retry. The codebase's established remedy for check-then-act on a single row is a **pessimistic locked read** (`findByIdForUpdate`, declared on five repositories across booking, payment, marketplace, reviews and video, and driven from ten call sites). AC5 uses that.
- **`skillars-8-1` D1 is no longer blocked, and the 2026-08-04 audit note on it is out of date.** The note reads "Story 8.2 has shipped; no `playerId→userId` mapping exists anywhere in `platform.messaging`". The mapping the item asked for is available in `platform.security.repo`.
- **What AC4 does and does not claim about reachability.** ROLE_PLAYER users now authenticate (`PlayerRegistrationResource`, `ShadowAccountService.createSelfOwnedPlayerProfile:83-105`) and every `/api/messaging` endpoint is `@PreAuthorize(IS_AUTHENTICATED)`, so such a caller reaches `getConversations` today and gets **404 `security.userNotFound`** rather than an empty list. ## Acceptance Criteria

1. **A moderation verdict may only be written while the message is still `PENDING` and still undeleted, and the read that decides it must be locked.** `ModerationResultApplier.applyResult` takes `messageRepository.findByIdForUpdate(messageId)` instead of `findById`, and writes the verdict **only** when `getModerationStatus() == PENDING` **and `getDeletedAt() == null`**; otherwise it logs at WARN naming the current status (and whether the row was deleted) alongside the discarded verdict, performs no write, publishes no SSE, and returns a `ModerationResult` carrying the **current** status (not the discarded one). Mirror `ReviewModerationService:92-124` — including its comment explaining why no `entityManager.refresh` is needed here: `applyResult` is `@Transactional` and `MessagingService.sendMessage` is `@Transactional(NOT_SUPPORTED)`, so the locked query is the **first** read of the row in a fresh transaction and returns live DB state. State that in a comment at the call site rather than leaving it inferable.

   **The `deletedAt` half is not defensive padding — it is reachable, and AC2 widens the window.** `softDeleteMessage` (`:270-275`) refuses deletion only for `UNDER_REVIEW` and `BLOCKED`, so a `PENDING` message **can** be deleted; and `toMessageDto` (`:403-405`) does not hide `PENDING` content, so the sender can see the message and its id from a second session while the original `sendMessage` request is still blocked on Gemini. Without this check the verdict lands on a deleted row, and via AC3 raises an admin alert carrying a content preview for a message the sender explicitly removed and that no other view will return; `AdminMessageService.approveMessage` would then emit a `NEW_MESSAGE` SSE pointing at content `findByConversationIdAndNotDeleted` filters out. See Dev Notes for why the alternative fix — blocking deletion of `PENDING` messages — was rejected.

   `findByIdForUpdate` is new on `MessageRepository`: copy the annotation stack from `CoachReviewRepository:23-25` (`@Lock(LockModeType.PESSIMISTIC_WRITE)` + explicit `@Query`). Enumerate the writers this guard exists to lose to, as `ReviewModerationService` does: `AdminMessageService.approveMessage`/`blockMessage`, AC2's sweeper, and a duplicate invocation of the same moderation call (which this makes idempotent for free).

   The `messageNotFound` branch (`:37-41`) keeps its current WARN-and-return-`PENDING` behaviour.

2. **A message stranded in `PENDING` is swept to `UNDER_REVIEW`, never to `APPROVED`.** A new `MessageModerationSweeper` in `com.softropic.skillars.platform.messaging.service` runs on `@Scheduled` + `@SchedulerLock` and, for each message whose `moderation_status = 'PENDING'`, whose `deleted_at IS NULL`, and whose `created_at` is older than a configurable grace period, transitions it to `UNDER_REVIEW` **in its own transaction per message**, under the same `findByIdForUpdate` + `PENDING`-and-undeleted guard as AC1 (a message that resolved *or was deleted* between the select and the sweep must be left alone). Grace comes from `platform.messaging.moderation_orphan_grace_minutes` via `configService.getBoundedLong(key, 30, 5, 1440)`, seeded by migration.

   The `deleted_at IS NULL` predicate belongs in the query as well as the guard, not only in the guard: without it a soft-deleted `PENDING` message is re-selected on every 10-minute run forever. A soft-deleted `PENDING` message is deliberately left exactly as it is — deletion already removes it from every user-facing and moderation-facing view (`findByConversationIdAndNotDeleted`, `findLastApproved`, `countUnread` all filter `deletedAt IS NULL`), so there is nothing left to recover and no new status is needed.

   **Fail-closed is not negotiable and must be stated in a class-level comment.** The sweeper does not re-call Gemini and does not approve: it does not know why the verdict never landed, and delivering unmoderated content to a minor is the failure this module exists to prevent. `UNDER_REVIEW` is the correct terminal state because it is exactly what `applyResult` already writes for an `UNCERTAIN` verdict (`:55-58`) and the only status `AdminMessageService.approveMessage`/`blockMessage` (`:97,:141`) will act on — so a swept message lands in the one state a human can resolve.

   Each swept message emits the AC3 event, increments a counter, and logs at **INFO** with `messageId`, `conversationId`, `senderId` and `createdAt`. Structure the run exactly like `SessionPackForfeitureScheduler.forfeitExpiredPacks` (`:32-61`) / `PaymentPendingSweeper.sweepStrandedPayments`: select outside, per-message `TransactionTemplate.execute` wrapped in `try/catch (Exception e) { log.error(...) }`, so one failure cannot abort the sweep. Do **not** annotate the scheduled method `@Transactional`.

3. **Every message held for review reaches the admin queue.** A new messaging event `MessageHeldForReviewEvent(Long messageId, Long conversationId, String reason)` is published by `ModerationResultApplier.applyResult` whenever the status it writes is `UNDER_REVIEW`, and by AC2's sweeper for each swept message. `AdminAlertEventListener` gains an `@EventListener @Transactional` handler that raises an alert of a new type `AdminAlertType.MODERATION_UNRESOLVED` with `AdminAlertReferenceType.MESSAGE`, reusing `insertAlert`'s existing OPEN-duplicate suppression verbatim.

   Because both publishers sit inside AC1's and AC2's guarded branches, a message that is already resolved or already soft-deleted raises no alert — that placement is the requirement, not an accident of where the line happens to go. Do not publish the event beside the guard.

   Direction matters: **messaging publishes, admin listens.** `platform.admin` already imports `platform.messaging.contract` (`AdminAlertEventListener:9-10`); messaging must not gain an import of `platform.admin`. The existing `ModerationFailureEvent` stays as-is and keeps its logging role — it fires only on a Gemini *exception*, so it cannot cover the `UNCERTAIN`-verdict or swept cases, which is why a new event is needed rather than a listener on the old one.

   Supporting changes: `admin.admin_alerts`'s `type` CHECK constraint (`V70:5`) must be widened by migration or every insert fails; `AdminQueueService.buildSummary` gains a `MODERATION_UNRESOLVED` case yielding a truncated content preview (reuse the `MESSAGE_REPORT` branch's shape at `:63-75`); `AdminQueueSummaryDto` gains a `moderationHolds` field and `getSummary` (`:121-127`) populates it. `AdminQueueSummaryDto` has **no frontend consumer** (verified — there is no admin moderation page in `src/frontend`), so adding the field is backend-only.

   When an admin approves or blocks such a message, the alert-resolution block in each of `AdminMessageService.approveMessage` and `blockMessage` must resolve the `MODERATION_UNRESOLVED` alert too — today it looks up `MESSAGE_REPORT` only, so a swept message would leave a permanently OPEN alert after being resolved.

4. **An orphaned player profile degrades one conversation, never a whole list — and the PLAYER branch resolves identity through the mapping that now exists.**

   **Fail-safe on read paths.** `AgePolicyService` gains `Optional<MessagingPolicy> findMessagingPolicy(Long playerId)` returning empty when the profile row is absent; `getMessagingPolicy` keeps throwing and stays the variant used on **write** paths, where fail-closed is correct (`MessagingService.initiateConversation:71`, `sendMessage:142`). The **read** paths switch to the `Optional` variant and degrade locally: `getConversations`'s PARENT filter (`:104`) **excludes** the affected conversation and logs at ERROR with the `playerId` and `conversationId`; `getConversations`'s PLAYER branch (`:109`) treats an empty result the same way it treats a missing profile — **empty list**, ERROR logged, no throw; `resolveOtherPartyName` (`:345`, `:353`) falls back to the existing `"Unknown Player"` label; `ModerationResultApplier.resolveRecipient` (`:101`) returns null (which its caller already handles, `:72`) rather than rolling back a committed moderation decision; `AdminMessageService.resolveRecipient` (`:197`) does the same. The oversight endpoints (`getConversationsForPlayer:211`, `getMessagesForPlayerConversation:237`) keep the throwing variant — the parent named a specific player, so a missing profile there is a genuine 404.

   That is **six** read-path sites and **four** write/oversight sites, accounting for all ten call sites; Task 6 requires each to be listed with its disposition, so do not treat this split as approximate.

   **PLAYER identity.** `MessagingService` resolves the caller's profile once via `playerProfileRepository.findByUserId(callerUserId)` and uses `profile.getId()` for both the policy lookup and `findActiveByPlayerId` (`:107-113`), and `verifyIsParty`'s PLAYER arm (`:303`) compares `profile.getId()` with `conv.getPlayerId()`. A caller with no player profile gets an **empty list** from `getConversations` (not 404) and `NOT_A_PARTY` from `verifyIsParty` — the same 403 they get today, by an honest route. Note `:109` is the line carrying the reported bug (it passes `callerUserId` into a player-profile-id parameter), so it changes twice: the argument becomes `profile.getId()` **and** the variant becomes `findMessagingPolicy`.

   **The same two defects exist a second time, in `MessagingReportService`, and must be fixed there too.** `MessagingReportService.verifyIsParty` (`:127-141`) is a copy of `MessagingService.verifyIsParty` carrying a comment that says so ("Duplicates `MessagingService.verifyIsParty()` — injecting `MessagingService` would create a circular dep"), with the identical silent `default -> Objects.equals(conv.getPlayerId(), callerUserId)` arm. It gates `reportMessage` and `reportConversation`, both `@PreAuthorize(IS_AUTHENTICATED)`. Apply the same two changes: resolve the profile via `findByUserId` and throw on an unknown role. `MessagingReportService` does **not** currently inject `PlayerProfileRepository` — add it to the constructor (`@RequiredArgsConstructor` field). **Do not "fix" the duplication** by injecting `MessagingService` or extracting a shared bean: the circular dependency the comment names is real, and a refactor of the module's collaboration graph is not this story's job. Fixing one copy and leaving the other is the outcome to avoid.

   **No silent default role.** `MessagingResource.resolveRole` (`:224-232`) returns `"PLAYER"` only when the caller actually holds `ROLE_PLAYER`; a caller with none of `ROLE_COACH`/`ROLE_PARENT`/`ROLE_PLAYER` is rejected with `OperationNotAllowedException(..., MessagingErrorCode.NOT_A_PARTY)` instead of being treated as a player. `MessagingService`'s three role `switch`es (`verifyIsParty:297-304`, `resolveLastReadAt:386-390`, `updateLastRead:395-399`) and `MessagingReportService.verifyIsParty` (`:129-135`) replace their `default` arm with an explicit `case "PLAYER"` plus a `default -> throw new IllegalArgumentException("Unknown messaging role: " + role)`. Delete the unused single-argument `resolveRole(Authentication)` overload at `:220-222` if it has no call sites; check before deleting.

5. **A concurrent double soft-delete loses cleanly.** `softDeleteMessage` (`:259-282`) loads the message through `messageRepository.findByIdForUpdate` (added by AC1) so the `deletedAt != null` check at `:276` runs under the row lock, and the second caller gets **409 `messaging.alreadyDeleted`** rather than a silent 204. Ordering: take the locked read first and keep every existing guard (conversation membership, sender ownership, `UNDER_REVIEW`/`BLOCKED` moderation hold) in its current order after it. **Do not add `@Version` to `Message`** — see "Corrections" for why.

6. **Four grouped correctness fixes, each with its own test.**
   - **(a)** `MessagingService:124`'s length guard counts Unicode code points (`content.codePointCount(0, content.length())`), so a 2000-code-point message of astral characters is accepted and a 2001-code-point one is not.
   - **(b)** `sendMessage` captures `Instant.now()` **once** (`:172`, `:174`) and uses the same value for `message.createdAt` and `conv.lastMessageAt`, so the two agree **for that send**. Claim no more than that: no consumer anywhere reads `lastMessageAt` as a cursor (see Dev Notes), and the fix does not make `createdAt <= lastMessageAt` a system invariant, because concurrent sends to one conversation can still commit out of order.
   - **(c)** `MessageRepository.findBeforePivot`/`findAfterPivot` (`:32-37`) break the `createdAt` tie on `id`: `(m.createdAt < :pivot OR (m.createdAt = :pivot AND m.id < :pivotId))` for before, the mirrored `>` form for after, with `ORDER BY m.createdAt DESC, m.id DESC` / `ASC, ASC`. Both callers (`AdminMessageService:58,63`) pass `msg.getId()` as the new parameter. The pivot message itself must still be excluded from both windows.
   - **(d)** The migration drops `idx_message_reports_message_id` and `idx_conversation_reports_conversation_id` (`V66:27-28`), both redundant against the leading column of `uq_message_reports_message_reporter` and `uq_conversation_reports_conv_reporter`. Use `DROP INDEX IF EXISTS` — `skillars-11-3` D1 asked for that convention on destructive DDL and this is the first migration since to have the chance.

## Dev Notes

### AC1/AC2 — the two halves of one dead end, and why they ship together

`MessagingService.sendMessage` is deliberately `@Transactional(NOT_SUPPORTED)` (`:122`). It commits the message as `PENDING` in a short `TransactionTemplate` (`:156-178`) precisely so `ModerationResultApplier` can see it, then calls `moderationService.moderate(...)` (`:181`) synchronously in the request thread, then re-reads the row (`:182`) to build the response.

Two things can go wrong in the window between the PENDING commit and the verdict write:

1. **The verdict never lands.** `GeminiModerationService.moderate` catches `Exception` around the Gemini call (`:64-67`) and degrades to `UNCERTAIN`, so a Gemini outage is handled. What is not handled is `applyResult` itself throwing — a DB error, a connection-pool timeout — or the JVM dying. There is no retry, no outbox, and nothing reads `PENDING`. The message rests there permanently. Worse, it is asymmetrically visible: `toMessageDto` (`:403-405`) hides content only for `BLOCKED`/`UNDER_REVIEW`, so the **sender sees their message as sent**, while `findLastApproved` and `countUnread` filter on `APPROVED` so the **recipient never sees it at all**.

2. **The verdict lands too late.** The Gemini call takes seconds outside any transaction. An admin can approve or block the message in that window (`AdminMessageService:92,:136` — though only from `UNDER_REVIEW` today, which AC2 makes newly reachable for these messages), and `applyResult`'s unconditional write reverts it. This is the identical shape `deferred-13` found in the reviews module and `deferred-14` closed: `ReviewModerationService:104-124` is the fix, comment for comment.

Ship them together. AC2 without AC1 creates the second problem where it did not exist before: the sweeper writes `UNDER_REVIEW`, a straggling `applyResult` writes `APPROVED` over it, and a message no human ever saw is delivered. AC1 without AC2 leaves the dead end intact.

### AC1/AC2 — why both guards check `deletedAt`, and why the alternative was rejected

A `PENDING` message can be soft-deleted. `softDeleteMessage` refuses only `UNDER_REVIEW` and `BLOCKED` (`:270-275`), and `toMessageDto` (`:403-405`) does not hide `PENDING` content — so the sender sees the message, and its id, from any other session while the original `sendMessage` request is still blocked on the synchronous Gemini call. AC2 then widens that window from "the length of one Gemini call" to "the 30-minute grace period", because a stranded message sits visible-to-sender for exactly that long before the sweeper touches it.

Left unguarded, three things follow from writing a verdict onto a deleted row: the sweeper re-selects it on every 10-minute run forever; AC3 raises an admin alert carrying a **content preview** for a message the sender explicitly removed and which no other query returns; and `AdminMessageService.approveMessage` will happily approve it and emit a `NEW_MESSAGE` SSE for content the recipient's `findByConversationIdAndNotDeleted` filters out.

**The alternative — blocking deletion of `PENDING` messages, alongside `UNDER_REVIEW` and `BLOCKED` — was considered and rejected.** It is the wrong trade in both directions: before AC2 it denies a sender the ability to unsend during a slow Gemini call, and after AC2 it denies it for up to 30 minutes on exactly the messages the platform has failed to moderate. Skipping deleted rows costs one predicate in two places and leaves the sender in control.

A soft-deleted `PENDING` message is therefore left exactly as it is, permanently. That is not an oversight to tidy up later: deletion already removes it from every user-facing and moderation-facing read (`findByConversationIdAndNotDeleted`, `findLastApproved`, `countUnread` all filter `deletedAt IS NULL`), so there is nothing to recover and no new status to invent. Only `findAllForAdmin` still returns it, which is the deliberate asymmetry `skillars-10-1` patches D2 tracks.

### AC2 — why `UNDER_REVIEW` and not a retry

Three options were considered and two rejected:

- **Re-call Gemini.** Rejected. The sweeper does not know why the first verdict never landed — if it was `applyResult` failing, a second Gemini call is wasted spend; if it was the Gemini call itself hanging past a timeout, a retry re-runs the exact failure. And a `SAFE` result from a retry would deliver content that failed the pipeline once, to a recipient who may be a minor, with no human in the loop.
- **`BLOCKED`.** Rejected. It is terminal-looking to the sender (`toMessageDto` hides the content) and, unlike `UNDER_REVIEW`, `AdminMessageService.approveMessage:97` will not act on it — an admin could not undo a wrong sweep.
- **`UNDER_REVIEW`.** Correct. It is what `applyResult` already writes for `UNCERTAIN` (`:55-58`), it hides the content, and it is the one status the admin actions accept. Combined with AC3 the message becomes a queue item a human resolves.

### AC3 — why a new event rather than a listener on `ModerationFailureEvent`

`ModerationFailureEvent` is published only inside `GeminiModerationService`'s `failureReason != null` branch (`:71-77`) — that is, only when the Gemini call **threw**. It does not fire when Gemini returns a well-formed `UNCERTAIN` verdict, and obviously not for AC2's swept messages. Attaching the admin alert to it would cover roughly one of the three ways a message reaches `UNDER_REVIEW`.

Publishing from `ModerationResultApplier` on the `UNDER_REVIEW` branch covers `UNCERTAIN` and Gemini-failure alike (both funnel through the same `default ->` arm at `:55-58`), and the sweeper publishes the third case explicitly. Keep `ModerationFailureEvent` — it carries the failure *reason*, which the new event does not need to duplicate, and removing a published contract type is a separate decision (AC7 records it as a new ledger item rather than deciding it here).

Module direction is not negotiable: `platform.admin` already imports `platform.messaging.contract` (`AdminAlertEventListener:9-10`), and project-context's dependency rules plus "prefer Domain Events for cross-module communication" put the listener on the admin side. Messaging must not gain an import of `platform.admin`.

### AC4 — the read/write asymmetry, stated once

`getMessagingPolicy` throwing is **correct** on write paths. `initiateConversation:71` and `sendMessage:142` are deciding whether a message may exist at all; if the age tier cannot be determined, refusing is the safe answer and the 404 is honest — the caller named a player that has no profile.

It is **wrong** on read paths. `getConversations:102-105` is assembling a list; one unresolvable row should cost that row, not the list. `resolveOtherPartyName:345,353` is choosing a display label and already has an `"Unknown Player"` fallback three lines away for the sibling lookup. `ModerationResultApplier.resolveRecipient:101` is choosing an SSE recipient inside a transaction that has already decided a moderation verdict — throwing there rolls back the verdict and strands the message in `PENDING`, which is the exact failure AC2 exists to clean up. `AdminMessageService.resolveRecipient:197` is the same shape.

The 2026-08-05 audit downgraded `8-2` D1/D2 on reachability grounds: no path in `src/main` deletes a `player_profiles` row (`GdprErasureService` anonymises the `User` and leaves the profile; `UserAdminService.deleteUserInTransaction` deletes only never-activated `User` rows). That downgrade stands — this is hardening against a data-integrity failure, not a live user-facing crash. It is included because the fix is small, because AC4 is already editing every one of those call sites for the PLAYER-identity half, and because the blast radius (an entire conversation list) is disproportionate to the cause.

### AC4 — the duplicate in `MessagingReportService`

`MessagingReportService.verifyIsParty` (`:127-141`) is a hand-copy of `MessagingService.verifyIsParty`, carrying a comment that admits it: "Duplicates `MessagingService.verifyIsParty()` — injecting `MessagingService` would create a circular dep." Both defects AC4 fixes are present in the copy, character for character: the silent `default -> Objects.equals(conv.getPlayerId(), callerUserId)` arm comparing a user id to a player-profile id, and no rejection of an unrecognised role. It gates `reportMessage` and `reportConversation`, both `@PreAuthorize(IS_AUTHENTICATED)` — the abuse-reporting path, which is exactly where a wrong party check matters most.

The reachability argument is the same one AC4 already accepts for the orphaned-profile half, so the same conclusion applies: the fix is two lines, the blast radius is an authorization check, and fixing one copy while leaving its acknowledged twin untouched would leave the module in a worse state than either fixing both or fixing neither — a later reader comparing the two would have no way to tell which is correct.

The circular dependency is real and is not this story's problem to solve. `MessagingReportService` needs `PlayerProfileRepository` injected (it has `CoachProfileRepository` but not the player one) and nothing else. Keep both copies, keep the comment, and extend it to record that they are deliberately kept in sync.

### AC4 — what `V84` changed, and the boundary this story does not cross

`V84__player_self_registration.sql` dropped `player_profiles.parent_id`'s NOT NULL, added `user_id` with a `chk_pp_owner` CHECK (exactly one of the two set), seeded `ROLE_PLAYER` as authority 102, and added a partial unique index on `user_id`. `ShadowAccountService.createSelfOwnedPlayerProfile:83-105` creates such profiles; `PlayerRegistrationResource` exposes the flow.

That makes ROLE_PLAYER callers real, and every `/api/messaging` endpoint is `IS_AUTHENTICATED`, so they reach `getConversations` — where `getMessagingPolicy(callerUserId)` (`:109`) passes a **user id** to a parameter that wants a **player-profile id**, and 404s. AC4 fixes that.

**What AC4 does not do.** A self-registered player still cannot obtain a conversation: `initiateConversation` requires a `CONFIRMED`/`UPCOMING`/`IN_PROGRESS`/`COMPLETED` booking (`:60-65`) and every booking-creation endpoint is `HAS_PARENT_ROLE`. Also note that a *self-owned* player profile has `parentId == null`, while `Conversation.parentId` is `nullable = false` (`Conversation.java:29-30`, `V65`) — so if player self-booking is ever added, `ConversationCreationHelper.tryCreate` will fail with a NOT NULL violation surfacing as the rethrown `DataIntegrityViolationException` at `MessagingService:85`. **Do not fix that here.** Making `conversations.parent_id` nullable changes the meaning of the column for every consumer (`verifyIsParty:302`, `resolveRecipient:105`, the oversight endpoints) and belongs with the product decision about adult-player messaging. Record it in the AC7 audit block as a known consequence rather than pre-emptively widening the schema.

### AC5 — why not `@Version`

`skillars-8-4` W4 says the race "requires `@Version` on `Message`". It does not, and adding one would be actively harmful. Four code paths write this row: `ModerationResultApplier.applyResult:63`, `AdminMessageService.approveMessage:101` and `blockMessage:144`, AC2's sweeper, and `softDeleteMessage:281`. Optimistic locking makes every interleaving between them throw `OptimisticLockingFailureException` — including from `applyResult`, which runs in the request thread with `TransactionSynchronization` callbacks registered for SSE emission and has no retry. The moderation pipeline would start failing sends for a race that AC1's status guard already resolves correctly and silently.

A pessimistic locked read is what this codebase uses for check-then-act on one row: `findByIdForUpdate` is declared on five repositories (`CoachProfileRepository:31-34`, `CoachReviewRepository:23-25`, `SessionPackPurchaseRepository`, `BookingRescheduleRequestRepository`, `VideoQuotaRepository`) and driven from ten call sites. AC1 adds it to `MessageRepository` anyway; AC5 costs one line by reusing it.

### AC6b — what the two `Instant.now()` calls actually cost

`skillars-8-1` D5 warns that "any consumer using `lastMessageAt` as a cursor may miss the just-sent message". Story creation looked for that consumer and there is none. `countUnread`'s `:since` parameter comes from `resolveLastReadAt` — the per-role `coachLastReadAt`/`parentLastReadAt`/`playerLastReadAt` columns, stamped by `updateLastRead` on `GET /messages` — never from `conv.lastMessageAt`. Grepping backend and frontend, `lastMessageAt` is read in exactly three places: the two conversation-list sorts (`:117`, `:222`) and a relative-time label (`MessagingPage.vue:30`).

So the fix is plain correctness — two timestamps that describe one event should be one timestamp — and not a hidden-message bug. Say that in the commit message rather than repeating the item's framing.

Note also what the fix does **not** buy: `createdAt <= lastMessageAt` is guaranteed for a single send, not as a system invariant. `sendMessage`'s conversation update is an unlocked `findById`/`save` (`:157`, `:174-175`), so two concurrent sends to one conversation can commit out of order and leave `lastMessageAt` behind the true latest `createdAt`. Today that is a list-sort glitch and nothing more, precisely because nothing reads it as a cursor. **Do not fix it here** — locking the conversation row on every send to correct a sort order would be a poor trade, and it would collide with the send path's deliberate `NOT_SUPPORTED` transaction shape.

### AC6c — the tiebreaker, precisely

`findBeforePivot`/`findAfterPivot` currently read:

```
WHERE m.conversationId = :convId AND m.createdAt < :pivot AND m.deletedAt IS NULL ORDER BY m.createdAt DESC
```

A message written in the same millisecond as the pivot satisfies neither `<` nor `>` and vanishes from both halves of the admin's context window with no indication. `Message.id` is a TSID (`BaseEntity:26-28`), which is time-ordered, so it is a correct secondary key — but do **not** replace `createdAt` with `id` entirely: TSID monotonicity is per-node and `created_at` is what the column semantics and the existing index (`idx_messages_created_at`, `V65`) are built on. Compound predicate plus compound `ORDER BY`, both directions mirrored, pivot still excluded because the tie branch is strict on `id`.

### Testing standards

- Integration tests are `*IT.java`, Testcontainers-backed, seeded with raw `jdbcTemplate` inside `transactionTemplate.execute` and torn down in `@AfterEach`. FK-constrained seeding needs fixed ids, which is why Instancio is not used in ITs (see `skillars-5-6` AD4). Messaging ITs are standalone `@SpringBootTest` classes annotated `@Sql(SecurityIT.SEC_DATA_SQL_PATH)` — there is no messaging IT base class, so shared helpers get copied per class.
- Unit tests use `@ExtendWith(MockitoExtension.class)` with **strict** stubbing — an unused stub fails the build, which is what Task 2 has to repair in `ModerationResultApplierTest`.
- Concurrency ITs use `CyclicBarrier`/`CountDownLatch` + an executor; `BookingServiceConcurrencyIT` is the reference implementation.
- **Mutation-verify every concurrency-sensitive test, in both directions, and record the result.** `deferred-13` found both of its barrier-based ITs passing unchanged against unfixed code, and even "hold `SELECT FOR UPDATE`, assert timeout" passed the mutation — waiting is not the discriminator. Assert on **what the caller observes after unblocking** and on final stored state.
- Scheduler unit tests construct the bean by hand rather than `@InjectMocks` (`BookingExpirySchedulerTest:44-50`); `@InjectMocks` does not run `@PostConstruct`, a trap `deferred-14` hit.
- Use **Awaitility** for asynchronous assertions; `Thread.sleep` in tests is an accepted-but-discouraged legacy pattern (`skillars-5-1` D4).

### Project Structure Notes

- `ModerationResultApplier` is a separate bean from `GeminiModerationService` specifically so its `@Transactional` boundary is a real proxy boundary — do not inline the guard into `GeminiModerationService`, whose `moderate()` runs outside any transaction by design.
- `MessagingService`'s `NOT_SUPPORTED` propagation is load-bearing: it is what lets the PENDING row commit before the Gemini call. Nothing in this story may add `@Transactional` to `sendMessage`.
- Config keys are seeded by Flyway into `main.platform_config` with `ON CONFLICT (key) DO NOTHING` and explicit ids. Highest id in use is **601** (`V90`); `platform.message_retention_months` (the module's only other key, read at `MessageRetentionScheduler:27`) is seeded elsewhere — check before assuming an id.
- ShedLock is wired platform-wide (`V80__shedlock_table.sql`, `ShedLockConfigIT`); a new scheduler needs only `@SchedulerLock` with a unique `name`.
- `admin.admin_alerts` constrains `type`, `reference_type` and `status` with inline `CHECK (x IN (...))` lists (`V70:3-12`). Any new enum value on either side needs a migration; the entity's `@Enumerated(EnumType.STRING)` will happily write a value the CHECK rejects at INSERT time.
