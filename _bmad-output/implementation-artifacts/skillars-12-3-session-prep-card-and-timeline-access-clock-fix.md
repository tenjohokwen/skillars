# Story 12.3: Session Prep Card and Coach Timeline Access Clock Fix

Status: done

## Story

As a coach,
I want to open an upcoming booking and immediately see what we worked on last time, what's next, what we've been focusing on, and any neglected skills,
so that I walk into every session already knowing the plan — without hunting through a separate roster or history screen, and without my own history being invisible to me just because I use Quick Complete.

## Acceptance Criteria

1. **Coach-access clock reads a faithful "last completed, attended session with this coach" signal, not the SLU-only proxy.** `development.player_timeline_events` gains a new nullable `coach_id uuid` column (additive migration, no new table). `TimelineEventListener` populates it going forward **only for an attended `SESSION_COMPLETED` event** (`event.isPlayerAttended() == true`) — mirroring `SluCalculationService.onBookingCompleted`'s own `!event.isPlayerAttended()` early return exactly, so a non-attended wrap-up never earns coach timeline access any more than it earns an SLU row today (see Dev Notes "Why the new signal must be attendance-gated" — this was a real gap in this story's first draft, caught by pre-implementation review as H3). `TimelineQueryService.getTimeline`'s `isCoach` branch computes the clock's "last activity" from the **later of**: (a) the existing `SluRepository.findLastSessionDate(playerId, coachId)` signal, and (b) the new coach-scoped lookup of the most recent *attended* `SESSION_COMPLETED` `PlayerTimelineEvent` for that exact `(playerId, coachId)` pair (i.e. one whose `coach_id` column is actually populated). A coach whose only history with a player is one or more attended, Quick-Completed bookings (zero SLU rows, one-or-more timeline rows carrying that coach's own `coach_id`) must no longer read `accessExpired=true` — this is the AC the whole story exists to satisfy. A coach whose history is entirely session-builder-based (today's passing behavior) must see **no change** — existing `PlayerTimelineResourceIT` tests covering the SLU-only path stay green unmodified.
2. **The merge, not a replacement; and the backfill's one accepted gap.** This story does not remove or alter `SluRepository.findLastSessionDate` or its existing coach-scoped semantics — it is still one of the two inputs being merged. It also does not change the redaction rule from story 12-2 (`whatWeDid`/`whatsNext` still visible only to the authoring coach) — this AC is about *whether the clock lets the request through at all*, not about *what's visible once it does*. The one-time backfill (Task 1.1) sets `coach_id` for every pre-existing row whose `metadata` already carries a top-level `coachId` key — it cannot retroactively check attendance, because attendance was never recorded on the timeline event itself (only on `SessionCompletionData`/`BookingCompletedEvent`, neither of which the backfill can join against from inside a Flyway migration). This means a pre-existing non-attended `SESSION_COMPLETED` row could be backfilled with a real `coach_id` and incorrectly satisfy the clock — accepted for this story because the application has no production deployment yet (same reasoning story 12-2's D2 finding was dismissed on), so there is no real non-attended historical data to mis-backfill; this is a go-forward correctness guarantee (AC1), not a retroactive one. The write-forward obligation applies to the `SESSION_COMPLETED` writer specifically; this story does not investigate or guarantee a `coach_id` value for `RADAR_ASSESSMENT`/`PERFORMANCE_REPORT` events — confirmed by reading both writers that neither currently stores a `coachId` metadata key at all (`RADAR_ASSESSMENT` writes only `skillCodes`; `PERFORMANCE_REPORT` writes `coachName`, a display string, not an id) — so the backfill's event-type-agnostic `WHERE` clause is defensive only today, not presently load-bearing for either.
3. **New read-only endpoint, `GET /api/development/bookings/{bookingId}/prep`**, `ROLE_COACH`-gated, authorized by **booking ownership** (the booking's `coachId` must equal the calling coach's own `coachId`, resolved **in the resource**, never from a client-supplied coach id — mirroring `CoachRosterResource`'s exact layering, not resolved deeper inside the service). An unknown `bookingId` returns **404** (`ResourceNotFoundException`); a `bookingId` that exists but belongs to a different coach returns **403** (`OperationNotAllowedException`, the same exception `BookingCompletionService.verifyCoachOwnership` already throws for the identical mismatch) — both responses reveal only booking existence/ownership, never any player data (`SessionPrepResponse` carries no player name or any other player-identifying field beyond the already-known `playerId`). The response returns: the merged `lastSessionDate` from AC1/AC2 (nullable — null means this coach and this player have never completed an attended session together by any mechanism); `lastWhatWeDid`/`lastWhatsNext` (nullable strings) — populated **only when the timeline event that produced `lastSessionDate` is itself the source**, i.e. the coach-scoped `SESSION_COMPLETED` timeline lookup's `occurredAt` is not strictly before the SLU signal; if the SLU signal is strictly the later of the two (meaning a more recent session happened through the builder with no matching recap, or the matching timeline row's async write was silently lost — see Dev Notes "Why the recap fields can legitimately be null even when `lastSessionDate` is not"), both recap fields are null rather than showing a recap from an older, different session; `focusThreadSkillCodes` (a list, possibly empty, capped at `SessionFocusThreadCalculator.MAX_FOCUS_CODES = 3`, of development-focus codes this coach and player have worked on most, ranked by frequency across their last `SessionRepository`-queried `SESSION_WINDOW = 10` session-builder sessions together, ties broken by recency — see Task 3); and `openNeglectedSkillCount` (player-level, reused read-only exactly as story 12-1 does — see Dev Notes "Why this endpoint doesn't call `/neglected-skills` or `/slu/coach-contributions`").
4. **The endpoint is read-only and status-agnostic by design.** It does not restrict by booking status (no check that the booking is specifically `UPCOMING`) — the frontend (AC5) is the only place that decides when the "Prep" affordance is shown, and nothing about the endpoint's own correctness depends on the booking being in any particular state. Do not add a status gate to the backend that the brainstorm doc never asked for.
5. **New "Prep" action on each `UPCOMING` booking card** in `CoachCommandCenterPage.vue`, opening a new component (dialog-style, following the existing `coachRescheduleDialogOpen`/`noShowPlayerDialogOpen` pattern already on that page — see Dev Notes "Why a dialog, not a new route") that calls the new endpoint and renders: the last-session date and recap ("what we worked on" / "what's next"), the focus thread, and the open-neglected-skill-count — each field individually falling back to an honest empty-state string when null/empty, and in particular rendering **three distinct** empty states rather than conflating them: "never trained together" (no `lastSessionDate` at all, matching story 12-1's roster-page copy), "no recap yet" (`lastSessionDate` present but both recap fields null — see AC3), and "no focus thread yet" (`focusThreadSkillCodes` empty). A genuine 403/404/5xx from the endpoint renders a dedicated error state, not a silent blank card. The player's display name shown on the card comes from the parent component's own `playerName` prop (already available on `CoachCommandCenterPage.vue`'s booking data), not from the endpoint response.
6. **A "Plan this session" action inside the same card links to the existing `coach/session-builder/:bookingId` route** (`SessionBuilderPage.vue`, route name `coach-session-builder`), passing this booking's id — this is this story's answer to the brainstorm's "quick note field for this session's plan" (see Dev Notes "What the 'quick note field' actually means here" for why a new free-text field was rejected in favor of linking to the surface that already captures a session's real plan, including `Session.developmentFocus`).
7. All new/changed user-facing strings (the new card's labels, empty states, and the new action buttons) are externalized via i18n in `en-US`, `de-DE`, and `fr-FR`, following the existing `coach.myPlayers*`-style flat-key-with-feature-prefix convention inside the shared `coach` i18n namespace (e.g. `coach.sessionPrep*`) — see Dev Notes "Why `coach.*`, not `booking.wrapUp.*`" for why this departs from the sibling `WrapUpSequence.vue` component's own namespace.
8. New backend test coverage must include, at minimum: an IT scenario proving AC1's fix — a coach with zero `player_skill_stats` rows for a player but one **attended** `SESSION_COMPLETED` timeline event carrying their own populated `coach_id` reads `accessExpired=false` and can read their own recap back (this exact scenario has no existing test anywhere today — confirmed absent during this story's research; seeding it requires a widened or new seeding helper that actually sets `coach_id` — the existing `insertSessionCompletedEventWithRecap` helper does not, see Task 2.3); a negative IT proving a **non-attended** `SESSION_COMPLETED` event does *not* advance the clock (AC1's attendance gate); an IT or unit test proving the pre-existing SLU-only path is unaffected; IT coverage of the new `/prep` endpoint covering booking-not-found (404), booking-owned-by-another-coach (403), a brand-new player with no history at all (must not error), a case where the recap must be null despite a non-null `lastSessionDate` (AC3's consistency rule), and a fully populated case; and a pure unit test for the focus-thread ranking logic (Task 3.1), independent of any HTTP/DB layer, matching the `RosterAttentionCalculatorTest` precedent (JUnit 5 + AssertJ, no Spring context, no mocks — not a Mockito test, see Testing Standards Summary).
9. New frontend test coverage for the new card component, covering: loading, error, the three independent empty states from AC5, a populated state asserting all four fields render, and the "Plan this session" link's target route.
10. **Explicitly out of scope for this story** — must not be implemented here: Priority 4's full coach-facing single-player detail page reusing `PlayerTimelinePanel.vue` (a separate future story, even though it would have needed this exact clock fix too — see Source); the recap→report-generation Fast-Follow; editing or correcting a previously submitted recap; the player/parent-initiated flag (the brainstorm doc keeps it "on the list" for revisiting alongside homework/messaging-adjacent stories — it is parked, not permanently closed); fixing the pre-existing missing-relationship-check gap on `/neglected-skills` and `/slu/coach-contributions` (story 12-1 already flagged this as a separate follow-up, not this story's job — and this story sidesteps it entirely by reading the underlying repository directly rather than calling either endpoint, see Dev Notes); and fixing `ReportGenerationService`'s own independent SLU-only coach-player-relationship gate (a **third** consumer of the narrow SLU-only signal, found during this story's review — see Dev Notes "A third, still-unfixed SLU-only gate"). Do not let any of these creep in.

### Why the new signal must be attendance-gated

`SluCalculationService.onBookingCompleted` returns early on `!event.isPlayerAttended()` (`SluCalculationService.java:52-55`) — a non-attended booking earns no SLU row today, by explicit design ("SLU is only earned for attended sessions"). `TimelineEventListener.onBookingCompleted`, by contrast, writes the `SESSION_COMPLETED` timeline row **unconditionally** — there is no attendance check anywhere in that class. Non-attendance is a real, switchable, user-facing path: `WrapUpSequence.vue` exposes a `playerAttended` toggle (defaulting to attended, but explicitly changeable before submission), and `BookingCompletionService.submitWrapUp` persists whatever value is submitted. Had this story's clock fix used the timeline signal as-is, a single non-attended wrap-up between a coach and a player would have granted that coach up to `development.timeline.coachAccessExpiryDays` (seeded 90) days of full timeline access — including that player's radar assessments and performance reports authored by *other* coaches — on the strength of a session that never happened. `deferred-work.md` itself separately warns that changing this kind of access policy "widens data access for currently-expired coaches and deserves its own ACs and tests" — so this story makes that an explicit, tested AC (AC1's attendance gate, Task 2.3's negative test) rather than an accidental side effect of fixing the Quick-Complete blind spot.

### Why the recap fields can legitimately be null even when `lastSessionDate` is not

Once the clock reads two signals (SLU rows and timeline events) instead of one, they can diverge on which one is more recent — and `lastWhatWeDid`/`lastWhatsNext` only ever come from a timeline event's metadata. Concretely: a Quick-Complete session on day 1 writes a timeline event with a recap; a session-builder session on day 20, with no recap submitted (or whose timeline write was lost — `TimelineEventListener`'s catch block only logs, per story 12-2's own accepted "silent async-write loss" risk), advances the SLU signal to day 20 with no corresponding timeline row. `lastSessionDate` correctly reports day 20 (the real most-recent session), but there is no recap for day 20 — showing day 1's recap text next to a day-20 date would misattribute it. `CoachPlayerLastSessionResolver`'s `recapSourceEventOrNull` (Task 2.1) encodes exactly this rule: the recap is only ever shown when its own event is the one that actually produced `lastSessionDate`. The card's "no recap yet" empty state (AC5) is the correct, honest fallback for this case — not an error, not a stale recap.

### Why this story bundles a brainstorm priority with a deferred-work defect

Normally this project keeps brainstorm-sourced feature stories and `deferred-work.md`-sourced bug/gap bundles separate (see `skillars-12-1`/`skillars-12-2`'s own Dev Notes on why Epic 12 is a standalone initiative, not a `skillars-deferred-N` bundle). This story is the deliberate exception, because the defect isn't incidental to the feature — it's a **blocking prerequisite** for the feature to actually work for every coach. Priority 3's whole premise ("auto-surface last session date + what was covered") is the exact data the broken clock hides from a Quick-Complete-only coach. Shipping Priority 3 against the unfixed clock would have reproduced story 12-2's own D1 finding one story later, for a second feature. Fixing it once, here, closes it for both the already-shipped recap-capture (12-2) and this story's own Prep Card, and for whatever Priority 4 eventually builds too.

### `CoachPlayerLastSessionResolver` — why a new shared class, not two separate inline computations

Both the timeline-access clock (Task 2.2) and the Prep Card's own `lastSessionDate`/recap fields (Task 3.4) need "when did this specific coach last complete an attended session with this specific player, and with what recap" — and they must agree, or a coach could see a populated Prep Card while simultaneously being told their timeline access is expired, because two slightly-divergent computations disagreed. Story 12-1 hit the same shape of problem for its own `lastActivityDate` merge and resolved it by computing the merge once and feeding both downstream consumers from that single value — this story follows the same pattern one level higher (across two separate services, not two fields of one DTO) by extracting the merge-and-attribution logic into its own small, reusable class.

### Why this endpoint doesn't call `/neglected-skills` or `/slu/coach-contributions`

Story 12-1's own Dev Notes already flagged — and deliberately did not fix — that `/api/development/players/{playerId}/neglected-skills` and `/api/development/players/{playerId}/slu/coach-contributions` have **no coach-player relationship check at all**: any authenticated `ROLE_COACH` principal can call either for any `playerId`. 12-1 sidestepped this by calling `NeglectedSkillFlagRepository` directly rather than going through the unguarded resource/service layer, and this story does the same for the identical reason: `SessionPrepService` already performs its own, *stronger* authorization check (booking ownership — AC3) before touching any player data, so reading the repository directly costs nothing extra in rigor while avoiding a second, weaker gate. This story does not call `SluContributionService`/`NeglectedSkillResource` at all, and does not fix their missing relationship check either (AC10) — that remains a separate follow-up exactly as 12-1 left it.

### A third, still-unfixed SLU-only gate

`ReportGenerationService` (around `ReportGenerationService.java:145-147`) independently gates report generation on the exact same narrow signal this story fixes elsewhere — `Instant lastSession = sluRepository.findLastSessionDate(playerId, coachId); if (lastSession == null) { throw new AccessDeniedException(...); }` — found during this story's pre-implementation review, not in the original research pass. This story fixes `TimelineQueryService`'s clock (AC1) but does **not** touch this one: after this story ships, a Quick-Complete-only coach will be able to read their timeline and open the Session Prep Card, while still being refused report generation for the same player, for the same underlying reason this story otherwise fixes. Explicitly out of this story's AC scope (AC10) — recorded here and in `deferred-work.md` as a known, separate follow-up rather than fixed as a drive-by.

### Why a dialog, not a new route

The brainstorm's own wording ("inside an upcoming booking's detail view") assumes a detail view exists to extend. It doesn't — this story's research confirmed `CoachCommandCenterPage.vue` renders every booking as an inline card inside a week grid, with no per-booking modal, dialog, or route today. Two existing dialogs on that same page (`coachRescheduleDialogOpen`, `noShowPlayerDialogOpen`) are the closest precedent for "a focused, booking-scoped overlay triggered from a card button," so this story creates the "detail view" the brainstorm assumed as a dialog following that exact pattern, rather than a new full-page route. `coach/session-builder/:bookingId` is the right target for Task 4.2's link precisely because it's a real page doing real planning work — not a precedent for making the Prep Card itself a route, which would be disproportionate for what is fundamentally a read-only summary plus one outbound link.

### What the "quick note field for this session's plan" actually means here

The brainstorm's literal wording asks for "a quick note field for this session's plan" on the Prep Card itself. This story deliberately does **not** build a new free-text field with its own persistence target, for two reasons found during research: (1) there is no existing place such a note would naturally live or be consumed — inventing a new column/table for a single ad hoc note that nothing downstream reads would be exactly the kind of new persistence Epic 12 has otherwise avoided throughout; (2) a real "this session's plan" surface already exists and is fully built — `SessionBuilderPage.vue` (`coach/session-builder/:bookingId`), which already captures `Session.developmentFocus` and real drill/block content. That page is also independently flagged in `deferred-work.md` ("coach UI CRUD audit (2026-10-14)" — "Training sessions — built but orphaned... no page anywhere links or navigates to this route") as unreachable from anywhere in the app. Linking to it from the Prep Card is not a side quest to fix that orphan defect — it is the most faithful reading of "a quick note field for this session's plan" available in this codebase, and it happens to also make that page reachable as a consequence, not a goal of this story. Do not additionally build a separate free-text note field on top of this link; that would be two competing answers to the same brainstorm line.

### Why `coach.*`, not `booking.wrapUp.*`

`SessionPrepCard.vue` lives in `components/booking/`, the same directory as `WrapUpSequence.vue` — but `WrapUpSequence.vue` uses the `booking.wrapUp.*` i18n namespace exclusively (confirmed: 26 references to `t('booking.wrapUp...')`, zero to `coach.*`). This story's i18n keys go under `coach.sessionPrep*` anyway, grouped with the related `coach.myPlayers*` feature family (same epic, same "coach looking at a specific player's development data" concept) rather than with `booking.wrapUp.*` (an unrelated wrap-up-wizard namespace that happens to share a directory). Directory co-location and i18n-namespace grouping are tracking two different things in this codebase; stated here explicitly so a future reader doesn't "fix" this as an inconsistency.

### The focus thread is honestly scoped to session-builder history only

`Session.developmentFocus` is only ever meaningfully populated when a session goes through the session builder. A coach who exclusively Quick Completes will see an empty focus thread — this is not a bug this story needs to work around; it's the same honest scoping 12-1's Dev Notes already established for `lastSessionDate` ("the API-facing field keeps its narrower, honest meaning"). Do not attempt to synthesize a focus thread from any other signal to paper over this.

### Explicitly out of scope (do not implement, do not let scope creep in)

Priority 4's coach-facing single-player detail page reusing `PlayerTimelinePanel.vue` (a separate future story — note that `PlayerTimelinePanel.vue` has no `coachId` prop and reads via a Pinia store action, `store.fetchTimeline`, not a direct API call; wiring it into a coach route is its own piece of work, not a drive-by here); the recap→report-generation Fast-Follow; any ability to edit a previously submitted recap; the player/parent-initiated flag; fixing `/neglected-skills`/`/slu/coach-contributions`'s missing relationship check (see "Why this endpoint doesn't call..." above); and fixing `ReportGenerationService`'s own independent SLU-only gate (see "A third, still-unfixed SLU-only gate" above).

### Known residual risks (acceptable for this story, not for silent "fixing")

- **The backfill cannot retroactively apply the attendance gate** (see AC2) — accepted because this application has no production deployment yet, so there is no real non-attended historical data at risk.
- **A row inserted between this migration's authorship and its actual deployment, by a `TimelineEventListener` that hasn't yet been updated by Task 1.3, would land with `coach_id IS NULL`** — harmless (the merge in Task 2.1 still works for every row that has *either* a qualifying SLU row or a populated timeline `coach_id`), self-healing the moment both halves of Task 1 ship together in the same deploy.
- **AC1's fix amplifies an existing, open pagination gap**: `PlayerTimelineRepository.findByPlayerIdOrderByOccurredAtDesc` takes no `Pageable` (already tracked in `deferred-work.md` against this same table), and this story's whole purpose is to let more coaches past the gate that currently short-circuits many of them with an empty list before that unbounded query even runs. Latency/payload only — not a new defect this story introduces, but worth flagging so it isn't later mis-triaged as a 12-3 regression.
