## Story

As the platform owner,
I want (1) real proof that `VideoDeletionService`'s per-video transaction isolation and `DrillUploadService`'s cross-drill video lock actually do what their own fixes claim, and (2) a working review-submission UI so an eligible parent or player can actually write, edit, and read coach reviews — since the backend for both has existed since `skillars-deferred-80`/`-81` and the original `reviews` module respectively, but neither is provably correct (tests) or reachable (UI) today,
so that the two most valuable open findings the last two code-review cycles produced stop being open findings, and the reviews module — fully built on the backend, entirely absent on the frontend — becomes an actual feature.

- **Booking/Availability/Reschedule, Messaging/Admin/Reviews/Disputes: nothing new.** No `## Deferred from:` section has been added to either module's territory since `skillars-deferred-82`'s own pass closed it out.
- **Video/Playback/Moderation: 2 real, actionable items survived** — both from the `skillars-deferred-80`/`-81` code-review sections that `skillars-deferred-82`'s own research apparently didn't fully mine (it closed 7 *other* bullets from those same two sections but left these 2 — plus 4 more that turned out to be false premises/Spring-level non-issues — untouched). These became AC1 and AC2 below.

**With Video/Playback/Moderation yielding only 2 items — both small, both test-coverage-only — this again did not clear this project's "no small stories" bar on its own.** Per this project's documented dry-ledger fallback (see `[[project_skillars_release_workflow]]`), the project owner chose to add an unrelated task (2026-08-29) rather than ship a 2-AC test-only story. ## Acceptance Criteria

1. **Prove `VideoDeletionService.cascadeDeleteForAccount`'s per-video transaction isolation actually holds under a mid-cascade failure — not just that the `@Lazy` self-proxy resolves without NPE.** Confirmed live: `AccountDeletionCascadeIT` (7 tests) exercises `cascadeDeleteForAccount` through a real `@Autowired VideoDeletionService` — so Spring's `@Lazy @Autowired self` wiring from `skillars-deferred-80` AC2 does resolve correctly in a real container — but every existing test only asserts the happy-path end-state (all videos `PURGED`). None simulates one video's `deleteVideo(...)` failing partway through to prove the *point* of AC2's fix: that `self.deleteVideo(...)` gives each video its own transaction, so video N's failure cannot roll back video N-1's already-committed purge. `VideoDeletionServiceTest`'s own unit test (`ReflectionTestUtils.setField(service, "self", service)`, line 54) bypasses the real proxy entirely and cannot prove this either way — it's a same-instance direct call, not a proxied one.

   - Add a new test to `AccountDeletionCascadeIT.java` (same file, same `@MockitoBean VideoProviderAdapter` / seeding helpers already present): seed two videos, A and B, for one coach owner via the existing `seedVideo(ownerId, providerAssetId)` helper (`:190-198`) — both default to `OperationalState.READY` (`:196`), so assert B is still `READY` post-cascade, not merely "unchanged" in the abstract. Change the existing `@Autowired VideoDeletionOutboxRepository outboxRepository` field to `@MockitoSpyBean` (mirrors this exact codebase's own established pattern for proving real-commit/rollback behavior with a spy on a Spring Data repository — see `CaptureReservationIT.java:81` spying `SessionPackPurchaseRepository`, comment: "a mock cannot fail a real Spring commit"). Stub `doThrow(new RuntimeException("simulated outbox failure")).when(outboxRepository).save(argThat(o -> o.getVideoId().equals(videoB.getId())))` — leave video A's save un-stubbed (real behavior).
   - **Cascade iteration order does not matter to this test's correctness (confirmed, story-review resolved)**: `cascadeDeleteForAccount`'s query (`VideoRepository.findByOwnerIdAndOperationalStateNot`, a derived method with no `@Query`/`Sort` — `VideoRepository.java:101`) has no guaranteed row order. This is a non-issue for this test specifically because the injected failure is keyed to video B's *id* via `argThat`, not to "whichever video is processed first" — regardless of which of A/B the cascade's loop reaches first, B's `deleteVideo` transaction always hits the stubbed throw and A's never does. Do not add an explicit sort or seed-ordering workaround; it would be solving a problem this design doesn't have.
   - **The stubbed exception fires before `deleteVideo`'s only other action past the outbox check (`publisher.publishEvent(new VideoPurgedEvent(videoId))`, `VideoDeletionService.java:100`) — confirmed by direct read of the method body (`:65-100`)**: `deleteVideo` runs `video.save()` (PURGE) → quota decrement (skipped here, `skipQuotaDecrement=true` in the cascade path) → `deletionLogRepository.save()` → the stubbed `outboxRepository.save()` → `publisher.publishEvent()`. The throw at the outbox-save step means `publishEvent` is never reached for B, and every earlier statement in B's transaction (the `video.save()` PURGE, the deletion-log row) rolls back together with it — Spring's declarative `@Transactional` rolls back the *whole* method on an uncaught `RuntimeException`, not just the failing statement. No try/catch wraps the outbox save internally (confirmed, none exists in the method body) that could swallow the injected exception before it propagates.
   - Fire the cascade (`listener.onAccountDeleted(new AccountDeletionRequestedEvent(coachOwnerId, AccountRole.COACH, List.of()))`), same as the existing happy-path test. Note for context (not itself asserted): the thrown exception propagates out of `self.deleteVideo(...)` and is caught by `cascadeDeleteForAccount`'s own outer `try/catch` (`VideoDeletionService.java:~170-174`, adds the id to `failedIds` and logs), so the cascade itself does not abort — this is why the test can safely assert on both A and B without the harness crashing.
   - Assert: video A's `operationalState` is `PURGED` and exactly one outbox row exists for it (its transaction committed independently and fully, unaffected by B's later failure). Assert: video B's `operationalState` is still `READY` (its own `deleteVideo(...)` transaction rolled back atomically on the outbox-save exception, not left half-applied), and `outboxRepository.existsByVideoIdAndStatus(videoB.getId(), "PENDING")` is `false` — reuse this exact repository method (`VideoDeletionOutboxRepository.java:50`) rather than inventing a `findByVideoId` query, which this interface does not expose. This is the actual proof the class needs: each `self.deleteVideo(...)` call is a genuinely separate, atomic transaction — not that the cascade merely "still works" when nothing fails.
   - Test: `mvn -o test -Dtest=AccountDeletionCascadeIT`, confirm the full class (8 tests including the new one) stays green.

2. **Prove `DrillUploadService`'s cross-drill video lock (`skillars-deferred-81` AC3) actually causes serialization between two concurrent callers — not just that the end result happens to be correct.** Confirmed live: `DrillUploadServiceConcurrencyIT.deleteVideo_concurrentCallsOnTwoClonesSharingOneVideoId_doesNotDoublePublishDeletionEvent` (lines 301-372) races two threads via a `CyclicBarrier`, then asserts exactly one `VideoPhysicalDeletionEvent` was published. This confirms the *outcome* is correct but not that the lock (`videoRepository.findByIdForUpdate(videoId)`, `DrillUploadService.java:168`) *caused* it — if the lock were silently removed, the same assertion could still pass by chance if the two threads happened to interleave favorably (JVM thread scheduling, not the lock, would be doing the work the test credits to the lock).

   - Add a new test to the same file, alongside the existing one (do not replace it — the existing end-result assertion remains valuable on its own). Change `videoRepository` to a `@MockitoSpyBean` (this codebase's own precedent, `CaptureReservationIT`/`MessageModerationSweeperIT`, spies the exact repository under test directly on the `@Autowired` field — no separate field needed unless another test in this same class relies on the un-spied bean, which none currently do).
   - **Design note (story-review resolved, timing-threshold approach replaced)**: a first draft of this AC measured wall-clock timestamps around an injected delay and asserted a minimum separation between the two threads' successful lock acquisitions. Investigating `PessimisticLockRetryer.withBoundedRetry` (`infrastructure/persistence/PessimisticLockRetryer.java:99-116`) directly shows why the specific flakiness scenario raised in review (the second thread's call exiting *before* the first thread's injected delay finishes) is actually impossible here: a failed `NO_WAIT` attempt is retried via a JDBC *savepoint rollback within the same still-open transaction* (`session.doWork(connection -> connection.rollback(savepointHolder[0]))`, `:112`), not a new transaction — so the losing thread cannot succeed until the winning thread's surrounding `@Transactional` method actually returns and commits, releasing the row lock. That said, a pure wall-clock threshold is still worth avoiding on general CI-timing-flakiness grounds (the review's point #1 stands on its own merits even though point #2's specific mechanism doesn't apply) — so this AC uses a timing-independent proof instead: **direct evidence that the losing thread's call was rejected and retried**, not just that end state and rough timing look right.
   - Instrument `findByIdForUpdate(videoId)` via `doAnswer`, wrapping `invocation.callRealMethod()` in a try/catch: on a caught `PessimisticLockingFailureException` (a real `NO_WAIT` rejection — `PessimisticLockRetryer` catches and retries this exact type), record the current thread's name into a `ConcurrentHashMap.newKeySet()`-backed `Set<String> threadsThatRetried`, then re-throw so the retryer's own catch/retry logic still runs unmodified. On a **successful** return, guarded by an `AtomicBoolean.compareAndSet(false, true)` so this only fires once, sleep ~300ms *before* returning the real result — this widens the contention window deterministically (removing reliance on incidental JVM/DB timing to produce a collision at all) but is no longer itself the thing the test asserts on.
   - Run the existing two-clone concurrent setup (same `CyclicBarrier`/`ExecutorService` shape as the existing test). After both futures complete, assert `threadsThatRetried` is non-empty — direct proof that at least one thread's attempt was genuinely rejected by the lock and had to retry, not merely that the two threads happened to finish in a way that produced the right end state.
   - Test: `mvn -o test -Dtest=DrillUploadServiceConcurrencyIT`, confirm the full class stays green including both the existing and the new test.
   - **Shared-repository-instance concern (story-review, resolved, no action needed)**: `VideoRepository` is a singleton Spring Data JPA proxy bean; `DrillUploadService` is also a singleton, `@Autowired` with that same one instance. Both `Future` tasks in this test call methods on the identical `drillUploadService` bean (standard Spring scoping, not per-thread), so both threads necessarily go through the one spied `VideoRepository` instance — no additional wiring or verification needed beyond what ordinary Spring bean scoping already guarantees.

4. **Build the write side: an eligible parent or player can submit a new review, or edit their existing one, from `CoachPublicProfilePage.vue`.** Confirmed live: `POST /api/reviews/coaches/{coachId}` (submit) and `PATCH /api/reviews/{reviewId}` (update) both take `SubmitReviewRequest(rating: 1-5 required, body: optional, max 1000 chars)`. `GET /api/reviews/me/coaches/{coachId}` (`ReviewResource.java:97`) tells the caller whether they already have a review for this coach — **critical, easy-to-miss detail**: when no review exists, this endpoint does not 404, it returns **HTTP 403** with `errorMsg.errorKey = "reviews.reviewNotFound"` (`ReviewQueryService.java:74`, routed through `ReviewApiAdvice`'s generic-403 fallback branch, `ReviewApiAdvice.java:~58`) — a plain `status === 404` check will not distinguish "no review yet" from a real authorization failure; check the `errorKey`, not the status code, to decide which state to show. Eligibility itself (a completed session with this coach within the last `reviews.submissionWindowDays` config days, default 14 — `ReviewSubmissionService.java:130-140`) is only evaluated at submit/update time, not queryable in advance — there is no pre-flight eligibility check to call.

   - Gate this entire feature on `authStore.isParent || authStore.isPlayer` (not `isCoach`, not a guest) — matches the backend's own `AuthorRole` enum (`PARENT`, `PLAYER` only; a `COACH` caller gets `AUTHOR_ROLE_NOT_ALLOWED`, `ReviewSubmissionService.java:52-56`), so the UI never even offers the action to a role the backend would reject.
   - On mount, for an eligible-role caller only, call `getMyReviewForCoach(coachId)`. On success: show "Your review" (rating, body, and — `v-if="review.moderationStatus === 'PENDING' || review.moderationStatus === 'UNDER_REVIEW'"` — a short note that it's awaiting moderation and not yet publicly visible; `v-if="review.moderationStatus === 'BLOCKED'"` a note that it was removed by moderation; `APPROVED` shows neither note) with an "Edit" button. On failure with `errorKey === 'reviews.reviewNotFound'`: show a "Write a review" button instead. On any other failure: log it, do not block the rest of the page from rendering (mirrors this exact codebase's own established pattern — `CoachPublicProfilePage.vue`'s player-branch `onMounted` catch from `skillars-deferred-82` AC2 keeps rendering on a non-404 error rather than crashing the page).
   - Both buttons open the same dialog component (a `q-dialog`, new — no existing review-dialog to reuse): a `q-rating` input (`v-model`, required, 1-5) mirroring the exact editable pattern already established in `WrapUpSequence.vue:38-44` (`size`, `color="amber"`, `icon="star_border"`, `icon-selected="star"`, `:max="5"`) plus a `q-input type="textarea"` for `body` (optional, `maxlength="1000"`, matching the backend's own limit so the UI never lets a user compose something the server will reject on length alone). Reset the dialog's local state on open rather than relying on stale values from a prior open in the same session: on "Write a review" click, reset to a blank form (`rating = null`, `body = ''`) before opening; on "Edit" click, pre-fill from the already-fetched review with safe fallbacks (`rating: review.rating ?? null`, `body: review.body ?? ''` — `body` can be `null` from the backend since it's an optional field) before opening. Do this at the point each button is clicked (not in a shared `@show` handler keyed off which mode is active), so there is no window where the wrong flow's stale data is visible even briefly.
   - Submit calls `submitReview`/`updateReview` as appropriate. On success, close the dialog, refresh the "your review" state (re-call `getMyReviewForCoach`) and re-fetch page 0 of the approved-reviews list (AC3) — a fresh submission won't appear there immediately (pending moderation), but an edit to an already-`APPROVED` review should reflect once re-approved; simplest correct behavior is just to refresh both, not to special-case moderation timing client-side.
   - On failure, use the existing `useErrorHandler` composable (`src/frontend/src/composables/useErrorHandler.js`) exactly as other dialogs in this codebase do — it already maps the backend's `errorMsg.errorKey` (which for every `ReviewErrorCode` value is already namespaced `reviews.*`, e.g. `reviews.noRecentSession`, `reviews.alreadySubmitted`) straight to an i18n key via `t()`/`te()`; no custom error-code-to-message mapping needed, only the i18n keys themselves (next bullet). Keep the dialog open on failure so the user can correct/retry.
   - Add new i18n keys under a new top-level `reviews:` namespace (required — `ReviewErrorCode`'s codes are all `reviews.*`-prefixed and `useErrorHandler` resolves them by exact dot-path) to **all three locale packs** (`en-US`, `de-DE`, `fr-FR` — standing convention, see `skillars-deferred-81` AC2's identical 3-pack precedent for a new toast). English content (authoritative; DE/FR must mirror the meaning in this file's existing tone/register, not a literal machine translation):
