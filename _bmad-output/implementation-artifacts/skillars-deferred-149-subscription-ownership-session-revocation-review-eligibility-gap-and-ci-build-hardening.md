### Finding 1 — `SubscriptionService.assertPlayerOwnership` has no self-registered-player branch

`SubscriptionResource.getMyPlayerSubscription` (`SubscriptionResource.java:91-92`) guards the read with `@PreAuthorize("@playerOwnershipGuard.check(authentication, #playerId)")`. `PlayerOwnershipGuard.check` authorizes **both** a parent on a parent-owned profile (`existsByIdAndParentId`) and a self-registered player on their own profile (`existsByIdAndUserId`) — the same dual check `skillars-deferred-147` added for every other player-owned resource.

But the service call beneath it, `SubscriptionService.assertPlayerOwnership` (`SubscriptionService.java:899-904`):

```java
private void assertPlayerOwnership(Long parentUserId, Long playerId) {
    if (!parentPlayerLinkRepository.existsByParentIdAndPlayerId(parentUserId, playerId)) {
        throw new PaymentGatewayException("payment.subscription.playerOwnership");
    }
}
```

checks **only** `main.parent_player_links` — parent-child, with no self-registered-player disjunct at all. The resource's `currentParentId()` helper (`SubscriptionResource.java:134-136`) is actually `securityUtil.requireCurrentUserId()` — i.e. "the caller's own id," not "a confirmed parent" — so it resolves correctly for a self-registered player too; the rejection happens purely inside `assertPlayerOwnership`'s DB check. A self-registered adult player who passes the controller's `@PreAuthorize` therefore still gets `payment.subscription.playerOwnership` from the service call one line later.

`assertPlayerOwnership` is called from **four** places in `SubscriptionService` (`:113`, `:319`, `:382`, `:457` — `getPlayerSubscription`, `subscribePlayer`, `changePlayerTier`, `cancelPlayerSubscription`), but only `getPlayerSubscription`'s controller method (`getMyPlayerSubscription`) uses the dual-check `@PreAuthorize`; the other three controller methods (`subscribePlayer`, `changePlayerTier`, `cancelPlayerSubscription`) are gated `@PreAuthorize(SecurityConstants.HAS_PARENT_ROLE)` — parent-only, unaffected by this fix, confirmed no other change needed there. Widening `assertPlayerOwnership` therefore only changes observable behavior for the one route that already claims to support a self-registered player.

The frontend route `parent/player/:playerId/subscription` (`routes.js:205-209`, backing `PlayerSubscriptionPage.vue`) is currently `meta: { requiresAuth: true, role: 'PARENT' }` — `skillars-deferred-148` deliberately left it `PARENT`-only, matching what the backend *actually* supported end-to-end at the time, and filed this exact gap as its own deferred-work item rather than folding a larger fix into a mechanical-fixes bundle.

Confirmed via `grep` that no caller outside `SubscriptionResource`/`SubscriptionService` invokes any of the four `assertPlayerOwnership`-gated service methods — the widening has no other call-site surface to worry about.

### Finding 2 — Two vacuous registration-email-verification tests per file, in `CoachRegistrationResourceIT` and `ParentRegistrationResourceIT`

Found by acting directly on the "wider grep" companion ask recorded under "Deferred from: manual review during skillars-deferred-143" — "any other IT seeding state with a bare `jdbcTemplate` write in a test method body has the same silent no-op" — rather than from a ledger entry that already named these files.

Both `CoachRegistrationResourceIT.verifyEmail_expiredToken_returns400WithCanResend` (`:205-238`, seed insert at `:221`) and `.verifyEmail_usedToken_returns400` (`:243-273`, seed insert at `:259`) — and the byte-identical pair in `ParentRegistrationResourceIT` (`:198-236` seed at `:214`; `:237-271` seed at `:253`) — insert a row into `main.email_verification_tokens` via a **bare** `jdbcTemplate.update(...)` call, outside any `transactionTemplate.execute(...)` wrap, then immediately call the real HTTP endpoint (`httpTestClient.makeHttpRequest`, a genuine round trip to the running server in a separate connection/transaction). `spring.datasource.hikari.auto-commit=false` (`application.yaml:183`) means that bare write is rolled back the moment the connection is released back to the pool — the row never exists for the server to find. This is the identical mechanism `skillars-deferred-144` AC5 already fixed once in `AuthResourceIT.refresh_expiredToken_returns401`.

Confirmed empirically what each test proves instead, by tracing the production code: `CoachRegistrationService.verifyEmail(UUID token)` (`CoachRegistrationService.java:112-121`) does `emailTokenRepository.findByToken(token).orElseThrow(() -> new EmailTokenException("security.emailTokenInvalid", true))`, then checks `.isUsed()` → `"security.emailTokenUsed"`, then expiry → `"security.emailTokenExpired"` — **every** branch throws `EmailTokenException`, and `ApiAdvice.emailTokenExceptionHandler` (`ApiAdvice.java:555-562`) maps **every** `EmailTokenException` to `400 BAD_REQUEST` uniformly, with `canResend` carried straight from the exception (both the "invalid"/not-found and "expired" branches pass `true`).

Consequence: with the seeded row invisible, `findByToken` always falls into `orElseThrow` first — i.e. the **"not found"** branch fires, not "expired" or "used":
- `verifyEmail_expiredToken_returns400WithCanResend` asserts `400` + body contains `"canResend"` + `"true"` — both are *also* true for "not found," so the test passes without ever reaching the expiry check it is named for.
- `verifyEmail_usedToken_returns400` asserts **only** `400` (no error-key check at all) — true for every `EmailTokenException` variant, so this test proves nothing about the "used" branch specifically.

`PlayerRegistrationResourceIT` was checked and does **not** have this pair of tests — out of scope, not silently skipped.

### Finding 3 — Theft-driven refresh-token revocation never terminates a live JWT session

Full mechanism (confirmed by reading `AuthService`, `JwtManagerImpl`, `TokenCreatorImpl`, `DaoAuthProvider`, `Principal`, `JWTAuthorizationFilter`, and the constants in `SecurityConstants` — not assumed):

- **Two tokens, two lifetimes.** `potc` (the JWT session cookie) has a 15-minute TTL (`SecurityConstants.JWT_TTL`). `rtkn` (the refresh token) is a 7-day opaque value (`REFRESH_TOKEN_TTL`), stored server-side only as a SHA-256 hash in `refresh_tokens`.
- **"Reuse" is checked only inside `AuthService.refresh()`.** It looks up the presented `rtkn` by hash; if that row's `used` flag is already `true`, this is the classic refresh-token-rotation theft signal. Outside a 30-second multi-tab grace window (`REFRESH_GRACE_WINDOW`), both branches (`AuthService.java:157`, `:166`) call `refreshTokenRepository.markAllUsedByUserId(ownerId)` — a bulk `UPDATE refresh_tokens SET used=true WHERE user_id=?` — and nothing else.
- **That write never touches the `user` row.** Ordinary API requests never go through `AuthService.refresh()` — they're authorized by `JWTAuthorizationFilter.attemptAuthorization` against the `potc` JWT directly, which has two paths (javadoc at `JWTAuthorizationFilter.java:69-88`): a **fast path** (the common case) that does zero DB work and just re-stamps a fresh 15-minute JWT via `extendTtlOfToken`; and a **DB re-auth path**, taken only once the JWT's own `dbRefreshToken` claim has elapsed (`DB_REFRESH_TOKEN_INTERVAL` = 5 minutes), which calls `daoAuthProvider.authorize(...)` — re-loading the account and re-running Spring Security's own pre-authentication checks — but **never reads `refresh_tokens`** either. So a JWT that already existed before the revocation keeps working on the fast path indefinitely, and even the periodic DB re-auth path has no way to see that revocation happened.
- **Why the JWT's own `iat` claim cannot be used as a staleness signal (researched and rejected during story creation).** `TokenCreatorImpl.toClaims` (`TokenCreatorImpl.java:50`) sets `Claims.ISSUED_AT = now()` on **every** call, including the fast path's `extendTtlOfToken` → `toClaims(principal, dbRefreshToken, true, null)` (`JwtManagerImpl.java:166`). A stolen JWT used continuously on the fast path gets its `iat` refreshed on every single request, so comparing `iat` against a revocation timestamp on the (bounded-to-5-minutes) DB re-auth path would never catch it. The one claim that *does* survive fast-path extensions unchanged is `dbRefreshToken` itself (`extendTtlOfToken` extracts and re-passes the *incoming* value rather than regenerating it) — but that is a forward-looking "next DB-check deadline," not a backward-looking issuance marker, and it resets on every legitimate DB re-auth success too, revoked or not. No existing JWT claim can distinguish "issued before this revocation" from "issued after" without adding a new claim that behaves differently from `iat` — out of proportion to the owner-accepted fix below.
- **Decision taken (see header): accept the ~5-minute bound the DB re-auth path already provides**, by flipping state on the `user` row the same way `skillars-deferred-143` did for account locking, rather than engineering a new per-session epoch claim.

### Finding 4 — `isGenuineDenial` doesn't treat a hard-deleted user's wrap code as a genuine denial — but widening to every other wrap code would create new risk, not remove it

`JWTAuthorizationFilter.isGenuineDenial` (`JWTAuthorizationFilter.java:342-357`) treats `AccountStatusException` and `AuthorizationException(ACCOUNT_NOT_LOGIN_ABLE)` as genuine denials (full teardown: refresh-token revocation + cookie clearing), but not `AuthorizationException(USER_NOT_FOUND)`. A user whose row is hard-deleted while holding a valid JWT hits the routine (not genuine) branch on this filter's leg — cookies cleared, no revocation. Practical gap is nil today (`AuthService.refresh()`'s own `findById` rejection independently revokes the same case, and `POST /api/auth/refresh`'s frontend wrapper, `skillarsRefresh()` in `auth.api.js:45-47`, has zero call sites anywhere in `src/frontend` — confirmed dead code, not merely unused).

Reading the full method (`DaoAuthProvider.java:28-59`), `authorize()` can actually produce **four** other error codes, not two — `UNKNOWN` fires at **two** separate sites: `catch (InternalAuthenticationServiceException)` at `:37-41` (exactly how Spring's `DaoAuthenticationProvider` wraps a repository/`DataSource` failure) **and** the generic `catch (Exception)` catch-all at `:52-56`; `USER_NOT_FOUND` at `:42-46`; plus `MISSING_RIGHTS`/`MISSING_USERNAME` from the methods `authorize()` itself calls (`checkAuthorities`/`determineUsername`), which are not genuine-denial candidates at all (they fire on every ordinary insufficient-role 403 and on a malformed/anonymous authentication respectively). **`UNKNOWN` is deliberately not widened** — it is the generic infrastructure-failure bucket, and making it a genuine denial would mean a connection-pool exhaustion, lock timeout, or query timeout at the 5-minute DB-reauth boundary revokes the user's 7-day refresh token and forces a full re-login, for every user who happens to cross the boundary during the blip. That is a materially different risk than this item's "zero-risk completeness fix" framing, and it cuts against `isGenuineDenial`'s own documented design intent (`:309-340`: routine causes must not reach the DB-write path). Scope is narrowed to `USER_NOT_FOUND` only — the one code that unambiguously means "this account is genuinely gone," not "something transient went wrong while checking."

`ConfigStartupAssertion.java:182` and `ConfigService.java:321` (the PUT-time guard, `rejectReviewEligibilityWindowOrdering`) both reject only `minSessionAgeDays >= updateCooldownDays`. `minSessionAgeDays = 29` with `updateCooldownDays = 30` passes both guards while leaving a one-day-wide qualifying window — edits at the cooldown boundary still 403 as `reviews.noQualifyingSession`, the exact symptom the guard's own error message attributes to a config error, now undetectable by it. ### Finding 7 — The Dockerfile's selective `COPY` makes `git.dirty=true` permanent in every image (not `.dockerignore`'s exclusion patterns — those are a red herring for this specific symptom)

`Dockerfile` copies exactly three paths into the builder stage: `pom.xml` (`:6`), `src/` (`:10`), and `.git/` (`:11` — deliberate, needed by `git-commit-id-maven-plugin`, `pom.xml:733-748`, bound to Maven's `initialize` phase). Every other git-tracked path (`docs/`, `requirements/`, `_bmad/`, `.github/`, `deploy/`, `docker-compose*.yml`, `Dockerfile`, `mvnw`, `mvnw.cmd`, `.gitignore`, `.gitattributes`) is simply **never `COPY`ed at all** — `.dockerignore`'s header even says so in as many words (`:3-4`: "the Dockerfile only consumes three paths"). JGit's dirty-check compares the copied `.git/index` (which still lists those paths as part of HEAD's tracked tree) against what actually exists on disk in the container's working directory, finds them absent, and reports them as deletions — stamping `git.dirty=true` into every build's `git.properties` regardless of how clean the real commit is. **Removing or narrowing `.dockerignore`'s exclusion patterns at `:43-70` would change nothing** — those paths aren't in the container because the Dockerfile never `COPY`s them, not because `.dockerignore` filters them out of an otherwise-complete copy; `.dockerignore` only controls what the Docker **build context** (the tarball sent to the daemon) contains, which is a separate question from what the Dockerfile's own `COPY` instructions then select from it. A repo-wide grep confirms zero consumers of this value today (no `management.info.git.mode: full` configured in any `application*.yaml`, so Spring Boot Actuator's default `/manage/info` git contributor doesn't even surface the dirty flag at all currently) — this is pure provenance hygiene, not a live bug.

### C. Theft-driven refresh-token-reuse session revocation (Finding 3)

New nullable column, `main."user".security_session_invalidated_at` (`timestamp without time zone` — matching every other nullable timestamp column on this table, not `TIMESTAMPTZ`; see the migration shape below), additive, no FK/CHECK.

**Migration shape — follow `V157__coach_reviews_author_last_edited_at.sql` exactly, not a bare `ALTER TABLE`:**

```sql
-- Additive, nullable ADD COLUMN per the expand/contract standard (migration-conventions.md rule 1).
-- timestamp without time zone, matching every other nullable timestamp column on this table
-- (activation_date, reset_expiration, account_expiration, created_date, last_modified_date).

    ADD COLUMN IF NOT EXISTS security_session_invalidated_at timestamp without time zone;
```

`SET LOCAL lock_timeout` is mandatory above `SESSION_SCOPED_LOCK_TIMEOUT_BASELINE` (`MigrationLint.java` baseline `150`; this story's migration is `V158`) — a bare `ALTER TABLE ADD COLUMN` with no lock-timeout statement in effect fails `MigrationConventionLintTest.realMigrations_aboveBaseline_areClean` on `MISSING_LOCK_TIMEOUT`, and a plain (non-`LOCAL`) `SET lock_timeout` above that same baseline independently fails `SESSION_SCOPED_LOCK_TIMEOUT`. `ADD COLUMN IF NOT EXISTS` matches every recent migration's convention.

**Envers — this is the part most likely to be missed, and breaks `login()` itself if it is.** `User` is Hibernate-Envers `@Audited` (`User.java:45`), with a real `main.user_aud` table that does **not** automatically gain new columns. Two precedents exist on this exact entity: `V143` added `cleanup_failed_at` etc. as `@NotAudited` (*"this is operational marker state, not user-facing auditable history — `main.user_aud` has no matching column and none is added by this story"*); `V145` exists **only because** a prior change (`skillars_role`/`verification_status`) was added to the audited region without a matching `user_aud` column and had to be back-filled. **This field follows `V143`'s path — `@NotAudited`** (it is session-security operational state, not user-facing history, same classification as `cleanupFailedAt`): the entity field must carry `@NotAudited`, placed in the `@NotAudited` cluster (`User.java:100-133`), **not** near `locked` (`:71-72`, inside the audited region — do not follow Design C's earlier draft placement literally). If `@NotAudited` is rejected during implementation for any reason, the alternative is a matching `ALTER TABLE main.user_aud ADD COLUMN ...` in the same migration (`V146`'s path) — but `@NotAudited` is the cheaper, correct choice here and should be the default.

New `User.java` field `securitySessionInvalidatedAt` (`Instant`, nullable, `@NotAudited`) + getter/setter, placed beside `cleanupFailedAt` and friends (`:100-133`), not beside `locked`.

**New `UserRepository` method — `REQUIRES_NEW`, not ambient.** Mirror `RefreshTokenRepository.markAllUsedByUserId`/`markUsedByTokenHash` (`:79-82`, `:117-121`), **not** `changeAccountLockStatus`/`markCleanupFailed` (wrong precedent — see below):

```java
@Query("update User set securitySessionInvalidatedAt = :invalidatedAt where id = :userId")
@Modifying
@Transactional(propagation = Propagation.REQUIRES_NEW)
void invalidateSessionsForUser(@Param("userId") Long userId, @Param("invalidatedAt") Instant invalidatedAt);
```

**This is not optional, and the obvious-looking alternative is wrong.** Both call sites — `AuthService.refresh()`'s two theft branches (`:157-159`, `:166-168`) — call `markAllUsedByUserId(ownerId)` and then **throw immediately** (`BadCredentialsException`, a `RuntimeException`). `AuthService` carries a bare class-level `@Transactional` (`:48`) with Spring's default rollback-on-`RuntimeException` rule, `AuthResource` is not itself transactional, and `spring.jpa.open-in-view` is `false` (`application.yaml:158`) — so `AuthService.refresh()` is its own outermost transaction boundary, and that boundary rolls back the instant the branch throws. An ambient (non-`REQUIRES_NEW`) write to `invalidateSessionsForUser` at that point would be silently discarded along with everything else in the transaction — `security_session_invalidated_at` would stay `NULL` forever and **AC3 would ship as a complete no-op**. This is exactly the reasoning `RefreshTokenRepository.markAllUsedByUserId`'s own javadoc (`:86-96`) already states for the sibling write at the same call site (*"a caller that revokes-then-throws must not have the revocation undone by its own rollback"*) and exactly the reasoning `AuthService.java:216-218` repeats for `terminateSession`'s own `REQUIRES_NEW` revocation on the account-liveness rejection path. `changeAccountLockStatus` (no `@Transactional` at all) is not a counter-example — it has **zero callers** anywhere in `src/main` or `src/test` and is not evidence that an ambient write is safe here.

**No self-deadlock risk from `REQUIRES_NEW` at this call site** — neither theft branch writes the `user` row before this point in the method, so the inner `REQUIRES_NEW` transaction takes an uncontended lock, the same argument `AuthService.java:205-208` already makes for why the later `refresh_tokens` `REQUIRES_NEW` revocation in this same method is safe.

**`AuthService.refresh()`'s two theft-detection branches** (`AuthService.java:157`, `:166`) each gain one line immediately alongside the existing `refreshTokenRepository.markAllUsedByUserId(ownerId)` call:

```java

```

**`AuthService.login()`** clears the flag on every successful password-verified login — add `user.setSecuritySessionInvalidatedAt(null)` immediately after `ensureAccountIsLive(user)` succeeds (`AuthService.java:97`). `user` is a managed entity inside the class-level `@Transactional` method (loaded via `userRepository.findOneByLogin(...)` a few lines above, `:87`), so a plain setter is sufficient — Hibernate dirty-checks and flushes on commit, the same pattern the rest of this method already relies on (nothing in `login()` calls an explicit `.save()` for anything else either).

**The actual enforcement hook — `Principal.instanceFrom`** (`Principal.java:140-160`) currently hardcodes `.credentialsNonExpired(true)` (`:150`), an unused slot. Change it to:


This is the entire enforcement mechanism — no other file changes. `Principal extends org.springframework.security.core.userdetails.User` (Spring Security's own `UserDetails` base), and `DaoAuthProvider.authorize()` (the method the filter's 5-minute DB-reauth path already calls, `JWTAuthorizationFilter.java:206-207`) already calls `getPreAuthenticationChecks().check(user)` (`DaoAuthProvider.java:36`) — Spring's own `AccountStatusUserDetailsChecker`, which throws `CredentialsExpiredException` (an `AccountStatusException` subtype) the moment `isCredentialsNonExpired()` is `false`. `DaoAuthProvider.authorize()`'s existing `catch (AccountStatusException ase)` (`:47-51`) already maps **any** such exception uniformly to `AuthorizationException(SecurityError.ACCOUNT_NOT_LOGIN_ABLE)` — already one of `isGenuineDenial`'s existing triggers (`JWTAuthorizationFilter.java:354`), which already drives the full teardown (`securityUtil.terminateSession`). **Zero changes needed to `DaoAuthProvider.java` or `JWTAuthorizationFilter.java` for this mechanism to work** — the hook already exists and is already wired end-to-end; only the one previously-hardcoded boolean needs to become conditional.
