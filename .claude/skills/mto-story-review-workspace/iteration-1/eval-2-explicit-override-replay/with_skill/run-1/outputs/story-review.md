## 4. Corner Cases, False Assumptions, Missed Flows — Survived Step 4b

### 4.1 Real finding: `RoutingDataSourceContext` leaks into cascaded AFTER_COMMIT REQUIRES_NEW listeners triggered from inside the routed call (independently re-verified by me)

The story's own Review Findings dismissed a "[Patch] Routing Context Potential Leak" finding by checking only the *same-key* nested case (GDPR's `erase()` → `eraseTransactional()` → `deletePlayerDevelopmentData()`, all setting `GDPR_ERASURE_DATASOURCE_KEY`) and correctly found that harmless. It never checked the *different-key, side-effect-triggered* case, which is real:

- `RoutingDataSource.determineCurrentLookupKey()` (`RoutingDataSource.java:50-52`) reads `RoutingDataSourceContext.get()` fresh on **every** connection acquisition, app-wide, with zero scoping — confirmed by direct read.
- `persistPaymentFailure` sets the routing key to `PAYMENT_REQUIRES_NEW_DATASOURCE_KEY`, then calls `self.persistPaymentFailureTransactional(...)` inside the same `try` (`BookingPaymentPersistenceService.java:288-291`).
- `persistPaymentFailureTransactional` calls `transitionOrReport(...)` → `bookingService.transition(...)` → `BookingService.transitionInternal` (`:174`), which publishes `BookingStatusChangedEvent` — confirmed by direct read. `declineBatchBookingTransactional` does the same (`:398`); `reserveCaptureTransactional` does not call `transitionOrReport`, so it is unaffected.
- Two independent listeners consume that event **synchronously, inside the same REQUIRES_NEW transaction's commit callback**, before control returns to the wrapper method — both confirmed `@TransactionalEventListener(AFTER_COMMIT)` + `@Transactional(REQUIRES_NEW, ...)`, neither `@Async`:
  - `BookingBatchStatusListener.onBookingStatusChanged` (`:34-35`) — can cascade into `BookingBatchService.updateBatchStatusFromBooking`, a real write.
  - `SessionPlanService.handleBookingTerminalNonCompletion` (`SessionPlanService.java:195-196`) — writes `session.setStatus(CANCELLED)`.
- Both of these listeners' own REQUIRES_NEW transactions open new connections while `RoutingDataSourceContext` is **still set to the payment key** — `RoutingDataSourceContext.clear()` doesn't run until `persistPaymentFailure`'s `finally`, after both listeners have already fired. So these unrelated booking-batch/session-plan writes get misrouted onto the 10-connection, 5-second-timeout payment pool instead of the 30s primary pool.

I independently re-verified this entire chain myself, reading `RoutingDataSource.java`, `BookingPaymentPersistenceService.java`, `BookingService.java`, `BookingBatchStatusListener.java`, and `SessionPlanService.java` directly (not relying on the subagent's report alone) — it holds.

**Not newly introduced by this story** — the identical shape pre-dates it: `GdprErasureService.eraseTransactional` publishes `UserErasedEvent` while GDPR-routed, and `UserErasedEventListener.onUserErased` (confirmed `AFTER_COMMIT` + `REQUIRES_NEW`, not async) is misrouted onto the 3-connection GDPR pool the same way. AC2 faithfully mirrors an established pattern — and faithfully inherits its blind spot, but now on booking/payment request-thread traffic instead of an admin-only trigger, which is exactly the kind of volume difference the story's own AC2 motivation (real production traffic vs. admin path) says matters.

**Severity:** Not a data-correctness bug — same physical database either way — but it undermines AC2's own stated purpose (isolating payment `REQUIRES_NEW` pressure) since unrelated writes now silently draw from the payment pool's budget, a draw the sizing arithmetic never accounted for, and those unrelated writes now inherit a much tighter 5s timeout instead of 30s. Worth a genuine follow-up story; not a "must fix before ship" given it mirrors an already-shipped, incident-free pattern, but it is a real gap the story's own dismissal of the adjacent "Routing Context Potential Leak" finding should have caught and didn't.

### 4.2 Minor: pool-sizing Javadoc anchors to a number that isn't load-bearing

`paymentRequiresNewHikariConfig`'s Javadoc justifies `maximumPoolSize=10` as "2x `booking.batch.maxSize` (=5)". `BOOKING_BATCH_MAX_SIZE` is actually runtime-configurable up to 100 (`ConfigBounds.java:181-183`), but the batch loop draws pool connections **sequentially**, not concurrently within one batch (confirmed: `PaymentLifecycleService.onBatchBookingAccepted` calls the three REQUIRES_NEW methods once per booking, each with its own complete set/clear cycle, never overlapping). So raising `batch.maxSize` wouldn't actually increase peak concurrent draw — the "2x batch.maxSize" framing is a numeric anchor for the constant `10`, not a real functional dependency. Documentation-precision issue only, not a sizing bug.

## 5. What Did Not Survive Re-Verification

- **Nothing from the four layers was outright fabricated.** Every citation, ledger reference, and mechanistic claim pointed at content that genuinely exists somewhere in the codebase; "DRIFTED" here means relocated, not invented.
- **The "wrong citation" framing for deferred-work.md items #15/#16** (Section 1) does not indicate the story's own review process failed — those citations are exact matches against the commit the story explicitly claims as its baseline (`c9a2691d`). They only failed against current HEAD because of one intervening ledger-cleanup PR. Flagging this as a citation "error" would itself be a false positive; it's correctly categorized here as staleness with an identified, benign cause.
- **The routing-context-leak finding (4.1) is NOT the same as the story's own dismissed "[Patch] Routing Context Potential Leak"** — that dismissal was correct on its own narrower terms (the same-key nested case really is harmless). I did not find the story's dismissal reasoning itself to be wrong; I found it addressed a different, narrower case than the one that's actually exploitable. This distinction matters for triage: the existing dismissal should stand as written, and the new finding should be logged separately rather than treated as "the review missed something it already looked at."
- **No transaction-boundary or atomicity claim in this story was found to be backwards or unverified-when-asserted** — the one claim shaped exactly like the original skill-motivating defect (Section 3, item 5) was traced to the actual code and confirmed correct, twice.
