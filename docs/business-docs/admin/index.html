Admin / Staff

Internal Skillars staff — operations, trust & safety, and platform partnerships. This page is scoped honestly: it covers what's actually clickable in the UI today, separately from what's real backend capability with no UI yet.

Who this persona is

Admin/staff accounts run the business behind the scenes: keeping the infrastructure healthy and — per the backend capability documented in the technical docs — moderating content, resolving disputes, enforcing coach reliability, and handling GDPR data requests. As of this build, exactly one of those has a working frontend (system health); everything else is operated directly against the API, not through a Skillars admin screen.

1. System health — the only working admin screen

  1. /admin/health-dashboard: an overall UP/DOWN status pill, plus a card per backend component (database, cache, external providers, etc.) with status and detail rows. Non-admin users see only the overall pill with an "Admin access required" notice instead of component details.

2. The B2B tenant screens — removed from the backend, still present in the UI

These screens no longer work, and this is a real defect rather than an unfinished feature. The B2B partner ("tenant") capability — external businesses integrating over API with an API key — was deleted from the backend. Every endpoint it served (/v1/admin/tenants and its key/webhook sub-routes) is gone.

What was not removed: the frontend routes /admin/tenants and /admin/tenants/:tenantRef, their page components (TenantListPage.vue, TenantDetailPage.vue), and all 14 tenant calls in admin.api.js — which is every call in that file except the single health-check one. They are all still shipped and still reachable. Anyone navigating there will hit a screen that fails to load its data, because it is calling endpoints that no longer exist.

If you are demoing or onboarding, do not open these screens. They should be deleted from the frontend; until then, treat them as dead code that happens to be routable.

What's real but API-only (no admin UI yet)

The backend fully supports the following — they're documented in depth in the technical docs — but there is currently no admin-facing screen for any of them:

Trust & safety moderation

A unified moderation queue fed by reports from messaging, reviews, and video — real backend endpoints, no UI.

Coach enforcement

Reliability strikes, visibility reduction, and suspension for repeated late cancellations/no-shows.

Dispute resolution

Handling disputes raised over a booking.

GDPR requests

Data export and erasure requests — legally time-boxed, currently operated without a dedicated screen.

Review moderation

AI + flag-based moderation of coach reviews before they go public. Doubly invisible: there's no admin screen to moderate them, and no UI for anyone to submit one in the first place.

Message moderation queue

Messages the AI held as uncertain, or that were never moderated at all, are escalated for a human decision — with no screen to make it on.

The gap is worth quantifying honestly when planning: the moderation queue, coach enforcement, disputes and GDPR flows are not stubs — they are complete, tested backend features with alerting, audit logs and state machines behind them. What is missing is purely the admin frontend. That makes this the largest build-vs-usable gap in the product.

Conventions & Gotchas

Don't promise a stakeholder a moderation/dispute/GDPR dashboard — none exists in the frontend today. If someone asks "where do I go to approve a GDPR erasure request," the honest answer is: nowhere in the UI yet — it's handled directly against the backend.

There is no multi-tenancy in Skillars, and there never was. Every coach/player/parent shares the same platform regardless of which club or program they belong to. The old "tenant" feature was never about clubs — it meant an external API partner — and it has now been removed entirely. If a stakeholder asks about "onboarding a club as a tenant," neither the old feature nor the assumed one exists.

The moderation backend has grown while the UI has not. Since this page was last written the backend added a MODERATION_UNRESOLVED alert type — raised when a message's AI moderation verdict never landed and a human must decide — plus an automatic sweeper that escalates such messages after about 30 minutes. These land in the same queue with no screen to read them. The practical consequence: the moderation queue now accumulates items nobody can see in a UI, which is worth stating plainly when discussing launch readiness.
