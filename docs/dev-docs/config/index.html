    Config

    The database-backed key/value store admins use to tune business thresholds, quotas, and per-tier gates without a deploy — with range validation on write and a fail-fast check at boot.

    Business Overview

    The config module is Skillars' single "knobs and dials" table: a flat list of typed key/value rows (main.platform_config) that other modules read at runtime instead of hardcoding a number or a per-tier switch in Java. Product/Ops can change a business rule — a commission rate, a storage quota, a moderation SLA window, an age-tier cutoff — through the admin config editor (src/frontend/src/pages/admin/AdminConfigPage.vue, route /admin/config) rather than filing a code change and waiting for a release.

    The seed data lives in the baseline V139__baseline_seed_data.sql (120 rows; the historical per-feature migrations were squashed into V138/V139), plus later migrations such as V156__reviews_eligibility_config_rework.sql. Four broad categories of value live here:

    • Per-tier feature gates — e.g. coach.tier.scout.video_upload, player.tier.athlete.skills_radar — booleans stored as the strings "true"/"false".
    • Quotas — per-tier storage/bandwidth (coach.tier.academy.storage_quota_gb, video.quota.<tier>.storageBytes, video.quota.<tier>.bandwidthBytesMonthly) and per-type video caps (video.<type>.maxSizeBytes, .maxDurationSeconds).
    • Business thresholds and timers — platform.commission_rate, reliability.strike.visibilityThreshold/suspensionThreshold, disputes.submissionWindowDays, platform.moderation_sla_minutes, platform.message_retention_months, gdpr.export.urlExpiryHours, reviews.minSessionAgeDays/updateCooldownDays, reminder intervals, signed-URL TTLs, batch sizes and lock timeouts.
    • Policy cutoffs — the age-tier boundaries the security module's age-policy logic is built on (security.age-policy.*).

    Only ROLE_ADMIN/ROLE_LTD_ADMIN can read or change a value via ConfigResource. Treat this as a values store, not a schema store: keys are seeded by Flyway, and the API can only update an existing key — with one exception, the unseeded ConfigBounds.HAS_CODE_DEFAULT keys, which a PUT creates. Writes to bounded keys are range-checked, and a bad stored value for a critical key blocks startup outside the dev profile.

    Technical Overview

    Package layout

    Key entities & tables

    EntityTableNotes
    PlatformConfig (extends BaseEntity)main.platform_config key (VARCHAR 255, unique uq_platform_config_key), value (TEXT), value_type (CHECK chk_platform_config_type: STRING/LONG), optional description, updated_at.     Key services

    ClassResponsibility
    ConfigServiceCaches the whole table and serves typed reads: getString/getLong(key) (throw IllegalStateException if missing or non-numeric), getLong(key, default)/getInt(key, default) (WARN + default), getBoundedLong(key, default, min, max)/getBoundedInt(...) (out-of-range → WARN + default), getBoundedInt(BoundedKey) (same, with key, default and range all taken from the ConfigBounds entry; HAS_CODE_DEFAULT keys only), getBoundedLong(key, min, max) (missing still throws; out-of-range is clamped to the nearest bound), getBoolean(key) (missing or non-boolean → false + WARN + config.value.misconfigured metric), getBoolean(key, default), find(key). Write/admin side: updateConfig, findResponse, listForAdmin, invalidate.
    ConfigBoundsStatic registry of BoundedKey(key, min, max, failFast, note, defaultValue): ~34 named keys (pack pause, dispute window, moderation SLA/retries/lock timeout, video lifecycle and playback TTL, timeline/roster windows, GDPR export TTL and erase lock timeout, message retention, batch sizes, review eligibility and moderation-orphan grace, DLQ/outbox attempts, rate-limit TTL, stuck-completion and recap-edit windows) plus generated video.quota.<tier>.* and video.<type>.* keys. ALL is the full list; HAS_CODE_DEFAULT (24 keys) marks keys whose call site has a code default. Also holds MIN_REVIEW_ELIGIBILITY_WINDOW_GAP_DAYS (7), the one definition of the review-window gap. The review keys and the rate-limit TTL are read straight from their BoundedKey; most other call sites still pass their [min, max] literally — for those, change a bound in both places.
    ConfigStartupAssertionApplicationListener<ApplicationReadyEvent>. For every ConfigBounds.ALL key reads the raw stored value and logs ERROR + increments config.value.misconfigured{key,reason} for missing / non-numeric / out-of-range values; also checks two cross-field invariants (reliability.strike.visibilityThreshold ≤ suspensionThreshold; reviews.updateCooldownDays − reviews.minSessionAgeDays ≥ 7) and that every @SchedulerLock in the context has lockAtLeastFor ≤ lockAtMostFor. Any failFast violation throws AppSetupException and blocks boot — except under the dev profile, where it only logs.
    ConfigMapperMapStruct mapper, PlatformConfig → ConfigValueResponse.

    REST endpoints

    MethodPathPurposeAuth / Role
    GET/api/config/valuesAdmin editor list: every stored row plus every unseeded HAS_CODE_DEFAULT key, each with its ConfigBounds range, sorted by key. Reads the table directly, not the cache.ROLE_ADMIN / ROLE_LTD_ADMIN

    PUT/api/config/values/{key}Update a value (or create an unseeded HAS_CODE_DEFAULT key); 404 for any other unknown key, 400 for a non-numeric/out-of-range bounded value or a review-window pair violationROLE_ADMIN / ROLE_LTD_ADMIN

    There is no delete endpoint, and keys outside HAS_CODE_DEFAULT can only be added by a migration.

    Value types

    ConfigValueType has exactly two members:

    • STRING — free text, including booleans ("true"/"false") and decimals like the commission rate "0.08".
    • LONG — whole numbers, parsed with Long.parseLong(value.trim()). Rows created by the HAS_CODE_DEFAULT upsert path are always LONG.

    value_type is descriptive metadata (and a DB CHECK) — the typed getters do not branch on it; the method you call decides how the string is parsed.

    Boundary vs. infrastructure.feature

    Skillars has a second, unrelated toggle mechanism: infrastructure.feature.FeatureToggleService (implemented by PropertiesFeatureToggleService), gating a small fixed enum of coarse, whole-platform switches (AppFeature.ARACHNID_ENABLED, VIDEOINTEL_ENABLED). Those are Spring @ConfigurationProperties (FeatureProperties) — changing one requires an env/config change and a restart, and there is no admin API. platform_config is for business-tunable values (tier gates, quotas, thresholds) Ops can change live. A true environment-level on/off switch belongs in AppFeature; a business rule an admin might tune without redeploying belongs in platform_config. Static settings such as thread-pool sizes stay in application.yaml because they cannot change at runtime.

    Key Flows

    Admin updates a config value

    sequenceDiagram
  participant A as Admin (AdminConfigPage)
  participant CR as ConfigResource
  participant CS as ConfigService
  participant DB as main.platform_config
  participant Other as Any reader on this node

  A->>CR: PUT /api/config/values/disputes.submissionWindowDays {"value":"21"}
  CR->>CS: updateConfig(key, "21")
  CS->>DB: findByKey(key)
  alt absent and not in HAS_CODE_DEFAULT
    CS-->>CR: ResourceNotFoundException (404)
  end
  CS->>CS: rejectOutOfRange (ConfigBounds, 400)
  CS->>CS: rejectReviewEligibilityWindowOrdering (reads partner key from DB, 400)
  alt row exists
    CS->>DB: setValue, setUpdatedAt, save
  else unseeded HAS_CODE_DEFAULT key
    CS->>DB: insert LONG row (unique-key race: re-read winner, apply value)
  end
  CS->>CS: invalidate() bumps invalidationEpoch (after commit if a TX is active)
  CS-->>A: 200 ConfigValueResponse
  Other->>CS: getBoundedLong(...)
  CS->>CS: must-be-fresh: wait for or run findAll() reload
  CS-->>Other: 21

    updateConfig is not @Transactional; it writes through to Postgres and then calls invalidate(), which only bumps an in-memory invalidationEpoch on the node that handled the request. The next read on that node reloads every row. Every other node keeps serving its cached value until its own TTL expires (app.config.cache-ttl-seconds, default 300s). A direct SQL edit or migration invalidates nothing, on any node — see docs/deployment/runbook.md, "Config change appears to have no effect".

    Cache load and refresh

    sequenceDiagram
  participant Boot as Spring context
  participant CS as ConfigService
  participant DB as main.platform_config
  participant Sched as scheduledRefresh
  participant R as Reader thread

  Boot->>CS: @PostConstruct init(), refreshCache()
  CS->>DB: findAll()
  CS->>CS: cache = Map.copyOf(rows), loadedEpoch = epoch seen before the read
  loop fixedDelay = cacheTtlSeconds
    Sched->>CS: scheduledRefresh()
    CS->>CS: skip if not stale, or if refreshLock.tryLock() fails
  end
  R->>CS: any getter, ensureFresh()
  alt stale by TTL only
    CS->>CS: tryLock once, on failure serve cached snapshot
  else invalidated or never loaded (must be fresh)
    CS->>CS: tryLock(4s), rethrow a recent leader failure as ConfigRefreshException
  end

    The cache is a single volatile reference to an immutable map swapped atomically by load(), so a reader can never see a mix of old and new values (skillars-deferred-163). Refresh is single-flight on a ReentrantLock (skillars-deferred-161): only one thread runs findAll(). A reader that is stale only by TTL never waits — it serves the snapshot, and a TTL-only load failure is logged at WARN and swallowed. A reader after invalidate() (or before the first load) must see fresh data: it waits up to 4s for the lock; if the leader's load failed within the last 15s, waiters rethrow that failure as ConfigRefreshException (an IllegalStateException, so HTTP 500) instead of each queueing their own findAll() behind Hikari's 30s connection timeout. Each load stamps the epoch it observed before reading, so an invalidate() landing mid-load is not lost.

    Startup validation

    On ApplicationReadyEvent, ConfigStartupAssertion validates every ConfigBounds.ALL key against the raw stored value. Absent/blank is fine for a HAS_CODE_DEFAULT key (DEBUG only); for any other key it is an ERROR, as is a non-numeric or out-of-range value. If any failFast key (e.g. pack.pause.maxDays, disputes.submissionWindowDays, platform.moderation_sla_minutes, gdpr.export.urlExpiryHours, platform.message_retention_months, booking.batch.maxSize), a cross-field pair or a @SchedulerLock ordering is violated, boot fails with AppSetupException (non-dev only). Schedulers registered before ApplicationReadyEvent can tick once against the clamped value before the refusal.

    Conventions & Gotchas

    Cache staleness is per-node, not cluster-wide. A PUT invalidates only the node that served it, and there is no fleet-wide broadcast. Other nodes (and every node after a direct DB edit) lag by up to app.config.cache-ttl-seconds. If every node must be correct now, wait out the TTL or restart. The TTL is deliberately left at 300s — the table changes a few times a year.

    A new bounded key touches three places. Seed it in a migration (unless it belongs in HAS_CODE_DEFAULT), add a BoundedKey to ConfigBounds and to ALL (and to HAS_CODE_DEFAULT if the call site has a default), and read it with getBoundedInt(BoundedKey) (or pass the entry's own key()/defaultValue()/min()/max()) rather than retyping the range. Without the ConfigBounds entry the PUT path accepts any string and the boot check never sees the key. Pick failFast only when a bad value loses data or halts a core flow — it blocks production boot.

    Cross-key checks must read the database, not the cache. rejectReviewEligibilityWindowOrdering reads the partner key with configRepository.findByKey (readStoredBoundedInt): with a cached read, two PUTs landing on different nodes inside the TTL could each pass and together commit a pair that ConfigStartupAssertion then refuses to boot with. Both guards read the 7-day gap from ConfigBounds.MIN_REVIEW_ELIGIBILITY_WINDOW_GAP_DAYS, and reviews.minSessionAgeDays's max (358) is derived from it.

    Pick the getter by failure mode. 1-arg getString/getLong throw IllegalStateException on a missing key (the "operator must set this" contract); getBoundedLong(key, min, max) keeps that but clamps out-of-range values; the defaulted variants never throw. Use a bounded getter for anything that drives scheduler timing or business thresholds. getBoolean(key) returns false for a missing key, so a mistyped feature-gate key silently disables the feature — watch the config.value.misconfigured metric.

    Don't run must-be-fresh reads inside long transactions. The reload runs in the caller's transaction (deliberately not REQUIRES_NEW, to avoid holding two connections). A failed load inside a transaction has already marked it rollback-only, and invalidate() called inside a transaction is deferred to afterCommit.

    Don't confuse this with infrastructure.feature. Coarse platform switches (AppFeature) are property-driven and need a restart. Per-tier gates, quotas and business thresholds belong in platform_config. See the Boundary section above.
