Config

The database-backed key/value store admins use to tune business thresholds, quotas, and per-tier gates without a deploy.

Business Overview

The config module is Skillars' single "knobs and dials" table: a flat list of typed key/value rows (platform_config) that other modules read at runtime instead of hardcoding a number or a per-tier switch in Java. It exists so that Product/Ops can change a business rule — a commission rate, a storage quota, a moderation SLA window, an age-tier cutoff — by editing one row through an admin-only REST endpoint, rather than filing a code change and waiting for a release.

Looking at the seed data (Flyway migrations V20, V25, V42, V57) shows four broad categories of value living here:

  • Per-tier feature gates — e.g. coach.tier.scout.video_upload, player.tier.athlete.skills_radar — booleans (stored as the strings "true"/"false") that decide whether a given Coach or Player subscription tier can use a capability.
  • Quotas — per-tier storage and bandwidth limits in GB (coach.tier.academy.storage_quota_gb, player.tier.pro.bandwidth_quota_gb), and drill-video size/duration caps.
  • Business thresholds and timers — platform.commission_rate, platform.reliability_strike_expiry_days, platform.strike_threshold.auto_suspension, platform.moderation_sla_minutes, platform.message_retention_months, reminder intervals, signed-URL TTLs.
  • Policy cutoffs — the U10/young-teen/teen max-age boundaries the security module's age-tier logic is built on (security.age-policy.*).

Only ROLE_ADMIN/ROLE_LTD_ADMIN accounts can read or change a value, via ConfigResource. There is no self-service UI referenced in this backend module — whoever exposes an admin console for this simply calls GET/PUT /api/config/values/{key}. New engineers should treat this as a values store, not a schema store: keys are pre-seeded by Flyway migrations, and the API can only update an existing key's value — it cannot create or delete keys.

Technical Overview

Package layout

PackagePurpose
apiConfigResource — the only entry point into this module, two admin-only endpoints.
contractPublic surface: ConfigValueType enum, ConfigValueResponse DTO, UpdateConfigRequest DTO.
configConfigProperties (@ConfigurationProperties(prefix = "app.config"), currently just cacheTtlSeconds, default 300) and ConfigModuleConfig which registers it.
serviceConfigService — the module's real public API (injected directly by ~40 services across the codebase) and ConfigMapper (MapStruct entity→DTO mapping).
repoPlatformConfig JPA entity and PlatformConfigRepository (Spring Data, one derived finder: findByKey).

Key entities & tables

EntityTableNotes
PlatformConfig (extends BaseEntity)main.platform_config key (unique, VARCHAR 255), value (TEXT), value_type (enum, CHECK-constrained to STRING/LONG), optional description, updated_at. Seeded almost entirely via Flyway (V20, V25, V42, V57 and others) — there is no code path that inserts a brand-new key at runtime.

Key services

ServiceResponsibility
ConfigServiceLoads the entire platform_config table into an in-memory ConcurrentHashMap cache and serves typed reads off it: getString, getLong, getLong(key, default), getInt(key, default), getBoundedLong(key, default, min, max) (rejects out-of-range values, logs a warning, falls back to default), getBoolean/getBoolean(key, default), and find(key) returning an Optional<String>. Also owns updateConfig(key, value) (used by the admin endpoint) and invalidate().
ConfigMapperMapStruct mapper, PlatformConfig → ConfigValueResponse.

REST endpoints

MethodPathPurposeAuth / Role
GET/api/config/values/{key}Fetch one config entry (current value, type, last-updated timestamp)ROLE_ADMIN / ROLE_LTD_ADMIN
PUT/api/config/values/{key}Update an existing config entry's value (must already exist — 404 otherwise)ROLE_ADMIN / ROLE_LTD_ADMIN

There is no list/search endpoint and no create/delete endpoint — keys are enumerated only by reading the Flyway migrations or the database directly.

Value types

ConfigValueType has exactly two members:

  • STRING — free text, including booleans stored as the literal strings "true"/"false" and decimals like the commission rate "0.08".
  • LONG — whole numbers (quotas, day/hour/minute counts, strike thresholds), parsed via Long.parseLong.

value_type is descriptive metadata on the row (and a DB CHECK constraint) — ConfigService's typed getters don't branch on it; callers simply call getLong/getString/getBoolean for the key they expect and get a parse failure or warning-plus-default if the stored value doesn't match.

Boundary vs. infrastructure.feature

Skillars has a second, unrelated toggle mechanism: infrastructure.feature.FeatureToggleService (implemented by PropertiesFeatureToggleService), gating a small fixed enum of coarse, whole-platform switches (AppFeature.PAYMENTS, INVOICING, ARACHNID_ENABLED, VIDEOINTEL_ENABLED). Those are backed by Spring @ConfigurationProperties (FeatureProperties), i.e. plain application properties/environment variables validated at startup — changing one requires a config-map/env change and a restart (or at minimum a re-deploy), and there is no admin API for them. platform.config, by contrast, is a DB-backed, per-key store meant for business-tunable values (tier gates, quotas, thresholds) that Ops can change live through ConfigResource without touching the deployment at all. If you're adding a true environment-level on/off switch (e.g. "is the payment provider integration enabled in this environment"), it belongs in AppFeature; if you're adding a business rule an admin might reasonably want to tune per environment without redeploying, it belongs in platform_config.

Key Flows

Admin updates a config value and it takes effect

sequenceDiagram
  participant A as Admin
  participant CR as ConfigResource
  participant CS as ConfigService
  participant DB as platform_config
  participant Other as Any other module (e.g. BookingReminderScheduler)

  A->>CR: PUT /api/config/values/platform.reminder_interval_primary_hours {"value":"12"}
  CR->>CS: updateConfig(key, "12")
  CS->>DB: findByKey(key)
  alt key not found
    CS-->>CR: throw ResourceNotFoundException (404)
  end
  CS->>DB: entity.setValue("12"), setUpdatedAt(now), save
  CS->>CS: invalidate() -- lastRefreshed = Instant.MIN (this JVM only)
  CS-->>CR: ConfigValueResponse
  CR-->>A: 200 OK

  Note over CS: next read on this instance forces refreshCache()
  Other->>CS: getInt("platform.reminder_interval_primary_hours", 24)
  CS->>CS: ensureFresh() sees stale flag, reloads all rows from DB
  CS-->>Other: 12

updateConfig writes straight through to Postgres and then calls invalidate(), which just resets lastRefreshed to Instant.MIN on the JVM handling the request — it does not proactively push the new value anywhere. The next call into ConfigService on that same instance triggers a full refreshCache() (reloads every row, not just the changed key), so the change is effectively immediate for that instance. Any other application instance in the cluster keeps serving its old cached value until its own @Scheduled refresh fires (interval = app.config.cache-ttl-seconds, default 300s), so a multi-instance deployment can see up to five minutes of skew between nodes.

Startup and periodic cache refresh

sequenceDiagram
  participant Boot as Spring context startup
  participant CS as ConfigService
  participant DB as platform_config
  participant Sched as @Scheduled refresh

  Boot->>CS: @PostConstruct init()
  CS->>DB: findAll()
  CS->>CS: populate ConcurrentHashMap cache, lastRefreshed = now

  loop every cacheTtlSeconds (default 300s)
    Sched->>CS: scheduledRefresh()
    CS->>DB: findAll()
    CS->>CS: cache.putAll(new); cache.keySet().retainAll(new.keySet())
  end

The cache is populated once at startup and refreshed on a fixed delay driven by the same app.config.cache-ttl-seconds property that governs staleness checks in ensureFresh(). The refresh uses put-all-then-retain-all so a reader never sees an empty cache mid-refresh, and a synchronized double-check inside refreshCache() prevents two threads from both re-querying the database when several callers race a cold cache at once.

Conventions & Gotchas

Cache staleness is per-instance, not cluster-wide. An admin's PUT only invalidates the cache on the instance that served the request. In a multi-instance deployment, other instances keep the old value for up to app.config.cache-ttl-seconds (default 300s / 5 minutes). Don't assume a config change is instantly visible everywhere — for anything latency-sensitive, lower the TTL or plan around the skew window.

The API can only update, never create. ConfigService.updateConfig calls findByKey(...).orElseThrow(ResourceNotFoundException) — there is no path to insert a brand-new key through ConfigResource. Every key must first be seeded by a Flyway migration (V20__platform_config.sql and several later migrations add more keys). If a feature needs a new config key, that's a migration, not just an API call.

Typed getters trust the caller, not value_type. getLong/getBoolean/etc. parse the stored string directly based on which method you call; the value_type column is metadata (and a DB CHECK constraint) rather than something ConfigService branches on at read time. Calling getLong on a key whose value isn't numeric throws IllegalStateException (or, for the defaulted variants, logs a warning and silently returns the default) — use getLong(key, default) or getBoundedLong(key, default, min, max) for anything that drives scheduler timing or business thresholds so a bad value degrades gracefully instead of throwing.

Don't confuse this with infrastructure.feature. Coarse platform on/off switches (AppFeature: PAYMENTS, INVOICING, ARACHNID_ENABLED, VIDEOINTEL_ENABLED) are property-driven and need a restart/redeploy. Per-tier gates, quotas, and business thresholds belong here in platform_config and are admin-tunable at runtime. See the Boundary section above before adding a new toggle to either.
