Tenant

Admin-managed API tenants — external systems that authenticate with an API key and receive signed webhooks; not a per-club data-partitioning scheme.

Business Overview

It is tempting to assume "tenant" means a club, school, or franchise that owns its own coaches and players — that is not what this module does. There is no tenant_id column anywhere on Coach, Player, Booking, or any other domain entity, and nothing in marketplace, booking, session, or payment scopes queries by tenant. Instead, a Tenant here represents an external system/business partner that is granted machine-to-machine access to a future/limited /v1/** API surface — think a third-party integrator calling into Skillars with an API key, and Skillars calling back out to that partner's webhook URL when relevant events happen. It is a B2B integration-credentials module, not a multi-club SaaS partitioning layer.

API key issuance Key rotation Webhook config Tenant lifecycle

Only Admins manage tenants — every endpoint in TenantAdminResource is gated by SecurityConstants.HAS_ADMIN_ROLE and lives under /v1/admin/tenants. There is no self-service tenant onboarding UI; an admin creates the tenant record, hands the one-time-shown raw API key to the partner out of band, and manages its lifecycle (renaming, email/webhook updates, suspension, key rotation) from the admin console.

Key business rules embedded in the code:

  • Tenant names must be unique (case-insensitive) — TenantService.createTenant rejects a duplicate name before anything is persisted.
  • A tenant can hold at most one ACTIVE API key per (tenant, environment) pair (PROD/DEV/SANDBOX) at a time — generating or reactivating a key while one is already active is rejected.
  • Suspending a tenant (TENT-04) atomically revokes every active and rotated key for that tenant — a suspended tenant cannot authenticate via any leftover grace-period key.
  • Reactivating a suspended tenant (TENT-07) always issues a brand-new PROD key, since the old one was revoked on suspension.
  • The raw API key and a regenerated webhook secret are shown exactly once, at creation/rotation/regeneration time — they are never stored in plaintext and can never be retrieved again after that response.

Key services

ServiceOrchestrates
TenantServiceTenant lifecycle: create (name-uniqueness check, UUID tenantRef, derived key prefix, initial webhook secret, first API key via ApiKeyService), update name/email/webhook URL, suspend (cascades to revoking all keys), reactivate (issues a new PROD key), regenerate webhook secret. Publishes a lifecycle event after every mutation.
TenantQueryServiceRead-only projections for the admin console: paginated/status-filtered tenant list, full tenant detail (with key summaries, but never the webhook secret), and a dedicated webhook-secret lookup.
ApiKeyServiceThe credential engine: generates and SHA-256-hashes new keys (rejecting a duplicate ACTIVE key per tenant+environment), authenticates a raw key against the hash with a 24-hour rotation grace window, rotates a key (revoking any prior ROTATED key for the same tenant+environment to prevent overlapping grace periods), revokes/reactivates keys, and bulk-expires stale ROTATED keys past the grace window.

Tenant isolation: request-scoped, not row-level

This module does not enforce row-level tenant isolation across domain tables, because it does not model per-club data ownership. What it does enforce is request-scoped tenant identity for API-key authenticated requests:

  • infrastructure.web.ApiKeyAuthenticationFilter is a non-@Component servlet filter, wired only via addFilterBefore in infrastructure.web.TenantSecurityConfig's @Order(1) security chain, scoped to /v1/** excluding /v1/account/** and /v1/admin/** (those stay on the existing JWT chain). It reads the X-Api-Key header, calls ApiKeyService.authenticate, rejects suspended tenants with 403 before any SecurityContext is populated, then sets a TenantPrincipal (role ROLE_TENANT, username = tenantRef).
  • infrastructure.security.TenantContext is a ThreadLocal<String> holding the current tenantRef for the life of the request, set by the filter and always cleared in a finally block (using remove(), not set(null), to avoid leaking state across pooled servlet threads).
  • infrastructure.threadpool.TenantContextTaskDecorator propagates that same TenantContext value onto async worker threads (mirroring the existing MDC decorator pattern), so tenant identity survives an @Async hop.
  • TenantContext.get() is also read by infrastructure.web.LoggingFilter to attach tenantId to structured request-end logs (null/absent for ordinary JWT-authenticated requests).
  • Depends on infrastructure.persistence (AbstractAuditingEntity base class), infrastructure.security (SecurityConstants, TenantContext), infrastructure.web (the filter/security-config classes above), and infrastructure.util.ClockProvider (testable time source for event timestamps).
  • As of this writing no other /v1/** resource endpoints exist yet besides /v1/account/** and /v1/admin/** — the API-key chain currently authenticates requests but there is no partner-facing business endpoint mounted under it. Treat this as a forward-looking integration surface.

Key Flows

Provisioning a new tenant

sequenceDiagram
  participant Admin as Admin (console)
  participant Api as TenantAdminResource
  participant Svc as TenantService
  participant KeySvc as ApiKeyService
  participant Repo as TenantRepository
  participant Listener as TenantLifecycleEmailListener
  Admin->>Api: POST /v1/admin/tenants {name, environment, email, webhookUrl}
  Api->>Svc: createTenant(name, environment, email, webhookUrl)
  Svc->>Repo: existsByNameIgnoreCase(name)
  Repo-->>Svc: false (unique)
  Svc->>Svc: build Tenant(tenantRef=UUID, keyPrefix=derived, webhookSecret=UUID)
  Svc->>Repo: save(tenant)
  Svc->>KeySvc: generateAndStore(tenant, environment)
  KeySvc-->>Svc: ApiKeyAndRawKey(entity, rawKey)
  Svc-->>Listener: publish TenantCreatedEvent
  Listener-->>Listener: email notification-email only (tenant has no confirmed email yet)
  Svc-->>Api: TenantCreationResult(tenant, key, rawKey)
  Api-->>Admin: 201 {tenant, apiKey.rawKey} — shown once

An admin submits a name, initial environment, and optional email/webhook URL. TenantService rejects duplicate names, then builds the Tenant row with a random UUID tenantRef (used later as the security-principal identity), a name-derived key prefix, and a freshly generated webhook secret. It saves the tenant, delegates to ApiKeyService to mint the first API key (SHA-256 hash stored, raw value returned only in this response), and publishes TenantCreatedEvent — routed only to the internal notification address, since the tenant itself has no verified email yet. The raw API key is returned once in the 201 response body and can never be retrieved again; if it is lost, the only recovery is generating a new key or rotating.

Tenant-scoped request authentication

sequenceDiagram
  participant Partner as External partner system
  participant Filter as ApiKeyAuthenticationFilter
  participant KeySvc as ApiKeyService
  participant Ctx as TenantContext (ThreadLocal)
  participant Sec as SecurityContextHolder
  Partner->>Filter: request to /v1/** with X-Api-Key header
  Filter->>KeySvc: authenticate(rawKey)
  KeySvc->>KeySvc: sha256Hex(rawKey)
  KeySvc-->>Filter: TenantApiKey (ACTIVE, or ROTATED within 24h grace)
  alt tenant is SUSPENDED
    Filter-->>Partner: 403 Forbidden
  else tenant is ACTIVE
    Filter->>Ctx: TenantContext.set(tenantRef)
    Filter->>Sec: setAuthentication(TenantPrincipal, ROLE_TENANT)
    Filter->>Filter: chain.doFilter(...)
    Filter->>Ctx: TenantContext.clear() (finally block)
    Filter->>Sec: clearContext() (finally block)
  end

Every request under /v1/** (other than /v1/account/** and /v1/admin/**, which stay on the JWT chain) is intercepted by ApiKeyAuthenticationFilter before Spring Security's normal authentication filter runs. The raw key is hashed and looked up with a 24-hour grace window so a just-rotated key still works briefly. A suspended tenant is rejected with 403 before any security context is populated. On success the filter sets both a request-scoped TenantContext (for logging/async propagation) and a TenantPrincipal with ROLE_TENANT in the SecurityContextHolder. Both are unconditionally cleared in a finally block so servlet thread pooling never leaks one tenant's identity into the next request.

Conventions & Gotchas

Do not confuse this "tenant" with per-club/organization multi-tenancy. A new engineer's first instinct is to look for a tenant_id filter on marketplace/booking/session queries — there isn't one. Coaches and Players are not partitioned by tenant anywhere in the schema. If a future feature needs to scope data to a club/organization, that is a different concept and should not be bolted onto this module without redesigning it.

TenantContext must always be cleared, including on the async hop. It is a raw ThreadLocal on pooled servlet and executor threads. ApiKeyAuthenticationFilter clears it with remove() in a finally block, and TenantContextTaskDecorator mirrors that for @Async work. Any new code path that reads or sets TenantContext directly must follow the same set/finally-clear pattern or risk leaking one tenant's identity into a later, unrelated request handled by the same thread.

Raw keys and webhook secrets are shown exactly once. Only the SHA-256 hash of an API key is persisted (TenantApiKey.keyHash); the raw value is returned in the create/generate/rotate response and then gone forever. The webhook secret is stored in plaintext (needed to compute HMAC signatures) but is only ever surfaced through the dedicated GET .../webhook-secret endpoint — it is deliberately omitted from TenantDetailDto and from every published domain event.

Key rotation is grace-windowed, and overlapping grace periods are prevented on purpose. Rotating a key flips it to ROTATED with a rotatedAt timestamp; it keeps authenticating for 24 hours (ApiKeyService.GRACE_PERIOD) before the scheduled RotatedKeyCleanupJob flips it to REVOKED. Rotating again before the previous grace period ends immediately revokes that still-in-grace key rather than letting two old keys work simultaneously — don't "fix" this by removing the findRotatedKeyByTenantIdAndEnvironment revoke step.
