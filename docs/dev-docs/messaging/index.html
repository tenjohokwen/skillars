Messaging

In-app conversations between coaches, parents, and players — gated by an active booking, moderated by an LLM before delivery, and age-policy-aware so minors are never left unsupervised.

Business Overview

Skillars lets coaches and families coordinate around a session — scheduling changes, drill feedback, encouragement — without exchanging personal contact details. The messaging module is the in-app chat that makes this possible while keeping a parent in the loop whenever the player is a minor. A conversation is always a triangle: a coach, a player, and that player's parent (even when the parent never sends a message, they are a silent oversight party on the thread).

A conversation cannot be started out of thin air. MessagingService.initiateConversation() requires an existing confirmed (or completed) booking between the coach and the player (BookingRepository.existsByCoachIdAndPlayerIdAndStatusIn(...)) — otherwise the request fails with NO_BOOKING_RELATIONSHIP. This is the module's core anti-abuse rule: coaches cannot cold-message players or parents they have never coached.

Who is allowed to talk to whom is governed by AgeMessagingPolicy, derived from AgePolicyService.getMessagingPolicy(playerId) in the security module's age-tier rules:

PolicyAge tierPlayer can send?Parent role
PROHIBITEDUnder 10NoPrimary participant (parent messages on player's behalf)
PARENT_MANAGED10–12NoPrimary participant
SUPERVISED13–17YesOversight — can read, cannot send
UNRESTRICTEDAdult playerYesExcluded entirely — parent has no access

Every message is written as PENDING, sent to a moderation service, and only becomes visible once approved. Any party can report a message or an entire conversation; reporting a conversation immediately flips it to BLOCKED for everyone, and reporting a message puts that single message UNDER_REVIEW so it is hidden pending admin review. Messages older than a configurable retention window (default 24 months) are purged nightly unless they are attached to an open safety report — the platform intentionally keeps evidence of anything under active dispute.

Key entities & tables

EntityTable (schema)Notes
Conversationmessaging.conversationsOne row per (coach, player) pair — unique constraint enforced by catching DataIntegrityViolationException on concurrent create. Tracks status (ACTIVE/ARCHIVED/BLOCKED) and a per-role *_last_read_at timestamp used for unread counts.
Messagemessaging.messagesBelongs to a conversation; carries moderationStatus (PENDING/APPROVED/BLOCKED/UNDER_REVIEW), a nullable deliveredAt, and a soft-delete deletedAt. Content is TEXT, capped at 2000 chars by service-level validation (no @Size on the entity).

ConversationReportmessaging.conversation_reportsSame shape as MessageReport but at the conversation level; creating one immediately blocks the conversation.

Dependency-wise, messaging leans on booking (to gate conversation creation on a real relationship), marketplace (CoachProfileRepository for identity/display name resolution), security (PlayerProfileRepository, AgePolicyService, SecurityUtil, Principal), config (ConfigService for the retention window), and infrastructure.gemini for LLM moderation. Notably it does not use infrastructure.sanitizer anywhere — content safety is delegated entirely to the Gemini verdict, not to any HTML/XSS-style input sanitization.

Key Flows

Sending a message through moderation

sequenceDiagram
  participant Sender
  participant MessagingResource
  participant MessagingService
  participant DB as messages table
  participant Moderation as GeminiModerationService
  participant Gemini as GeminiClient (LLM)
  participant Applier as ModerationResultApplier
  participant SSE as MessagingEmitterRegistry
  participant Recipient

  Sender->>MessagingResource: POST /conversations/{id}/messages
  MessagingResource->>MessagingService: sendMessage(conversationId, content, senderId, role)
  MessagingService->>MessagingService: validate length, verify party, check BLOCKED, check age policy
  MessagingService->>DB: save Message(status=PENDING) + commit
  MessagingService->>Moderation: moderate(messageId, content)
  Moderation->>Gemini: evaluate(prompt with delimited content)
  Gemini-->>Moderation: verdict (SAFE / UNSAFE / UNCERTAIN)
  Moderation->>Applier: applyResult(messageId, verdict)
  Applier->>DB: update moderationStatus (+ deliveredAt if SAFE)
  Applier->>SSE: after commit, emit NEW_MESSAGE or MESSAGE_BLOCKED
  SSE-->>Recipient: push event (if subscribed)
  MessagingService-->>MessagingResource: MessageDto (content hidden if BLOCKED/UNDER_REVIEW)
  MessagingResource-->>Sender: 202 Accepted

The message row is committed as PENDING before moderation even runs, so a crash mid-moderation never loses the message — it just stays pending. Moderation itself runs synchronously in the request thread (not queued), calling out to Gemini with the raw content wrapped between fixed delimiter markers to reduce prompt-injection risk. The response DTO always hides content when the status is BLOCKED or UNDER_REVIEW, so a blocked message is never leaked back to either party. Live delivery uses an in-process SSE emitter map, and the push is deliberately deferred to afterCommit() so a client never receives a notification for a message that a rollback later erases.

Reporting a message and the parental oversight view

sequenceDiagram
  participant Reporter
  participant MessagingResource
  participant MessagingReportService
  participant DB as message_reports / messages
  participant EventBus as ApplicationEventPublisher
  participant AdminListener as AdminAlertEventListener
  participant Parent

  Reporter->>MessagingResource: POST /conversations/{id}/messages/{msgId}/report
  MessagingResource->>MessagingReportService: reportMessage(conv, msg, reporter, role, reason, details)
  MessagingReportService->>MessagingReportService: verify reporter is a party
  MessagingReportService->>DB: check not already reported by this user
  MessagingReportService->>DB: set Message.moderationStatus = UNDER_REVIEW
  MessagingReportService->>DB: save MessageReport(status=OPEN)
  MessagingReportService->>EventBus: publish MessageReportedEvent
  EventBus->>AdminListener: onMessageReported(event)
  MessagingReportService-->>MessagingResource: ReportResponse(reportId)

  Parent->>MessagingResource: GET /players/{playerId}/conversations
  MessagingResource->>MessagingReportService: (via MessagingService) verify parent owns player + age policy allows oversight
  MessagingResource-->>Parent: ALL conversations for player, including BLOCKED

Reporting a single message hides it (UNDER_REVIEW) without touching the rest of the conversation, while reporting the whole conversation is more drastic — it immediately sets the conversation to BLOCKED, which stops all future sends for both sides until an admin resolves the report. Both report types are deduplicated per (item, reporter) pair. The parental oversight endpoints are a distinct read path: they deliberately bypass the "hide BLOCKED conversations" filter used elsewhere and never touch the read-timestamp columns, since they exist purely for safety visibility, not for participating in the chat.

Conventions & Gotchas

No sanitizer dependency. Unlike other user-generated-content paths in the platform, messaging content is never passed through infrastructure.sanitizer. Safety filtering is 100% delegated to the Gemini moderation verdict (SAFE/UNSAFE/UNCERTAIN). If Gemini is unreachable or misconfigured and the deployment falls back to PassThroughModerationService, every message is marked SAFE with no content inspection at all — treat that fallback as dev/local-only, never enable it in an environment where real minors are messaging.

SSE emitters are in-memory and per-instance. MessagingEmitterRegistry keeps its userId → SseEmitter map in a local ConcurrentHashMap. Behind a load balancer with multiple app instances, a user's live push only works if their SSE connection and the message-sending request land on the same instance — there is no cross-instance fan-out (e.g. via Redis pub/sub). Don't assume delivery is guaranteed; clients must still poll/reconcile via the paginated GET endpoint.

Age policy drives almost every branch. AgeMessagingPolicy (derived from AgePolicyService.getMessagingPolicy) governs who can initiate, who can send, whose name is shown to whom, and whether a conversation shows up in a player's own list at all. When adding a new messaging feature, always ask "what does this do under PROHIBITED / PARENT_MANAGED / SUPERVISED / UNRESTRICTED?" rather than assuming a simple two-party model.

Retention deletes are hard deletes, gated by open reports. MessageRetentionScheduler runs nightly and permanently removes messages/conversations older than platform.message_retention_months (default 24) — but skips anything referenced by an OPEN/UNDER_REVIEW report row, so evidence under active moderation is preserved. There is a separate, unconditional MessageRepository.deleteAllBySenderId() used for GDPR Article 17 erasure requests — that one ignores report status entirely, so a right-to-erasure request will remove a user's messages even if they're the subject of an open report.

Conversations are keyed by (coach, player), not by a chat "thread ID" you create client-side. initiateConversation is idempotent — calling it again for the same coach/player pair returns the existing conversation. Creation races are handled by creating in a REQUIRES_NEW sub-transaction and catching DataIntegrityViolationException to re-query, so don't be surprised to see that pattern when tracing conversation-creation code.
