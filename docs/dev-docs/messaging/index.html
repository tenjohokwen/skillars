    Messaging

    In-app conversations between coaches, parents, and players — gated by a real booking, moderated by an LLM before delivery, and age-policy-aware so minors are never left unsupervised.

    Business Overview

    Skillars lets coaches and families coordinate around a session — scheduling changes, drill feedback, encouragement — without exchanging personal contact details. The messaging module is the in-app chat that makes this possible while keeping a parent in the loop whenever the player is a minor. A conversation is keyed by (coach, player) and carries the player's parent as a third party (conversations.parent_id). For a self-registered adult player there is no parent, so parent_id is nullable.

    A conversation cannot be started out of thin air. MessagingService.initiateConversation() requires a booking between the coach and the player in one of CONFIRMED, UPCOMING, IN_PROGRESS or COMPLETED (BookingRepository.existsByCoachIdAndPlayerIdAndStatusIn(...)) — otherwise it fails with NO_BOOKING_RELATIONSHIP. This is the module's core anti-abuse rule: coaches cannot cold-message players or parents they have never coached. Any of the three parties can start the thread: the coach (who may omit coachId — it defaults to their own profile), the parent who owns the player, or the self-registered player themselves. The call is idempotent and returns the existing thread if there is one.

    Who is allowed to talk to whom is governed by AgeMessagingPolicy, derived from AgePolicyService.getMessagingPolicy(playerId) in the security module's age-tier rules. The policy is evaluated on every call, not stored on the conversation, so a player who has a birthday moves to the next tier straight away (pinned by AgeTierTransitionTest):

    PolicyAge tierPlayer can start / send?In player's own list?Parent roleCoach sees thread as
    PROHIBITEDUnder 10NoNoPrimary participant (messages on the player's behalf)"Parent of {first name}"
    PARENT_MANAGED10–12NoNoPrimary participant"Parent of {first name}"
    SUPERVISED13–17YesYesCan read and send (parentObserver=true in the summary)"{first name} & parent"
    UNRESTRICTEDAdult playerYesYesExcluded: cannot start, send, list or oversee"{first name}"

    Every message is written as PENDING and then moderated synchronously by Gemini in the same request. A SAFE verdict makes it APPROVED and pushes it live; UNSAFE makes it BLOCKED; UNCERTAIN (or a Gemini error) parks it in UNDER_REVIEW for a human. Any party can report a message or a whole conversation. Reporting a conversation flips it to BLOCKED for everyone right away. This is the only "block" action users have. Reporting a message puts that one message UNDER_REVIEW, which hides its content until an admin decides. Messages older than a configurable retention window (default 24 months) are purged nightly, except messages tied to an open safety report: evidence under active review is kept.

    Frontend: src/frontend/src/pages/messaging/MessagingPage.vue (store stores/messaging.store.js, deep link /messaging?conversation=<id>). "Message coach" and "Message player" buttons on the bookings list, coach public profile, coach roster and player detail pages call composables/useStartConversation.js. Admin moderation lives in pages/admin/AdminModerationPage.vue.

    Key entities & tables

    All four tables live in the messaging schema and are defined in the squashed baseline V138__baseline_schema.sql. No later migration touches them. Both config keys are seeded in V139__baseline_seed_data.sql.

    EntityTableNotes
    Conversationmessaging.conversationsOne row per (coach, player), enforced by uq_conversations_coach_player. coach_id is a CoachProfile UUID, player_id a PlayerProfile PK, and parent_id a user id (nullable). Tracks status (ACTIVE/ARCHIVED/BLOCKED; nothing writes ARCHIVED today), last_message_at, and one *_last_read_at column per role, used for unread counts.
    Messagemessaging.messagesCarries sender_id (user id), sender_role, moderation_status (PENDING/APPROVED/BLOCKED/UNDER_REVIEW), a nullable delivered_at (set on APPROVED), and a soft-delete deleted_at. Content is TEXT. sendMessage limits it to 1–2000 code points (no @Size on the entity or request). There is no @Version, on purpose (see gotchas). The FK to conversations has no cascade.
    MessageReportmessaging.message_reportsUnique per (message, reporter) via uq_message_reports_message_reporter. reason is a MessageReportReason (HARASSMENT, INAPPROPRIATE_CONTENT, SPAM, CONTACT_SOLICITATION, OTHER), plus details (≤500) and status (OPEN/UNDER_REVIEW/RESOLVED/DISMISSED) with resolved_at/resolved_by. ON DELETE CASCADE from messages.
    ConversationReportmessaging.conversation_reportsThe same shape at conversation level (uq_conversation_reports_conv_reporter). Creating one blocks the conversation right away.

    Key services

    ServiceOrchestrates
    MessagingServiceConversation lifecycle, sending and listing messages, soft delete, unread counts, parental oversight reads, and the SSE party check. It is class-level @Transactional, but sendMessage is NOT_SUPPORTED so the Gemini call never holds a DB connection. The conversation list is built in a fixed number of queries (SummaryContext: batched age policies, names, latest approved message and unread counts per conversation).
    ConversationCreationHelperPackage-private. Creates a conversation in its own REQUIRES_NEW transaction so that a unique-constraint race can be caught and re-queried cleanly by the caller.
    MessagingReportServiceMessage and conversation reporting: checks the reporter is a party, deduplicates, changes the moderation or conversation status, and publishes MessageReportedEvent / ConversationReportedEvent. It keeps its own copy of verifyIsParty on purpose, because injecting MessagingService would create a circular dependency.
    GeminiModerationServiceThe @Primary ModerationService. Sends the content (truncated to platform.messaging.moderation.gemini.max-input-chars, default 4000, without splitting a surrogate pair) to infrastructure.gemini.GeminiClient, wrapped between ---BEGIN/END USER CONTENT--- delimiters that are first stripped from the input. Any exception becomes UNCERTAIN and also publishes ModerationFailureEvent. The prompt is platform.messaging.moderation.gemini.prompt-template in application.yaml.
    PassThroughModerationServiceNamed bean "passThrough", not primary, that marks everything SAFE. Nothing injects it today. It exists only as an explicit dev or test fallback.
    ModerationResultApplierWrites the verdict under MessageRepository.findByIdForUpdate, and only if the row is still PENDING and not deleted. It resolves the SSE recipient and emits NEW_MESSAGE (to the recipient) or MESSAGE_BLOCKED (to the sender) in afterCommit(). On an UNCERTAIN verdict it publishes MessageHeldForReviewEvent(reason=MODERATION_UNCERTAIN).
    MessagingEmitterRegistryAn in-memory userId → SseEmitter map, with timeout platform.messaging.sse-timeout-ms (default 300000). It sends a : connected comment 200 ms after registering and a heartbeat event every 30 s (@Scheduled, per instance, no ShedLock, which is correct because each instance owns its own emitters).
    MessageRetentionSchedulerRuns daily at 02:00 (ShedLock MessageRetentionScheduler_runRetention, PT30M/PT1M). It bulk-deletes messages older than platform.message_retention_months (bounded 1–600, default 24) that have no OPEN/UNDER_REVIEW report, then publishes MessagesPurgedEvent. Next it deletes conversations past the same cutoff that have no messages left and no open conversation report.
    MessageModerationSweeperRuns every 10 minutes (ShedLock MessageModerationSweeper_sweep, PT20M/PT2M). It moves messages stuck in PENDING for longer than platform.messaging.moderation_orphan_grace_minutes (bounded 5–1440, default 30) to UNDER_REVIEW, up to 500 per run. It publishes MessageHeldForReviewEvent(reason=MODERATION_ORPHAN_SWEPT) and increments the messaging.moderation.swept counter. It is fail-closed (see gotchas).
    AgeMessagingPolicyEnum that maps the security module's MessagingPolicy flags (canMessage/directAllowed/parentVisible) to the four tiers. Its predicates are playerIsBlocked(), parentIsBlocked(), parentHasAccess(), parentIsPrimary() and visibleToPlayer().

    REST endpoints

    Everything is under /api/messaging. Most endpoints accept an optional ?role=PARENT|PLAYER hint (see "Role resolution" in the gotchas). Party authorization is enforced in the service layer, not by @PreAuthorize.

    MethodPathPurposeAuth / Role
    POST/conversationsStart a conversation, or fetch the existing one for this (coach, player) pair, whatever its status, BLOCKED included. Body: {coachId?, playerId}. coachId is optional only for a COACH caller (otherwise 400 messaging.coachIdRequired). playerId is a PlayerProfile id. Returns 200 with a ConversationSummaryDto.Authenticated. The caller must be the coach, the player's parent, or the player themselves.
    GET/conversationsThe caller's non-BLOCKED conversations for the resolved role, newest lastMessageAt first. Parents only see tiers where they have access, and players only see SUPERVISED/UNRESTRICTED threads.Authenticated
    POST/conversations/{conversationId}/messagesSend a message. It is saved PENDING, moderated synchronously, and the final MessageDto is returned with 202 Accepted.Authenticated party allowed by the age tier
    GET/conversations/{conversationId}/messagesPaged history: page (default 0), size (default 20, max 100), newest first (createdAt DESC, id DESC). Soft-deleted rows are excluded. Updates the caller role's *_last_read_at.Authenticated party
    GET/players/{playerId}/conversationsParental oversight: all of the child's conversations, including BLOCKED ones.HAS_PARENT_ROLE, must own the player (403, never 404), tier must not be UNRESTRICTED
    GET/players/{playerId}/conversations/{conversationId}/messagesParental oversight: read-only history. Does not update any last-read timestamp.Same as above
    DELETE/conversations/{conversationId}/messages/{messageId}Soft-delete your own message. Refused while it is UNDER_REVIEW/BLOCKED (moderationPending), and a second delete returns 409 alreadyDeleted.Authenticated, original sender only
    POST/conversations/{conversationId}/messages/{messageId}/reportReport one message ({reason, details}). It becomes UNDER_REVIEW (unless already BLOCKED) and a MessageReport is created. Returns 201.Authenticated party
    POST/conversations/{conversationId}/reportReport the whole conversation. Sets it to BLOCKED right away. Returns 201.Authenticated party
    GET/conversations/{conversationId}/eventsOpens an SSE stream after a party check on this conversation. The emitter is registered per user, so the stream then carries NEW_MESSAGE/MESSAGE_BLOCKED events for all of the user's conversations, and the client routes them by the payload's conversationId.Authenticated party

    ConversationSummaryDto = {conversationId, otherPartyName, otherPartyAvatarUrl (always null), lastMessagePreview (first 60 chars of the latest APPROVED message), lastMessageAt, unreadCount, status, canSend, parentObserver}. canSend is advisory for the UI only and repeats the send gates (not BLOCKED, tier allows the role). sendMessage checks every rule again. MessageDto.content is null when the status is BLOCKED or UNDER_REVIEW.

    Domain events

    EventPublished byConsumed by
    MessageReportedEventMessagingReportService.reportMessage()admin.service.AdminAlertEventListener.onMessageReported creates a MESSAGE_REPORT alert. This is a synchronous @EventListener. The insert itself runs in a nested REQUIRES_NEW transaction, and a duplicate OPEN alert is silently suppressed, but any other failure still propagates and fails the report request.
    ConversationReportedEventMessagingReportService.reportConversation()AdminAlertEventListener.onConversationReported creates a CONVERSATION_REPORT alert (same mechanics).
    ModerationFailureEventGeminiModerationService.moderate() when the Gemini call throwsNo listener anywhere. The event is published and dropped. Admins see the failure through MessageHeldForReviewEvent instead, because a failure maps to UNCERTAIN.
    MessageHeldForReviewEventModerationResultApplier (MODERATION_UNCERTAIN) and MessageModerationSweeper (MODERATION_ORPHAN_SWEPT)AdminAlertEventListener.onMessageHeldForReview (REQUIRES_NEW) creates a MODERATION_UNRESOLVED alert. Both publishers catch the exception if the alert fails.
    MessagesPurgedEventMessageRetentionScheduler, after a delete batch with at least one rowAdminAlertEventListener.onMessagesPurged (REQUIRES_NEW) resolves OPEN alerts that point at hard-deleted messages.

    Both MessageHeldForReviewEvent and MessagesPurgedEvent exist so that messaging never has to import com.softropic.skillars.platform.admin. The dependency runs messaging → (event) → admin. In the other direction, admin reaches into this module's repo directly: AdminMessageService (approve/block a held message, then emit SSE with its own copy of resolveRecipient), AdminConversationService (detail view; unblockConversation sets ACTIVE and resolves every open ConversationReport and the CONVERSATION_REPORT alert), AdminQueueService, GdprExportService and GdprErasureService (MessageRepository.deleteAllBySenderId).

    Outbound dependencies: booking (relationship gate), marketplace (CoachProfileRepository, and PlayerProfileService.getPlayerNamesByPlayerIds for batched names), security (PlayerProfileRepository, AgePolicyService, SecurityUtil, Principal), config (ConfigService for retention and sweep grace), and infrastructure.gemini. Messaging does not use infrastructure.sanitizer. The notification module does not listen to messaging either, so a new message produces no email or in-app notification, only the SSE push.

    Sending a message through moderation

    sequenceDiagram
  participant Sender
  participant MessagingResource
  participant MessagingService
  participant DB as messages table
  participant Moderation as GeminiModerationService
  participant Gemini as GeminiClient (LLM)
  participant Applier as ModerationResultApplier
  participant SSE as MessagingEmitterRegistry
  participant Recipient

  Sender->>MessagingResource: POST /conversations/{id}/messages
  MessagingResource->>MessagingService: sendMessage(conversationId, content, senderId, role)
  Note over MessagingService: NOT_SUPPORTED - no surrounding transaction
  MessagingService->>MessagingService: 1-2000 code points, verifyIsParty, not BLOCKED, age tier
  MessagingService->>DB: TransactionTemplate: re-check BLOCKED, save Message(PENDING), bump lastMessageAt, commit
  MessagingService->>Moderation: moderate(messageId, content)
  Moderation->>Gemini: evaluate(prompt + delimited content)
  Gemini-->>Moderation: SAFE / UNSAFE / UNCERTAIN (exception = UNCERTAIN)
  Moderation->>Applier: applyResult(messageId, verdict)
  Applier->>DB: findByIdForUpdate, write only if still PENDING and not deleted
  Applier->>SSE: afterCommit: NEW_MESSAGE to recipient, or MESSAGE_BLOCKED to sender
  SSE-->>Recipient: push (only if connected to this instance)
  MessagingService->>DB: re-read message
  MessagingService-->>MessagingResource: MessageDto (content null if BLOCKED/UNDER_REVIEW)
  MessagingResource-->>Sender: 202 Accepted

    The message row is committed as PENDING before moderation runs, so a crash mid-moderation never loses the message. MessageModerationSweeper later moves any such row to UNDER_REVIEW. The SSE recipient depends on who sent the message. Messages from a parent or player go to the coach's user id. Messages from the coach go to the parent's user id, except in the UNRESTRICTED tier, where they go to the player's user id (resolved through PlayerProfile.userId, because Conversation.playerId is a profile PK). In the SUPERVISED tier only the parent gets the live push for a coach message; the teen sees it on the next fetch. The push is registered in afterCommit() so a client never hears about a message that a rollback erases.

  AdminListener->>DB: insert AdminAlert(MESSAGE_REPORT)
  MessagingReportService-->>Reporter: 201 {reportId}

  Parent->>MessagingResource: GET /players/{playerId}/conversations

  MessagingService->>MessagingService: owns player (else 403), tier not UNRESTRICTED
  MessagingService-->>Parent: ALL conversations for the player, including BLOCKED

    Reporting a single message hides only that message. Reporting the whole conversation sets it to BLOCKED, which stops all sends for every party and removes it from the normal GET /conversations lists (findActiveBy* excludes BLOCKED) until an admin calls AdminConversationService.unblockConversation. The oversight endpoints are a separate read path. They include BLOCKED threads on purpose and never touch read timestamps, because they exist for safety visibility, not for taking part in the chat. The frontend shows them as a read-only per-child view.

    Conventions & Gotchas

    PENDING content is shown to its sender only. toMessageDto(msg, viewerUserId) hides content for BLOCKED and UNDER_REVIEW for everyone, and for PENDING for everyone except the sender. findByConversationIdAndNotDeleted does not filter on status, so a recipient (or a parent in the oversight view) still gets the row, with content: null and moderationStatus: PENDING, and the frontend renders the "held for review" notice. This covers the Gemini call and a stranded message's up-to-30-minute sweep grace. The SSE path never carried content: it pushes ids only, and NEW_MESSAGE fires only after an APPROVED verdict commits. Unread counts and list previews count only APPROVED rows. (Before fix/content-consistency-and-lost-updates, PENDING content went to every party.)

    No sanitizer, and the fallback is wide open. Messaging content never passes through infrastructure.sanitizer, so safety filtering depends entirely on the Gemini verdict. If someone wires PassThroughModerationService in, every message becomes SAFE without inspection. Never do that where real minors are messaging.

    SSE is in-memory, per instance and one stream per user. MessagingEmitterRegistry keeps a single emitter per user id in a local ConcurrentHashMap. Opening a second stream (a second tab or device) complete()s the first. Behind a load balancer the push only arrives if the stream and the verdict-writing request land on the same instance. There is no cross-instance fan-out, so clients must still reconcile through the paged GET. MessagingResource.subscribeToEvents calls flushBuffer() on purpose: without it Tomcat never commits the 200 and the client hangs.

    Role resolution has a fixed precedence, and ?role= is the escape hatch. MessagingResource.resolveRole honours a PARENT or PLAYER hint only if the caller holds that authority. Otherwise it picks COACH, then PARENT, then PLAYER. A user who is both a parent and a self-registered player cannot reach their own PLAYER threads without ?role=PLAYER. Every "is this caller a party" check (verifyIsParty, duplicated in MessagingReportService) is evaluated for the resolved role only. A new endpoint must accept the hint too, or multi-role users will get 403s.

    Age policy drives almost every branch, and it is evaluated live. AgeMessagingPolicy decides who can start a thread, who can send, which name is shown to whom, and whether a thread appears in a player's list. Because the tier is looked up on every call, a conversation's behaviour changes on the player's birthday with no data change. When you add a feature, check what it does under each of the four tiers. A missing player_profiles row degrades read paths locally ("Unknown Player", row dropped from a list), while write paths (getMessagingPolicy) throw.

    Retention deletes are hard deletes, gated by open reports. MessageRetentionScheduler skips any message referenced by an OPEN/UNDER_REVIEW report row. A conversation is only deleted once it has no messages left, because messages.conversation_id has no cascade. Separately, MessageRepository.deleteAllBySenderId() (GDPR Article 17, called from GdprErasureService) ignores report status, so an erasure request removes a user's messages even when they are the subject of an open report. Because both deletes are unconditional at row level, retention publishes MessagesPurgedEvent so admin can close MODERATION_UNRESOLVED alerts that would otherwise stay OPEN forever. A MESSAGE_REPORT alert is safe, because retention keeps reported messages. platform.message_retention_months is a fail-fast key: ConfigStartupAssertion refuses to boot on a bad stored value.

    MessageModerationSweeper is fail-closed on purpose. Never make it approve a message or retry Gemini. It cannot know why the first verdict never landed. A retry that returned SAFE would deliver content that no successful moderation pass ever saw, possibly to a minor. UNDER_REVIEW is the correct end state: it is what the applier already writes for UNCERTAIN, and it is the only status AdminMessageService.approveMessage/blockMessage act on. The batch is capped at 500 because a moderation outage is exactly what builds a large backlog, and every swept row raises an alert. Soft-deleted PENDING messages are skipped permanently.

    Locking on messages: pessimistic, never @Version. ModerationResultApplier, MessageModerationSweeper, AdminMessageService and softDeleteMessage all re-read the row through findByIdForUpdate and check the state again under the lock. A late Gemini verdict therefore loses to an admin decision, a sweep or a sender's delete. Optimistic locking would turn those harmless interleavings into exceptions. softDeleteMessage authorizes the caller with an unlocked read first (so a stranger cannot pin a row), then takes the lock and calls entityManager.refresh(..., PESSIMISTIC_WRITE). The refresh is required because the JPQL locked query returns the already-managed, stale instance.

    Conversations are keyed by (coach, player). There is no client-generated thread id. initiateConversation is idempotent and returns the existing row whatever its status, so the client must render a BLOCKED thread as read-only (canSend=false). Creation races are handled with a REQUIRES_NEW insert that catches DataIntegrityViolationException and re-queries.
