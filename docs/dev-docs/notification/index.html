    Notification

    The platform's user-notification engine: it turns domain events from every other module into templated, retried, and auditable emails, mirrors user-facing ones into an in-app inbox, enforces per-category email opt-out with one-click unsubscribe, and runs a DB-configurable operational alerting system.

    Business Overview

    Skillars is a multi-sided marketplace (Players/Parents, Coaches, Admins), and almost every meaningful state change — a booking request, a declined reschedule, a session pack about to expire, a flagged video — needs to reach a human. Rather than each module formatting and sending its own mail, every other module publishes a plain domain event (or enqueues onto this module's outbox) and the notification module owns the "last mile": mapping that event to a template, resolving the recipient's language, checking the recipient's email preferences, rendering HTML, sending it, durably retrying if it fails, and — for user-facing events — writing a row into that user's in-app inbox.

    Coach, Parent and self-registered Player users are the main end recipients — booking lifecycle emails, session pack warnings, reschedule/no-show notices, shared performance reports. Every authenticated role has the header bell + /notifications inbox and the email-preference section on the Profile page. Admin is a recipient for CSAM/video-moderation alerts, the operator of the /v1/admin/alerts endpoints used to configure operational alerting, and the caller of the SES cutover preflight. System/Ops is the implicit recipient of alert emails when a configured metric threshold is breached.

    Key business rules found in the code:

    • Notification centre (#313, V175). Every EmailTemplate is classified exactly once in NotificationCatalog into a NotificationCategory (BOOKING, REMINDER, SESSION_PACK, DEVELOPMENT, MODERATION, ACCOUNT, SYSTEM), plus whether it also produces an in-app inbox row and which frontend route that row deep-links to.
    • Only REMINDER and DEVELOPMENT are opt-out-able (NotificationCategory.optOutable()) — today that is BOOKING_REMINDER, SESSION_PACK_EXPIRY_WARNING and PERFORMANCE_REPORT_SHARED. Booking, session-pack, moderation, account/security and system mail is transactional and always sent; a PUT to turn one of those off is a 400. The three VIDEO_APPROVAL_* templates are retired (ADR 18, "Minors never upload"): no producer, Thymeleaf files deleted, catalogued email-only. The enum constants and their envelope_entity CHECK values stay, @Deprecated, only so already-stored rows still load.
    • Opt-out is enforced at send time (MailService → NotificationPreferenceService.emailDecision), not at enqueue time, so an opt-out made while a reminder is already sitting in the outbox or the retry queue still takes effect. The in-app inbox row is written regardless of the email preference.
    • Opt-out-able emails carry a footer unsubscribe link and RFC 8058 List-Unsubscribe/List-Unsubscribe-Post headers; the token is an HMAC-signed (userId, category) pair with no expiry.
    • Inbox rows are kept 90 days (platform.notification.in-app-retention-days, floor 7) and deleted on GDPR erasure together with the user's email preferences.
    • Registration/OTP mail — the six COACH_/PARENT_/PLAYER_ verification and OTP templates — is durable through this module's outbox/retry pipeline (since ses-1.4). These, and all other ACCOUNT templates, are email-only: no inbox row. SEND_OTP is retired: its only producer, the legacy POST /authenticate → /otp login-2FA flow, was removed, and the constant (plus its CHECK value) stays only so stored or still-queued envelopes resolve. MailManager still masks its data in logs.
    • Every outbound email is modeled as an Envelope (recipients + template + template data + a deadline + an idempotent sendId). Producers reach the send pipeline through three shapes (outbox, direct Envelope publish, direct sync call) — see "Producer census" below.
    • Alert rules (metricName, threshold, windowSeconds, notificationChannel) are admin-configurable at runtime via REST, hot-reloaded from the DB every 60s, and support LOG or EMAIL (sent to the platform.admin_alert_email config row; blank by default, in which case nothing is sent and an ERROR is logged).
    • Failed sends are never silently dropped: they're persisted with a retry flag and picked up by EmailRetryScheduler, up to MAX_RETRY_ATTEMPTS = 6 total attempts, after which the envelope is ATTEMPTS_EXHAUSTED. An envelope past its deadline is DEADLINE_EXPIRED even if retries remain.
    • Video moderation admin alerts are a startup-time safety gate: if the Arachnid (CSAM detection) feature flag is enabled but platform.admin_alert_email is blank, the application refuses to start.

    Key services

    ServiceOrchestrates
    MailManagerSend pipeline entry point. sendEmailFromTemplate is the @Async("sendMailPool") AFTER_COMMIT listener for Envelope events; sendEmailSync (REQUIRES_NEW) is called directly by NotificationEmailOutboxHandler, EmailRetryScheduler, AlertNotificationListener, VideoModerationEmailListener.sendAdminAlertSync and SesCutoverPreflightResource. It takes a Postgres advisory lock on hashtext(sendId) first (cluster-wide per-send serialization; a null sendId is rejected), skips recipients already marked delivered, runs each send through the per-template Resilience4j breaker (EmailTemplate.circuitBreakerName(): emailService by default, registrationEmailService for the six registration/OTP templates, sesPreflightService for the preflight) + RetryTemplate, and persists the outcome as an EnvelopeEntity. It never rethrows — callers that care read the persisted row back. A local SES rate-limit rejection does not count as an attempt.
    MailServicePer-recipient send: asks NotificationPreferenceService.emailDecision (suppress / send plain / send with unsubscribe token), renders via EmailContentRenderer (Thymeleaf template named after the lowerCamelCase enum constant, e.g. BOOKING_CONFIRMED → mails/bookingConfirmed.html, subject via MessageSource; EmailTemplate.NONE is the raw subject/body escape hatch used by alerts), adds unsubscribeUrl + List-Unsubscribe headers when a token was minted, then dispatches through the OutboundEmailSender port. Records the mail.send metric (not for suppressed sends). A failed preference lookup is thrown as EmailTransportTransientException (retryable); a malformed payload as EmailTransportPermanentException.
    NotificationOutboxSupport / NotificationEmailOutboxHandlerOutbox producer/consumer (aggregate type NOTIFICATION_EMAIL). enqueueEmail is MANDATORY — it joins the BEFORE_COMMIT listener's business transaction, stamps the deadline from template.deliveryDeadline(), writes the outbox row, requests a drain, and writes the in-app inbox row (InAppNotificationService.recordForEmail) in the same transaction. The handler re-checks the deadline (persists DEADLINE_EXPIRED and completes), calls sendEmailSync, reads the EnvelopeEntity back and throws on FAILED+retry=true so the outbox retries. See Outbox.
    NotificationCatalogStatic, exhaustive switch (no default) mapping each EmailTemplate to Entry(category, inApp, coachLink, otherLink, linkDataKey). Deep links are hash-router paths (/coach/booking-requests, /parent/bookings, /dashboard, /player/videos, …); PERFORMANCE_REPORT_SHARED derives its link from the email's reportsPageUrl. Also holds PARAM_WHITELIST, the only email-data keys copied into an inbox row.
    InAppNotificationServicerecordForEmail resolves the recipient address to a user (NotificationRecipientLookup, case-insensitive email match; no account → skipped), picks the deep link (coach vs other), whitelists params (strings ≤ 200 chars), and inserts via UserNotificationWriter (ON CONFLICT DO NOTHING) — all inside a JDBC savepoint, catching every failure, so the inbox can never fail the business transaction. Also list (page size capped at 50), unread count, mark-read and mark-all-read, each a single recipient-scoped statement.
    NotificationPreferenceServicegetPreferences/setPreference (opt-out-able categories only), unsubscribe(token) (@RateLimited 120/min per IP; invalid token and deleted user both return the same 400), and emailDecision — the send-time check, run in a savepoint because it executes inside sendEmailSync's REQUIRES_NEW transaction.
    UnsubscribeTokenServiceMints/verifies v1.<b64url(userId:CATEGORY)>.<b64url(HmacSHA256)>, constant-time compare, max 512 chars, opt-out-able categories only. Key derived from skillars.platform.registration-verification-secret with purpose label skillars-email-unsubscribe-v1 (startup fails if the secret is blank).
    JdbcSavepointsRuns a supplier inside a raw JDBC savepoint on the transaction's connection (rolls back to it on RuntimeException and rethrows). Exists because JpaTransactionManager cannot do Propagation.NESTED with Hibernate.
    InAppNotificationRetentionSchedulerDaily at 03:30 (@SchedulerLock InAppNotificationRetentionScheduler_purge, PT30M/PT1M): deletes rows older than the retention window in batches of 1000, each batch its own transaction, max 500 batches per run.
    EmailRetrySchedulerEvery 60s (email.retry.interval-ms; @SchedulerLock EmailRetryScheduler_retryFailedEmails, PT10M / email.retry.lock-at-least): SELECT ... FOR UPDATE SKIP LOCKED up to 10 failed+retryable envelopes, marks expired/exhausted ones terminal in-transaction, then calls sendEmailSync for the rest in an afterCommit hook (network I/O kept off the DB connection). The ShedLock is what prevents a second pod re-selecting a row between commit and send.
    AlertEvaluationService / AlertRuleCache / AlertNotificationListenerEvaluator every 30s (alert.evaluation-interval-ms) over the cached enabled rules, publishing AlertFiredEvent on breach; cache refreshed every 60s (alert.rule-cache.refresh-interval-ms) and on every admin write; listener logs WARN and, for EMAIL rules, calls sendEmailSync with EmailTemplate.NONE to platform.admin_alert_email. Neither scheduled method is ShedLock-guarded (both are per-instance by nature). computeMetricValue is still a stub returning -1.0.
    ResendEmailServiceLooks up an EnvelopeEntity by sendId and republishes it as a fresh Envelope event — a manual resend hook.

    Producer census (all shapes, all modules)

    • Outbox shape (@TransactionalEventListener(BEFORE_COMMIT) + NotificationOutboxSupport.enqueueEmail; inbox row written by enqueueEmail): BookingEmailListener, SessionPackEmailListener, VideoOwnerEmailListener, AdminOutcomeEmailListener (this module — its owner-flagged handler is an @EventListener that opens its own TransactionTemplate transaction, because the async moderation pipeline publishes with none); Coach/Parent/PlayerRegistrationEmailListener (platform.security). SessionPackExpiryNotifier (payment) publishes the event that SessionPackEmailListener turns into an enqueue.
    • Direct-publish shape (new Envelope(...) + publishEvent, sent by MailManager.sendEmailFromTemplate AFTER_COMMIT; inbox row written by InAppEnvelopeListener BEFORE_COMMIT on the same event): AccountChangeEmailListener, VideoModerationEmailListener.onAdminAlert (this module); AccountManagementFacade, EmailRegistrationStrategy, SendMailListener (platform.security); ReportGenerationService (platform.development). Each hardcodes its own deadline rather than reading deliveryDeadline(). ResendEmailService republishes the same way. An Envelope published with no active transaction reaches neither listener (fallbackExecution = false).
    • Direct-sync shape (MailManager.sendEmailSync, no outbox, no event): AlertNotificationListener, VideoModerationEmailListener.sendAdminAlertSync (the video.contract.ModerationAdminAlertSender port, called by the video module's ModerationAdminAlertOutboxHandler), and SesCutoverPreflightResource. These never produce inbox rows (all are SYSTEM).

    Every path converges on MailManager.sendEmailSync → MailService → OutboundEmailSender.

    Coach start reminder (V219). BookingEmailListener.onCoachStartReminder sends COACH_START_REMINDER to the coach (reminderType START / LATE, playerName, bookingsUrl) when booking.CoachStartReminderScheduler finds a session still UPCOMING at its start and at start + 10 minutes. Category BOOKING: transactional and safety-relevant, so unlike BOOKING_REMINDER it is never opt-out-able, and it writes a coach inbox row (deep link /coach/booking-requests). There is no push channel; email and the inbox are the notification channels. An automatic never-started refund reuses BOOKING_CANCELLED_COACH_UNAVAILABLE (parent) and BOOKING_CANCELLED_BY_SKILLARS (coach) with cancelledBy = NEVER_STARTED.

    Safeguarding expiry reminder (V223). CoachSafeguardingEmailListener.onSafeguardingExpiring (BEFORE_COMMIT) turns marketplace.contract.CoachSafeguardingExpiringEvent, published by the daily CoachSafeguardingService.sendExpiryReminders job, into COACH_SAFEGUARDING_EXPIRING (category ACCOUNT, so never opt-out-able, in-app link /coach/safeguarding). It is its own listener class, not a handler on the booking / pack / admin-outcome listeners, so the pinned handler counts of EmailListenerAnnotationCoverageTest and EmailDataRoundTripContractTest are unchanged; the data map is string-typed (the date is formatted in the coach's zone at the producer).

    Forfeit notices to the family (V212). A forfeit pays the coach and refunds nothing, so the payer is told. BookingEmailListener.onPlayerNoShowNotifyFamily sends SESSION_FORFEITED_NO_SHOW to PlayerNoShowEvent.getParentEmail() (the user Booking.parentId names: the parent, or the self-booking adult player; never resolved through playerId, a PlayerProfile key). onBookingCancelledByParentForfeit sends SESSION_FORFEITED_LATE_CANCEL only when BookingCancelledByParentEvent.isForfeit() (captured and not refund-eligible), with paidWith (PACK/CHARGE) and sessionPrice. A refunded or pre-capture cancel, and a withdrawn request, send the family nothing (the coach's BOOKING_CANCELLED_BY_PARENT is unchanged). Both carry disputeWindowDays (disputes.submissionWindowDays, 14) and a bookingsUrl, and are in-app BOOKING rows deep-linking to the parent bookings page. BookingEmailListener now has 24 handlers.

    Internally: Envelope (published by direct-publish producers; consumed BEFORE_COMMIT by InAppEnvelopeListener and AFTER_COMMIT by MailManager) and AlertFiredEvent (AlertEvaluationService → AlertNotificationListener).

    How email actually leaves the building

    This module never constructs a SesV2Client or JavaMailSender. MailService calls the OutboundEmailSender port in infrastructure.email; exactly one implementation is active, chosen by app.email.transport through each bean's own @ConditionalOnProperty:

    ValueBeanProfiles
    loginfrastructure.email.log.LoggingEmailSender (logs; optionally dumps to app.email.log.dump-dir)base application.yaml (and the fallback when the property is absent), dev (dumps to target/mails since ses-1.5), test
    smtpinfrastructure.email.smtp.SmtpEmailSender (app.email.smtp.provider-configs)uat
    sesinfrastructure.ses.SesEmailSender (AWS SES v2, SesSendRateLimiter, SesHealthIndicator)prod

    OutboundEmailRequest now carries a headers map (validated header names, no CR/LF in values) which both SmtpEmailSender and SesEmailSender apply — that is how List-Unsubscribe reaches the wire. EmailTransportArchitectureTest forbids any platform/** class from touching the SES SDK; hence SesAccountChecker lives in infrastructure.ses. See Infrastructure. Other dependencies: infrastructure.threadpool (MDC decorator, graceful shutdown), infrastructure.feature (Arachnid gate), infrastructure.web.FrontendLinkBuilder (unsubscribe/deep-link URLs), platform.config.service.ConfigService (platform.admin_alert_email), and platform.outbox.

    Key Flows

    Booking confirmed → inbox row + templated email

    sequenceDiagram
  participant Booking as booking module
  participant Listener as BookingEmailListener
  participant Outbox as NotificationOutboxSupport
  participant InApp as InAppNotificationService
  participant Drain as OutboxService drain
  participant Handler as NotificationEmailOutboxHandler
  participant Manager as MailManager
  participant Mail as MailService
  participant Sender as OutboundEmailSender

  Booking->>Listener: BookingConfirmedEvent (BEFORE_COMMIT)
  Listener->>Outbox: enqueueEmail(BOOKING_CONFIRMED, ...) [MANDATORY]
  Outbox->>Outbox: INSERT outbox_messages + requestDrainAfterCommit()
  Outbox->>InApp: recordForEmail(...) [JDBC savepoint, never throws]
  InApp->>InApp: INSERT user_notifications ON CONFLICT DO NOTHING
  Note over Booking,InApp: booking row, outbox row, inbox row commit together
  Drain->>Handler: handle(payload) [async, after commit]
  Handler->>Manager: sendEmailSync(envelope) [REQUIRES_NEW, advisory lock on sendId]
  Manager->>Mail: sendEmailFromTemplate(recipient, ...) [breaker + retry]
  Mail->>Mail: emailDecision (transactional: SEND_PLAIN, no DB)
  Mail->>Sender: send(OutboundEmailRequest)
  Manager->>Manager: save EnvelopeEntity(SENT or FAILED)
  Handler->>Handler: read back, FAILED+retry → throw → outbox backoff

    BookingEmailListener runs inside the booking transaction, so the outbox row and the inbox row commit atomically with the booking. The outbox drain (see Outbox) calls the handler after commit, off the request thread. Because sendEmailSync swallows exceptions, the handler reads the persisted EnvelopeEntity to decide whether to let the outbox retry.

    Opt-out-able email: preference check and one-click unsubscribe

    sequenceDiagram
  participant Mail as MailService
  participant Pref as NotificationPreferenceService
  participant Tok as UnsubscribeTokenService
  participant Sender as OutboundEmailSender
  participant Inbox as Mailbox provider
  participant API as UnsubscribeResource

  Mail->>Pref: emailDecision(BOOKING_REMINDER, to)
  Pref->>Pref: savepoint: lookup user by email, read preference
  alt REMINDER disabled
    Pref-->>Mail: SUPPRESS
    Mail-->>Mail: return normally (envelope recorded SENT, no metric)
  else enabled
    Pref->>Tok: mint(userId, REMINDER)
    Pref-->>Mail: send + token
    Mail->>Sender: send(body with unsubscribeUrl, List-Unsubscribe headers)
  end
  Inbox->>API: POST /api/notifications/unsubscribe?token=... (List-Unsubscribe=One-Click)
  API->>Pref: unsubscribe(token) [rate-limited]
  Pref->>Tok: verify(token)
  Pref->>Pref: upsert (userId, REMINDER, false)

    The body link points at the frontend landing page (#/unsubscribe?token=...), which asks for a click and then POSTs the same endpoint; the List-Unsubscribe header points straight at the API under FrontendLinkBuilder.base(). A suppressed send counts as delivered for that recipient, so retries never resend it. If the preference lookup itself fails, the send fails retryably — neither sending nor dropping is safe on an unknown preference.

    sequenceDiagram
  participant Admin

    Failed send → durable retry

    sequenceDiagram
  participant Manager as MailManager
  participant Sender as OutboundEmailSender
  participant DB as main.envelope_entity
  participant Scheduler as EmailRetryScheduler

  Manager->>Sender: send(OutboundEmailRequest)
  Sender-->>Manager: EmailTransportTransientException
  Manager->>DB: save EnvelopeEntity(FAILED, retry=true, attempts++)
  loop every 60s, ShedLock
    Scheduler->>DB: SELECT ... retry AND FAILED FOR UPDATE SKIP LOCKED LIMIT 10
    alt deadline passed
      Scheduler->>DB: DEADLINE_EXPIRED, retry=false
    else attempts >= 6
      Scheduler->>DB: ATTEMPTS_EXHAUSTED, retry=false
    else
      Scheduler->>Manager: sendEmailSync(envelope) [afterCommit]
    end
  end

    Note there are two retry layers for outbox-routed mail: the outbox row is retried with exponential backoff by platform.outbox while the handler keeps throwing, and EmailRetryScheduler independently re-drives any FAILED/retry=true envelope. Both go through sendEmailSync's advisory lock and per-recipient delivered flags, which is what stops them double-sending.

    Conventions & Gotchas

    Adding a new email type touches six places. (1) an EmailTemplate constant (subject key, optionally deadline + breaker name); (2) a NotificationCatalog case — the switch is exhaustive, so forgetting it is a compile error; (3) mails/<lowerCamelCase>.html, and if the category is opt-out-able, include mails/fragments/unsubscribeFooter.html (as bookingReminder.html, sessionPackExpiryWarning.html, performanceReportShared.html do); (4) the subject key in i18n/messages*.properties; (5) a Flyway migration widening main.envelope_entity.envelope_entity_email_template_check (EnvelopeEntitySchemaIT pins enum ↔ constraint parity — SES_CUTOVER_PREFLIGHT shipped without one and needed V168); (6) if in-app, a notifications.types.<TYPE> text in the frontend en-US/de-DE/fr-FR i18n, and add any new display params to NotificationCatalog.PARAM_WHITELIST.

    Step (3) is now enforced: EmailTemplateFileParityTest fails when a constant has no mails/<lowerCamelCase>.html (exemptions: NONE, and COACH_VISIBILITY_REDUCED / EMAIL_CHANGE, which nothing sends, and the three @Deprecated VIDEO_APPROVAL_* constants whose bodies V184 removed). Before C6, BOOKING_CANCELLED_BY_PARENT, BOOKING_CANCELLED_BY_COACH, COACH_NO_SHOW and PLAYER_NO_SHOW had no body and PACK_PAUSED's was misnamed sessionPackPaused.html: Thymeleaf's TemplateInputException is not an EmailTransportPermanentException, so MailManager marked each envelope FAILED + retryable, EmailRetryScheduler retried it every minute until its delivery deadline, and it then expired. Nobody was told. A render failure looks like a transient failure; only a build-time check catches a missing template.

    Inbox writes must be JDBC-only. InAppNotificationService and NotificationPreferenceService.emailDecision run inside someone else's transaction via JdbcSavepoints. A JPA query there would auto-flush the business session first, and rolling back to the savepoint would silently discard business SQL Hibernate thinks it flushed. Use JdbcTemplate (that's why UserNotificationWriter, NotificationRecipientLookup and NotificationEmailPreferenceRepository are plain JDBC). The price of best-effort inbox writes: an inbox row can, rarely, be missing for an email that was sent.

    Recipients are resolved by a case-insensitive email match. Producers address mail by email only, so both the inbox and the opt-out check look the address up in main."user".email. Registration stores the address as typed, so NotificationRecipientLookup tries the exact match first (the user_email_key unique index) and only on a miss compares lower(email) — an unindexed scan paid only by addresses that matched nothing exactly. If the folded address matches two accounts (addresses that differ only by case are distinct under the unique constraint) it resolves to nobody rather than to the wrong inbox. An address that matches no user (an admin alias) gets no inbox row and an email with no unsubscribe link. The resolved user is the email owner — for a minor that is the parent, and recipient_user_id is always a main."user" id (never a PlayerProfile PK).

    Unsubscribe tokens never expire and are keyed off skillars.platform.registration-verification-secret (env PLATFORM_REGISTRATION_VERIFICATION_SECRET). Rotating that secret silently invalidates every unsubscribe link already in mailboxes (users can still opt out from the Profile page). Never add a GET handler to the unsubscribe path — prefetchers would unsubscribe users.

    A preference-suppressed send is recorded as SENT on the EnvelopeEntity (the correct terminal state — a re-drive must not retry it) and logged as [EMAIL_SUPPRESSED_BY_PREFERENCE]. Don't use envelope_entity.status to count actual deliveries; use the mail.send metric, which skips suppressed sends.

    ComponentConfig only defines the MailManager bean when enable.test.mail=false (the default). With enable.test.mail=true another bean must supply it. SesCutoverPreflightResource only exists under app.email.transport=ses — a 404 on /v1/admin/ses/preflight in dev/uat is expected. EmailTransportPropertyValidator aborts startup on an unrecognised transport value but accepts an absent one (falls back to log).

    AlertRule has no setters (Lombok @SuperBuilder only), so AlertRuleAdminResource.update() is delete-then-recreate — the row's id and audit history are not preserved across an update.

    EnvelopeEntity has no @Table(schema=...), but Hibernate's default_schema is main and the table is main.envelope_entity in V138__baseline_schema.sql; it is never deleted from (terminal rows are kept). Registration/OTP mail goes through it too, so a schema problem here breaks account verification, not just booking-email history.

    Email template data is string-typed by contract: it is JSON round-tripped through the outbox, so producers must format numbers/instants themselves. EmailDataRoundTripContractTest pins the real property (a value's type survives the JSON round trip) for the shapes the listeners use; it does not scan every producer. Some producers still put ints in (creditsRemaining, requestedCount, acceptedCount); the inbox param whitelister tolerates that.
