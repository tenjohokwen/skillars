Notification

The platform's outbound-email engine: it turns domain events from every other module into templated, retried, and auditable emails, plus a DB-configurable operational alerting system.

Business Overview

Skillars is a multi-sided marketplace (Players/Parents, Coaches, Admins), and almost every meaningful state change — a booking request, a declined reschedule, a session pack about to expire, a flagged video — needs to reach a human by email. Rather than each module formatting and sending its own mail, every other module publishes a plain domain event and the notification module owns the "last mile": mapping that event to a template, resolving the recipient's language, rendering HTML, sending it, and durably retrying if it fails. This keeps email formatting, SMTP plumbing, and delivery-retry logic in one place instead of scattered across booking, payment, video, and security code.

Coach and Parent are the main end recipients — booking lifecycle emails, session pack warnings, reschedule/no-show notices. Admin is a recipient for CSAM/video-moderation alerts, plus the operator of the /v1/admin/alerts endpoints used to configure operational alerting. System/Ops is the implicit recipient of alert emails when a configured metric threshold is breached (e.g. a fraud-spike or callback-anomaly rule).

Key business rules found in the code:

  • Registration/OTP mail — the six COACH_/PARENT_/PLAYER_ prefixed verification and OTP templates — is durable through this module's own outbox/retry pipeline as of ses-1.4; it used to be a separate, fire-and-forget path that bypassed this module entirely. (The unrelated login-2FA SEND_OTP template was never part of that fire-and-forget path — it already published an Envelope through this module's own pipeline before ses-1.4, and still does; see the producer census below.)
  • Every outbound email is modeled as an Envelope (recipients + template + arbitrary template data + a deadline + an idempotent sendId) — a domain-agnostic mail request. Producers reach this module's send pipeline through three different shapes, not one: most booking/session-pack mail and all registration/OTP mail enqueues directly onto this module's own durable outbox and never constructs an Envelope at all; several other producers — two inside this module, several more in other modules entirely — still build an Envelope and publish it as a Spring application event; and a couple of call sites skip both the outbox and the event bus and call the send pipeline synchronously. See "Producer census" below (after Key Services) for the full, per-class breakdown.
  • Alert rules (metricName, threshold, windowSeconds, notificationChannel) are admin-configurable at runtime via REST, hot-reloaded from the DB every 60s (no restart needed), and support two channels: LOG (just a WARN log line) or EMAIL (also sends to ops@skillars.internal).
  • Failed sends are never silently dropped: they're persisted with a retry flag and picked up by a scheduled retry job, up to MAX_RETRY_ATTEMPTS = 6 total attempts, after which the envelope is marked ATTEMPTS_EXHAUSTED. An envelope past its deadline is marked DEADLINE_EXPIRED and abandoned even if retries remain.
  • Video moderation admin alerts are a startup-time safety gate: if the Arachnid (CSAM detection) feature flag is enabled but platform.admin_alert_email is blank, the application refuses to start rather than silently dropping abuse alerts.

Key services

ServiceOrchestrates
MailManagerThe send pipeline entry point: sendEmailFromTemplate listens for Envelope events after transaction commit (async, on the sendMailPool executor) — every direct-publish producer lands here, not just this module's own two (see the producer census below); sendEmailSync is called directly by NotificationEmailOutboxHandler, EmailRetryScheduler, AlertNotificationListener (ops alerting), and VideoModerationEmailListener's own synchronous admin-alert path. Either way it runs the send through a Resilience4j circuit breaker + Spring RetryTemplate (3 attempts, 1s backoff) and persists the outcome as an EnvelopeEntity. Since ses-1.4 the breaker is resolved per template via EmailTemplate.circuitBreakerName() — the six COACH_/PARENT_/PLAYER_ registration and OTP templates get their own isolated registrationEmailService breaker (the separate login-2FA SEND_OTP template is unaffected — it keeps the default emailService breaker like everything else), so a signup spike of bad addresses can't open the breaker that gates booking confirmations.
MailServiceRenders via EmailContentRenderer (Thymeleaf HTML template, name = EmailTemplate enum constant converted to lowerCamelCase, e.g. BOOKING_CONFIRMED → bookingConfirmed.html under src/main/resources/mails/, plus the i18n subject via MessageSource; EmailTemplate.NONE is a raw-subject/body escape hatch used by alert emails), then dispatches through the OutboundEmailSender port (infrastructure.email) — SES, SMTP, or a log/file transport, selected by app.email.transport, is invisible to this class. See the Infrastructure dev-doc for the transport package itself (this class no longer picks a provider). Also records the mail.send transport-tagged outcome metric via MailMetrics.
NotificationOutboxSupport / NotificationEmailOutboxHandlerThe outbox producer/consumer pair. enqueueEmail is the entry point every BEFORE_COMMIT listener calls (MANDATORY propagation — it joins the caller's own transaction, so the outbox row commits atomically with the business row it describes, never in a separate transaction that could fail independently). The generic outbox poller (platform.outbox.service) dispatches each row to NotificationEmailOutboxHandler, which calls MailManager.sendEmailSync — this is the pipeline the "Booking confirmed" diagram below depicts.
EmailRetrySchedulerEvery 60s (configurable), SELECT ... FOR UPDATE SKIP LOCKEDs up to 10 failed+retryable envelopes, expires/exhausts stale ones in-transaction, then dispatches the rest via MailManager.sendEmailSync only after the DB transaction commits (the transport call is deliberately kept off the DB connection).
AlertEvaluationServiceScheduled (30s) evaluator that reads enabled rules from AlertRuleCache and computes a metric value per rule, publishing AlertFiredEvent on breach. Metric computation is currently a stub (computeMetricValue always returns -1.0 — domain-specific metrics were removed during a template conversion and are a TODO).
AlertRuleCacheIn-memory AtomicReference cache of enabled AlertRules, refreshed from the DB every 60s and on startup — lets admins change rules via REST with no redeploy.
AlertNotificationListenerReacts to AlertFiredEvent: always logs a WARN, and if the rule's channel is EMAIL, sends a plain-text ops alert (via EmailTemplate.NONE) to ops@skillars.internal, swallowing any mail failure so the alerting loop itself never breaks.
ResendEmailServiceLooks up a previously-persisted EnvelopeEntity by sendId and republishes it as a fresh Envelope event — a manual "resend" escape hatch (e.g. for support tooling).
infrastructure.listener.*Four listener classes (AccountChangeEmailListener, BookingEmailListener, SessionPackEmailListener, VideoModerationEmailListener) that each consume one family of cross-module domain events and translate them into a template send — this is where the module's actual "which event maps to which template" logic lives. Only AccountChangeEmailListener and VideoModerationEmailListener still publish an Envelope; BookingEmailListener and SessionPackEmailListener call NotificationOutboxSupport.enqueueEmail directly, BEFORE_COMMIT — the same shape three more listeners in platform.security use for registration/OTP mail (see Dependencies on other layers below). (A fifth, TenantLifecycleEmailListener, was deleted with the tenant module, along with its six tenant*.html templates and their EmailTemplate constants.)

Producer census (all shapes, all modules)

This module's own four infrastructure.listener.* classes and the three registration listeners in platform.security.infrastructure.listener are not the whole picture. EmailTemplate.deliveryDeadline()'s own class-level javadoc documents that at least six more call sites elsewhere build an Envelope directly and publish it, each with its own hardcoded deadline, never reading deliveryDeadline(). Three shapes exist in total:

  • Outbox shape (BEFORE_COMMIT + NotificationOutboxSupport.enqueueEmail): BookingEmailListener, SessionPackEmailListener (this module); Coach/Parent/PlayerRegistrationEmailListener (platform.security).
  • Direct-publish shape (new Envelope(...) + publisher.publishEvent(...), picked up by MailManager's own AFTER_COMMIT listener): AccountChangeEmailListener, VideoModerationEmailListener (this module); AccountManagementFacade, EmailRegistrationStrategy, SendMailListener (platform.security); ReportGenerationService (platform.development) — six of these seven call sites are the ones EmailTemplate.deliveryDeadline()'s javadoc names explicitly. ResendEmailService (this module) republishes an already-persisted Envelope the same way, as a manual resend — not a new producer.
  • Direct-sync shape (calls MailManager.sendEmailSync directly, skipping both the outbox and the event bus): AlertNotificationListener (ops alerting) and VideoModerationEmailListener's own sendAdminAlertSync — the same class as the direct-publish shape above also has this second, synchronous entry point, used when a durable row's early deletion on the video-moderation outbox would otherwise race the actual send (its own code comment explains why).

Whichever shape a producer uses, every path converges on MailManager.sendEmailSync (the outbox handler and the retry scheduler call it directly; sendEmailFromTemplate, the Envelope-event listener, just wraps it) — see Key services above and Key Flows below.

Domain events consumed

The notification module is almost entirely event-driven on the consuming side — it listens for events published by many other platform modules and turns each into an Envelope:

AccountChangeEvent (security) BookingRequestedEvent (booking) BookingConfirmedEvent (booking) BookingDeclinedEvent (booking) BookingExpiredEvent (booking) BookingReminderEvent (booking) QuickCompleteConfirmationRequiredEvent (booking) RescheduleRequestedEvent (booking) RescheduleAcceptedEvent (booking) RescheduleDeclinedEvent (booking) BatchBookingRequestedEvent (booking) BatchBookingAcceptedEvent (booking) DuplicateBookingProposedEvent (booking) BookingCancelledDueToPauseEvent (booking) BookingCancelledByParentEvent (booking) BookingCancelledByCoachEvent (booking) CoachNoShowEvent (booking) PlayerNoShowEvent (booking) SessionPackExpiryWarningEvent (class in booking, published by payment) SessionPackExpiredEvent (class in booking, published by payment) PackPausedEvent (class in booking, published by payment) VideoModerationAdminAlertEvent (video) VideoModerationOwnerNotificationEvent (video)

Internally, the module also publishes and consumes its own events: an Envelope (published by any direct-publish-shape producer — see the producer census above — and consumed by MailManager) and AlertFiredEvent (published by AlertEvaluationService, consumed by AlertNotificationListener).

Dependencies on other layers

This module does not construct a SesV2Client or JavaMailSenderImpl itself — its own send path (MailService → OutboundEmailSender) dispatches through the transport port in infrastructure.email, which resolves to whichever of infrastructure.ses/infrastructure.email.smtp/infrastructure.email.log is active for app.email.transport (see Infrastructure). As of ses-1.4, the registration-flow path goes through the exact same pipeline: three listeners in platform.security.infrastructure.listener (CoachRegistrationEmailListener, ParentRegistrationEmailListener, PlayerRegistrationEmailListener) — exactly the same shape as this module's own BookingEmailListener/SessionPackEmailListener (@TransactionalEventListener(BEFORE_COMMIT) + an enqueueEmail call) — call this module's NotificationOutboxSupport.enqueueEmail directly, which lands on the same NotificationEmailOutboxHandler → MailManager → MailService → OutboundEmailSender tail as every other outbox-routed email. There is no longer a module that bypasses this one for outbound mail. Beyond that, this module depends on infrastructure.threadpool (MDC-propagating task decorator for its executors), infrastructure.feature (feature-flag gate for Arachnid/CSAM alerting), and platform.config.service.ConfigService (runtime-configurable admin alert email address).

Key Flows

Booking confirmed → templated email sent

sequenceDiagram
  participant Booking as booking module
  participant Listener as BookingEmailListener
  participant Outbox as NotificationOutboxSupport
  participant Poller as outbox poller (platform.outbox.service)
  participant Handler as NotificationEmailOutboxHandler
  participant Manager as MailManager
  participant Mail as MailService
  participant Sender as OutboundEmailSender
  participant DB as envelope_entity

  Booking->>Listener: BookingConfirmedEvent (BEFORE_COMMIT)
  Listener->>Listener: build Recipient + data map
  Listener->>Outbox: enqueueEmail(BOOKING_CONFIRMED, ...) [MANDATORY — joins the booking transaction]
  Note over Listener,Outbox: outbox row commits atomically with the booking row
  loop outbox drain
    Poller->>Handler: handle(payload)
    Handler->>Manager: sendEmailSync(envelope)
    Manager->>Mail: sendEmailFromTemplate(recipient, template, data) [circuit breaker + retry]
    Mail->>Mail: render via EmailContentRenderer
    Mail->>Sender: send(OutboundEmailRequest) [transport-neutral]
    Manager->>DB: save EnvelopeEntity(status=SENT or FAILED)
  end

A coach accepting a booking request triggers BookingConfirmedEvent from the booking module. BookingEmailListener is a @TransactionalEventListener(phase = BEFORE_COMMIT), so it runs inside the booking transaction itself and calls NotificationOutboxSupport.enqueueEmail directly — no Envelope Spring event is published for this flow any more. The outbox row commits atomically with the booking row it describes (skillars-deferred-91/-92); the generic outbox poller then dispatches it to NotificationEmailOutboxHandler, which calls MailManager.sendEmailSync. From there the pipeline is the same regardless of which producer enqueued it: render via EmailContentRenderer, dispatch through the transport-neutral OutboundEmailSender port, and persist the outcome either way so a failure is never silently lost.

Admin configures an EMAIL alert rule, which later fires

sequenceDiagram
  participant Admin
  participant API as AlertRuleAdminResource
  participant Repo as AlertRuleRepository
  participant Cache as AlertRuleCache
  participant Eval as AlertEvaluationService
  participant Notif as AlertNotificationListener
  participant Manager as MailManager

  Admin->>API: POST /v1/admin/alerts {metric, threshold, channel=EMAIL}
  API->>Repo: save(AlertRule)
  API->>Cache: refresh()
  Cache->>Repo: findAllByEnabledTrue()
  loop every 30s
    Eval->>Cache: getCachedRules()
    Eval->>Eval: computeMetricValue(metric)
    alt breach
      Eval->>Notif: publish AlertFiredEvent
      Notif->>Notif: log WARN
      Notif->>Manager: sendEmailSync(envelope) to ops@skillars.internal
    end
  end

An admin (JWT + ROLE_ADMIN) creates or updates a rule through AlertRuleAdminResource; the rule is saved to main.alert_rule and the in-memory cache is refreshed immediately so the new rule takes effect without waiting for the next scheduled reload. AlertEvaluationService runs every 30s, evaluating each cached rule; today computeMetricValue is a stub that always returns -1.0 (domain metrics were stripped out and are a TODO), so in practice EMAIL/LOG alerts won't currently fire until that gap is closed — but the configuration, caching, and notification plumbing around it is fully wired.

Failed send → durable retry

sequenceDiagram
  participant Manager as MailManager
  participant Sender as OutboundEmailSender
  participant DB as envelope_entity
  participant Scheduler as EmailRetryScheduler

  Manager->>Sender: send(OutboundEmailRequest)
  Sender-->>Manager: EmailTransportException
  Manager->>DB: save EnvelopeEntity(status=FAILED, retry=true, attempts++)
  loop every 60s
    Scheduler->>DB: SELECT ... WHERE retry=true AND status=FAILED FOR UPDATE SKIP LOCKED
    alt deadline passed
      Scheduler->>DB: status=DEADLINE_EXPIRED, retry=false
    else attempts >= 6
      Scheduler->>DB: status=ATTEMPTS_EXHAUSTED, retry=false
    else
      Scheduler->>Manager: sendEmailSync(envelope) [after commit]
    end
  end

When the transport call throws a retryable exception, MailManager persists the envelope as FAILED with retry=true instead of propagating the error. EmailRetryScheduler polls for such rows with SELECT ... FOR UPDATE SKIP LOCKED so multiple app instances never double-send the same envelope. Rows past their deadline or at the 6-attempt cap are marked terminal and never refetched; everything else is re-dispatched only after the polling transaction commits, keeping the transport call's network I/O off the database connection pool.

Conventions & Gotchas

The whole module's mail — including registration/OTP — goes out over one transport switch. app.email.transport (ses/smtp/log) selects which of three beans implementing OutboundEmailSender is active; each is gated by its own @ConditionalOnProperty, not a central selector. EmailTransportPropertyValidator only validates the raw property string at startup — it aborts on a present-but-unrecognised value, but an absent value is legal by design and falls through to the base log default; it selects no bean itself. Since ses-1.4, registration/OTP mail uses this exact same switch as booking/pack/alert mail — there is no separate suppression path to trip over any more. See Infrastructure for the transport package layout.

ComponentConfig only defines the MailManager bean when enable.test.mail=false (the default). If a profile sets enable.test.mail=true, no MailManager bean is registered by this class — expect a different (test-only) bean to supply it, or startup will fail with an unsatisfied dependency.

Adding a new email type means touching three places in lockstep: add a constant to the EmailTemplate enum (with a subjectKey pointing at an i18n message), add an HTML file under src/main/resources/mails/ named after the lowerCamelCase form of the enum constant (e.g. BOOKING_REMINDER → bookingReminder.html), and add the i18n key to messages_*.properties. Miss any one of the three and the send will fail at render or subject-lookup time.

AlertRule has no public setters and is built exclusively via its Lombok @SuperBuilder. AlertRuleAdminResource.update() therefore implements "update" as delete-then-recreate (same pattern as FeeRuleAdminResource elsewhere) rather than mutating the existing row — don't expect the row's primary key or audit history to be preserved across an update.

EnvelopeEntity still has no explicit @Table(schema = ...), unlike AlertRule which is pinned to schema = "main" — but this is no longer the "undocumented provenance" gap an earlier revision of this callout described. V136__pin_envelope_entity_schema.sql (shipped by skillars-deferred-110, later folded into V138__baseline_schema.sql by skillars-deferred-112's migration rebaseline) pinned envelope_entity/envelope_entity_recipients as an explicit, version-controlled migration, column-for-column matching what Hibernate's own auto-DDL had been silently creating and altering via the generate-ddl: true + ddl-auto: none precedence quirk this codebase's own Database & Migrations page corrects at length. Since ses-1.4, registration and OTP mail route through EnvelopeEntity for the first time, so a schema issue here affects account verification, not just booking-email history. (The ses-1-7-documentation ledger section this paragraph used to cross-reference was pruned once closed, per deferred-work.md's own delete-outright-when-closed convention — this paragraph is now the only surviving record of that history.)

Alert threshold evaluation is currently a no-op: AlertEvaluationService.computeMetricValue() always returns -1.0 (a marked TODO — domain-specific metrics like FAILURE_RATE were removed during a refactor). Configuring alert rules via the admin API works end-to-end, but no rule will actually breach and fire until real metric computation is added back.
