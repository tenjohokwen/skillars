    Your First Day

    One linear path from git clone to your first merged PR: run the stack, create the four personas, click through the core booking loop while reading the code behind each step, run one test of each kind, and ship through CI.

    Day-one checklist

    1. Install the toolchain

    JDK 17, Maven 3.9, Docker with the Compose plugin, Node 22. Prerequisites

    2. Run the stack

    docs/deployment/local/setup.sh, then start.sh. Health is green on :8367. Run locally

    3. Find your email

    Dev sends nothing. OTPs and verification links land in target/mails/. Email in dev

    4. Create the personas

    Register a coach, parent (+ child) and adult player, bootstrap an admin, run seed-accounts.sql. Accounts

    5. Walk the core loop

    Publish → book → accept → deliver → wrap up → review → admin view. Guided tour

    6. Run three tests

    One unit test, one Testcontainers IT, one Vitest spec. Tests

    7. Ship a PR

    Branch, conventional commit, PR, green CI, squash merge. Workflow

    8. Read on

    A suggested order through the module pages. What to read next

    Keep the Glossary open in another tab. Booker, shadow profile, SLU, wrap-up, payout hold, tombstone and similar terms are used on every page and defined there.

    Clone & run locally

    The detail behind every step lives in docs/deployment/local/deployment.md (infrastructure) and manual-testing.md (run modes, accounts, seeding payment state). The short version:

    git clone git@github.com:tenjohokwen/skillars.git && cd skillars
docs/deployment/local/setup.sh     # interactive, idempotent wizard
docs/deployment/local/start.sh     # starts app postgres redis storage-init grafana
curl -s http://localhost:8367/manage/health   # {"status":"UP"} once Flyway has run
docs/deployment/local/stop.sh      # docker compose ... down (volumes kept)

    setup.sh checks and fixes, in order: Docker daemon + Compose plugin; .env.local (copied from .env.example, placeholders filled, the generated Grafana admin password printed); the checked-in docker-compose.local.yml; deploy/seaweedfs/s3-identity.json; the /etc/hosts entry (it prints the command and waits, it never sudo-s for you); a world-writable target/mails/; the skillars:local image build (Maven + Quasar inside Docker, several minutes the first time); and finally that start.sh exists. Re-run it any time as a status check.

Do not run secData.sql or initTestData.sql under the dev profile: JwtSecretBootstrapRunner already created the JWT key row (app.bootstrap.jwt-secret.enabled: true in application-dev.yaml) and both scripts fail on sec_version_bus_id_key. -DskipFrontend produces a jar with no UI: fine for Mode B, never for anything deployed.

    Where email goes in dev

    application-dev.yaml sets app.email.transport: log. No mail is sent. LoggingEmailSender logs Sending email (log transport) and writes the rendered HTML to target/mails/<correlationId>.html. File names are random UUIDs: open the newest file, or grep -l you@example.com target/mails/*. In Mode A the folder is bind-mounted from the container; if Docker created it root-owned (Linux) the app cannot write there, so re-run setup.sh (and sudo rm -rf target/mails first on Linux). mvn clean deletes it; start.sh recreates it.

    Verification links can also be fetched from main.email_verification_tokens (SQL in manual-testing.md, "Fetch the token"). OTP codes cannot: only a hash is stored, so target/mails/ is the only source. In practice you rarely need the OTP, because V139__baseline_seed_data.sql seeds security.registration.phone-otp-required=false and email verification alone activates the account. See Notification for the transports.

    Accounts and seed data

    There are no pre-built login accounts. Flyway seeds roles, config and 20 platform drills, but no users. You register each persona through the UI, and docs/deployment/local/seed-accounts.sql then upgrades existing accounts to a paid state without calling Stripe. It contains no passwords: you choose them at registration. Use example.com addresses: the User entity's email regex only accepts 2–3 letter TLDs, and a longer one fails as an opaque HTTP 500 at persist time.

    PersonaHow to create it locallyWhat it can do
    Coach/#/coach-register → verify via target/mails → /#/login → finish all five steps of /#/coach/profile-builder and publish.     Parent/#/parent-register → verify → login → /#/parent/create-player to create a child (a shadow PlayerProfile with no login; a minor needs the consent checkbox).Search and book for a child, pay from the credit wallet or a pack, cancel/reschedule, confirm a quick-complete, review, dispute, homework and development views, video approvals, GDPR export/erasure for self or child.
    Player (adult)/#/player-register (18+ only, enforced by PlayerRegistrationService) → verify → /#/player/profile-builder.The same booker flows as a parent, for their own profile. Minors never log in.

    Then make the coach bookable and the parent solvent, still without Stripe:

    docker compose -f docker-compose.yml -f docker-compose.local.yml --env-file .env.local \
  exec -T postgres psql -U postgres -d skillars \
  -v coach_email=coach@example.com -v owner_email=parent@example.com \
  < docs/deployment/local/seed-accounts.sql

    It writes a COMPLETE payment.coach_stripe_accounts row (the booking payment-readiness gate is a pure DB read), sets the coach tier (ACADEMY by default, -v coach_tier=INSTRUCTOR to override), adds 5000.00 of wallet credit to the owner (so bookings settle to CONFIRMED with no gateway call), and an active PRO player subscription. The credit ledger is append-only: every re-run adds more credit and cannot be undone. The script refuses to run on any database other than skillars, skillars_dev or skillars_local.

    Run one test of each kind

    The full backend suite (mvn -B verify, over ten minutes on CI runners) is GitHub's job, not yours. Locally, run what you touched:

    Backend unit test (surefire, no Docker)

    mvn -DskipFrontend -Dtest=AgePolicyServiceTest test

    src/test/java/com/softropic/skillars/platform/security/service/AgePolicyServiceTest.java is a plain Mockito test of the age-tier boundaries. Unit tests are anything not named *IT; slice tests are named *WebMvcTest.

    Integration test (failsafe, Docker must be running)

    mvn -DskipFrontend -Dtest=NoUnitTests -Dsurefire.failIfNoSpecifiedTests=false \
    -Dit.test=ConfigResourceIT verify

    -Dtest=NoUnitTests with failIfNoSpecifiedTests=false skips the unit phase; -Dit.test picks the IT. ConfigResourceIT extends AbstractIntegrationTest (src/test/java/com/softropic/skillars/config/), which carries @SpringBootTest, profiles dev,test and the JVM-static Testcontainers. Before writing your own IT read docs/testing/readme.md: extend the base class, add no class-level Spring annotations, seed your own data (every table is reset per test method), claim an id range, and reuse an existing mock set. Every new @MockitoBean combination forks a Spring context, and CI fails above 17 contexts. Add -o once your ~/.m2 is warm.

    Frontend unit test (Vitest)

    cd src/frontend
npm ci                                                   # postinstall runs quasar prepare (.quasar/)
npx vitest run src/utils/__tests__/timelineLinksSpec.js  # one spec
npm run test:unit                                        # the whole suite

    Specs live beside the code in __tests__/ folders and import describe/it/expect explicitly (no globals). The suite is not part of mvn verify: npm test is a deliberate no-op stub. Import aliases resolve through .quasar/tsconfig.json, so in a git worktree make sure that worktree has its own .quasar/ (run npm ci there), otherwise specs can run against another checkout's code. See frontend-unit-tests.md.

    The dev workflow

    Branches and commits

    master is protected by the NoDirectPush ruleset (.github/rulesets/no-direct-push.json): no direct pushes, no force-push, no deletion, changes only through a PR. Branch names in use are feat/…, fix/…, chore/…, docs/… and story/<story-id>-<slug> for planned stories (e.g. story/12-4-coach-facing-player-detail-page). Commit subjects follow Conventional Commits with the touched modules as scope, as git log shows:

    feat(admin): GDPR tracker, finance overview, stuck-booking force-complete, ... (#314)
fix(session,video,payment,notification,frontend): role guards for self-registered players, ... (#307)
docs(dev-docs): refresh every page against current master, add Outbox and Frontend pages (#315)
build(deps): bump actions/setup-java from 6.0.1 to 6.1.0 (#285)
chore(deps): bump tomcat-embed-core to 10.1.59 and guava to 33.7.2 for new Trivy CVEs (#308)

    PRs are squash-merged, so the PR title becomes the single commit on master with (#NNN) appended: write the PR title as a conventional commit. Story work often also references its story id (deferred-165, 12.10) in the title.

    CI jobs

    WorkflowTriggerJobWhat it does
    pr-build.ymlPR to masterbuild requiredmvn -B verify (frontend build, all unit tests, all ITs), then assert-context-count.sh build.log 17 (fails if the IT JVM builds more than 17 Spring contexts) and container-sampler.sh (at most one Postgres/Redis/storage container alive at once). Uploads surefire/failsafe reports as an artifact.
    docker-image requiredBuilds the image without pushing, asserts its embedded git.properties matches the commit, and fails on CRITICAL/HIGH Trivy findings not listed in .trivyignore.
    frontend-quality.github/actions/frontend-quality: prettier --check "**/*.{js,vue,scss,json}" and eslint . (with NODE_ENV=production, so a stray debugger fails). Not a required check, but the same action gates the image publish on master, so treat red as blocking. Run npx prettier --write on what you touched.
    frontend-unit-tests.ymlPR touching src/frontend/**, the frontend-tests label, or manualfrontend-unitnpm run test:unit:ci twice, with TZ=UTC and TZ=America/New_York. Not required, but do not merge red.
    ci.ymlPush to mastertestmvn -B verify again on the merged commit.
    frontend-qualitySame composite action as on PRs.
    build-and-pushneeds: [test, frontend-quality]. Pushes the image to GHCR (sha-<short> tag, plus :latest behind an ordering guard) and verifies its provenance.
    deploy.ymlManualdeployDeploys a given image tag to production over SSH, smoke-tests it and auto-reverts on failure.
    apply-branch-ruleset.ymlManualapplyRe-applies the NoDirectPush ruleset from the repo file.

    GitHub CI is the full gate. Do not run the full mvn verify locally before pushing. It is slow, ties up Docker, and is exactly what pr-build.yml runs anyway, along with the context-count and container-ceiling checks you cannot reproduce locally. Run the targeted unit/IT/Vitest commands above for what you changed, plus Prettier/ESLint on touched frontend files, push, and let CI do the rest. If CI goes red, download the test-reports-pr-<n> artifact.

    Your first PR, end to end

    git switch master && git pull
git switch -c fix/short-description
# ...change code, run the targeted tests...
git commit -m "fix(booking): reject reschedule into a blocked slot"
git push -u origin fix/short-description
gh pr create --base master --title "fix(booking): reject reschedule into a blocked slot" --body "..."
# wait for build + docker-image (and frontend-quality / frontend-unit if they ran), get review,
# then squash-merge, delete the branch, and git pull master

    If your change adds a Flyway migration, read Database first: the next version follows the current highest (ls src/main/resources/db/migration | sort -V | tail -1) and lint tests run in the build. If it adds a lock call site or an @Scheduled method, read the NOWAIT and ShedLock sections of Database and Scheduled Jobs; audit tests pin those counts.
