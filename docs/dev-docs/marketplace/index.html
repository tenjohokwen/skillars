Marketplace

Coach discovery, search/filter, and the multi-step profile builder coaches use to become bookable.

Business Overview

Marketplace answers the first question every Parent or Player has: "which coach should I book?" It is the public storefront of Skillars — a searchable, filterable directory of coach profiles (city, district, language, price range, age group coached, skill/specialty) and the coach-facing wizard used to build and publish that storefront listing in the first place. Everything downstream — booking, payments, reviews — points back at a CoachProfile as the anchor identity for "this is a coach on the platform."

Two personas touch this module directly:

  • Parents / Players — anonymous or authenticated users browse GET /api/marketplace/coaches (permit-all, no login required) and view a single coach's public profile page, including reviews, media gallery, pricing and session packs.
  • Coaches — authenticated users with ROLE_COACH build their profile through a strict 5-step wizard (ProfileBuilderResource) before it can be published and appear in search.

Key business rules found in the code:

  • City is mandatory for every search. CoachSearchSpecification.inCity() always produces a predicate, and the repository's language-matching native query is explicitly city-scoped "to avoid a global scan of all active coaches" — there is no platform-wide coach search.
  • Only ACTIVE and REDUCED profiles are searchable. REDUCED coaches (a status presumably driven by moderation/enforcement in the Admin module) still appear in results but are always sorted after ACTIVE coaches (CoachSearchSpecification.isActive() + the status-first Sort in CoachSearchService.buildSort()).
  • The profile builder is a strict, ordered state machine. Step 2 requires Step 1's display name to be set; Step 3 requires specialties + age groups from Step 2; Step 4 requires pricing from Step 3; Step 5 requires an availability window from Step 4. Skipping ahead throws MarketplaceException("marketplace.stepOutOfOrder", ...).
  • Publishing re-validates everything, not just the last step. publishProfile() calls validateAllStepsComplete(), checking display name, specialties, age groups, pricing, and availability windows all over again before flipping status from DRAFT to ACTIVE and provisioning a default SCOUT-tier CoachSubscription.
  • Availability windows must not overlap and must be well-formed. validateAvailabilityWindows() rejects an end time before/equal to its start time and rejects overlapping windows on the same day of week.
  • Minimum-rating filtering is a stub. CoachSearchParams.minRating is typed but CoachSearchSpecification has no rating lower-bound predicate wired to it beyond hasMinRating() — the DTO comment for it explicitly says "stub: > 0 returns 0 results until Epic 9", so don't trust it as a real feature yet.
  • Capability badges are scaffolded but empty. CoachCapabilityService always returns an empty badge list per coach — it's wired for a future epic that will source badges from activity in other modules (e.g. session completion counts).

Key services

CoachSearchSpecificationStatic factory of composable Specification<CoachProfile> predicates (status, city, district, skill, age group, min/max price via subqueries, min rating) used by CoachSearchService.

CoachCapabilityServiceScaffold for capability badges (per-coach and batch); currently returns empty lists for every coach. Reads a configurable activity-window setting via ConfigService for future use.

PlayerProfileServiceRead-only lookups against security.repo.PlayerProfile/UserRepository: parent id, player name/age, parent email/name by player id. Used by other modules (video, development) that need player/parent context but live outside security.

Domain events

Marketplace does not currently publish its own domain events. It consumes one: filestorage.event.StorageObjectConfirmedEvent, handled by CoachProfilePhotoEventListener to sync a confirmed photo upload back onto the coach's photoUrl. Elsewhere in the platform, booking.contract.CoachReliabilityStrikeQueuedEvent and services in payment/admin write directly into CoachReliabilityStrikeRepository — marketplace only reads that table back out.

Cross-module dependencies observed in imports: infrastructure.exception (ResourceNotFoundException), infrastructure.sanitizer (ContactDetailSanitizer for bio text), filestorage.event/repo/service (photo upload confirmation + storage key parsing), security.contract.AgeTier, security.repo.PlayerProfile/PlayerProfileRepository/UserRepository, security.service.SecurityUtil, reviews.contract.ReviewListResponse and reviews.service.ReviewQueryService (profile page reviews), and config.service.ConfigService (capability badge window setting).

Key Flows

Browsing / searching coaches

sequenceDiagram
  participant Parent as Parent/Player (browser)
  participant Resource as CoachMarketplaceResource
  participant Search as CoachSearchService
  participant Spec as CoachSearchSpecification
  participant DB as coach_profiles (JPA)
  participant Enrich as Specialty/Pricing/Strike/Capability repos

  Parent->>Resource: GET /api/marketplace/coaches?city=...&skill=...&page=0
  Resource->>Search: searchCoaches(params, page, size)
  Search->>Spec: build(params)
  Spec-->>Search: Specification (status ACTIVE/REDUCED, city, district, skill, ageGroup, price, rating)
  Search->>DB: findAll(spec, pageable)
  DB-->>Search: Page of CoachProfile
  Search->>Search: applyLanguageFilter() via native query (post-fetch)
  Search->>Enrich: batch load specialties/prices/strikes/badges for page IDs only
  Enrich-->>Search: maps keyed by coachId
  Search->>Search: assemble CoachCardDto, sortPage() if sortBy=price
  Search-->>Resource: CoachSearchResponse
  Resource-->>Parent: 200 OK (coach cards + pagination)

A search always requires a city, which keeps the specification and the native language query scoped and cheap. Only ACTIVE/REDUCED coaches are visible, with ACTIVE ranked first. Enrichment data (specialties, price, reliability strikes, capability badges) is batch-loaded only for the coaches on the current result page, avoiding N+1 queries and avoiding loading the entire city's coach roster into memory. Price sorting is applied in Java after enrichment because per-session price lives in a separate coach_pricing table, not on CoachProfile itself; this means price sort is only correct within a page, not globally across pages.

Viewing a single coach's public profile

sequenceDiagram
  participant Parent as Parent/Player
  participant Resource as CoachMarketplaceResource
  participant Profile as CoachProfileService
  participant ReviewSvc as ReviewQueryService (reviews module)
  participant Repos as Specialty/AgeGroup/Pricing/SessionPack/Availability/Media repos

  Parent->>Resource: GET /api/marketplace/coaches/{coachId}
  Resource->>Profile: getPublicProfile(coachId)
  Profile->>Profile: findById + filter status ACTIVE/REDUCED/PENDING_REVIEW
  Profile->>Repos: load specialties, age groups, pricing, session packs,
  Note over Profile,Repos: availability (-> "available" flag), reliability strikes, media gallery (top 6)
  Profile-->>Resource: CoachProfileDto (reviews field = null)
  Resource->>ReviewSvc: getFirstPageForCoach(coachId)
  ReviewSvc-->>Resource: ReviewListResponse
  Resource-->>Parent: 200 OK (CoachProfileDto with reviews populated)

The profile is visible for ACTIVE, REDUCED, and even PENDING_REVIEW coaches — otherwise a CoachProfileNotFoundException is thrown. CoachProfileService deliberately returns reviews = null in the DTO to avoid a circular dependency between the marketplace and reviews services; the controller stitches the first page of reviews back in afterward.

Coach builds and publishes a profile

sequenceDiagram
  participant Coach as Coach (ROLE_COACH)
  participant Resource as ProfileBuilderResource
  participant Service as CoachProfileService

  Coach->>Resource: PUT steps/1 (identity, bio, city, languages, timezone)
  Resource->>Service: saveStep1()
  Coach->>Resource: PUT steps/2 (specialties, age groups)
  Resource->>Service: saveStep2() - requires displayName set
  Coach->>Resource: PUT steps/3 (per-session price, session packs)
  Resource->>Service: saveStep3() - requires specialties+ageGroups set
  Coach->>Resource: PUT steps/4 (weekly availability windows)
  Resource->>Service: saveStep4() - requires pricing set, validates overlap
  Coach->>Resource: PUT steps/5 (photo key)
  Resource->>Service: saveStep5() - requires availability set, validates key prefix
  Coach->>Resource: POST publish
  Resource->>Service: publishProfile()
  Service->>Service: validateAllStepsComplete() (re-checks steps 1-4)
  Service->>Service: status DRAFT -> ACTIVE, create CoachSubscription(SCOUT)
  Service-->>Resource: ProfileBuilderStatusResponse
  Resource-->>Coach: 200 OK (profile now searchable)

Each step is guarded against being submitted out of order, and the profile only becomes searchable after publishProfile() re-validates every prior step and flips status from DRAFT to ACTIVE. The photo itself is uploaded separately through filestorage; step 5 only records the storage key, and the actual photoUrl can also be set asynchronously later by CoachProfilePhotoEventListener when the upload is confirmed.

Conventions & Gotchas

Timezones are validated as real IANA zone ids. Both ProfileBuilderStep1Request.canonicalTimezone and each ProfileBuilderStep4Request.AvailabilityWindowRequest.canonicalTimezone carry @IanaTimezone (from infrastructure.validation) on top of @NotBlank. This matters downstream: AvailabilityService.hasBookingConflict and the booking overlap checks resolve local times against these strings, so an unparseable zone would fail deep inside booking rather than at the request boundary.

Annotate list elements, not just the list. ProfileBuilderStep4Request.windows is declared List<@NotNull @Valid AvailabilityWindowRequest>. Bean Validation skips the cascade on a null element, so with only @Valid on the list a payload of {"windows":[null]} passed every constraint and then NPE'd inside CoachProfileService.validateAvailabilityWindows as a 500. Repeat this element-level pattern for any new collection field.

CoachProfileRepository.findByIdForUpdate is the platform's booking serialization point. There is no "coach calendar" row, so booking takes a PESSIMISTIC_WRITE lock on the CoachProfile row (with a 5s jakarta.persistence.lock.timeout hint) to serialize concurrent booking creates/accepts for the same coach. Be aware that a change to this entity's write paths can affect booking throughput — see Booking's slot-exclusivity section.

Search always needs a city. There is no cross-city or "search everywhere" mode — every specification and the native language-filter query are scoped to city. If you're adding a new filter, keep it inside this city-scoped query pattern rather than introducing an unscoped scan.

The profile builder wizard enforces strict ordering server-side, not just client-side. Each saveStepN method checks that the previous step's data actually exists in the DB before accepting new data, and throws MarketplaceException("marketplace.stepOutOfOrder", ...) otherwise. Don't assume the frontend wizard UI is the only thing preventing out-of-order submission.

Photo URLs are validated against a strict key prefix. saveStep5() rejects any photoUrl that doesn't start with coach_profile/{userId}/ — this prevents a coach from pointing their profile photo at an arbitrary storage object belonging to someone else. Any new code that sets photoUrl directly (as CoachProfilePhotoEventListener does) should preserve this invariant.

Rating and review count are denormalized onto CoachProfile. average_rating/review_count are not computed by marketplace — they're written by reviews.service.CoachRatingService.recompute() via the updateRatingAggregate bulk update query. If ratings look stale, look in the reviews module, not here.

minRating and capability badges are not fully implemented yet. CoachSearchParams.minRating is a stub per its own code comment (returns 0 results for now, pending Epic 9), and CoachCapabilityService always returns empty badge lists. Don't build features on top of these assuming they filter/populate anything today.

Related Modules

  • Reviews — supplies the review list shown on a coach's public profile and owns the rating/review-count aggregate written back onto CoachProfile.
  • Booking — reads coach profiles, pricing, session packs, and availability windows to schedule sessions; queues reliability strikes that marketplace surfaces.
  • Payment — reads/writes CoachSubscription tier and billing, session pack pricing, and reliability strikes (e.g. ReliabilityStrikeService).
  • Filestorage — owns the actual coach profile photo upload pipeline; marketplace only listens for its confirmation event and stores the resulting key.
  • Security — supplies AgeTier, SecurityUtil for current-user resolution, and player/parent identity data used by PlayerProfileService.
  • Admin — moderation/enforcement flows (GDPR export/erasure, coach enforcement, disputes) that read and mutate marketplace data such as profile status and reliability strikes.
  • Development, Video, Session, Messaging — all read coach/player identity and profile data from marketplace to attribute drills, videos, session plans, and conversations to the right coach.
  • Config — provides the configurable activity-window setting used by CoachCapabilityService.
