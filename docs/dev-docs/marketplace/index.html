    Marketplace

    Coach discovery (search/filter and the public profile), the multi-step profile builder coaches use to become bookable, and the coach's own profile/gallery management.

    Business Overview

    Marketplace answers the first question every Parent or Player has: "which coach should I book?" It is the public storefront of Skillars — a searchable, filterable directory of coach profiles (city, district, language, price range, age group coached, skill, minimum rating) and the coach-facing wizard used to build and publish that listing. Everything downstream — booking, payments, reviews, enforcement — points back at a CoachProfile as the anchor identity for "this is a coach on the platform", and its row is also the platform's per-coach lock.

    Two personas touch this module directly:

    • Parents / Players — anonymous or authenticated users browse GET /api/marketplace/coaches (permit-all) and open a coach's public profile with reviews, a media gallery (up to 6 images), pricing and session packs.
    • Coaches — users with ROLE_COACH build their profile through a strict 5-step wizard (ProfileBuilderResource), publish it, and later edit it from "My Profile": re-submit any step, remove their photo, and manage their public gallery.

    Key business rules found in the code:

    • City is mandatory for every search (@RequestParam @NotBlank), and CoachSearchSpecification.inCity() always produces a predicate — there is no platform-wide search.
    • Only ACTIVE and REDUCED profiles are searchable; REDUCED coaches (set by payment.ReliabilityStrikeService or admin enforcement) are sorted after ACTIVE ones. The public profile page additionally shows PENDING_REVIEW profiles.
    • The profile builder is an ordered state machine. Step 2 needs Step 1's display name, Step 3 needs specialties + age groups, Step 4 needs pricing, Step 5 needs an availability window; otherwise MarketplaceException("marketplace.stepOutOfOrder").
    • Publishing re-validates every step and is only allowed from DRAFT (marketplace.alreadyPublished for ACTIVE, marketplace.profileNotEligibleToPublish for SUSPENDED/REDUCED/PENDING_REVIEW/DEACTIVATED). It sets ACTIVE + status_changed_at and find-or-creates a CoachSubscription (default SCOUT, an existing paid tier is preserved).
    • Availability windows must have end > start and must not overlap on the same day. Every window is stamped with the profile's canonical_timezone (the per-window value in the request is validated but discarded); changing the profile timezone in Step 1 re-stamps all windows.
    • City and timezone must be plausible together. CityTimezoneValidator rejects a known city paired with a zone in a different IANA region (marketplace.cityTimezoneMismatch) and fails open on anything it cannot classify (unknown or ambiguous city, no-slash zone ids, UTC aliases).
    • A suspended coach cannot rewrite availability (Step 4 throws COACH_UNAVAILABLE after taking the profile lock).
    • Capability badges are still a scaffold. CoachCapabilityService returns empty badge lists for every coach.

    Key services

    ServiceOrchestrates
    CoachSearchServiceBuilds the Specification, paginates in the DB, applies the language filter post-fetch (native ANY(languages) query), batch-loads specialties/prices/90-day strike counts/badges for the page only, signs photo keys, and sorts by price within the page.
    CoachSearchSpecificationComposable predicates: status ACTIVE/REDUCED, city, district, skill, age group, min/max price (EXISTS subqueries on coach_pricing), and averageRating >= minRating when minRating > 0.
    CoachProfileServiceWizard steps 1–5 + publish, getOwnProfile (DRAFT-safe full profile), deletePhoto, getPublicProfile (4 queries, guarded by CoachPublicProfileQueryCountIT), getSupportedTimezones, and lookups used across the platform (getCoachIdByUserId, getCoachSubscriptionTier, getDisplayNamesByIds, validateReadyForActivation for admin reinstatement).
    CoachGalleryServiceThe coach's own gallery (#312): list, add an uploaded image, delete. Re-validates the confirmed storage object server-side and serialises adds/deletes on the profile row lock.
    CityTimezoneValidatorPackage-private plausibility check for Step 1 (small hand-maintained city→region map, fail-open).
    CoachCapabilityServiceBadge scaffold (single + batch); reads marketplace.capability.badge.activity.window.days (default 90) for future use.
    CoachProfilePhotoEventListenerOn filestorage's StorageObjectConfirmedEvent for a coach_profile/{userId}/… key, sets that coach's photoUrl to the key.
    PlayerProfileServiceRead-only player/parent lookups over security repositories (parent id, player name(s)/age, parent email/name), used by development, messaging and video.

    Domain events

    Marketplace publishes no domain events. It consumes one: filestorage.event.StorageObjectConfirmedEvent (synchronous @EventListener, inside the confirm transaction) in CoachProfilePhotoEventListener. Profile status is changed from outside the module by payment.ReliabilityStrikeService (PENDING_REVIEW/REDUCED) and admin.AdminCoachEnforcementService (SUSPENDED, reinstatement to ACTIVE/DRAFT); the rating aggregate by reviews; verification_tier by the admin console via CoachProfileRepository.updateVerificationTier.

    Cross-module dependencies observed in imports: infrastructure.exception, infrastructure.persistence.PessimisticLockRetryer, infrastructure.sanitizer.ContactDetailSanitizer (bio), infrastructure.validation.IanaTimezone, filestorage (FileStorageService for signed URLs/soft delete/findActiveObject, StorageKeyGenerator, StorageObjectConfirmedEvent), security (AgeTier, SecurityUtil, PlayerProfileRepository/UserRepository), booking.contract.BookingError (Step 4 suspended-coach error), reviews (ReviewQueryService, ReviewListResponse) and config.ConfigService. In the other direction, admin, booking, development, messaging, payment, reviews, security, session and video all import marketplace classes — mostly CoachProfileService/CoachProfileRepository.

    Key Flows

    Browsing / searching coaches

    sequenceDiagram
  participant Parent as Parent/Player (browser)
  participant Resource as CoachMarketplaceResource
  participant Search as CoachSearchService
  participant Spec as CoachSearchSpecification
  participant DB as coach_profiles (JPA)
  participant Enrich as Specialty/Pricing/Strike/Capability repos

  Parent->>Resource: GET /api/marketplace/coaches?city=...&skill=...&page=0
  Resource->>Search: searchCoaches(params, page, size)
  Search->>Spec: build(params)
  Spec-->>Search: Specification (status, city, district, skill, ageGroup, price, minRating)
  Search->>DB: findAll(spec, pageable sorted status ASC then name or rating)
  DB-->>Search: Page of CoachProfile
  Search->>Search: applyLanguageFilter() via native query (post-fetch)
  Search->>Enrich: batch load specialties/prices/strikes/badges for page IDs only
  Enrich-->>Search: maps keyed by coachId
  Search->>Search: CoachCardDto (signed photo URL), sortPage() if sortBy=price
  Search-->>Resource: CoachSearchResponse
  Resource-->>Parent: 200 OK (coach cards + pagination)

    The DB sort is status ASC first (ACTIVE sorts before REDUCED alphabetically — the enum is stored as a string), then displayName or averageRating DESC NULLS LAST. Enrichment is batch-loaded only for the current page. Price sort happens in Java after enrichment because the price lives in coach_pricing, so it is only correct within a page. With a language filter, totalElements comes from a separate countByLanguageAndCity query; see the gotcha below on why language-filtered paging is approximate.

    Viewing a single coach's public profile

    sequenceDiagram
  participant Parent as Parent/Player
  participant Resource as CoachMarketplaceResource
  participant Profile as CoachProfileService
  participant ReviewSvc as ReviewQueryService (reviews module)
  participant Repos as marketplace repos + FileStorageService

  Parent->>Resource: GET /api/marketplace/coaches/{coachId}
  Resource->>Profile: getPublicProfile(coachId)
  Profile->>Repos: (1) profile LEFT JOIN pricing, status ACTIVE/REDUCED/PENDING_REVIEW
  Profile->>Repos: (2) facts UNION ALL: specialties, age groups, availability count, 90-day strikes
  Profile->>Repos: (3) session packs, (4) media gallery (first 6)
  Profile->>Repos: sign photo key and gallery keys
  Profile-->>Resource: CoachProfileDto (reviews = null)
  Resource->>ReviewSvc: getFirstPageForCoach(coachId)
  ReviewSvc-->>Resource: ReviewListResponse
  Resource-->>Parent: 200 OK (CoachProfileDto with reviews populated)

    Any other status (incl. DRAFT) is a CoachProfileNotFoundException. The query count is fixed at four regardless of profile size (CoachPublicProfileQueryCountIT). Photo and gallery values are stored as private-bucket keys and turned into signed download URLs on the way out; legacy absolute gallery URLs pass through. The service returns reviews = null to avoid a marketplace↔reviews service cycle; the controller stitches reviews in.

    Coach builds and publishes a profile

    sequenceDiagram
  participant Coach as Coach (ROLE_COACH)
  participant Resource as ProfileBuilderResource
  participant Service as CoachProfileService

  Coach->>Resource: PUT steps/1 (identity, bio, city, languages, timezone)
  Resource->>Service: saveStep1() - CityTimezoneValidator, lock, re-stamp windows if zone changed
  Coach->>Resource: PUT steps/2 (specialties, age groups)
  Resource->>Service: saveStep2() - requires displayName, delete + flush + reinsert
  Coach->>Resource: PUT steps/3 (price, duration, session packs)
  Resource->>Service: saveStep3() - requires specialties and age groups
  Coach->>Resource: PUT steps/4 (weekly availability windows)
  Resource->>Service: saveStep4() - requires pricing, overlap check, lock, not SUSPENDED
  Coach->>Resource: PUT steps/5 (photo key)
  Resource->>Service: saveStep5() - requires availability, key prefix coach_profile/userId/
  Coach->>Resource: POST publish
  Resource->>Service: publishProfile()
  Service->>Service: requireDraftStatus, lock + refresh, re-check, validateAllStepsComplete
  Service->>Service: status ACTIVE, statusChangedAt, find-or-create CoachSubscription(SCOUT)
  Service-->>Resource: ProfileBuilderStatusResponse
  Resource-->>Coach: 200 OK (profile now searchable)

    Step 1 creates the DRAFT profile if none exists. Steps can be re-submitted after publishing ("My Profile" edits reuse the same endpoints); Steps 2 and 3 delete and re-insert their child rows with an explicit flush() in between, because Hibernate otherwise orders INSERTs before DELETEs and trips uq_coach_specialty/uq_coach_age_group/uq_session_pack. The photo is uploaded through filestorage (sign → PUT → confirm); step 5 records the key, and CoachProfilePhotoEventListener also sets it when the upload is confirmed.

    Coach adds a gallery image

    sequenceDiagram
  participant Coach as Coach (ROLE_COACH)
  participant Storage as filestorage StorageResource
  participant Resource as ProfileBuilderResource
  participant Gallery as CoachGalleryService

  Coach->>Storage: POST /api/storage/sign/upload (entity coach_gallery, entityId = own userId)
  Coach->>Storage: PUT bytes, then POST /api/storage/confirm/{key}
  Coach->>Resource: POST /api/marketplace/coaches/me/profile/gallery {key}
  Resource->>Gallery: addImage(userId, key)
  Gallery->>Gallery: key prefix coach_gallery/userId/, findActiveObject: owner, JPEG/PNG/WebP, max 5 MB
  Gallery->>Gallery: lock CoachProfile row (NOWAIT + retry)
  Gallery->>Gallery: same key already linked? return it. 6 items already? galleryFull
  Gallery-->>Coach: 201 CoachMediaItemDto (signed URL)

    Validation uses the HEAD-verified storage record, never the client's declared type/size. Images only — short video clips would need the video module and are not supported. Delete takes the same lock, removes the row and soft-deletes the object, tolerating an already-gone object or a stale created_by (as deletePhoto does). GDPR coach erasure deletes coach_media rows and enqueues their coach_gallery/* blobs (admin.GdprErasureService).

    Conventions & Gotchas

    CoachProfileRepository.findByIdForUpdate is the platform's per-coach serialization point. It is PESSIMISTIC_WRITE with jakarta.persistence.lock.timeout = 0, i.e. NOWAIT — not a blocking wait. Every call site wraps it in PessimisticLockRetryer.withBoundedRetry (retry from a savepoint, ~3.2s budget); exhausting the budget surfaces as a 409 from ApiAdvice. Booking create/accept, reschedule, duplicate-next-week, admin enforcement, strikes, Step 1/4, publish, photo delete and gallery writes all take it. Lock, then entityManager.refresh(profile, PESSIMISTIC_WRITE), then re-check state — a check made before the lock is only a fast path.

    CoachProfile has no @Version and no @DynamicUpdate. A save() rewrites every column, so an unlocked read-modify-save can silently revert a concurrent status change (e.g. suspendCoach). That is why the status-sensitive writers lock first, and why verification_tier is updatable = false (only the admin bulk UPDATE writes it). Any new writer of this entity should either lock-and-refresh or use a targeted @Modifying UPDATE (as updateRatingAggregate/markRecapDataErased do).

    Timezones are validated as real IANA region ids, and the picker comes from the server. ProfileBuilderStep1Request.canonicalTimezone (and each Step 4 window's) carries @IanaTimezone. The frontend must offer GET …/me/profile/timezones, not the browser's Intl zone — a browser on newer tzdata than the JVM (e.g. Europe/Kyiv) used to make Step 1 uncompletable. The profile's zone is authoritative for all availability (deferred-140): booking resolves windows against it.

    Annotate list elements, not just the list. ProfileBuilderStep4Request.windows is List<@NotNull @Valid AvailabilityWindowRequest>. With only @Valid on the list, {"windows":[null]} passed validation and NPE'd inside validateAvailabilityWindows as a 500. Repeat this element-level pattern for new collection fields.

    Search always needs a city, and the language filter is a post-fetch step. Keep new filters city-scoped. The language filter runs after the DB page is fetched, so a language-filtered page can contain fewer than size results (or none) while later pages hold matches, and its native query only matches ACTIVE coaches — REDUCED coaches disappear when a language is given. Moving language into the Specification (e.g. a native-function predicate) would fix both.

    Storage keys, not URLs. photo_url and gallery file_url hold private-bucket object keys; always resolve through FileStorageService.signedDownloadUrl (CoachGalleryService.resolveUrl is the shared rule). Key prefixes are the ownership check: coach_profile/{userId}/ for the photo (Step 5) and coach_gallery/{userId}/ plus a storage owner check for gallery items. Preserve these if you add new writers.

    Rating and review count are denormalized onto CoachProfile by reviews.service.CoachRatingService.recompute() via updateRatingAggregate. If ratings or the minRating filter look wrong, look in reviews. (The "stub until Epic 9" comment on CoachSearchParams.minRating is stale — the filter is live.)

    CoachSubscriptionTier declaration order is load-bearing. SCOUT, INSTRUCTOR, ACADEMY is asserted in a static initializer because the session module's feature-gate "minimum tier" lookup iterates values() in order.

    Related Modules

    • Reviews — supplies the review list on the public profile and writes the rating aggregate back onto CoachProfile.
    • Booking — reads profiles, pricing, availability and the profile timezone; locks the profile row to serialise per-coach booking writes.
    • Payment — issues reliability strikes (and the resulting PENDING_REVIEW/REDUCED status), manages CoachSubscription tiers and purchasable pack tiers.
    • Admin — coach enforcement (suspend/reinstate, strike deletion), verification tier, GDPR erasure of coach profile text, gallery and recap data.
    • Filestorage — owns the photo and gallery upload pipeline (coach_profile, coach_gallery entities) and signed download URLs.
    • Security — AgeTier, SecurityUtil, and player/parent data behind PlayerProfileService.
    • Session, Development, Video, Messaging — resolve coach ids, tiers and display names through CoachProfileService.
    • Config — the capability-badge activity-window setting.
