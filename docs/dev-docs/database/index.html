    Database & Migrations

    How Postgres is carved up per module, how schema changes are applied, and the handful of rules that will bite you the first time you add a migration.

    Shape of the Database

    One Postgres database (Postgres 17 in both docker-compose.yml and the test container), split into nine schemas — a main schema for cross-cutting and identity tables, plus one schema per domain module that owns persistent state. Modules do not share tables: a cross-module reference is a plain id column, never a foreign key into another module's schema (with the deliberate exceptions noted below). This is what keeps the module boundaries described elsewhere in these docs real at the data layer and not just in package names.

    The V138 rebaseline

    Migrations live in src/main/resources/db/migration/ and are named V<n>__snake_case_description.sql. The whole pre-production history (V02–V137, 131 files) was squashed by skillars-deferred-112 into two generated files: V138__baseline_schema.sql (pure DDL from pg_dump --schema-only) and V139__baseline_seed_data.sql (160 seed rows: platform_config, authorities, skill_definitions, platform drills). There are currently 74 files, V138–V223, with gaps — V174, V176–V177, V179–V180, V190, V194, V196 and V201–V204 were never used, which Flyway does not mind — but never back-fill a gap: always take a number above the current latest. Older migration numbers you'll see quoted in code comments (V59, V87, V128 …) refer to the deleted history — recover any of them with git show 4a3f218d:src/main/resources/db/migration/<file> (the last pre-squash commit).

    A local database that predates the squash fails Flyway validation with "Detected applied migration not resolved locally". Drop and recreate it (dropdb skillars && createdb skillars, then boot). Don't use flyway repair or ignoreMigrationPatterns. Procedure: docs/deployment/migration-rebaseline.md.

    Run mvn clean after migrations are deleted or renamed. target/classes/db/migration is not pruned, so stale files stay on Flyway's classpath — after the squash this surfaced as ERROR: schema "admin" already exists, which looks nothing like a build problem.

    Migration conventions (enforced from V140 on)

    Every migration above V139 must be online-safe for a rolling deploy. The authority is docs/deployment/migration-conventions.md; the mechanical subset is enforced by MigrationConventionLintTest (unit-test phase, no container) using src/test/java/com/softropic/skillars/db/MigrationLint.java. In short:

    • Expand/contract. New columns nullable or defaulted; NOT NULL later. Enum/CHECK widening lands a release before the first write of the new value.
    • SET LOCAL lock_timeout before any lock-taking DDL (plain SET leaks into later migrations in the same run), or an explicit -- migration-lint: allow-unbounded-lock-wait <reason>.
    • FK / CHECK on a growing table → ADD CONSTRAINT … NOT VALID, then VALIDATE CONSTRAINT later. Small admin tables opt out with -- migration-lint: allow-validating-constraint (see V162, V171).
    • DROP is last and guarded: IF EXISTS plus -- migration-lint: drop-prepared-in: V<n> naming the release that removed the last reader (V141 → V142 is the worked example).
    • Backfills are batched, via the executeInTransaction=false sidecar (V<n>__x.sql.conf).
    • CREATE INDEX CONCURRENTLY does not work here — Flyway's own bookkeeping connection holds a transaction open for the whole migrate(), so a concurrent build self-deadlocks. Use a plain CREATE INDEX with -- migration-lint: allow-blocking-index <reason> and get sign-off.
    • INSERT INTO main.platform_config omits id (identity column) and uses ON CONFLICT (key) DO NOTHING — see V156.

    Many recent migrations take a documented "same-release exception" justified by "no production deployment yet / prod is not live": V169 and V173 ship an index with the code that needs it, and almost every migration from V182 to V223 skips NOT VALID/VALIDATE (marker allow-validating-constraint), builds a plain index (allow-blocking-index), runs a single-transaction backfill (allow-full-table-dml, V178) or ships a CHECK widening together with its first write (rule 5). That justification expires with the first production deploy — after it, copy the conventions, not these precedents. (V197 is the exception that already does it properly: its status CHECKs are re-added NOT VALID.)

    Auditing: Hibernate Envers

    Six entity classes carry @Audited — User, Authority, SecKey, Secret, PersistentToken, and VideoModerationScan. (AbstractAuditingEntity also carries the annotation, but as a @MappedSuperclass it only governs which of its columns appear in an audit row — extending it does not by itself make an entity audited.) Envers writes a companion *_aud table per audited entity plus the shared revision table main.revinfo (with revinfo_seq), all in main (org.hibernate.envers.default_schema: main, store_data_at_delete: true). Since generate-ddl was removed, a new audited entity needs its *_aud table written by hand — V148's user_authority_aud is the template. Separate from Envers, main.audit_log is the security audit trail (platform.security.audit: AuditLog, written by TrailService).

    Entity Conventions

    Most entities extend infrastructure.persistence.BaseEntity or AbstractAuditingEntity. See Infrastructure for the full detail; the parts that constrain your migrations:

    • IDs are TSIDs (@Id @Tsid Long on BaseEntity) — time-sortable and cheaper to index than a random UUID. Column type is BIGINT. Many newer tables (session_pack_purchases, video tables, user_notifications, appeals, coach_payout_debts) use UUID keys, some use a natural key (charge_disputes by Stripe dispute id, pack_session_refunds by booking id) and some outbox tables use identity columns; check the entity before assuming.
    • Auditing columns — created_by/created_date/ last_modified_by/last_modified_date, plus status, request_id, and session_id on anything extending AbstractAuditingEntity. Your CREATE TABLE must include them.
    • Timestamps are TIMESTAMPTZ, mapped to Instant (a few legacy "user" columns are still timestamp without time zone). See docs/handling-time.md for the wider timezone conventions.
    • Hikari runs with auto-commit: false (with hibernate.connection.provider_disables_autocommit: true). Anything not inside a Spring transaction does not commit — see the test notes below.
    • Optimistic locking (@Version) on rows several paths full-row save (Booking, Video, Dispute, Drill, EnvelopeEntity, CoachStripeAccount, LoginAttempt, pack purchases/tiers, tokens, since V188 CoachProfile and Session, and since V197 PaymentCoachSubscription/PaymentPlayerSubscription). A new version column is bigint NOT NULL DEFAULT 0 (metadata-only on Postgres, no backfill). A losing save throws ObjectOptimisticLockingFailureException, which ApiAdvice maps to 409. Every @Modifying UPDATE against such a table must SET version = version + 1 or be allow-listed with a reason in NativeModifyingVersionAuditTest. And never re-read a @Version entity you already loaded unlocked with a locked entity query: Hibernate's lock upgrade version-checks it and throws StaleObjectStateException if the row moved — lock by id first (scalar query or id-only lookup), as CoachProfileRepository.findByIdForUpdate and BookingRepository.findIdsByCoachIdAndStatusIn do.

    Locking Conventions

    Rows that more than one request can mutate concurrently (bookings, batches, reschedule requests, pack purchases, player and coach profiles, sessions, drills, videos, reviews, users, Stripe customers) are locked with findByIdForUpdate — a @Lock(PESSIMISTIC_WRITE) query carrying @QueryHints(jakarta.persistence.lock.timeout = "0"), i.e. FOR UPDATE NOWAIT. A NOWAIT lock fails instantly on contention, so every such call is wrapped in infrastructure.persistence.PessimisticLockRetryer.withBoundedRetry(lockName, supplier).

    PieceBehaviour
    PessimisticLockRetryerFlushes, takes a JDBC savepoint via Session.doWork (declarative NESTED is unavailable — DefaultJpaDialect has no savepoint support), runs the supplier, and on PessimisticLockingFailureException rolls back to the savepoint and retries with jittered backoff. Defaults app.locking.retry.max-attempts=8, app.locking.retry.initial-backoff-ms=100 (≈3.2s worst case, holding the pooled connection). Exhaustion rethrows the exception, which ApiAdvice maps to a 409. Metrics: persistence.lock_retry timer and .retries/.exhausted counters, tagged lock and outcome.
    PessimisticLockRetryerCallSiteAuditTest (src/test/.../infrastructure/persistence/)Source-text scan of src/main/java. (1) Pins EXPECTED_CALL_SITE_COUNT = 64 .withBoundedRetry( sites and fails if any retried lambda contains a write (.save(, .delete(, publishEvent(, new …Event(, .send(, .enqueue(, RestTemplate) — the supplier can run more than once, so it must be a read (lock + optional entityManager.refresh); writes go after it returns. (2) Fails if a file calls a NOWAIT lock method (map NOWAIT_LOCK_METHODS_BY_REPOSITORY_TYPE) with no withBoundedRetry in the file. (3) Fails if a repository method with lock.timeout = "0" is missing from that map. For CoachProfileRepository and SessionRepository the registered NOWAIT method is lockByIdForUpdate (a scalar id lock); findByIdForUpdate there is a default method that calls it and then findById, and the scan (NOWAIT_DELEGATING_DEFAULT_METHODS) treats both names as the NOWAIT lock. Adding a call site means bumping the count and adding a line to its Javadoc history.
    Deliberately blocking locksVideoQuotaRepository, CoachPayoutRepository, MessageRepository and CoachReviewRepository.findByIdForUpdate (as opposed to its findByIdForUpdateNoWait) have no NOWAIT hint and no retry wrapper, by design.
    Claim-style queuesSchedulers and outbox drainers use FOR UPDATE SKIP LOCKED batch claims (often with a run-scoped claimed_at) instead — see Scheduled Jobs.

    REQUIRES_NEW + a row the caller already wrote = self-deadlock. If the outer transaction has written (and so locked) a row, an inner REQUIRES_NEW transaction that NOWAIT-locks the same row fails with Postgres 55P03 every time — the retryer cannot help, because the holder is its own suspended caller — and surfaces as a 409. Check before the write, or move the lock into the outer transaction.

    Patterns Worth Knowing

    Constraints as the last line of defence

    Several invariants are enforced in the database rather than only in application code, because more than one code path writes the same table. The worked example is booking.bookings' excl_bkg_coach_slot_overlap — an EXCLUDE USING gist (coach_id WITH =, tstzrange(requested_start_time, requested_end_time, '[)') WITH &&) over the committed statuses — so no two live bookings can hold overlapping time for the same coach, including from BookingBatchService and RescheduleService, which skip the application-layer pre-check. Partial unique indexes play the same role for "at most one active X" rules (V172, V173, V169), and per-type partial unique indexes on payment.parent_credit_ledger (uq_pcl_booking_refund, uq_pcl_booking_refund_reversal, uq_pcl_batch_share_refund, uq_pcl_chargeback_credit_*) make money-moving writes idempotent. That ledger is also append-only: trg_ledger_no_update/trg_ledger_no_delete (payment.enforce_ledger_append_only()) reject any UPDATE or DELETE, so a ledger column can never be backfilled — V208 adds spend_only_amount with no backfill for exactly that reason. Violations surface as DataIntegrityViolationException and are mapped by platform.security.api.ApiAdvice's CONSTRAINT_MAPPINGS/CONFLICT_CONSTRAINTS to a clean 409 rather than a 500.

    Adding a named constraint usually means editing ApiAdvice too. If you add a unique or check constraint a user can plausibly trip, add its name to the constraint-mapping tables so the client gets a meaningful error code instead of a generic 500.

    Enum columns carry CHECK constraints

    Enums persisted as @Enumerated(EnumType.STRING) are frequently backed by a CHECK (col = ANY (ARRAY[...])). JPA will happily write a value the CHECK rejects, so adding an enum constant without a migration fails at INSERT time, not at startup — admin_alerts_type_check (V152/V153 … V209), admin_action_log_action_type_check (V162/V171/V183/V189), envelope_entity_email_template_check (V168 … V212) and chk_ledger_type (V198/V199/V208) are the worked examples: drop and recreate the constraint with the widened list in one ALTER TABLE. Grep for the constraint name before adding a constant, and take the list from the latest migration that rebuilt it. Merge hazard: because every widening restates the full list, two branches that each widen the same CHECK both merge cleanly and the later migration silently drops the other's value — the migrations carry a "MERGE NOTE: re-union the list" comment for this. Parity ITs (EnvelopeEntitySchemaIT, AdminQueueIT, the admin action-log IT) catch the enum side. The opposite choice — no CHECK at all, for an enum expected to grow fast — is V175's.

    Seeding runtime config

    Tunables live in main.platform_config and are read through config's ConfigService. The baseline set is in V139; a migration that introduces a new key inserts it without an id and with ON CONFLICT (key) DO NOTHING — see V156. ConfigService caches for app.config.cache-ttl-seconds (300s), so a newly seeded key isn't visible instantly on other instances.

    Partial indexes for "not yet processed" scans

    Scheduled jobs that repeatedly scan for unprocessed rows are backed by partial indexes rather than full ones — e.g. idx_session_pack_purchases_expiry_notify ON (expires_at) WHERE expired_notified_at IS NULL. The index shrinks as rows are processed. If you add a "stamp a column once processed" scheduler, add the matching partial index with it. Status-scoped partial indexes must use a whitelist predicate (status IN (...)), never status <> 'X' — StatusScopedPartialIndexConventionIT enforces this across the live schema.

    GDPR tombstones

    Erasure scrubs rather than deletes some rows and leaves a sticky timestamp — player_profiles.development_data_erased_at (V151), coach_profiles.recap_data_erased_at (V166), a locked "user" row. Writers that could resurrect scrubbed data check the tombstone after taking their own row lock. If you add user content to a table, make it reachable from admin.GdprErasureService and, if a concurrent writer could re-insert it, add the same guard.

    Test Database

    • One Postgres per test JVM. config.SharedContainers holds JVM-static Testcontainers (postgres:17-alpine, Redis, SeaweedFS) — never Spring beans — shared by every context. Flyway migrates it once from V138. See docs/testing/container-architecture.md.
    • Every test method starts empty. DatabaseResetTestExecutionListener truncates application tables before each method and restores the Flyway-seeded reference data (snapshotted on first reset) — seed what you need, clean up nothing. It never truncates flyway_schema_history, main.shedlock (that silently disables every lock — it backdates lock_until instead) or the vestigial qrtz_*. See docs/testing/test-data-isolation.md.
    • Bare jdbcTemplate writes in an IT method body never commit, because Hikari's auto-commit is false. Wrap fixture writes in transactionTemplate.execute(...) (or use @Sql).
    • Two separate Instant.now() calls for a booking's start/end can violate chk_bkg_end_after_start on fast CI machines — derive end from start.
    • Scheduled jobs don't fire under the test profile; call them through the proxy and use AbstractIntegrationTest.releaseSchedulerLock(name).
    • Schema guards that run in the suite: MigrationConventionLintTest (unit phase), StatusScopedPartialIndexConventionIT, EnvelopeEntitySchemaIT, PessimisticLockRetryerCallSiteAuditTest.

    Gotchas

    A finite jakarta.persistence.lock.timeout is a no-op on this Postgres/Hibernate combination. Hibernate's PostgreSQLDialect only special-cases 0 (NOWAIT) and -2 (SKIP LOCKED) — any finite millisecond value falls through, so the query blocks indefinitely under contention. For a bounded wait use 0 plus PessimisticLockRetryer — see docs/persistence/pessimistic-lock-retry.md.

    Never edit a migration that has been applied anywhere. Flyway checksums the whole file, comments included. The V138 squash was only legal because no production database existed; that option is gone after the first production deploy. Add a new migration instead.

    The qrtz_* tables are vestigial. V138 still creates them, but Quartz is no longer a dependency: it was never used to schedule a job, and its quartz: block sat at the YAML root rather than under spring.quartz, so the clustered JDBC job store it described never took effect. Nothing reads or writes these tables. They are left in place (dropping them would be a contract migration for no gain). All background work uses Spring @Scheduled + ShedLock — see Scheduled Jobs.

    Cross-module references are plain id columns, not foreign keys. booking.bookings.session_pack_purchase_id points at payment.session_pack_purchases as a bare UUID, deliberately not a JPA association — booking must never load or mutate a pack row. Likewise admin.gdpr_requests.player_id has no FK so the request outlives the profile. Expect to write the join yourself when reporting across modules.

    Know which id space a column is in. bookings.player_id is a main.player_profiles PK, not a "user" id; resolve the human via player_profiles.user_id/parent_id. user_notifications.recipient_user_id is always a "user" id (a minor's notifications land with the parent).

    GDPR erasure bypasses the usual guards. Deletion paths used by admin.GdprErasureService (e.g. MessageRepository.deleteAllBySenderId()) ignore the report/retention predicates that normal cleanup respects. If you add a table holding user content, make sure it is covered there — and be aware the delete is unconditional.
