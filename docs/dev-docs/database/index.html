Database & Migrations

How Postgres is carved up per module, how schema changes are applied, and the handful of rules that will bite you the first time you add a migration.

Shape of the Database

One Postgres database, split into nine schemas — a main schema for cross-cutting and identity tables, plus one schema per domain module that owns persistent state. Modules do not share tables: a cross-module reference is a plain id column, never a foreign key into another module's schema (with the deliberate exceptions noted below). This is what keeps the module boundaries described elsewhere in these docs real at the data layer and not just in package names.

Video state lives in main rather than a schema of its own, despite video being one of the larger modules — a historical artefact of V15__video_schema.sql landing before the per-module schema convention settled. Don't take it as the pattern to copy.

Migrations: Flyway

SettingValueConsequence
spring.flyway.enabledtrueMigrations run automatically at startup.
spring.flyway.defaultSchemamainflyway_schema_history lives in main.

spring.flyway.baseline-on-migratetrueAn existing non-empty DB without a history table gets baselined instead of erroring.
spring.jpa.hibernate.ddl-autononeHibernate never creates or alters a table. Every schema change must be a migration — there is no "it'll be created on startup" fallback.

custom.flyway.check-schematrue in devActivates DbSchemaChecker, which fails startup if Flyway reports pending migrations.

Migrations live in src/main/resources/db/migration/ and are named V<n>__snake_case_description.sql. There are currently 85 files, numbered up to V91 — the numbering is intentionally non-contiguous (see below), and Flyway does not require contiguous versions.

Version numbers have gaps, and that is fine — but deleting an applied migration is not free. V01, V03, V05, V06, V08, and V09 no longer exist: they were the tenant module's migrations and were deleted outright when that module was removed (91 → 85 files). That was only safe because there is no UAT or production environment yet, so no flyway_schema_history anywhere had to be preserved.

If your local dev database predates that change it will now fail Flyway validation with "detected applied migration not resolved locally". Drop and recreate it. CI and the integration suite always start from an empty container and are unaffected. Once a real environment exists, this option disappears — supersede with a new drop migration instead of deleting.

Run mvn clean verify, not mvn verify, after touching migrations. Deleted migration files linger in target/classes. When the tenant migrations were removed, a plain mvn verify left the six stale files on the classpath and Flyway ran the old V08 against tables the deleted V01 no longer created — producing 60+ spurious context-load failures in completely unrelated video tests. The failure looks nothing like a migration problem, which is what makes it expensive.

Auditing: Hibernate Envers

Six entity classes carry @Audited — User, Authority, SecKey, Secret, PersistentToken, and VideoModerationScan. (AbstractAuditingEntity also carries the annotation, but as a @MappedSuperclass it only governs which of its columns appear in an audit row — extending it does not by itself make an entity audited.) Envers writes a companion *_aud table per audited entity plus a single shared revision table, main.revinfo (with revinfo_seq), created in V07__envers_audit_tables.sql. V11__audit_schema_gap_closure.sql declares foreign keys from every *_aud table it creates onto main.revinfo(rev).

V07 is load-bearing for far more than its filename suggests. It creates the tenant audit tables and the shared Envers revinfo/revinfo_seq. When the tenant module was removed, V07 was edited rather than deleted — keeping revinfo and dropping only the two tenant_*_aud tables. Deleting it wholesale would have failed at V11, whose foreign keys depend on revinfo existing. If you ever need to prune a migration, check what else it creates first.

Entity Conventions

Every entity extends infrastructure.persistence.BaseEntity or AbstractAuditingEntity. See Infrastructure for the full detail; the parts that constrain your migrations:

  • IDs are TSIDs (@Tsid-generated Long) — time-sortable and cheaper to index than a random UUID. Column type is BIGINT. Some newer tables (session_pack_purchases, video tables) use UUID primary keys instead; check the entity before assuming.
  • Auditing columns — created_by/created_date/ last_modified_by/last_modified_date, plus status, request_id, and session_id on anything extending AbstractAuditingEntity. Your CREATE TABLE must include them.
  • Timestamps are TIMESTAMPTZ, mapped to Instant. See docs/handling-time.md for the wider timezone conventions.

Patterns Worth Knowing

Constraints as the last line of defence

Several invariants are enforced in the database rather than only in application code, because more than one code path writes the same table. The worked example is V87__booking_overlap_exclusion_constraint.sql, which adds a Postgres EXCLUDE USING gist constraint so no two committed bookings can hold overlapping time for the same coach — including from BookingBatchService and RescheduleService, which skip the application-layer pre-check. Violations surface as DataIntegrityViolationException and are mapped by ApiAdvice's CONSTRAINT_MAPPINGS/CONFLICT_CONSTRAINTS to a clean 409 rather than a 500.

Adding a named constraint usually means editing ApiAdvice too. If you add a unique or check constraint a user can plausibly trip, add its name to the constraint-mapping tables so the client gets a meaningful error code instead of a generic 500.

Enum columns carry CHECK constraints

Enums persisted as @Enumerated(EnumType.STRING) are frequently backed by a CHECK (col IN (...)). JPA will happily write a value the CHECK rejects, so adding an enum constant without a migration fails at INSERT time, not at startup — V91 is the worked example, recreating admin_alerts_type_check to admit MODERATION_UNRESOLVED. Grep for the constraint name before adding a constant.

Seeding runtime config

Tunables live in main.platform_config and are read through config's ConfigService. A migration that introduces a new key seeds it with an explicit id and ON CONFLICT (key) DO NOTHING so re-running against a partially-seeded database is safe — see V90 and V91. Remember ConfigService caches for ~300s, so a newly seeded key isn't visible instantly.

Partial indexes for "not yet processed" scans

Scheduled jobs that repeatedly scan for unprocessed rows are backed by partial indexes rather than full ones — e.g. idx_session_pack_purchases_expiry_notify ON (expires_at) WHERE expired_notified_at IS NULL. The index shrinks as rows are processed. If you add a "stamp a column once processed" scheduler, add the matching partial index with it.

Gotchas

Never edit a migration that has been applied anywhere. Flyway checksums every applied file; editing one fails validation on the next startup. The tenant-removal edit to V07 was only permissible because no persistent environment existed. Add a new migration instead.

Quartz tables exist but nothing uses Quartz. V02__quartz_schema.sql creates the Quartz tables and spring-boot-starter-quartz is still a dependency, but the only Quartz job in the codebase (RotatedKeyCleanupJob) was deleted with the tenant module. All current background work uses Spring @Scheduled + ShedLock — see Scheduled Jobs. Don't add a Quartz job just because the tables are there.

Cross-module references are plain id columns, not foreign keys. booking.bookings.session_pack_purchase_id points at payment.session_pack_purchases as a bare UUID, deliberately not a JPA association — booking must never load or mutate a pack row. Expect to write the join yourself when reporting across modules.

GDPR erasure bypasses the usual guards. Deletion paths used by admin.GdprErasureService (e.g. MessageRepository.deleteAllBySenderId()) ignore the report/retention predicates that normal cleanup respects. If you add a table holding user content, make sure it is covered there — and be aware the delete is unconditional.
