    Home / Frontend

    Frontend

    The Vue 3 + Quasar 2 single-page app in src/frontend — one hash-routed SPA serving all four personas (Player, Parent, Coach, Admin), built into the Spring Boot jar.

    Why / What It Is

    Every Skillars persona uses the same SPA. There is no separate admin app and no server-side rendering: the Quasar build (quasar build → src/frontend/dist/spa) is copied into target/classes/static by maven-resources-plugin at process-resources and served by Spring Boot from the same origin as the API. Same-origin matters: authentication is entirely cookie-based (an HttpOnly JWT cookie plus a few JS-readable companion cookies), so the SPA never handles a bearer token, and EventSource streams carry the session cookie automatically.

    The app is organised by persona: a single route table (src/router/routes.js) with meta-driven role guards, one layout (MainLayout.vue) whose drawer renders a different nav block per role, and pages grouped under src/pages/{auth,coach,parent,player,admin,marketplace,messaging}. Each backend module has a matching thin API file in src/api/ and (usually) a Pinia store in src/stores/.

    Pages call API modules either directly or through a store; there is no repository/service layer in between. All HTTP goes through the single api axios instance exported by boot/axios.js — never a bare axios import — because the interceptors carry session tracking and the 401 teardown. SSE streams are the one exception (native EventSource, see below).

    Router & route guards

    quasar.config.js sets vueRouterMode: 'hash', so every SPA URL is https://host/#/path. All routes are children of / (MainLayout.vue); '' redirects to /login; a tagged catch-all /:catchAll(.*)* (meta: { notFound: true }) renders ErrorNotFound.vue. Numeric route params are constrained with (\\d+) (e.g. parent/players/:playerId(\\d+)/videos).

    Route metaGuard behaviour (router/index.js)
    requiresAuthNot authenticated → /login?redirect=<fullPath>.
    requiresGuestAuthenticated → routeForRole(role). Used by every login/registration/verification page.
    requiresCoachAuthenticated non-coach → own landing route.
    role: 'PARENT' | 'PLAYER' | 'COACH'Single-role gate (older routes): every meta.role value on the matched records must equal the caller's role, else → own landing route. Generic since fix/security-session-revocation — it used to check only PARENT/PLAYER, so coach/revenue and coach/bookings/:bookingId/receipt (role: 'COACH') were login-gated only.
    roles: [...]Additive multi-role gate (UAT.5 AC4 onward): caller's role must be in the union of meta.roles across matched records. Used for dual-role PARENT/PLAYER routes and all /admin/* routes (['ADMIN']).
    (special)Entering /coach/command-center as a coach loads profileBuilder.store status and redirects to /coach/profile-builder if the profile is incomplete.

    Authentication state on navigation comes from authStore.hydrateFromCookie(), run once on the first navigation: it parses the non-HttpOnly skp cookie (URL-encoded JSON {"id":"<Long as string>","role":"COACH"}). The guard does not call the backend — it trusts the cookie for routing only; every API call is authorised server-side by the JWT.

    Landing routes — router/roleRoutes.js

    ROLE_ROUTES is the single definition (used by the guard and LoginPage.vue): COACH → /coach/command-center, PARENT → /parent/dashboard, PLAYER → /player/home, ADMIN → /admin/health-dashboard; anything else → /dashboard. /player/home is not a real page: PlayerHomeRedirectPage.vue resolves the caller's own player-profile id and redirects to /player/locker-room/:playerId. routeForRole uses Object.hasOwn so a forged skp role like constructor falls through to the default.

    Role navigation — MainLayout.vue

    The drawer renders one <template v-if="authStore.isCoach|isParent|isPlayer|isAdmin"> block per role; /dashboard is shown only to admins or role-less users, /profile to everyone. Parents additionally get a "My players" list built from playerStore.players via parentChildLinks(id), plus ParentChildSwitcher in the header. For a PLAYER the layout resolves the caller's own player-profile id (selfPlayerId) and only then renders the locker-room, packs and development links (lockerRoomRoute/packsRoute/developmentRoute are null until resolved). Both resolutions are driven by watch(() => authStore.isPlayer / isParent), not onMounted, because the layout never remounts across a client-side login. Adding a page means adding a route and a drawer entry — several pages were historically unreachable because only one of the two was done.

    API layer & auth

    boot/axios.js creates api = axios.create({ baseURL: '', withCredentials: true }). API modules are thin: either an exported object (authApi, sessionApi, notificationApi) or named functions (messaging.api.js), each returning api.get/post/.... The response interceptor unwraps to response.data, so callers receive the body directly, not an axios response.

    InterceptorBehaviour
    RequestIncrements the pending-request counter (drives useLoading → GlobalLoadingBar); sets Accept-Language to the current vue-i18n locale (backend error messages/emails localise from it); calls recordActivity() except for GET /refresh.
    Response (success)Decrements counter; refreshExpiryState() (every authenticated response rewrites the rint cookie — the JWT's new absolute expiry in epoch ms); returns response.data.
    Response (error)On 401 with errorMsg.errorKey security.sessionExpired or security.unauthorized: stops session monitoring, clears user/skp cookies and navigates to /login via pushLoginOrHardNavigate(router, { expired }) — expired is true only for sessionExpired. 403/5xx/network errors are only logged. The original error is always re-thrown for the component to handle.

    Login / session flow.

    • LoginPage.vue calls authApi.skillarsLogin → POST /api/auth/login (AuthResource). The backend sets the HttpOnly JWT cookie (potc), skp, user (display name, or the __blank__ sentinel) and rint; the JSON LoginResponse goes to authStore.setUser. Redirect target: ?redirect= if isSafeRedirect passes, else routeForRole(role). 403 = account not verified, 429 = rate-limited. There is no second-factor step in the SPA (the legacy OtpPage.vue and the 2FA profile toggle were removed).
    • There is no client-side token refresh loop. The JWT is sliding: JWTAuthorizationFilter extends it on each authenticated request and rewrites rint. plugins/sessionManager.js ticks every 30 s against rint, shows SessionWarningDialog 5 minutes before expiry, and "Continue session" calls sessionApi.refresh() → GET /refresh (TTL extension only, empty 200). POST /api/auth/refresh (full token rotation) exists on the backend but the SPA does not call it (the unused skillarsRefresh wrapper was removed from auth.api.js). If rint runs out, tick() dispatches window event session:expired; App.vue tears down state and redirects. Details: docs/session-refresh-mechanism.md.
    • boot/axios.js also sets a one-year fcookie browser-fingerprint cookie on boot (fraud signal; distinct from the backend's bcookie).

    Error handling. Backend errors are an ErrorDto (helpCode, errorMsg.{errorKey,message}, fieldErrors[]). utils/errorHandler.js's parseApiError normalises it; useErrorHandler() exposes reactive errorMessage (a status-based fallback key such as security.sessionExpired when the backend sent no message of its own; otherwise the translated errorKey if the catalogue has it, else the raw server message), fieldErrors, helpCode, setError/clearError. Pages show errorMessage in a q-banner or via $q.notify.

    Server-Sent Events

    SSE uses the native EventSource, not axios, so none of the interceptors run on it (no loading-bar tick, no rint refresh, no 401 teardown). All three streams open the EventSource with { withCredentials: true }, matching axios. Each stream implements its own backoff/fallback:

    StreamOpened byEvents / fallback
    /api/messaging/conversations/{id}/eventsmessaging.api.js subscribeToEvents, from messaging.store connectSseNEW_MESSAGE, MESSAGE_BLOCKED. The backend emitter is per user (MessagingEmitterRegistry), so events are routed by the payload's conversationId. Exponential reconnect (1 s, 2 s), then from the 3rd failure an interval poll of messages.
    /api/bookings/{id}/eventsuseBookingSse (booking.store.js), and directly in CoachCommandCenterPage.vuestatus, heartbeat (reconnects). Closes on a terminal status. Backoff 1–30 s; after 3 errors switches to a recursive-setTimeout poll (2 s floor, 30 s cap).
    /api/video/{id}/eventsvideo.store.jsstatus until a terminal processing state; polls /api/video/{id}/status (fetch, credentials: 'include') while disconnected. Owner-only on the server (VideoAccessGuard.isCurrentUserOwner).

    Notifications are not pushed. NotificationBell.vue refreshes GET unread-count on mount, on every route.path change and on window focus; there is deliberately no user-level push channel. Notification deep links go through safeDeepLink (app-relative paths only) before router.push.

    i18n

    • Three locales: en-US (default), fr-FR, de-DE (src/i18n/index.js). Fallback for every locale is en-US. The language menu in MainLayout.vue persists the choice in localStorage['locale'] and clears any backend lang cookie so Accept-Language wins again.
    • Keys are nested by domain namespace, e.g. auth.*, coach.*, parent.*, player.*, admin.*, booking.*, messaging.*, notifications.*, nav.*, common.*, error.*, security.*, validation.*. Backend errorKey values (security.sessionExpired, error.notFound, ...) are looked up directly as i18n keys, so backend error keys and frontend catalogue keys share one namespace.
    • Use const { t } = useI18n() in <script setup> and $t in templates. Every new key must be added to all three locale files.
    • i18n/__tests__/localeKeyParitySpec.js fails if the three catalogues' key sets differ.
    • i18n/__tests__/i18nTemplateKeyResolutionSpec.js statically scans every .vue and .js under src/ for $t(/$te(/t(/i18n.global.t( calls and asserts each literal key exists in en-US. Calls whose key is dynamic (template literal, concatenation, variable) must be listed in its DYNAMIC_KEY_CALL_SITES array, keyed by 'src/...File.vue:<line>' with a reason (56 entries today). Because entries are file:line, any edit that shifts lines above a dynamic-key call breaks this spec — update the line numbers in the same change.

    Design system

    Dark-first glassmorphism with a light theme. css/app.scss imports, in order: tokens/colors (CSS custom properties), typography, animations (incl. prefers-reduced-motion), glass (.glass-card and surfaces), layouts (.app-bg, .app-page, grids), components (Quasar overrides). tokens/_colors.scss defines dark values on :root and overrides on :root[data-theme="light"] (--bg-*, --surface-glass*, --border-*, --accent-*, --text-*, component tokens); tokens/_typography.scss holds the clamp() font scale. boot/theme.js applies the persisted theme (localStorage['skillars-theme']) before first render; toggleTheme() flips the data-theme attribute and returns the new state. To add a colour, define it in both :root blocks and use var(--token) — never hard-code hex in a component.

    Testing

    • Vitest 4 + @vue/test-utils + happy-dom, config in vitest.config.mjs (globals: false — import describe/it/expect/vi explicitly; testTimeout: 10000). Specs: src/**/__tests__/**/*.{js,mjs} and src/**/*.{spec,test}.{js,mjs}.
    • test/vitest/setup-file.js installs the Quasar plugin, a real createI18n with an empty en-US catalogue (so t('key') renders the key), and a global $t mock that echoes keys. Specs therefore assert raw keys — which is why the two i18n specs above exist. Pinia is not global: specs opt in with createTestingPinia().
    • Page specs define a local async function mountPage(...) (there is no shared helper): build a router with createMemoryHistory() and stub sibling routes, router.push + await router.isReady(), mount(Page, { global: { plugins: [router, createTestingPinia(...)] } }), await flushPromises(), and unmount in afterEach. API modules are mocked with vi.mock('src/api/...').
    • Aliases (src/, components/, stores/, ...) resolve through vite-tsconfig-paths reading .quasar/tsconfig.json; #q-app/wrappers has a hand-maintained alias to the runtime @quasar/app-vite/wrappers.
    • CI. .github/workflows/frontend-unit-tests.yml runs npm run test:unit:ci on a matrix of TZ=UTC and TZ=America/New_York (catches DST/local-time bugs — build test dates from fixed instants). It fires on PRs whose diff touches src/frontend/** (.github/scripts/detect-frontend-changes.sh), on the frontend-tests label, or on manual dispatch. It is not a required check. See docs/testing/frontend-unit-tests.md.
    • Prettier + ESLint gate. The composite action .github/actions/frontend-quality/action.yml (used by both ci.yml and pr-build.yml) runs npx prettier --check "**/*.{js,vue,scss,json}" and ESLint.     Conventions & Gotchas

    Hash routing leaks into the backend. Every link to the SPA must contain /#/. Emails and notifications built on the server use infrastructure.web.FrontendLinkBuilder (route("parent/bookings") → ${app.frontend-url}/#/parent/bookings); a link without the hash 404s or lands on the SPA root. Likewise, never do window.location.href = '/login' in the SPA — use router.push or pushLoginOrHardNavigate. Renaming a route path can break existing email links and notification deep links (e.g. parent/approvals survives as a redirect for exactly that reason).

    Git worktrees need src/frontend/.quasar. It is gitignored and generated by quasar prepare (npm postinstall). In a fresh worktree with a symlinked node_modules and no .quasar, Vitest's alias resolution falls through to the main checkout, so tests silently run against the main checkout's src/ and pass or fail for the wrong code. Copy it in: cp -R <main>/src/frontend/.quasar <worktree>/src/frontend/.

    A symlinked node_modules is not ignored. .gitignore's node_modules/ and src/frontend/node_modules/ patterns (trailing slash) match directories only, not a symlink of that name. Don't git add -A in a worktree that symlinks it.

    Ids are strings. Ids are TSID longs larger than Number.MAX_SAFE_INTEGER; the backend serialises them as strings (including in skp). Keep them as strings — never Number(id) or parseInt — and compare with string equality (the messaging store's sameId). Also: Booking.playerId and the :playerId route params are player-profile ids, not user ids.

    The router guard is UX, not security. It trusts the JS-readable skp cookie. Every backend endpoint must enforce its own role/ownership check; a route's meta only decides where the user lands. Prefer meta.roles for new routes; meta.role and requiresCoach remain for older ones and are enforced for every value (routerGuardSpec.js covers the COACH case).

    Shared pages, role-aware. VideoManagementPage.vue serves both coach/videos and player/videos; dual-role parent/* pages hide parent-only actions behind authStore.isParent. When adding a mutating button to a dual-role page, check which roles can see it.

    ?redirect= is validated twice. isSafeRedirect requires an app-relative path that resolves to a real route (not the notFound catch-all). Hash mode is what actually prevents off-origin redirects; if you ever switch to history mode, harden the shape check first.
