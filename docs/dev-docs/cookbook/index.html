    Cookbook: "How do I add…"

    One checklist per common change: every file that must move, a recent commit or class to copy, and the guard test that fails your PR if you miss a step.

    How to read this. Paths are relative to the repo root; …/ abbreviates src/main/java/com/softropic/skillars/ and test…/ abbreviates src/test/java/com/softropic/skillars/. Line numbers are as of master 4db90562. Every guard named here is described, with its error message and how to run it alone, on CI Guards. The module pages hold the "why"; this page is the "where".

    1. A REST endpoint

    Copy: …/platform/notification/api/NotificationResource.java and test…/platform/notification/api/UnsubscribeResourceWebMvcTest.java (commit e350d169).

    1. Controller in platform/<module>/api/, named *Resource, @RestController + @RequestMapping("/api/<module>/…"). Everything under /api/** already requires authentication (AppEndpoints.SECURED_API); there is no per-path URL rule to add for a secured endpoint.
    2. Authorize every method with @PreAuthorize using the constants in …/infrastructure/security/SecurityConstants.java:33-46 (HAS_COACH_ROLE, HAS_ADMIN_ROLE, HAS_PARENT_OR_PLAYER_ROLE, IS_AUTHENTICATED, …). Role alone is not ownership:
      • a playerId path/body parameter → @PreAuthorize("@playerOwnershipGuard.check(authentication, #playerId)") (…/platform/security/service/PlayerOwnershipGuard.java; parent of the child or the self-registered player). Coach-or-owner variants combine it with hasRole('ROLE_COACH') or ….
      • a coach acting on a player → CoachPlayerAuthorizationService.requireCoachPlayerRelationship(…) in the service (see RadarAssessmentService).
      • a "my own" resource → take no user id from the client at all; resolve it with SecurityUtil.requireCurrentUserId() and scope every query by it (as NotificationResource does).
    3. Public (unauthenticated) endpoint? Add the exact path to AppEndpoints.PUBLIC_ENDPOINTS (…/platform/security/config/AppEndpoints.java:30), consumed by SecurityConfiguration.configureRequestMatching (line 186). Use an exact path, or a /-preceded trailing /** — never foo**. Guard: AppEndpointsConventionTest. Also add @PreAuthorize(SecurityConstants.IS_PERMIT_ALL) on the method and document what authenticates the call instead (signature, HMAC token).
    4. DTOs live in platform/<module>/contract/ as records with jakarta.validation annotations; take them as @Valid @RequestBody. A failure becomes a 400 via ApiAdvice.methodArgumentNotValidExceptionHandler. A custom message = "{some.key}" must exist in src/main/resources/i18n/messages.properties (guard: MessageCodeBaseBundleCompletenessTest).
    5. Errors. Throw a domain exception, not IllegalStateException (that maps to 500 by design). Mapping lives in …/platform/security/api/ApiAdvice.java plus per-module advices (BookingApiAdvice, PaymentApiAdvice, SessionApiAdvice, ReviewApiAdvice, MessagingApiAdvice, VideoApiAdvice). The response body is ErrorDto(helpCode, ErrorMsg(errorKey, message)); the frontend looks errorKey up as an i18n key. If you add a unique/check constraint a user can trip, add it to CONSTRAINT_MAPPINGS (line 135) and, for a retryable race, CONFLICT_CONSTRAINTS (line 162) — otherwise it surfaces as a generic 400.
    6. Message keys for new error keys go in all four backend bundles (messages.properties, _en, _de, _fr; guard: MessageBundleParityTest) and, if the SPA shows them, in the three frontend locales.
    7. Tests. Security/routing shape → a slice named *WebMvcTest (never *IT). Copy UnsubscribeResourceWebMvcTest's nested TestSecurityConfig and its mock set: the slice loads every @RestControllerAdvice and filter, which pull in VideoMetrics and JwtSecretService. Behaviour against a real DB → an *IT extending AbstractIntegrationTest (recipe 11). Guard: IntegrationTestConventionTest.noSliceTestIsNamedIT.
    8. Frontend: add the call to the module's src/frontend/src/api/<module>.api.js (recipe 12).

    2. A Flyway migration

    Copy: V173__drills_private_uniqueness_active_only.sql (index swap, commit fd2b8822) or V172__gdpr_player_scope_and_appeals.sql (new table + guarded drop, commit 1f273c37). Full rules: Database and docs/deployment/migration-conventions.md.

    1. Name src/main/resources/db/migration/V<next>__<schema>_<table>_<what>.sql. Check the highest number on master right before you push (currently V213; the sequence has unused gaps such as V174 and V201–V204, so always take highest + 1) — two open PRs picking the same number is the usual collision. Never edit a migration that has run anywhere.
    2. Header comment explaining why, and any "same-release exception" you are taking.
    3. Schema: put the table in its owning module's schema (booking, payment, admin, …), not main. Cross-module references are plain id columns, no FK.
    4. SET LOCAL lock_timeout = '5s'; before the first lock-taking statement (plain SET is rejected — it leaks into later migrations in the same run).
    5. Indexes: plain CREATE INDEX IF NOT EXISTS preceded by -- migration-lint: allow-blocking-index <reason>. CREATE INDEX CONCURRENTLY does not work in this Flyway runner (it self-deadlocks), so don't reach for it.
    6. Constraints on a growing table: ADD CONSTRAINT … NOT VALID, validate later; on a small or new table -- migration-lint: allow-validating-constraint <reason>. Enum columns need a hand-written CHECK (Hibernate no longer generates them); a status-scoped partial index uses a whitelist (status IN (…)), never <>/NOT IN.
    7. Drops: IF EXISTS + -- migration-lint: drop-prepared-in: V<n> naming the earlier release that removed the last reader; no reference to the dropped name may remain in src/main.
    8. Data changes: UPDATE/DELETE need a bounding WHERE (or -- migration-lint: allow-full-table-dml <reason>); big backfills go in an executeInTransaction=false sidecar (V<n>__x.sql.conf).
    9. If the change touches something mapped: a named constraint users can trip → ApiAdvice mapping; an enum value → CHECK widening shipped a release before the first write.
    10. After deleting or renaming a migration locally, mvn clean (stale files stay on the classpath).

    Guards: MigrationConventionLintTest (unit phase, all of the above), StatusScopedPartialIndexConventionIT, SchemaAssumptionsTest (only one EXCLUDE constraint may exist), and — for main.envelope_entity — EnvelopeEntitySchemaIT.

    3. A JPA entity / table

    Copy: …/platform/admin/repo/Appeal.java + the admin.appeals block of V172 (commit 1f273c37).

    1. Migration first (recipe 2). ddl-auto is none: Flyway is the only source of schema. Include every column the entity maps — for AbstractAuditingEntity subclasses that means created_by/created_date/last_modified_by/last_modified_date, status, request_id, session_id. Use timestamptz for Instant.
    2. Entity in platform/<module>/repo/ with @Table(schema = "<module>", name = "…") — without schema it lands in main. Ids: BaseEntity's TSID Long, or @GeneratedValue(strategy = GenerationType.UUID) with a uuid DEFAULT gen_random_uuid() column (as Appeal). Enums: @Enumerated(EnumType.STRING) + a CHECK in the migration.
    3. @Version? Add it (column version integer DEFAULT 0 NOT NULL, as booking.bookings) when request threads read-modify-save() the same row concurrently. Skip it, with a Javadoc saying why, when every state transition is a single conditional UPDATE … WHERE status = 'OPEN' (Appeal's reasoning). If a @Version table also gets a @Modifying bulk UPDATE, it must SET … version = version + 1 (JPQL alias form is fine — see VideoRepository.resetLifecycleLockedAt) or be listed in the test's ALLOWED_WITHOUT_BUMP. Guard: NativeModifyingVersionAuditTest.
    4. Repository next to the entity. Concurrently-mutated rows need a lock finder (recipe 4).
    5. Envers? Only six entities are @Audited; a new one needs its *_aud table by hand (V148's user_authority_aud is the template).
    6. User content? Make it reachable from admin.service.GdprErasureService (and export), and if a concurrent writer could re-insert after erasure, add a tombstone check after the writer's row lock (see DevelopmentDataErasureGuard).
    7. Test fixtures must seed every NOT NULL column; the database is truncated before every IT method.

    4. A row lock on a hot row

    Copy: UserRepository.findByIdForUpdate (…/platform/security/repo/UserRepository.java:192-195) and its caller AdminUserService.lockAndLoad (…/platform/admin/service/AdminUserService.java:270-274), commit 91a34b43. Background: Database → Locking Conventions.

    1. Finder: a JPQL query with @Lock(LockModeType.PESSIMISTIC_WRITE) and @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "0")) (= FOR UPDATE NOWAIT). Not a native FOR UPDATE NOWAIT: that failure marks the transaction rollback-only and every contended call ends in UnexpectedRollbackException. Not a finite timeout either — on this Postgres/Hibernate pair it is silently ignored and the query blocks forever. If the entity has @Version and callers may already hold it unlocked, lock a scalar id projection instead and then findById: copy CoachProfileRepository.findByIdForUpdate / lockByIdForUpdate (…/platform/marketplace/repo/CoachProfileRepository.java:54-62, also SessionRepository). A locked entity query on an already-managed @Version instance makes Hibernate version-check the stale snapshot and throw StaleObjectStateException (a 409) on exactly the race the lock and entityManager.refresh exist to absorb.
    2. Wrap the call in lockRetryer.withBoundedRetry("<lockName>", () -> repo.findByIdForUpdate(id).orElseThrow(…)) (…/infrastructure/persistence/PessimisticLockRetryer.java:150), inside a @Transactional method.
    3. Only reads inside the lambda (lock, orElseThrow, optionally entityManager.refresh). The supplier can run several times; every save/delete/publishEvent/enqueue/ send goes after withBoundedRetry returns — the row lock is held until commit anyway.
    4. Bump the pin: EXPECTED_CALL_SITE_COUNT in test…/infrastructure/persistence/PessimisticLockRetryerCallSiteAuditTest.java:185 (64 today) and add a line to its Javadoc history saying which method you added.
    5. New repository type? Add it to NOWAIT_LOCK_METHODS_BY_REPOSITORY_TYPE (same file, line 336) so the "unwrapped NOWAIT call" check covers it.
    6. Inner REQUIRES_NEW? Don't NOWAIT-lock a row the outer transaction already wrote — Postgres 55P03 every time, surfacing as a 409 the retryer cannot fix.

    Guard: PessimisticLockRetryerCallSiteAuditTest (count + write-in-lambda + unwrapped-NOWAIT checks).

    5. A scheduled job

    Copy: …/platform/admin/service/GdprErasureRetryScheduler.java (thin scheduler delegating to a service, commit a7d2b91b); for a claim-based drainer, RadarCompositeDlqProcessor. Catalogue and rules: Scheduled Jobs, docs/deployment/scheduler-lock-tuning.md.

    1. A thin @Component whose @Scheduled method calls a service method, so ITs can call the service directly.
    2. Schedule from a property: fixedDelayString = "${platform.<module>.<job>.poll_delay_ms:60000}" or a cron. Check the staggered daily slots on the Scheduled Jobs page before picking a cron hour.
    3. @SchedulerLock(name = "ClassName_method", lockAtMostFor = …, lockAtLeastFor = …) unless the job only touches per-node state or claims rows with SKIP LOCKED. lockAtMostFor ≈ 2× the expected run; lockAtLeastFor ≤ lockAtMostFor (ConfigStartupAssertion checks this at boot and refuses to start outside dev). A short-delay drainer makes lockAtLeastFor a property too.
    4. Claim-based drainers (claimed_at + stale-claim reset): bound the run's wall clock (MAX_RUN_DURATION) below lockAtMostFor, and keep lockAtMostFor strictly below STALE_CLAIM_WINDOW with a real buffer — RadarCompositeDlqProcessor: 8 min / PT10M / 15 min; VideoDeletionOutboxProcessor: 12 min / 15 min / 20 min. Otherwise the next instance resets and re-claims rows the running one still holds. Pin the ordering in a unit test (see VideoDeletionOutboxProcessorSchedulerLockTest.runtimeBudget_staysStrictlyInsideLockAndStaleWindow).
    5. Runtime tunables (batch size, windows) are platform_config keys → recipe 9. Bound the batch; drain the rest next tick. One transaction per item if one failure shouldn't abort the run; never hold a transaction across Stripe/Bunny/Gemini calls.
    6. Don't add a method-level @Transactional on the scheduled method — use per-item TransactionTemplate (guard: SchedulerLockTransactionOrderingIT for the three schedulers it covers).
    7. Document it: add a row to Scheduled Jobs (and its totals).
    8. Test: schedulers don't fire under the test profile. Call the method through the Spring proxy and call releaseSchedulerLock("ClassName_method") (test…/config/AbstractIntegrationTest.java:211) between runs.

    6. A domain event + listener

    Copy: producer side …/platform/booking/contract/BookingStatusChangedEvent.java; listener side …/platform/payment/service/RefundEnqueueListener.java (BEFORE_COMMIT) and …/platform/payment/service/CancellationRefundService.java:106-107 (onCoachNoShow, AFTER_COMMIT + REQUIRES_NEW).

    1. Declare the event in the producer's contract package (platform/<module>/contract/ or contract/event/). Both ApplicationEvent subclasses and plain records are in use. Carry ids and immutable facts, not entities. Consumers import only contract.
    2. Publish with ApplicationEventPublisher.publishEvent(…) inside the business transaction.
    3. Pick the phase:
      • @TransactionalEventListener(phase = BEFORE_COMMIT) — the work must be atomic with the producer (it joins the transaction; a throw rolls the business change back). Use this to enqueue durable side effects.
      • @TransactionalEventListener(phase = AFTER_COMMIT) — best-effort follow-up that may be lost on a crash. There is no ambient transaction: if it writes, add @Transactional(propagation = REQUIRES_NEW); if it is slow, add @Async("<pool>") with an explicit pool name.
      • Plain @EventListener — runs synchronously at publish time, inside the publisher's transaction.
    4. Must survive a crash? (email, refund, payout, S3 delete, external call) → don't do it in an AFTER_COMMIT listener; enqueue an outbox row from BEFORE_COMMIT (recipe 7).
    5. Test: assert publication with the shared RecordedEvents bean (declared in test…/config/TestConfig.java), never a per-class capture @TestConfiguration (forks a context).

    Guards: AsyncExecutorQualifierTest (bare or unknown @Async), EmailListenerAnnotationCoverageTest (an on*(Event) method on the email listeners without a listener annotation).

    7. An outbox message type

    Copy: …/platform/video/service/ModerationOutboxSupport.java + ModerationRetryOutboxHandler.java (commit 90121602). Design: Outbox.

    1. *OutboxSupport in the owning module: a public static final String …_AGGREGATE_TYPE, a payload record, and an enqueue method annotated @Transactional(propagation = Propagation.MANDATORY) that calls outboxService.enqueue(type, json) then outboxService.requestDrainAfterCommit(). Use enqueue(type, json, notBefore) for a delayed row.
    2. Call it inside the business transaction — from the service or a BEFORE_COMMIT listener, never AFTER_COMMIT.
    3. Handler: a @Component implementing …/platform/outbox/contract/OutboxMessageHandler (aggregateType() + handle(String payload)). Two handlers with the same type fail startup.
    4. Idempotent handle(): anchor on a DB state check and/or a remote idempotency key (delivery is at-least-once). Throw only for retryable failures; turn a permanently impossible row into a logged no-op.
    5. Payload is a cross-version contract: add fields as nullable; don't delete a handler while rows of its type remain.
    6. No migration — aggregate_type has no CHECK.
    7. Test: an *IT next to test…/platform/outbox/ModerationOutboxIT.java; the test profile drains synchronously (app.outbox.drain-async: false), so assert right after the call.
    8. Add a row to the "Who uses it" table on the Outbox page.

    9. A platform_config key

    Copy: reviews.minSessionAgeDays — seeded by V156__reviews_eligibility_config_rework.sql (commit f789ce5b), bounded by ConfigBounds.REVIEWS_MIN_SESSION_AGE_DAYS, read in ReviewSubmissionService. Background: Config.

    1. Seed in a migration: INSERT INTO main.platform_config (key, value, value_type, description) VALUES (…) ON CONFLICT (key) DO NOTHING; — no id column (it is an identity; guard: MigrationConventionLintTest PLATFORM_CONFIG_EXPLICIT_ID). Skip the seed only if the call site has a code default and the key goes in HAS_CODE_DEFAULT.
    2. Bound it (any numeric key): a BoundedKey(key, min, max, failFast, note, defaultValue) constant in …/platform/config/service/ConfigBounds.java (record at line 77), added to ALL (declared at line 552), and to HAS_CODE_DEFAULT (line 518) if the call site has a default. Without it the admin PUT accepts any string and ConfigStartupAssertion never checks the key. failFast = true blocks production boot on a bad value — only for keys whose misconfiguration loses data or halts a core flow.
    3. Read it with the getter matching the failure mode. For a HAS_CODE_DEFAULT key prefer getBoundedLong/Int(ConfigBounds.X), which takes the key, default and [min, max] from the registry entry so the call site cannot drift (as BookingService.requireRequestQuota reads ConfigBounds.BOOKING_REQUEST_MAX_PENDING_PER_COACH); it throws for a key without a code default. Otherwise getBoundedLong/Int(key, default, min, max) (WARN + default), getBoundedLong(key, min, max) (missing throws, out-of-range clamps), getBoolean(key, default) — and with the string forms, pass the same [min, max] as ConfigBounds by hand.
    4. Per-tier / per-video-type key? Templated keys are generated from enum segments in ConfigBounds; a new CoachSubscriptionTier/VideoType constant needs its segment there (guard: ConfigBoundsEnumCoverageTest).
    5. Cross-key invariant? Validate the partner from the database, not the cache, in ConfigService and mirror it in ConfigStartupAssertion.
    6. Remember the 300 s per-node cache: an edit is not visible on other instances immediately.

    10. A feature / tier gate

    Copy: DrillLibraryService.checkSessionBuilderGate (…/platform/session/service/DrillLibraryService.java:399-405) for a config-driven gate; RadarAssessmentService (hard-coded RADAR_ALLOWED_TIERS) for a fixed one.

    1. Choose the mechanism. Operator-tunable per tier → seed feature.<name>.enabled.<TIER> for every CoachSubscriptionTier (SCOUT, INSTRUCTOR, ACADEMY; see feature.sessionBuilder.enabled.* in V139) and read it with configService.getBoolean(…). Fixed by product rule → an EnumSet of allowed tiers. (infrastructure.feature.FeatureToggleService/AppFeature are application-level property toggles, not tier gates.)
    2. Resolve the tier with coachProfileService.getCoachSubscriptionTier(coachId).
    3. Gate before anything that leaks existence (a 403 before a 404 — see the comment in RadarAssessmentService).
    4. Throw FeatureGatedException(featureKey, requiredTier) (…/platform/security/contract/exception/); ApiAdvice.featureGatedHandler maps it to 403 with errorKey = security.featureGated. Pass null as the tier only if no tier grants it.
    5. Read-side mirror: if a GET returns data a downgraded coach should no longer see, gate it too (see ReportGenerationService.getBranding's comment).
    6. Frontend: branch on err.response.data.errorMsg.errorKey === 'security.featureGated' and render src/frontend/src/components/common/FeatureGateOverlay.vue (DrillDetailPanel.vue handles the error key at line 564 and renders the overlay; sessionBuilder.store.js:153 turns it into an isGated flag).
    7. Player-side quota (video) lives in video.quota.<tier>.* keys — see Video.

    11. An integration test

    Copy: test…/platform/notification/api/NotificationCenterIT.java (commit e350d169). Read docs/testing/readme.md and docs/testing/why-inheritance-over-import.md once.

    1. Name it *IT and extends AbstractIntegrationTest (or a family base: BaseVideoIT, BasePaymentIT, BaseSessionIT, BaseStorageIT). Declare none of @SpringBootTest, @ActiveProfiles, @Import(TestConfig.class).
    2. Every context-key change forks a Spring context: a @MockitoBean/@MockitoSpyBean field (type and field name count), @TestPropertySource, @DynamicPropertySource, class-level @Import, nested @TestConfiguration. Prefer the base's inherited spies (paymentGateway, coachProfileRepository, …) or copy a peer's mock set with identical field names (e.g. videoProviderAdapter + fileStorageService, shared by 27 classes). If you really need a fork, bump EXPECTED_DISTINCT_CONTEXT_KEYS (test…/config/IntegrationTestConventionTest.java:109, 14 today) or EXPECTED_TEST_PROPERTY_SOURCE_COUNT (line 89) with a // context-fork: reason — and remember the CI ceiling is 17 contexts total.
    3. Seed your own data; every table is empty at the start of every method. Use an id range from the fixture id registry in docs/testing/test-data-isolation.md. No teardown.
    4. Wrap fixture writes in transactionTemplate.execute(…) — Hikari runs with auto-commit: false, so a bare jdbcTemplate.update in the test body never commits.
    5. Booking fixtures: derive end from start (Instant start = …; Instant end = start.plus(…)); two separate Instant.now() calls can violate chk_bkg_end_after_start on fast CI runners.
    6. Events: autowire RecordedEvents. Schedulers: call directly + releaseSchedulerLock(name). Outbox: drains synchronously. HTTP: MockMvc (@AutoConfigureMockMvc is on the base) or httpTestClient.
    7. Run one: mvn -o verify -DskipFrontend -Dit.test=MyIT. If you touched mocks/annotations, also run mvn -o test -DskipFrontend -Dtest=IntegrationTestConventionTest — it prints every context configuration when the count is off.

    Guards: IntegrationTestConventionTest (unit phase), the CI context-count gate (.github/scripts/assert-context-count.sh), the container sampler.

    Copy: src/frontend/src/pages/NotificationsPage.vue + src/frontend/src/pages/__tests__/NotificationsPageSpec.js (commit e350d169). Background: Frontend.

    1. Page in src/frontend/src/pages/<area>/, <script setup>, const { t } = useI18n().

Route in src/frontend/src/router/routes.js with a lazy component: () => import(…) and meta: requiresAuth: true plus one of requiresCoach: true, role: 'PARENT', role: 'PLAYER', or roles: [...] for dual-role pages. The guard is src/frontend/src/router/index.js:40-96; a public page has no meta (see unsubscribe).

    5. Store (only if state is shared across components): setup-style defineStore('id', () => { … }) in src/frontend/src/stores/.
    6. i18n: every key in all three of src/frontend/src/i18n/{en-US,de-DE,fr-FR}/index.js, including nav.* for the drawer label.     8. Before pushing, from src/frontend: npx prettier --write "**/*.{js,vue,scss,json}" --ignore-path ../../.gitignore, NODE_ENV=production npx eslint ., npx vitest run. In a new worktree, copy src/frontend/.quasar in first or Vitest resolves the main checkout's code.

    Guards: Prettier and ESLint (frontend-quality job), localeKeyParitySpec, i18nTemplateKeyResolutionSpec, routerGuardSpec (frontend-unit-tests workflow — see CI Guards for why that one is not a required check).
