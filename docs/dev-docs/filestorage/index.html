Filestorage

The single, audited front door every platform module must use to upload, download, and delete files — nobody talks to S3 directly except this module.

Business Overview

Skillars stores files for almost every persona: a coach's profile photo and gallery images, a coach's report branding logo, a branded session-report PDF, and a GDPR data-export ZIP. None of those modules knows whether the bytes end up in S3 or MinIO, or get mirrored to a backup bucket. That is filestorage's job. It answers, once for the whole platform: how do we accept a browser upload safely, enforce a size, type and quota policy, know who owns the file, let it be downloaded without proxying bytes through our servers, and eventually delete it?

Personas touch filestorage almost entirely indirectly, through the module that owns the business flow:

  • Coaches upload a profile photo in the Marketplace profile builder. The bytes go straight from the browser to S3 via a presigned URL (entity coach_profile), and CoachProfilePhotoEventListener links the confirmed key to the profile.
  • Coaches upload up to 6 public-profile gallery images (entity coach_gallery, added in #312). The browser runs sign → PUT → confirm, then calls POST /api/marketplace/coaches/me/profile/gallery {key}. marketplace.CoachGalleryService then checks the key again on the server with FileStorageService.findActiveObject (owner, JPEG/PNG/WebP, ≤5 MB), and removal soft-deletes the object. Frontend: components/profile/EditCoachGalleryDialog.vue.
  • Coaches upload a report-branding logo (entity coach_branding) and download generated session-report PDFs. development.ReportGenerationService stores the PDF server-side (storeBytes, key reports/{uuid}/report.pdf), reads the logo (downloadBytes, after assertOwnership), and hands out signedDownloadUrls.
  • Parents, players and admins get GDPR export ZIPs that admin.GdprExportService stores with storeBytes (key gdpr/exports/{requestId}.zip) and shares with a time-limited signedDownloadUrl(key, Duration). admin.GdprErasureService deletes a user's blobs (exports, child and coach report PDFs, gallery images) through BlobDeletionOutboxSupport.
  • The old booking wrap-up voice note is gone (story 12.7, D3). Legacy audio/webm objects tagged entity=booking may still exist, unread and unlinked. Clean-up is tracked in _bmad-output/implementation-artifacts/deferred-work.md.

Key business rules found in the code:

  • Browser uploads happen in two phases and never pass through the app server. The caller first asks for a presigned S3 PUT URL (sign/upload), uploads the bytes directly to S3, then calls confirm/{key} so the backend can check the object actually landed (HeadObject) before trusting it.
  • Every owner has a storage quota (10 GiB by default, platform.filestorage.quota.default-bytes), checked at sign time against the sum of the owner's file_storage_objects.size_bytes.
  • Validation policy (platform.filestorage.validation.*): allowed MIME types image/jpeg|png|gif|webp, application/pdf, text/plain, application/octet-stream; extensions jpg jpeg png gif webp pdf txt bin; maximum 100 MiB. Domain modules add stricter rules on top (the gallery allows only JPEG, PNG and WebP up to 5 MB).
  • User-initiated deletes are soft first and physical later. DELETE only sets deleted_at. A scheduled job removes the S3 object after app.storage.deletion.retention-days (default 30).
  • Confirmed uploads can be mirrored to a backup bucket through the outbox_replication_jobs table, but replication is off in every profile (app.storage.replication.enabled: false).

Key entities & DB tables

All three tables are in the main schema, defined in V138__baseline_schema.sql. No later migration changes them.

EntityTableNotes

Key services

ServiceOrchestrates
FileStorageServiceThe main entry point. It has two separate surfaces.
FSO-tracked (browser) flow: signUpload() runs the validation chain, checks quota, generates a key and presigns a PUT (app.storage.upload-ttl-seconds, 600). confirmUpload() runs HeadObject and checks content type, size and ETag, then in one TransactionTemplate saves the FSO and a REPLICATE job. After that commits it publishes StorageObjectConfirmedEvent. signDownload() records a StorageAccessEvent and presigns a GET (app.storage.presign-ttl-seconds, 300). softDelete() checks that the caller's login equals createdBy, then runs a conditional softDeleteByKey. findActiveObject(key) (new in #312) returns the confirmed, non-deleted FSO as a StorageObjectDto so a domain module can check the HEAD-verified owner, type and size before linking a key.
Raw (server-generated) helpers: storeBytes (direct S3Client.putObject, optional Content-Disposition), downloadBytes, signedDownloadUrl(key) / signedDownloadUrl(key, Duration), deleteRawBytes (immediate hard delete), and assertOwnership. These bypass the FSO table: no quota, no replication, no soft-delete lifecycle and no audit row.
BlobDeletionOutboxSupport / BlobDeletionOutboxHandlerRe-drivable deletion of raw keys through the generic platform.outbox module (aggregate type BLOB_DELETION, payload {storageKey}). Producers call enqueue(keys) and requestDrainAfterCommit() inside their business transaction. The handler calls deleteRawBytes, which is idempotent because S3 DeleteObject succeeds on a missing key. The only producer today is GdprErasureService. This replaced the old bespoke PendingBlobDeletionService (skillars-deferred-100).
ReplicatedStorageServiceA StorageService decorator, created only when replication is enabled. put() delegates to the primary and then enqueues a REPLICATE job if an FSO exists for the key. delete and deleteAll (the bulk delete added in skillars-deferred-164) touch the primary only. Everything else passes straight through.
OutboxPollerSchedulerExists only when replication is enabled. Runs every app.storage.poller.fixed-delay-ms (5 s) under ShedLock OutboxPollerScheduler_pollAndProcess (PT10M, at least app.storage.poller.lock-at-least, default PT2S). It claims up to app.storage.poller.batch-size (10) PENDING jobs with FOR UPDATE SKIP LOCKED and marks them PROCESSING in the same transaction. Then it copies primary → backup (REPLICATE) or deletes on backup (DELETE), retrying up to app.storage.replication.max-attempts (5) before marking a job FAILED. It also updates a queue-depth gauge.
DeletionSchedulerServiceAlways on. Runs on the same 5 s cadence under ShedLock DeletionSchedulerService_processDeletions (PT5M, at least app.storage.deletion.lock-at-least, default PT2S). It selects soft-deleted FSOs older than the retention cutoff (FOR UPDATE SKIP LOCKED, batch 10), calls StorageService.delete, then uses a conditional markPhysicallyDeleted and enqueues a DELETE job only if that update hit one row.
StorageMigrationServiceAn ops utility. It is a plain class, not a bean, so nothing wires it. It moves objects between two StorageService back ends (migrate, migrateAll(ownerId)) and exports and imports FSO metadata as StorageObjectDto.
StorageKeyGeneratorBuilds keys as {entity}/{entityId}/{yyyy}/{mm}/{uuid}.{extension} and parses them back. This is how listeners and domain modules recover which business entity an upload belongs to (for example, CoachGalleryService requires the prefix coach_gallery/{userId}/).
ValidationChain + ValidationStepsOrdered pipeline on every sign-upload: FilenameSanitizationStep (1), MimeTypeValidationStep (10), ExtensionValidationStep (20), FileSizeValidationStep (30), and ChecksumValidationStep (40, which requires a 64-character lowercase SHA-256 hex if a checksum is given).

Keys may contain /, so the controller reads them from PATH_WITHIN_HANDLER_MAPPING_ATTRIBUTE instead of a path variable.

Domain events

filestorage.event.StorageObjectConfirmedEvent is published by FileStorageService.confirmUpload() after the FSO and outbox transaction has committed, not inside it. Listeners run synchronously on the request thread with no surrounding transaction. There is one listener: marketplace.service.CoachProfilePhotoEventListener (plain @EventListener). It parses the key, and for entity=coach_profile keys only, sets the coach's photoUrl. Gallery and branding keys are linked by explicit domain calls, not by this event. filestorage consumes no events. Its BLOB_DELETION handler is driven by the generic outbox poller.

Dependency on infrastructure.blobstore: filestorage is built on infrastructure.blobstore's StorageService interface (used by replication, migration and deletion), its S3Client/S3Presigner beans (used directly by FileStorageService, because presigning is S3-specific), BlobstoreProperties (app.storage.*) and StorageMetrics. Back-end details such as S3/MinIO, bucket, credentials and backup wiring are on the Infrastructure page. Two configuration namespaces are involved: app.storage.* (blobstore: TTLs, poller, replication, retention) and platform.filestorage.* (this module: validation, quota).

Key Flows

Uploading a file (presigned two-phase upload)

sequenceDiagram
  participant Browser as Browser (Coach/Parent)
  participant Resource as StorageResource
  participant Service as FileStorageService
  participant Chain as ValidationChain
  participant S3 as S3 (via S3Presigner/S3Client)
  participant DB as file_storage_objects / outbox_replication_jobs
  participant Listener as CoachProfilePhotoEventListener

  Browser->>Resource: POST /api/storage/sign/upload {entity, entityId, contentType, extension, fileSizeBytes, checksum}
  Resource->>Resource: owner-bound entity? entityId must equal caller
  Resource->>Service: signUpload(request)
  Service->>Chain: validate(request)
  Chain-->>Service: OK (or StorageValidationException, 422)
  Service->>DB: sumSizeBytesByOwnerId (QuotaExceededException, 429)
  Service->>Service: key = StorageKeyGenerator.generate(entity, entityId, ext)
  Service->>S3: presign PUT (upload-ttl-seconds)
  Service-->>Browser: 200 {key, uploadUrl, expiresAt}
  Browser->>S3: PUT bytes directly to uploadUrl
  Browser->>Resource: POST /api/storage/confirm/{key} {contentType, fileSizeBytes, ...}
  Resource->>Service: confirmUpload(key, request)
  alt FSO already exists for key
    Service-->>Browser: 200 existing record (no new event)
  else
    Service->>S3: HeadObject(key)
    S3-->>Service: contentType, contentLength, eTag
    Service->>Service: declared type/size must match, ETag present
    Service->>DB: TX: save FileStorageObject + OutboxReplicationJob(REPLICATE, PENDING), commit
    Service->>Listener: publish StorageObjectConfirmedEvent (after commit, no TX)
    Service-->>Browser: 200 ConfirmUploadResponse
  end
  opt gallery upload
    Browser->>Browser: POST /api/marketplace/coaches/me/profile/gallery {key}
    Note over Browser: CoachGalleryService.addImage re-validates via findActiveObject
  end

The app server never sees browser-uploaded bytes. confirmUpload() is the trust boundary: it checks size, content type and the presence of an ETag with a live HeadObject, and it stores the HEAD values, not the client's claims. Confirmation is idempotent: if an FSO already exists for the key, it is returned unchanged and no event is published. Because the event is published after the commit, a listener that throws makes the HTTP call fail even though the FSO is already persisted. A client retry then hits the idempotent short-circuit and never re-fires the event (see gotchas).

Downloading a file

sequenceDiagram
  participant Caller as Browser
  participant Resource as StorageResource
  participant Service as FileStorageService
  participant DB as file_storage_objects / storage_access_events
  participant S3 as S3 (via S3Presigner)

  Caller->>Resource: GET /api/storage/sign/download/{key}
  Resource->>Service: signDownload(key)
  Service->>DB: findByKeyAndDeletedAtIsNull(key)
  alt not found or soft-deleted
    Service-->>Caller: 404 StorageObjectNotFoundException
  else found
    Service->>DB: save StorageAccessEvent(key, ownerId, sizeBytes)
    Service->>S3: presign GET (presign-ttl-seconds)
    Service-->>Caller: 200 {key, downloadUrl, expiresAt}
    Caller->>S3: GET downloadUrl (direct)
  end

Downloads never proxy bytes through the application. A soft-deleted object is treated as not found, so deletion takes effect at once for REST downloads even though the bytes remain during the retention window. Most of the app does not call this endpoint at all, though. Coach photos, gallery images, report PDFs and GDPR exports are signed server-side with signedDownloadUrl and embedded in DTOs, which neither checks deleted_at nor writes an access event.

Soft delete, retention, replication and raw-blob deletion

sequenceDiagram
  participant Caller as Caller
  participant Service as FileStorageService
  participant DelSched as DeletionSchedulerService
  participant Outbox as OutboxPollerScheduler (replication only)
  participant Primary as Primary StorageService
  participant Backup as Backup StorageService
  participant Gdpr as GdprErasureService
  participant GenOutbox as platform.outbox (BLOB_DELETION)

  Caller->>Service: DELETE /api/storage/{key} (or CoachGalleryService/CoachProfileService.softDelete)
  Service->>Service: createdBy == current login? softDeleteByKey
  Service-->>Caller: 204 (deleted_at set)

  loop every app.storage.poller.fixed-delay-ms (ShedLock)
    DelSched->>DelSched: findEligibleForPhysicalDeletion(deleted_at older than retentionDays, 10)
    DelSched->>Primary: delete(key)
    DelSched->>DelSched: TX: markPhysicallyDeleted == 1 then save OutboxReplicationJob(DELETE)
  end

  loop every app.storage.poller.fixed-delay-ms (ShedLock)
    Outbox->>Outbox: pollPending FOR UPDATE SKIP LOCKED, mark PROCESSING
    alt REPLICATE
      Outbox->>Primary: get(key)
      Outbox->>Backup: put(key, stream)
    else DELETE
      Outbox->>Backup: delete(key)
    end
    Outbox->>Outbox: COMPLETED, or retry, then FAILED after max-attempts
  end

  Gdpr->>GenOutbox: enqueue(keys) + requestDrainAfterCommit (inside erasure TX)
  GenOutbox->>Service: BlobDeletionOutboxHandler, deleteRawBytes(key) (idempotent)

FSO-tracked deletion has two stages: the user-facing DELETE only sets a flag, and the scheduler does the irreversible S3 delete later, then queues a backup DELETE through the same replication outbox. DeletionSchedulerService's SKIP LOCKED claim commits before the loop runs, so ShedLock plus the conditional markPhysicallyDeleted (affected-row count checked before the outbox save) is what stops two ticks from double-enqueueing. Raw keys written by storeBytes are never soft-deleted. They are removed immediately (deleteRawBytes) or through the re-drivable BLOB_DELETION outbox.

Conventions & Gotchas

Never call infrastructure.blobstore storage beans from another platform module. Always go through filestorage. Other modules must use the /api/storage/** endpoints (browser uploads) or FileStorageService's methods, plus BlobDeletionOutboxSupport for deletes that must survive a crash. This rule holds today. Outside this module, the only infrastructure.blobstore imports are exception and error-code types: StorageObjectNotFoundException in CoachProfileService and CoachGalleryService, and BlobstoreErrorCode/exceptions in ApiAdvice.

There are two kinds of object, with different guarantees. Browser uploads get an FSO row, so quota, replication, the soft-delete and retention lifecycle, findActiveObject and REST download auditing all apply. Server-generated files written by storeBytes (report PDFs under reports/, GDPR ZIPs under gdpr/exports/) get none of that: they are invisible to quota, never replicated, and assertOwnership passes for them because it only rejects when an FSO row exists with a different owner. Do not use assertOwnership as proof that a key belongs to the caller unless the key is guaranteed to be FSO-tracked. Prefer findActiveObject and an explicit owner comparison, as CoachGalleryService does.

Replication is off, but the outbox rows are still written. confirmUpload() always inserts a REPLICATE job, and DeletionSchedulerService always inserts a DELETE job. OutboxPollerScheduler is only created when app.storage.replication.enabled=true, which no profile sets. With the current config, main.outbox_replication_jobs collects PENDING rows that nothing drains. If you turn replication on in an existing environment, the poller starts by working through that whole backlog, including DELETE jobs for keys that were never replicated.

The quota is soft and counts deleted files. signUpload() sums size_bytes for the owner without filtering deleted_at, so deleting files never frees quota. There is also a time-of-check/time-of-use gap: the check happens at sign time and is not repeated at confirm time, so several large uploads signed at once can all pass. Do not treat the quota as a hard, race-proof limit.

Upload-time ownership checks are opt-in, and downloads have none. StorageResource enforces "entityId must equal the caller" only for OWNER_BOUND_ENTITIES (coach_profile, coach_branding, coach_gallery). If you add an owner-sensitive entity, add it there. confirm does not check the key's prefix against the caller, and its idempotent short-circuit returns an existing FSO to whoever asks. sign/download lets any authenticated user download any confirmed key. Protection relies on keys containing a random UUID. Domain modules that link keys must check them again server-side (prefix + findActiveObject owner), as CoachGalleryService.addImage does.

The event fires after commit, and a retry will not fire it again. Because StorageObjectConfirmedEvent is published after the FSO transaction, a failure in CoachProfilePhotoEventListener returns an error to the browser while the FSO is already saved, and a repeated confirm short-circuits without publishing. New features should link uploads with an explicit, idempotent domain call (the gallery pattern) rather than a new listener on this event.

The sign/confirm/download flow bypasses the StorageService abstraction on purpose. Presigned URLs need S3Presigner, which the generic interface does not expose, and the raw helpers also call S3Client directly. Only ReplicatedStorageService, OutboxPollerScheduler, DeletionSchedulerService and StorageMigrationService use the portable interface. The presigning path is S3-only, which includes MinIO in dev.

Video bytes do not go through this module. The video module has no import of filestorage or infrastructure.blobstore. Video goes through its own Bunny Stream pipeline, which is also why the coach gallery accepts images only.
