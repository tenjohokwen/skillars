Filestorage

The single, audited front door every platform module must use to upload, download, and delete files — nobody talks to S3 directly except this module.

Business Overview

Skillars accumulates files from almost every persona: a Coach's profile photo, a voice note recorded during a Booking wrap-up, a GDPR data-export ZIP an Admin generates for a Parent, a branded session-report PDF a Coach downloads. None of those modules know or care whether the bytes end up in S3, on local disk, or get mirrored to a backup region — that's filestorage's job. It exists to answer, once, for the whole platform: "how do we accept an upload safely, enforce a size/type/quota policy on it, know who owns it, let it be downloaded again without proxying the bytes through our own servers, and eventually delete it — including from a backup copy — without losing track of any of that in the process?"

Personas touch filestorage almost entirely indirectly, through whichever module owns the business flow:

  • Coaches upload a profile photo during the Marketplace profile builder; the photo bytes go straight from the browser to S3 via a presigned URL that filestorage issues.
  • Parents/Coaches record a voice note during a session wrap-up (Booking module); the frontend calls filestorage's generic /api/storage endpoints directly, tagging the upload with entity=booking.
  • Admins trigger GDPR export/erasure jobs that store a generated ZIP bundle and later delete it, via filestorage's programmatic Java API.
  • Coaches download generated session-report PDFs and branding logos (Development module), again via filestorage's programmatic API and presigned download URLs.

Key business rules found in the code:

  • Uploads are two-phase and never touch the app server's bytes. A caller first asks for a presigned S3 PUT URL (sign/upload), uploads bytes directly to S3 from the browser, then calls back to confirm/** so the backend can verify the object actually landed (via HeadObject) before it trusts it exists.
  • Every owner has a storage quota (10 GiB by default, platform.filestorage.quota.default-bytes), enforced by summing existing file_storage_objects.size_bytes for the caller before a new upload is signed.
  • Deletes are soft first, physical later. A DELETE just marks a row deleted_at; a scheduled job physically removes the S3 object only after a retention window (app.storage.deletion.retention-days, default 30 days) has passed.
  • Every write can be asynchronously mirrored to a backup region/bucket via a transactional outbox table, so a slow or failing backup copy never blocks the primary upload/delete request.

Technical Overview

Package layout

filestorage.contractRequest/response records (sign/confirm/download), ValidationRequest, StorageObjectDto (metadata export/import), and FileStorageErrorCode.

filestorage.repoJPA entities/repositories: FileStorageObject, OutboxReplicationJob, StorageAccessEvent.
filestorage.serviceThe core orchestration: FileStorageService, ReplicatedStorageService, OutboxPollerScheduler, DeletionSchedulerService, StorageMigrationService, StorageKeyGenerator, and the validation chain.
filestorage.service.validationFive ordered ValidationStep components run by ValidationChain on every sign-upload request.

Key entities & DB tables

EntityTableNotes
FileStorageObjectfile_storage_objectsThe record of a confirmed upload: key, owner_id, filename, content type, size, checksum, JSON tags, provider/bucket, upload_confirmed_at, plus deleted_at/physical_deleted_at for the two-stage delete lifecycle. Extends AbstractAuditingEntity, so createdBy is used as the upload's owner-of-record for delete authorization.
OutboxReplicationJoboutbox_replication_jobsTransactional outbox row per REPLICATE/DELETE action, with status (PENDING/PROCESSING/COMPLETED/FAILED), attemptCount, and errorMessage. One row is created in the same DB transaction as the primary write it shadows.
StorageAccessEventstorage_access_eventsAppend-only audit log of every signed-download request (key, owner, size, timestamp) — used for access auditing, not currently exposed via any read API.

Key services

ServiceOrchestrates
FileStorageServiceThe main entry point. signUpload() runs the validation chain, checks the owner's quota, generates a storage key, and presigns an S3 PUT. confirmUpload() verifies the object via HeadObject, persists FileStorageObject, enqueues a REPLICATE outbox job, and publishes StorageObjectConfirmedEvent — all inside one transaction. signDownload() records a StorageAccessEvent and presigns a GET. softDelete() checks the caller is the original uploader (createdBy) before flagging deleted_at. It also exposes programmatic helpers (storeBytes, downloadBytes, signedDownloadUrl, deleteRawBytes, assertOwnership) used by server-side callers that generate their own files (PDFs, ZIPs) rather than accepting a browser upload.
ReplicatedStorageServiceA StorageService decorator (conditional @Primary bean when app.storage.replication.enabled=true): after delegating put() to the real primary StorageService, it enqueues a REPLICATE outbox job for that key. All other methods pass straight through.
OutboxPollerSchedulerScheduled job (app.storage.poller.fixed-delay-ms, default 5s) that claims PENDING outbox rows with FOR UPDATE SKIP LOCKED, streams the object from the primary StorageService to the backup one for REPLICATE jobs (or calls delete() on the backup for DELETE jobs), and retries with an attempt counter up to app.storage.replication.max-attempts before marking a job FAILED.
DeletionSchedulerServiceScheduled job on the same interval that finds soft-deleted FileStorageObjects past the retention cutoff, physically deletes them from the primary store, enqueues a DELETE outbox job (so the backup copy is cleaned up too), and marks physical_deleted_at.
StorageMigrationServiceOps utility (plain class, not a managed bean) for moving objects between two StorageService backends — e.g. local-disk-to-S3 migration — plus exporting/importing FileStorageObject metadata as StorageObjectDto for backup/restore.
StorageKeyGeneratorGenerates keys as {entity}/{entityId}/{yyyy}/{mm}/{uuid}.{extension} and parses them back apart. This convention is how other modules (e.g. Marketplace) recover "which business entity does this confirmed upload belong to" without any extra columns.
ValidationChain + ValidationStepsOrdered pipeline run on every sign-upload: FilenameSanitizationStep (order 1, strips control chars/path traversal), MimeTypeValidationStep (10), ExtensionValidationStep (20), FileSizeValidationStep (30), ChecksumValidationStep (40, requires a 64-char lowercase SHA-256 hex if provided).

Domain events

filestorage publishes filestorage.event.StorageObjectConfirmedEvent from FileStorageService.confirmUpload(), inside the same transaction as the persisted FileStorageObject. It is currently consumed by exactly one listener platform-wide: marketplace.service.CoachProfilePhotoEventListener, which parses the key via StorageKeyGenerator and, only for entity=coach_profile keys, updates the matching coach's photoUrl. filestorage does not consume any events published by other modules.

Dependency on infrastructure.blobstore: filestorage is built directly on top of infrastructure.blobstore's StorageService interface (used by the replication/migration/deletion code paths) and its S3 SDK beans — S3Client and S3Presigner, built by BlobstoreConfig from BlobstoreProperties — which FileStorageService autowires directly for the sign/confirm/download HTTP flow (presigning needs the S3-specific presigner API, not just the generic StorageService abstraction). Everything backend-specific — S3 vs. local disk, bucket names, credentials, backup-region wiring — lives in infrastructure.blobstore and is covered in depth on the Infrastructure page; this page only documents the boundary.

Key Flows

Uploading a file (presigned two-phase upload)

sequenceDiagram
  participant Browser as Browser (Coach/Parent)
  participant Resource as StorageResource
  participant Service as FileStorageService
  participant Chain as ValidationChain
  participant S3 as S3 (via S3Presigner/S3Client)
  participant DB as file_storage_objects / outbox_replication_jobs
  participant Listener as e.g. CoachProfilePhotoEventListener

  Browser->>Resource: POST /api/storage/sign/upload {entity, entityId, contentType, extension, fileSizeBytes, checksum}
  Resource->>Service: signUpload(request)
  Service->>Chain: validate(request)
  Chain-->>Service: OK (or StorageValidationException)
  Service->>Service: check owner quota (sumSizeBytesByOwnerId)
  Service->>Service: generate key via StorageKeyGenerator
  Service->>S3: presign PUT (uploadTtlSeconds)
  Service-->>Resource: SignUploadResponse {key, uploadUrl, expiresAt}
  Resource-->>Browser: 200 OK
  Browser->>S3: PUT bytes directly to uploadUrl
  Browser->>Resource: POST /api/storage/confirm/{key} {contentType, fileSizeBytes, checksum}
  Resource->>Service: confirmUpload(key, request)
  Service->>S3: HeadObject(key)
  S3-->>Service: contentType, contentLength, eTag
  Service->>DB: save FileStorageObject + OutboxReplicationJob(REPLICATE, PENDING)
  Service->>Listener: publish StorageObjectConfirmedEvent
  Service-->>Resource: ConfirmUploadResponse
  Resource-->>Browser: 200 OK

The app server never sees the file's bytes — the browser uploads straight to S3 using the presigned URL, which keeps upload traffic off the Spring Boot instances entirely. confirmUpload() is the trust boundary: it re-verifies size, content type, and that an ETag exists via a live HeadObject call, so a client can't simply lie about what it uploaded. If a FileStorageObject for the key already exists, confirmUpload() short-circuits and returns the existing record — confirmation is idempotent. The event publish and outbox insert happen in the same transaction as the object save, so a listener never sees a confirmed upload that isn't durably persisted.

Downloading / streaming a file

sequenceDiagram
  participant Caller as Caller (browser or another module)
  participant Resource as StorageResource
  participant Service as FileStorageService
  participant DB as file_storage_objects / storage_access_events
  participant S3 as S3 (via S3Presigner)

  Caller->>Resource: GET /api/storage/sign/download/{key}
  Resource->>Service: signDownload(key)
  Service->>DB: findByKeyAndDeletedAtIsNull(key)
  alt not found or soft-deleted
    Service-->>Resource: StorageObjectNotFoundException (404)
  else found
    Service->>DB: save StorageAccessEvent(key, ownerId, sizeBytes)
    Service->>S3: presign GET (presignTtlSeconds)
    Service-->>Resource: SignDownloadResponse {key, downloadUrl, expiresAt}
    Resource-->>Caller: 200 OK
    Caller->>S3: GET downloadUrl (direct fetch/stream)
  end

Like uploads, downloads never proxy bytes through the application — the caller gets a short-lived presigned URL and streams directly from S3. A soft-deleted object (deleted_at set) is treated as not found, so deletion takes effect immediately for downloads even though the physical bytes and DB row still exist during the retention window. Every successful sign-download is recorded as a StorageAccessEvent before the URL is even returned, giving an audit trail of who accessed what and when.

Soft delete, retention, and cross-region replication (outbox pattern)

sequenceDiagram
  participant Caller as Caller
  participant Resource as StorageResource
  participant Service as FileStorageService
  participant DelSched as DeletionSchedulerService
  participant Outbox as OutboxPollerScheduler
  participant Primary as Primary StorageService
  participant Backup as Backup StorageService

  Caller->>Resource: DELETE /api/storage/{key}
  Resource->>Service: softDelete(key, currentUser)
  Service->>Service: verify createdBy == currentUser
  Service-->>Resource: 204 No Content (deleted_at set)

  loop every poller.fixed-delay-ms
    DelSched->>DelSched: find FSOs with deleted_at < now-retentionDays
    DelSched->>Primary: delete(key)
    DelSched->>DelSched: enqueue OutboxReplicationJob(DELETE, PENDING), mark physical_deleted_at
  end

  loop every poller.fixed-delay-ms
    Outbox->>Outbox: pollPending() FOR UPDATE SKIP LOCKED, mark PROCESSING
    alt job type REPLICATE
      Outbox->>Primary: get(key)
      Outbox->>Backup: put(key, data, length, contentType)
    else job type DELETE
      Outbox->>Backup: delete(key)
    end
    Outbox->>Outbox: mark COMPLETED, or increment attempt / mark FAILED
  end

Deletion is deliberately two-staged: the user-facing DELETE only flips a flag, so it's instant and reversible-in-principle during the retention window. A separate scheduler does the actual, irreversible S3 deletion later and — importantly — routes that physical deletion through the same outbox table used for replication, so the backup copy is guaranteed to eventually be deleted too, not just the primary. The outbox poller uses FOR UPDATE SKIP LOCKED so multiple app instances can run the scheduler concurrently without double-processing a job, and gives up on a job (marking it FAILED) only after replication.max-attempts retries.

Conventions & Gotchas

Never call infrastructure.blobstore directly from another platform module — always go through filestorage. Every other module that needs to store or retrieve a file (profile photos, drill videos, generated documents, GDPR bundles) must go through filestorage's public surface: the /api/storage/** REST endpoints for end-user-driven uploads/downloads, or FileStorageService's programmatic methods (storeBytes, downloadBytes, signedDownloadUrl, deleteRawBytes, assertOwnership) for server-generated files, as Admin and Development already do. filestorage is the only module that is allowed to depend on infrastructure.blobstore's StorageService/S3Client/S3Presigner beans directly. This is the single point of control for: swapping the storage backend (S3 vs. local disk) or adding a new one without touching business modules; enforcing per-owner quota and the file-validation chain consistently; recording ownership (FileStorageObject.ownerId/createdBy) and access history (StorageAccessEvent) for every file regardless of which module requested it; and guaranteeing the soft-delete/retention/outbox-replication lifecycle runs for every object. A module that wrote straight to infrastructure.blobstore would silently skip all of that — no quota accounting, no audit trail, no replication, and no coordinated deletion.

The sign/confirm/download HTTP flow bypasses the StorageService abstraction on purpose. FileStorageService autowires S3Client and S3Presigner directly rather than going through infrastructure.blobstore.service.StorageService, because presigned URLs are an S3-presigner-specific capability that the generic interface doesn't expose. Only the replication/migration/deletion code paths (ReplicatedStorageService, OutboxPollerScheduler, DeletionSchedulerService, StorageMigrationService) go through the portable StorageService interface. Keep this split in mind if you ever try to make the whole module provider-agnostic — the presigning path is currently S3-only.

Quota is checked at sign-upload time, not at confirm time. signUpload() sums existing bytes for the owner and compares against the quota before issuing a presigned URL — there's a time-of-check/time-of-use gap if a caller signs several large uploads concurrently before confirming any of them, since nothing re-checks the quota in confirmUpload(). Don't rely on the quota being a hard, race-proof limit today.

Entity-ownership validation at upload time is opt-in, not universal. StorageResource only enforces "entityId must match the caller" for entities listed in its OWNER_BOUND_ENTITIES set (currently just coach_profile). Any other entity value (e.g. booking) is accepted with whatever entityId the client sends at sign-upload time — ownership for those is only enforced later, and only for delete, via softDelete() checking createdBy. If you add a new owner-sensitive entity type, add it to OWNER_BOUND_ENTITIES.

Not every module that handles files goes through filestorage today. The video module has no imports of filestorage or infrastructure.blobstore anywhere in its source as of this writing — it manages its own video bytes through a separate pipeline. Don't assume drill-video storage is covered by anything documented on this page; check the Video module directly.

Related Modules

  • Marketplace — CoachProfilePhotoEventListener consumes StorageObjectConfirmedEvent to sync a confirmed coach profile photo upload onto CoachProfile.photoUrl.
  • Booking — the frontend wrap-up flow calls /api/storage/sign/upload and /confirm/** directly (tagged entity=booking) to store session voice-note recordings; no Java code in the booking module itself touches filestorage.
  • Admin — GdprExportService/GdprErasureService use FileStorageService.storeBytes/signedDownloadUrl/deleteRawBytes to store, share, and clean up generated GDPR export ZIPs.
  • Development — ReportGenerationService uses the same programmatic API to store/download/delete session-report PDFs and coach branding logo assets.
  • Security — supplies SecurityUtil (current user/business id resolution) that filestorage depends on for ownership; conversely, security.api.ApiAdvice maps filestorage's QuotaExceededException/StorageValidationException to HTTP error responses in the platform's global exception handler.
  • Infrastructure — infrastructure.blobstore is the only thing filestorage is allowed to sit on top of; see the boundary callout above and the Infrastructure page for the S3/local-disk backend details.
