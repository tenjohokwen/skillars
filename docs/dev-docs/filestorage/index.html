    Filestorage

    The single, audited front door every platform module must use to upload, download, and delete files — nobody talks to S3 directly except this module.

    Business Overview

    Skillars stores files for almost every persona: a coach's profile photo and gallery images, a coach's report branding logo, a branded session-report PDF, and a GDPR data-export ZIP. None of those modules knows whether the bytes end up in S3 (SeaweedFS in every environment today), or get mirrored to a backup bucket. That is filestorage's job. It answers, once for the whole platform: how do we accept a browser upload safely, enforce a size, type and quota policy, know who owns the file, let it be downloaded without proxying bytes through our servers, and eventually delete it?

    Personas touch filestorage almost entirely indirectly, through the module that owns the business flow:

    • Coaches upload a profile photo in the Marketplace profile builder. The bytes go straight from the browser to S3 via a presigned URL (entity coach_profile), and CoachProfilePhotoEventListener links the confirmed key to the profile.
    • Coaches upload up to 6 public-profile gallery images (entity coach_gallery, added in #312). The browser runs sign → PUT → confirm, then calls POST /api/marketplace/coaches/me/profile/gallery {key}. marketplace.CoachGalleryService then checks the key again on the server with FileStorageService.findActiveObject (owner, JPEG/PNG/WebP, ≤5 MB), and removal soft-deletes the object. Frontend: components/profile/EditCoachGalleryDialog.vue.
    • Coaches upload a report-branding logo (entity coach_branding) and download generated session-report PDFs. development.ReportGenerationService stores the PDF server-side (storeBytes, key reports/{uuid}/report.pdf), reads the logo (downloadBytes, after assertOwnership), and hands out signedDownloadUrls.
    • Coaches may attach an enhanced criminal-record certificate to an optional safeguarding-check request (S-09). marketplace.CoachSafeguardingService encrypts it with Cryptopher and stores the ciphertext with storeBytes under safeguarding/{coachId}/{uuid}.enc. There is no file_storage_objects row, so signDownload cannot hand out a URL for it; only the audited admin endpoint reads it back (downloadBytes + decrypt). It is deleted through BlobDeletionOutboxSupport when staff decide, on withdraw / replace / erasure, and by a sweeper after coach.safeguarding.uploadRetentionDays. PROD's daily volume backup archives the bucket directory, so a deleted upload can outlive its deletion in a backup until that archive rotates (see the provisioning checklist).
    • Parents, players and admins get GDPR export ZIPs that admin.GdprExportService stores with storeBytes (key gdpr/exports/{requestId}.zip) and shares with a time-limited signedDownloadUrl(key, Duration). admin.GdprErasureService deletes a user's blobs (exports, child and coach report PDFs, gallery images, and since C4 the coach's profile photo and report-branding logo — only keys that are the coach's own uploads) through BlobDeletionOutboxSupport.
    • The old booking wrap-up voice note is gone (story 12.7, D3). Legacy audio/webm objects tagged entity=booking may still exist, unread and unlinked. Clean-up is tracked in _bmad-output/implementation-artifacts/deferred-work.md.

    Key business rules found in the code:

    • Browser uploads happen in two phases and never pass through the app server. The caller first asks for a presigned S3 PUT URL (sign/upload), uploads the bytes directly to S3, then calls confirm/{key} so the backend can check the object actually landed (HeadObject) before trusting it.
    • Every owner has a storage quota (10 GiB by default, platform.filestorage.quota.default-bytes), checked at sign time against the sum of size_bytes of the owner's non-deleted file_storage_objects (soft-deleting a file frees its quota at once), and enforced again at confirm time against the real size, serialized per owner (see the gotcha below).
    • Validation policy (platform.filestorage.validation.*): allowed MIME types image/jpeg|png|gif|webp, application/pdf, text/plain, application/octet-stream; extensions jpg jpeg png gif webp pdf txt bin; maximum 100 MiB. Domain modules add stricter rules on top (the gallery allows only JPEG, PNG and WebP up to 5 MB).
    • User-initiated deletes are soft first and physical later. DELETE only sets deleted_at. A scheduled job removes the S3 object after app.storage.deletion.retention-days (default 30).
    • Confirmed uploads can be mirrored to a backup bucket through the outbox_replication_jobs table, but replication is off in every profile (app.storage.replication.enabled: false), and while it is off no replication job is written.
    • Only the uploader (or an admin) can get a download URL from sign/download. Files shown to other users (coach photos, gallery images, branding logos, report PDFs, GDPR exports) are signed by their owning module with signedDownloadUrl, after that module's own access check.

    Technical Overview

    Package layout

    PackagePurpose

    filestorage.configFileStorageProperties (platform.filestorage.*: validation rules, quota) and FileStorageConfig, which creates ReplicatedStorageService (@Primary) and OutboxPollerScheduler only when app.storage.replication.enabled=true.

    filestorage.repoJPA entities and repositories: FileStorageObject, OutboxReplicationJob, StorageAccessEvent.
    filestorage.serviceFileStorageService, ReplicatedStorageService, OutboxPollerScheduler, DeletionSchedulerService, BlobDeletionOutboxSupport + BlobDeletionOutboxHandler, StorageMigrationService, StorageKeyGenerator, ValidationChain/ValidationStep, and FileValidator/FileValidatorImpl.
    filestorage.service.validationFive ordered ValidationStep components that ValidationChain runs on every sign-upload request.

    Key entities & DB tables

    All three tables are in the main schema, defined in V138__baseline_schema.sql. The only later change is V147__file_storage_objects_auditing_columns.sql, which adds the seven AbstractAuditingEntity columns (created_by, created_date, last_modified_by, last_modified_date, request_id, session_id, status) to file_storage_objects that Hibernate had been adding outside Flyway.

    EntityTableNotes
    FileStorageObjectmain.file_storage_objectsThe record of a confirmed browser upload: key, owner_id (the confirmer's business id), original filename, content type and size (taken from HeadObject, not the client), checksum, JSON tags, provider and bucket, upload_confirmed_at, plus deleted_at/physical_deleted_at for the two-stage delete. Extends AbstractAuditingEntity. createdBy (the login) is what softDelete authorizes against. Files written with storeBytes have no row here.
    OutboxReplicationJobmain.outbox_replication_jobsOne row per REPLICATE/DELETE action for an FSO, with status (PENDING/PROCESSING/COMPLETED/FAILED), attemptCount, lastAttemptedAt and errorMessage (≤500). Inserted in the same transaction as the write it shadows.
    StorageAccessEventmain.storage_access_eventsAppend-only audit row for every REST sign-download (key, owner, size, timestamp). There is no read API. The programmatic signedDownloadUrl does not write one.

    Key services

    ServiceOrchestrates
    FileStorageServiceThe main entry point. It has two separate surfaces.
    FSO-tracked (browser) flow: signUpload() runs the validation chain, checks quota, generates a key and presigns a PUT (app.storage.upload-ttl-seconds, 600). confirmUpload() accepts only keys of the shape StorageKeyGenerator issues (so a storeBytes key such as reports/… is a 404) and, for owner-bound entities, only keys whose entityId is the caller. It runs HeadObject and checks content type, size and ETag, re-applies the max-size limit to the real size (the presigned PUT does not bind the length), then in one TransactionTemplate takes the owner's quota advisory lock, re-checks the quota against the real size, and saves the FSO (plus a REPLICATE job when replication is enabled). After that commits it publishes StorageObjectConfirmedEvent. signDownload() requires the caller to be the FSO's owner or an admin (anyone else gets a 404), then records a StorageAccessEvent and presigns a GET (app.storage.presign-ttl-seconds, 300). softDelete() checks that the caller's login equals createdBy, then runs a conditional softDeleteByKey. findActiveObject(key) (new in #312) returns the confirmed, non-deleted FSO as a StorageObjectDto so a domain module can check the HEAD-verified owner, type and size before linking a key.
    Raw (server-generated) helpers: storeBytes (direct S3Client.putObject, optional Content-Disposition), downloadBytes, signedDownloadUrl(key) / signedDownloadUrl(key, Duration), deleteRawBytes (immediate hard delete). These bypass the FSO table: no quota, no replication, no soft-delete lifecycle and no audit row. assertOwnership(key, ownerId) passes only for a non-deleted FSO owned by ownerId, so it always fails for these raw keys.
    BlobDeletionOutboxSupport / BlobDeletionOutboxHandlerRe-drivable deletion of raw keys through the generic platform.outbox module (aggregate type BLOB_DELETION, payload {storageKey}). Producers call enqueue(keys) and requestDrainAfterCommit() inside their business transaction. The handler calls deleteRawBytes, which is idempotent because S3 DeleteObject succeeds on a missing key. The only producer today is GdprErasureService. This replaced the old bespoke PendingBlobDeletionService (skillars-deferred-100).
    ReplicatedStorageServiceA StorageService decorator, created only when replication is enabled. put() delegates to the primary and then enqueues a REPLICATE job if an FSO exists for the key. delete and deleteAll (the bulk delete added in skillars-deferred-164) touch the primary only. Everything else passes straight through.
    OutboxPollerSchedulerExists only when replication is enabled. Runs every app.storage.poller.fixed-delay-ms (5 s) under ShedLock OutboxPollerScheduler_pollAndProcess (PT10M, at least app.storage.poller.lock-at-least, default PT2S). It claims up to app.storage.poller.batch-size (10) PENDING jobs with FOR UPDATE SKIP LOCKED and marks them PROCESSING in the same transaction. Then it copies primary → backup (REPLICATE) or deletes on backup (DELETE), retrying up to app.storage.replication.max-attempts (5) before marking a job FAILED. It also updates a queue-depth gauge.
    DeletionSchedulerServiceAlways on. Runs on the same 5 s cadence under ShedLock DeletionSchedulerService_processDeletions (PT5M, at least app.storage.deletion.lock-at-least, default PT2S). It selects soft-deleted FSOs older than the retention cutoff (FOR UPDATE SKIP LOCKED, batch 10), calls StorageService.delete, then uses a conditional markPhysicallyDeleted and enqueues a backup DELETE job only if that update hit one row and replication is enabled.
    StorageMigrationServiceAn ops utility. It is a plain class, not a bean, so nothing wires it. It moves objects between two StorageService back ends (migrate, migrateAll(ownerId)) and exports and imports FSO metadata as StorageObjectDto.
    StorageKeyGeneratorBuilds keys as {entity}/{entityId}/{yyyy}/{mm}/{uuid}.{extension} and parses them back. This is how listeners and domain modules recover which business entity an upload belongs to (for example, CoachGalleryService requires the prefix coach_gallery/{userId}/).
    ValidationChain + ValidationStepsOrdered pipeline on every sign-upload: FilenameSanitizationStep (1), MimeTypeValidationStep (10), ExtensionValidationStep (20), FileSizeValidationStep (30), and ChecksumValidationStep (40, which requires a 64-character lowercase SHA-256 hex if a checksum is given).

    REST endpoints

    MethodPathPurposeAuth/Role
    POST/api/storage/sign/uploadValidate and quota-check a proposed upload ({entity, entityId, contentType, extension, fileSizeBytes, checksum?, tags?}) and return {key, uploadUrl, expiresAt}.HAS_ANY_ROLE.     Errors (global security.api.ApiAdvice): QuotaExceededException → 429, StorageValidationException → 422, StorageObjectNotFoundException → 404, StorageProviderException → 502, AccessDeniedException (owner-bound entityId mismatch on sign or confirm) → 403, AuthorizationException on delete. Keys may contain /, so the controller reads them from PATH_WITHIN_HANDLER_MAPPING_ATTRIBUTE instead of a path variable.

    Domain events

    filestorage.event.StorageObjectConfirmedEvent is published by FileStorageService.confirmUpload() after the FSO and outbox transaction has committed, not inside it. Listeners run synchronously on the request thread with no surrounding transaction. There is one listener: marketplace.service.CoachProfilePhotoEventListener (plain @EventListener). It parses the key, and for entity=coach_profile keys only, sets the coach's photoUrl. Gallery and branding keys are linked by explicit domain calls, not by this event. filestorage consumes no events. Its BLOB_DELETION handler is driven by the generic outbox poller.

    Dependency on infrastructure.blobstore: filestorage is built on infrastructure.blobstore's StorageService interface (used by replication, migration and deletion), its S3Client/S3Presigner beans (used directly by FileStorageService, because presigning is S3-specific), BlobstoreProperties (app.storage.*) and StorageMetrics. Back-end details such as the S3 endpoint (SeaweedFS), bucket, credentials and backup wiring are on the Infrastructure page. Two configuration namespaces are involved: app.storage.* (blobstore: TTLs, poller, replication, retention) and platform.filestorage.* (this module: validation, quota).

    Key Flows

    Uploading a file (presigned two-phase upload)

    sequenceDiagram
  participant Browser as Browser (Coach/Parent)
  participant Resource as StorageResource
  participant Service as FileStorageService
  participant Chain as ValidationChain
  participant S3 as S3 (via S3Presigner/S3Client)
  participant DB as file_storage_objects / outbox_replication_jobs
  participant Listener as CoachProfilePhotoEventListener

  Browser->>Resource: POST /api/storage/sign/upload {entity, entityId, contentType, extension, fileSizeBytes, checksum}
  Resource->>Service: signUpload(request)
  Service->>Service: owner-bound entity? entityId must equal caller (403)
  Service->>Chain: validate(request)
  Chain-->>Service: OK (or StorageValidationException, 422)
  Service->>DB: sumSizeBytesByOwnerId (QuotaExceededException, 429)
  Service->>Service: key = StorageKeyGenerator.generate(entity, entityId, ext)
  Service->>S3: presign PUT (upload-ttl-seconds)
  Service-->>Browser: 200 {key, uploadUrl, expiresAt}
  Browser->>S3: PUT bytes directly to uploadUrl
  Browser->>Resource: POST /api/storage/confirm/{key} {contentType, fileSizeBytes, ...}
  Resource->>Service: confirmUpload(key, request)
  Service->>Service: owner-bound entityId must equal caller (403)
  alt FSO already exists for key
    Service->>Service: owner must equal caller and not soft-deleted (else 404)
    Service->>Listener: re-publish StorageObjectConfirmedEvent (only within upload-ttl-seconds of the first confirm)
    Service-->>Browser: 200 existing record
  else
    Service->>Service: key must have the StorageKeyGenerator shape (404)
    Service->>S3: HeadObject(key)
    S3-->>Service: contentType, contentLength, eTag
    Service->>Service: declared type/size must match, ETag present, real size within max size
    Service->>DB: TX: pg_advisory_xact_lock(owner), re-check key, sum usage vs quota (429)
    Service->>DB: save FileStorageObject (+ OutboxReplicationJob REPLICATE if replication on), commit
    Service->>Listener: publish StorageObjectConfirmedEvent (after commit, no TX)
    Service-->>Browser: 200 ConfirmUploadResponse
  end
  opt gallery upload
    Browser->>Browser: POST /api/marketplace/coaches/me/profile/gallery {key}
    Note over Browser: CoachGalleryService.addImage re-validates via findActiveObject
  end

    The app server never sees browser-uploaded bytes. confirmUpload() is the trust boundary: it checks size, content type and the presence of an ETag with a live HeadObject, and it stores the HEAD values, not the client's claims. Confirmation is idempotent and owner-scoped: if an FSO already exists for the key and belongs to the caller, it is returned and, if the first confirm was less than app.storage.upload-ttl-seconds ago, StorageObjectConfirmedEvent is published again. Because the event is published after the commit, a listener that throws makes the HTTP call fail even though the FSO is already persisted, and the client's retry is what re-drives the listener. Listeners must therefore be idempotent. Two concurrent confirms of the same key race on the unique key index (SQLState 23505), and the loser takes the idempotent path. Any other constraint violation is still an error.

    Downloading a file

    sequenceDiagram
  participant Caller as Browser
  participant Resource as StorageResource
  participant Service as FileStorageService
  participant DB as file_storage_objects / storage_access_events
  participant S3 as S3 (via S3Presigner)

  Caller->>Resource: GET /api/storage/sign/download/{key}
  Resource->>Service: signDownload(key)
  Service->>DB: findByKeyAndDeletedAtIsNull(key)
  alt not found or soft-deleted
    Service-->>Caller: 404 StorageObjectNotFoundException
  else caller is neither owner nor admin
    Service-->>Caller: 404 StorageObjectNotFoundException
  else found
    Service->>DB: save StorageAccessEvent(key, ownerId, sizeBytes)
    Service->>S3: presign GET (presign-ttl-seconds)
    Service-->>Caller: 200 {key, downloadUrl, expiresAt}
    Caller->>S3: GET downloadUrl (direct)
  end

    Downloads never proxy bytes through the application. A soft-deleted object is treated as not found, so deletion takes effect at once for REST downloads even though the bytes remain during the retention window. The frontend does not call this endpoint at all today. Coach photos, gallery images, report PDFs and GDPR exports are signed server-side with signedDownloadUrl and embedded in DTOs, which neither checks deleted_at nor writes an access event.

    Soft delete, retention, replication and raw-blob deletion

    sequenceDiagram
  participant Caller as Caller
  participant Service as FileStorageService
  participant DelSched as DeletionSchedulerService
  participant Outbox as OutboxPollerScheduler (replication only)
  participant Primary as Primary StorageService
  participant Backup as Backup StorageService
  participant Gdpr as GdprErasureService
  participant GenOutbox as platform.outbox (BLOB_DELETION)

  Caller->>Service: DELETE /api/storage/{key} (or CoachGalleryService/CoachProfileService.softDelete)
  Service->>Service: createdBy == current login? softDeleteByKey
  Service-->>Caller: 204 (deleted_at set)

  loop every app.storage.poller.fixed-delay-ms (ShedLock)
    DelSched->>DelSched: findEligibleForPhysicalDeletion(deleted_at older than retentionDays, 10)
    DelSched->>Primary: delete(key)
    DelSched->>DelSched: TX: markPhysicallyDeleted == 1 and replication on then save OutboxReplicationJob(DELETE)
  end

  loop every app.storage.poller.fixed-delay-ms (ShedLock)
    Outbox->>Outbox: pollPending FOR UPDATE SKIP LOCKED, mark PROCESSING
    alt REPLICATE
      Outbox->>Primary: get(key)
      Outbox->>Backup: put(key, stream)
    else DELETE
      Outbox->>Backup: delete(key)
    end
    Outbox->>Outbox: COMPLETED, or retry, then FAILED after max-attempts
  end

  Gdpr->>GenOutbox: enqueue(keys) + requestDrainAfterCommit (inside erasure TX)
  GenOutbox->>Service: BlobDeletionOutboxHandler, deleteRawBytes(key) (idempotent)

    FSO-tracked deletion has two stages: the user-facing DELETE only sets a flag, and the scheduler does the irreversible S3 delete later, then (only with replication on) queues a backup DELETE through the same replication outbox. DeletionSchedulerService's SKIP LOCKED claim commits before the loop runs, so ShedLock plus the conditional markPhysicallyDeleted (affected-row count checked before the outbox save) is what stops two ticks from double-enqueueing. Raw keys written by storeBytes are never soft-deleted. They are removed immediately (deleteRawBytes) or through the re-drivable BLOB_DELETION outbox.

    Conventions & Gotchas

    S-18, images are withheld until Project Arachnid has judged them. confirmUpload stores an image as scan_status = PENDING when ARACHNID_ENABLED is on (MediaScanPolicy); anything else is NOT_REQUIRED. MediaScanService (async, on StorageObjectConfirmedEvent, plus MediaScanRetryScheduler for retries) scans a short-lived URL and writes CLEAN, or on a hash match FLAGGED (bytes kept, not purged), QUARANTINED for the uploader's other objects, an urgent admin alert, and a safety suspension (UserSuspensionRequestedEvent). Scanner down, timeout or any exception is no verdict: the object stays PENDING and is retried; an admin is alerted after infrastructure.arachnid.alert-after-attempts tries. signedDownloadUrl (every cross-user read) returns null and downloadBytes throws for anything but CLEAN/NOT_REQUIRED; the owner's signDownload still serves PENDING so they see their own upload. Prod/uat refuse to boot with scanning off unless ALLOW_UNSCANNED_MEDIA=true (DeployedMediaScanningValidator, gauge skillars_media_scanning_unsafe). There is no admin release tool yet for a false-positive quarantine.

    The confirm-time quota check is a per-owner critical section. Two parallel confirms by one owner used to each read the owner's usage before either inserted, so both passed and together overshot the quota (C5). confirmUpload now runs FileStorageObjectRepository.acquireOwnerQuotaLock (pg_advisory_xact_lock(namespace, hashtext(owner))) as the first statement of its insert transaction, then re-reads findByKey (a parallel confirm of the same key is the idempotent retry, not a second charge), then sumSizeBytesByOwnerId, then inserts. An advisory lock because there is no per-owner quota row to lock; it is released at commit and held only for the insert (the S3 HeadObject runs before it). Any new path that inserts quota-counted FSO rows must take the same lock before reading the usage.

    Never call infrastructure.blobstore storage beans from another platform module. Always go through filestorage. Other modules must use the /api/storage/** endpoints (browser uploads) or FileStorageService's methods, plus BlobDeletionOutboxSupport for deletes that must survive a crash. This rule holds today. Outside this module, the only infrastructure.blobstore imports are exception and error-code types: StorageObjectNotFoundException in CoachProfileService and CoachGalleryService, and BlobstoreErrorCode/exceptions in ApiAdvice.

    There are two kinds of object, with different guarantees. Browser uploads get an FSO row, so quota, replication, the soft-delete and retention lifecycle, findActiveObject and REST download auditing all apply. Server-generated files written by storeBytes (report PDFs under reports/, GDPR ZIPs under gdpr/exports/) get none of that: they are invisible to quota, never replicated, cannot be claimed through confirm, and assertOwnership fails for them (it requires a non-deleted FSO owned by the caller; before B3 it passed for any key with no FSO row, which let a coach point a branding logoKey at a report PDF or GDPR ZIP). ReportGenerationService.saveBranding skips the check only when the submitted logoKey is the coach's stored key and a browser-upload key, so a colour-only save still works after the logo object was soft-deleted. Access to raw keys is decided entirely by the module that wrote them.

    Replication jobs are only written while replication is on. confirmUpload() and DeletionSchedulerService check app.storage.replication.enabled before inserting into main.outbox_replication_jobs, because OutboxPollerScheduler (the only consumer) exists only when it is true, and no profile sets it. Before B3 both always inserted, so environments that ran older builds hold PENDING rows that nothing drains. No migration deletes them, since an operator may have enabled replication through the environment. If you turn replication on, objects uploaded while it was off are not backfilled to the backup (use StorageMigrationService), and the poller will first work through any old backlog. To drop that backlog in an environment where replication has never been enabled: DELETE FROM main.outbox_replication_jobs WHERE status = 'PENDING'.

    The quota is soft. signUpload() sums size_bytes of the owner's non-deleted FSOs (deleted_at IS NULL), so a soft delete frees quota immediately even though the bytes stay in the bucket for the retention window. The quota and max size are checked at sign time against the declared size and again at confirm time against the real size. Since C5 the confirm-time check runs under the owner's advisory lock (see the first gotcha), so parallel confirms can no longer overshoot it; the sign-time check is still advisory only. Server-written storeBytes objects never count, and there is one global limit (platform.filestorage.quota.default-bytes), not a per-tier one.

    Entity-level ownership checks are opt-in; record ownership is not. "entityId must equal the caller" is enforced at sign and at confirm only for FileStorageService.OWNER_BOUND_ENTITIES (coach_profile, coach_branding, coach_gallery). If you add an owner-sensitive entity, add it there. Independently of the entity, a repeat confirm and sign/download are limited to the FSO's owner (plus admins for download). If another user needs to read a file, sign it server-side with signedDownloadUrl after your own access check rather than widening sign/download. Domain modules that link keys must still check them server-side (prefix + findActiveObject owner), as CoachGalleryService.addImage does.

    The event fires after commit, and every repeat confirm fires it again. Because StorageObjectConfirmedEvent is published after the FSO transaction, a failure in CoachProfilePhotoEventListener returns an error to the browser while the FSO is already saved. The client's retry takes the idempotent path, which re-publishes the event, so the photo link is re-driven. This means listeners must be idempotent. The re-publish only happens within app.storage.upload-ttl-seconds of the first confirm, so a late replay of an older photo key does not revert the profile photo. The link is still not durable without a retry (no outbox). New features should link uploads with an explicit, idempotent domain call (the gallery pattern) rather than a new listener on this event.

    The sign/confirm/download flow bypasses the StorageService abstraction on purpose. Presigned URLs need S3Presigner, which the generic interface does not expose, and the raw helpers also call S3Client directly. Only ReplicatedStorageService, OutboxPollerScheduler, DeletionSchedulerService and StorageMigrationService use the portable interface. The presigning path is S3-only, which includes SeaweedFS in dev, UAT and production.

    Video bytes do not go through this module. The video module has no import of filestorage or infrastructure.blobstore. Video goes through its own Bunny Stream pipeline, which is also why the coach gallery accepts images only.
