    Scheduled Jobs

    Every recurring background job in the application, what it recovers or cleans up, and the multi-instance safety rules you must follow when adding another one.

    Why This Page Exists

    A large amount of Skillars' correctness does not happen in a request thread. Bookings that nobody actions expire on a timer; a booking stranded mid-payment is swept back out; a coach who abandons the wrap-up wizard has the session force-completed; a message or review whose moderation verdict never landed is escalated to a human; packs forfeit at expiry; outboxes drain; failed GDPR erasures are retried; local subscriptions are reconciled against Stripe. There are 41 @Scheduled methods in 40 classes across 12 platform modules plus infrastructure, and 32 of them are ShedLock-guarded. Several are the only thing standing between a crashed transaction and a permanently stuck row, so knowing they exist is a prerequisite for debugging "why is this record stuck".

    Re-inventory with grep -rn '@Scheduled(' src/main/java --include='*.java' and grep -rn '@SchedulerLock(' src/main/java --include='*.java' — the table below was rebuilt from exactly that on the current master.

    ConcernWhereNotes
    Enabling @Scheduledinfrastructure.config.SchedulingConfig@EnableScheduling behind @ConditionalOnProperty("app.scheduling.enabled", matchIfMissing = true). On everywhere except the test profile.
    Enabling ShedLockplatform.notification.config.AsyncConfig@EnableSchedulerLock(defaultLockAtMostFor = "PT10M", order = LOWEST_PRECEDENCE - 100). Deliberately not conditional — see below.

    Lock tuning runbookdocs/deployment/scheduler-lock-tuning.mdWhich lockAtLeastFor/lockAtMostFor values are property-driven and how to retune them alongside the job's delay.

    Scheduling is off under the test profile; ShedLock is not. src/test/resources/application-test.yaml sets app.scheduling.enabled: false and is the only place that does. This became necessary when the integration suite consolidated onto a few long-lived Spring contexts: a job with a 5-minute delay never fires in a context that lives 90 seconds, and that accidental protection disappeared. Worse, the per-test reset backdates every ShedLock row, making every guarded job eligible on every test method.

    Overriding each job's delay in test config cannot substitute for the switch: 23 of the 41 @Scheduled methods hard-code their delay or cron with no property placeholder. Meanwhile @EnableSchedulerLock stays unconditional because tests invoke scheduled methods directly through the Spring proxy, so the lock advisor must still apply — that is the behaviour AbstractIntegrationTest.releaseSchedulerLock(String) is written against. (The same file also sets app.outbox.drain-async: false so the outbox's AFTER_COMMIT drain runs on the calling thread in tests.)

    Why the ShedLock advisor is explicitly ordered. ShedLock's default InterceptMode.PROXY_METHOD puts a real AOP advisor on the same proxy chain as @Transactional, and both default to Ordered.LOWEST_PRECEDENCE — so without an explicit order their relative nesting is unspecified. Setting a higher-precedence order forces the lock advisor outermost, guaranteeing the transaction runs to completion (commit or rollback) before the lock is released. Otherwise a lock could be freed while its DB transaction was still open, and a second instance could start work against uncommitted state.

    Conventions & Gotchas

    9 of the 41 jobs are unguarded, and each has a reason. Five are per-instance by design (ConfigService, AlertRuleCache, AlertEvaluationService, MessagingEmitterRegistry, RateLimitingService) — they touch only in-memory state or this instance's metrics/connections. The other four (UploadSessionExpiryScheduler, ReconciliationWorkerScheduler.reconcile, WebhookEventProcessorScheduler, ModerationSlaMonitorService) rely on row-level FOR UPDATE [SKIP LOCKED] claims instead of ShedLock, which is a valid alternative. Every job that writes shared state without a row claim — including all the daily billing crons — is now 🔒. Keep it that way.

    Set lockAtMostFor to roughly 2× the delay, not equal to it. The convention (see PaymentPendingSweeper and the comment in MessageModerationSweeper) is that a run which merely reaches its own next tick must not have its lock expire mid-execution, which would let a second instance start an overlapping sweep. So a 15-minute delay pairs with PT30M, a 10-minute delay with PT20M, the 5-minute booking sweepers with PT15M. lockAtLeastFor is typically PT2M to stop a very fast run from being immediately re-eligible on another instance; for short-delay drainers it is property-driven (e.g. app.outbox.lock-at-least, app.storage.poller.lock-at-least) so an operator lowering the delay can lower the floor with it.

    lockAtMostFor must be strictly shorter than the stale-claim window (10 min lock vs 15 min window in RadarCompositeDlqProcessor, 15 vs 20 in VideoDeletionOutboxProcessor). For claim-based drainers (VideoDeletionOutboxProcessor, RadarCompositeDlqProcessor), if the lock could expire before a claim counts as stale, the next instance would reset and re-claim rows the still-running instance is processing. Both classes also bound a run's wall-clock time below the lock (e.g. 8 min under PT10M) and hand unprocessed rows straight back to PENDING. Read their Javadoc before changing either number.

    Batch per row, in its own transaction, when the batch is user-visible. SessionPackForfeitureScheduler, SessionPackExpiryNotifier, QuickCompleteTimeoutService and StuckCompletionSweeperService wrap each item in its own transactionTemplate.execute and catch per item, so one bad row cannot abort the whole run. Retention jobs do the same per batch so no single transaction holds a long lock. Follow that shape for anything that emails users or raises alerts.

    Publish events inside the transaction template, not outside it. A listener registered at AFTER_COMMIT never fires if publishEvent is called outside any transaction — this was a real bug in SessionPackExpiryNotifier, whose fix was to move the publish inside transactionTemplate.execute. Stamping a "notified at" column inside that same transaction is what makes a delivered notification always a recorded one.

    Daily crons are deliberately staggered. 01:00 unactivated users · 02:00 subscription changes + message retention · 03:00 grace periods + video lifecycle · 03:30 in-app & SLU-marker retention · 04:00 tier reconciliation · 05:00 Stripe reconciliation · 06:00 GDPR erasure retry (and Monday neglected-skill detection) · 08:00 pack expiry warnings. The payment crons are ordered so a coach touched by 02:00/03:00 is not redundantly reconciled at 04:00. Check this list before picking a slot.

    A skipped run is observable. When another instance holds the lock, the wrapped provider logs that the lock is held and skips, and increments scheduler.lock.skipped{lock_name=...}. If a job "isn't running", check that counter before assuming it never fired — a stale lock row in main.shedlock looks identical to a dead scheduler from the outside.

    Adding a New Job

    1. Put the @Scheduled method on a @Component, not on a service that also serves request threads — it keeps the job's transaction boundaries independent. The newer jobs use a thin scheduler class that delegates to a service method (e.g. GdprErasureRetryScheduler → GdprErasureService.retryFailedErasures) so tests can call the service directly.
    2. Prefer fixedDelayString/cron bound to a property so the value is tunable without a rebuild. (22 existing jobs don't do this; don't add a 23rd.)
    3. Add @SchedulerLock with a unique name (convention: ClassName_method) and a lockAtMostFor of ~2× the delay, unless the job only touches per-instance state or claims rows with SKIP LOCKED.
    4. Bound the batch size if the backlog can grow without limit, and drain the remainder on the next tick.
    5. Wrap per-item work in its own transaction if a single failure shouldn't abort the run. Never hold a DB transaction across an external HTTP call (Stripe, Bunny, Gemini).
    6. Remember the job will not fire in integration tests — call the method directly through the proxy and use AbstractIntegrationTest.releaseSchedulerLock(name) between invocations.
