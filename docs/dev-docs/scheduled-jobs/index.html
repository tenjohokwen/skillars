Scheduled Jobs

Every recurring background job in the application, what it recovers or cleans up, and the multi-instance safety rules you must follow when adding another one.

Why This Page Exists

A large amount of Skillars' correctness does not happen in a request thread. Bookings that nobody actions expire on a timer; a booking stranded mid-payment is swept back out; a message whose moderation verdict never landed is escalated to a human; packs forfeit at expiry; outboxes drain; caches refresh. There are 30 @Scheduled methods across 9 modules, and until now the only way to find them was to grep. Several of them are also the only thing standing between a crashed transaction and a permanently stuck row, so knowing they exist is a prerequisite for debugging "why is this record stuck".

How Scheduling Is Wired

ConcernWhereNotes
Enabling @Scheduledinfrastructure.config.SchedulingConfig@EnableScheduling behind @ConditionalOnProperty("app.scheduling.enabled", matchIfMissing = true). On everywhere except the test profile.
Enabling ShedLockplatform.notification.config.AsyncConfig@EnableSchedulerLock(defaultLockAtMostFor = "PT10M", order = LOWEST_PRECEDENCE - 100). Deliberately not conditional — see below.
Lock storageinfrastructure.config.ShedLockConfigJDBC lock provider over the main.shedlock table, usingDbTime() so lock expiry uses DB clock rather than per-instance wall clock.
Skipped-run visibilityShedLockConfig.lockProviderWraps the provider to log and increment a scheduler.lock.skipped counter (tagged by lock name) whenever lock() returns empty.

Scheduling is off under the test profile; ShedLock is not. src/test/resources/application-test.yaml sets app.scheduling.enabled=false and is the only place that does. This became necessary when the integration suite consolidated from 37 short-lived Spring contexts onto a few long-lived ones: a job with a 5-minute delay never fires in a context that lives 90 seconds, and that accidental protection disappeared. Worse, the per-test reset backdates every ShedLock row, making every guarded job eligible on every one of ~905 test methods.

Overriding each job's delay in test config cannot substitute for the switch: 16 of the 30 @Scheduled methods hard-code their delay or cron with no property placeholder. Meanwhile @EnableSchedulerLock stays unconditional because tests invoke scheduled methods directly through the Spring proxy, so the lock advisor must still apply — that is the behaviour BasePaymentIT.releaseSchedulerLock is written against.

Why the ShedLock advisor is explicitly ordered. ShedLock's default InterceptMode.PROXY_METHOD puts a real AOP advisor on the same proxy chain as @Transactional, and both default to Ordered.LOWEST_PRECEDENCE — so without an explicit order their relative nesting is unspecified. Setting a higher-precedence order forces the lock advisor outermost, guaranteeing the transaction runs to completion (commit or rollback) before the lock is released. Otherwise a lock could be freed while its DB transaction was still open, and a second instance could start work against uncommitted state.

Conventions & Gotchas

Only 9 of the 30 jobs are ShedLock-guarded. Every job without 🔒 above will run concurrently on every application instance. For the cache-refresh and heartbeat jobs that is harmless by design. For anything that writes shared state it is not — so if you deploy more than one instance, audit the unguarded jobs in the "Outbox / queue drainers" and "Lifecycle & billing" tables before assuming they're safe. Several drainers rely on their own atomic claim-a-batch UPDATE rather than ShedLock, which is a valid alternative; the daily billing crons largely do not.

Set lockAtMostFor to roughly 2× the delay, not equal to it. The convention in this codebase (see PaymentPendingSweeper and the comment in MessageModerationSweeper) is that a run which merely reaches its own next tick must not have its lock expire mid-execution, which would let a second instance start an overlapping sweep. So a 15-minute delay pairs with PT30M, a 10-minute delay with PT20M. lockAtLeastFor is typically PT2M to stop a very fast run from being immediately re-eligible on another instance.

Batch per row, in its own transaction, when the batch is user-visible. SessionPackForfeitureScheduler and SessionPackExpiryNotifier both wrap each item in its own transactionTemplate.execute and catch per item, specifically so one bad row (e.g. a purchase pointing at a missing coach) cannot abort the whole run. Follow that shape for anything that emails users or raises alerts.

Publish events inside the transaction template, not outside it. A listener registered at AFTER_COMMIT never fires if publishEvent is called outside any transaction — this was a real bug in SessionPackExpiryNotifier, whose fix was to move the publish inside transactionTemplate.execute as SessionPackForfeitureScheduler already did. Stamping a "notified at" column inside that same transaction is what makes a delivered notification always a recorded one.

A skipped run is observable. When another instance holds the lock, the wrapped provider logs "Scheduler lock '{name}' is held by another instance — skipping this run" and increments scheduler.lock.skipped{lock_name=...}. If a job "isn't running", check that counter before assuming it never fired — a stale lock row in main.shedlock looks identical to a dead scheduler from the outside.

Adding a New Job

  1. Put the @Scheduled method on a @Component, not on a service that also serves request threads — it keeps the job's transaction boundaries independent.
  2. Prefer fixedDelayString/cron bound to a property so the value is tunable without a rebuild. (16 existing jobs don't do this; don't add a 17th.)
  3. Add @SchedulerLock with a unique name and a lockAtMostFor of ~2× the delay unless the job is provably idempotent across instances.
  4. Bound the batch size if the backlog can grow without limit, and drain the remainder on the next tick.
  5. Wrap per-item work in its own transaction if a single failure shouldn't abort the run.
  6. Remember the job will not fire in integration tests — call the method directly through the proxy, as the existing suite does.
