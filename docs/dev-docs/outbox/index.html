    Outbox

    The generic transactional outbox: a single main.outbox_messages table that lets any module commit "do this side effect later" atomically with its business change, then drains it off the request path with per-row transactions, exponential backoff, and no row ever dropped.

    Business Overview

    Many Skillars operations promise a side effect that can't run inside the database transaction: a Stripe refund or coach payout transfer, a transactional email, an S3 object deletion after GDPR erasure, an operator alert. If the side effect runs after commit and the JVM dies (or the remote service is down), the promise is silently lost; if it runs before commit and the transaction rolls back, it happened for nothing. The outbox solves this the standard way: the producer writes an intent row in the same transaction as the business change, and a drainer executes the intent after commit, retrying until it succeeds.

    platform.outbox (introduced by skillars-deferred-91, extracted from deferred-90's bespoke blob-deletion queue) is deliberately domain-agnostic: it knows nothing about refunds or emails. Each domain registers an OutboxMessageHandler for its own aggregate_type. There is no REST API and no UI — it's pure infrastructure. Business guarantee it gives: once a business transaction has committed, its outbox operations will eventually run at least once; rows that keep failing are retried forever and reported as [OUTBOX_STUCK] for a human.

    Table: main.outbox_messages

    Defined in V138__baseline_schema.sql (the deferred-112 rebaseline that folded in the original deferred-91 migration and the later next_attempt_at column, originally V126). Mapped by OutboxMessage.

    ColumnTypeMeaning
    idbigint identity, PKAlso the FIFO tie-breaker in the claim order.
    aggregate_typetext NOT NULLDiscriminator selecting the handler (no CHECK — new types need no migration).
    payloadjsonb NOT NULLHandler-defined JSON written at enqueue time.
    attemptsinteger default 0Failed handle attempts so far.
    last_errortextString.valueOf(cause), truncated to 1000 chars.
    created_attimestamptz default now()Enqueue time.
    next_attempt_attimestamptz default now()Earliest claim time: now for fresh rows, a future notBefore for delayed rows, or now + backoff after a failure.

    Index idx_outbox_claim (next_attempt_at, attempts, id) serves the claim query. Successfully handled rows are deleted; the table only ever holds pending or failing work, so a non-empty table at rest means something is backing off.

    Key classes

    ClassWhat it does
    OutboxServiceenqueue(type, payload) / enqueue(type, payload, notBefore) — plain save, must run inside the producer's transaction. requestDrainAfterCommit() publishes OutboxDrainRequestedEvent, de-duplicated per transaction via a TransactionSynchronizationManager resource key so N enqueues in one transaction trigger one drain. onOutboxDrainRequested is @Async("outboxDrainPool") + @TransactionalEventListener(AFTER_COMMIT). sweep() is the scheduled safety net. drain() loops chunks (max 200) and never lets an exception escape (an afterCommit throw would turn an already-committed request into a 500).
    OutboxChunkProcessorNot transactional. Calls OutboxRowProcessor.claimAndHandle() up to CHUNK_SIZE = 25 times; on OutboxRowFailure calls recordFailure. Exists as a separate bean so the REQUIRES_NEW on the row processor goes through the Spring proxy.
    OutboxRowProcessorclaimAndHandle() (REQUIRES_NEW): claims one due row with FOR UPDATE SKIP LOCKED, dispatches to the handler map (built from all OutboxMessageHandler beans at startup; duplicate aggregateType fails startup via Collectors.toMap), deletes the row on success, or throws OutboxRowFailure so the whole transaction — including any DB writes the handler made — rolls back. recordFailure() (REQUIRES_NEW, a clean second transaction): attempts++, last_error, next_attempt_at = now + backoff.
    OutboxMessageRepositoryclaimNextDue(now, pageable): WHERE nextAttemptAt <= :now ORDER BY attempts ASC, id ASC with PESSIMISTIC_WRITE + lock timeout -2 (Hibernate's SKIP LOCKED). countByAttemptsGreaterThanEqual for the stuck alarm.
    OutboxConfigoutboxDrainPool: core 1, max 2, queue 50, DiscardPolicy (a rejected drain is harmless — the sweep picks the rows up; CallerRunsPolicy would put draining back on the request thread), MDC decorator, graceful shutdown of ExecutorShutdown.OUTBOX_DRAIN_SECONDS (10 s). With app.outbox.drain-async=false (test profile only) it is a SyncTaskExecutor.

    Retry, backoff and locking

    • Backoff (OutboxRowProcessor.backoffFor): 30 s after the first failure, doubling per attempt (30 s, 1 m, 2 m, 4 m, …) capped at 1 h. Deterministic, no jitter — SKIP LOCKED already spreads pods.
    • No retry limit, no dead-letter. A row is retried forever. At attempts >= 10 (STUCK_ATTEMPTS_THRESHOLD) every sweep logs [OUTBOX_STUCK] at ERROR with the count. Handlers convert permanently-impossible work into a logged no-op instead of throwing, to avoid immortal poison rows.
    • Concurrency is guaranteed by the row lock, not by ShedLock: the async post-commit drains (on any pod) and the sweep can all run at once, and SKIP LOCKED makes each skip rows another claimer holds.
    • Sweep: @Scheduled(fixedDelayString = "${app.outbox.sweep-ms:300000}") (5 min) with @SchedulerLock(name = "OutboxService_sweep", lockAtMostFor = "PT10M", lockAtLeastFor = "${app.outbox.lock-at-least:PT1M}"). The lock only stops pods sweeping in lockstep; correctness doesn't depend on it (see docs/deployment/scheduler-lock-tuning.md). Disabled under the test profile via app.scheduling.enabled=false.
    • Drain stop conditions: a chunk claimed nothing, a chunk processed zero rows (all failures — they now have a future next_attempt_at), or 200 chunks.

    Key Flows

    Enqueue in the business transaction → post-commit drain

    sequenceDiagram
  participant Biz as Business service (@Transactional)
  participant L as BEFORE_COMMIT listener
  participant S as *OutboxSupport (MANDATORY)
  participant O as OutboxService
  participant DB as main.outbox_messages
  participant Pool as outboxDrainPool
  participant C as OutboxChunkProcessor
  participant R as OutboxRowProcessor
  participant H as OutboxMessageHandler

  Biz->>L: domain event
  L->>S: enqueueX(...)
  S->>O: enqueue(type, json)
  O->>DB: INSERT (same transaction)
  S->>O: requestDrainAfterCommit()
  O-->>O: publish OutboxDrainRequestedEvent (once per tx)
  Note over Biz,DB: COMMIT: business rows + outbox row together
  O->>Pool: onOutboxDrainRequested [AFTER_COMMIT, @Async]
  loop up to 200 chunks of 25
    C->>R: claimAndHandle() [REQUIRES_NEW]
    R->>DB: SELECT ... next_attempt_at <= now ORDER BY attempts, id LIMIT 1 FOR UPDATE SKIP LOCKED
    R->>H: handle(payload)
    alt success
      R->>DB: DELETE row, COMMIT
    else throws
      R-->>C: OutboxRowFailure (tx rolled back)
      C->>R: recordFailure(id, cause) [REQUIRES_NEW]
      R->>DB: attempts++, last_error, next_attempt_at = now + backoff
    end
  end

    If the JVM dies between commit and drain, or the pool discards the drain task, nothing is lost: the 5-minute sweep() runs the same drain(). If the business transaction rolls back, the outbox row never existed and the AFTER_COMMIT listener never fires.

    Why two transactions per row

    The handler runs inside the claim transaction, so a handler's own @Transactional (REQUIRED) collaborators — CreditWalletService.writeLedgerEntry, SnapshotBatchWriter.writeAllDeltas, the payout status updates — join it and commit atomically with the row's deletion. But on PostgreSQL a failed statement aborts the whole transaction, so failure bookkeeping can't be written there: it goes in a second, clean REQUIRES_NEW after the first has rolled back. The original deferred-91 design dispatched a chunk of 25 in one transaction; one constraint violation rolled back all 25 and the attempts counter never moved.

    Conventions & Gotchas

    Enqueue inside the business transaction, from a BEFORE_COMMIT listener or the service itself — never AFTER_COMMIT. Make your *OutboxSupport method @Transactional(propagation = MANDATORY) so a caller without a transaction fails loudly instead of opening its own (the non-atomic window deferred-92 closed). The one exception is a producer with genuinely no ambient transaction (SluSnapshotOutboxSupport, REQUIRES_NEW). Remember a MANDATORY method that throws marks the shared transaction rollback-only even if the listener catches — an enqueue failure always fails the business operation, which is the point.

    handle() must be idempotent. Delivery is at-least-once: a handler that succeeded remotely but whose delete then failed (or whose pod died before commit) is re-driven. Anchor on a DB state check and/or a remote idempotency key. And throw only for failures a retry could fix — a permanently impossible row that throws is an immortal poison row that trips [OUTBOX_STUCK] forever.

    The claim transaction (row lock + a pooled connection) is held for the whole handler call, including its network I/O (Stripe, SES/SMTP, S3). Keep handlers short. NotificationEmailOutboxHandler additionally opens MailManager.sendEmailSync's own REQUIRES_NEW, so an email drain uses two connections at once. The pool is 1–2 threads, so this is bounded, but don't raise it casually.

    Always call requestDrainAfterCommit() after enqueuing — otherwise the row waits up to 5 minutes for the sweep. Rows enqueued with a future notBefore (coach payouts) are not due when the post-commit drain fires, so they are always executed by a later sweep, up to app.outbox.sweep-ms after release_after. Calling requestDrainAfterCommit() with no transaction active publishes an event the AFTER_COMMIT listener ignores (no fallbackExecution) — again, only the sweep will pick the row up.

    Unknown aggregate_type is retried, not dropped. During a rolling deploy an old pod can claim a row whose handler only exists in the new build; it fails with "no OutboxMessageHandler registered", backs off, and is processed once a new pod claims it. Removing a handler while rows of its type remain leaves them stuck forever — drain or migrate them first. Payload JSON is a cross-version contract for the same reason: add fields as nullable (see NotificationEmailPayload.deadline/firstname).

    No ordering guarantee. Claim order is attempts ASC, id ASC across all types, with several concurrent claimers; a failing row sinks below fresh work. Don't build a handler that assumes it sees rows of one aggregate in enqueue order.

    Tests: application-test.yaml sets app.outbox.drain-async: false (drain runs synchronously on the committing thread, so ITs can assert right after the call) and app.scheduling.enabled: false (no sweep — call OutboxService.drain() directly). The async hand-off itself is covered only by OutboxServiceAsyncWiringTest. Module ITs: ModerationOutboxIT, NotificationEmailOutboxAtomicityIT, RefundOutboxIT, SluSnapshotOutboxIT under src/test/java/.../platform/outbox/.

    Not every "outbox" in the codebase is this one. These are separate, module-private queues with their own tables and pollers: main.outbox_replication_jobs (filestorage.OutboxPollerScheduler, cross-region replication), main.video_deletion_outbox (video.VideoDeletionOutboxProcessor), main.video_webhook_events (video.WebhookEventOutboxService, webhook dedupe), and main.envelope_entity (notification.EmailRetryScheduler, email retry). The old bespoke PendingBlobDeletion queue no longer exists — it moved onto this outbox as BLOB_DELETION (deferred-100). Likewise app.email.log.dump-dir was renamed from outbox-dir to avoid the name clash.

    Operating it. Search logs for [OUTBOX_STUCK], [OUTBOX_RETRY], [OUTBOX_DRAIN_FAILED] and [OUTBOX_DRAIN]. A stuck row is inspected with SELECT id, aggregate_type, attempts, last_error, next_attempt_at FROM main.outbox_messages ORDER BY attempts DESC; setting next_attempt_at = now() forces it into the next drain. Deleting a row abandons a committed promise (a refund, an email) — only do it after doing the work by hand.
