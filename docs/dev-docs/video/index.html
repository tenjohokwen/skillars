Video

Owns the full lifecycle of an uploaded video — upload, quota enforcement, three-layer content moderation, minor-safety parental approval, transcoding, playback authorization, and eventual archival/deletion — behind a Bunny.net provider adapter.

Business Overview

Skillars videos are the raw material behind drill review and skill assessment: a Coach uploads a DRILL_DEMO or COACH_REVIEW clip, and a Player (frequently a minor) uploads HOMEWORK footage responding to an assigned drill. Because a large share of players are minors, this module is one of the most compliance-sensitive parts of the platform: every uploaded video passes through a three-layer moderation pipeline — CSAM matching (Arachnid), explicit-content detection (VideoIntel), and a minor-safety gate that routes any minor's video to their linked Parent for explicit approval before it is ever transcoded or made playable. Admins get a separate surface to lock, archive, delete, or reconcile videos when the pipeline or the Bunny.net provider gets out of sync.

Key business rules baked into the code:

  • Coaches may only upload DRILL_DEMO or COACH_REVIEW videos; players may only upload HOMEWORK — enforced in VideoResource, not just client-side.
  • Minor players are always allowed to initiate an upload (no 403 at upload time); the minor-safety gate in ModerationOrchestrationService is what defers visibility until a parent approves, per Story 6.6.
  • Each video type has its own size/duration ceiling (e.g. COACH_REVIEW ≤ 1 GB) enforced by VideoTypeConstraints, and storage is metered per owner via a byte-quota tied to subscription tier.
  • Storage quota is tier-gated — a "Scout" tier with a zero storage quota is rejected outright (QuotaService.check()).
  • COACH_REVIEW videos never expose a download URL (only a signed streaming URL) — download is only offered for owner-downloadable types like HOMEWORK/DRILL_DEMO.
  • A CSAM match (Arachnid) immediately locks the video, alerts admins, and triggers account suspension — the most severe path in the module.
  • Subscription expiry cascades into video access: a player's READY videos get BLOCKED when their subscription lapses (unless another active subscription covers them), then ARCHIVED after 30 days, then physically purged after 90 — with a special "yearly exemption" that pauses the archival clock for YEARLY-tier subscribers.

Dependencies on infrastructure and other modules

infrastructure.video supplies the VideoProviderAdapter SPI (implemented by BunnyVideoProviderAdapter) covering upload credential issuance, playback/download URL signing, asset status, transcoding triggers, and webhook signature verification — this module never talks to Bunny.net directly. infrastructure.videointel supplies VideoIntelClient, used only by ModerationOrchestrationService for Layer 2 explicit-content scanning. The module also depends on infrastructure.arachnid (CSAM matching, Layer 1) and infrastructure.feature (feature-flags gating whether each moderation layer runs). Cross-module platform dependencies: marketplace (coach/player profile lookups to resolve ownerId), security (age policy, parent-player links, account-deletion cascade, principal/session utilities), booking (recent-completed-booking check that grants a coach playback access to a player's video), session (drill-video ref-counting so shared drill assets aren't prematurely purged), payment (subscription-expiry event that drives lifecycle blocking), and config (dynamic runtime configuration values).

Key Flows

Upload → moderation → transcoding → playback

sequenceDiagram
  participant Coach as Coach/Player
  participant VR as VideoResource
  participant VS as VideoService
  participant QP as QuotaProvider
  participant Bunny as VideoProviderAdapter (Bunny)
  participant WH as WebhookEventProcessorScheduler
  participant MOD as ModerationOrchestrationService
  participant VAS as VideoApprovalService
  participant PS as PlaybackService

  Coach->>VR: POST /uploads/initiate
  VR->>VS: initializeUpload(request)
  VS->>QP: check(ownerId, bytes)
  VS->>QP: reserve(ownerId, bytes, videoType)
  VS->>Bunny: initializeUpload()
  VS-->>Coach: signed TUS upload URL + videoId (UPLOADING)
  Coach->>Bunny: TUS upload (direct)
  Bunny-->>WH: webhook video.upload.success
  WH->>WH: transition UPLOADING to PROCESSING
  WH->>MOD: publish VideoUploadedEvent (AFTER_COMMIT)
  MOD->>MOD: transition PROCESSING to SCANNING
  MOD->>MOD: Arachnid then VideoIntel then Minor Gate
  alt owner is a minor
    MOD->>VAS: createApprovalRequest (HIDDEN)
    Note over VAS: parent later calls approve/reject
    VAS->>Bunny: triggerTranscoding() after approval
  else adult or coach video
    MOD->>Bunny: triggerTranscoding()
  end
  Bunny-->>WH: webhook video.encoding.success
  WH->>VS: completeTranscoding()
  VS->>QP: commit(reservationHandle)
  VS->>VS: transition to READY
  Coach->>PS: GET /{id}/play
  PS->>PS: authorizePlayback (state + revocation checks)
  PS-->>Coach: signed playback URL + JWT

A single upload passes through four operational states before it is playable: UPLOADING → PROCESSING → SCANNING → TRANSCODING → READY. The quota reservation made at initiate-time is only committed (storage counted against the owner) once transcoding completes, and is released on any failure path. If the owner is a minor, the pipeline diverts to HIDDEN and creates a VideoApprovalRequest instead of calling Bunny immediately — the actual triggerTranscoding() call is deferred until a parent approves, and happens strictly after the DB transaction commits so the external HTTP call never holds a connection open. Webhook delivery is asynchronous and can arrive out of order (encoding.success before upload.success), which WebhookEventProcessorScheduler explicitly compensates for.

Quota check → reserve → commit/release

sequenceDiagram
  participant VS as VideoService
  participant QS as QuotaService (QuotaProvider)
  participant DB as video_quota_reservations

  VS->>QS: check(ownerId, requestedBytes)
  QS-->>VS: true/false (advisory only, no lock)
  VS->>QS: reserve(ownerId, bytes, videoType)
  QS->>DB: SELECT ... FOR UPDATE (serializes per owner)
  QS->>DB: INSERT reservation status=ACTIVE, expiresAt=now+TTL
  QS-->>VS: reservationHandle (UUID)
  alt upload + transcoding succeed
    VS->>QS: commit(reservationHandle)
    QS->>DB: UPDATE ACTIVE to COMMITTED + increment storage_used_bytes (atomic CTE)
  else upload/transcoding fails or session expires
    VS->>QS: release(reservationHandle)
    QS->>DB: UPDATE ACTIVE to RELEASED (storage NOT decremented)
  end
  Note over DB: QuotaReservationTimeoutService reaps ACTIVE rows past expiresAt

check() is advisory only — it holds no lock, so a concurrent reservation can drain quota between the check and a subsequent reserve() call; reserve() is the authoritative gate because it takes a SELECT ... FOR UPDATE row lock on the owner's quota row. commit() and release() are both single atomic SQL statements guarded by a WHERE status = 'ACTIVE' clause, which is what makes them idempotent under retries or races. Reservations that are neither committed nor released within their TTL (e.g. an abandoned upload) are cleaned up by QuotaReservationTimeoutService's ShedLock-guarded reaper — without this, quota would leak indefinitely.

Conventions & Gotchas

Visibility is stored here but not enforced here. The Visibility enum (PRIVATE/GROUP/UNLISTED) lives on the Video entity purely as data. Per contract/package-info.java, gating access based on Visibility is explicitly the consuming application's responsibility. Do not assume calling PlaybackService or VideoAccessGuard enforces Visibility — it doesn't. If a new caller needs Visibility-based access control, it must implement that check itself before reaching this module's playback/list APIs.

QuotaProvider implementations must be idempotent and TTL-bounded. Per the contract's package-info.java, all methods (especially commit and release) must be safe to call more than once for the same handle, reservations must carry a TTL, and a reaper must prune orphaned reservations. QuotaService satisfies this via status-transition guards (ACTIVE→COMMITTED/ACTIVE→RELEASED) and QuotaReservationTimeoutService. Any alternative QuotaProvider implementation (e.g. for a different billing model) that skips idempotency or the reaper will leak or double-count quota under retries.

No teamId on Video. This is deliberate per the contract package-info — the module has no concept of team ownership. Consuming applications own the linkage between teams and videos (e.g. via session's drill references). Don't add a teamId column here to "simplify" a query; join through the owning module instead.

VideoPurgedEvent ≠ physical deletion. It fires AFTER_COMMIT when a video is marked PURGED (logical delete), but the actual Bunny.net asset removal happens later, asynchronously, via VideoDeletionOutboxProcessor. Any consumer must not treat this event as confirmation that storage/CDN cost has actually been reclaimed, and must use @TransactionalEventListener(phase = AFTER_COMMIT), never a plain @EventListener, since the publishing transaction can still roll back.

Owner identity is polymorphic and format-sniffed. ownerId is a UUID string for coach-owned videos and a decimal Long string for player-owned videos — there is no discriminator column. Guards like VideoAccessGuard and ModerationOrchestrationService distinguish the two by attempting UUID.fromString() first, falling back to Long.parseLong(). When adding new owner-aware logic, follow this same probe order rather than assuming one format.
