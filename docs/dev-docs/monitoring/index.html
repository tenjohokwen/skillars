    Monitoring

    The operational logging/observability surface every module relies on to be debuggable in production. There is no platform.monitoring code package any more.

    Business Overview

    Skillars coaches, parents, and players book live, time-boxed activity: a session slot, a video review window, a payment that has to clear before a booking is confirmed. None of that tolerates silent failure. A payment provider call that fails without anyone noticing turns into a missed session or an unresolved charge with no paper trail. This page covers the operability setup that every module depends on when something goes wrong in production: structured logs, access logs, the actuator/metrics surface, and the LGTM stack. All of it is configured in infrastructure and resource files.

    Technical Overview

    TLS startup assertion (removed)

    The platform.monitoring package used to hold one class, TlsStartupAssertion, an ApplicationReadyEvent check that failed startup outside dev if client.momo.tcp-config.check-certificate was false. It was written for Orange Money / MTN MoMo clients that no longer exist (payments go through Stripe), nothing set that property, and the default was true, so it could never fail. It was removed together with the unused defaultTcpConfig: &DEFAULT_TCP YAML anchor and the dead infrastructure.client RestTemplate wrapper it was meant to guard. Nothing in src/main customizes TLS trust (no custom SSLContext, TrustManager or hostname verifier), so every outbound client uses its library's default certificate verification.

    If you add an outbound client with a "skip certificate check" option, add a startup guard that reads that client's real property. ConfigStartupAssertion in the Config module shows the pattern: listen for ApplicationReadyEvent (after full wiring, not @PostConstruct) and throw AppSetupException. An exception from that listener makes SpringApplication.run close the context and rethrow, so the JVM exits non-zero instead of serving traffic.

    Structured logging

    src/main/resources/config/logback-spring.xml configures a ConsoleAppender named JSON, using logstash-logback-encoder's LoggingEventCompositeJsonEncoder. Every log line is emitted as JSON with UTC timestamp, level, thread, logger name, message, MDC, arguments, key-value pairs (kv(...) from StructuredArguments), and stack trace, plus a fixed service/environment/version block taken from spring.application.name, app.environment and app.version.

    A second appender, LOKI, is defined conditionally (see the Loki callout below). It uses loki-logback-appender 2.x (Loki4jAppender, a nested <http><sender class="JavaHttpSender"/></http>, and newline-separated <labels> app/environment/level). The message body is the same JSON layout as the console appender.

    Access logs

    Tomcat access logs are routed through SLF4J by infrastructure.web.Slf4jAccessLogValve, not written to a file. This means they inherit both root appenders and can be queried in Loki like any other log line:

    LoggerServerWired by
    skillars.accessmain app (port 9990)AccessLogConfig
    skillars.access.managementactuator (port 8367, separate child context)ManagementAccessLogConfig (a @ManagementContextConfiguration registered in META-INF/spring/…ManagementContextConfiguration.imports; its port guard stops the copy that component scanning puts in the main context from logging every request twice)

    Both loggers are at INFO. Setting skillars.access to OFF silences both. The management log is mostly the 30-second container healthcheck plus Prometheus scrapes, so it is the bulk of access-log volume in a quiet environment.

    The LGTM stack

    Skillars documents a full LGTM (Loki, Grafana, Tempo, Prometheus) observability stack for the whole application: structured logs for exact error context, Prometheus metrics for rate/volume health signals, Tempo traces for causal request chains, and Grafana for dashboards and alerting. Its provisioning lives in deploy/lgtm/ (loki.yml, prometheus.yml, tempo.yml, alerts.yml, grafana-*.yml, dashboards/). Six dashboards ship in the Skillars folder (overview, business health, payments, performance, database, background work). The app adds two metric families for them: skillars.backlog.* (OperationalBacklogMetrics, work waiting in the database) and http.server.allocated (RequestAllocationMetricsFilter, heap allocated per route). Only rules in grafana-alerts.yml notify anyone. Grafana is pinned to an exact tag in docker-compose.yml (11.6.16, the last 11.x line); the pin comment lists what was checked before the last bump, so re-run that check on a live stack before changing it.     Key Flows

    A log line's path: application code logs through SLF4J, the JSON console appender always writes it, and the LOKI appender ships it to Loki only when loki.enabled is true. Access-log lines take the same path through Slf4jAccessLogValve. Prometheus scrapes /manage/prometheus on the management port, and traces go to Tempo over OTLP.

    Conventions & Gotchas

    Whether logs reach Loki depends on profile and environment. loki.enabled is ${LOKI_ENABLED:false} in application.yaml, and application-prod.yaml overrides it to true. docker-compose.yml runs the prod profile with LOKI_ENABLED=true, and docker-compose.local.yml (dev profile) inherits that, so logs do reach Loki under Docker Compose. docker-compose.uat-hostwinds.yml sets LOKI_ENABLED=false because there is no Loki container there. If you run the JAR standalone (mvn spring-boot:run, an IDE run config) without the prod profile, it falls back to false. Only the console JSON appender is then live, and every LogQL query in docs/lgtm-observability.md returns nothing until you set LOKI_ENABLED=true.

    Don't "simplify" the <if>/<root> layout in logback-spring.xml. The LOKI appender is defined inside <if> (a real Loki4jAppender, or logback's no-op NOPAppender when disabled). <root> sits outside it and references LOKI unconditionally. Two other layouts were tried and both broke. Nesting <if> inside <root> logs a warning. Putting <root> inside both branches leaves the context with no appenders, and Spring Boot then fails startup. Logback configuration errors are fatal here, and that includes 1.x-style loki4j syntax.

    Prometheus scrapes the management port, not 9990. /manage/prometheus is served on 8367 and is unauthenticated (PUBLIC_MGMT_ENDPOINTS). Keep port 8367 off the public ingress.
