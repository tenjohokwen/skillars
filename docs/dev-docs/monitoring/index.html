Monitoring

A single fail-fast startup guard plus the operational logging/observability surface every other module relies on to be debuggable in production.

Business Overview

Skillars coaches, parents, and players book live, time-boxed activity: a session slot, a video review window, a payment that has to clear before a booking is confirmed. None of that tolerates silent failure. A payment provider call that fails without anyone noticing turns into a missed session or an unresolved charge with no paper trail. The monitoring package itself is intentionally tiny (one class, TlsStartupAssertion). This page also covers the wider operability setup that every module depends on when something goes wrong in production: structured logs, access logs, the actuator/metrics surface, and the LGTM stack. Almost all of that is configured in infrastructure and resource files, not in this package.

Technical Overview

TlsStartupAssertion

TlsStartupAssertion (platform.monitoring) is a Spring ApplicationListener<ApplicationReadyEvent>. It hooks ApplicationReadyEvent rather than @PostConstruct because that event fires only after every bean is wired, which is the right moment for an "is this deployment configured correctly" check. ConfigStartupAssertion in the Config module uses the same pattern for required platform config keys.

On firing, the assertion does two things in order:

  • Dev-profile guard. If the active Spring profiles include dev, it logs a debug line and returns.
  • Certificate-check assertion. Otherwise it reads client.momo.tcp-config.check-certificate, defaulting to true when the property is absent. If that resolves to false it throws AppSetupException; if not, it logs TLS assertion passed at INFO.

The property it checks is not set anywhere, so today the assertion always passes. The class was written for Orange Money / MTN MoMo mobile-money clients that no longer exist in the codebase. Payments go through Stripe (app.payment.stripe.*). No YAML file sets client.momo.*. The defaultTcpConfig: &DEFAULT_TCP anchor in application.yaml (which does contain checkCertificate: false) is still defined, but nothing references it with *DEFAULT_TCP. The safe-by-default true therefore wins in every profile. The guard only bites again if someone re-introduces client.momo.tcp-config.check-certificate: false outside dev. Don't read the INFO line as proof that any real HTTP client verifies certificates.

An exception thrown from an ApplicationReadyEvent listener happens after the context has been refreshed. SpringApplication.run treats it as a run failure: it closes the context and rethrows, so the JVM exits non-zero instead of carrying on to serve traffic.

Structured logging

src/main/resources/config/logback-spring.xml configures a ConsoleAppender named JSON, using logstash-logback-encoder's LoggingEventCompositeJsonEncoder. Every log line is emitted as JSON with UTC timestamp, level, thread, logger name, message, MDC, arguments, key-value pairs (kv(...) from StructuredArguments), and stack trace, plus a fixed service/environment/version block taken from spring.application.name, app.environment and app.version.

A second appender, LOKI, is defined conditionally (see the Loki callout below). It uses loki-logback-appender 2.x (Loki4jAppender, a nested <http><sender class="JavaHttpSender"/></http>, and newline-separated <labels> app/environment/level). The message body is the same JSON layout as the console appender.

Access logs

Tomcat access logs are routed through SLF4J by infrastructure.web.Slf4jAccessLogValve, not written to a file. This means they inherit both root appenders and can be queried in Loki like any other log line:

LoggerServerWired by
skillars.accessmain app (port 9990)AccessLogConfig
skillars.access.managementactuator (port 8367, separate child context)ManagementAccessLogConfig (a @ManagementContextConfiguration registered in META-INF/spring/…ManagementContextConfiguration.imports; its port guard stops the copy that component scanning puts in the main context from logging every request twice)

Both loggers are at INFO. Setting skillars.access to OFF silences both. The management log is mostly the 30-second container healthcheck plus Prometheus scrapes, so it is the bulk of access-log volume in a quiet environment.

The LGTM stack

Skillars documents a full LGTM (Loki, Grafana, Tempo, Prometheus) observability stack for the whole application: structured logs for exact error context, Prometheus metrics for rate/volume health signals, Tempo traces for causal request chains, and Grafana for dashboards and alerting. Its provisioning lives in deploy/lgtm/ (loki.yml, prometheus.yml, tempo.yml, alerts.yml, grafana-*.yml, skillars-dashboard.json). Reference docs:

  • docs/lgtm-observability.md — LogQL/PromQL/TraceQL query reference.
  • docs/deployment/monitoring.md — alert inventory and response actions.
  • docs/deployment/runbook.md — incident runbooks.
  • docs/deployment/uptime-monitor.md — external UptimeRobot monitor setup.
  • docs/deployment/local/deployment.md — running the stack locally alongside the app.

Key Flows

flowchart TD
  A[ApplicationReadyEvent fires] --> B{dev profile active?}
  B -- yes --> C[log.debug: assertion skipped]
  C --> Z[App continues serving traffic]
  B -- no --> D[Read client.momo.tcp-config.check-certificate
default = true, currently unset everywhere]
  D --> E{checkCertificate == true?}
  E -- yes --> F[log.info: TLS assertion passed]
  F --> Z
  E -- no --> G[throw AppSetupException]
  G --> H[SpringApplication.run fails: context closed]
  H --> I[JVM exits non-zero, app never serves traffic]

The assertion runs once per boot, after the full application context is up. Because no profile sets the property, the non-dev branch currently always takes the true path. The failure branch exists only as a tripwire for a future provider config that disables certificate checks outside dev.

Conventions & Gotchas

Whether logs reach Loki depends on profile and environment. loki.enabled is ${LOKI_ENABLED:false} in application.yaml, and application-prod.yaml overrides it to true. docker-compose.yml runs the prod profile with LOKI_ENABLED=true, and docker-compose.local.yml (dev profile) inherits that, so logs do reach Loki under Docker Compose. docker-compose.uat-hostwinds.yml sets LOKI_ENABLED=false because there is no Loki container there. If you run the JAR standalone (mvn spring-boot:run, an IDE run config) without the prod profile, it falls back to false. Only the console JSON appender is then live, and every LogQL query in docs/lgtm-observability.md returns nothing until you set LOKI_ENABLED=true.

Don't "simplify" the <if>/<root> layout in logback-spring.xml. The LOKI appender is defined inside <if> (a real Loki4jAppender, or logback's no-op NOPAppender when disabled). <root> sits outside it and references LOKI unconditionally. Two other layouts were tried and both broke. Nesting <if> inside <root> logs a warning. Putting <root> inside both branches leaves the context with no appenders, and Spring Boot then fails startup. Logback configuration errors are fatal here, and that includes 1.x-style loki4j syntax.

The dev-profile skip in TlsStartupAssertion is deliberate. It keeps local/sandbox setups able to point at endpoints without valid certificates. If a provider client is ever wired to a check-certificate flag again, re-check that this assertion reads that property. It is hard-coded to client.momo.tcp-config.check-certificate, which nothing currently sets.

Prometheus scrapes the management port, not 9990. /manage/prometheus is served on 8367 and is unauthenticated (PUBLIC_MGMT_ENDPOINTS). Keep port 8367 off the public ingress.
