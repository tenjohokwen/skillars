Monitoring

A single fail-fast startup guard plus the operational logging/observability surface every other module relies on to be debuggable in production.

Business Overview

Skillars coaches, parents, and players book live, time-boxed activity: a session slot, a video review window, a payment that has to clear before a booking is confirmed. None of that tolerates silent failure — a coach whose TLS configuration is quietly broken, or a payment provider call that fails without anyone noticing, turns into a missed session or an unresolved charge with no paper trail. The monitoring module itself is intentionally tiny (one class), but it exists precisely because "fail loudly at startup, and leave a trail once running" is cheaper to guarantee once, centrally, than to re-check per module. This page also anchors the broader operability story — structured logs and the LGTM stack — that every module depends on when something goes wrong in production.

Technical Overview

TlsStartupAssertion

TlsStartupAssertion (platform.monitoring) is a Spring ApplicationListener<ApplicationReadyEvent>. It deliberately hooks ApplicationReadyEvent rather than @PostConstruct: ApplicationReadyEvent fires only after every bean is fully wired and the application is ready to accept traffic, which is the correct point for an operational "is production configured correctly" assertion — a @PostConstruct check could run before other configuration has finished loading.

On firing, the assertion does two things in order:

  • Dev-profile guard. If the active Spring profiles include dev, the assertion logs a debug line and returns immediately. Local/sandbox application.yaml intentionally sets checkCertificate: false via the shared *DEFAULT_TCP YAML anchor, and the assertion must not block that.
  • Certificate-check assertion. Outside the dev profile, it reads client.momo.tcp-config.check-certificate (defaulting to true if the property is absent — safe-by-default). Both the Orange Money and MTN MoMo mobile-money provider clients share this same flag via the YAML anchor. If it resolves to false, the assertion throws AppSetupException with a message pointing at the exact property to fix.

Because AppSetupException is thrown from an ApplicationReadyEvent listener, Spring Boot treats it as a startup failure: the context fails to complete refresh and the JVM exits non-zero rather than serving traffic with certificate verification silently disabled. This is the fail-fast contract — a misconfigured production/staging deployment never comes up "green" with TLS verification off for the payment providers.

Structured logging

src/main/resources/config/logback-spring.xml configures a single ConsoleAppender named JSON, using logstash-logback-encoder's LoggingEventCompositeJsonEncoder. Every log line is emitted as JSON with UTC timestamp, level, thread, logger name, message, MDC context, and exception arguments/stack trace, plus a fixed service/environment/version block sourced from spring.application.name, app.environment, and app.version. This is what makes log lines machine-parseable for LogQL queries once/if they reach Loki (see the callout below).

The LGTM stack

Beyond this module, Skillars documents a full LGTM (Loki, Grafana, Tempo, Prometheus/Mimir) observability stack for the payment-orchestration surface: structured logs for exact error context, Prometheus/Mimir metrics for rate/volume health signals, Tempo traces for causal request chains, and Grafana for unified dashboards and alerting. See docs/lgtm-observability.md for the full LogQL/PromQL/TraceQL query reference, incident runbooks, dashboard panel definitions, and alert rules. For how to bring the stack up locally alongside the app, see docs/deployment/local-deployment.md.

Key Flows

flowchart TD
  A[ApplicationReadyEvent fires] --> B{dev profile active?}
  B -- yes --> C[log.debug: assertion skipped]
  C --> Z[App continues serving traffic]
  B -- no --> D[Read client.momo.tcp-config.check-certificate
default = true]
  D --> E{checkCertificate == true?}
  E -- yes --> F[log.info: TLS assertion passed]
  F --> Z
  E -- no --> G[throw AppSetupException]
  G --> H[Spring context fails to complete refresh]
  H --> I[JVM exits non-zero — app never serves traffic]

The assertion runs exactly once per boot, after the full application context is up. In the common case (dev profile, or a correctly configured non-dev environment) it is a no-op observability line and the app proceeds normally. The failure path only triggers when a non-dev deployment has checkCertificate: false set for the shared Orange/MTN TCP config — a configuration mistake that would otherwise let payment-provider HTTP clients skip certificate verification silently. Throwing from an ApplicationReadyEvent listener is what converts that mistake into a hard, visible deployment failure instead of a runtime security gap discovered later.

Conventions & Gotchas

Loki log shipping is not actually wired up. logback-spring.xml defines lokiUrl/lokiEnabled Spring properties (sourced from loki.url/loki.enabled) and the project depends on loki-logback-appender, but no Loki appender is configured in the logback file — only the console JSON appender is attached to root. In practice this means docker logs/dcl logs against the running container is the only way to see application logs today, and the Loki datasource in Grafana Explore will return nothing no matter how the LogQL query in docs/lgtm-observability.md is written. Treat every LogQL example there as aspirational/reference until a Loki appender is actually added to logback-spring.xml.

The dev-profile skip is a deliberate escape hatch, not a bug. Local/sandbox application.yaml intentionally sets checkCertificate: false on the shared *DEFAULT_TCP anchor so developers can hit mock/sandboxed provider endpoints without valid certs. Don't "fix" this by removing the dev-profile guard in TlsStartupAssertion — that would break local development instead.

One flag governs both providers. Orange Money and MTN MoMo TCP client config share the same *DEFAULT_TCP YAML anchor, so client.momo.tcp-config.check-certificate is a single switch for certificate verification across both provider integrations — there's no way to disable it for one provider only via this property.
