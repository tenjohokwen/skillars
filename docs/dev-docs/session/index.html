    Home / Session

    Session

    Owns coaching content and curriculum authoring — drill libraries (curated and coach-authored), session-plan blocks, reusable templates, and player homework — as distinct from booking's scheduling and calendar concerns.

    Business Overview

    The session module is where a coach designs what actually happens during a training session, independent of when it happens. It answers questions like: which drills will we run, in what order, for how long, targeting which development goals — and afterwards, what homework should the player practice before the next session. It does not know about calendars, availability, or credit wallets; those concerns belong to booking and payment.

    Primary personas and how they touch this module:

    • Coach — browses the curated PLATFORM drill library and their own PRIVATE library; authors private drills from scratch (create / edit / delete), clones platform drills to customize them, tags drills, uploads demo videos for private drills, builds a session plan (ordered blocks of drills) for a specific booking, saves a plan as a reusable template, and deploys a template onto an upcoming booking picked from a list. On the player detail page the coach also sees the homework they assigned and whether it was done.
    • Parent — views the homework ("Locker Room Drills") assigned to their child after a completed session and marks assignments as complete.
    • Player — the subject of plans and homework (referenced by playerId, a PlayerProfile PK, not a user id). A self-registered adult player can read and complete their own locker room; a minor's is acted on by the parent.

    Key business rules encoded in the code:

    • Drills are either PLATFORM (curated, no owner_coach_id) or PRIVATE (coach-owned, non-null owner_coach_id) — enforced by the chk_drill_owner CHECK constraint. (Older docs and comments say COACH; the DB value is PRIVATE.) Status is ACTIVE or ARCHIVED.
    • A coach may use every PLATFORM drill and their own PRIVATE drills — never another coach's PRIVATE drill. This one rule lives in DrillUsagePolicy and is applied on plan create/update, template deploy, homework selection and the development timeline.
    • A private drill's name is unique among that coach's ACTIVE private drills (idx_drills_coach_name_unique_active, V173); a coach can hold at most one ACTIVE clone per source drill (idx_drills_clone_uniqueness_active, V173).
    • Only PLATFORM drills can be cloned (CLONE_NOT_ALLOWED otherwise).
    • Tags are private per-coach labels on the coach's own PRIVATE drills (composite key drill, tag, coach).
    • A session plan is one-to-one with a booking (uq_sessions_booking_id; a second create is SESSION_ALREADY_EXISTS). A plan can only be created or a template deployed against a booking that is CONFIRMED — UPCOMING is explicitly not plannable any more.
    • Every plan/template carries a computed "Session DNA" radar score (technical / physical / cognitive / match realism / weak-foot focus, 0–100), an equipment checklist and a per-block SLU (skill-load units), all derived from drill metadata.
    • Session Builder (plans, templates, suggestions) and drill video upload are independently feature-gated per coach subscription tier.
    • Homework (max 2 drills) is chosen by the coach at wrap-up in booking and materialised here when the booking completes — there is no "create homework" endpoint in this module.

    Session vs. Booking — the boundary new devs get wrong. booking owns scheduling and the booking lifecycle; session owns curriculum content. They touch through: (1) session reading BookingQueryService.getBookingSnapshot() / findCoachBookings() to validate ownership/status and build the deploy picker; (2) session listening to BookingCompletedEvent (homework + plan → COMPLETED) and BookingStatusChangedEvent (plan → CANCELLED on terminal non-completion); and (3) the reverse direction — booking.BookingCompletionService reads SessionRepository, DrillRepository and DrillUsagePolicy directly to validate homework drills and snapshot the plan's blocks at wrap-up (booking.session_completion_data.plan_blocks_snapshot, V170). session never writes booking or payment data; it only reads pack status via payment.service.PackSessionService (hasActivePackForAnyOf / getActivePackId).

    Key Flows

    1. Coach builds a session plan for a booking

    sequenceDiagram
  participant Coach
  participant Resource as SessionBuilderResource
  participant Plan as SessionPlanService
  participant Gate as DrillLibraryService
  participant Booking as Booking Module
  participant DB as session.sessions

  Coach->>Resource: POST /api/session/sessions {bookingId, blocks, developmentFocus}
  Resource->>Plan: createSession(req, coachUserId)
  Plan->>Gate: checkSessionBuilderGate(coachUserId)
  Gate-->>Plan: OK (tier allows Session Builder)
  Plan->>DB: existsByBookingId? (SESSION_ALREADY_EXISTS)
  Plan->>Booking: getBookingSnapshot(bookingId)
  Booking-->>Plan: coachId, playerId, status
  Plan->>Plan: booking owned by coach and CONFIRMED
  Plan->>Plan: DrillUsagePolicy.requireAllUsable (404 on unknown/foreign drill)
  Plan->>Plan: compute Session DNA + equipment list
  Plan->>DB: save Session (status=DRAFT)
  Plan-->>Resource: SessionPlanResponse (blocks with per-block SLU)
  Resource-->>Coach: 201 Created

    The tier gate runs first, then a read-only booking snapshot confirms ownership and that the booking is CONFIRMED. Every referenced drill must be a PLATFORM drill or one of the coach's own PRIVATE drills (any status, so a plan holding a since-archived drill of the coach's own still saves). Unknown, null and foreign ids all answer the same 404 so the API never confirms another coach's drill exists. DNA and equipment are stored with the blocks, not recomputed on read; uq_sessions_booking_id (mapped to 409) backs the pre-check against a race. Updates follow the same path, are refused with SESSION_PLAN_LOCKED once the plan is COMPLETED/CANCELLED or the booking is terminal, and accept only DRAFT/SAVED as a client-set status. The COMPLETED/CANCELLED check is repeated after taking the row lock, so a completion that commits while the edit is in flight wins.

    2. Coach authors / deletes a private drill

    sequenceDiagram
  participant Coach
  participant Resource as DrillLibraryResource
  participant Lib as DrillLibraryService
  participant DB as session.drills

  Coach->>Resource: PUT /api/session/drills/{id} (DrillUpsertRequest)
  Resource->>Lib: updateDrill(id, req, coachUserId)
  Lib->>DB: findById, check PRIVATE and owned (else 404)
  Lib->>DB: findByIdForUpdate (NOWAIT, PessimisticLockRetryer) + refresh
  Lib->>Lib: re-check ownership on locked row, require ACTIVE
  Lib->>Lib: sanitize text, resolve skillWeighting (sum 100)
  Lib->>DB: saveAndFlush (name clash -> 409 session.drillNameTaken)
  Resource-->>Coach: 200 DrillResponse
  Coach->>Resource: DELETE /api/session/drills/{id}
  Resource->>Lib: deleteDrill -> same lock + ownership
  Lib->>Lib: linked video? -> DRILL_HAS_VIDEO
  Lib->>DB: status = ARCHIVED (soft delete)
  Resource-->>Coach: 204

    Create is a plain insert: the name-uniqueness rule is enforced only by idx_drills_coach_name_unique_active, which ApiAdvice maps to 409 session.drillNameTaken (saveAndFlush makes the violation surface inside the call). skillWeighting is optional: if supplied it must cover exactly the drill's skills and sum to 100; otherwise the existing weighting is kept when the skill set is unchanged, else derived (primary skills share 70, or 100 with no secondaries). setupDiagram is never client-settable. Edits are visible wherever the drill is used, because plans/templates/homework store drill ids, not copies. Delete is an archive so those references survive; a drill with a linked video must have the video removed first, which runs the ref-count/physical-deletion path.

    3. Coach uploads a demo video for a private drill

    sequenceDiagram
  participant Coach
  participant Resource as DrillUploadResource
  participant Upload as DrillUploadService
  participant Video as Video Module
  participant DB as session.drill_video_refs

  Coach->>Resource: POST /api/session/drills/{drillId}/video/initiate
  Resource->>Upload: initiateUpload(drillId, coachUserId, req)
  Upload->>Upload: PRIVATE and owned? (DRILL_NOT_OWNED) + tier gate
  Upload->>Video: VideoTypeConstraints.validate(DRILL_DEMO, size, duration)
  Upload->>Upload: lock Drill row, then Video row (fixed order)
  Upload->>Upload: existing READY video? -> DRILL_VIDEO_ALREADY_LINKED
  Upload->>Video: initializeUpload(..., DRILL_DEMO)
  Video-->>Upload: videoId, upload URL, TUS auth fields
  Upload->>DB: setVideoId / upsertVideoId
  Upload-->>Resource: DrillUploadInitiateResponse
  Resource-->>Coach: 201 Created

    Limits for DRILL_DEMO belong to the video module; violations are re-thrown as DrillConstraintViolationException (422 via SessionApiAdvice). The lock section only reads (per PessimisticLockRetryer's contract); writes and the event publish happen after it but inside the same transaction, so the DB lock still covers them. Replacing a non-READY (PROCESSING/FAILED) video publishes VideoPhysicalDeletionEvent for the orphaned one if nothing else references it. The bytes go straight from the client to the provider (TUS); session never handles them.

    4. Coach deploys a template onto a booking

    sequenceDiagram
  participant Coach
  participant Resource as SessionTemplateResource
  participant Tpl as SessionTemplateService
  participant Booking as Booking Module
  participant DB as session schema

  Coach->>Resource: GET /api/session/templates/deployable-bookings
  Resource->>Tpl: listDeployableBookings(coachUserId)
  Tpl->>Booking: findCoachBookings(coachId, [CONFIRMED], now, now+60d)
  Tpl->>DB: findBookingIdsWithPlan(candidates)
  Tpl-->>Coach: bookings without a plan and with a player
  Coach->>Resource: POST /api/session/templates/{id}/deploy?bookingId=
  Resource->>Tpl: deployTemplate(templateId, bookingId, coachUserId)
  Tpl->>Tpl: gate, template owned and ACTIVE (TEMPLATE_NOT_OWNED)
  Tpl->>Booking: getBookingSnapshot -> owned, CONFIRMED, has player
  Tpl->>DB: existsByBookingId? (SESSION_ALREADY_EXISTS)
  Tpl->>Tpl: DrillUsagePolicy.requireAllUsable(template drills)
  Tpl->>DB: insert Session (DRAFT, sourceTemplateId/Name), incrementDeployCount
  Tpl-->>Coach: 201 SessionPlanResponse

    The picker is only a hint — deploy re-checks every condition. Deploy copies the template's stored DNA and equipment list rather than recomputing them, and re-runs the drill-usage rule because it bypasses SessionPlanService: a template copied from a plan saved before deferred-162 could otherwise re-deploy another coach's private drill forever.

    5. Booking completes, homework is assigned, parent/player completes it

    sequenceDiagram
  participant Booking as Booking Module
  participant HW as HomeworkAssignmentService
  participant DB as session.homework_assignments
  participant TL as development.TimelineEventListener
  participant User as Parent / Player
  participant Resource as HomeworkResource

  Booking->>HW: BookingCompletedEvent(bookingId, playerId, coachId, homeworkDrillIds)
  Note over HW: @Async, AFTER_COMMIT, at most 2 drills
  loop each drill, own REQUIRES_NEW tx
    HW->>HW: erasure guard (stop if player erased)
    HW->>DB: insert if (bookingId, drillId) absent
  end
  HW->>TL: HomeworkAssignedEvent(newly inserted ids only)
  User->>Resource: GET /api/session/players/{playerId}/homework
  Resource->>HW: getLockerRoomDrills(playerId)
  HW-->>User: assignments from coaches with an active pack
  User->>Resource: POST /api/session/homework/{assignmentId}/complete
  Resource->>HW: markComplete(assignmentId, callerUserId)
  HW->>DB: PlayerOwnershipGuard.owns else 404, INSERT ... ON CONFLICT DO NOTHING

    session never decides when homework is assigned. The coach picks drills at wrap-up and booking.BookingCompletionService validates them with DrillUsagePolicy.isAssignableAsHomework; this module materialises them after the booking transaction commits. One REQUIRES_NEW transaction per drill means a duplicate-key failure on drill 2 cannot roll back drill 1, and the HomeworkAssignedEvent is published from a finally so drill 1 is still announced. The timeline consumer keeps one HOMEWORK_ASSIGNED row per (player, booking) and merges a later event's drill ids into it, under the same erasure-guard lock. In the Locker Room, assignments from a coach whose pack with the family has lapsed are hidden though the rows remain. Completion is idempotent and race-safe via insertIfAbsent (native ON CONFLICT (assignment_id) DO NOTHING), which avoids a caught flush failure poisoning the transaction.

    Conventions & Gotchas

    Two independent feature gates. feature.sessionBuilder.enabled.<TIER> and feature.drillVideoUpload.enabled.<TIER> (tiers SCOUT, INSTRUCTOR, ACADEMY). Every plan/template/suggestion method calls DrillLibraryService.checkSessionBuilderGate() first; the drill library itself (list, CRUD, clone, tags) is not gated. Both gates throw FeatureGatedException carrying the lowest enabled tier (found by iterating CoachSubscriptionTier.values(), whose declaration order is asserted at class load) so the frontend can upsell. If no tier enables a feature, the feature.gate.fully_disabled counter increments.

    A session plan's status has three writers. The coach's updateSession rewrites the whole row (status included) with save(), while handleBookingCompleted and handleBookingTerminalNonCompletion move it to COMPLETED/CANCELLED. updateSession therefore takes SessionRepository.findByIdForUpdate (NOWAIT, wrapped in PessimisticLockRetryer) after its ownership check, refreshes, and re-checks COMPLETED/CANCELLED on the locked state. The listeners are single conditional UPDATEs (markCompletedByBookingId, markCancelledIfOpenByBookingId), which take the same row lock and so serialize with it. Both move only an open (DRAFT/SAVED) plan, so a CANCELLED plan is no longer revived by a later completion event. Before fix/content-consistency-and-lost-updates an edit racing a booking completion could flip COMPLETED back to SAVED. Since C5 (V188) Session also carries @Version: both conditional UPDATEs do version = version + 1, so a full-row save from a snapshot read before them fails (409) instead of reverting them, and findByIdForUpdate locks with a scalar query before findById so the unlocked-read-then-lock shape does not trip Hibernate's lock-upgrade version check. A new writer of this entity must do the same: lock-and-refresh or a conditional UPDATE that bumps the version.

    Use DrillUsagePolicy for any new code that puts a drill in front of a player. Before deferred-162, a plan could reference another coach's PRIVATE drill and return it in full. Writes must call requireAllUsable (same 404 for unknown and foreign — never a 403 that leaks existence); reads of legacy rows must filter through usableOnly. Note the deliberate asymmetry: plans accept ARCHIVED own drills, homework does not.

    Drill row locks: check, lock, re-check. DrillRepository.findByIdForUpdate is PESSIMISTIC_WRITE with lock timeout 0 (NOWAIT) and is always wrapped in PessimisticLockRetryer.withBoundedRetry, whose supplier must be read-only (it can run more than once). Ownership is checked before locking (so a probe never locks someone else's row) and again on the refreshed, locked entity. When both a drill and a video are locked, the order is always Drill then Video (initiateUpload and deleteVideo both follow it) to rule out deadlocks. deleteDrill's "has video?" check runs under the same drill lock the upload path takes.

    Drill videos are shared, not owned 1:1. Cloning copies the source's video_id into a new DrillVideoRef. Physical deletion is decided by existsByVideoId (does any ref still point at it?), not by ref_count, which is bookkeeping only. Never edit drill_video_refs outside DrillUploadService (or the video module's outbox processor) — you can strand a video or delete one another drill still uses.

    Idempotency keys off bookingId, never sessionId. session_id on homework_assignments is null for QUICK-mode bookings, and Postgres treats NULL <> NULL, so a unique constraint on it would protect nothing. Follow this pattern for any event handler keyed on an optional FK.

    Archived means "gone from pickers", not deleted. Drill delete and template delete are soft (ARCHIVED). Library, suggestions and homework only offer ACTIVE drills; plans keep working. V173 made the uniqueness indexes ACTIVE-only so an archived drill frees its name and clone slot.

    DNA, equipment and SLU are computed, not authored. DNA and equipment are snapshotted on each plan save (and copied verbatim on template create/deploy); per-block SLU is computed on every read from current drill metadata. So after a drill edit, a plan's DNA stays stale until the plan is saved again, but its SLU changes immediately. For QUICK bookings the timeline/SLU use the wrap-up snapshot in booking.session_completion_data.plan_blocks_snapshot (V170) rather than the live plan.

    Error-code reuse. SESSION_BOOKING_NOT_OWNED is also thrown for "booking not CONFIRMED" and "booking has no player", and TEMPLATE_NOT_OWNED for an archived template — check the message, not just the code, when debugging.
