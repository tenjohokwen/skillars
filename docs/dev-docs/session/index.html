Session

Owns coaching content and curriculum authoring — drill libraries, session-plan blocks, reusable templates, and player homework — as distinct from booking's scheduling and calendar concerns.

Business Overview

The session module is where a coach designs what actually happens during a training session, independent of when it happens. It answers questions like: which drills will we run, in what order, for how long, targeting which development goals — and afterwards, what homework should the player practice before the next session. It does not know about calendars, availability, or credit wallets; those concerns belong to booking.

Primary personas and how they touch this module:

  • Coach — browses a curated PLATFORM drill library and/or a private COACH-owned library, clones platform drills to customize them, tags drills for their own organization, uploads demo videos for private drills, builds a session plan (ordered blocks of drills) for a specific booking, saves a session as a reusable template, and deploys a template into a new booking later.
  • Parent — views the homework ("Locker Room Drills") assigned to their child after a completed session and marks individual assignments as complete.
  • Player — is the subject of session plans and homework (referenced by playerId) but does not call this module's endpoints directly; the parent account acts on the player's behalf.

Key business rules encoded in the code:

  • Drills are either PLATFORM (curated, globally owned, no owner_coach_id) or COACH (privately owned, must have an owner_coach_id) — enforced by a database CHECK constraint, not just application logic.
  • Only PLATFORM drills can be cloned into a coach's private library; cloning a COACH drill is rejected (CLONE_NOT_ALLOWED).
  • Tags on drills are private per-coach labels (composite key of drill, tag, coach) — never global metadata.
  • A session plan is one-to-one with a booking: creating a second plan for the same bookingId is rejected (SESSION_ALREADY_EXISTS), and a plan can only be created or a template deployed against a booking that is CONFIRMED or UPCOMING.
  • Every session/template computes a "Session DNA" radar score (technical / physical / cognitive / match realism / weak-foot focus, 0–100) and an equipment checklist, derived purely from the metadata of the drills placed in its blocks.
  • Access to the "Session Builder" (session plans/templates) and to drill video upload are independently feature-gated per coach subscription tier.
  • Homework is generated automatically when a booking completes — coaches do not call a "create homework" endpoint directly.

Session vs. Booking — the boundary new devs get wrong. booking owns scheduling: creating bookings, coach availability, booking status transitions, session-pack/credit consumption. session owns curriculum content: what drills, in what structure, and homework follow-through. The two modules only touch through: (1) session reading a booking's snapshot via BookingQueryService.getBookingSnapshot() to validate ownership/status before creating or deploying a plan, and (2) session reacting to BookingCompletedEvent, published by booking, to generate homework assignments. session never writes to booking data and never touches payment/credit logic directly (it only reads pack status via SessionPackService.hasActivePack/getActivePackId to decide whether homework is still visible to a family).

Key Flows

1. Coach builds a session plan for a booking

sequenceDiagram
  participant Coach
  participant Resource as SessionBuilderResource
  participant Plan as SessionPlanService
  participant Gate as DrillLibraryService
  participant Booking as Booking Module
  participant DB as session.sessions

  Coach->>Resource: POST /api/session/sessions {bookingId, blocks, developmentFocus}
  Resource->>Plan: createSession(req, coachUserId)
  Plan->>Gate: checkSessionBuilderGate(coachUserId)
  Gate-->>Plan: OK (tier allows Session Builder)
  Plan->>Booking: getBookingSnapshot(bookingId)
  Booking-->>Plan: coachId, playerId, status
  Plan->>Plan: verify booking owned by coach and CONFIRMED/UPCOMING
  Plan->>Plan: resolve drill metadata, compute Session DNA + equipment list
  Plan->>DB: save Session (status=DRAFT)
  Plan-->>Resource: SessionPlanResponse
  Resource-->>Coach: 201 Created

The coach submits blocks of drills for a specific booking. Before anything is written, the module checks that the coach's subscription tier has Session Builder enabled, then asks booking for a read-only snapshot to confirm the coach actually owns that booking and that it is in a plannable state. Drill metadata for every referenced drill is batch-loaded once to compute both the Session DNA radar score and the equipment checklist, which are stored alongside the blocks rather than recomputed on every read. Creating a second plan for the same booking is rejected outright, with a database unique-constraint fallback catching any race. Coaches typically call the suggestions endpoint (DrillSuggestionService) while building blocks to fill remaining slots with drills matched to the player's development focus.

2. Coach uploads a demo video for a private drill

sequenceDiagram
  participant Coach
  participant Resource as DrillUploadResource
  participant Upload as DrillUploadService
  participant Constraints as Video Module (constraints)
  participant VideoSvc as Video Module (upload)
  participant DB as session.drill_video_refs

  Coach->>Resource: POST /api/session/drills/{drillId}/video/initiate
  Resource->>Upload: initiateUpload(drillId, coachUserId, req)
  Upload->>Upload: verify drill is COACH-owned by this coach
  Upload->>Constraints: validate(DRILL_DEMO, fileSizeBytes, durationSeconds)
  Constraints-->>Upload: OK or VideoValidationException
  Upload->>VideoSvc: initializeUpload(coachId, fileName, size, mimeType, DRILL_DEMO)
  VideoSvc-->>Upload: videoId, signedUploadUrl, expiresAt
  Upload->>DB: upsert DrillVideoRef(drillId, videoId)
  Upload-->>Resource: DrillUploadInitiateResponse
  Resource-->>Coach: 201 Created (signedUploadUrl)

Video upload is only allowed on drills the coach privately owns, and only if the coach's tier has the drill-video-upload feature enabled. Size/duration limits for a DRILL_DEMO video are not owned by this module — they are delegated to the video module's VideoTypeConstraints, and any violation is re-thrown as a DrillConstraintViolationException so the frontend gets a drill-scoped 422 error instead of a generic video error. If a READY video is already linked, the coach must delete it first. The actual file bytes never pass through session; the client uploads directly to the signed URL returned by the video module.

3. Booking completes, homework is assigned, parent completes it

sequenceDiagram
  participant Booking as Booking Module
  participant HW as HomeworkAssignmentService
  participant DB as session.homework_assignments
  participant Parent
  participant Resource as HomeworkResource

  Booking->>HW: publish BookingCompletedEvent(bookingId, playerId, coachId, homeworkDrillIds)
  Note over HW: @TransactionalEventListener AFTER_COMMIT, @Async
  HW->>DB: create HomeworkAssignment per drill (idempotent on bookingId+drillId)
  Parent->>Resource: GET /api/session/players/{playerId}/homework
  Resource->>HW: getLockerRoomDrills(playerId)
  HW-->>Resource: assignments (only coaches with an active session pack)
  Resource-->>Parent: 200 OK
  Parent->>Resource: POST /api/session/homework/{assignmentId}/complete
  Resource->>HW: markComplete(assignmentId, parentId)
  HW->>DB: verify parent owns player, insert HomeworkCompletion (idempotent)
  HW-->>Resource: OK

This is the flow that most clearly shows the module boundary: session never decides when homework is assigned — it reacts to a booking-owned lifecycle event, after that booking's transaction has committed. Assignments key off bookingId rather than the (sometimes null) sessionId, because "quick" bookings can skip session planning entirely. When the parent views the Locker Room, assignments from a coach whose session pack with that family has lapsed are hidden even though the row still exists, and marking complete is re-validated against parent-child ownership independently of the earlier gate on the controller.

Conventions & Gotchas

Two independent feature gates. Session Builder access (feature.sessionBuilder.enabled.<TIER>) and drill video upload (feature.drillVideoUpload.enabled.<TIER>) are separate config keys per coach subscription tier. Every session/template/drill-suggestion service method calls DrillLibraryService.checkSessionBuilderGate() first — a coach can be blocked from the whole module without being blocked from video upload specifically, or vice versa. Both throw FeatureGatedException, not a plain 403, so the frontend can show an upsell rather than a generic error.

PLATFORM vs COACH drills is a DB-enforced invariant, not just a convention. The chk_drill_owner check constraint requires PLATFORM drills to have a null owner_coach_id and COACH drills to have a non-null one. Cloning only works PLATFORM → COACH; attempting to clone a COACH drill throws CLONE_NOT_ALLOWED.

Drill videos are ref-counted, not owned 1:1. DrillVideoRef.refCount lets an original drill and its clones share one underlying video-module asset. Deleting a video from one drill only fires VideoPhysicalDeletionEvent (real deletion) when no other DrillVideoRef row still points at that videoId. Never delete/replace a DrillVideoRef row directly without going through DrillUploadService — doing so can either strand a video with no cleanup path or physically delete a video another drill still relies on.

Idempotency keys off bookingId, never sessionId. HomeworkAssignmentService.handleBookingCompleted deliberately uses the (booking_id, drill_id) unique constraint for idempotent replay protection instead of session_id, because sessionId is nullable (quick-mode bookings have no session plan) and Postgres treats NULL <> NULL — a unique constraint on a nullable column gives zero protection once that column is null. Follow this pattern for any future event handler keyed on optional foreign keys.

Session DNA and the equipment list are computed, not authored. Both are derived purely from the metadata of drills placed in a session/template's blocks (SessionDnaCalculator, EquipmentListService) and recomputed on every create/update — there is no direct API to set them, so if a drill's metadata changes, existing sessions/templates keep their previously computed snapshot until next saved.
