    Admin

    Admin-only tooling for trust & safety moderation, account and coach enforcement, dispute resolution, appeals, stuck-booking remediation, and GDPR data-subject requests.

    Business Overview

    Skillars is a two-sided marketplace connecting minors (Players), their Parents, and Coaches, so the platform needs a back office that lets Admins keep the marketplace safe and legally compliant without touching the consumer-facing apps. The admin module is that back office. Most of its endpoints are gated behind SecurityConstants.HAS_ADMIN_ROLE (ROLE_ADMIN or ROLE_LTD_ADMIN) and are driven by the admin console pages under src/frontend/src/pages/admin/. Three controllers are end-user facing: disputes, appeals, and GDPR self-service.

    Moderation queue Account enforcement Coach enforcement Dispute resolution Appeals Booking force-complete GDPR requests

    1. Unified moderation queue. Reported messages and conversations, AI-moderation holds, flagged reviews, coach strike thresholds, raised disputes, GDPR erasure deadline overruns and orphaned Stripe subscriptions all originate in other modules (or in admin itself). AdminAlertEventListener (plus GdprErasureService directly) turns each into one deduplicated AdminAlert row, and AdminQueueService serves a single paginated, type-filterable queue over that table. Only status=OPEN is exposed — the API rejects any other status filter.

    2. Account enforcement (AdminUserService, V171). Admins can search any user, suspend or reactivate a non-admin account, and clear a user's failed-login rate limit. "Suspended" is the existing main."user".locked flag; suspending also revokes live sessions and, for a coach, suspends the marketplace profile in the same transaction.

    3. Coach enforcement. Coaches accumulate reliability strikes (no-shows, unexcused cancellations) via the payment module's ReliabilityStrikeService. Crossing reliability.strike.visibilityThreshold (default 3 in 30 days) sets the coach to REDUCED; crossing reliability.strike.suspensionThreshold (default 5) sets PENDING_REVIEW and publishes StrikeThresholdReachedEvent, which lands in the admin queue. There is no automatic suspension — an admin inspects the coach's strike and cancellation history, then suspends (auto-cancelling their REQUESTED bookings and, unless the admin opts out, their upcoming ones with full refunds), reinstates, or issues/deletes strikes. Admins also set the coach's marketplace verification tier (BASIC/TRUSTED/FEATURED).

    4. Dispute resolution. A Parent, a self-registered Player, or the booking's (non-suspended) Coach can raise a dispute on a terminal booking within disputes.submissionWindowDays (default 14). An admin reviews it alongside the payment breakdown and coach cancellation history, then resolves it with FULL_CREDIT, PARTIAL_CREDIT, NO_ACTION or COACH_WARNING, or dismisses it. Resolution also reconciles the coach's payout.

    5. Appeals (AppealService, V172, FR-ADM-004 / FR-TSC-003). A user subject to an enforcement action — a reliability strike, a coach suspension, a blocked review, or a resolved/dismissed dispute — may submit one appeal within 14 days. An admin decides it UPHELD or OVERTURNED; the decision is final, and overturning applies the reversal in the same transaction.

    6. Stuck-booking force-complete (AdminBookingCompletionService). Support can look up a booking by id and force-complete one abandoned at wrap-up with placeholder completion data, sharing BookingCompletionService.forceCompleteWithPlaceholderData with the automatic StuckCompletionSweeperService.

    GDPR is a legal deadline, not a nice-to-have. Any authenticated user can request an export or erasure of their own data (Articles 15/17/20), and since V172 a Parent can do the same for a parent-owned (shadow) child profile, which has no account of its own. Erasure anonymises the user, hard-deletes messages, deletes/anonymises reviews, scrubs coach-authored narrative, cascades through every development-tracking table, and revokes refresh tokens. Exports are a ZIP behind a signed, time-limited URL. Both run after the request row commits; failed erasures are re-driven daily by GdprErasureRetryScheduler. Get the wiring wrong and you silently miss the regulatory deadline.

    Key Flows

    Coach enforcement: strike threshold to suspension

    sequenceDiagram
  participant Payment as payment.ReliabilityStrikeService
  participant Listener as AdminAlertEventListener
  participant Alerts as admin_alerts
  participant Admin as Admin (console)
  participant Enforce as AdminCoachEnforcementService
  participant Booking as booking.BookingRepository
  Payment->>Payment: count >= suspensionThreshold: status PENDING_REVIEW
  Payment->>Listener: StrikeThresholdReachedEvent(coachId)
  Listener->>Alerts: REQUIRES_NEW insert STRIKE_THRESHOLD (dedup on OPEN)
  Admin->>Enforce: GET /api/admin/coaches/{coachId}/enforcement
  Enforce-->>Admin: status, tier, strikes, cancellation history
  Admin->>Enforce: POST /api/admin/coaches/{coachId}/suspend
  Enforce->>Enforce: findByIdForUpdate (bounded retry), no-op if already SUSPENDED
  Enforce->>Booking: findByCoachIdAndStatusIn(REQUESTED, plus ACCEPTED to UPCOMING unless opted out)
  Enforce->>Booking: cancelBookingAsAdmin per booking (booking row lock, CANCEL_ADMIN, BookingStatusChangedEvent)
  Booking-->>Payment: BookingCancelledByAdminEvent (refund if captured, neutral parent notice, no strike)
  Note over Enforce: a capture in flight (CAPTURE_PENDING) fails the whole suspension - 409 admin.coaches.paymentInProgress
  Enforce->>Enforce: CoachSuspendedEvent (+ CoachSuspensionNotificationEvent if notifyCoach)
  Enforce->>Alerts: AdminActionLog(COACH_SUSPEND)
  Note over Enforce: notifyCoach - AdminOutcomeEmailListener enqueues COACH_SUSPENDED (BEFORE_COMMIT)

    Safety hold. A CSAM match on a coach's video publishes AccountSuspensionRequestedEvent with the video's ownerId, which for a coach upload is the CoachProfile UUID. CoachSafetySuspensionListener (AFTER_COMMIT, fallbackExecution, never throws) calls suspendCoachForSafetyHold (REQUIRES_NEW), which runs the same locked suspension in two transactions: applySafetyHoldStatus (REQUIRES_NEW) commits the profile SUSPENDED and the COACH_SAFETY_HOLD row first, then sweepBookingsForSafetyHold (REQUIRES_NEW) cancels every not-yet-started booking (REQUESTED, ACCEPTED, PAYMENT_PENDING, CONFIRMED, UPCOMING) through the state machine (CANCEL_ADMIN, actor id 0) with full refunds - so booking-row contention can fail the sweep (the listener retries the whole, idempotent hold three times) but never undo the takedown. A coach an admin had already suspended is converted (new statusChangedAt + the COACH_SAFETY_HOLD row) and swept too; a coach already under a safety hold is only re-swept. It does not notify the coach, and is logged as COACH_SAFETY_HOLD with admin_id = 0 (AdminActionLog.SYSTEM_ACTOR_ID; the column is NOT NULL and has no FK) at the same instant as the profile's statusChangedAt. That row is what makes the hold non-appealable: AppealService answers 409 appeals.notAppealable on submit and never reverses it on overturn (an admin can still reinstate directly from the console). What the hold cannot cancel server-side - an IN_PROGRESS / PAUSED session, or a PAYMENT_PENDING booking whose Stripe capture is in flight - raises one urgent SAFETY_HOLD_BOOKING admin alert per booking (reason IN_PROGRESS / PAUSED / PAYMENT_IN_FLIGHT); the queue summary resolves the parent's email at read time so the admin can contact them (the alert row stores no contact PII). The hold never fails on those. An admin marks one handled from the moderation queue (POST /api/admin/queue/safety-hold-alerts/{alertId}/resolve, an atomic conditional UPDATE; 404 once it is no longer open). The payout freeze for a held coach belongs to the payment module and keys off the COACH_SAFETY_HOLD row. CoachSafetySuspensionListener runs at HIGHEST_PRECEDENCE because with no transaction the multicaster stops at the first listener that throws, and this one never throws.

    Suspension is not just a status flip (DECISIONS item 2): every REQUESTED booking for the coach is cancelled and, by default, so is every ACCEPTED / PAYMENT_PENDING / CONFIRMED / UPCOMING one (request flag cancelUpcomingBookings, default true, a checkbox in the suspend dialog; the response reports cancelledBookings). Each goes through the booking state machine (BookingService.cancelBookingAsAdmin, cancel reason COACH_UNAVAILABLE for both paths - neutral, because the booking row reaches the parent's GDPR export; the real reason is on the coach's admin_action_log row), so the batch roll-up, SSE and session-plan listeners see a BookingStatusChangedEvent; a booking whose fresh status (re-read under its row lock) is no longer cancellable is skipped. Its BookingCancelledByAdminEvent refunds the payer in full when payment was captured (card/credit to the credit wallet, pack session restored, expired pack refunded to the wallet), issues no reliability strike, and sends the parent a neutral "the coach is unavailable" notice. A PAYMENT_PENDING booking with a capture in flight fails the whole suspension with a retryable 409 admin.coaches.paymentInProgress (all-or-nothing). Live sessions are left to finish. No payout freeze for an ordinary suspension. The coach-profile row lock matters: the booking accept paths re-check SUSPENDED under the same lock, so a suspension cannot slip in between their check and write. reinstateCoach runs CoachProfileService.validateReadyForActivation first and falls back to DRAFT if the profile is incomplete, ensures a SCOUT coach_subscriptions row exists, and then re-checks the in-window strike count: below the visibility threshold it resolves the STRIKE_THRESHOLD alert, otherwise it re-publishes StrikeThresholdReachedEvent so the alert stays open. Explicit admin intent wins: a reinstate proceeds even if another admin just suspended.

    Account suspension

    sequenceDiagram
  participant Admin as Admin (console)
  participant Svc as AdminUserService
  participant Users as main.user
  participant Tokens as refresh_tokens
  participant Enforce as AdminCoachEnforcementService
  Admin->>Svc: POST /api/admin/users/{userId}/suspend {reason, cancelUpcomingBookings}
  Svc->>Svc: reject self (400)
  Svc->>Users: findByIdForUpdate (NO_WAIT, bounded retry)
  Svc->>Svc: reject ADMIN / LTD_ADMIN target (409)
  Svc->>Users: lock(), clear persistent tokens, saveAndFlush
  Svc->>Users: invalidateSessionsForUserInCurrentTransaction (stamp)
  Svc->>Tokens: markAllUsedByUserId (REQUIRES_NEW)
  Svc->>Enforce: suspendCoach(coachId, notifyCoach=false, cancelUpcomingBookings) if a coach profile exists
  Svc->>Users: AdminActionLog(USER_SUSPEND)

    Every authentication path already enforces locked. The residual window is a still-valid JWT on the filter's no-DB fast path until its next DB re-auth (5 min). Suspend is idempotent (an already-locked account writes no second audit row but still makes sure the coach profile is suspended). Reactivating the account does not reinstate the coach profile, and is refused (admin.users.erased) when a self-scoped erasure request exists for the user — a parent's erasure of a child does not block it. It is also refused (admin.users.safetyHold) for an account in verificationStatus = SUSPENDED, the child-safety suspension the CSAM scan applies (AccountSuspensionEventListener, security module).

    Dispute resolution

    sequenceDiagram
  participant Party as Parent / Player / Coach
  participant DisputeApi as DisputeResource
  participant DisputeSvc as DisputeService
  participant Listener as AdminAlertEventListener
  participant Admin as Admin (console)
  participant Wallet as payment.CreditWalletService
  participant Payout as payment.coach_payouts
  Party->>DisputeApi: POST /api/disputes {bookingId, reason, details}
  DisputeApi->>DisputeSvc: raiseDispute(...)
  DisputeSvc->>DisputeSvc: reason, owner, terminal status, window, no open dispute
  DisputeSvc-->>Listener: DisputeRaisedEvent
  Listener->>Listener: DISPUTE_RAISED alert (referenceId = bookingId)
  Admin->>DisputeSvc: GET /api/admin/disputes/queue, then /{disputeId}
  Admin->>DisputeSvc: POST /api/admin/disputes/{disputeId}/resolve
  DisputeSvc->>Wallet: writeLedgerEntry(BOOKING_REFUND) for credit outcomes
  DisputeSvc->>Payout: findByIdForUpdate: RELEASED enqueue reversal, PENDING_RELEASE/HOLD cancel
  DisputeSvc->>DisputeSvc: RESOLVED, resolve alert, AdminActionLog(DISPUTE_RESOLVE)
  DisputeSvc-->>Party: DisputeResolvedEvent - DISPUTE_RESOLVED email + inbox row (BEFORE_COMMIT)

    Eligible reasons are COACH_NO_SHOW, SESSION_QUALITY, SAFETY_CONCERN, UNAUTHORISED_CHARGE, OTHER; eligible booking statuses are COMPLETED, CANCELLED* and NO_SHOW_*. The submission window is measured from Booking.getStatusAnchor() (when the booking reached that status, V178 status_changed_at; updated_at only while that is NULL), so a later unrelated write to the booking cannot reopen it. Ownership resolves the player through PlayerProfile.userId (Booking.playerId is a profile id) and the coach through CoachProfile.userId. Credit is computed only from a CAPTURED BookingPayment (credit debited + Stripe charged); otherwise FULL_CREDIT issues nothing and logs a warning. The coach's payout share of a partial refund is proportional. Dismissal is audited as DISPUTE_DISMISS (V183; before that it was logged as DISPUTE_RESOLVE, so older dismissal rows still carry that type — the dispute's own status tells them apart). Both outcomes notify the raiser (DISPUTE_RESOLVED / DISPUTE_DISMISSED; a minor player raiser's parent instead), and a COACH_WARNING resolution notifies the coach (COACH_WARNING_ISSUED). While a dispute is open — or after a RESOLVED outcome other than NO_ACTION — the booking's session recap is locked (DisputeRepository.existsRecapLockingDispute, exposed to booking via DisputeRecapLockLookup).

  Api->>Svc: submit: owner (else 404), still enforced, within 14 days
  Svc->>Svc: saveAndFlush (unique index loser gets 409)
  Admin->>Svc: POST /api/admin/appeals/{appealId}/decide {outcome, note}
  Svc->>Svc: decideIfOpen conditional UPDATE (0 rows gets 409)
  alt OVERTURNED
    Svc->>Enforce: deleteStrike / reinstateCoach / approveReview (same TX)
    Svc->>Svc: markReversalApplied(true or false)
  end
  Svc->>Svc: AdminActionLog(APPEAL_UPHOLD or APPEAL_OVERTURN)

    Overturning applies the reversal only if the appealed enforcement still stands: a strike already deleted, a coach since reinstated and re-suspended (different statusChangedAt), or a review no longer BLOCKED records reversalApplied = false. Suspension and review reversals take the row lock (findByIdForUpdate / findByIdForUpdateNoWait) before checking, so a concurrent edit cannot slip between the check and the reversal. DISPUTE_RESOLUTION appeals never reverse money automatically — the admin corrects it by hand. A reversal failure rolls back the decision too. Every decision is written to admin_action_log as APPEAL_UPHOLD / APPEAL_OVERTURN (V183, reference = appeal id, reason = subject + reversal outcome + note, capped at 500 chars); the reversal's own actions are logged by the services that perform them, and a reinstated coach / approved review notifies its owner.

    GDPR erasure (self or child)

    sequenceDiagram

  participant GdprApi as GdprResource
  participant ReqSvc as GdprRequestService
  participant EventListener as GdprEventListener
  participant EraseSvc as GdprErasureService
  participant Retry as GdprErasureRetryScheduler

  GdprApi->>ReqSvc: requestErasure / requestChildErasure
  ReqSvc->>ReqSvc: pre-checks, saveAndFlush (partial unique index loser gets 409)
  Note over ReqSvc,EventListener: event delivered AFTER_COMMIT, on the request thread
  EventListener->>EraseSvc: erase(requestId, userId) or eraseChild(requestId, parentId, playerId)
  EraseSvc->>EraseSvc: pool pre-check, route to GDPR datasource, REQUIRES_NEW
  EraseSvc->>EraseSvc: scrub, a contended scrub raises GDPR_ERASURE_DEADLINE alert
  EraseSvc->>EraseSvc: COMPLETED, or FAILED if any scrub was skipped
  EraseSvc-->>User: UserErasedEvent, AccountDeletionRequestedEvent (self only)
  Retry->>EraseSvc: daily 06:00 retryFailedErasures (FAILED, older than 1h, retry_count below 3)

    Self erasure is refused while a self-scoped export or erasure is active, or while a coach has REQUESTED/ACCEPTED bookings. Child erasure is refused while the child has any live booking (GdprRequestService.CHILD_ERASURE_BLOCKING_BOOKING_STATUSES), an active export, or is already erased (developmentDataErasedAt set). The child check and the request insert run under the child's player_profiles row lock, which every booking-creation path also takes before refusing a child with an in-flight (PENDING/PROCESSING/FAILED) erasure request (booking.playerNotBookable), so a new booking and a child-erasure request cannot both succeed. Self erasure anonymises the user (deleted.<id>@erased.io), hard-deletes messages, deletes or anonymises reviews (APPROVED ones are anonymised so ratings survive), revokes refresh tokens and deletes prior export blobs; a COACH additionally has profile free text, gallery media, recap narrative (session completion data, timeline metadata, performance report next_steps — scrubbed, not deleted) and availability-block reasons scrubbed; a PARENT/PLAYER has each child's development data deleted under a per-child lock budget. Child erasure runs the same per-child hook and also scrubs the profile identity, committed with the developmentDataErasedAt tombstone; bookings, payment/credit rows, messages and videos are deliberately kept.

    Conventions & Gotchas

    GDPR work runs synchronously on the HTTP request thread. GdprEventListener is a plain (non-@Async) @TransactionalEventListener(phase = AFTER_COMMIT), so the export build or erasure is added to the response time of the POST. That is why erasure has a gdprEraseLockBudget, a Hikari pre-check (assertConnectionPoolNotSaturated) and its own routed connection pool (RoutingDataSourceContext.set(GDPR_ERASURE_DATASOURCE_KEY), always cleared in finally). The listener must never be @Transactional; the services open their own REQUIRES_NEW transactions via self proxies.

    A failed erasure is FAILED, never silently COMPLETED. Any skipped or contended scrub marks the request FAILED and raises a GDPR_ERASURE_DEADLINE alert (one per distinct reason). If erase() throws, markFailed commits the FAILED status in one REQUIRES_NEW transaction and then raises the alert in another — a duplicate-alert race must not roll back the status. retryFailedErasures bumps retry_count in its own transaction before each attempt so the 3-attempt cap survives a failing re-drive.

    A child-scoped GDPR request's user_id is the parent. Always branch on playerId: routing a child request to erase() would anonymise the parent's own account. Self-scoped lookups use the ...PlayerIdIsNull... repository methods for the same reason.

    Admin outcomes are notified through the outbox, with the recipient resolved by the publisher. Suspension (only when the admin ticks "notify coach"), reinstatement, dispute warning, dispute resolved / dismissed, GDPR export ready and review approved / blocked each publish an event carrying an AdminNotificationRecipient; notification.AdminOutcomeEmailListener enqueues the email and inbox row BEFORE_COMMIT in the decision's transaction (all eight templates are transactional, never opt-out-able). The exception is GdprExportReadyEvent: handled AFTER_COMMIT in its own transaction, so a failed notice can never roll the export back to PENDING. DisputeResolvedEvent carries the amount actually credited (zero for a FULL_CREDIT on a zero-price booking), not the requested outcome. Resolve recipients with AdminNotificationRecipientResolver: a coach by CoachProfile.userId, a user id directly, a minor player with a linked parent redirected to the parent (GDPR export is the exception — it goes to the requester, whose profile page holds the download). The signed export URL is never emailed. A null recipient skips the email with a WARN.

    Alert inserts are isolated on purpose. AdminAlertEventListener.insertAlert runs saveAndFlush inside a REQUIRES_NEW TransactionTemplate and catches DataIntegrityViolationException outside the callback. Catching inside does not work: a failed flush marks the session rollback-only and the template's commit throws UnexpectedRollbackException. saveAndFlush (not save) matters because AdminAlert.alertId is GenerationType.UUID, which defers the INSERT to commit. Several handlers are additionally annotated REQUIRES_NEW because they are published from inside messaging's moderation/retention transactions and Stripe webhook handling — a failed alert must never roll back the publisher's work.

    Adding an AdminAlertType, AdminAlertReferenceType or AdminActionType needs a migration. All three columns carry CHECK constraints; JPA will happily write a value the CHECK rejects, failing at INSERT time. V152/V153 (alerts) and V162/V171 (action log) are the worked examples — drop and recreate the constraint with SET LOCAL lock_timeout. New alert types also need a summary case in AdminQueueService and a count in the queue summary.

    Queues expose OPEN only. /api/admin/queue and /api/admin/disputes/queue return 400 for any status other than OPEN; the appeals queue accepts any AppealStatus. Alerts are deduplicated per (reference_id, type) while OPEN.

    Strike deletion can re-tier a coach. For a PENDING_REVIEW/REDUCED coach and an in-window strike, deleteStrike recounts under the coach row lock: still at or above the suspension threshold leaves the status; at or above visibility sets REDUCED; below both runs activation validation and returns the coach to ACTIVE (resolving the STRIKE_THRESHOLD alert and auditing COACH_REINSTATE). The delete is a bulk deleteByIdAndCoachId (0 rows → 404 for the losing concurrent caller). ConfigStartupAssertion refuses to boot if visibilityThreshold > suspensionThreshold.

    Enforcement reads are REPEATABLE_READ. getEnforcementProfile and getCoachesUnderEnforcement read status and strike counts in one snapshot. Spring silently ignores the isolation if an outer transaction is already open — do not call them from inside a test-level @Transactional/TransactionTemplate.

    Verification tier is written by bulk UPDATE. CoachProfile.verificationTier is updatable = false so an unlocked coach-side save can never write a stale tier back; setVerificationTier uses CoachProfileRepository.updateVerificationTier under the row lock.

    Two classes are called PlatformConfig. admin.config.PlatformConfig is a Spring @Configuration; config.repo.PlatformConfig is the main.platform_config entity. Check the import.

    ReviewModerationLog lives in the reviews schema even though the entity is in admin.repo.
