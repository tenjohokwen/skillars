Admin

Admin-only tooling for trust & safety moderation, coach enforcement, dispute resolution, and GDPR data-subject requests.

Business Overview

Skillars is a two-sided marketplace connecting minors (Players), their Parents, and Coaches, so the platform needs a back office that lets Admins keep the marketplace safe and legally compliant without touching the consumer-facing apps. The admin module is that back office. It is the only module in the codebase whose endpoints are almost entirely gated behind SecurityConstants.HAS_ADMIN_ROLE — everything here is a tool for internal staff, surfaced through a separate admin console.

The module solves four related problems:

Moderation queue Coach enforcement Dispute resolution GDPR requests

1. Unified moderation queue. Reported messages, reported conversations, flagged reviews, coach strike thresholds, and raised disputes all originate in other modules (messaging, reviews, payment, admin itself). Rather than making admins hunt across five different screens, AdminAlertEventListener listens for the domain events those modules publish and inserts a single AdminAlert row per incident. AdminQueueService then serves one paginated, filterable "queue" backed by that table. Only status=OPEN alerts are currently exposed — the API rejects any other status filter.

2. Coach enforcement. Coaches accumulate reliability strikes (no-shows, unexcused cancellations) from the payment module's ReliabilityStrikeService. When a coach crosses the visibility threshold (default 3 strikes / 30 days) their profile is downgraded; crossing the suspension threshold (default 5 strikes / 30 days, enforced upstream in payment) triggers a StrikeThresholdReachedEvent that lands in the admin queue. From there an admin can inspect the coach's strike and cancellation history, suspend the coach (auto-cancelling their pending bookings and publishing refund-triggering events), reinstate them, or manually issue/void a strike.

3. Dispute resolution. A Parent or Player can raise a dispute against a completed/cancelled booking (e.g. coach no-show, safety concern) within a configurable submission window (default 14 days, disputes.submissionWindowDays). An admin reviews the dispute alongside the booking's payment breakdown and the coach's cancellation history, then resolves it with one of four outcomes — full credit, partial credit, no action, or a formal coach warning — or dismisses it outright.

GDPR is a legal deadline, not a nice-to-have. GdprRequestService lets any authenticated user request an export or erasure of their personal data (GDPR Articles 15 & 17). Erasure hard-deletes messages, deletes/anonymises reviews, cascades through every development-tracking table (SLU snapshots, radar assessments, performance reports, timelines, homework), revokes all refresh tokens, and anonymises the core user record. Exports are built as a signed, time-limited ZIP download. Both are processed asynchronously after the request is accepted — get the async wiring wrong and you silently miss the regulatory deadline.

This module leans heavily on other platform modules: security for the current principal, role checks, and the user/player/refresh-token data erasure touches; booking for the bookings being disputed or auto-cancelled; marketplace for coach profiles, pricing, and reliability strikes; payment for the reliability-strike engine, credit-wallet refunds, and cancellation history; messaging and reviews for the content actually being moderated; development and session purely as GDPR-erasure cascade targets; filestorage for storing/deleting the GDPR export ZIP; and config for every tunable threshold and window used here. From infrastructure it only uses the shared security constants/errors, the generic exception types, and feature flag properties — it does not talk to blob storage directly, going through filestorage instead.

Key Flows

Coach enforcement: strike threshold to suspension

sequenceDiagram
  participant Payment as payment.ReliabilityStrikeService
  participant Listener as AdminAlertEventListener
  participant Alerts as AdminAlert (DB)
  participant Admin as Admin (console)
  participant Enforce as AdminCoachEnforcementService
  participant Booking as booking.BookingRepository
  Payment->>Listener: StrikeThresholdReachedEvent(coachId)
  Listener->>Alerts: insert STRIKE_THRESHOLD alert (dedup on OPEN)
  Admin->>Enforce: GET /api/admin/coaches/{coachId}/enforcement
  Enforce-->>Admin: profile + strike history + cancellation history
  Admin->>Enforce: POST /api/admin/coaches/{coachId}/suspend
  Enforce->>Booking: findByCoachIdAndStatus(REQUESTED)
  Enforce->>Booking: cancel each pending booking
  Enforce-->>Payment: publish BookingCancelledByAdminEvent (per booking)
  Enforce-->>Admin: publish CoachSuspendedEvent, CoachSuspensionNotificationEvent
  Enforce->>Alerts: write AdminActionLog(COACH_SUSPEND)

A coach who racks up unexcused cancellations or no-shows accumulates reliability strikes in the payment module. Once the configured threshold is crossed, StrikeThresholdReachedEvent lands the coach in the moderation queue as a deduplicated AdminAlert. An admin opens the coach's enforcement profile to review strike and cancellation history, then suspends the coach. Suspension is not just a status flip: every pending (REQUESTED) booking for that coach is cancelled server-side and a BookingCancelledByAdminEvent is published per booking so the payment module can refund the parent. Every action — suspend, reinstate, manual strike, strike deletion — is written to AdminActionLog for audit purposes.

Dispute resolution

sequenceDiagram
  participant Parent as Parent/Player
  participant DisputeApi as DisputeResource
  participant DisputeSvc as DisputeService
  participant Listener as AdminAlertEventListener
  participant Admin as Admin (console)
  participant Wallet as payment.CreditWalletService
  Parent->>DisputeApi: POST /api/disputes {bookingId, reason, details}
  DisputeApi->>DisputeSvc: raiseDispute(...)
  DisputeSvc->>DisputeSvc: check eligible status + owner + submission window
  DisputeSvc-->>Listener: publish DisputeRaisedEvent
  Listener->>Listener: insert DISPUTE_RAISED alert
  Admin->>DisputeSvc: GET /api/admin/disputes/{disputeId}
  DisputeSvc-->>Admin: booking + payment split + coach cancellation history
  Admin->>DisputeSvc: POST /api/admin/disputes/{disputeId}/resolve {resolution, creditAmount}
  DisputeSvc->>Wallet: writeLedgerEntry(BOOKING_REFUND) (if credit resolution)
  DisputeSvc-->>Admin: publish DisputeResolvedEvent (+ CoachWarningIssuedEvent if COACH_WARNING)

A Parent or Player can dispute a booking only if it is in an eligible terminal status (completed, cancelled, or no-show) and only within the configurable submission window (default 14 days). Raising a dispute both creates a Dispute row and publishes DisputeRaisedEvent, which the same alert listener used for coach enforcement turns into a queue entry. An admin resolves the dispute with one of four outcomes: FULL_CREDIT and PARTIAL_CREDIT write a refund ledger entry via CreditWalletService, NO_ACTION does nothing financially, and COACH_WARNING optionally issues a partial credit alongside a formal warning event to the coach. Disputes are optimistically locked and can only be resolved or dismissed once.

GDPR erasure request

sequenceDiagram
  participant User as Authenticated user
  participant GdprApi as GdprResource
  participant ReqSvc as GdprRequestService
  participant EventListener as GdprEventListener
  participant EraseSvc as GdprErasureService
  User->>GdprApi: POST /api/gdpr/erasure
  GdprApi->>ReqSvc: requestErasure(userId)
  ReqSvc->>ReqSvc: reject if pending export/erasure or active coach bookings
  ReqSvc-->>GdprApi: GdprRequest(PENDING) + GdprErasureRequestedEvent
  Note over ReqSvc,EventListener: event delivered AFTER_COMMIT
  EventListener->>EraseSvc: erase(requestId, userId)
  EraseSvc->>EraseSvc: anonymise user, hard-delete messages
  EraseSvc->>EraseSvc: delete/anonymise reviews, cascade development data
  EraseSvc->>EraseSvc: revoke refresh tokens, mark request COMPLETED
  EraseSvc-->>User: publish UserErasedEvent, AccountDeletionRequestedEvent

Erasure requests are validated before acceptance — you cannot request erasure while an export is mid-flight, and a coach with active (REQUESTED/ACCEPTED) bookings cannot be erased outright. Once accepted, the actual erasure runs in its own REQUIRES_NEW transaction, triggered only after the request record commits, so a crash mid-erasure cannot silently leave the request stuck at PENDING — the listener catches the failure and marks the request FAILED in a fresh transaction. Erasure is deliberately asymmetric: messages are hard-deleted (satisfying Article 17), but already-APPROVED reviews are anonymised rather than deleted so aggregate coach ratings stay intact.

Conventions & Gotchas

GDPR export links expire. GdprExportService signs the download URL for a configurable window (default 48h, gdpr.export.urlExpiryHours). GdprRequestService returns HTTP 410 Gone once expiresAt has passed, and GdprErasureService deletes any previously completed export ZIPs from storage as part of erasure. Do not assume a download URL from an old AdminGdprRequestDto is still valid.

GDPR event listeners must never be @Transactional. GdprEventListener uses @TransactionalEventListener(phase = AFTER_COMMIT) precisely because no surrounding transaction exists at that point — the erasure/export services open their own transactions. If erase() throws, the listener calls markFailed() in a brand-new REQUIRES_NEW transaction so the FAILED status is durable even though the erasure transaction rolled back.

The moderation queue only shows OPEN alerts. AdminModerationResource.getQueue returns HTTP 400 for any status other than OPEN — there is no "resolved" queue view yet. Alerts are deduplicated per (referenceId, type, OPEN); re-reporting an already-open message does not create a second alert, and a DataIntegrityViolationException from a concurrent insert race is swallowed intentionally.

Two alert handlers run REQUIRES_NEW, and that is load-bearing. onMessageHeldForReview and onMessagesPurged get their own transaction because they are published from inside messaging's ModerationResultApplier, MessageModerationSweeper, and MessageRetentionScheduler. Sharing the publisher's transaction would let a failed alert insert roll back the moderation verdict itself and return the message to PENDING — exactly the stranding those classes exist to fix. Both publishers catch and log around publishEvent, which is where the separate transaction commits or fails.

Note a try/catch inside the handler body would not achieve this: AdminAlert.alertId is GenerationType.UUID, so the INSERT is deferred to flush at commit — after the method body has already returned.

Adding an AdminAlertType needs a migration, not just an enum constant. admin.admin_alerts.type carries a CHECK constraint listing every valid value. The JPA side is @Enumerated(EnumType.STRING) and will happily write a value the CHECK rejects, so a forgotten migration fails at INSERT time rather than at startup. V91 is the worked example — it drops and recreates admin_alerts_type_check to admit MODERATION_UNRESOLVED.

Strike deletion can silently reinstate a coach. deleteStrike recomputes the coach's active-strike count after deletion; if it drops back under the visibility threshold and the coach is currently PENDING_REVIEW or REDUCED, the coach is automatically flipped back to ACTIVE and the open STRIKE_THRESHOLD alert is resolved as a side effect — this is not a separate "reinstate" call.

ReviewModerationLog lives in the wrong schema on purpose. It is defined in admin.repo alongside the other audit entities, but is mapped to @Table(schema = "reviews") because it is conceptually part of the reviews domain. Don't be surprised when it doesn't show up under the admin schema in the database.
