    Anatomy of a Request

    One real user action traced end to end, with a file:line pointer at every hop: a parent requests a session with a coach, and the coach accepts it. Read this once and you know where to look for almost any other request.

    Path conventions. Frontend paths are relative to the repo root. Java paths omit the common prefix src/main/java/com/softropic/skillars/, so platform/booking/service/BookingService.java:367 means src/main/java/com/softropic/skillars/platform/booking/service/BookingService.java, line 367. Line numbers are from master as of this page; if one has drifted, search for the method name.

    Part 1 — the parent requests a session

    1. The page

    The route parent/coaches/:coachId/request-booking (src/frontend/src/router/routes.js:151-158, meta.roles: ['PARENT', 'PLAYER'] — the first dual-role route) renders src/frontend/src/pages/parent/BookingRequestPage.vue. The confirm button (:156-164) calls submit() (:591), which posts the slot chosen from the availability calendar plus the store's availabilitySignature (the stale-view guard), an optional sessionPackPurchaseId and notes. On success it navigates to /parent/bookings (:668).

    The error toast is chosen from err.response.data.errorMsg.errorKey (:607-664), one if branch per wire code. A new backend error code is invisible to the user until you add a branch here — it falls through to the generic booking.requests.submitError toast and a console.warn. Per the comment at :608-612, the i18n key lives under the wire code's namespace (payment.* codes resolve under payment.* even on this booking page).

    2. Store and API module

    src/frontend/src/stores/booking.store.js:494 submitBookingRequest calls createBookingRequest and then reloads the parent's list (loadParentBookings, :359). src/frontend/src/api/booking.api.js:21 is a one-liner: api.post('/api/bookings/requests', request). API modules contain no logic — they only bind URLs to the shared axios instance.

    3. The axios boot file

    src/frontend/src/boot/axios.js builds the single instance (:94-97): empty baseURL (the Quasar dev server proxies /api to localhost:9990, src/frontend/quasar.config.js:111-114) and withCredentials: true.

    • No Authorization header. Auth is entirely cookie-based: the browser sends the HttpOnly JWT cookie potc (SecurityConstants.JWT_COOKIE_NAME) and friends automatically. The request interceptor (:100-127) only adds Accept-Language (backend error messages are localised from it) and records activity for the idle-session monitor.
    • The response interceptor unwraps response.data (:142), so callers receive the body, not the axios response. Errors are rejected with the original axios error (:251), which is why pages read err.response.data.errorMsg.errorKey.
    • On 401 with security.sessionExpired/security.unauthorized it tears down the session and redirects to /#/login (:163-224); 403 and 5xx are only logged (:227-241) — the page decides what the user sees.

    4. Security filter chain

    The chain is assembled in platform/security/config/SecurityConfiguration.java:118-184. CSRF is disabled (:137); the custom filters are JWTAuthorizationFilter (every secured request), SecurityAdviceFilter, LoggingFilter and SessionRefreshFilter. There is no login filter: the only password login is the controller POST /api/auth/login (the legacy /authenticate → /otp filters and Spring's form login were removed).

    platform/security/infrastructure/jwt/filter/JWTAuthorizationFilter.java:

    • doFilterInternal (:142) skips unrestricted endpoints, otherwise calls attemptAuthorization (:193).
    • Fast path (:221-247): the principal comes straight from the JWT claims — no DB read — and URL-level authorities are checked; extendTtlOfToken re-issues the 15-minute cookies (sliding window).
    • DB path (:205-220): once the token's embedded DB-refresh stamp is older than DB_REFRESH_TOKEN_INTERVAL (5 min), daoAuthProvider.authorize reloads the user (catching locked/disabled accounts) and assertSessionNotRevoked (:258-268) rejects a JWT issued before the account's securitySessionInvalidatedAt (refresh-token-theft revocation).
    • Any auth failure is written as a 401 ErrorDto directly by the filter (:148-179) — it never reaches a controller or ApiAdvice.

    Locking an account is not instant. Between DB re-auth cycles the filter trusts the JWT, so a just-locked or just-erased account keeps working for up to 5 minutes. See Security for the full cookie set (potc, rtkn, skp, rint, bcookie).

    5. Controller

    platform/booking/api/BookingResource.java:36-41: @PreAuthorize(SecurityConstants.HAS_PARENT_OR_PLAYER_ROLE) and @RequestBody @Valid CreateBookingRequest. The caller id comes from securityUtil.requireCurrentUserId() (:101) — never from the body. Returns 201. The same resource also carries the parent-side PUT /{id}/confirm (confirm a coach-proposed booking, :82-87) and PUT /{id}/withdraw (:93-98).

    platform/booking/contract/CreateBookingRequest.java is a record with Bean Validation: @NotNull ids, @Future start, @Size(max = 500) notes, and an @AssertTrue isEndAfterStart() so a reversed range is a 400 before the service runs.

    Controllers are thin by convention. Ownership (does this parent own this player profile? this pack?) is checked in the service, not with @PreAuthorize SpEL. The role annotation only answers "may this kind of user call this endpoint at all".

    6. Service transaction

    platform/booking/service/BookingService.java:367 createBookingRequest is one @Transactional method. In order:

    1. Cheap checks first, unlocked (:368-415): player ownership (parent via player.parentId, adult player via player.userId), an unlocked fast-fail on the player's erasure tombstone (requireNotErased), coach status (requireBookableCoachStatus, :551), Stripe-readiness (requireCoachPaymentReady, :563-567 — throws PaymentGatewayException("payment.coachStripeNotConfigured")), future start, end after start, and exact session length (SessionDurationResolver).
    2. Lock the coach row (:427-436): lockRetryer.withBoundedRetry(...) around coachProfileRepository.findByIdForUpdate, followed by entityManager.refresh(c, PESSIMISTIC_WRITE). The coach profile row is the per-coach mutex that serialises every slot-changing write. Then, under that lock (:437-439): the coach status is re-checked; requirePlayerBookableUnderLock (:608) takes the player_profiles row lock and refuses an erased player or one with a child-erasure request in flight (booking.playerNotBookable); and requireRequestQuota (:954) refuses a start beyond booking.request.maxHorizonDays (default 120, booking.beyondBookingHorizon) or a parent who already has booking.request.maxPendingPerCoach (default 10) requests awaiting this coach (booking.tooManyPendingRequests). Lock order is coach row, then player row.
    3. Availability (:441-462): windows read after the lock, signature compared, slot must fit a window in the coach's timezone and not hit a blackout block.
    4. Overlap (:464, requireNoOverlappingBooking at :575-584): findOverlappingBookings against ACTIVE_SLOT_STATUSES (includes REQUESTED).
    5. Pack validation if a pack was chosen (:467-510) — ownership deliberately first so the error can't be used as an oracle; then same player, not expired, not paused (now or at the session start), not dispute-frozen, same coach, sessions left.
    6. Insert (:514-534): notes sanitised by ContactDetailSanitizer. A card/credit booking gets its agreed_price locked from the coach's current price, read under the coach lock (requireRequestTimePrice, :770); a coach with no pricing is refused with booking.coachPricingUnavailable. A pack booking keeps the pack's own price. Status defaults to REQUESTED in Booking.onCreate (platform/booking/repo/Booking.java:179-182). Creation does not go through transition().
    7. Publish BookingRequestedEvent (:537) — still inside the transaction.

    The refresh after findByIdForUpdate is required, not defensive. The coach was already loaded unlocked a few lines earlier; the locked read returns that managed instance without overwriting its fields, so without the refresh the "re-check status under lock" would re-read the stale value (comment at :430-433). Copy this pattern whenever you lock an entity you have already loaded.

    7. Locking: NOWAIT + bounded retry

    platform/marketplace/repo/CoachProfileRepository.java:54-56: findByIdForUpdate is a default method that first takes the lock with the scalar query lockByIdForUpdate (:58-62, SELECT c.id with @Lock(PESSIMISTIC_WRITE) and jakarta.persistence.lock.timeout = 0) and only then reads the entity with findById. Locking an id projection instead of the entity keeps Hibernate from "upgrading" an already-managed @Version instance and throwing StaleObjectStateException (comment at :45-53). Timeout 0 means FOR UPDATE NOWAIT: if another transaction holds the row, Postgres fails immediately with 55P03. infrastructure/persistence/PessimisticLockRetryer.java:150 withBoundedRetry catches that, rolls back to a JDBC savepoint it took before the attempt (:157-159, :175), sleeps with jittered backoff and tries again — 8 attempts, 100 ms growing ×1.6 to 800 ms, ~3.2 s worst case (app.locking.retry.*, :89-99). After the last attempt the PessimisticLockingFailureException escapes and becomes a 409 (see Error paths).

    Only reads go inside the retried lambda. The savepoint rollback discards whatever the lambda did. The retryer also flushes before each savepoint and holds the pooled connection while sleeping. PessimisticLockRetryerCallSiteAuditTest pins the number of call sites (EXPECTED_CALL_SITE_COUNT, currently 64), so adding one means updating that test. Why NOWAIT at all: see Decisions.

    8. Repository and SQL

    platform/booking/repo/BookingRepository.java:24-37 findOverlappingBookings is plain JPQL (half-open interval test, optional self-exclusion) — unlocked, because the coach-row lock already serialises writers. The DB backstop is the exclusion constraint excl_bkg_coach_slot_overlap (src/main/resources/db/migration/V138__baseline_schema.sql:2188): a GiST tstzrange overlap per coach_id, but only for ACCEPTED through PAUSED — two overlapping REQUESTED rows are legal in the database and kept apart only by the app check. Tables live in the booking schema; see Database.

    9. Events and listeners

    Spring's ApplicationEventPublisher is the module bus. For BookingRequestedEvent exactly one listener runs: platform/notification/infrastructure/listener/BookingEmailListener.java:64 onBookingRequested, @TransactionalEventListener(BEFORE_COMMIT). It builds the template data and calls NotificationOutboxSupport.enqueueEmail.

    PhaseRunsUse it for
    BEFORE_COMMITInside the producer's transaction, just before commit. A throw rolls the business change back.Writing outbox rows and inbox rows atomically with the business change.
    AFTER_COMMITAfter commit, synchronously on the same thread (unless @Async). A throw is only logged — the request already succeeded.Reactors that need committed data: payment settlement, SSE push, batch roll-up, the outbox drain trigger.

    The try/catch in the listener does not make an enqueue failure harmless. enqueueEmail is @Transactional(propagation = MANDATORY); if it throws, Spring marks the shared transaction rollback-only even though the listener catches, and the booking insert rolls back (UnexpectedRollbackException). That is intended: no booking without its email. See Outbox.

    10. Outbox row and inbox row

    platform/notification/service/NotificationOutboxSupport.java:133-150:

    • outboxService.enqueue("NOTIFICATION_EMAIL", json) — a plain insert into main.outbox_messages in the current transaction (platform/outbox/service/OutboxService.java:56).
    • outboxService.requestDrainAfterCommit() (OutboxService.java:77) — registers one drain per transaction.
    • inAppNotificationService.recordForEmail(...) (platform/notification/service/InAppNotificationService.java:80) — writes the coach's in-app inbox row if the template's catalog entry is in-app (BOOKING_REQUESTED is, recipient coach: NotificationCatalog.java:78-81). It runs in a JDBC savepoint (:93) and never throws, so a broken inbox write cannot fail the booking.

    11. Commit, then drain

    The commit makes the booking, the outbox row and the inbox row visible together. Then OutboxService.onOutboxDrainRequested (:108-110, @Async("outboxDrainPool") + AFTER_COMMIT) drains on a background thread: OutboxRowProcessor.claimAndHandle (platform/outbox/service/OutboxRowProcessor.java:101-121, REQUIRES_NEW) claims one row with FOR UPDATE SKIP LOCKED, calls the handler and deletes the row. If the JVM dies first, the 5-minute sweep() picks it up.

    In tests the drain is synchronous (app.outbox.drain-async: false in application-test.yaml), so an IT can assert on the email right after the call. In dev it is async — the file in target/mails appears a moment after the HTTP response.

    12. Email transport

    platform/notification/service/NotificationEmailOutboxHandler.java:59 deserialises the payload and calls MailManager.sendEmailSync (platform/notification/service/MailManager.java:102, its own REQUIRES_NEW + per-sendId advisory lock for de-duplication), which renders the Thymeleaf template and calls MailService.sendEmailFromTemplate → outboundEmailSender.send(request) (MailService.java:126). The OutboundEmailSender bean is chosen by app.email.transport:

    ValueBeanProfile
    loginfrastructure/email/log/LoggingEmailSender.java (also the default if unset)dev, test — logs a masked line and, with app.email.log.dump-dir: target/mails (application-dev.yaml:24), writes <correlationId>.html (:115-124)
    smtpinfrastructure/email/smtp/SmtpEmailSender.javauat
    sesinfrastructure/ses/SesEmailSender.javaprod

    The handler throws only for a retryable failure, which leaves the outbox row to be retried with backoff.

    13. How the coach finds out

    There is no push to the coach for a new request. createBookingRequest publishes no BookingStatusChangedEvent, and BookingSseService streams are per existing booking id, opened by a page that already shows that booking. Nor is there a user-level push channel: src/frontend/src/components/notification/NotificationBell.vue:68-70 says so explicitly. The coach sees the request through (a) the email, (b) the bell's unread count, refreshed on mount, on every route change and on window focus (:88-101), and (c) the inbox list on coach/booking-requests (GET /api/bookings/requests/coach).

    Part 2 — the coach accepts

    Frontend

    src/frontend/src/pages/coach/CoachBookingRequestsPage.vue:181 handleAccept → bookingStore.approveBooking (booking.store.js:501) → acceptBooking (booking.api.js:26-27) — note the per-call timeout: 20000: the response is not sent until payment has settled (below). On failure the page reloads the inbox and picks a toast from the errorKey (:186-205: coachUnavailable, slotUnavailable, parentConfirmationRequired, priceNotLocked, requestExpired, else the generic booking.requests.acceptError).

    Controller and state transition

    BookingResource.java:62-69 (HAS_COACH_ROLE) calls BookingService.acceptBooking (BookingService.java:617), which:

    1. checks the caller's coach profile owns the booking (:618-625);
    2. locks the coach row exactly as in step 6 and rejects a SUSPENDED coach (:629-645);
    3. re-checks overlap against ACTIVE_SLOT_STATUSES_EXCLUDING_REQUESTED, excluding itself (:648-657) — another overlapping request may have been accepted meanwhile;
    4. for a still-REQUESTED booking, fails fast if its start time has passed (booking.requestExpired) or it has no price to charge (resolveSessionPrice, :749-761: the pack's per-session price, else the agreed_price locked at request time, else booking.priceNotLocked — there is no fallback to the coach's current price) (:661-664);
    5. calls acceptAndInitiatePayment (:705-717): locks the booking row, runs requireConsentingAcceptor (:932-945 — a coach-proposed booking can only be accepted by its parent via PUT /{id}/confirm, so a coach accept gets booking.parentConfirmationRequired), re-checks the start time under the lock, then ACCEPT silently and INITIATE_PAYMENT with a BookingStatusChangedEvent, so observers see one change: REQUESTED → PAYMENT_PENDING. Each leg goes through transitionInternal (:187-204): booking row locked (lockBookingForUpdate, NOWAIT + retry + refresh, :210-216), BookingStateMachine.validate / targetStatus (platform/booking/service/BookingStateMachine.java:105-119), actor-role check, save;
    6. publishes BookingAcceptedEvent carrying the resolved session price (:679).

    Never set booking.status directly. transition() is the only sanctioned path: it validates the transition table and the actor's role (EVENT_ROLES) and publishes the event that SSE, batch roll-up and session plans depend on. See Booking.

    Payment capture or credits

    After commit, platform/payment/service/PaymentLifecycleService.java:166-188 onBookingAccepted (AFTER_COMMIT + REQUIRES_NEW) runs synchronously on the coach's request thread:

    • a terminal payment row (duplicate delivery) → ignore; an outstanding CAPTURE_PENDING reservation → abort and escalate, never re-charge (:169-178);
    • pack-funded → PackSessionService.deductSession, then persistPaymentSuccess with zero credit and zero card (handlePackBasedBooking, :190-222);
    • otherwise handleCreditBasedBooking (:224-283):
      • the wallet balance is read, and when it is positive re-read under the payer's wallet lock (walletBalanceForSettlement, :156-162, CreditWalletService.lockAndGetBalance), held until the deduction commits so a concurrent cash-out cannot spend the same credit;
      • CreditCardSplit.of(balance, price, minimumCardCharge) uses as much credit as covers the price and charges the rest; a card part below Stripe's minimum is re-balanced to the minimum instead of being declined. The balance counts both wallet pools: spend-only credit (refunds that may be spent but never cashed out) pays for bookings exactly like cashable credit;
      • credit covers everything → persistPaymentSuccess directly, nothing reaches Stripe and no reservation row is written (:278-282);
      • a card share → reserveCapture writes a CAPTURE_PENDING row on the dedicated payment pool, carrying the charge's idempotency key pi-booking-<bookingId> (ChargeKeys.forBooking), before calling Stripe (BookingPaymentPersistenceService.java:130-178); then StripePaymentGateway.chargeAndCapture (platform/payment/service/StripePaymentGateway.java:100) charges the platform account under that key (no destination charge — the coach is paid only after completion);
      • a decline → persistPaymentFailure; a timeout, 5xx or idempotency conflict raises ChargeOutcomeUnknownException and the booking is not declined: the reservation stays CAPTURE_PENDING and ChargeOutcomeReconciler later asks Stripe for the PaymentIntent by its key and settles or declines (:261-265);
      • after a successful charge the PaymentIntent id is stamped on the reservation and the settle runs in its own transaction (settleChargedBookingOrCompensate, :295-314). If that settle fails, the booking is declined and the card share is returned as wallet credit (declineBookingAfterCharge); if that fails too, the reservation is left for the reconciler.
    • persistPaymentSuccess (BookingPaymentPersistenceService.java:323-354) debits the wallet (spend-only pool first, CreditWalletService.debitForBooking), writes the CAPTURED payment row (locking the commission rate), transitions PAYMENT_CAPTURED → CONFIRMED and publishes BookingConfirmedEvent; failure → PAYMENT_FAILED → DECLINED + BookingDeclinedEvent (persistPaymentFailureTransactional, :373-390).

    That is why BookingResource.acceptBooking re-fetches the booking before responding (:66-68): by then it is normally CONFIRMED or DECLINED, and stays PAYMENT_PENDING only while a charge outcome is unknown. A crash between the accept commit and settlement leaves PAYMENT_PENDING: with no payment row, payment.PaymentPendingSweeper declines it (no money moved); with a keyed CAPTURE_PENDING row, ChargeOutcomeReconciler resolves it. Details: Payment.

    Notifications and live updates

    • BookingEmailListener.onBookingConfirmed (:90, BEFORE_COMMIT) enqueues BOOKING_CONFIRMED to the parent plus a parent inbox row — the same outbox path as Part 1. There is no email at the accept step itself.
    • platform/booking/service/BookingSseService.java:58-73 pushes each committed BookingStatusChangedEvent to subscribers of that booking id. The parent's ParentBookingsPage.vue:262 renders BookingStateChip with a booking id; for a non-terminal status the chip opens useBookingSse (src/frontend/src/stores/booking.store.js:60-147, EventSource /api/bookings/{id}/events, endpoint BookingEventResource.java:48-61), so the parent's chip flips to PAYMENT_PENDING and then CONFIRMED without a reload.
    • The coach's payout is not touched here: it is enqueued on BookingCompletedEvent with a hold window (CoachPayoutEnqueueListener, outbox COACH_PAYOUT_TRANSFER).

    SSE is node-local and per row. The emitter registry is an in-memory map, so a client only hears about transitions committed on the instance it is connected to; the client falls back to reconnect-with-backoff and then polling (booking.store.js:91-101). Each non-terminal chip on a list opens its own EventSource.

    Error paths

    All controller exceptions are mapped by platform/security/api/ApiAdvice.java (plus the package-scoped platform/booking/api/BookingApiAdvice.java) into an ErrorDto: { helpCode, errorMsg: { errorKey, message } }, with message localised from Accept-Language. The frontend switches on errorKey; quote the helpCode when searching logs.

    Business-rule violations are 403, not 409/422. OperationNotAllowedException extends AuthorizationException, so every "slot unavailable" is a 403 that axios logs as [403 Forbidden] and that also publishes a SecurityAlertEvent (ApiAdvice.java:697-701). Don't build frontend logic on the status code — switch on errorKey.

    Errors after commit are invisible to the caller. An exception in an AFTER_COMMIT listener (payment settlement, SSE) is logged and swallowed; the HTTP response is still 2xx. That is why payment records failures as data (CHARGE_FAILED row + DECLINED, or a CAPTURE_PENDING reservation left for ChargeOutcomeReconciler when the charge outcome is unknown) and why durable side effects go through the outbox instead.
