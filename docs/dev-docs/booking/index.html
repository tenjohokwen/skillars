Booking

Turns a marketplace browse into a scheduled, paid, delivered coaching session — and manages everything that can happen to it in between.

Business Overview

The booking module is the transactional heart of Skillars: it owns the full lifecycle of a coaching session from the moment a parent requests a time slot to the moment the session is marked complete (or cancelled, disputed, refunded). Every other module that cares about "did this session happen" — payments, reviews, video access, player development timelines, coach reliability scoring — reacts to events this module publishes rather than owning booking state itself.

Parent is the primary actor: parents request sessions for their player(s), pay for them (directly via Stripe or by drawing down a pre-purchased session pack / platform credit wallet), cancel, request reschedules, and confirm session completion. Coach declares weekly availability and one-off blackout blocks, accepts or declines requests, runs the live session (start/pause/resume/end), and submits a wrap-up. Because players are frequently minors, the player never books directly — the parent account is always the actor of record, and coaches interact with the parent, not the child. System (schedulers) auto-expires stale requests, sends reminders, force-completes abandoned "quick complete" sessions, and expires session packs.

Key business rules enforced in this module (see BookingService, SessionPackService, BookingStateMachine):

  • Availability-gated booking: a request is only accepted if the requested time falls inside one of the coach's declared CoachAvailabilityWindows and doesn't fall inside a CoachAvailabilityBlock (blackout).
  • Coach must be booking-ready: the coach profile must not be SUSPENDED, and the coach must have a fully configured Stripe destination account (paymentGateway.isCoachPaymentReady) before a request can even be created.
  • Cancellation refund windows (parent-initiated): more than 24h before the session → FULL refund eligibility; 6–24h → PARTIAL; under 6h → NONE. A coach-initiated cancellation is always FULL. A coach no-show reported by the parent is always FULL. A player no-show reported by the coach is always NONE.
  • Reschedule limits: only bookings in CONFIRMED or UPCOMING status can be rescheduled, only one pending reschedule request is allowed per booking at a time, and the proposed time must be in the future.
  • Batch bookings: a parent can request up to a configured maximum number of slots (booking.batch.maxSize) against one coach in a single submission; the coach can accept the whole batch in one action, and the batch's aggregate status (PENDING / PARTIALLY_ACCEPTED / FULLY_ACCEPTED / DECLINED) rolls up automatically as individual bookings change status.
  • Session packs are single-use credits, not cash: a pack purchase gives the player a number of session credits against a specific coach, with a tiered expiry window (longer packs get longer expiry). A pack can be paused exactly once per its lifetime, which pushes out its expiry by the pause length and requires resolving any bookings that fall inside the pause window (cancel-and-confirm flow).
  • Session completion has two paths: "Quick Complete" (mode LIVE) finalizes the session immediately when the coach submits the wrap-up and deducts a credit right away; the standard path puts the booking in COMPLETED_PENDING_CONFIRMATION and waits for the parent to confirm — if the parent never responds, a scheduler auto-confirms after a configurable timeout.
  • Stale requests self-clean: a REQUESTED booking the coach never actions is automatically declined after a configurable number of hours (default 48h).

Domain events

Booking publishes on Spring's ApplicationEventPublisher; most listeners (payment, notification) subscribe via @TransactionalEventListener(phase = AFTER_COMMIT) so they only fire once the booking row is durably committed.

BookingRequestedEvent BookingAcceptedEvent BookingDeclinedEvent BookingStatusChangedEvent BookingCancelledByParentEvent BookingCancelledByCoachEvent BookingCancelledDueToPauseEvent PlayerNoShowEvent CoachNoShowEvent CoachReliabilityStrikeQueuedEvent BookingExpiredEvent BookingReminderEvent BookingCompletedEvent QuickCompleteConfirmationRequiredEvent RescheduleRequestedEvent RescheduleAcceptedEvent RescheduleDeclinedEvent DuplicateBookingProposedEvent BatchBookingRequestedEvent BatchBookingAcceptedEvent PackPausedEvent SessionPackExhaustedEvent SessionPackExpiredEvent SessionPackExpiryWarningEvent

The module consumes only its own internal BookingStatusChangedEvent (in BookingBatchStatusListener and BookingSseService) — it doesn't listen to events from other modules. Downstream, payment (PaymentLifecycleService, CancellationRefundService, BookingPaymentPersistenceService, RevenueReportingService), notification (BookingEmailListener, SessionPackEmailListener), development (TimelineEventListener, SluCalculationService), admin (DisputeService, AdminCoachEnforcementService), and session (HomeworkAssignmentService) all subscribe to booking events.

Key Flows

Booking a session (request → accept → payment → confirmed)

sequenceDiagram
  participant Parent
  participant BookingResource
  participant BookingService
  participant PaymentLifecycleService
  participant Coach

  Parent->>BookingResource: POST /api/bookings/requests
  BookingResource->>BookingService: createBookingRequest()
  BookingService->>BookingService: validate coach status, availability window, pack credits
  BookingService-->>Parent: BookingResponse (REQUESTED)
  BookingService--)Coach: BookingRequestedEvent (email)
  Coach->>BookingResource: PUT /requests/{id}/accept
  BookingResource->>BookingService: acceptBooking()
  BookingService->>BookingService: transition ACCEPT then INITIATE_PAYMENT (status = PAYMENT_PENDING)
  BookingService--)PaymentLifecycleService: BookingAcceptedEvent (AFTER_COMMIT)
  PaymentLifecycleService->>PaymentLifecycleService: deduct pack credit or charge Stripe/credit wallet
  PaymentLifecycleService->>BookingService: transition PAYMENT_CAPTURED (status = CONFIRMED)
  BookingResource->>BookingService: re-fetch booking
  BookingResource-->>Coach: BookingResponse (CONFIRMED)

A parent's request starts life as REQUESTED and is only accepted into the system if the slot sits inside the coach's declared availability, the coach is booking-ready, and (if a session pack was specified) the pack belongs to the parent, matches the coach, and still has credits. When the coach accepts, BookingService fires two transitions in the same transaction — ACCEPT then INITIATE_PAYMENT — landing the booking in PAYMENT_PENDING before publishing BookingAcceptedEvent. Because that event is consumed by PaymentLifecycleService as an AFTER_COMMIT listener, payment capture (or pack deduction) happens synchronously right after commit and moves the booking to CONFIRMED or back to DECLINED before the coach's HTTP request even returns — which is why BookingResource.acceptBooking() re-fetches the booking before responding.

Cancellation and reschedule

sequenceDiagram
  participant Parent
  participant CancellationResource
  participant RescheduleResource
  participant BookingService
  participant RescheduleService
  participant Coach

  Parent->>CancellationResource: POST /{id}/cancel
  CancellationResource->>BookingService: cancelBookingAsParent()
  BookingService->>BookingService: compute hoursBeforeSession -> refundEligibility (FULL/PARTIAL/NONE)
  BookingService->>BookingService: transition CANCEL_PARENT
  BookingService--)Coach: BookingCancelledByParentEvent
  Note over Parent,Coach: ...or, instead of cancelling outright:
  Parent->>RescheduleResource: POST /{id}/reschedule
  RescheduleResource->>RescheduleService: requestReschedule()
  RescheduleService--)Coach: RescheduleRequestedEvent
  Coach->>RescheduleResource: PUT /{id}/reschedule/{rid}/accept
  RescheduleResource->>RescheduleService: acceptReschedule()
  RescheduleService->>RescheduleService: overwrite booking start/end time, mark request ACCEPTED
  RescheduleService--)Parent: RescheduleAcceptedEvent

Cancellation and reschedule are separate, competing paths on a live booking. Cancellation always computes a refund-eligibility tier based on hours-until-session before transitioning the booking to CANCELLED_PARENT or CANCELLED_COACH; the actual refund is executed downstream by payment.CancellationRefundService off the cancellation event, not by this module. Reschedule only works while the booking is CONFIRMED or UPCOMING, allows only one pending proposal at a time, and — unlike cancellation — never changes the booking's status; it only overwrites the requested start/end time once the coach accepts.

Session completion (live delivery to confirmed completion)

sequenceDiagram
  participant Coach
  participant SessionCompletionResource
  participant BookingCompletionService
  participant SessionPackService
  participant Parent

  Coach->>SessionCompletionResource: POST /{id}/start
  SessionCompletionResource->>BookingCompletionService: startSession() [UPCOMING -> IN_PROGRESS]
  Coach->>SessionCompletionResource: POST /{id}/end
  SessionCompletionResource->>BookingCompletionService: endSession() [-> COMPLETED_PENDING_CONFIRMATION]
  Coach->>SessionCompletionResource: POST /{id}/complete (WrapUpRequest)
  SessionCompletionResource->>BookingCompletionService: submitWrapUp()
  alt mode == LIVE (Quick Complete)
    BookingCompletionService->>BookingCompletionService: transition QUICK_COMPLETE [-> COMPLETED]
    BookingCompletionService->>SessionPackService: deductCredit()
    BookingCompletionService--)Parent: BookingCompletedEvent
  else mode == SCHEDULED
    BookingCompletionService--)Parent: QuickCompleteConfirmationRequiredEvent
    Parent->>SessionCompletionResource: PUT /{id}/confirm-completion
    SessionCompletionResource->>BookingCompletionService: confirmCompletion() [-> COMPLETED]
    BookingCompletionService->>SessionPackService: deductCredit()
    BookingCompletionService--)Parent: BookingCompletedEvent
  end

A live session moves UPCOMING → IN_PROGRESS (optionally through PAUSED and back) and ends in COMPLETED_PENDING_CONFIRMATION once the coach submits a wrap-up (SessionCompletionData: attendance, ratings, voice note, homework drills). If the wrap-up mode is LIVE ("Quick Complete"), the booking is completed and the pack credit deducted immediately. Otherwise the parent must explicitly confirm via confirm-completion before the credit is deducted and BookingCompletedEvent fires — and if the parent never confirms, QuickCompleteTimeoutService force-completes it after a configurable timeout so credits and downstream flows (reviews, development timeline) aren't stuck forever.

Conventions & Gotchas

Two parallel session-credit systems exist. Legacy bookings draw against booking.repo.SessionPackPurchased via SessionPackService (getCreditsRemaining, deductCredit, pause). Bookings created with a sessionPackPurchaseId instead draw against payment.repo.SessionPackPurchase via payment.service.PackSessionService, deducted inside PaymentLifecycleService. Before touching credit logic, check which system the booking you're working on actually uses — BookingService.createBookingRequest() acquires a pessimistic lock on the legacy table "to prevent concurrent double-booking on the old system" even when the new system is the one deducting.

Circular dependencies are broken with @Lazy field injection, not constructor injection. BookingService ↔ SessionPackService and platform.session.service.DrillSuggestionService ↔ platform.booking.api are both cyclic at the bean level. Follow the existing pattern (@Autowired @Lazy private ... field) when adding new cross-references — introducing a constructor-injected dependency here will break application startup.

BookingStateMachine is the only place status transitions are legal. Never call booking.setStatus(...) directly outside BookingService.transition() — the state machine also enforces which ActorRole may fire which event (EVENT_ROLES map in BookingService), so bypassing it also bypasses that authorization check.

Events are published inside the same @Transactional method that changes state, but listeners run AFTER_COMMIT. This is intentional (it guarantees the DB row is durable before anyone reacts to it) but means side effects like Stripe charges or emails happen synchronously after the triggering method returns and before the HTTP response is sent — see BookingResource.acceptBooking(), which re-fetches the booking for exactly this reason.

Controller method ordering matters. In BookingResource, GET /requests/coach is declared before the /{id}/accept and /{id}/decline mappings specifically to avoid Spring path-matching ambiguity with the {id} path variable. Keep new literal-path endpoints above wildcard ones in the same resource.

Related Modules

  • Marketplace — supplies coach profiles, pricing, recurring availability windows, and the sellable session pack catalog that booking reads from.
  • Payment — owns Stripe charge/refund/capture, the credit wallet, and the newer session-pack-purchase-linked credit system; reacts to every booking lifecycle event to move money.
  • Session — supplies drill suggestions surfaced after wrap-up and consumes completion data for homework assignment and templates.
  • Security — provides player/parent identity, ownership checks, and the role-based auth (SecurityConstants) enforced on every booking endpoint.
  • Config — supplies every tunable threshold used by booking (expiry hours, reminder windows, commission rate, pack expiry tiers, batch size, pause limits).
  • Notification — sends the actual booking/pack lifecycle emails off booking's domain events.
  • Development — builds the player skill timeline and coach reliability scoring from completed/cancelled/no-show booking events.
  • Admin — disputes and GDPR erasure/export flows reference booking records directly.
  • Reviews — review eligibility is gated on a completed booking existing between the parties.
