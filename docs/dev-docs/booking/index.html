Booking

Turns a marketplace browse into a scheduled, paid, delivered coaching session — and manages everything that can happen to it in between.

Business Overview

The booking module is the transactional heart of Skillars: it owns the full lifecycle of a coaching session from the moment a parent requests a time slot to the moment the session is marked complete (or cancelled, disputed, refunded). Every other module that cares about "did this session happen" — payments, reviews, video access, player development timelines, coach reliability scoring — reacts to events this module publishes rather than owning booking state itself.

Parent is the primary actor: parents request sessions for their player(s), pay for them (directly via Stripe or by drawing down a pre-purchased session pack / platform credit wallet), cancel, request reschedules, and confirm session completion. Coach declares weekly availability and one-off blackout blocks, accepts or declines requests, runs the live session (start/pause/resume/end), and submits a wrap-up. Because players are frequently minors, the player never books directly — the parent account is always the actor of record, and coaches interact with the parent, not the child. System (schedulers) auto-expires stale requests, sends reminders, and force-completes abandoned "quick complete" sessions.

Booking no longer owns session packs. The legacy SessionPackService, SessionPackPurchased entity, SessionPackResource, and SessionPackExpiryScheduler were all deleted from this module, and migration V89__drop_legacy_session_packs.sql dropped the booking.session_packs_purchased table. Credits now live entirely in payment (PackSessionService + payment.repo.SessionPackPurchase). Booking keeps only the pack event contracts in booking.contract — payment publishes them, notification consumes them. A booking references a pack solely through its sessionPackPurchaseId column.

Key business rules enforced in this module (see BookingService, BookingStateMachine):

  • Availability-gated booking: a request is only accepted if the requested time falls inside one of the coach's declared CoachAvailabilityWindows and doesn't fall inside a CoachAvailabilityBlock (blackout).
  • Coach must be booking-ready: the coach profile must not be SUSPENDED, and the coach must have a fully configured Stripe destination account (paymentGateway.isCoachPaymentReady) before a request can even be created.
  • No two active bookings can hold overlapping time for the same coach: a coach can have at most one booking in REQUESTED/ACCEPTED/PAYMENT_PENDING/CONFIRMED/UPCOMING/IN_PROGRESS/PAUSED status per overlapping [requestedStartTime, requestedEndTime) range. Enforced both at request creation and again when the coach accepts (closing the race where two overlapping requests are accepted before either commits) — see Slot exclusivity below.
  • Cancellation refund windows (parent-initiated): more than 24h before the session → FULL refund eligibility; 6–24h → PARTIAL; under 6h → NONE. A coach-initiated cancellation is always FULL. A coach no-show reported by the parent is always FULL. A player no-show reported by the coach is always NONE.
  • Reschedule limits: only bookings in CONFIRMED or UPCOMING status can be rescheduled, only one pending reschedule request is allowed per booking at a time, and the proposed time must be in the future.
  • Batch bookings: a parent can request up to a configured maximum number of slots (booking.batch.maxSize) against one coach in a single submission; the coach can accept the whole batch in one action, and the batch's aggregate status (PENDING / PARTIALLY_ACCEPTED / FULLY_ACCEPTED / DECLINED) rolls up automatically as individual bookings change status.
  • A pack-funded booking must resolve to a live pack at creation: if the request carries a sessionPackPurchaseId, BookingService loads that payment.repo.SessionPackPurchase and rejects the request unless the pack belongs to the parent, matches the coach, and still has unexpired credits. The credit itself is not deducted here — payment does that at settlement.
  • Session completion has two paths: "Quick Complete" (mode LIVE) finalizes the session immediately when the coach submits the wrap-up; the standard path puts the booking in COMPLETED_PENDING_CONFIRMATION and waits for the parent to confirm — if the parent never responds, a scheduler auto-confirms after a configurable timeout.
  • Stale requests self-clean: a REQUESTED booking the coach never actions is automatically declined after a configurable number of hours (default 48h).

Domain events

Booking publishes on Spring's ApplicationEventPublisher; most listeners (payment, notification) subscribe via @TransactionalEventListener(phase = AFTER_COMMIT) so they only fire once the booking row is durably committed.

Key Flows

Booking a session (request → accept → payment → confirmed)

sequenceDiagram
  participant Parent
  participant BookingResource
  participant BookingService
  participant PaymentLifecycleService
  participant Coach

  Parent->>BookingResource: POST /api/bookings/requests
  BookingResource->>BookingService: createBookingRequest()
  BookingService->>BookingService: validate coach status, availability window, pack credits
  BookingService->>BookingService: lock CoachProfile row, check for overlapping active bookings
  BookingService-->>Parent: BookingResponse (REQUESTED)
  BookingService--)Coach: BookingRequestedEvent (email)
  Coach->>BookingResource: PUT /requests/{id}/accept
  BookingResource->>BookingService: acceptBooking()
  BookingService->>BookingService: lock CoachProfile row, re-check for overlapping active bookings
  BookingService->>BookingService: transition ACCEPT then INITIATE_PAYMENT (status = PAYMENT_PENDING)
  BookingService--)PaymentLifecycleService: BookingAcceptedEvent (AFTER_COMMIT)
  PaymentLifecycleService->>PaymentLifecycleService: deduct pack credit or charge Stripe/credit wallet
  PaymentLifecycleService->>BookingService: transition PAYMENT_CAPTURED (status = CONFIRMED)
  BookingResource->>BookingService: re-fetch booking
  BookingResource-->>Coach: BookingResponse (CONFIRMED)

A parent's request starts life as REQUESTED and is only accepted into the system if the slot sits inside the coach's declared availability, the coach is booking-ready, the slot doesn't overlap an existing active booking for that coach (see Slot exclusivity), and (if a session pack was specified) the pack belongs to the parent, matches the coach, and still has credits. When the coach accepts, BookingService re-runs the same overlap check — closing the race where the coach accepts two overlapping requests before either commits — then fires two transitions in the same transaction — ACCEPT then INITIATE_PAYMENT — landing the booking in PAYMENT_PENDING before publishing BookingAcceptedEvent. Because that event is consumed by PaymentLifecycleService as an AFTER_COMMIT listener, payment capture (or pack deduction) happens synchronously right after commit and moves the booking to CONFIRMED or back to DECLINED before the coach's HTTP request even returns — which is why BookingResource.acceptBooking() re-fetches the booking before responding.

Slot exclusivity (double-booking prevention)

Two layers enforce that a coach can't end up with two overlapping active bookings:

  • App-layer check + lock (primary path, gives a clean pre-emptive error). createBookingRequest and acceptBooking both call coachProfileRepository.findByIdForUpdate(coachId) — a PESSIMISTIC_WRITE lock on the CoachProfile row, with a 5s jakarta.persistence.lock.timeout query hint — immediately before running bookingRepository.findOverlappingBookings(coachId, startTime, endTime, statuses, excludeBookingId). There is no dedicated "coach's calendar" row, so the coach's own profile row is the serialization point: locking it forces concurrent create/accept calls for the same coach to run one-at-a-time around the overlap check. If any active booking overlaps, the call throws OperationNotAllowedException with BookingError.SLOT_UNAVAILABLE (booking.slotUnavailable). createBookingRequest checks against REQUESTED/ACCEPTED/PAYMENT_PENDING/CONFIRMED/UPCOMING/IN_PROGRESS/PAUSED; acceptBooking's re-check excludes REQUESTED (a merely-requested competing booking isn't a real conflict yet) and excludes the booking's own id (so retrying an accept on an already-accepted booking doesn't self-match).
  • DB-level exclusion constraint (backstop for every write path). Migration V87__booking_overlap_exclusion_constraint.sql adds excl_bkg_coach_slot_overlap, a Postgres EXCLUDE USING gist constraint on (coach_id WITH =, tstzrange(requested_start_time, requested_end_time, '[)') WITH &&), scoped to the same non-REQUESTED active statuses. This guarantees no two committed rows can overlap regardless of which code path wrote them — including BookingBatchService and RescheduleService, which don't call the app-layer check above. A violation surfaces as a DataIntegrityViolationException, mapped by ApiAdvice's CONSTRAINT_MAPPINGS/CONFLICT_CONSTRAINTS to the same booking.slotUnavailable / 409 rather than a raw 500.

The lock is per-coach, not per-slot — a known, accepted trade-off. Because findByIdForUpdate locks the whole CoachProfile row, all concurrent createBookingRequest/acceptBooking calls for the same coach serialize through it, even for non-overlapping times (e.g. Tuesday vs. Friday). Accepted as fine at current booking volume — don't "fix" this without evidence of real contention (slow-query/lock-wait monitoring), and note a lock-timeout now fails fast with 409 generic.conflict (PessimisticLockingFailureException handler in ApiAdvice) rather than hanging.

Known gap: batch and reschedule writes only get the DB backstop, not the pre-emptive app-layer check. BookingBatchService.createBatch and RescheduleService.acceptReschedule can still write an overlapping row — it will fail at the DB with a clean booking.slotUnavailable 409 via the exclusion constraint, but without the coach-lock pre-check's earlier, more explicit UX. Tracked as a residual gap in deferred-work.md; not yet closed as of this writing.

Editing/deleting a recurring CoachAvailabilityWindow also surfaces a (non-blocking) conflict warning: AvailabilityService.hasBookingConflict() looks 90 days ahead for CONFIRMED/UPCOMING bookings whose local start time (in the window's canonicalTimezone) falls inside the edited window's day-of-week/time range, and returns that via AvailabilityWindowResponse.hasConflict. This is currently backend-only — no frontend component reads hasConflict, so no warning is actually shown to a coach yet.

  Parent->>CancellationResource: POST /{id}/cancel

  BookingService->>BookingService: transition CANCEL_PARENT
  BookingService--)Coach: BookingCancelledByParentEvent
  Note over Parent,Coach: ...or, instead of cancelling outright:
  Parent->>RescheduleResource: POST /{id}/reschedule
  RescheduleResource->>RescheduleService: requestReschedule()
  RescheduleService--)Coach: RescheduleRequestedEvent
  Coach->>RescheduleResource: PUT /{id}/reschedule/{rid}/accept

  RescheduleService--)Parent: RescheduleAcceptedEvent

Cancellation and reschedule are separate, competing paths on a live booking. Cancellation always computes a refund-eligibility tier based on hours-until-session before transitioning the booking to CANCELLED_PARENT or CANCELLED_COACH; the actual refund is executed downstream by payment.CancellationRefundService off the cancellation event, not by this module. Reschedule only works while the booking is CONFIRMED or UPCOMING, allows only one pending proposal at a time, and — unlike cancellation — never changes the booking's status; it only overwrites the requested start/end time once the coach accepts.

Session completion (live delivery to confirmed completion)

sequenceDiagram
  participant Coach
  participant SessionCompletionResource
  participant BookingCompletionService
  participant Parent

  Coach->>SessionCompletionResource: POST /{id}/start
  SessionCompletionResource->>BookingCompletionService: startSession() [UPCOMING -> IN_PROGRESS]
  Coach->>SessionCompletionResource: POST /{id}/end
  SessionCompletionResource->>BookingCompletionService: endSession() [-> COMPLETED_PENDING_CONFIRMATION]
  Coach->>SessionCompletionResource: POST /{id}/complete (WrapUpRequest)
  SessionCompletionResource->>BookingCompletionService: submitWrapUp()
  alt mode == LIVE (Quick Complete)
    BookingCompletionService->>BookingCompletionService: transition QUICK_COMPLETE [-> COMPLETED]
    BookingCompletionService--)Parent: BookingCompletedEvent
  else mode == SCHEDULED
    BookingCompletionService--)Parent: QuickCompleteConfirmationRequiredEvent
    Parent->>SessionCompletionResource: PUT /{id}/confirm-completion
    SessionCompletionResource->>BookingCompletionService: confirmCompletion() [-> COMPLETED]
    BookingCompletionService--)Parent: BookingCompletedEvent
  end

A live session moves UPCOMING → IN_PROGRESS (optionally through PAUSED and back) and ends in COMPLETED_PENDING_CONFIRMATION once the coach submits a wrap-up (SessionCompletionData: attendance, ratings, voice note, homework drills). If the wrap-up mode is LIVE ("Quick Complete"), the booking is completed immediately. Otherwise the parent must explicitly confirm via confirm-completion before BookingCompletedEvent fires — and if the parent never confirms, QuickCompleteTimeoutService force-completes it after a configurable timeout so downstream flows (reviews, development timeline) aren't stuck forever.

Completion no longer moves money or credits. An older version of this page showed deductCredit() on both branches above. That is wrong for the current code: the pack credit is deducted much earlier, by payment.PaymentLifecycleService reacting to BookingAcceptedEvent, and is given back by payment.CancellationRefundService.restoreSession(...) on cancellation/no-show. BookingCompletionService only changes booking state and writes SessionCompletionData.

Conventions & Gotchas

There is now exactly one session-credit system, and booking doesn't own it. The two parallel systems this page used to warn about are gone: the legacy booking.repo.SessionPackPurchased table was dropped in V89. All credit reads and writes go through payment.service.PackSessionService against payment.repo.SessionPackPurchase. Booking validates a pack at request time and stores its id; it never decrements one.

Circular dependencies are broken with @Lazy field injection, not constructor injection. One such cycle remains in this module: SessionCompletionResource → platform.session.service.DrillSuggestionService, which is broken by a @Lazy field (platform.session imports platform.booking.contract, closing the loop). Note the booking↔payment direction is not cyclic and needs no @Lazy: PackSessionService constructor-injects BookingService, but nothing in BookingService injects back into payment. Follow the existing pattern (@Autowired @Lazy private ...) if you do introduce a cycle — an eager constructor-injected one will break application startup.

BookingStateMachine is the only place status transitions are legal. Never call booking.setStatus(...) directly outside BookingService.transition() — the state machine also enforces which ActorRole may fire which event (EVENT_ROLES map in BookingService), so bypassing it also bypasses that authorization check.

Events are published inside the same @Transactional method that changes state, but listeners run AFTER_COMMIT. This is intentional (it guarantees the DB row is durable before anyone reacts to it) but means side effects like Stripe charges or emails happen synchronously after the triggering method returns and before the HTTP response is sent — see BookingResource.acceptBooking(), which re-fetches the booking for exactly this reason.

Controller method ordering matters. In BookingResource, GET /requests/coach is declared before the /{id}/accept and /{id}/decline mappings specifically to avoid Spring path-matching ambiguity with the {id} path variable. Keep new literal-path endpoints above wildcard ones in the same resource.

Related Modules
