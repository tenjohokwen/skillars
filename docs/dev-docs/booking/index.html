    Booking

    Turns a marketplace browse into a scheduled, paid, delivered coaching session — and manages everything that can happen to it in between.

    Business Overview

    The booking module is the transactional heart of Skillars: it owns the full lifecycle of a coaching session from the moment a slot is requested to the moment the session is marked complete (or declined, expired, cancelled, no-showed). It also owns the coach's one-off blackout blocks, the session-prep notes attached to a booking, and the coach's post-session wrap-up and recap. Every other module that cares about "did this session happen" — payment, reviews, video access, player development timelines, session plans/homework — reacts to events this module publishes or reads its tables, rather than owning booking state itself.

    Parent / Self-registered player is the booker: every booker-side endpoint is guarded by HAS_PARENT_OR_PLAYER_ROLE. A parent books for a child PlayerProfile (player.parentId == caller); an adult player with no parent books for their own profile (player.userId == caller). Either way the caller's user id is stored in Booking.parentId — so "parent" in this module really means "the paying account". Minors never have accounts, so they never book. The booker requests (single or batch), withdraws a still-pending request, confirms or declines a coach's "repeat next week" proposal, pays (Stripe, credit wallet, or a pre-purchased pack), cancels, proposes/answers reschedules, reports a coach no-show, adds a session-prep request, and confirms a quick-completed session. Coach declares weekly availability (stored in marketplace) and one-off blackout blocks, accepts or declines requests (singly or a whole batch — never their own proposals), proposes a repeat of a completed session, proposes/answers reschedules, cancels with a reason code, reports a player no-show, writes a private plan note, runs the live session (start/pause/resume/end), submits the wrap-up, and edits the recap afterwards. System (five ShedLock-guarded schedulers) expires stale or past-start requests, moves bookings to UPCOMING and sends reminders, auto-confirms quick completes, force-completes abandoned wrap-ups, and ends live sessions left open / flags sessions that were never started. Admin can force-complete or cancel a single booking from a support ticket (via the admin module).

    Booking does not own session packs. The legacy pack service/entity/resource/scheduler were deleted from this module and the booking.session_packs_purchased table was dropped (originally V89; pre-V138 migrations are now squashed into V138__baseline_schema.sql). Credits live entirely in payment (PackSessionService + payment.repo.SessionPackPurchase). Booking keeps only the pack event contracts in booking.contract — payment publishes them. A booking references a pack solely through its sessionPackPurchaseId column.

    Key business rules enforced in this module (mostly BookingService, BookingStateMachine):

    • Availability-gated booking: every create/reschedule/duplicate path requires the slot to sit inside one of the coach's marketplace.CoachAvailabilityWindows (interpreted in the coach profile's canonicalTimezone; booking.slotOutsideAvailability), not overlap a CoachAvailabilityBlock (booking.slotBlockedByCoach), and not cross local midnight (booking.sessionCrossesMidnight). Shared helpers: BookingService.requireSlotWithinAvailabilityWindow and isSlotBlocked.
    • Exact session length: end - start must equal SessionDurationResolver.resolve(coachId) (coach's CoachPricing.sessionDurationMinutes, else config booking.session.defaultDurationMinutes, default 60, bounded 15–240); a reschedule must keep the booking's original length (booking.invalidSessionDuration).
    • Stale-view guard: create, batch-create and reschedule accept an optional availabilitySignature; if the coach's windows changed since the client loaded the calendar, the request fails with booking.availabilityChanged (AvailabilityService.computeAvailabilitySignature).
    • Coach must be booking-ready: single and batch creation both require coach status ACTIVE/REDUCED/PENDING_REVIEW (BookingService.requireBookableCoachStatus, re-checked under the coach row lock) and paymentGateway.isCoachPaymentReady (requireCoachPaymentReady, else 422 payment.coachStripeNotConfigured via BookingApiAdvice). Every accept path rejects a SUSPENDED coach. PENDING_REVIEW (5 strikes) stays bookable by design: the epics spec has the coach keep operating while flagged for admin attention, with no automatic suspension without admin action; only marketplace search hides them.
    • Erased players cannot be booked: single create, batch create and duplicate-next-week reject a player whose developmentDataErasedAt is set or who has a child-scoped ERASURE request in PENDING/PROCESSING/FAILED (booking.playerNotBookable). The authoritative check (BookingService.requirePlayerBookableUnderLock) runs under the player_profiles row lock, which GdprRequestService.requestChildErasure also takes before its live-booking check, so a booking and a child-erasure request cannot both succeed. Lock order: coach row, then player row.
    • No overlapping active bookings per coach — app-layer check under a coach-row lock on every write path plus a DB exclusion constraint; see Slot exclusivity.
    • Parent cancellation refund (binary): cancelBookingAsParent sets refundEligible = true only if payment was captured (status was CONFIRMED/UPCOMING) and either the session is more than 24h away (from the earlier of original_start_time and the current start, so a reschedule cannot reopen the window) or it is still unstarted booking.lateCancel.graceMinutes (default 30) after its start (Deferred-64 AC4, narrowed by fix/booking-cancel-policy-loopholes; BookingService.isParentCancelRefundEligible). original_start_time (V191) is stamped by the first accepted reschedule. Cancelling a PAYMENT_PENDING booking whose BookingPayment is CAPTURE_PENDING is refused with 409 booking.paymentInProgress; a started session (IN_PROGRESS/PAUSED) is refused with booking.sessionInProgress — the parent disputes it instead. Coach cancellation of a captured booking and coach no-show are full refunds; a player no-show or a captured, non-refund-eligible parent cancel is a forfeit, and payment.CoachPayoutEnqueueListener pays the coach their normal net for it. An admin/system cancellation on a coach suspension or child-safety hold (cancelBookingAsAdmin) is a full refund of what was actually paid when payment was captured (same CONFIRMED/UPCOMING whitelist), nothing otherwise, never a coach strike, and the same CAPTURE_PENDING interlock. The money moves in payment, not here.
    • Completed is final for cancellation: cancel/no-show on a COMPLETED booking fails fast with booking.alreadyCompleted (rejectIfPostCompletion) — post-completion problems go through admin disputes.
    • No-show and start are time-gated: start and quick-complete are rejected before requestedStartTime (booking.sessionNotYetStarted). A coach may report a player no-show only from start + booking.playerNoShow.graceMinutes (default 15, bounded 5–1440), a parent a coach no-show only from start + booking.lateCancel.graceMinutes (default 30); earlier is booking.noShowTooEarly. BookingResponse.coachNoShowReportableAt carries the latter instant for the parent UI.
    • Coach proposals need parent consent: a "repeat next week" booking (BookingDuplicationService) is created REQUESTED with proposed_by_coach = true (V206). Only the parent can accept it (PUT /requests/{id}/confirm — the same accept + charge pipeline as a coach accept) or decline it (PUT /requests/{id}/withdraw); the coach can still withdraw it with the ordinary decline. acceptAndInitiatePayment enforces the direction under the booking row lock (requireConsentingAcceptor): a coach accepting their own proposal is booking.parentConfirmationRequired, a parent confirming a non-proposal booking.notACoachProposal.
    • Withdraw is not cancel: withdrawBookingRequest moves only a REQUESTED booking (checked under the row lock) to CANCELLED_PARENT and never refunds or forfeits anything; once the booking has moved on it is booking.requestNotPending, so a withdraw racing a coach accept cannot cancel a just-charged booking.
    • Request quota and horizon: single and batch creation (under the coach row lock, requireRequestQuota) refuse a start beyond booking.request.maxHorizonDays (default 120, bounded 1–730; booking.beyondBookingHorizon) and more than booking.request.maxPendingPerCoach (default 10, bounded 1–100; booking.tooManyPendingRequests) of the parent's own REQUESTED bookings with one coach (countPendingParentRequests; coach proposals excluded; a batch counts all its slots).
    • Past-start requests cannot be accepted: coach accept, batch accept and parent confirm all refuse a REQUESTED booking whose start has passed (booking.requestExpired; requireRequestStartNotPassed, authoritative under the row lock in acceptAndInitiatePayment), and the expiry scheduler declines it.
    • Reschedule: either party may propose (the other answers; booking.cannotRespondToOwnProposal), only for CONFIRMED/UPCOMING bookings, one PENDING proposal per booking at a time, future start, same duration, inside availability and not blocked.
    • Batch bookings: up to booking.batch.maxSize (bounded 1–100) slots against one coach in one submission; slots must have distinct start times and not overlap each other; the coach can accept all in one action and the batch status (PENDING / PARTIALLY_ACCEPTED / FULLY_ACCEPTED / DECLINED) rolls up as members change. Accept-all first claims the batch PENDING → ACCEPTING under the batch row lock in its own short transaction (V206 widened the status CHECK), so a concurrent second accept-all gets booking.batchAlreadyProcessed; a failed run hands it back to PENDING.
    • A pack-funded booking must resolve to a live pack at creation: the pack must belong to the caller (checked first, so the error can't be used as an oracle) and to the booked player (payment.packPlayerMismatch), not be expired, not be paused now or at the session's start (payment.packPaused, window [paused_from, paused_until)), not be frozen by an open card dispute (payment.packFrozen), match the coach, and have remaining sessions. The credit itself is deducted by payment at settlement.
    • Two completion modes (LIVE | QUICK), derived by the server: submitWrapUp uses LIVE only when the coach pressed Start (liveStartedAt) and ended the session themselves (autoEndedAt NULL), otherwise QUICK; WrapUpRequest.mode is only logged when it disagrees. A LIVE wrap-up completes the booking immediately; a QUICK wrap-up leaves it in COMPLETED_PENDING_CONFIRMATION for the booker to confirm, auto-confirmed after booking.quick_complete_timeout_hours. See Session completion.
    • Sessions nobody settles are swept: an IN_PROGRESS/PAUSED session still open booking.unresolvedSession.graceMinutes (default 120, bounded 30–10080) after its scheduled end is moved to COMPLETED_PENDING_CONFIRMATION with auto_ended_at stamped; an UPCOMING session past the same cutoff is never auto-paid or auto-refunded, it raises one SESSION_NEVER_STARTED admin alert (unresolved_alerted_at, V209).
    • Recap is editable for a bounded time: the coach may add/correct the recap on a COMPLETED booking until requestedEndTime + booking.recap.editWindowDays (default 30, bounded 7–365), unless the coach or player has been GDPR-erased or a dispute locks it.
    • Stale requests self-clean: a REQUESTED booking the coach never actions is auto-declined after booking.request_expiry_hours (default 48), or as soon as its start time has passed.
    • Free text is sanitized: booking notes, playerRequest, coachPlanNote and all three recap fields go through ContactDetailSanitizer then are truncated to 500 chars (BookingService.sanitizeAndTruncate), so off-platform contact details can't leak via the DB or the emails built from them.

    Domain events

    Booking publishes on Spring's ApplicationEventPublisher, always inside the transaction that changed state. Listener phase matters: outbox writers (notification.BookingEmailListener, payment.RefundEnqueueListener, payment.CoachPayoutEnqueueListener) are BEFORE_COMMIT, so the outbox row commits atomically with the booking change, as does payment.CancellationRefundService.onBookingCancelledByCoach (cancellation history under a per-coach advisory lock; the strike itself runs after commit); side-effecting reactors (payment.PaymentLifecycleService, CancellationRefundService's no-show handlers, development.TimelineEventListener/SluCalculationService, session.HomeworkAssignmentService/SessionPlanService, admin.AdminAlertEventListener, and booking's own SSE/batch listeners) are AFTER_COMMIT.

    Booking a session (request → accept → payment → confirmed)

    acceptAndInitiatePayment is the one method every accept path (single and batch) must use: it fires ACCEPT silently and INITIATE_PAYMENT with a status-change event, so observers see a single change to PAYMENT_PENDING. The AFTER_COMMIT payment listener runs synchronously on the request thread after commit, which is why BookingResource.acceptBooking() re-fetches before responding. A booking stranded in PAYMENT_PENDING (crash between commit and capture) is swept by payment.PaymentPendingSweeper (findPaymentPendingOlderThan); the booker can also cancel it (no refund — nothing was captured) unless a capture is in flight.

    A coach-proposed booking (duplicate-next-week) takes the same path with the roles swapped: PUT /requests/{id}/confirm → confirmProposedBooking checks ownership on an unlocked read, then locks the coach row, rejects a suspended coach, re-checks overlap and the locked price, and calls acceptAndInitiatePayment with a PARENT actor (EVENT_ROLES now grants ACCEPT/INITIATE_PAYMENT to PARENT for exactly this) before publishing BookingAcceptedEvent. Accept and settlement charge only agreed_price (or the pack's price); there is no fallback to the coach's current price any more.

    Slot exclusivity (double-booking prevention)

    • App-layer check under a per-coach lock. Every write path that creates or moves an active slot — createBookingRequest, acceptBooking, confirmProposedBooking, BookingBatchService.createBatch (every slot, via requireNoOverlappingBooking) and its per-booking accept, RescheduleService (propose and accept), BookingDuplicationService, and AvailabilityService's window/block writes — takes coachProfileRepository.findByIdForUpdate(coachId) before reading windows or running bookingRepository.findOverlappingBookings(...). That query uses the NO_WAIT lock hint (jakarta.persistence.lock.timeout = 0), so every call site wraps it in PessimisticLockRetryer.withBoundedRetry (JDBC savepoint, 8 attempts, ~3.2s jittered budget); contention beyond that surfaces as 409 generic.conflict via ApiAdvice's PessimisticLockingFailureException handler. The lock is followed by entityManager.refresh(c, PESSIMISTIC_WRITE) — required, because the JPQL locked read returns the already-managed instance without refreshing its fields. Overlap fails with booking.slotUnavailable. Create checks against ACTIVE_SLOT_STATUSES (incl. REQUESTED); accept, parent confirm, reschedule and duplication use ACTIVE_SLOT_STATUSES_EXCLUDING_REQUESTED and exclude the booking's own id (duplication has none yet; reschedule checks overlap only at accept).
    • DB exclusion constraint (backstop). excl_bkg_coach_slot_overlap — EXCLUDE USING gist (coach_id WITH =, tstzrange(requested_start_time, requested_end_time, '[)') WITH &&) for status ACCEPTED/PAYMENT_PENDING/CONFIRMED/UPCOMING/IN_PROGRESS/PAUSED (originally V87, now in the V138 baseline). A violation is mapped by ApiAdvice's constraint table to the same booking.slotUnavailable 409.

    The lock is per-coach, not per-slot — a known, accepted trade-off. All create/accept/reschedule/ availability writes for one coach serialize through that coach's profile row, even for unrelated times. Fine at current volume; don't "fix" it without lock-wait evidence. Note the lock also serializes against AdminCoachEnforcementService.suspendCoach, which takes the same row lock.

    The DB constraint ignores REQUESTED. Only the app-layer check stops a new request from landing on top of an existing request: single and batch create both run it (against ACTIVE_SLOT_STATUSES, REQUESTED included) under the coach lock. A new create path must do the same.

    Updating a recurring window returns a non-blocking AvailabilityWindowResponse.hasConflict (CONFIRMED/UPCOMING bookings in the next 90 days whose local start, in the coach's current profile zone, falls in the window). Delete does not compute it, and no frontend code reads it yet.

    Note the naming trap: the event QUICK_COMPLETE is what a LIVE-mode wrap-up fires, while a QUICK-mode wrap-up is the one that waits for confirmation. BookingCompletedEvent is the trigger for coach payout, timeline/SLU and homework — so a booking that never leaves COMPLETED_PENDING_CONFIRMATION stalls all of them, which is why two backstops exist. The mode is the server's: a coach who quick-completes and then submits mode=LIVE still gets a QUICK wrap-up, so the parent's confirm / dispute window cannot be skipped. submitWrapUp locks the booking row (after the ownership check) before reading anything, so a duplicate submit serialises behind the first and is a no-op: it finds the completion row with the booking still COMPLETED_PENDING_CONFIRMATION (QUICK) and returns, or finds the booking COMPLETED (LIVE) and gets the status mismatch. The old catch of the UNIQUE booking_id violation was removed — it could never fire, because the insert only flushed at commit.

    Abandoned wrap-ups: sweeper and admin force-complete

    BookingCompletionService.forceCompleteWithPlaceholderData(bookingId, actorRole, actorUserId) writes a placeholder SessionCompletionData (playerAttended = false, mode QUICK, all ratings/recap null), fires COMPLETE, and publishes BookingCompletedEvent — releasing the coach payout. It returns a ForceCompleteOutcome: NOT_STUCK (status isn't COMPLETED_PENDING_CONFIRMATION), ALREADY_RESOLVED (a completion row exists), or FORCE_COMPLETED. Those pre-checks matter for the admin path, which accepts any id from a support ticket: writing the row first would permanently block the coach's own wrap-up via the UNIQUE constraint. StuckCompletionSweeperService calls it as SYSTEM; admin.AdminBookingCompletionService calls it as ADMIN and always writes an AdminActionLog (BOOKING_FORCE_COMPLETE) recording the outcome. Race exceptions are deliberately not caught inside the method — the joined transaction is already rollback-only — but at the caller's transaction boundary.

    If the coach later submits the wizard for a force-completed booking, submitWrapUp recognises the placeholder signature and answers booking.recapStillEditableAfterForceComplete (if the recap is still editable) so the UI can redirect to the recap dialog, or the specific not-editable reason otherwise.

    Live sessions the coach never ended reach this path too: UnresolvedSessionSweeperService moves them to COMPLETED_PENDING_CONFIRMATION (autoEndedAt), and if no wrap-up follows the stuck-completion sweeper force-completes them. A session that ended without ever being started (UPCOMING) is deliberately not force-completed or refunded: it gets one SESSION_NEVER_STARTED admin alert, while the parent can still report a coach no-show and the coach can still quick-complete.

    Recap lifecycle

    recapEditability() is the single verdict used by both GET and PUT /{id}/recap, checked in this order: coach erased (coach_profiles.recap_data_erased_at tombstone from V166 or the coach user is locked) or player erased (developmentDataErasedAt) → booking.recapNotEditableErased; locked by a dispute (BookingDisputeLookup.isRecapLockedByDispute: any active dispute, or one resolved with a resolution other than NO_ACTION) → booking.recapNotEditableDisputed; outside the window → booking.recapEditWindowClosed. updateRecap takes a row lock on the completion row (findForUpdateByBookingId) before the erasure checks so a concurrent erasure either finishes first or waits. The missing-recap nudge queries in BookingRepository repeat the dispute predicate in JPQL — keep them in sync with admin.DisputeRecapLockLookup.

    Session prep notes

    Two independent free-text fields feed the coach's Session Prep Card (development.SessionPrepService): the booker's playerRequest (PATCH /{id}/player-request) and the coach's private coachPlanNote (PATCH /{id}/coach-plan-note). Both are editable only while the booking is CONFIRMED/UPCOMING and before requestedEndTime (Booking.isPrepNoteEditable, shared with the prep response's editable flag); errors are booking.notEditable / booking.sessionAlreadyEnded. setCoachPlanNote uses saveAndFlush so a version clash maps to booking.concurrentModification inside the method.

    GDPR touch-points

    • Player/child erasure: BookingRepository.anonymizeNotesAndPlayerRequestByPlayerId and SessionCompletionDataRepository.anonymizeByPlayerId. Coach erasure: anonymizeCoachPlanNoteByCoachId, SessionCompletionDataRepository.anonymizeByCoachId, CoachAvailabilityBlockRepository.anonymizeReasonByCoachId.     Conventions & Gotchas

    Status changes go through BookingService.transition(). It locks the booking row (findByIdForUpdate, NO_WAIT + retry, then refresh), validates the actor against EVENT_ROLES, validates the transition with BookingStateMachine, saves, and publishes BookingStatusChangedEvent. Don't call booking.setStatus(...) directly. Coach suspension and the child-safety hold use BookingService.cancelBookingAsAdmin (event CANCEL_ADMIN, ADMIN actor, legal from REQUESTED, ACCEPTED, PAYMENT_PENDING, CONFIRMED and UPCOMING to CANCELLED, never from IN_PROGRESS/PAUSED; the neutral cancel reason COACH_UNAVAILABLE, because the row reaches the parent's GDPR export). It returns an AdminBookingCancellationOutcome (CANCELLED / PAYMENT_IN_PROGRESS / LIVE_SESSION / NOT_CANCELLABLE) rather than throwing, because it joins the caller's transaction and a throw would roll it back; the caller decides what each outcome means. A safety hold sweeps all of the coach's bookings in one transaction; an admin suspension (since fix/payment-wallet-dispute-integrity) cancels each booking in its own REQUIRES_NEW transaction (AdminCoachEnforcementService.cancelBookingForSuspension), retries busy rows once and raises a BOOKING_ACTION_REQUIRED alert for any still busy. Everything is decided under the booking row lock. The caller passes booking ids (findIdsByCoachIdAndStatusIn), never loaded entities: a booking already managed at an old @Version makes the locked re-read throw StaleObjectStateException when a concurrent writer has moved it, instead of returning the fresh status. An admin can also cancel one booking from the admin bookings page (admin.AdminBookingCancellationService, C6): the same method with cancel reason ADMIN_SUPPORT, so the parent's notice says the Skillars team cancelled it rather than that the coach is unavailable.

    Refund decisions are made under the booking row lock, from the status being left. cancelBookingAsParent, cancelBookingAsCoach and cancelBookingAsAdmin all lock the row (after the ownership check), read the status, and only treat payment as captured from CONFIRMED/UPCOMING (plus PAUSED for the coach). cancelDueToPause locks first too. Before C6 the coach path read the status unlocked and carried no capture flag, so a coach cancelling an ACCEPTED booking refunded a card booking that was never charged and restored a pack session that was never deducted. The refund amount is resolveAmountPaid (what booking_payments recorded, else agreed_price, else — only for a row-less pre-V192 booking — the coach's current price; a pack booking previews the pack's next settlement value, its per-session share rounded down with the last session taking the remainder); it throws when there is no price at all, so a coach / parent / no-show cancellation fails rather than commit a 0.00 "full refund". Only cancelBookingAsAdmin uses the non-throwing resolveAmountPaidOrZero (it joins the caller's transaction) and logs [ADMIN_CANCEL_REFUND_AMOUNT_UNKNOWN]; payment's RefundEnqueueListener then enqueues no 0.00 refund but raises a BOOKING_ACTION_REQUIRED alert. PAUSED counts as captured for the coach (calling off a paused session refunds the family). The parent cannot cancel a started session at all (booking.sessionInProgress): CANCEL_PARENT was removed from PAUSED because a parent cancel there was a forfeit that paid the coach for a session they had stopped.

    DISPUTED, REFUND_PENDING and REFUNDED are unreachable today. The state machine defines DISPUTE/SETTLE_REFUND/SETTLE_COMPLETE/REFUND_PROCESSED, but no code fires them. Disputes live in admin (DisputeService) and never touch booking status; their effect on booking is the recap lock via BookingDisputeLookup (a parent may also dispute an IN_PROGRESS/PAUSED session, whose resolution then waits until the booking has completed). The enum values and DB states are kept on purpose. Note also: the only exits from PAUSED are RESUME and CANCEL_COACH (coach) and COMPLETE_PENDING (coach, or SYSTEM via UnresolvedSessionSweeperService); there is no admin cancel of a live session.

    ID spaces. Booking.playerId is a PlayerProfile PK, not a user id; Booking.parentId is the booker's user id (a parent, or the adult player themself). Resolve a player's identity via PlayerProfile.userId/parentId.

    Scheduler and multi-step methods must not share one transaction. A BookingStateTransitionException or OptimisticLockingFailureException thrown inside transition() (REQUIRED) marks the joined transaction rollback-only; catching it and returning normally then fails at commit with UnexpectedRollbackException. That is why all schedulers use per-row TransactionTemplates, batch accept-all uses a REQUIRES_NEW template per booking (and claims the batch in its own short transaction, never holding the batch row lock across the loop), and forceCompleteWithPlaceholderData leaves race exceptions to its callers.

    Reminders are "queued", not "sent". BookingEmailListener.onBookingReminder is BEFORE_COMMIT and filters out a null or blank parent/coach address per recipient, so primaryReminderSentAt/secondaryReminderSentAt mean an outbox row was durably written; delivery is the outbox drain's job. Booking reminders are in the REMINDER notification category (opt-out-able per user since the notification centre, and also shown in-app) and the template carries the one-click unsubscribe footer.

    Read-after-lock needs entityManager.refresh. findByIdForUpdate is a JPQL query; if the entity is already managed from an earlier unlocked read, Hibernate takes the DB lock but hands back the stale in-memory instance. Every locked read in this module is followed by refresh(entity, PESSIMISTIC_WRITE) — keep doing that.

    Batch inbox counts are live counts. getCoachBookingRequests reports a batch group's size as the number of members still REQUESTED, not BookingBatch.requestedCount (which goes stale as members are individually actioned).

    Circular dependency with session is broken by @Lazy field injection. SessionCompletionResource → session.service.DrillSuggestionService uses @Autowired @Lazy because platform.session depends back on booking. Booking ↔ payment is not a bean cycle (booking injects only payment repositories and the PaymentGateway; payment's PackSessionService injects BookingService). Introduce any new cycle the same @Lazy way — an eager constructor cycle breaks startup.

    Controller ordering. In BookingResource, literal paths (/config, /coach) are declared before /{id}/accept and /{id}/decline. Keep new literal-path endpoints above wildcard ones. PlayerRequestResource deliberately lives under /api/bookings/{id}, not /requests, because it edits a confirmed booking, not a pending request.

    Timezones. Every window is interpreted in the coach profile's current canonicalTimezone (the per-window column is still written but no computational path reads it). A booking stamps the profile zone at creation and keeps it. Invalid or blank zones fall back to UTC with a WARN rather than failing.

    Frontend. Booker: pages/parent/BookingRequestPage.vue, ParentBookingsPage.vue (Confirm / Decline on a coach proposal, Withdraw on a pending request). Coach: pages/coach/CoachBookingRequestsPage.vue (own proposals shown as awaiting parent confirmation, no Accept), AvailabilityManagerPage.vue, CoachCommandCenterPage.vue, components in components/booking/ (ActiveSessionScreen, WrapUpSequence, SessionRecapDialog, CoachPlanNotePanel, DisputeAction). Admin: pages/admin/AdminBookingsPage.vue. State lives in stores/booking.store.js.
