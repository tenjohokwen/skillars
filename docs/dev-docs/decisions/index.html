    Why It's Built This Way

    Short decision records for the choices that surprise newcomers most. Each says what problem forced the choice, what was decided, what it costs, and where the code enforces it, with the story or commit that made it.

    Where these come from. Story files under _bmad-output/implementation-artifacts/ (named by story key, e.g. skillars-deferred-62-*.md), _bmad-output/planning-artifacts/architecture.md, docs/, commit messages and javadoc. Where no rationale was ever recorded, the record says so instead of inventing one. Java paths omit src/main/java/com/softropic/skillars/.

    1. Transactional outbox instead of AFTER_COMMIT listeners

    Context. Refunds, payout transfers, emails and SLU snapshot writes used to run in @TransactionalEventListener(AFTER_COMMIT). A throw there is only logged, and a JVM death between commit and listener loses the work with no retry. The deferred-91 story counted the same defect recurring six times across stories (a dropped refund, a dropped cancellation email, an SLU under-report). deferred-90 had already built a one-off durable queue for blob deletion.

    Decision. Generalise that queue into platform.outbox: producers insert an intent row in their own transaction (from a BEFORE_COMMIT listener, through a MANDATORY *OutboxSupport), and a post-commit async drain plus a 5-minute sweep execute it. deferred-92 closed the gap where an enqueue could open its own transaction.

    Consequences. At-least-once delivery, so every handler must be idempotent. Rows retry forever (no dead letter), surfaced as [OUTBOX_STUCK]. An enqueue failure fails the business operation. AFTER_COMMIT is still used for reactors that may be lost or are recovered elsewhere (SSE push, payment settlement backed by PaymentPendingSweeper).

    Where enforced. platform/outbox/service/OutboxService.java, OutboxRowProcessor.java; the *OutboxSupport classes; NotificationEmailOutboxAtomicityIT. See Outbox.

    2. NOWAIT row locks + PessimisticLockRetryer instead of lock timeouts

    Context. Four findByIdForUpdate repositories carried jakarta.persistence.lock.timeout = 5000 and comments promising a bounded ~5 s wait. deferred-62 proved this does nothing on PostgreSQL under Hibernate 6.6: the dialect only honours the NO_WAIT and SKIP_LOCKED sentinels, so a contended request blocked indefinitely (a throwaway IT held a lock for 12 s and the caller waited all 12).

    Decision. Owner decision 2026-08-24: switch to PESSIMISTIC_WRITE + lock.timeout = 0 (FOR UPDATE NOWAIT, which Postgres honours) wrapped in an application retry. Plain NOWAIT without retry was rejected because every brief overlap would become a 409.

    Consequences. PessimisticLockRetryer.withBoundedRetry retries from a JDBC savepoint (Spring's NESTED is unavailable with DefaultJpaDialect): 8 attempts, ~3.2 s worst case, then 409 generic.conflict. It holds the pooled connection while sleeping (accepted and sized in deferred-99). Only locked reads may go inside the lambda. A plain UPDATE still ignores NOWAIT, which is why the payment REQUIRES_NEW code carries explicit deadlock warnings.

    Where enforced. infrastructure/persistence/PessimisticLockRetryer.java; PessimisticLockRetryerCallSiteAuditTest (pins 64 call sites); ApiAdvice.pessimisticLockExceptionHandler; docs/persistence/pessimistic-lock-retry.md.

    3. ShedLock on shared-state jobs, ten deliberately unguarded

    Context. The code is written to be safe on more than one instance (scale-out, and two JVMs overlapping during a rolling deploy), and every @Scheduled method runs on each instance. A job that writes shared rows without a row claim would do its work once per instance.

    Decision. Every job that writes shared state without a row claim carries @SchedulerLock (36 of 46). The ten unguarded ones are deliberate: six touch only per-instance state (ConfigService, AlertRuleCache, AlertEvaluationService, MessagingEmitterRegistry, RateLimitingService, and InstanceHeartbeatMonitor, which must write its own heartbeat row on every instance — ADR 20), and four claim rows with FOR UPDATE [SKIP LOCKED] instead (UploadSessionExpiryScheduler, ReconciliationWorkerScheduler, WebhookEventProcessorScheduler, ModerationSlaMonitorService). The lock advisor is ordered outermost (7e697d4a) so the transaction finishes before the lock is released. Lock expiry uses DB time.

    Consequences. Jobs use one TransactionTemplate per row, never a method-level @Transactional. Lock floors must be retuned with cadence (docs/deployment/scheduler-lock-tuning.md, deferred-123). Scheduling is off under the test profile (deferred-19) but ShedLock stays on, because ITs call jobs through the proxy.

    Where enforced. platform/notification/config/AsyncConfig.java (@EnableSchedulerLock), infrastructure/config/ShedLockConfig.java, SchedulerLockTransactionOrderingIT. See Scheduled Jobs.

    4. Routing DataSource with isolated pools

    Context. Some code opens a REQUIRES_NEW transaction while its caller still holds a connection: GDPR erasure (admin-triggered, per-child transactions) and payment settlement (reserveCapture, persistPaymentFailure, batch decline). With one pool, enough concurrent callers each holding one connection and waiting for a second can starve the pool.

    Decision. Give those acquisitions their own small Hikari pools. A second PlatformTransactionManager was tried and empirically disproved: the app has one EntityManagerFactory, which ignores any other DataSource. So routing happens inside the single DataSource bean: RoutingDataSource keyed by a thread-local RoutingDataSourceContext.

    Consequences. The key must be set before the @Transactional(REQUIRES_NEW) proxy opens its connection, hence the "thin non-transactional wrapper + self call" pattern. Extra pools must match the primary pool's auto-commit setting, or statements silently run outside a transaction.

    Where enforced. infrastructure/config/DataSourceConfig.java (GDPR_ERASURE_DATASOURCE_KEY, PAYMENT_REQUIRES_NEW_DATASOURCE_KEY), RoutingDataSource.java; BookingPaymentPersistenceService.reserveCapture, GdprErasureService.

    5. Flyway history squashed into V138 + V139

    Context. Before the first production deploy, history held several lock-unsafe ACCESS EXCLUSIVE migrations (V60, V94, V97, V98, V117, V124) grandfathered past MigrationLint, plus checksum-frozen files. Rewriting them online-safe would produce a byte-identical end state that only costs fresh installs.

    Decision. True squash, not a Flyway baselineVersion: delete V02–V137, add V138__baseline_schema.sql (pure DDL) and V139__baseline_seed_data.sql (seed rows). Expand/contract rules bind every migration from V140 on.

    Consequences. Every dev/UAT database had to be dropped and recreated. Migration numbers below 138 in old commits and comments exist only in git history. CREATE INDEX CONCURRENTLY is still not safe here even with the .sql.conf executeInTransaction=false sidecar (found during implementation).

    Where enforced. src/main/resources/db/migration/; MigrationConventionLintTest; docs/deployment/migration-rebaseline.md, docs/deployment/migration-conventions.md. See Database.

    6. Hash-mode router, so backend links go through FrontendLinkBuilder

    Context. The SPA runs vueRouterMode: 'hash' (src/frontend/quasar.config.js:40). No reason for choosing hash over history mode was recorded. The consequence was: hand-built backend links such as https://host/coach/payment-settings 404'd or landed on the SPA root, and some used the backend origin instead of the frontend's. The axios 401 redirect had the same bug (deferred-126).

    Decision. Every backend-generated link into the app (booking, report and account emails, the Stripe callback redirect) is built by FrontendLinkBuilder from app.frontend-url + /#/.

    Consequences. Query strings land inside the fragment, where vue-router reads them. Switching to history mode would need server-side SPA fallback and a sweep of this builder's callers and sessionRedirect.js.

    Where enforced. infrastructure/web/FrontendLinkBuilder.java; src/frontend/src/utils/sessionRedirect.js.

    7. Platform charges + completion-gated payouts, not destination charges

    Context. Payment used Stripe destination charges (transfer_data.destination + application_fee_amount), so the coach was paid at capture, days before the session. A cancellation, coach no-show or dispute then meant clawing money back from a connected account. deferred-63 asked for completion-gated payout.

    Decision. B-1, separate charges and transfers (owner sign-off 2026-09-09): charge the full price to the platform account with transfer_group = bookingId; on BookingCompletedEvent enqueue a COACH_PAYOUT_TRANSFER outbox row due after payment.payout.hold_hours (default 48). B-2 (manual capture) breaks on bookings more than 7 days out; B-3 (reversal on cancel) kept the problem.

    Consequences. Pre-completion cancellations are plain refunds of platform-held funds. There is no post-completion cancellation (disputes only, with COACH_PAYOUT_REVERSAL). Commission is locked at capture. Coach revenue reports are based on coach_payouts RELEASED.

    Where enforced. platform/payment/contract/PaymentGateway.java javadoc, StripePaymentGateway.chargeAndCapture, CoachPayoutOutboxSupport, CoachPayoutTransferHandler; docs/architecture/payout-and-capture-pending.md.

    8. CAPTURE_PENDING reservation before every Stripe charge

    Context. Settlement runs in an AFTER_COMMIT listener after accept. If it dies mid-capture, a later sweep cannot tell "never charged" from "charged, outcome unknown", and charging again risks a double charge.

    Decision. Before calling Stripe, reserveCapture commits a CAPTURE_PENDING booking_payments row in its own REQUIRES_NEW transaction. Invariant: for a PAYMENT_PENDING booking, no row means no Stripe call was attempted. Pack-funded and fully credit-covered settlements deliberately do not reserve.

    The reservation also carries the Stripe idempotency key the charge is sent under (booking_payments.charge_idempotency_key, V207), committed before the call and copied onto the PaymentIntent's chargeKey metadata. A charge whose outcome is unknown (timeout, lost connection, 5xx, idempotency conflict: ChargeOutcomeUnknownException) is no longer declined on the spot: ChargeOutcomeReconciler asks Stripe once the reservation is older than booking.payment.charge_reconcile_after_minutes (10) and settles, declines or waits. A charge that succeeded but cannot be settled is compensated (card share to the wallet), never kept.

    Consequences. A duplicate event landing on a reserved row is escalated (CAPTURE_UNCONFIRMED, reconcile by hand), never re-charged. Stale reservations exit via CAPTURE_ABANDONED (deferred-91 Part A). The caller must hold no lock or write on the booking row, or the second connection self-deadlocks.

    Where enforced. platform/payment/service/BookingPaymentPersistenceService.java (javadoc on reserveCapture), PaymentLifecycleService.java, ChargeOutcomeReconciler, PaymentPendingSweeper; ChargeIdempotencyIT.

    9. Slot exclusivity: per-coach row lock + DB exclusion constraint

    Context. Two parents booking the same coach slot, a coach accepting two overlapping requests, or a window edit racing a booking can all double-book a coach. A check-then-insert is a TOCTOU race unless writers serialise.

    Decision. Every slot-changing write path locks the coach's coach_profiles row first (findByIdForUpdate, NOWAIT + retry), then reads windows and blocks and runs the overlap query (Deferred-78 moved the lock before the window read). The exclusion constraint excl_bkg_coach_slot_overlap is the backstop for accepted-and-later statuses.

    Consequences. Overlapping REQUESTED rows are legal in the DB, so the app check is the only guard at creation. The constraint violation (SQLSTATE 23P01) maps to 409 booking.slotUnavailable. New write paths must take the same lock.

    Where enforced. BookingService.createBookingRequest / acceptBooking, RescheduleService, BookingBatchService, AvailabilityService; V138__baseline_schema.sql; ApiAdvice.resolveConstraintName. See Booking and the walkthrough.

    10. One password login: the legacy /authenticate → /otp stack was removed

    Context. The original login was POST /authenticate (JWTAuthenticationFilter) plus an email OTP at POST /otp, with in-memory brute-force counters. Story skillars-1.5 (2026-06-12) added the /api/auth/* family (DB-backed rate limiting, refresh-token rotation with theft detection, an account-verification gate) alongside it, removing nothing. The SPA has used only /api/auth/login since; the legacy pair stayed a live, public password oracle with its own counters and in-memory client blacklist, kept only because IT helpers logged in through it.

    Decision. Owner decision 2026-10-28 (follow-up list): delete it. The IT helpers moved to POST /api/auth/login (e2e/AdminLogin.login, same cookies), then the filters, TwoFactorLoginService, LoginInfo, FraudAwareAuthenticationManager, LoginAttemptsService and the FraudEvent blacklist were removed — and Spring's default formLogin() too, which was a second, unthrottled password check at POST /login. The registration phone/email OTP flows are unrelated and stay.

    Consequences. One login path, one rate limiter (now claimed per key with an advisory try-lock, so a parallel burst cannot exceed the budget), no second factor (user.otp_enabled is unread). main.login_info is unused and is dropped in a later release (expand/contract); the SEND_OTP email template stays in the enum so historical or queued envelopes still resolve.

    Where enforced. platform/security/config/SecurityConfiguration.java (filterChain); SecurityFilterChainIT.removedLegacyLoginEndpoints_doNotAuthenticate. See Security.

    11. filestorage is the only gateway to the blobstore

    Context. Quota, validation, presigned upload/confirm, soft-delete retention, audit and replication are domain rules. If feature modules call the S3 adapter directly, each reimplements or bypasses them.

    Decision. The provider-adapter pattern (_bmad-output/project-context.md): infrastructure.blobstore holds only the StorageService port, provider implementations, transport types and provider exceptions. platform.filestorage owns all file domain logic. Other modules go through FileStorageService and may import only blobstore contract exception types.

    Consequences. Video is the exception: it stores media in Bunny.net through infrastructure.video.VideoProviderAdapter, because it needs TUS upload, transcoding webhooks and signed playback (architecture.md). The rule is convention plus review — no architecture test enforces it today.

    Where enforced. Today the only blobstore imports outside filestorage/infrastructure are contract.exception types (ApiAdvice, CoachProfileService, CoachGalleryService). See Filestorage.

    12. Business config in platform_config, not properties

    Context. Tier entitlements, quotas, expiry windows, reminder intervals and commission are business knobs that admins must change without a deploy (FR-PLT-001).

    Decision. A typed key/value platform_config table behind ConfigService, with a per-node cache (default TTL 300 s). "No module reads application.yml for business rules" (architecture.md). application*.yaml keeps only infrastructure settings.

    Consequences. A change is not instant on other nodes: invalidate() clears only the serving instance's cache, and the rest wait for scheduledRefresh. Bad values are clamped at read time and, for ConfigBounds keys, fail startup (ConfigStartupAssertion, deferred-107). Seeds live in migrations. Read per use, never cache in a field.

    Where enforced. platform/config/service/ConfigService.java, ConfigBounds.java, admin edit API ConfigResource. See Config.

    13. One outbound email port with log / smtp / ses transports

    Context. Email had two stacks: a SesEmailService interface with one real implementation, a no-op and a dev-only bridge into SMTP. Registration/OTP mail was silently dropped in dev at one point (D4).

    Decision. A seven-phase plan (requirements/ses-email-consolidation.md): ses-1.1 introduced the transport-neutral OutboundEmailSender port with a neutral exception taxonomy, selected by app.email.transport; later phases put SMTP behind it and moved dev to log (ses-1.5).

    Consequences. An unknown transport value aborts startup (EmailTransportPropertyValidator). Dev never sends mail: it writes target/mails/<correlationId>.html. uat uses SMTP, prod SES. SMTP internals must not leak out of infrastructure/email/smtp.

    Where enforced. infrastructure/email/ (OutboundEmailSender, EmailTransport), @ConditionalOnProperty on each sender; EmailTransportArchitectureTest. See Notification.

    14. In-app inbox written BEFORE_COMMIT in a savepoint, with no push channel

    Context. The notification centre needed an inbox row for most transactional emails. The row must not exist if the business change rolls back, but a broken inbox write must never fail a booking.

    Decision. The inbox row is written next to the outbox enqueue, inside the producing transaction (NotificationOutboxSupport.enqueueEmail, or InAppEnvelopeListener for directly-published envelopes), wrapped in a JDBC savepoint and never thrown. No user-level push channel was built: messaging's SSE is per conversation, and none was built just for this (NotificationBell.vue comment).

    Consequences. The unread badge refreshes on mount, route change and window focus — not live. Which templates appear in-app, and for whom, is defined in one place (NotificationCatalog).

    Where enforced. platform/notification/service/InAppNotificationService.java, NotificationCatalog.java, src/frontend/src/components/notification/NotificationBell.vue.

    15. AbstractIntegrationTest inheritance + a pinned context count

    Context. About 88 ITs copied an annotation header (@SpringBootTest, @ActiveProfiles, @Import(TestConfig), @TestPropertySource). Any drift in it forked a new Spring context cache key, silently costing a full startup plus containers. By deferred-160 the failsafe JVM had 47 distinct contexts against a cache of 32, so contexts were evicted and rebuilt, and the count depended on class order (flaky gates).

    Decision. Every IT extends AbstractIntegrationTest (deferred-19). deferred-160 hoisted common mocks and spies onto it, renamed @WebMvcTest slices to *WebMvcTest so surefire runs them, and pinned the result: 14 base configurations + 3 allowlisted sliced classes = 17 contexts.

    Consequences. Adding a field-level @MockitoBean or a new @Import/property set in a subclass forks a context and fails CI. The gate also fails on a full cache or on rebuilds. The honest cost (one inheritance slot, less explicit test headers) is written up in docs/testing/why-inheritance-over-import.md.

    Where enforced. IntegrationTestConventionTest (EXPECTED_DISTINCT_CONTEXT_KEYS = 14), .github/scripts/assert-context-count.sh (ceiling 17, called from .github/workflows/pr-build.yml); docs/testing/readme.md.

    16. The tenant module was removed

    Context. A multi-tenant API-key module (/v1/admin/tenants and an API-key authentication chain) existed but was never used by the product. Every application endpoint is under /api/**, and its tests were already disabled.

    Decision. Delete it entirely (2026-08-08): the module, ApiKeyAuthenticationFilter, TenantSecurityConfig, TenantContext, its emails, i18n keys and migrations. Before deleting, the team checked that the removed @Order(1) /v1/** filter chain did not change protection for any surviving endpoint.

    Consequences. Skillars is single-tenant: no tenant_id, TenantContext or ROLE_TENANT. Any surviving reference is stale. The old Envers revinfo tables were kept because other audited entities depend on them.

    Where enforced. Nothing to enforce — the code is gone. See the callout on Home.

    17. A coach suspension / safety hold cancels upcoming bookings with a full refund and no strike

    Context. A suspension used to cancel only REQUESTED bookings: a suspended coach's CONFIRMED sessions stayed scheduled and paid for, and a child-safety (CSAM) hold could only log them. Cancelling them as the coach (CANCEL_COACH) would strike the coach and refund under the wrong actor.

    Decision. CANCEL_ADMIN is legal from every pre-session status (REQUESTED, ACCEPTED, PAYMENT_PENDING, CONFIRMED, UPCOMING), never from IN_PROGRESS / PAUSED. The payer is made whole only for money actually taken (captured = CONFIRMED / UPCOMING): card/credit to the credit wallet for what was paid, a pack session restored (or, for an expired pack, a wallet refund). No reliability strike, no cancellation history. The parent gets a neutral notice (BOOKING_CANCELLED_COACH_UNAVAILABLE, "the coach is unavailable") that never names the reason. An admin suspension does this by default with an opt-out (cancelUpcomingBookings); a safety hold always does it (after committing the takedown on its own, so booking contention cannot undo it), and raises an urgent SAFETY_HOLD_BOOKING alert per booking it cannot cancel. Since C6 (PR #361) an admin suspension is not all-or-nothing either: the suspension commits first, then each booking is cancelled in its own REQUIRES_NEW transaction; a booking that is busy (capture in flight, row locked) gets one retry and then becomes a BOOKING_ACTION_REQUIRED alert instead of failing the suspension with a 409. Only the safety hold freezes payouts (payment module).

    Consequences. Families are never left holding a session with a coach who cannot deliver it. Card portions are refunded as wallet credit, as for a coach cancellation (cash-out turns it back into a card refund). Live sessions and busy bookings still need a human: the alerts carry the parent contact in the queue summary, and the admin cancels them one by one with the single-booking cancel (POST /api/admin/bookings/{id}/cancel).

    Where enforced. BookingStateMachine, BookingService.cancelBookingAsAdmin, AdminCoachEnforcementService.applyAdminSuspension / cancelBookingForSuspension, RefundEnqueueListener / CancellationRefundService.onBookingCancelledByAdmin; CoachSuspensionCancelsUpcomingBookingsIT, BookingStateMachineTest.

    18. Minors never upload; coach videos of a child are linked to the session

    Context. Story 6.6 let minors upload and held the video in HIDDEN until a parent approved it (VideoApprovalService, /parent/approvals, three VIDEO_APPROVAL_* emails). The footage still reached Bunny and both moderation providers before anyone decided whether it should exist, and the approval path was unreachable in the data model anyway (only a user_id profile can upload, and those never carry a parent_id), so a minor's upload would have hit the "no parent" fallback and transcoded unapproved. Meanwhile a coach's review of a child's session was invisible to that child's parent.

    Decision. Product decision 2026-10-28, option A. (1) A player upload is allowed only for a self-registered adult profile; anything else is refused at initiation (and on retry) with 403 VIDEO_MINOR_UPLOAD_REFUSED plus an urgent admin alert, since reaching it means an invariant broke. The moderation minor layer stays as a fail-closed re-check (HIDDEN + alert, never "approve"). The approval machinery is deleted. (2) A coach video can name its subject: a COACH_REVIEW must, a DRILL_DEMO may, pick one of the coach's held sessions; the server takes the player from that booking. The player's parent(s), and the player if self-registered, may play it — no download, no delete. GDPR erasure of the player (account, parent account, or parent-requested child erasure) purges those coach videos rather than unlinking them. Consent for filming a child (option ii) is a follow-up with legal.

    Consequences. Videos uploaded before V184 stay unlinked — no parent sees them. Old HIDDEN videos from the approval gate stay HIDDEN (deletable). video_approval_requests has no reader or writer and is dropped in a later release (expand/contract). The VIDEO_APPROVAL_* EmailTemplate constants and CHECK values stay, @Deprecated, because stored envelope/inbox rows may carry them; /parent/approvals survives as a redirect to the parent dashboard for links in already-sent emails.

    Where enforced. MinorUploadPolicy (VideoResource initiate + retry, ModerationOrchestrationService), VideoSubjectService, VideoAccessGuard.isSubjectViewer, chk_videos_subject_pair (V184), AccountDeletionCascadeListener; tests MinorUploadPolicyTest, MinorSafetyGateIT, VideoSubjectServiceTest, AccountDeletionCascadeIT, GdprChildScopeIT. See Video.

    19. Pack- and credit-funded sessions are paid per completed session; a safety hold freezes payouts

    Context. ADR 7's payout only covered the card-charged part of a booking, so a coach was never paid for a session funded by a session pack or by wallet credit, although the platform held that money. A CSAM safety hold (B6) took the coach's profile down but left their pending payouts to release on schedule.

    Decision. (Owner, 2026-10-28.) Pay every completed session through the existing completion-gated payout, held payment.payout.hold_hours from completion: card + credit at the rate stamped at capture (one row, one transfer for a mixed booking); a pack session gets amount_charged / session_count (rounded down, the last session takes the remainder) at the rate stamped at pack purchase, allocated under the pack row lock so the total never exceeds what the pack was charged. Unused sessions of an expired pack are not paid out: the platform keeps that money. While a coach is under a CSAM safety hold their payouts are FROZEN and are released only when an admin reinstates the coach. Normal suspensions do not freeze payouts. Two per-payout freezes were added later (V193): dispute_frozen while a dispute on the booking is open, and chargeback_frozen while a card dispute on its charge is open. A payout releases only when none of the three stands.

    Consequences. A dispute on a pack session treats the pack share as the session price. Credit-funded transfers have no charge behind them and draw on the platform's available balance (BALANCE_INSUFFICIENT is retried). The admin finance commission figure is computed from coach_payouts.commission_amount, so it covers card, credit and pack sessions. Sessions completed before V186 are not paid retroactively.

    Where enforced. CoachPayoutOutboxSupport.enqueuePayout / allocatePackShare, CoachPayoutFreezeService, CoachPayoutAdjustmentService.freezeForDispute, the freeze check in CoachPayoutTransferHandler, DisputeService.paidForSession; CoachPayoutPackCreditIT.

    20. Single instance until SSE fan-out exists

    Context. Scheduled jobs, row locks, the outbox and the login rate limiter are multi-instance safe (ADR 3). Server-sent events are not: MessagingEmitterRegistry, BookingSseService and VideoSseService keep their SseEmitters in one JVM's memory, so on a second instance a user connected to the other node silently misses real-time events.

    Decision. Owner decision 2026-10-28 (item 4, option A): defer cross-instance fan-out and run a single instance. When scaling out becomes necessary, fan SSE events out through Postgres LISTEN/NOTIFY (no new infrastructure: every instance already holds a pool to the same database) before adding the second instance. Until then, make an accidental second instance visible: each instance upserts a heartbeat row in main.app_instance_heartbeat (V187) every minute and logs WARN status=MULTIPLE_INSTANCES while another instance's row is fresh (three beats). ShedLock's locked_by was rejected as the signal: it only shows whichever host last won a job lock.

    Consequences. The heartbeat job deliberately has no @SchedulerLock (each instance must beat for itself). Timestamps are the database's now(), so host clock skew cannot hide a peer. A graceful shutdown deletes its own row, so a rolling deploy only warns during the overlap. The skillars.app.instances.live gauge exposes the count.

    Where enforced. infrastructure/persistence/InstanceHeartbeatMonitor.java, InstanceHeartbeatMonitorIT; docs/deployment/deploy-guide.md ("Single instance only") and the runbook scenario "More than one application instance".

    21. Forfeits pay the coach; refunds cost the coach the same share; refused reversals become debt

    Context. The 2026-10-28 payment audit found the platform kept 100% of a forfeited session (player no-show, parent cancel inside 24h), a dispute could only ever take money from the coach, and the coach's share of a refund depended on timing: a refund before payout release cut the pending row, one after release reversed a transfer, and two partial refunds on a pending payout cut less than the same refunds after release. A reversal Stripe refused was left as an alert with nothing owed.

    Decision. (Owner, 2026-10-28.) A forfeit pays the coach the normal net through the usual completion-gated payout. A refund of r out of price p costs the coach originalNet × r / p whatever the payout's state: a pending/held/frozen payout is cut pro rata, a released one gets a COACH_PAYOUT_REVERSAL for that share. A dispute resolved UPHOLD_COACH claws the refunded credit back from the payer's wallet (up to the current balance, never negative) and pays the coach the full net (a top-up transfer if the payout was already cut); the platform absorbs any gap. A reversal Stripe refuses non-retryably is recorded as coach debt (payment.coach_payout_debts, V205) and alerted.

    Consequences. Refund paths must go through CoachPayoutAdjustmentService.applyRefund, never adjust coach_payouts directly. Dispute credits are capped per booking (DisputeCreditService, DISPUTE_CREDIT ledger type) and a dispute can only be resolved once the booking has settled (409 disputes.bookingNotSettled).

    Where enforced. CoachPayoutEnqueueListener (onPlayerNoShow, forfeit parent cancels), CoachPayoutAdjustmentService (applyRefund, payInFull), RefundClawbackService, CoachPayoutDebtService.recordDebt, CoachPayoutOutboxSupport.enqueueTopUp; ForfeitPayoutAndClawbackIT.
