Payment

Moves money between parents, coaches, and the platform — Stripe Connect payouts, credit wallets, subscriptions, session packs, and the reliability-strike system that keeps coach supply honest.

Business Overview

Skillars is a two-sided marketplace: parents pay for their kids' coaching sessions, and coaches need to get paid out reliably without the platform touching card numbers or bank details directly. The payment module is the single place where money actually moves. It owns four related but distinct concerns:

Coach payouts (Stripe Connect)

Coaches onboard via a Stripe Connect OAuth flow. Once Stripe confirms charges_enabled and payouts_enabled, the platform can create Destination Charges that split a booking's price into a coach payout and a platform commission in a single Stripe call.

Parent credit wallet

Refunds, admin adjustments, and pack-related reversals are never sent back to a card immediately — they land in an append-only parent_credit_ledger as store credit. Parents can later "cash out" that credit back to their card (minus a Stripe processing fee) or spend it on future bookings.

Subscriptions & session packs

Coaches subscribe to tiers (SCOUT/INSTRUCTOR/ACADEMY) that unlock marketplace visibility features; players/parents subscribe to tiers (ATHLETE/SEMI_PRO/PRO) that unlock video/skill-radar features. Parents can alternatively prepay a coach-defined session pack (bulk sessions at a fixed per-session price) instead of paying per booking.

Reliability strikes

Coaches who cancel late or no-show accumulate strikes. A rolling 30-day strike count drives two marketplace consequences: reduced search visibility, then suspension pending admin review — this is the module's main trust & safety lever over coach behavior.

Key business rules found in the code

Commission & fees. Every Stripe destination charge deducts a platform commission (platform.commission.rate, config-driven) as application_fee_amount, on top of Stripe's own processing fee (payment.stripe.feeRate + payment.stripe.feeFixed), which is also charged separately to parents cashing out credit.

Cancellation refund matrix. Parent cancellations only refund if made >24h before the session (event.isRefundEligible()); otherwise the session/credit is forfeited. Coach cancellations and coach no-shows always refund the parent (credit or restored pack session) and, unless the reason is one of MUTUAL_AGREEMENT, HEALTH_MEDICAL, FAMILY_EMERGENCY, WEATHER, also trigger a reliability strike. Player no-shows forfeit the fee with no refund and no strike.

Reliability thresholds. Counting strikes in the trailing 30 days: reaching reliability.strike.visibilityThreshold (default 3) reduces marketplace visibility; reaching reliability.strike.suspensionThreshold (default 5) moves the coach to PENDING_REVIEW for manual admin action. These two outcomes are mutually exclusive per invocation — suspension is checked first.

Session packs expire and can be extended once. A purchased pack expires 60 days after purchase. The coach can extend it by 30 more days, but only once (extendedAt must be null) and only within a 14-day window before expiry. Packs nearing expiry with sessions remaining trigger a daily warning notification 14 days out — stamped with expiryWarnedAt so a 14-day window scanned by a daily cron doesn't email the same parent fourteen mornings in a row.

A pack can be paused exactly once per lifetime. pausePack refuses if pausedUntil is already set. The pause length is bounded by the pack.pause.maxDays config key, must start today or later, and must start before the pack expires. Pausing pushes expiresAt out by the pause length. If any of the parent's bookings with that coach fall inside the pause window, the first call returns them without applying the pause (PauseConflictResponse.applied = false); the client re-submits with confirmedCancellationIds to cancel them and commit the pause — a deliberate two-step confirm flow, not an error.

Unused sessions are forfeited at expiry, not refunded. SessionPackForfeitureScheduler runs hourly, stamps expiredNotifiedAt, and fires SessionPackExpiredEvent carrying the remaining count so the parent is told what they lost. No credit is written back to the wallet.

Subscription tier changes are asymmetric. Upgrades apply immediately with Stripe proration; downgrades are scheduled to take effect at the current billing period's end via a *_subscription_changes table, applied by a nightly cron job. Player SEMI_PRO/PRO tiers are yearly-billing only.

Key Flows

Coach Stripe Connect onboarding

sequenceDiagram
  participant Coach as Coach (browser)
  participant API as StripeOnboardingResource
  participant Svc as StripeOnboardingService
  participant Stripe as Stripe OAuth
  participant DB as coach_stripe_accounts

  Coach->>API: GET /coaches/me/stripe/onboard
  API->>Svc: generateOnboardingUrl(coachId)
  Svc->>Stripe: OAuth.authorizeUrl(state=coachId)
  Stripe-->>Svc: authorize URL
  Svc-->>Coach: StripeOnboardingUrlResponse
  Coach->>Stripe: redirected, approves Connect access
  Stripe-->>API: GET /coaches/me/stripe/callback?code&state
  API->>API: validate state == coachId (CSRF guard)
  API->>Svc: handleOAuthCallback(coachId, code)
  Svc->>Stripe: OAuth.token(code)
  Stripe-->>Svc: stripe_user_id (connected account id)
  Svc->>DB: upsert CoachStripeAccount(status=PENDING)
  API-->>Coach: redirect to /coach/payment-settings

Onboarding uses Stripe's OAuth Connect flow rather than embedded Account Links — the coach is redirected to Stripe, authorizes access, and Stripe redirects back to a backend callback endpoint (not the frontend) with a one-time code and the original state value. The controller checks that state equals the authenticated coach's id before exchanging the code, which prevents an attacker from linking their own Stripe account to a victim coach's session (CSRF account-linking). The account starts in PENDING status; it only flips to COMPLETE later, asynchronously, via the account.updated webhook — the OAuth callback itself never sets chargesEnabled/payoutsEnabled.

Stripe webhook: idempotent, signature-verified event processing

sequenceDiagram
  participant Stripe
  participant WH as StripeWebhookResource
  participant Svc as StripeWebhookService
  participant Idem as stripe_webhook_events
  participant Acct as CoachStripeAccount
  participant Sub as SubscriptionService

  Stripe->>WH: POST /webhooks/stripe (Stripe-Signature header)
  WH->>Svc: processWebhook(payload, sigHeader)
  Svc->>Svc: Webhook.constructEvent (verify signature, outside TX)
  Svc->>Idem: INSERT eventId ON CONFLICT DO NOTHING (in TX)
  alt duplicate event (0 rows inserted)
    Idem-->>Svc: no-op, return
  else new event
    alt account.updated
      Svc->>Acct: set chargesEnabled / payoutsEnabled
      Svc->>Acct: status = COMPLETE or RESTRICTED
      Svc-->>Svc: publish CoachStripeOnboardingCompleteEvent after commit
    else customer.subscription.updated / deleted
      Svc->>Sub: handleSubscriptionWebhook(type, subId, data)
      Sub->>Sub: sync status / currentPeriodEnd, or reset to free tier
    else invoice.payment_failed
      Svc->>Sub: mark PAST_DUE, stamp pastDueSince (first failure only)
    end
  end
  WH-->>Stripe: 200 OK

Signature verification happens outside any transaction; the idempotency insert and the actual event handling then run atomically inside one @Transactional method (handleEventAtomically) via a self-injected proxy, so a duplicate Stripe retry can never partially apply an event. If the SDK fails to deserialize the payload for account.updated or invoice.payment_failed, the handler re-throws so the whole transaction — including the idempotency row — rolls back, letting Stripe retry until the deserialization bug is fixed rather than silently losing the event forever.

Booking payment capture: credit wallet + Stripe destination charge

sequenceDiagram
  participant Booking as BookingService
  participant Life as PaymentLifecycleService
  participant Wallet as CreditWalletService
  participant Gateway as StripePaymentGateway
  participant Persist as BookingPaymentPersistenceService

  Booking-->>Life: BookingAcceptedEvent (AFTER_COMMIT)
  Life->>Wallet: getBalance(parentId)
  Wallet-->>Life: creditBalance
  Life->>Life: creditToUse = min(balance, price)
stripeAmount = price - creditToUse
  alt stripeAmount > 0
    Life->>Gateway: chargeAndCapture(bookingId, parentId, coachId, stripeAmount)
    Gateway->>Gateway: Destination Charge, transfer_data.destination = coach account,
application_fee_amount = commission
    Gateway-->>Life: stripePaymentIntentId
  end
  Life->>Persist: persistPaymentSuccess(creditDebited, stripeCharged, ...)
  Persist->>Persist: write BOOKING_DEDUCTION ledger entry (if credit used)
  Persist->>Persist: save BookingPayment(status=CAPTURED)
  Persist->>Booking: transition(PAYMENT_CAPTURED)
  Persist-->>Booking: publish BookingConfirmedEvent

Credit is applied first, and Stripe is only charged for the remainder — so a parent with full credit coverage never touches Stripe for that booking. The Stripe call happens outside any local transaction (network I/O should never hold a DB transaction open); only after it succeeds (or is skipped entirely) does BookingPaymentPersistenceService commit the ledger entry, the BookingPayment row, and the booking's state transition to CONFIRMED as one atomic unit. If the Stripe charge throws, the booking is instead transitioned to PAYMENT_FAILED and no credit is ever debited. The batch variant (onBatchBookingAccepted) applies the same logic across many bookings sharing one Stripe charge, splitting the credit/Stripe amounts proportionally per booking afterward.

Conventions & Gotchas

Never skip webhook signature verification or idempotency. /api/payment/webhooks/stripe is permitAll by necessity (Stripe doesn't send session cookies), so Webhook.constructEvent(...) is the only thing standing between this endpoint and anyone on the internet forging account/subscription state changes. Any new webhook handler must also go through StripeWebhookService.handleEventAtomically so the stripe_webhook_events insert-if-absent still protects against Stripe's at-least-once retry delivery.

Stripe SDK calls must stay outside @Transactional methods. The services deliberately split "make the Stripe network call" from "persist the result" into separate methods, invoked through a @Autowired @Lazy self-reference so Spring's transactional proxy is honoured on the persistence half only (a direct this.foo() call bypasses the proxy). Wrapping a Stripe call inside a DB transaction risks holding a row lock or connection for the duration of a slow external HTTP call.

The credit ledger is append-only. parent_credit_ledger rows are never updated or deleted — balance is always SUM(amount) via ledgerRepository.sumByParentId. Compensating a failed operation means writing a new reversal row (e.g. CASH_OUT_REVERSAL), never mutating the original entry. Cash-out debits run at SERIALIZABLE isolation specifically to prevent two concurrent cash-out requests from both reading a stale balance and double-spending the same credit.

A coach can't be charged through until Stripe onboarding is COMPLETE. StripePaymentGateway.resolveCoachStripeAccountId throws payment.coachStripeNotConfigured (mapped to HTTP 422, logged at WARN not ERROR since it's an expected state) if the coach's onboarding_status isn't COMPLETE with charges_enabled true. This is booking's most common "why did payment fail" support case.

Session pack deduction/restoration uses a pessimistic lock. PackSessionService reads via findByIdForUpdate, not the plain repository finder, because concurrent bookings against the same pack (e.g. two devices) would otherwise both read the same remainingSessions and both decrement from it, under-counting the deduction.

PaymentPendingSweeper deliberately ignores credit/Stripe-funded stranded bookings. Do not "complete" it by dropping the pack-funded precondition. Settlement runs as an in-process AFTER_COMMIT listener with no retry and no dead-letter queue, so a JVM death between the PAYMENT_PENDING commit and settlement strands the booking — and because PAYMENT_PENDING is in ACTIVE_SLOT_STATUSES and in V87's exclusion constraint, that row holds the coach's slot forever.

The sweeper only recovers pack-funded bookings because those are the only ones it can decide safely. On the Stripe path chargeAndCapture runs before the DB writes that record it, so a crash in between leaves money captured at Stripe with no booking_payments row and no ledger entry — and there is no capture-lookup API, no handled payment_intent.* webhook, and no other durable trace. Nothing distinguishes "never charged" from "charged and lost the record", so auto-declining would risk handing back the slot while the parent stays charged for nothing. Pack-funded settlement never calls Stripe, which is what makes it decidable. The prerequisite fix — a durable pre-capture record plus status-aware idempotency checks in PaymentLifecycleService — is tracked in deferred-work.md under the skillars-deferred-15 audit block.

Local development: Stripe webhooks without a public URL

Stripe can only deliver webhooks (subscription renewals, dispute events, Connect onboarding completion) to a publicly reachable URL, which localhost isn't. For local iteration, use the Stripe CLI to forward Stripe's test-mode events to your machine instead of registering a real webhook endpoint:

stripe listen --forward-to localhost:9990/api/payment/webhooks/stripe

First run prints a whsec_... signing secret — set that as APP_PAYMENT_STRIPE_WEBHOOK_SECRET (it's different from any secret shown in the Dashboard; the CLI signs forwarded events with its own key) and APP_PAYMENT_STRIPE_API_KEY to a sk_test_... key from the Dashboard (Developers → API keys, with Test mode on). Also set APP_PAYMENT_STRIPE_PUBLISHABLE_KEY to the matching pk_test_... key — the frontend fetches it from GET /api/payment/stripe/config to initialise Stripe Elements; without it, card-collection UI shows the "unavailable" state instead of throwing. Trigger events on demand with stripe trigger payment_intent.succeeded etc. instead of driving the full UI flow each time.

Use the standard secret key (sk_test_...), not a Restricted key (rk_test_...). StripeOnboardingService exchanges Connect OAuth codes via OAuth.token, which Stripe only accepts with the account's standard secret key — a Restricted key fails that call no matter which permissions it's granted, even though it would work fine for the PaymentIntent/Refund/Subscription calls elsewhere in this module.

This is a local-only substitute for a real endpoint. Once the app is deployed somewhere publicly reachable (e.g. the UAT box in uat-deployment.md), register a real webhook endpoint against that domain in the Stripe Dashboard instead — stripe listen only forwards to whichever machine is running it, so it isn't a substitute for a real endpoint once other people need webhooks to reach the same server.
