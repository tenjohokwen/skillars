Security

Identity, authentication, and account lifecycle for every persona on Skillars — Players, Parents, Coaches, and Admins.

Business Overview

The security module is the front door for all four Skillars personas. It owns the User row that every other module ultimately joins against, and it is the only module allowed to mint the JWT/refresh-token pair that proves "who is making this request." Everything from booking a coach to viewing a radar assessment depends on this module having already authenticated the caller and attached the correct role and verification status to the security context.

Because Skillars serves minors, registration is not one flow but four, each with different rules:

  • Coach and Parent registration — adult-only, no date-of-birth collected (a placeholder DOB of 1900-01-01 is stored since it is irrelevant to those roles). Both follow the same register → email-verify → phone-OTP-verify → BASIC_VERIFIED pipeline.
  • Player (self-registration) — only permitted for adults (18+). PlayerRegistrationService rejects registration outright for anyone under 18 (via AgePolicyService.isMinor) rather than silently downgrading them; minors are expected to be registered by a parent instead.
  • Player (shadow account) — a Parent creates a PlayerProfile for their child via ShadowAccountResource/ShadowAccountService. A PlayerProfile is not a User: it has no login of its own for minors, and is linked to the parent's account through ParentPlayerLink. If the child is a minor, explicit parentConsent and a consentPolicyVersion must be supplied (GDPR/COPPA-style consent capture) before the profile is created.

Age itself drives business rules beyond registration: AgePolicyService buckets players into U10, AGE_10_12, AGE_13_17, and ADULT tiers, and derives a MessagingPolicy per tier (U10 players cannot message at all; 10-12 is parent-managed; 13-17 is supervised; adults are unrestricted). This is consumed by the messaging module, not enforced there, so a new engineer wiring up messaging must call back into security for the policy rather than re-deriving age rules locally.

Admins get a narrow, purpose-built surface here too: AdminLoginResource lets an ADMIN/LTD_ADMIN clear a locked-out user's login-attempt cache without waiting out the 4-hour window, and UserAdminService runs a scheduled job that purges accounts that never activated.

Key Flows

Coach / Parent / Player self-registration & verification

sequenceDiagram
  participant U as User (Coach/Parent/Player)
  participant R as *RegistrationResource
  participant S as *RegistrationService
  participant DB as user / email_verification_tokens / phone_otp_tokens
  participant N as notification (email)

  U->>R: POST /api/security/{role}/register
  R->>S: register{Role}(request)
  S->>S: validate email unique, sanitize name
  alt Player only
    S->>S: AgePolicyService.isMinor(dob)? reject if true
  end
  S->>DB: save User (UNVERIFIED, INACTIVE)
  S->>N: publish {Role}VerificationEmailEvent
  N-->>U: verification email with token link

  U->>R: GET /api/security/{role}/verify-email?token=...
  R->>S: verifyEmail(token)
  S->>DB: validate token, mark used
  S->>DB: User.verificationStatus = EMAIL_VERIFIED, activated=true
  S->>DB: save PhoneOtpToken
  S->>N: publish {Role}OtpEmailEvent
  N-->>U: OTP code

  U->>R: POST /api/security/{role}/verify-phone {userId, otp}
  R->>S: verifyPhone(userId, otp)
  S->>DB: check rate limit, hash-compare OTP
  S->>DB: User.verificationStatus = BASIC_VERIFIED
  S-->>U: 200 OK (can now log in)

All three roles share the same underlying tables (email_verification_tokens, phone_otp_tokens) and the same three-step state machine: UNVERIFIED → EMAIL_VERIFIED → BASIC_VERIFIED. Login is blocked by AuthService until BASIC_VERIFIED is reached for any user with a non-null skillarsRole. OTP codes are never stored in plaintext — only their SHA-256(otp+userId) hash is persisted, and phone-OTP verification is itself rate-limited per user via RateLimitingService.

Parent creates a shadow player profile (minor)

sequenceDiagram
  participant P as Parent (logged in)
  participant SR as ShadowAccountResource
  participant SS as ShadowAccountService
  participant AP as AgePolicyService
  participant DB as player_profiles / parent_player_links

  P->>SR: POST /api/security/players {name, dob, position, parentConsent, consentPolicyVersion}
  SR->>SS: createPlayerProfile(parentId, request)
  SS->>AP: getAgeTier(dob) / isMinor(tier)
  alt isMinor and no parentConsent
    SS-->>SR: throw ShadowAccountException(parentConsentRequired)
  end
  SS->>DB: save PlayerProfile (parentId set, consent timestamp/version)
  SS->>DB: save ParentPlayerLink (unique per player)
  SS-->>SR: PlayerProfileResponse
  SR-->>P: 201 Created

A PlayerProfile created this way has no login credentials of its own — the parent's User account is the authentication boundary. Every subsequent read (GET /api/security/players/{playerId}) is gated by PlayerOwnershipGuard, which checks the ParentPlayerLink table rather than trusting a role check alone. A unique DB constraint on parent_player_links prevents a second parent from linking the same player, surfaced as a 409 via ShadowAccountException.

Login and refresh-token rotation

sequenceDiagram
  participant C as Client
  participant AR as AuthResource
  participant AS as AuthService
  participant DB as login_attempts / refresh_tokens / user

  C->>AR: POST /api/auth/login {email, password}
  AR->>AS: login(email, password, ip)
  AS->>DB: countByIdentifier(sha256(email|ip)) within lock window
  alt too many recent failures
    AS-->>AR: throw LoginRateLimitedException (429)
  end
  AS->>DB: findOneByLogin, check password, activated, verificationStatus
  AS->>DB: save RefreshToken (hashed)
  AS-->>C: Set-Cookie potc (JWT), rtkn (refresh), skp (profile)

  C->>AR: POST /api/auth/refresh (rtkn cookie)
  AR->>AS: refresh(req, res)
  AS->>DB: findByTokenHash
  alt token already used, within 30s grace window
    AS->>DB: find successor token (multi-tab race, not theft)
  else token already used, outside grace window
    AS->>DB: markAllUsedByUserId (revoke all sessions)
    AS-->>C: 401 "Token reuse detected"
  end
  AS->>DB: mark old token used+rotatedAt, save new RefreshToken
  AS-->>C: new potc/rtkn cookies

Login failures are rate-limited by a SHA-256 hash of email|ip (canonicalising IPv6-loopback and ::ffff:-prefixed addresses first) so an attacker cannot lock out a legitimate user by hammering a different IP under the same email, nor vice versa. Refresh-token reuse detection distinguishes a genuine theft from an ordinary multi-tab race: if the presented (already-used) token was rotated less than 30 seconds ago, the caller is redirected to the current successor token instead of having all sessions revoked.

Conventions & Gotchas

Two parallel authentication systems coexist. AuthResource/AuthService (JWT + hashed RefreshToken in refresh_tokens, cookies potc/rtkn/skp) is the current mechanism for the four persona roles. The older LoginAttemptsService/TwoFactorLoginService/LoginInfo path backs the legacy form-login + email-OTP 2FA flow used by admin-style accounts with no skillarsRole. Don't assume rate-limiting or lockout behavior from one path applies to the other — they use entirely separate storage and counters.

Minors never get a standalone login. A minor's PlayerProfile has parentId set and userId null — there is no User row for them. Only adult self-registered players get userId set (and no parentId). Code that assumes every PlayerProfile maps 1:1 to a User will break for the (majority) minor case.

ApiAdvice maps DB constraint names to error keys — keep the two tables in sync. CONSTRAINT_MAPPINGS turns a named constraint violation into a message key, and CONFLICT_CONSTRAINTS lists the ones that should be 409 rather than 400. Booking's excl_bkg_coach_slot_overlap exclusion constraint appears in both, so a double-booking caught at the database surfaces as a clean booking.slotUnavailable 409 instead of a raw 500. If you add a named constraint a user can plausibly trip, add it here too — see Database & Migrations.

Lock-wait timeouts fail fast as 409, not 500. ApiAdvice handles PessimisticLockingFailureException and returns generic.conflict. This pairs with the bounded jakarta.persistence.lock.timeout hint on CoachProfileRepository.findByIdForUpdate (5s), so contention on a popular coach's row fails cleanly rather than blocking the request thread indefinitely.

AgePolicyService has two variants and they differ on purpose. getMessagingPolicy(playerId) throws UserNotFoundException on an unresolvable player — the safe answer on write paths. findMessagingPolicy(playerId) returns an Optional instead, for read paths where an orphaned player_profiles row should cost the one conversation or label that depends on it rather than failing the whole listing. Both delegate to the same private resolvePolicy, so the tier-boundary config lookups can't drift apart.

Verification status gates login, not just registration. Any User with a non-null skillarsRole (coach/parent/player) must reach SkillarsVerificationStatus.BASIC_VERIFIED before AuthService.login() will let them in, even if activated is true. Admin-style users (skillarsRole == null) skip this check entirely.

AgePolicyService is the single source of truth for age tiers. Thresholds (U10/young-teen/teen max ages) are config-driven via ConfigService with hardcoded fallbacks in AgePolicy.defaults(). Don't hardcode age comparisons elsewhere (e.g. in messaging or marketplace) — call getAgeTier/isMinor/getMessagingPolicy instead so a config change takes effect everywhere at once.

OTPs and passwords are always hashed at rest. Phone OTPs are stored as SHA-256(otp + userId), refresh tokens as SHA-256(rawToken), and passwords via BCryptPasswordEncoder. There is no code path that reads a plaintext credential back out of the database — plan test/debug tooling accordingly.
