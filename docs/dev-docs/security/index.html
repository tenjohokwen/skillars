    Security

    Identity, authentication, and account lifecycle for every persona on Skillars — Players, Parents, Coaches, and Admins.

    Business Overview

    The security module is the front door for all four Skillars personas. It owns the User row that every other module ultimately joins against, and it is the only module allowed to mint the JWT/refresh-token pair that proves "who is making this request." Everything from booking a coach to viewing a radar assessment depends on this module having already authenticated the caller and attached the correct role and verification status to the security context.

    Because Skillars serves minors, registration is not one flow but four, each with different rules:

    • Coach and Parent registration — adult-only, no date-of-birth collected (a placeholder DOB of 1900-01-01 is stored since it is irrelevant to those roles). Both follow the same register → email-verify → phone-OTP-verify → BASIC_VERIFIED pipeline.
    • Player (self-registration) — only permitted for adults (18+). PlayerRegistrationService rejects registration outright for anyone under 18 (via AgePolicyService.isMinor) rather than silently downgrading them; minors are expected to be registered by a parent instead. After verification the player creates their own PlayerProfile (POST /api/security/players/me).
    • Player (shadow account) — a Parent creates a PlayerProfile for their child via ShadowAccountResource/ShadowAccountService. A PlayerProfile is not a User: it has no login of its own for minors, and is linked to the parent's account through ParentPlayerLink. If the child is a minor, explicit parentConsent and a consentPolicyVersion must be supplied (GDPR/COPPA-style consent capture) before the profile is created.

    The phone-OTP step is switchable: with config key security.registration.phone-otp-required = false (default true), /verify-email sends the user straight to login and EMAIL_VERIFIED is enough to sign in.

    Age itself drives business rules beyond registration: AgePolicyService buckets players into U10, AGE_10_12, AGE_13_17, and ADULT tiers, and derives a MessagingPolicy per tier (U10 players cannot message at all; 10-12 is parent-managed; 13-17 is supervised; adults are unrestricted). This is consumed by the messaging module, not enforced there, so a new engineer wiring up messaging must call back into security for the policy rather than re-deriving age rules locally.

    Admin account enforcement (search, suspend/reactivate, unlock login) is driven from the Admin module's AdminUserService (/api/admin/users, frontend src/frontend/src/pages/admin/AdminUsersPage.vue), but every lever it pulls lives here: the user.locked flag, securitySessionInvalidatedAt, refresh-token revocation, and the login rate-limit tables. GDPR self-service (export/erasure, /api/gdpr) is likewise an admin-module feature that writes security-owned rows. This module keeps a narrow admin surface of its own: UserAdminService (lock, delete, and the nightly purge of never-activated accounts). Clearing a login lock is the admin console's POST /api/admin/users/{id}/unlock-login.

    Key services

    ServiceOrchestrates
    AuthServiceSPA login (DB-backed rate limit on SHA-256(email|ip), config security.login.max-attempts = 5 / security.login.lock-window-minutes = 15), refresh-token rotation with reuse/theft detection and a 30s multi-tab grace window, logout, and the potc/rtkn/skp cookies. ensureAccountIsLive (activated, then not locked) gates both login and refresh. Also clearLoginRateLimit/countRecentFailedAttempts (by subject_hash) for admin unlock.
    AccountManagementFacadeLegacy account registration (/v1/account/register), activation and password-reset orchestration used by AccountResource/ProfileResource; delegates to email/SMS strategies and is @RateLimited per IP (register 5/60min, resend 3/30, reset-init 3/15, reset-finish 5/10, change-email 5/60).
    CoachRegistrationService, ParentRegistrationService, PlayerRegistrationServiceNear-identical register → email-verify → phone-OTP-verify → BASIC_VERIFIED pipelines per role, differing mainly in DOB handling and the events they publish. Each method is @RateLimited per IP ({role}_register 3/60min, {role}_verify_email 10/10, {role}_resend_verification 3/30, {role}_resend_otp 3/30). ParentRegistrationService maps a user_phone_key violation (by constraint name, after saveAndFlush) to a phone-in-use error.
    RegistrationOtpResendSupportThe shared body of the three resendPhoneOtp methods: per-user rate cap, OTP re-issue, role-specific OTP email event.
    RegistrationVerificationTokenServiceIssues/verifies the opaque phone-verification handle (base64url(payload).base64url(HmacSHA256) over role, userId, expiry, 24h) returned by /verify-email and required by /verify-phone and /resend-otp, so those permitAll endpoints never take a raw userId. Keyed by skillars.platform.registration-verification-secret; aborts startup if unset.
    OtpHasherSole owner of phone_otp_tokens.otp_hash: HmacSHA256(otpKey, userId:otp), with otpKey derived from registration-verification-secret under a fixed purpose label (never equal to the handle-signing key).
    ShadowAccountServiceCreates/lists/fetches PlayerProfiles for parent-managed minors (with consent enforcement) and self-registered adults; updates position (updateOwnPosition/updateChildPosition); hides GDPR-erased children from listings. There is no "link another parent" path: one parent per player is enforced by uq_ppl_player_id.
    UserService / UserProfileServiceUser/profile lookups and self-service profile mutations (email, password, phone, address, info), each publishing an AccountChangeEvent for audit/notification.
    AgePolicyServiceConfig-driven age-tier calculation and derived MessagingPolicy (getMessagingPolicy, findMessagingPolicy, batch findMessagingPoliciesByPlayerIds), shared by shadow-account creation, player self-registration and messaging.
    LoginRateLimiterThe one failed-login limiter, in main.login_attempts keyed by SHA-256(login|ip): checkLimited, recordFailure, admin clear/countRecentFailures. Budget/window from security.login.max-attempts / lock-window-minutes. Used by AuthService.login and by the legacy /authenticate path, with the same key, so the two share one budget. The legacy path also checks isAccountLimited (same budget across all IPs); the SPA path does not, to avoid account-DoS.
    LoginAttemptsService / LoginDecisionManagerLogin decision for the legacy /authenticate path (FraudAwareAuthenticationManager): delegates counting to LoginRateLimiter (failures are recorded where /authenticate rejects a password, not from the app-wide BadCredentialsEvent). Only the FraudEvent-fed client blacklist (30 days) is still in memory, per instance.
    TwoFactorLoginServiceGenerates and validates the email OTP for the legacy /authenticate → /otp flow (distinct from the registration phone OTP).
    LoginTokenManager / JwtManagerImplMint, extend and delete the JWT cookie set (potc, user, rint, ION, skp…). The JWT carries ROLES and sessIat (SESSION_ISSUED_AT); role precedence for a multi-role claim set is explicit ADMIN > COACH > PARENT > PLAYER, and a null/non-string ROLES claim is rejected cleanly.
    PasswordResetServiceReset-key issuance/validation and password completion, delegating invariant checks to User domain methods.
    UserAdminServicelockUserAccount, deleteUserInformation, and the nightly removeNotActivatedUsers purge (batched, capped at 10,000 delete attempts per run, failures recorded in user.cleanup* columns).
    AuthCleanupServiceHousekeeping: hourly purge of expired refresh tokens and half-hourly purge of login_attempts older than 24h.
    AdminBootstrapRunner / JwtSecretBootstrapRunnerOpt-in startup runners. The first creates the first ROLE_ADMIN from app.bootstrap.admin.* (never elevates an existing user; fails boot on misconfiguration, swallows data errors). The second creates the JWT signing Secret when app.bootstrap.jwt-secret.enabled=true, and refuses to run unless the datasource host resolves to loopback/private space.
    SecurityUtilCentral "who is the current user" helper — getCurrentUser(), requireCurrentUserId(), requireCurrentBusinessId(), getCurrentCoachUserId(), role checks — plus session teardown: terminateSession (revoke the cookie's refresh token REQUIRES_NEW + clear cookies) and clearAuthCookies (cookies only).
    PlayerOwnershipGuardSpEL bean (@playerOwnershipGuard.check(authentication, #playerId)) that passes if the caller is the profile's parent or the self-registered player who owns it. owns(callerUserId, playerId) is the same check for service-layer use when the player id is only known after loading a row (e.g. homework).
    DevelopmentDataErasureGuardMANDATORY-propagation check that takes the player_profiles row lock and reports whether development data was GDPR-erased. Called by TimelineEventListener and HomeworkAssignmentService before they write, so a write can never land after an erasure's delete.

    Published (via ApplicationEventPublisher):

    • UserRegisteredEvent, CoachVerificationEmailEvent/CoachOtpEmailEvent, ParentVerificationEmailEvent/ParentOtpEmailEvent, PlayerVerificationEmailEvent/PlayerOtpEmailEvent — registration/verification emails and OTP codes per role.     Key Flows

    The two login stacks

    Both stacks are still wired in SecurityConfiguration.filterChain, and both end in the same JWT cookie (potc) checked by the same JWTAuthorizationFilter on every secured request. They differ in how the caller proves identity and which brute-force counters apply:

    SPA stack (in use)Legacy stack (wired, not used by the SPA)
    EntryPOST /api/auth/login → AuthResource/AuthServicePOST /authenticate (JWTAuthenticationFilter) → POST /otp (SecondFactorLoginFilter)
    Who uses itLoginPage.vue for every persona, admins included (admins get role = "ADMIN" in skp because their skillarsRole is null)No in-app caller (the SPA's authApi.login/verifyOtp and OtpPage.vue were removed). ITs still log in through it (e2e/AdminLogin, ConfigResourceIT, StorageResourceIT, ReportGenerationServiceIT)
    Second factorNoneOnly when User.otpEnabled (the authenticated principal comes from the user row); email OTP via TwoFactorLoginService/LoginInfo
    Brute-force countersOne DB-backed limiter for both: LoginRateLimiter over main.login_attempts, same SHA-256(login|ip) key, so failures on either path count against both
    Refreshrtkn rotation via POST /api/auth/refreshSliding-window extension only (GET /refresh)
    LogoutPOST /api/auth/logout (revokes the refresh token)POST /api/logout (Spring logout; also revokes the refresh token)

    Coach / Parent / Player self-registration & verification

    sequenceDiagram
  participant U as User (Coach/Parent/Player)
  participant R as RoleRegistrationResource
  participant S as RoleRegistrationService
  participant DB as user / email_verification_tokens / phone_otp_tokens
  participant O as notification outbox

  U->>R: POST /api/security/{role}/register
  R->>S: register (RateLimited per IP)
  S->>S: validate email unique, sanitize name
  alt Player only
    S->>S: AgePolicyService.isMinor(dob)? reject if true
  end
  S->>DB: save User (UNVERIFIED, inactive)
  S->>O: RoleVerificationEmailEvent, enqueued BEFORE_COMMIT
  O-->>U: verification email with token link

  U->>R: GET /api/security/{role}/verify-email?token=...
  R->>S: verifyEmail(token) (RateLimited 10 per 10 min per IP)
  S->>DB: reject used/expired token, reject locked user
  S->>DB: UNVERIFIED to EMAIL_VERIFIED, activated=true, mark token used
  alt phone-otp-required = false
    S-->>U: nextStep=login
  else
    S->>DB: saveAndFlush PhoneOtpToken (HMAC hash, 10 min)
    S->>O: RoleOtpEmailEvent
    S-->>U: nextStep=verify-phone + signed verificationToken
  end

  U->>R: POST /api/security/{role}/verify-phone {verificationToken, otp}
  R->>R: RegistrationVerificationTokenService.resolveUserId(token, role)
  R->>S: verifyPhone(userId, otp)
  S->>DB: find live OTP, check expiry, then rate limit (userId:otpId, 5 per 10 min)
  S->>DB: reject locked user / wrong status, OtpHasher.matches
  S->>DB: EMAIL_VERIFIED to BASIC_VERIFIED, OTP used
  S-->>U: 200 OK (can now log in)

    All three roles share the same tables and the same state machine: UNVERIFIED → EMAIL_VERIFIED → BASIC_VERIFIED. OTP codes are never stored in plaintext — only HmacSHA256(otpKey, userId:otp) from OtpHasher (deferred-162; the previous unkeyed SHA-256 of a 900,000-value code was brute-forceable offline). Rotating registration-verification-secret therefore invalidates every OTP in flight (10 min) and every phone-verification handle (24h); the user resends. Every OTP failure — missing, used, expired, rate-limited, or wrong code — returns the same 400 security.otpMismatch, and the rate-limit bucket is only touched once a live OTP has been found, so a resend starts a fresh budget. An EMAIL_VERIFIED user whose handle expired can re-click a freshly sent verification email to get a new OTP and handle (the status is not advanced twice).

    Parent creates a shadow player profile (minor)

    sequenceDiagram
  participant P as Parent (logged in)
  participant SR as ShadowAccountResource
  participant SS as ShadowAccountService
  participant AP as AgePolicyService
  participant DB as player_profiles / parent_player_links

  P->>SR: POST /api/security/players {name, dob, position, parentConsent, consentPolicyVersion}
  SR->>SS: createPlayerProfile(parentId, request)
  SS->>AP: getAgeTier(dob) / isMinor(tier)
  alt isMinor and no parentConsent
    SS-->>SR: throw ShadowAccountException(parentConsentRequired)
  end
  SS->>DB: save PlayerProfile (parentId set, consent timestamp/version)
  SS->>DB: save ParentPlayerLink (uq_ppl_player_id)
  SS-->>SR: PlayerProfileResponse
  SR-->>P: 201 Created

    A PlayerProfile created this way has no login credentials of its own — the parent's User account is the authentication boundary. Every subsequent read or position change on /api/security/players/{playerId} is gated by PlayerOwnershipGuard, which checks player_profiles.parent_id/user_id rather than trusting a role check alone. Other modules (session, video, development, payment) use the same guard bean — the #307 role-guard fix made several of them accept a self-registered ROLE_PLAYER owner where they previously assumed a parent.

    Login and refresh-token rotation (SPA stack)

    sequenceDiagram
  participant C as Client
  participant AR as AuthResource
  participant AS as AuthService
  participant DB as login_attempts / refresh_tokens / user

  C->>AR: POST /api/auth/login {email, password}
  AR->>AS: login(email, password, ip)
  AS->>DB: countByIdentifierAndAttemptedAtAfter(sha256(email|ip), window)
  alt attempts at or above max
    AS-->>C: LoginRateLimitedException, 429 + Retry-After
  end
  AS->>DB: findOneByLogin + password check
  alt bad credentials
    AS->>DB: save LoginAttempt (committed: noRollbackFor BadCredentialsException)
    AS-->>C: 401
  end
  AS->>AS: ensureAccountIsLive (activated, not locked)
  AS->>AS: role user and phone-otp-required: require BASIC_VERIFIED
  AS->>DB: save RefreshToken (hashed)
  AS-->>C: Set-Cookie potc (JWT), rtkn (refresh), skp (profile)

  C->>AR: POST /api/auth/refresh (rtkn cookie)
  AR->>AS: refresh(req, res)
  AS->>DB: findByTokenHash
  alt used, rotated under 30s ago
    AS->>DB: use newest live successor (multi-tab race)
  else used, outside grace window or no successor
    AS->>DB: markAllUsedByUserId + invalidateSessionsForUser (REQUIRES_NEW)
    AS-->>C: 401 Token reuse detected
  end
  AS->>DB: load user, ensureAccountIsLive (before any write)
  AS->>DB: mark old token used (optimistic lock), save new RefreshToken
  AS-->>C: new potc / rtkn / skp cookies

    Login failures are rate-limited by a SHA-256 hash of email|ip (canonicalising IPv6-loopback and ::ffff:-prefixed addresses first) so an attacker on another IP cannot lock out a legitimate user, nor vice versa. Until the "DB login rate limiter fix" the failed-attempt row was rolled back together with the BadCredentialsException it recorded, so the limiter never engaged; login is now @Transactional(noRollbackFor = BadCredentialsException.class). On refresh, the account liveness check runs before the token-rotation UPDATE: running it after made the REQUIRES_NEW revocation self-deadlock on the same refresh_tokens row (55P03 → 409). Two truly concurrent refreshes: the optimistic-lock loser gets a clean 401 and only its cookies are cleared.

    Per-request JWT authorization and session revocation

    JWTAuthorizationFilter re-issues the JWT with a fresh 15-minute TTL on every secured request (sliding window). Every DB_REFRESH_TOKEN_INTERVAL (5 min) it takes the DB re-auth path: DaoAuthProvider.authorize re-loads the user (catching locked/deactivated accounts), then assertSessionNotRevoked rejects any JWT whose sessIat claim predates user.securitySessionInvalidatedAt. Between those checks the fast path does no DB work. So suspension, GDPR erasure, and refresh-token-theft revocation all take effect on open sessions within at most 5 minutes. A genuine denial (locked, theft, invalid JWT) gets the full teardown (terminateSession), routine expiry only drops the JWT cookies, and the 401 body is an ErrorDto the SPA's axios interceptor routes on.

    Admin suspend (AdminUserService.suspendUser, admin module) sets locked = true under the user row lock (UserRepository.findByIdForUpdate, NO_WAIT + PessimisticLockRetryer), stamps securitySessionInvalidatedAt in the same transaction (invalidateSessionsForUserInCurrentTransaction, MANDATORY), then revokes all refresh tokens. unlockLogin calls AuthService.clearLoginRateLimit for both the login and the email.

    Conventions & Gotchas

    Two login stacks, one JWT. See the table above. Only /api/auth/login is used by the SPA, for every role including admins. The legacy /authenticate → /otp path is still a live, public endpoint pair (ITs log in through it). Both paths share one DB-backed failed-login limiter (LoginRateLimiter), so a lockout on one applies to the other and the admin "unlock login" clears it for both. The /otp step itself has no attempt counter beyond its 10-minute expiry and the client/session binding.

    No self-service 2FA toggle. User.otpEnabled is only read by the legacy /authenticate path; AuthService.login (the SPA) never enforces a second factor. The former PUT /api/account/2fa, its Toggle2faDialog.vue and the registration checkbox were removed rather than left as a toggle that silently did nothing. Real SPA 2FA needs /api/auth/login to issue the refresh/skp cookies only after the OTP step, and an attempt counter on that step.

    A safety suspension is a lock plus a status. Admin suspend, lockUserAccount and GDPR erasure use user.locked. The CSAM path (AccountSuspensionEventListener) sets verificationStatus = SUSPENDED and locks, stamps securitySessionInvalidatedAt and revokes every refresh token, like an admin suspend. SUSPENDED is also refused on its own: AuthService.ensureAccountIsLive (login and refresh) and Principal.instanceFrom (accountNonLocked, so the legacy login and the JWT filter's DB re-auth) treat it as locked, whatever phone-otp-required says. The admin console's reactivate refuses a SUSPENDED account (409 admin.users.safetyHold): lifting a child-safety hold is not a one-click action. A suspended coach's marketplace profile is not suspended by this path (the admin suspend does that via AdminCoachEnforcementService, which the security module cannot call).

    Minors never get a standalone login. A minor's PlayerProfile has parent_id set and user_id null — there is no User row for them. Booking.playerId and friends are PlayerProfile PKs, not user ids; resolve the human via PlayerProfile.userId/parentId. Code that assumes every PlayerProfile maps 1:1 to a User will break for the minor case.

    Writes of player development data must take the erasure guard. Anything that inserts timeline/homework/development rows for a player should call DevelopmentDataErasureGuard inside its write transaction (it is MANDATORY and locks player_profiles first — keep that lock order). An unlocked "is erased?" read leaves a window where a row lands after the erasure's delete.

    ApiAdvice maps DB constraint names to error keys — keep the two tables in sync. CONSTRAINT_MAPPINGS turns a named constraint violation into a message key, and CONFLICT_CONSTRAINTS lists the ones that should be 409 rather than 400. Current mappings include excl_bkg_coach_slot_overlap → booking.slotUnavailable, uq_pot_one_active_per_user → security.otpResendInProgress, uq_pcl_booking_refund, idx_spt_one_active_per_coach, uq_session_pack, and (V173) idx_drills_coach_name_unique_active → session.drillNameTaken. When a migration renames an index, update both sets — V173 replaced the old idx_drills_* names with *_active partial indexes. See Database & Migrations.

    Lock contention fails fast as 409, not 500. ApiAdvice maps PessimisticLockingFailureException to generic.conflict. On Postgres a finite jakarta.persistence.lock.timeout hint is ignored — only 0 (NO_WAIT) works — so findByIdForUpdate methods (e.g. CoachProfileRepository, UserRepository) use NO_WAIT and their callers wrap them in PessimisticLockRetryer (savepoint-based retry, about 3s budget). Only contention outlasting the retries becomes the 409.

    AgePolicyService has two variants and they differ on purpose. getMessagingPolicy(playerId) throws UserNotFoundException on an unresolvable player — the safe answer on write paths. findMessagingPolicy(playerId) (and the batch findMessagingPoliciesByPlayerIds) return empty instead, for read paths where an orphaned player_profiles row should cost the one conversation or label that depends on it rather than failing the whole listing. All delegate to the same private resolvePolicy.

    Verification status gates login, not just registration. With security.registration.phone-otp-required on (the default), any User with a non-null skillarsRole must reach BASIC_VERIFIED before AuthService.login() lets them in, even if activated is true. Admin-style users (skillarsRole == null) skip this check entirely.

    AgePolicyService is the single source of truth for age tiers. Thresholds are config-driven via ConfigService with hardcoded fallbacks in AgePolicy.defaults(). Don't hardcode age comparisons elsewhere — call getAgeTier/isMinor/getMessagingPolicy.

    Credentials are always hashed at rest. Phone OTPs as keyed HmacSHA256 via OtpHasher (inject the bean in tests; never re-implement it), refresh tokens as SHA-256(rawToken), passwords via BCryptPasswordEncoder. There is no code path that reads a plaintext credential back out of the database — plan test/debug tooling accordingly.

    A fresh database needs two bootstrap secrets. No migration seeds the JWT signing Secret or an admin user. Locally, set app.bootstrap.jwt-secret.enabled=true (refuses non-private DB hosts) and app.bootstrap.admin.email/password/phone. Also set skillars.platform.registration-verification-secret, or startup aborts.

    Mind REQUIRES_NEW on revocation writes. RefreshTokenRepository.markUsedByTokenHash, markAllUsedByUserId and UserRepository.invalidateSessionsForUser commit independently so they survive the caller's rollback. Never call them after your own transaction has updated the same row, or they self-deadlock (lock timeout → 409). Use invalidateSessionsForUserInCurrentTransaction when you already hold the user row lock.
