Development

Turns raw session activity and coach assessments into a longitudinal picture of a player's skill growth — training volume (SLU), coach-judged ability (Skills Radar), neglect detection, and shareable reports.

Business Overview

Skillars sells two different signals about a young player's progress, and the development module is where they are produced, reconciled, and surfaced. The module answers two distinct questions for Coaches and Parents: "how much has this player trained on each skill?" (an automatic, objective volume metric) and "how good has this player gotten at each skill, according to the people who watched them?" (a subjective, coach-entered rating). The two are deliberately kept as separate systems that are only correlated for the top subscription tier — mixing them by default would misleadingly imply that more training time equals more skill.

  • Coaches submit Skills Radar assessments after working with a player, view weekly SLU exposure/target dashboards, generate branded PDF performance reports, and (Academy tier only) see a SLU-vs-Radar correlation engine.
  • Parents (and, indirectly, Players via the family/player-ownership guard) view the same radar display, timeline, exposure dashboard, and performance reports for their own child — read-only, gated by playerOwnershipGuard rather than a coach role.
  • The system itself (not a human) calculates SLU automatically whenever a booked session completes, and runs a weekly scheduled job that flags skills a player is being under-trained on relative to coach-set targets.

SLU — "Skill Load Units." SLU is a training-volume metric computed per skill, per drill, at session-completion time: slu = repDensity × skillWeight × (intensity × intensityScale) × (pressureLevel × pressureScale) × (matchRealism × matchRealismScale) × durationMinutes (see SluFormula). It only fires for attended (no-show excluded) bookings whose session plan is SAVED or COMPLETED and has at least one drill assigned. Once written, player_skill_stats rows are treated as an immutable, append-only ledger — nothing recalculates historical SLU even if a drill's metadata changes later. A denormalized weekly snapshot (player_slu_weekly_snapshot) is upserted alongside every write so dashboards never need to aggregate the full history.

Skills Radar is a 0–100 composite ability score per skill, built from up to three assessment types a coach can submit: OBJECTIVE (50% weight), MATCH_OBSERVATION (30%), and COACH_EVALUATION (20%). Whenever a coach submits a radar entry, an async, after-commit event handler (RadarCompositeCalculationService) recomputes the weighted composite for every affected skill and upserts it into player_radar_composites. The very first composite computed for a player+skill is also frozen into player_radar_baselines (insert-if-absent, never overwritten) — this baseline is the fixed reference point later used to measure "improvement."

Neglected-skill detection is a weekly scheduled job (Monday 06:00 UTC, ShedLock-protected) that compares each player's actual SLU for the just-completed ISO week against the highest weekly SLU target any of their coaches has set for that skill. If actual SLU falls more than slu.neglected.threshold (a configurable fraction, validated to be in the open interval (0,1)) below that target, the skill is flagged as neglected (an open row in neglected_skill_flags); if it later recovers, the flag is auto-resolved. This is purely a training-volume signal — it says nothing about ability, and is one of the inputs the session module's drill-suggestion logic reads to recommend catch-up drills.

Skills Radar submission and PDF report generation are gated by coach subscription tier (SCOUT cannot use either; INSTRUCTOR/ACADEMY can; branding and the SLU/Radar correlation engine are ACADEMY-only), enforced with FeatureGatedException before any player-existence check runs, specifically to avoid leaking player existence via 404-vs-403 timing/response differences to a lower-tier coach.

Key Flows

Coach submits a Skills Radar assessment

sequenceDiagram
  participant Coach
  participant API as RadarAssessmentResource
  participant Svc as RadarAssessmentService
  participant Auth as CoachPlayerAuthorizationService
  participant Repo as RadarAssessmentRepository
  participant Bus as ApplicationEventPublisher
  participant Comp as RadarCompositeCalculationService
  participant Timeline as TimelineEventListener

  Coach->>API: POST /players/{playerId}/radar/entries
  API->>Svc: submitAssessment(coachUserId, playerId, request)
  Svc->>Auth: requireCoachPlayerRelationship
  Auth-->>Svc: ok (active booking exists)
  Svc->>Svc: check subscription tier (INSTRUCTOR/ACADEMY)
  Svc->>Repo: saveAll(RadarAssessmentEntry rows)
  Svc->>Bus: publish RadarEntrySubmittedEvent
  API-->>Coach: 204 No Content
  Bus--)Comp: after commit (async)
  Comp->>Comp: recompute weighted composite (50/30/20)
  Comp->>Comp: upsert composite + insert-if-absent baseline
  Bus--)Timeline: after commit (async)
  Timeline->>Timeline: write RADAR_ASSESSMENT timeline event

The tier gate runs before the coach-player relationship result is exposed to the response, specifically so a Scout-tier coach cannot distinguish "player doesn't exist" from "player exists but I can't assess them." Once entries are saved, the API returns immediately — the composite recalculation and timeline write both happen asynchronously after the transaction commits, so a slow chart recompute never blocks the coach's request. If this is the very first composite ever computed for that player/skill, it becomes the permanent baseline used later to measure improvement.

Session completes → SLU is recorded → neglect is (eventually) detected

sequenceDiagram
  participant Booking as booking module
  participant Slu as SluCalculationService
  participant Session as session.SessionRepository
  participant Formula as SluFormula
  participant Stats as SluRepository
  participant Snap as SluWeeklySnapshotRepository
  participant Cron as NeglectedSkillDetectionService
  participant Proc as NeglectedSkillProcessor
  participant Flag as NeglectedSkillFlagRepository

  Booking--)Slu: BookingCompletedEvent (after commit, async)
  Slu->>Session: findByBookingId
  Slu->>Slu: verify attended, status SAVED/COMPLETED, has blocks
  Slu->>Formula: calculate(drillMetadata, duration, scales) per drill
  Slu->>Stats: saveAll(PlayerSkillStat rows) — immutable ledger
  Slu->>Snap: upsertAdd (weekly totals, additive)

  Note over Cron: Every Monday 06:00 UTC, ShedLock-guarded
  Cron->>Proc: processPlayer(playerId, threshold, evalYear, evalWeek)
  Proc->>Proc: actual SLU vs max target per skill
  alt actual < target * (1 - threshold)
    Proc->>Flag: open NeglectedSkillFlag (if not already open)
  else recovered
    Proc->>Flag: resolve open flag
  end

SLU calculation is triggered only by attended bookings whose session plan actually has committed drill blocks — no-shows and empty "Quick Complete" sessions contribute nothing. The weekly snapshot table exists purely so the neglected-skill job and the exposure dashboard never need to sum the full player_skill_stats history. Detection always evaluates the previous completed ISO week (since the cron fires just after that week ends) and compares against the highest target set by any of the player's coaches, so one coach's target can flag a skill even if a different coach is the one training it.

Coach generates a performance report for a parent

sequenceDiagram
  participant Coach
  participant API as PerformanceReportResource
  participant Svc as ReportGenerationService
  participant Tier as CoachProfileService
  participant Chart as SkillsRadarChartRenderer
  participant FS as filestorage.FileStorageService
  participant Repo as PerformanceReportRepository
  participant Timeline as TimelineEventListener
  participant Notif as notification (Envelope event)

  Coach->>API: POST /players/{playerId}/reports {nextSteps}
  API->>Svc: generateReport(coachUserId, playerId, nextSteps)
  Svc->>Svc: requireCoachPlayerRelationship + tier gate
  Svc->>Svc: verify SLU session history exists
  Svc->>Chart: renderToPng(radar skills)
  Svc->>Svc: build PDF (branding if ACADEMY, chart, score table, next steps)
  Svc->>FS: storeBytes(pdf, storageKey)
  Svc->>Repo: saveAndFlush(PerformanceReport)
  Svc->>Timeline: writeTimelineEvent(PERFORMANCE_REPORT)
  Svc->>Notif: publish Envelope (PERFORMANCE_REPORT_SHARED email, +48h delay)
  API-->>Coach: 204 No Content

Report generation is one of the few synchronous, transactional flows in the module — the PDF must exist in storage and the DB row must be committed before the endpoint returns, because a persistence failure triggers best-effort cleanup of the just-uploaded PDF to avoid orphaned files. Academy-tier coaches get their saved branding (logo + colour) embedded; everyone else gets the default Skillars header. The parent notification email is scheduled 48 hours out and failures to send it are logged but never fail the report-generation request itself.

Conventions & Gotchas

player_skill_stats and radar baselines are append-only / write-once. PlayerSkillStat rows are never updated after a session completes — even if a drill's metadata changes later, historical SLU must not be retroactively recalculated. Baselines in player_radar_baselines use INSERT ... ON CONFLICT DO NOTHING specifically so the very first composite score is frozen forever as the improvement reference point. The only legitimate deletes are the deleteAllByPlayerId GDPR Article 17 erasure paths used by GdprErasureService.

Tier-gate checks must run before existence checks. In both RadarAssessmentService and ReportGenerationService, the subscription-tier FeatureGatedException is thrown before any player-specific data is touched, so a Scout-tier coach's request fails identically whether or not the player exists. Don't reorder these checks when adding new coach-tier-gated endpoints.

player_id is a BIGINT (TSID), not a UUID — despite what some historical specs say. Several entities carry an explicit comment noting this (e.g. PlayerSkillStat.playerId: "TSID Long — NOT UUID despite epics spec"). Coach and report IDs, by contrast, are UUIDs. Mixing these up is a common source of type errors when adding new queries.

Radar and SLU are intentionally separate systems. Skills Radar is a subjective, coach-entered ability score; SLU is an objective, system-computed training-volume metric. They are only ever correlated for Academy-tier coaches via DevelopmentCorrelationService, gated behind a minimum session-count config threshold. Don't conflate the two when building new player-facing UI — the UX spec explicitly calls out that this distinction must stay visually clear.

Native SQL enum casts need care. RadarAssessmentRepository's native queries return the Postgres development.assessment_type enum as plain text (rae.assessment_type::text); callers must do AssessmentType.valueOf((String) row[1]) rather than casting the row value directly, per the inline comment on the repository.

Related Modules

Booking

Publishes BookingCompletedEvent, the trigger for SLU calculation and the SESSION_COMPLETED timeline entry; also backs the coach-player relationship check.

Session

Session/Drill data (blocks, drill metadata, skill weighting) feeds the SLU formula; session's DrillSuggestionService reads neglected-skill flags to recommend catch-up drills.

Marketplace

Supplies coach and player profile identity plus coach subscription tier used for every feature gate in this module.

Filestorage

Stores and signs download URLs for generated PDF reports and coach branding logos — never touches infrastructure.blobstore directly.

Notification

Delivers the parent email when a new performance report is generated, via a published Envelope event.

Config

Supplies tunable thresholds (SLU scale factors, neglect threshold, correlation minimum session count, timeline coach-access expiry) via ConfigService.

Security

Provides SecurityUtil, role constants, and PlayerProfileRepository ownership checks used to gate coach vs. parent access on nearly every endpoint.

Admin

GdprErasureService calls this module's repositories directly to erase all development data (radar, SLU, timeline, reports) for a player on request.
