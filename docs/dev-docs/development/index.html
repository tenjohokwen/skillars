    Development

    Turns raw session activity and coach assessments into a longitudinal picture of a player's skill growth — training volume (SLU), coach-judged ability (Skills Radar), neglect detection, and shareable reports.

    Business Overview

    Skillars sells two different signals about a young player's progress, and the development module is where they are produced, reconciled, and surfaced. The module answers two distinct questions for Coaches and Parents: "how much has this player trained on each skill?" (an automatic, objective volume metric) and "how good has this player gotten at each skill, according to the people who watched them?" (a subjective, coach-entered rating). The two are deliberately kept as separate systems that are only correlated for the top subscription tier — mixing them by default would misleadingly imply that more training time equals more skill.

    • Coaches get a ranked "my players" roster, a Session Prep Card per upcoming booking, and per-player tools: Skills Radar assessments, weekly SLU exposure/trend/target dashboards, branded PDF performance reports and (Academy tier only) a SLU-vs-Radar correlation engine.
    • Parents (and self-registered Players, via the same ownership guard) view the radar display (with baseline), timeline, exposure dashboard, skill trends and performance reports for their own child. Access is read-only and gated by playerOwnershipGuard, not a coach role.
    • The system itself (not a human) calculates SLU automatically whenever a booked session completes, and runs a weekly scheduled job that flags skills a player is being under-trained on relative to coach-set targets.

    SLU — "Skill Load Units." SLU is a training-volume metric computed per skill, per drill, at session-completion time: slu = repDensity × skillWeight × (intensity × intensityScale) × (pressureLevel × pressureScale) × (matchRealism × matchRealismScale) × durationMinutes (see SluFormula; scales are config keys slu.intensity.scale, slu.pressure.scale, slu.matchRealism.scale). It only fires for attended (no-show excluded) bookings whose session plan is SAVED or COMPLETED and has at least one drill assigned. For a QUICK-mode wrap-up, the blocks come from the plan snapshot frozen at wrap-up (session_completion_data.plan_blocks_snapshot, V170, read through QuickPlanSnapshot), not the live plan. Once written, player_skill_stats rows are treated as an immutable, append-only ledger — nothing recalculates historical SLU even if a drill's metadata changes later. A denormalized weekly snapshot (player_slu_weekly_snapshot) is upserted alongside every write so dashboards never need to aggregate the full history.

    Skills Radar is a 0–100 composite ability score per skill, built from up to three assessment types a coach can submit: OBJECTIVE (50% weight), MATCH_OBSERVATION (30%), and COACH_EVALUATION (20%). Whenever a coach submits a radar entry, an async, after-commit event handler (RadarCompositeCalculationService) recomputes the weighted composite for every affected skill and upserts it into player_radar_composites. The very first composite computed for a player+skill is also frozen into player_radar_baselines (insert-if-absent, never overwritten) — this baseline is the fixed reference point later used to measure "improvement."

    Neglected-skill detection is a weekly scheduled job (Monday 06:00 UTC, ShedLock-protected) that compares each player's actual SLU for the just-completed ISO week against the highest weekly SLU target any of their coaches has set for that skill. Players with fewer than development.neglectedSkill.warmupSessionCount SLU sessions are skipped. If actual SLU falls more than slu.neglected.threshold (a configurable fraction, validated to be in the open interval (0,1)) below that target, the skill is flagged as neglected (an open row in neglected_skill_flags); if it later recovers, the flag is auto-resolved. This is purely a training-volume signal — it says nothing about ability, and is one of the inputs the session module's drill-suggestion logic reads to recommend catch-up drills.

    Skills Radar submission and PDF report generation are gated by coach subscription tier. SCOUT cannot use either; INSTRUCTOR/ACADEMY can; branding and the SLU/Radar correlation engine are ACADEMY-only. The gate throws FeatureGatedException. In the current code it runs after the coach-player relationship check (see Conventions & Gotchas).

    Key services

    ServiceOrchestrates
    SluCalculationServiceListens for BookingCompletedEvent (after commit, async); computes SLU per drill/skill via SluFormula, and dispatches the detail-row and weekly-snapshot writes to SluPersistenceDispatcher. Guards against no-shows, missing session plans, non-committed statuses, and duplicate delivery.
    SluPersistenceDispatcherAsync dispatcher that chains detail-row persistence through SluPersistenceRetrier, then (only on success) weekly-snapshot persistence through SnapshotPersistenceRetrier — ensuring a snapshot write never orphans detail rows that failed to persist. Runs on a dedicated sluRetryExecutor pool to avoid blocking other listeners.
    SluPersistenceRetrierRetryable bean that writes player_skill_stats detail rows with collision handling — a partial unique index on (session_id, skill_code) catches concurrent duplicate deliveries and treats them as idempotent no-ops rather than errors.
    SnapshotPersistenceRetrierRetryable bean that upserts the denormalized player_slu_weekly_snapshot row for the SLU total of a given ISO week (via SnapshotBatchWriter, idempotent per V119 marker). Runs only when the detail save returned SluSaveOutcome.SAVED (not ALREADY_PERSISTED/FAILED), so a duplicate delivery can't add a delta to a different week bucket.
    SluSnapshotOutboxSupport / SluSnapshotOutboxHandlerWhen the snapshot retrier exhausts its retries, the failed write is enqueued on the generic platform.outbox and re-driven off the request path; the V119 marker ensures only the missing deltas are applied.
    SluSnapshotAppliedRetentionServiceDaily (app.slu.snapshot-applied.prune-cron, default 03:30, ShedLock) prune of V119 marker rows older than 90 days.
    QuickPlanSnapshotThe single reader of session_completion_data.plan_blocks_snapshot, shared by SluCalculationService and TimelineEventListener so a QUICK completion's SLU and timeline drill list are computed from the same blocks. If no snapshot applies (LIVE mode, a pre-V170 row, or a corrupt snapshot), it returns empty and both callers use the live plan.
    RadarAssessmentServiceValidates coach-player relationship and subscription tier, persists submitted radar entries, and publishes RadarEntrySubmittedEvent.
    RadarCompositeCalculationServiceListens for RadarEntrySubmittedEvent (after commit, @Async("reportExecutor")); recomputes the weighted composite score and freezes the first-ever baseline. On failure, writes a DLQ row via RadarCompositeDlqService.
    RadarCompositeDlqServicePersists a radar_composite_dlq row (player, parent, skill codes, error) and increments the radar.composite.dlq.count metric. It does not trigger anything — the processor polls.
    RadarCompositeDlqProcessorPolls every platform.development.radar_composite_dlq.poll_delay_ms (default 60 s, ShedLock): claims rows, re-runs the calculation with backoff, and marks rows DEAD at max_attempts.
    RadarDisplayServiceAssembles the radar chart data (composite + baseline per skill) and manages per-coach skill display preferences.
    NeglectedSkillDetectionServiceWeekly ShedLock-guarded cron entry point; validates the neglect threshold config and iterates all players with targets.
    NeglectedSkillProcessorPer-player logic comparing actual weekly SLU snapshot vs. max target per skill; opens/resolves NeglectedSkillFlag rows.
    SluTargetServiceCRUD for coach-set weekly SLU targets; exposes open neglected-skill flags to callers.
    SluDashboardService / SluNarrativeService / SluContributionServiceBuild the weekly exposure trend, plain-language "what changed" narrative keys, and per-coach contribution percentages for the player exposure dashboard.
    DevelopmentCorrelationServiceAcademy-tier-gated engine that classifies each skill into one of four SLU-vs-composite-improvement insight buckets.
    ReportGenerationServiceSynchronously builds a branded PDF (OpenPDF 2.0.5 with vendored Noto Sans) embedding a radar chart image, a skill score table, up to 20 of this coach's session notes (REPORT_SESSION_NOTES_LIMIT) and the next-steps text. It saves a PENDING_UPLOAD row and publishes ReportGeneratedEvent. Its @Async("reportExecutor") AFTER_COMMIT handler onReportGenerated uploads through filestorage, then flips the row to READY, writes the timeline event and emails the parent. On upload failure the row is marked UPLOAD_FAILED; there is no automatic retry. Two rate limits apply: @RateLimited per IP, and an explicit per-coach budget of 10/min.
    SkillsRadarChartRendererPure AWT/Graphics2D renderer producing the PNG radar polygon embedded in PDF reports.
    TimelineEventListener / TimelineQueryServiceWrite development-relevant events onto the player timeline (each write in its own REQUIRES_NEW transaction, called through a @Lazy self-proxy). Producers: BookingCompletedEvent → SESSION_COMPLETED with drill snapshot and ratings (insertSessionCompletedIfAbsent, replay-safe). SessionRecapUpdatedEvent → re-reads session_completion_data FOR UPDATE and patches the recap keys onto the existing row. HomeworkAssignedEvent (needs fallbackExecution = true because its publisher has no transaction) → one HOMEWORK_ASSIGNED row per (player, booking), with later events merged in. RadarEntrySubmittedEvent → RADAR_ASSESSMENT. The report flow adds PERFORMANCE_REPORT. TimelineQueryService serves the feed, filters metadata through the allowlist, and applies the attended-session access clock for coaches.
    TimelineDrillSnapshotResolverResolves drill ids to {drillId, name} snapshots for timeline metadata, capped at 20 drills.
    CoachPlayerAuthorizationServiceShared guard verifying a booking relationship between a coach and player before any coach-only development data is read or written. Reads (requireCoachPlayerRelationshipForRead, ...IfCoach) use READ_RELATIONSHIP_STATUSES; writes use the narrower ACTIVE_RELATIONSHIP_STATUSES. Both also enforce CoachAccessWindow. Also used outside the module by session.service.CoachHomeworkQueryService.
    CoachAccessWindow / CoachPlayerLastSessionResolverThe single coach-access window (development.timeline.coachAccessExpiryDays, default 90) and the "latest attended session with this coach" signal it is measured from (latest attended booking end, capped at now, plus the recap source event).
    CoachRosterService / RosterAttentionCalculatorBuilds the coach's roster at read time (no table): players with a qualifying booking in the last 730 days, capped by development.roster.maxPlayers (default 150). Each player gets an attentionScore = 0.4·recency (normalised to 90 days) + 0.35·neglected-skill count (capped at 5) + 0.25·declining-trend count (capped at 5), plus dormant, hasUpcomingBooking and accessExpired flags.
    SessionPrepService / SessionFocusThreadCalculatorBuilds the Session Prep Card for one booking the calling coach owns (403 otherwise, authorized by booking ownership rather than the relationship check). The card carries: last attended session with its recap (what we did / what's next / what went well), a suggested "what's next" from an older session, up to 3 focus-thread skill codes ranked over recent session-builder sessions, open neglected skills, the player's own request, and the coach's private plan note with an editable flag.

    Key Flows

    Coach submits a Skills Radar assessment

    sequenceDiagram
  participant Coach
  participant API as RadarAssessmentResource
  participant Svc as RadarAssessmentService
  participant Auth as CoachPlayerAuthorizationService
  participant Repo as RadarAssessmentRepository
  participant Bus as ApplicationEventPublisher
  participant Comp as RadarCompositeCalculationService
  participant Timeline as TimelineEventListener

  Coach->>API: POST /players/{playerId}/radar/entries
  API->>Svc: submitAssessment(coachUserId, playerId, request)
  Svc->>Auth: requireCoachPlayerRelationship
  Auth-->>Svc: ok (ACTIVE booking + access window open)
  Svc->>Svc: check subscription tier (INSTRUCTOR/ACADEMY)
  Svc->>Repo: saveAll(RadarAssessmentEntry rows)
  Svc->>Bus: publish RadarEntrySubmittedEvent
  API-->>Coach: 204 No Content
  Bus--)Comp: after commit (async)
  Comp->>Comp: recompute weighted composite (50/30/20)
  Comp->>Comp: upsert composite + insert-if-absent baseline
  Bus--)Timeline: after commit (async)
  Timeline->>Timeline: write RADAR_ASSESSMENT timeline event

    The relationship check runs first, and "no such player" is indistinguishable from "no relationship" (both 403). Only a coach who has a relationship with the player gets as far as the tier gate's FeatureGatedException. Once entries are saved, the API returns immediately — the composite recalculation and timeline write both happen asynchronously after the transaction commits, so a slow chart recompute never blocks the coach's request. If this is the very first composite ever computed for that player/skill, it becomes the permanent baseline used later to measure improvement.

    Session completes → SLU is recorded → neglect is (eventually) detected

    sequenceDiagram
  participant Booking as booking module
  participant Slu as SluCalculationService
  participant Session as session.SessionRepository
  participant Formula as SluFormula
  participant Disp as SluPersistenceDispatcher
  participant Stats as SluPersistenceRetrier
  participant Snap as SnapshotPersistenceRetrier
  participant Outbox as SluSnapshotOutboxSupport
  participant Cron as NeglectedSkillDetectionService
  participant Proc as NeglectedSkillProcessor
  participant Flag as NeglectedSkillFlagRepository

  Booking--)Slu: BookingCompletedEvent (after commit, async)
  Slu->>Session: findByBookingId
  Slu->>Slu: verify attended, status SAVED/COMPLETED
  Slu->>Slu: blocks = QuickPlanSnapshot or live plan, must have drills
  Slu->>Slu: skip if SLU already exists for session
  Slu->>Formula: calculate(drillMetadata, duration, scales) per drill
  Slu--)Disp: dispatchSluPersistence (sluRetryExecutor)
  Disp->>Stats: saveSluWithRetry (immutable ledger)
  alt outcome SAVED
    Disp->>Snap: writeAllWithRetry (additive, V119 marker)
    opt retries exhausted
      Snap->>Outbox: enqueue re-drive
    end
  else ALREADY_PERSISTED or FAILED
    Disp->>Disp: skip snapshot write
  end

  Note over Cron: Every Monday 06:00 UTC, ShedLock-guarded
  Cron->>Proc: processPlayer(playerId, threshold, warmup, evalYear, evalWeek)
  Proc->>Proc: skip if sessions below warmup count
  Proc->>Proc: actual SLU vs max target per skill
  alt actual < target * (1 - threshold)
    Proc->>Flag: open NeglectedSkillFlag (if not already open)
  else recovered
    Proc->>Flag: resolve open flag
  end

    SLU calculation is triggered only by attended bookings whose session plan actually has committed drill blocks — no-shows and empty "Quick Complete" sessions contribute nothing. The weekly snapshot table exists purely so the neglected-skill job and the exposure dashboard never need to sum the full player_skill_stats history. Detection always evaluates the previous completed ISO week (since the cron fires just after that week ends) and compares against the highest target set by any of the player's coaches, so one coach's target can flag a skill even if a different coach is the one training it.

    Coach generates a performance report for a parent

    sequenceDiagram
  participant Coach
  participant API as PerformanceReportResource
  participant Svc as ReportGenerationService
  participant Resolver as CoachPlayerLastSessionResolver
  participant Chart as SkillsRadarChartRenderer
  participant Repo as PerformanceReportRepository
  participant Async as onReportGenerated (reportExecutor)
  participant FS as filestorage.FileStorageService
  participant Timeline as TimelineEventListener
  participant Notif as notification (Envelope event)

  Coach->>API: POST /players/{playerId}/reports {nextSteps}
  API->>Svc: generateReport(coachUserId, playerId, nextSteps)
  Svc->>Svc: per-coach rate limit (10/min)
  Svc->>Svc: requireCoachPlayerRelationship, then tier gate
  Svc->>Resolver: lastSessionDate (attended-session clock)
  Svc->>Svc: 403 if none or outside CoachAccessWindow
  Svc->>Chart: renderToPng(radar skills)
  Svc->>Svc: build PDF (branding if ACADEMY, chart, scores, session notes, next steps)
  Svc->>Repo: saveAndFlush(status PENDING_UPLOAD)
  Svc->>Svc: publish ReportGeneratedEvent(pdfBytes)
  API-->>Coach: 204 No Content
  Svc--)Async: after commit
  Async->>FS: storeBytes(pdf, reports/uuid/report.pdf)
  alt upload ok
    Async->>Repo: status READY + storageKey
    Async->>Timeline: writeTimelineEvent(PERFORMANCE_REPORT)
    Async->>Notif: publish Envelope (PERFORMANCE_REPORT_SHARED, +48h)
  else upload fails
    Async->>Repo: status UPLOAD_FAILED (no retry)
  end

    The PDF is built synchronously inside the request transaction. The upload to storage is not: it happens after commit on the dedicated reportExecutor pool, so the S3 round trip never holds the request's DB connection. A 204 therefore means "report queued", not "report available". listReports only returns READY rows, so a PENDING_UPLOAD or UPLOAD_FAILED report is never handed out as a signed URL to a missing file. A coach caller sees only their own reports (unless they are also the player's parent or self-owner); parents and players see every coach's reports. Academy-tier coaches get their saved branding (logo + colour) embedded; everyone else gets the default Skillars header. The parent email is scheduled 48 hours out, and failures to send it are only logged.

    Conventions & Gotchas

    player_skill_stats and radar baselines are append-only / write-once. PlayerSkillStat rows are never updated after a session completes — even if a drill's metadata changes later, historical SLU must not be retroactively recalculated. Baselines in player_radar_baselines use INSERT ... ON CONFLICT DO NOTHING specifically so the very first composite score is frozen forever as the improvement reference point. The only legitimate deletes are the deleteAllByPlayerId GDPR Article 17 erasure paths used by GdprErasureService.

    Relationship check first, tier gate second. In RadarAssessmentService.submitAssessment/getMyEntries and ReportGenerationService.generateReport, the coach-player relationship check runs first, and only then the subscription-tier FeatureGatedException (the old "Tier gate first" comment in RadarAssessmentService was corrected in B5). No existence leak results, because a missing player and a missing relationship both produce the same 403. But a Scout coach with no relationship gets a plain 403, not the feature-gate error. If you add a new tier-gated endpoint, make sure "unknown player" and "no relationship" still collapse into one response.

    player_id is a BIGINT (TSID), not a UUID — despite what some historical specs say. Several entities carry an explicit comment noting this (e.g. PlayerSkillStat.playerId: "TSID Long — NOT UUID despite epics spec"). Coach and report IDs, by contrast, are UUIDs. Mixing these up is a common source of type errors when adding new queries.

    Radar and SLU are intentionally separate systems. Skills Radar is a subjective, coach-entered ability score; SLU is an objective, system-computed training-volume metric. They are only ever correlated for Academy-tier coaches via DevelopmentCorrelationService, gated behind a minimum session-count config threshold. Don't conflate the two when building new player-facing UI — the UX spec explicitly calls out that this distinction must stay visually clear.

    Native SQL enum casts need care. RadarAssessmentRepository's native queries return the Postgres development.assessment_type enum as plain text (rae.assessment_type::text); callers must do AssessmentType.valueOf((String) row[1]) rather than casting the row value directly, per the inline comment on the repository.

    Where the coach tools live in the frontend. The coach's per-player workspace is coach/players/:playerId (CoachPlayerDetailPage.vue): radar (with saved skill-subset preferences), narrative, neglected skills (fed by GET .../neglected-skills for the "neglected since" date), exposure + trend, targets, contributions, correlation, assessments and reports. Each secondary section has its own loading/error state in development.store.js, so one failing endpoint never blanks the page. The same page also shows CoachHomeworkCard, backed by GET /api/session/coach/players/{playerId}/homework (session module, gated by this module's CoachPlayerAuthorizationService). The roster is CoachRosterResource's consumer, and the Session Prep Card is rendered from /bookings/{id}/prep. PlayerDevelopmentDashboardPage.vue is player-only (read-only radar, exposure, reports, timeline). Parents use ParentDevelopmentPortalPage.vue (radar with a baseline toggle, SkillTrendsPanel over /slu/skill-trends, reports, timeline). Timeline entries link to role-appropriate pages via src/frontend/src/utils/timelineLinks.js. Reads use the wide relationship-status list but writes use the narrow ACTIVE one, so a coach can open the page and still get a 403 on save.

    One coach-access window, two clocks (skillars-12-10). Every per-player read a coach makes (exposure, narrative, trends, contributions, neglected skills, radar display/preferences/entries, targets, correlation, reports list) and the two non-report writes (set targets, submit assessment) go through CoachPlayerAuthorizationService, which now also enforces CoachAccessWindow: development.timeline.coachAccessExpiryDays (default 90) measured from the pair's latest booking end (BookingRepository.findLatestEndTimeByCoachIdAndPlayerIdAndStatusIn) — over READ_RELATIONSHIP_STATUSES for reads, and over the narrow ACTIVE_RELATIONSHIP_STATUSES for writes, so a recent DISPUTED/NO_SHOW_COACH/PAYMENT_PENDING booking opens reads but never re-opens writes. A future-dated or just-finished booking therefore keeps reads open, so a brand-new player or the wrap-up-to-completion gap never 403s. The timeline and report generation deliberately use the stricter attended-session clock (CoachPlayerLastSessionResolver.lastSessionDate = latest attended booking end, capped at now — session time, not processing time) and treat “none” as closed. “No relationship” and “window closed” are the same 403 on purpose. The roster keeps its 730-day / 150-player membership bound but flags players past the window with accessExpired (name and last-session facts only; counts zeroed, per-player queries skipped) — the frontend lists them as a non-clickable “Lapsed” group. RosterQueryCountIT pins the per-player statement budget for each player shape: 4 (booked, nothing attended), 7 (attended: the resolver adds two session-end aggregates and the recap booking-id lookup), 2 (lapsed).

    Timeline metadata is an allowlist. TimelineQueryService exposes, per event type, only the keys it lists (drills for SESSION_COMPLETED/HOMEWORK_ASSIGNED, skillCodes for RADAR_ASSESSMENT, coachName/reportId on PERFORMANCE_REPORT to player/parent only); only the authoring coach sees the full map. A new metadata key is invisible to everyone else by default — add it to the allowlist deliberately.

    Related Modules

    Booking

    Publishes BookingCompletedEvent (the trigger for SLU calculation and the SESSION_COMPLETED timeline entry) and SessionRecapUpdatedEvent. It also backs the coach-player relationship check and the access-window clocks (BookingRepository), and supplies recap text and the QUICK plan snapshot through session_completion_data.

    Session

    Session/Drill data (blocks, drill metadata, skill weighting) feeds the SLU formula. Session's DrillSuggestionService reads neglected-skill flags to recommend catch-up drills. HomeworkAssignedEvent feeds the timeline, and CoachHomeworkQueryService reuses this module's coach-access guard.

    Marketplace

    Supplies coach and player profile identity plus coach subscription tier used for every feature gate in this module.

    Filestorage

    Stores and signs download URLs for generated PDF reports and coach branding logos — never touches infrastructure.blobstore directly.

    Notification

    Delivers the parent email when a new performance report is generated, via a published Envelope event.

    Config

    Supplies tunable thresholds (SLU scale factors, neglect threshold, correlation minimum session count, timeline coach-access expiry) via ConfigService.

    Security

    Provides SecurityUtil, role constants, and PlayerProfileRepository ownership checks used to gate coach vs. parent access on nearly every endpoint.

    Admin

    GdprErasureService calls this module's repositories directly to erase all development data (radar, SLU, snapshot markers, timeline, reports) for a player on request, and scrubs coach-authored recap metadata from timelines on coach erasure. GdprExportService reads them for the player data export.
