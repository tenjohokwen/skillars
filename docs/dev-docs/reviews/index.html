    Reviews

    Post-session coach ratings and written feedback from Players/Parents, gated by AI + human moderation before they ever reach the marketplace.

    Business Overview

    The reviews module is how Skillars builds trust in the coach marketplace. After a session, the Player or Parent behind it can leave a 1–5 star rating and an optional written review for the coach. Reviews feed marketplace's coach profile (average rating and review count, plus the first page of reviews embedded in the public profile DTO), and the coach can reply publicly once. Reviews are user-generated content visible to strangers, and the platform serves minors, so nothing goes live unmoderated. Every non-blank body is screened by an AI content check before it is shown, any live review can be flagged and escalated to a human admin queue, and a blocked review can be appealed.

    Key business rules found in the code:

    • Only Players and Parents can author reviews. POST /api/reviews/coaches/{coachId} and the eligibility pre-check are gated by HAS_PARENT_OR_PLAYER_ROLE at the API boundary. ReviewSubmissionService also runs AuthorRole.valueOf(...) (only PARENT/PLAYER) as defense in depth, which rejects anything else with AUTHOR_ROLE_NOT_ALLOWED.
    • You need a completed session with the coach that has had time to settle. evaluateEligibility calls BookingRepository.findQualifyingCompletedBookings, which returns COMPLETED bookings with updatedAt at least reviews.minSessionAgeDays old (default 7, bounded 1–358). This is a lower bound only, with no upper bound: a session from months ago still qualifies (skillars-deferred-145). The author must be the player (PlayerProfile.userId) or that player's linked parent (PlayerProfile.parentId). Ownership is a JOIN on the current PlayerProfile, never Booking.playerId compared against a user id. Finally, no dispute that the author raised against the coach may be open (DisputeRepository.existsActiveDisputeByAuthor, status not RESOLVED/DISMISSED). A coach-raised dispute does not block the review.
    • One review per author/coach pair, ever. This is checked in code (existsByAuthorIdAndCoachId) and by the unique constraint uq_coach_reviews_author_coach (translated to ALREADY_SUBMITTED). An existing review can be updated instead, subject to a rolling cooldown since lastModifiedAt (reviews.updateCooldownDays, default 30, bounded 1–365, UPDATE_TOO_SOON) and a new qualifying session completed after the author's own last edit. An edit has to be backed by new training activity.
    • Rating is 1–5 (DB CHECK coach_reviews_rating_check). The body is optional and up to 1000 characters (SubmitReviewRequest). A coach response is 1–500 characters.
    • Nothing is public until moderated. Every new or updated review starts PENDING. A blank body is auto-APPROVED (nothing to screen). A non-blank body goes to Gemini and ends up APPROVED, BLOCKED or UNDER_REVIEW (held for a human, with a heldReason). A review that is UNDER_REVIEW or BLOCKED cannot be edited by its author (EDIT_NOT_PERMITTED).
    • Community flagging can pull a live review out of public view. Any authenticated user other than the author or the reviewed coach can flag a review once. When open flags on an APPROVED review reach reviews.autoHoldFlagThreshold (default 3, bounded 1–1000), the review moves to UNDER_REVIEW (FLAG_THRESHOLD) and leaves the public list and the rating average until an admin resolves it.
    • A coach may respond exactly once, and only to an APPROVED review. If the author edits the review, any coach response is wiped and the review goes back into moderation.
    • A blocked review can be appealed. admin.AppealService handles subject type REVIEW_BLOCK. Upholding the appeal calls AdminReviewService.approveReview, but only if the review is still BLOCKED under the lock.

    Frontend: src/frontend/src/pages/marketplace/CoachPublicProfilePage.vue (public list with the newest/highest/lowest sort, eligibility-gated "Write a review", flag action in components/marketplace/ReviewFlagAction.vue), pages/coach/CoachReviewsPage.vue (the coach's own reviews and one-time response), and components/admin/ReviewModerationPanel.vue inside pages/admin/AdminModerationPage.vue (admin queue). Blocked-review appeals go through pages/admin/AdminAppealsPage.vue.

    Key services

    ServiceOrchestrates
    ReviewSubmissionServiceChecks the coach exists and runs eligibility (maturity floor, parent/self ownership, active-dispute gate). Enforces one review per pair and the edit cooldown, saves PENDING reviews and edits, and publishes ReviewSubmittedEvent carrying the moderationEpoch. Also handles the one-time coach response. submitReview runs REQUIRES_NEW so that a caught duplicate-key violation can never surface as UnexpectedRollbackException. checkWriteEligibility backs the read-only pre-check endpoint.
    ReviewModerationServiceListens for ReviewSubmittedEvent after commit and calls GeminiClient outside any transaction. The body is truncated to platform.reviews.moderation.gemini.max-input-chars (2000) and delimiter-fenced, and the prompt is platform.reviews.moderation.gemini.prompt-template. The verdict is written in a new REQUIRES_NEW transaction, guarded by epoch and status. It calls CoachRatingService.recompute on APPROVED/BLOCKED.
    ReviewFlagServiceRuns REQUIRES_NEW. Rejects self-flags (author or reviewed coach) and duplicates (unique index as backstop), all before taking the row lock. It then locks the review, inserts the flag, auto-holds an APPROVED review at the threshold (recomputing the aggregate), and publishes ReviewFlaggedEvent.
    ReviewQueryServiceRead-only, page size 10. Public list of APPROVED reviews (sort=newest|highest|lowest), the coach's own reviews in any status (newest lastModifiedAt first), the author's own review for one coach, and getFirstPageForCoach, which marketplace.CoachMarketplaceResource embeds in CoachProfileDto.reviews.
    CoachRatingServiceThe only writer of a coach's rating aggregate. One COUNT+AVG query over APPROVED rows, average rounded to one decimal, then CoachProfileRepository.updateRatingAggregate. Called by this module and by admin.AdminReviewService.

    Domain events

    • ReviewSubmittedEvent (reviewId, coachId, authorId, rating, body, moderationEpoch): published by submitReview/updateReview and consumed by this module's ReviewModerationService through @TransactionalEventListener(AFTER_COMMIT).
    • ReviewFlaggedEvent (reviewId, coachId, totalFlagCount, autoHeld): consumed by admin.AdminAlertEventListener.onReviewFlagged, which raises a REVIEW_FLAG alert, deduplicated so a review only ever has one OPEN flag alert.
    • ReviewModerationResolvedEvent (reviewId, coachId, previousStatus, newStatus): published by admin.AdminReviewService on approve and block. Nothing listens to it, not even the new notification centre, so neither the author nor the coach is told about a moderation outcome.

    Outbound dependencies: booking (BookingRepository.findQualifyingCompletedBookings), admin (DisputeRepository.existsActiveDisputeByAuthor, which is a reviews → admin repo edge), security (PlayerProfileRepository for ownership, Principal/SecurityUtil, OperationNotAllowedException), marketplace (CoachProfileRepository for existence and the aggregate write, CoachProfileService.getCoachIdByUserId in ReviewResource), config (ConfigService + ConfigBounds.REVIEWS_*), messaging (reuses contract.ModerationVerdict), and infrastructure (gemini.GeminiClient, PessimisticLockRetryer, ResourceNotFoundException). Inbound: admin reaches into this module's repo/service for moderation (AdminReviewService), the cross-domain queue (AdminQueueService), appeals (AppealService), GDPR export (findAllByAuthorId into reviews.json) and erasure (deleteNonApprovedByAuthorId + anonymiseApprovedReviews). marketplace embeds the first page of reviews in the public coach profile.

    Key Flows

    Player/Parent submits a review, AI moderates it asynchronously

    sequenceDiagram
  participant U as Player/Parent
  participant RR as ReviewResource
  participant RS as ReviewSubmissionService
  participant DB as coach_reviews
  participant RM as ReviewModerationService
  participant G as GeminiClient
  participant CRS as CoachRatingService

  U->>RR: GET /api/reviews/coaches/{coachId}/eligibility
  RR-->>U: {eligible, reasonCode}
  U->>RR: POST /api/reviews/coaches/{coachId} {rating, body}
  RR->>RS: submitReview(coachId, authorId, role, rating, body) [REQUIRES_NEW]
  RS->>RS: evaluateEligibility (matured COMPLETED booking, parent/self, no author dispute)
  RS->>DB: existsByAuthorIdAndCoachId?
  alt already reviewed
    RS-->>RR: 409 reviews.alreadySubmitted
  end
  RS->>DB: saveAndFlush CoachReview (PENDING, epoch=0)
  RS-->>RR: 201 Created {reviewId}
  RS->>RM: ReviewSubmittedEvent (delivered AFTER_COMMIT)

  Note over RM: Gemini call outside any transaction
  alt body is blank
    RM->>RM: verdict = APPROVED
  else body present
    RM->>G: evaluate(promptTemplate + fenced body)
    G-->>RM: SAFE / UNSAFE / UNCERTAIN (exception = UNCERTAIN, GEMINI_FAILURE)
  end
  RM->>DB: REQUIRES_NEW: findByIdForUpdateNoWait (bounded retry)
  alt epoch changed or status no longer PENDING
    RM->>RM: discard stale verdict
  else
    RM->>DB: status = APPROVED / BLOCKED / UNDER_REVIEW(heldReason)
    opt APPROVED or BLOCKED
      RM->>CRS: recompute(coachId)
    end
  end

    Submission is synchronous and fast. The caller gets a 201 once the eligibility and uniqueness checks pass, with the review in PENDING. AI moderation runs from a post-commit event so a slow or failing Gemini call never blocks the response. It uses a fresh REQUIRES_NEW transaction because the AFTER_COMMIT thread still has the original, now-finished EntityManager bound. A rating-only review skips Gemini but still goes through the same listener to reach APPROVED. The rating aggregate is recomputed only on an APPROVED/BLOCKED transition, never on every write.

    Community flag escalates a review, admin resolves it

    sequenceDiagram
  participant U as Flagging user
  participant RR as ReviewResource
  participant RFS as ReviewFlagService
  participant DB as review_flags / coach_reviews
  participant AL as AdminAlertEventListener
  participant A as Admin
  participant AR as AdminReviewResource
  participant AS as AdminReviewService

  U->>RR: POST /api/reviews/{reviewId}/flag {reason, details}
  RR->>RFS: flag(reviewId, flaggedBy, reason, details) [REQUIRES_NEW]
  RFS->>DB: unlocked projection (authorId, coachId)
  RFS->>RFS: reject author / reviewed coach / duplicate flagger
  RFS->>DB: findByIdForUpdateNoWait(reviewId) (bounded retry)
  RFS->>DB: saveAndFlush ReviewFlag (unique index backstop)
  RFS->>DB: countByReviewIdAndResolvedAtIsNull
  alt openFlags at or above autoHoldFlagThreshold and status is APPROVED
    RFS->>DB: status=UNDER_REVIEW, heldReason=FLAG_THRESHOLD
    RFS->>DB: CoachRatingService.recompute
  end
  RFS->>AL: ReviewFlaggedEvent
  AL->>DB: insert AdminAlert(REVIEW_FLAG) unless one is already OPEN

  A->>AR: GET /api/admin/reviews/queue?status=UNDER_REVIEW
  AR->>AS: getUnderReviewQueue(page)
  AS-->>A: reviews + flags + heldReason + coach name
  A->>AR: POST /api/admin/reviews/{reviewId}/approve (or /block {reason})
  AR->>AS: approveReview / blockReview
  AS->>DB: findByIdForUpdateNoWait, status=APPROVED|BLOCKED, heldReason=null
  AS->>DB: resolveAllOpenFlags (WARN if any were open)
  AS->>DB: recompute (always on approve, on block only if it was APPROVED)
  AS->>DB: save ReviewModerationLog
  AS->>AS: publish ReviewModerationResolvedEvent (no listener)

    A single flag never hides anything on its own. Only crossing the threshold on a currently APPROVED review triggers the auto-hold, and there is no unflag endpoint. Flags may also be cast on PENDING, UNDER_REVIEW or BLOCKED reviews. They accumulate but cannot trigger anything, and admin approve/block resolves them all via resolveAllOpenFlags. Approve works from any non-APPROVED status, including PENDING, which is the only way to rescue a review whose moderation write was lost (see gotchas). The admin queue only lists UNDER_REVIEW rows, though.

    Coach responds once to an approved review

    sequenceDiagram
  participant C as Coach
  participant RR as ReviewResource
  participant CPS as CoachProfileService
  participant RS as ReviewSubmissionService
  participant DB as coach_reviews

  C->>RR: POST /api/reviews/{reviewId}/response {body}
  RR->>CPS: getCoachIdByUserId(userId)
  RR->>RS: submitCoachResponse(reviewId, coachId, body)
  RS->>DB: findByIdForUpdateNoWait(reviewId) via PessimisticLockRetryer
  alt review.coachId != coachId
    RS-->>RR: 403 reviews.coachMismatch
  end
  alt moderationStatus != APPROVED
    RS-->>RR: 403 reviews.reviewNotApproved
  end
  alt coachResponseBody already set
    RS-->>RR: 409 reviews.responseAlreadySubmitted
  end
  RS->>DB: save coachResponseBody, coachResponseAt
  RS-->>RR: 204 No Content

    The row lock stops two concurrent responses, or a response arriving mid-approve/block. A coach response is not moderated: it goes live immediately on an approved review. It can only be cleared by the author editing the review.

    Conventions & Gotchas

    Every locked read of coach_reviews is NOWAIT + bounded retry. Six call sites (ReviewFlagService.flag, ReviewSubmissionService.updateReview/submitCoachResponse, AdminReviewService.approveReview/blockReview, ReviewModerationService.handleReviewSubmitted) plus AppealService.reverseReviewBlock use CoachReviewRepository.findByIdForUpdateNoWait (lock timeout 0) wrapped in PessimisticLockRetryer.withBoundedRetry (skillars-deferred-135). The blocking findByIdForUpdate is kept but has no callers. When a call site has already loaded the entity unlocked (updateReview), it must entityManager.refresh(locked, PESSIMISTIC_WRITE) and check status, cooldown and eligibility again on the fresh instance. flag() avoids that by reading an unlocked scalar projection (findAuthorAndCoachIdByReviewId), so the locked read is the first entity load.

    The AI verdict must lose to any decision already recorded, and to any newer edit. The Gemini call can take seconds, so the write-back re-reads under the lock and has two guards. First, moderationEpoch must still equal the epoch captured in the event: updateReview increments it on every edit, so a late verdict for an older text is dropped even though the row is PENDING again. Second, the status must still be PENDING. Admin approve/block, the flag auto-hold and duplicate deliveries all win. recompute sits inside the guarded branch, so a skipped write never recomputes.

    A failed moderation write leaves the review stuck in PENDING, and the admin queue will not show it. handleReviewSubmitted catches every exception from its REQUIRES_NEW block, including lock-retry exhaustion. Unlike messaging, there is no sweeper, and GET /api/admin/reviews/queue rejects any status other than UNDER_REVIEW. The review is invisible to the public and to the queue until someone calls POST /api/admin/reviews/{id}/approve or /block by id (both accept PENDING) or fixes the DB. Separately, a Gemini failure is not stuck: it becomes UNDER_REVIEW/GEMINI_FAILURE and does reach the queue.

    The update cooldown and the "new session" bound use two different timestamps, on purpose. UPDATE_TOO_SOON checks lastModifiedAt, which three non-author writers also touch (AdminReviewService.approveReview/blockReview, ReviewFlagService's auto-hold), so a moderation action also delays the next edit. The eligibility re-check's "new session since last edit" bound uses author_last_edited_at, which only submitReview/updateReview write (V157), so a moderation action cannot void a qualifying session the author already earned.

    Maturity is measured on Booking.updatedAt, not the session time. findQualifyingCompletedBookings filters b.updatedAt <= now - minSessionAgeDays. Any later write to a COMPLETED booking row, such as an admin force-complete, a dispute side effect or a recap update, restarts the 7-day clock. The query is capped at 50 distinct player ids, and hitting the cap logs a WARN.

    ReviewApiAdvice also handles admin.api.AdminReviewResource. It combines basePackages with assignableTypes (OR semantics). The class is referenced fully-qualified to avoid an import-level reviews.api → admin.api edge. As a result, every exception from AdminReviewResource lands here, including bean-validation failures on /block.

    COACH_PROFILE_MISSING is deliberately a 500, not a 409. An orphaned coach_profiles reference is a data-integrity failure the caller can neither cause nor fix. It should be unreachable, because GdprErasureService anonymises coach profiles rather than deleting them, so if it fires it should page. Keep the branch explicit: the advice falls back to 403, so an unlisted new ReviewErrorCode silently becomes FORBIDDEN.

    Public sort is by lastModifiedAt, with deterministic tie-breaks. "newest" means lastModifiedAt DESC, reviewId ASC. "highest" and "lowest" sort by rating, then lastModifiedAt DESC, then reviewId ASC. Rating alone has many ties on a 1–5 scale, and OFFSET paging over a non-total order repeats or skips rows between "load more" pages. Because a moderation action also bumps lastModifiedAt, an admin approval moves an old review to the top of "newest".

    Rating math lives in exactly one place. CoachRatingService.recompute is the only code that writes a coach's aggregate. It uses one combined COUNT+AVG query to avoid a TOCTOU race. Call it after any status change that can affect the APPROVED set, and never update the aggregate anywhere else.

    GDPR erasure treats APPROVED reviews differently from everything else. GdprErasureService deletes all of the author's non-approved reviews but only anonymises approved ones (native update to author_id = 0), because a live review is still useful social proof. Public DTOs never expose author identity, only authorRole. If you add a review field that holds PII, scrub it in that same erasure path.
