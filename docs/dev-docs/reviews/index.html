Reviews

Post-session coach ratings and written feedback from Players/Parents, gated by AI + human moderation before they ever reach the marketplace.

Business Overview

The reviews module is how Skillars builds trust in the coach marketplace: after a session, the Player or Parent who booked it can leave a 1–5 star rating and an optional written review for the coach. Those reviews feed marketplace's coach profile (average rating + review count) and give the coach a way to respond publicly once. Because reviews are user-generated content visible to strangers — and the platform serves minors — nothing goes live unmoderated: every non-blank review body is screened by an AI content check before it is shown, and any live review can be flagged by other users and escalated to a human admin queue.

Key business rules found in the code:

  • Only Players and Parents can author reviews (AuthorRole has just PARENT/PLAYER) — coaches cannot review themselves or other coaches. The submit-review endpoint itself only requires "authenticated" at the security layer; the actual role restriction happens inside ReviewSubmissionService via AuthorRole.valueOf(...), which rejects anything else with AUTHOR_ROLE_NOT_ALLOWED.
  • You must have had a recent completed session with the coach. checkEligibility calls into booking to confirm a completed booking exists within a config-driven submission window (reviews.submissionWindowDays, default 14 days). No session, no review.
  • One review per author/coach pair, ever. Enforced both in application logic (existsByAuthorIdAndCoachId) and by a DB unique constraint (caught as ALREADY_SUBMITTED). An existing review can be updated instead of re-submitted, but only once every 365 days (UPDATE_TOO_SOON) — a deliberately long cooldown meant to stop rating gaming.
  • Rating scale is 1–5, body is optional and capped at 1000 characters (SubmitReviewRequest).
  • Nothing is public until moderated. Every new/updated review starts PENDING. A blank body is auto-APPROVED immediately (nothing to screen); a non-blank body is sent to Gemini for a safety verdict, landing on APPROVED, BLOCKED, or UNDER_REVIEW (held for a human admin).
  • Community flagging can pull a live review back out of public view. Any authenticated user other than the review's author or the reviewed coach can flag a review; once open flags on an APPROVED review reach a threshold (reviews.autoHoldFlagThreshold, default 3), it auto-transitions to UNDER_REVIEW and disappears from the public list and the rating average until an admin resolves it.
  • A coach may respond exactly once, and only to a review that is currently APPROVED. Editing the underlying review (by the author) wipes any existing coach response and re-queues the review for moderation.

Technical Overview

Package layout

AdminReviewQueueEntryDto/ReviewFlagDto/BlockReviewRequest exist here specifically so the admin module can consume this module's shapes without reaching into repo.

serviceAll business logic: ReviewSubmissionService (submit/update/coach-response + eligibility), ReviewModerationService (async AI moderation), ReviewFlagService (community flagging + auto-hold), ReviewQueryService (read-only listings), CoachRatingService (rating aggregate recompute, shared with admin).

Key entities & tables

EntityTableNotes
CoachReviewreviews.coach_reviewsOne row per author/coach pair. Carries rating (1–5), optional body (max 1000 chars), moderationStatus (PENDING/APPROVED/BLOCKED/UNDER_REVIEW), heldReason (GEMINI_UNCERTAIN/GEMINI_FAILURE/FLAG_THRESHOLD/MANUAL) set only while held, and a single coachResponseBody/coachResponseAt pair for the coach's one-time reply.

Key services

ServiceOrchestrates
ReviewSubmissionServiceValidates coach existence and booking-eligibility, enforces one-review-per-pair and the 365-day edit cooldown, persists PENDING reviews/edits, publishes ReviewSubmittedEvent, and handles the coach's one-time response (locked via findByIdForUpdate pessimistic write).
ReviewModerationServiceListens for ReviewSubmittedEvent after commit, calls infrastructure.gemini.GeminiClient with the review body wrapped in a delimiter-fenced prompt, maps the verdict to a moderation status in a brand-new REQUIRES_NEW transaction, and triggers CoachRatingService.recompute when a review becomes APPROVED or BLOCKED. The write is guarded so a late AI verdict can never overwrite a decision already recorded — see gotchas.
ReviewFlagServiceValidates a flag isn't self-directed (by the author or by the reviewed coach), de-dupes per flagger (DB unique index as backstop), auto-escalates an APPROVED review to UNDER_REVIEW once open flags cross a config threshold, and publishes ReviewFlaggedEvent.
ReviewQueryServiceRead-only listings: public paginated approved reviews (sortable newest/highest/lowest), a coach's view of all their own reviews regardless of status, and a single author's own review for a given coach.
CoachRatingServiceSingle source of truth for recomputing a coach's average rating and review count from APPROVED reviews (one atomic count+avg query to avoid a TOCTOU race) and pushing it onto the coach's marketplace profile. Called by this module and directly by admin's moderation actions.

Domain events

  • Published: ReviewSubmittedEvent (new review or edit saved — drives async AI moderation), ReviewFlaggedEvent (consumed by admin's AdminAlertEventListener to raise an AdminAlert, deduped so a review only ever has one OPEN flag alert), ReviewModerationResolvedEvent (published by admin's AdminReviewService on approve/block — no listener currently consumes it in this codebase; it appears to be reserved for future notification wiring).
  • Consumed: ReviewModerationService consumes its own module's ReviewSubmittedEvent via @TransactionalEventListener(phase = AFTER_COMMIT).

Dependencies on other modules/infrastructure, based on actual imports: booking (BookingRepository.existsRecentCompletedBookingByAuthor for submission eligibility), marketplace (CoachProfileRepository for existence checks, coach display name, and the rating-aggregate write; CoachProfileService in ReviewResource to resolve a coach's own id from their user id), config (ConfigService for the submission window and auto-hold flag threshold), messaging (reuses its contract.ModerationVerdict enum for the Gemini verdict — a small but real coupling), security (Principal/SecurityUtil for caller identity, OperationNotAllowedException for business-rule failures), and cross-cutting infrastructure.gemini (GeminiClient for AI content moderation) and infrastructure.exception (ResourceNotFoundException). The admin module depends the other way: it reaches directly into this module's repo/service classes for moderation (AdminReviewService) and for GDPR export/erasure (GdprExportService dumps findAllByAuthorId into the user's data export; GdprErasureService calls deleteNonApprovedByAuthorId and anonymiseApprovedReviews to scrub a deleted user's identity from reviews that are still publicly visible).

Key Flows

Player/Parent submits a review, AI moderates it asynchronously

sequenceDiagram
  participant U as Player/Parent
  participant RR as ReviewResource
  participant RS as ReviewSubmissionService
  participant DB as coach_reviews
  participant RM as ReviewModerationService
  participant G as GeminiClient
  participant CRS as CoachRatingService

  U->>RR: POST /api/reviews/coaches/{coachId} {rating, body}
  RR->>RS: submitReview(coachId, authorId, role, rating, body)
  RS->>RS: checkEligibility (recent completed booking within window)
  RS->>DB: existsByAuthorIdAndCoachId?
  alt already reviewed
    RS-->>RR: 409 reviews.alreadySubmitted
  end
  RS->>DB: save CoachReview (status=PENDING)
  RS-->>RR: 201 Created {reviewId}
  RR-->>U: 201 Created
  RS->>RM: publish ReviewSubmittedEvent (AFTER_COMMIT)

  Note over RM: fires only after the submit TX commits
  alt body is blank
    RM->>DB: status=APPROVED
  else body present
    RM->>G: evaluate(promptTemplate + review body)
    G-->>RM: SAFE / UNSAFE / UNCERTAIN (or exception)
    RM->>DB: status=APPROVED / BLOCKED / UNDER_REVIEW(heldReason)
  end
  alt status is APPROVED or BLOCKED
    RM->>CRS: recompute(coachId)
    CRS->>DB: COUNT+AVG rating where APPROVED
    CRS->>DB: update coach's marketplace rating aggregate
  end

The submission itself is synchronous and fast — the caller gets a 201 the moment eligibility and uniqueness checks pass, with the review sitting PENDING. The AI moderation step is deliberately decoupled onto a post-commit event so a slow or failing Gemini call never blocks the HTTP response, and it runs in a brand-new REQUIRES_NEW transaction because the original request's entity manager/thread is gone by the time AFTER_COMMIT fires. Only a non-blank body is actually sent to Gemini; a rating-only review skips AI moderation entirely and goes live immediately. The coach's rating aggregate is only ever recomputed on an APPROVED/BLOCKED transition, never on every write.

Community flag escalates a review, admin resolves it

sequenceDiagram
  participant U as Flagging user
  participant RR as ReviewResource
  participant RFS as ReviewFlagService
  participant DB as review_flags / coach_reviews
  participant AL as AdminAlertEventListener
  participant A as Admin
  participant AR as AdminReviewResource
  participant AS as AdminReviewService

  U->>RR: POST /api/reviews/{reviewId}/flag {reason, details}
  RR->>RFS: flag(reviewId, flaggedBy, reason, details)
  RFS->>RFS: reject if flaggedBy is the author or the reviewed coach
  RFS->>DB: save ReviewFlag (unique per flagger, unique index as backstop)
  RFS->>DB: countByReviewIdAndResolvedAtIsNull
  alt openFlagCount >= autoHoldFlagThreshold and status==APPROVED
    RFS->>DB: status=UNDER_REVIEW, heldReason=FLAG_THRESHOLD
    RFS->>DB: CoachRatingService.recompute (drops out of public aggregate)
  end
  RFS->>AL: publish ReviewFlaggedEvent

  AL->>DB: insert AdminAlert(REVIEW_FLAG) unless one already OPEN

  A->>AR: GET /api/admin/reviews/queue?status=UNDER_REVIEW
  AR->>AS: getUnderReviewQueue(page)
  AS-->>A: reviews + flag details + heldReason + coach name

  A->>AR: POST /api/admin/reviews/{reviewId}/approve  (or /block)
  AR->>AS: approveReview / blockReview(reviewId, adminId)
  AS->>DB: status=APPROVED|BLOCKED, resolve all open flags
  AS->>DB: CoachRatingService.recompute (if it affects the public aggregate)
  AS->>DB: save ReviewModerationLog(action, adminId, reason)
  AS->>AS: publish ReviewModerationResolvedEvent

A single flag never hides anything by itself — only crossing the configured threshold on a currently APPROVED review triggers the auto-hold, and it is one-way from the flagger's perspective (no unflag endpoint). Approving/blocking always resolves every open flag on that review via resolveAllOpenFlags, so a review can't stay stuck in the queue after a decision. Blocking only triggers a rating recompute if the review was previously APPROVED (i.e. it was actually contributing to the public average); blocking a review that was still PENDING/UNDER_REVIEW doesn't need one.

Coach responds once to an approved review

sequenceDiagram
  participant C as Coach
  participant RR as ReviewResource
  participant CPS as CoachProfileService
  participant RS as ReviewSubmissionService
  participant DB as coach_reviews

  C->>RR: POST /api/reviews/{reviewId}/response {body}
  RR->>CPS: getCoachIdByUserId(userId)
  RR->>RS: submitCoachResponse(reviewId, coachId, body)
  RS->>DB: findByIdForUpdate(reviewId) (pessimistic write lock)
  alt review.coachId != coachId
    RS-->>RR: 403 reviews.coachMismatch
  end
  alt moderationStatus != APPROVED
    RS-->>RR: 403 reviews.reviewNotApproved
  end
  alt coachResponseBody already set
    RS-->>RR: 409 reviews.responseAlreadySubmitted
  end
  RS->>DB: save coachResponseBody, coachResponseAt
  RS-->>RR: 204 No Content

The pessimistic write lock on the review row prevents a race between two concurrent response attempts (or a response landing while an admin is mid-approve/block). Once set, a coach response can only be cleared by the review's author editing their review, which wipes both coachResponseBody and coachResponseAt and re-queues the review for moderation as if it were new.

Conventions & Gotchas

AI-moderation failures never surface as an HTTP error — the review just goes silent. ReviewModerationService.handleReviewSubmitted catches and swallows every exception from its REQUIRES_NEW transaction (see the code comment referencing "Epic 10"): if the status write fails after Gemini already returned a verdict, the review is left PENDING forever with no retry. This is only resolvable today via the admin queue's manual intervention, or a DB fix — there's no automated recovery path yet. Note the swallow also absorbs a lock-acquisition failure on the read described below, which leaves the review PENDING rather than mis-resolved — the safe direction.

The AI verdict must lose to any decision already recorded. The Gemini call runs outside any transaction and can take seconds — ample room for an admin to resolve the review meanwhile. So the write-back reads with findByIdForUpdate and then refuses to write unless the row is still PENDING. PENDING is the whole guard: ReviewSubmissionService.submitReview/updateReview are the only publishers of ReviewSubmittedEvent and both set PENDING immediately before publishing, so it is the only status this delivery may claim. Everything else wins — admin approve/block, and ReviewFlagService's auto-hold at the flag threshold. It also makes a duplicate event delivery idempotent for free.

Two subtleties if you touch this: because REQUIRES_NEW suspends the AFTER_COMMIT thread's stale EntityManager, the locked query is the transaction's first read of the row and returns fresh DB state — so it needs no entityManager.refresh() (contrast BookingService.createBookingRequest, where an earlier findById forces one). And recompute now sits inside the guarded branch, so a skipped write no longer recomputes the coach's aggregate.

ReviewApiAdvice also handles admin.api.AdminReviewResource. Its @RestControllerAdvice combines basePackages with assignableTypes (OR semantics), because AdminReviewResource lives in platform.admin.api but raises review-domain errors and needs review-shaped responses. The class is referenced fully-qualified rather than imported, to avoid an import-level reviews.api → admin.api dependency. Consequence worth knowing: this routes every exception from AdminReviewResource here, including bean-validation failures on /block.

COACH_PROFILE_MISSING is deliberately a 500, not a 409. An orphaned coach_profiles reference is a data-integrity failure the caller neither caused nor can fix by retrying — unlike ALREADY_BLOCKED, which is a genuine conflict. Filing it as 4xx would bury it in the "user error" bucket that 5xx-keyed alerting never looks at. It should be unreachable in production (GdprErasureService anonymises coach profiles rather than deleting them), so if it ever fires it should page. Keep the branch explicit: the advice's fallback is 403, so a newly added ReviewErrorCode that nobody lists silently becomes FORBIDDEN instead of reaching any 5xx.

The 365-day edit cooldown reads backwards at first glance. updateReview throws UPDATE_TOO_SOON when lastModifiedAt.isAfter(now - 365 days) — i.e. it blocks the edit if the review was modified recently, meaning a review can only be edited once per year. This is intentional (anti rating-manipulation), not a bug, but it surprises new readers expecting a short cooldown like other "edit window" patterns in the codebase.

Rating math lives in exactly one place. CoachRatingService.recompute is the only code path allowed to write a coach's aggregate rating/count onto their marketplace profile, and it uses a single combined COUNT+AVG query specifically to avoid a TOCTOU race between two separate reads. Both this module and admin's moderation actions call it directly after any status change that could affect the APPROVED set — never update the aggregate ad hoc elsewhere.

Role enforcement for submission is business logic, not a security annotation. POST /api/reviews/coaches/{coachId} only requires IS_AUTHENTICATED; the actual "only Players/Parents" rule is enforced inside ReviewSubmissionService via AuthorRole.valueOf(role), which throws AUTHOR_ROLE_NOT_ALLOWED for anything else (e.g. a coach calling their own endpoint). Don't assume the @PreAuthorize annotation tells you the full authorization story for this endpoint.

GDPR erasure treats APPROVED reviews differently from everything else. When a user is erased, admin's GdprErasureService deletes all of that author's non-approved reviews outright but only anonymises their approved ones (sets author_id = 0 via a native update, since a live review is still useful social proof for the coach). If you add a new reviews field containing PII, it needs to be scrubbed in that same erasure path.

Related Modules

  • Booking — supplies the "did this person actually have a completed session with this coach recently" check that gates review submission.
  • Marketplace — owns the CoachProfile that receives the recomputed rating aggregate, and resolves a logged-in coach's own coach id for the self-service endpoints.
  • Admin — hosts AdminReviewResource/AdminReviewService for the moderation queue (approve/block), listens for ReviewFlaggedEvent to raise alerts, and reaches into this module's repositories directly for GDPR export/erasure.
  • Config — provides the tunable submission window and auto-hold flag threshold via ConfigService.
  • Messaging — this module reuses its ModerationVerdict enum for the Gemini safety verdict.
  • Security — supplies the authenticated Principal/SecurityUtil identity resolution and the shared OperationNotAllowedException business-error type.
  • Infrastructure — infrastructure.gemini.GeminiClient performs the AI content-safety check; infrastructure.exception.ResourceNotFoundException backs not-found errors.
