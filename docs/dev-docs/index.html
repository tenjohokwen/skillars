Skillars — Developer Documentation

Everything a new engineer needs to understand what Skillars is, how the backend is organized, and where to go deeper.

Business Overview

Skillars is a youth sports skill-development and coaching marketplace. It connects Coaches with Players — many of whom are minors — for one-on-one and small-group training. Because a large share of players are minors, the product is built around a Parent account that supervises, consents on behalf of, and pays for a child's participation, with special handling for messaging, GDPR data rights, and content moderation. Admins run trust-and-safety, finance, and support operations behind the scenes.

The core loop a family goes through looks like this:

1. Discover

Parents/players search the marketplace for a coach by city, specialty, and age group.

2. Book

They book a session or session pack against the coach's published availability.

3. Pay

Payment is captured via credit wallet, session pack, or subscription, with Stripe handling coach payouts.

4. Train

Coaches plan session content (drills, homework) and may run a live session with video review.

5. Track

Player development is tracked over time via Skills Radar assessments and training-volume metrics.

6. Review

After the session, families leave a review that feeds back into the coach's marketplace ranking.

One module exists purely to keep the lights on: admin — moderation queue, coach enforcement, dispute resolution, and GDPR export/erasure.

There is no multi-tenancy. A tenant module used to exist — a B2B API-key integration layer for external partners, not per-club data partitioning — and it was removed entirely in commit a170e69. No tenant_id column, TenantContext, /v1/** API-key filter chain, or ROLE_TENANT principal remains anywhere in the codebase. If you find a reference to any of those, it is stale — please delete it.

Technical Overview

The backend is a single Spring Boot application (Java), package root com.softropic.skillars, organized as domain modules under com.softropic.skillars.platform.<module>. A cross-cutting com.softropic.skillars.infrastructure.* layer provides shared technical primitives (object storage, security helpers, persistence utilities, feature flags, thread pools, email, sanitization, external provider clients) that platform modules build on rather than reimplement. The frontend is Vue 3 (Quasar). Data lives in Postgres, with Redis for caching/session state.

New engineers most often get confused by two boundaries: booking vs. session (booking owns scheduling/calendar/credits; session owns training content — drills, plans, homework) and filestorage vs. infrastructure.blobstore (filestorage is the only module allowed to call blobstore directly — everyone else goes through filestorage's API). Both are explained in depth on their respective pages.

Conventions & Gotchas (platform-wide)

Never call infrastructure.blobstore directly. Only filestorage is allowed to. Every other module that needs to store or retrieve a file must go through filestorage's own API. See Filestorage and Infrastructure.

Email is silently suppressed in dev. When app.ses.enabled=false (the local default), NoOpSesEmailService logs the subject line only and sends nothing — a common source of "I registered but got no email" confusion locally.

booking vs. session — booking owns scheduling/calendar; session owns training content (drill library, plans, templates, homework). They meet only at a read-only booking snapshot and a completion event.

Session-pack credits live in payment, not booking. Booking used to own a parallel SessionPackService/session_packs_purchased system; it was deleted (migration V89). payment.service.PackSessionService and payment.repo.SessionPackPurchase are now the only credit system. Booking still declares the pack lifecycle events in booking.contract — payment publishes them. See Payment.

Background work is centrally catalogued. 30 @Scheduled methods run across 9 modules, but only 9 of them are ShedLock-guarded — the rest run concurrently on every instance. Rather than hunting for them per module, start at Scheduled Jobs.
