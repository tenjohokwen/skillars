    Skillars — Developer Documentation

    Everything a new engineer needs to understand what Skillars is, how the backend and frontend are organized, and where to go deeper.

    New to the team? Start with Your First Day. It is one linear path from clone to first merged PR: run the stack locally, create a coach, parent, player and admin, walk the booking loop with the code open, run one test of each kind, and get through CI. Keep the Glossary open alongside it for terms like booker, shadow profile, SLU, wrap-up, payout hold and tombstone.

    Business Overview

    Skillars is a youth sports skill-development and coaching marketplace. It connects Coaches with Players — many of whom are minors — for one-on-one and small-group training. Because a large share of players are minors, the product is built around a Parent account that supervises, consents on behalf of, and pays for a child's participation, with special handling for messaging, GDPR data rights, and content moderation. Adult players can also self-register and book for themselves. Admins run trust-and-safety, finance, and support operations behind the scenes.

    The core loop a family goes through looks like this:

    1. Discover

    Parents/players search the marketplace for a coach by city, specialty, language, rating, and age group.

    2. Book

    They book a single session or a batch of sessions against the coach's published availability.

    3. Pay

    Payment is taken from the credit wallet, a session pack, or a card charge on the platform account. Coaches are paid out via Stripe Connect only after the session completes and a hold period passes.

    4. Train

    Coaches plan session content (drills, templates, homework), deliver live or quick-complete, and share video for review.

    5. Track

    Player development is tracked over time via Skills Radar assessments, training volume (SLU), the development timeline, and PDF reports.

    6. Review

    After the session, families leave a review that feeds the coach's rating aggregate and marketplace ranking.

    Keeping everyone informed: notification sends templated email and writes the in-app notification inbox, honouring per-category email opt-outs. Keeping the lights on: admin — moderation queue, account and coach enforcement, disputes, appeals, stuck-booking force-complete, and GDPR export/erasure (self and child).

    There is no multi-tenancy. A tenant module (a B2B API-key integration layer, not per-club data partitioning) was removed entirely in commit a170e69. No tenant_id column, TenantContext, or ROLE_TENANT principal remains. If you find a reference to any of those, it is stale — please delete it.

    Technical Overview

    The backend is a single Spring Boot application (Java 17), package root com.softropic.skillars, organized as domain modules under com.softropic.skillars.platform.<module> (each with api / service / repo / contract / config subpackages). A cross-cutting com.softropic.skillars.infrastructure.* layer provides shared technical primitives (blob storage, email transport, provider clients, routing DataSource, lock retry, rate limiting, exceptions, validation) that platform modules build on rather than reimplement. Side effects that must survive a crash (emails, refunds, payouts, blob deletion, moderation retries) go through the transactional outbox. The frontend is a Vue 3 + Quasar hash-routed SPA under src/frontend. Data lives in Postgres (Flyway-managed, see Database).

    To see these layers working together, follow one booking from the Vue page to the email and SSE push in Anatomy of a request; for the reasoning behind the outbox, NOWAIT locking, platform charges and other non-obvious choices, read Why it's built this way.

    New engineers most often get confused by two boundaries: booking vs. session (booking owns scheduling/calendar/lifecycle; session owns training content — drills, plans, templates, homework) and filestorage vs. infrastructure.blobstore (filestorage is the gateway for files — other modules go through its API rather than calling blobstore). Both are explained in depth on their respective pages.

    Several edges are two-way (booking ↔ session, booking ↔ payment, video ↔ payment, marketplace ↔ reviews). Most reverse edges are a port interface declared in one module's contract package and implemented in the other (e.g. booking's BookingDisputeLookup is implemented by admin; video's ModerationAdminAlertSender by notification), or a Spring event listener.

    Conventions & Gotchas (platform-wide)

    Never call infrastructure.blobstore directly from a feature module. Go through filestorage's API; only its contract exception types (e.g. StorageObjectNotFoundException) may be referenced elsewhere. Video is separate again: it stores media in Bunny.net via infrastructure.video. See Filestorage and Infrastructure.

    Dev writes email to disk instead of sending it. The dev profile runs app.email.transport=log — registration/verification/OTP mail included. If "I registered but got no email" locally, open the newest file in target/mails (names are random UUIDs; grep the folder for the recipient) to find the OTP code or verification link. uat sends over SMTP and prod over SES. See Notification.

    Durable side effects go through the outbox, not @TransactionalEventListener(AFTER_COMMIT). Emails, refunds, coach payouts, blob deletion and several retries are enqueued in the business transaction (typically from a BEFORE_COMMIT listener calling a MANDATORY enqueue) and drained afterwards. Handlers must be idempotent. See Outbox.

    Row locks are NOWAIT + retry. Hot rows (coach profile, booking, wallet, drill, review…) are locked with findByIdForUpdate using NOWAIT and wrapped in PessimisticLockRetryer. Never write inside the retried lambda; PessimisticLockRetryerCallSiteAuditTest pins the number of call sites, so adding one means updating it. See Database.

    Mind the ID spaces. Booking.playerId is a PlayerProfile primary key, not a User id; resolve the human via PlayerProfile.userId / parentId. A child's GDPR request carries the parent's user_id plus a player_id scope.

    booking vs. session — booking owns scheduling and the booking lifecycle; session owns training content. They are coupled in both directions: booking reads session's drill/session repositories and DrillUsagePolicy; session listens to BookingStatusChangedEvent and uses BookingQueryService for the template-deploy picker.

    Session-pack credits live in payment, not booking. Booking's old parallel SessionPackService/session_packs_purchased system is gone. payment.service.PackSessionService and payment.repo.SessionPackPurchase are the only credit system; booking still declares pack lifecycle events in booking.contract, which payment publishes.

    Migrations were rebaselined. V02–V137 were squashed into V138 (schema) and V139 (seed data); new migrations continue from there (currently up to V175). Old migration numbers cited in commits or comments exist only in git history. See Database.

    Background work is centrally catalogued. 41 @Scheduled methods run across 12 platform modules plus infrastructure; 32 are ShedLock-guarded and the other 9 are safe per instance by design (per-node state or SKIP LOCKED claims). Start at Scheduled Jobs.

    Email links are hash-routed. The frontend uses hash-mode routing, so backend links into the app must be built with FrontendLinkBuilder (<frontendUrl>/#/...), never by string concatenation.
