    CI Guards: tests that will fail your PR

    The CI jobs, and every convention, audit, lint and parity test in the repo: what each protects, what usually trips it, what the failure looks like, how to fix it and how to run it alone. Ordered by how likely a newcomer is to hit it.

    What actually blocks a merge

    master is protected by the NoDirectPush ruleset, versioned in .github/rulesets/no-direct-push.json (re-applied by the manual apply-branch-ruleset.yml workflow): no direct push, no force-push, a PR is required, and the required status checks are build, docker-image and frontend-quality (all from pr-build.yml).

    frontend-quality (Prettier + ESLint) is a required check. It runs on every PR (backend-only ones too), and on master ci.yml's build-and-push has needs: [test, frontend-quality], so it also gates the image publish. Its log names every unformatted file (fix: npx prettier --write <files> from src/frontend) and every ESLint finding as file:line rule (most fix with npx eslint --fix <files>). The Vitest suite (frontend-unit-tests.yml) is opt-in and never required — a red i18n spec does not block a merge, which is exactly why it is easy to merge one.

    Docs-only PRs: the no-build label

    A PR that only changes documentation can skip the three required jobs. Open it with the label (gh pr create --label no-build). pr-build.yml's classify job runs .github/scripts/classify-no-build.sh, and when it answers skip=true the build, docker-image and frontend-quality jobs are skipped, which GitHub counts as passing. docs-check.yml still runs for docs/dev-docs/** changes.

    • The label is a request, not a bypass. It is honoured only when every changed file is under docs/ or _bmad-output/, or is a *.md at the repository root. Anything else, and docs/deployment/monitoring.md (read by AlertDocumentationParityTest), gets the full build with a warning annotation. If a test starts reading another doc, add it to the script's NEEDS_BUILD pattern.
    • Every failure path builds. No label, an unreadable label list, a diff that can't be computed, or a failed classify job all leave the three jobs running (!cancelled() in their if:).
    • Adding the label later: labels are read from the API, so re-run the workflow (gh run rerun <id>) or push a commit. There is deliberately no labeled trigger: a run fired by an unrelated label could overwrite a code PR's check results.
    • The merge to master still runs ci.yml in full (tests, image publish).

    Before you push: the cheap ones

    The *Test guards run in the surefire phase with no Spring context and no container, in seconds. Most of this page is covered by:

    # backend guards (from the repo root; drop -o on the very first run)
mvn -o test -DskipFrontend -Dtest='IntegrationTestConventionTest,MigrationConventionLintTest,PessimisticLockRetryerCallSiteAuditTest,NativeModifyingVersionAuditTest,MessageBundleParityTest,MessageCodeBaseBundleCompletenessTest,EmailTemplateSubjectKeyParityTest,EmailTemplateFileParityTest,AppEndpointsConventionTest,AsyncExecutorQualifierTest'

# frontend gates (from src/frontend, after npm ci)
npx prettier --check "**/*.{js,vue,scss,json}" --ignore-path ../../.gitignore
NODE_ENV=production npx eslint .
npx vitest run src/i18n/__tests__

    Reading failures: backend guards are AssertJ assertions whose .as(…) text is the explanation, so the shape is always java.lang.AssertionError: [<why this guard exists and what to do>] followed by Expecting empty but was: [<offenders>] or Expected size: N but was: M in: [<items>]. Read the bracketed text first; it usually names the fix.

    1. Prettier gate frontend-quality

    • Protects: the Prettier mandate for .js/.vue/.scss/.json under src/frontend (config src/frontend/.prettierrc.json: no semicolons, single quotes, width 100). Before skillars-deferred-92 gated it, 130 of ~150 files had drifted.
    • Trips it: any hand-edited frontend file you didn't run Prettier on, including package.json, eslint.config.js, and locale files. Not .html/.md.
    • Looks like: [warn] src/pages/Foo.vue lines, then [warn] Code style issues found in N files. Run Prettier with --write to fix.
    • Fix: cd src/frontend && npm run format, which runs the CI glob with --write: prettier --write "**/*.{js,vue,scss,json}" --ignore-path ../../.gitignore.
    • Run alone: the same command with --check.

    2. ESLint frontend-quality

    • Protects: src/frontend/eslint.config.js — Quasar + eslint-plugin-vue flat/essential, plus vue/no-bare-strings-in-template (user-visible text that never reached i18n, including q-* label/hint/placeholder/no-data-label/ error-message props) and no-debugger (error only when NODE_ENV=production, which CI sets).
    • Trips it: a literal string in a template or a q-btn label="Save"; a leftover debugger; unused variables/imports.
    • Looks like: path:line:col error … vue/no-bare-strings-in-template (rule id at the end of each line).
    • Fix: move the text to src/frontend/src/i18n/{en-US,de-DE,fr-FR}/index.js and use t('…')/$t('…'). Only genuinely untranslatable tokens (brand, symbols) go in the rule's allowlist. The rule cannot see strings inside <script> — Notify.create({ message: '…' }) still needs t() by convention.
    • Run alone: cd src/frontend && NODE_ENV=production npx eslint .

    3. Frontend i18n specs frontend-unit-tests

    Both live in src/frontend/src/i18n/__tests__/. They exist because the Vitest setup (src/frontend/test/vitest/setup-file.js) installs an empty catalogue, so every other spec renders and asserts raw keys and would pass with a typo.

    • localeKeyParitySpec.js — en-US, de-DE and fr-FR have identical key sets (skillars-deferred-155). Trips: adding a key to one locale. Looks like: de-DE has no keys missing relative to en-US failing with expected [ 'admin.finance.title' ] to deeply equal []. Fix: add the key to the other two files.
    • i18nTemplateKeyResolutionSpec.js — the most-edited guard in the repo (14 commits since September). Statically scans every .vue/.js under src/ for $t(/$te(/t(/ i18n.global.t( and asserts each literal key is a real en-US leaf (skillars-deferred-156). Four tests:
      1. every statically-resolved key exists — output src/…/Foo.vue:42 -> "admin.foo.titel". Fix the key or add it.
      2. every dynamic call site is recorded — a template literal, concatenation or variable key not in DYNAMIC_KEY_CALL_SITES. Add { at: 'src/…/Foo.vue:<line>', reason: '…' }.
      3. no translation call is wrapped across lines — Prettier sometimes splits a long t( call; the line-based scan cannot read it. Shorten the call (extract the params to a variable) so it fits on one line.
      4. every exception-list entry is still live — the list is keyed by file:line, so adding or removing a line above a listed call breaks it. Update the line numbers in the same change.
    • Run alone: cd src/frontend && npx vitest run src/i18n/__tests__.

    The job runs only when your PR touches src/frontend/** (or carries the frontend-tests label) and is not a required check — so check its result yourself before merging. Backend error keys are looked up as frontend i18n keys too, so a backend PR that introduces a new errorKey shown in the UI should add the frontend key and label the PR.

    4. IntegrationTestConventionTest build · unit phase

    • Where: src/test/java/com/softropic/skillars/config/IntegrationTestConventionTest.java. Reads compiled classes in target/test-classes reflectively; named *Test on purpose so it fails before any container starts.
    • Protects: Spring-context fragmentation. Hand-copied @SpringBootTest stacks once produced 37+ contexts out of 7 real configurations (each a full Boot startup, and then a Postgres + Redis pair). skillars-deferred-160 cut the failsafe JVM to 17.
    • Checks: every *IT extends AbstractIntegrationTest unless in ALLOWLIST (line 58); no *IT re-declares @SpringBootTest/@ActiveProfiles/@Import(TestConfig.class); EXPECTED_TEST_PROPERTY_SOURCE_COUNT = 4 (line 89); EXPECTED_DISTINCT_CONTEXT_KEYS = 14 (line 109); no slice test (@WebMvcTest etc.) is named *IT; no *IT class silently failed to load.
    • Trips it: a new @MockitoBean/@MockitoSpyBean field in an IT (the field name is part of the key — @MockitoBean FileStorageService storage and … fileStorageService are two contexts); a @TestPropertySource; a nested @TestConfiguration; naming a @WebMvcTest FooResourceIT.
    • Looks like: [Each distinct configuration below is a separate Spring ApplicationContext … Configurations (difference from AbstractIntegrationTest): 3 class(es): [AIT, BIT, CIT] field com.….FileStorageService fileStorageService [@…MockitoBean(…)] …] Expected size: 14 but was: 15 — the table lists every configuration and its classes, so find the one containing yours.
    • Fix: reuse an existing configuration (inherit a base spy, or match a peer's mock set with the same field names); rename a slice to *WebMvcTest. Only if a fork is genuinely needed, bump the constant with a // context-fork: reason. A LinkageError entry locally after a rename is a stale class file — mvn clean.
    • Run alone: mvn -o test -DskipFrontend -Dtest=IntegrationTestConventionTest

    5. Context-count gate build · pr-build only

    • Where: .github/scripts/assert-context-count.sh build.log 17, invoked from pr-build.yml's build step. Parses the last Spring test ApplicationContext cache statistics DEBUG line after the failsafe banner (logger enabled in src/test/resources/logback-test.xml).
    • Protects: the same thing as the test above, measured for real: missCount (contexts built) ≤ 17, the cache (maxSize = 32) not full, and no rebuilds beyond the one @DirtiesContext allowance (RateLimitingAspectIT). A full cache evicts and rebuilds, making the count depend on test order.
    • Trips it: a fork the reflective model cannot see, or a new @DirtiesContext. Also fails closed if the log has no failsafe banner or no statistics line (a crashed failsafe fork).
    • Looks like: FAIL: the suite built 18 Spring contexts, above the ceiling of 17., or FAIL: N contexts were built but only M are held (allowance: 1)., or FAIL: the Spring test-context cache is full (size = 32, maxSize = 32).
    • Fix: run IntegrationTestConventionTest to see the configurations; remove the fork or the @DirtiesContext. Raising the ceiling is a deliberate decision recorded in the script header and in pr-build.yml's comment.
    • Run alone: needs a full build log: mvn -B verify 2>&1 | tee build.log; .github/scripts/assert-context-count.sh build.log 17. In practice, rely on IntegrationTestConventionTest locally and let CI run this.

    6. PessimisticLockRetryerCallSiteAuditTest build · unit phase

    • Where: src/test/java/com/softropic/skillars/infrastructure/persistence/PessimisticLockRetryerCallSiteAuditTest.java. Comment- and string-aware source scan of src/main/java.
    • Protects: PessimisticLockRetryer.withBoundedRetry re-runs its supplier after rolling back to a savepoint, so a write inside it can execute twice (skillars-deferred-117; the scan's first run found DrillUploadService.initiateUpload/deleteVideo writing and publishing inside the lambda).     • Checks: exactly EXPECTED_CALL_SITE_COUNT (64 at the time of writing) .withBoundedRetry( sites; no .save(, .saveAndFlush(, .delete(, .deleteAll, publishEvent(, new …Event(, .send(, RestTemplate, .enqueue( inside a retried lambda; every file calling a lock method listed in NOWAIT_LOCK_METHODS_BY_REPOSITORY_TYPE also contains a .withBoundedRetry(; and every repository method annotated jakarta.persistence.lock.timeout = "0" is in that map (it once missed UserRepository, so its call sites were never scanned).     17. Trivy image scan docker-image

    • Protects: no CRITICAL/HIGH CVE in the runtime image (OS packages and jars).
    • Trips it: usually not your change — a new CVE published against an existing dependency or the Alpine base. A dependency bump can also introduce one.
    • Looks like: Trivy's table of findings (library, CVE id, severity, installed/fixed version) and a non-zero exit.
    • Fix: bump to the fixed version if one exists (the Dockerfile's apk upgrade layer is cache-busted every run, so published OS fixes are picked up automatically). If no fix exists anywhere, add the single CVE id to .trivyignore with a dated comment explaining why and when to remove it — that file's existing entries are the template; it needs owner sign-off. Never suppress a whole package.
    • Run alone: docker build -t skillars-app:local . && trivy image --severity CRITICAL,HIGH --ignorefile .trivyignore skillars-app:local
